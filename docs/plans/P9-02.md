### Batch 2 — SEQUENTIAL — `backend-feature` agent — BE-3

**Depends on:** Batch 1 complete + P9-01-BE-6 (Grant/Expire commands) merged.

`BillingGrantJob` — mirror `StreakSweepJob.cs` **exactly** in structure:

```
class BillingGrantJob
{
    [DisableConcurrentExecution(timeoutInSeconds: 60)]
    RunAsync(CancellationToken ct):
        using scope = scopeFactory.CreateAsyncScope()
        resolve BillingDbContext, BillingGrantOptions, IBillingSubscriptionContract, ISystemClock
        compute priorCycleId = last month's yyyyMM
        compute currentCycleId = this month's yyyyMM
        compute cycleEndUtc = end of current month (platform timezone from options)
        enumerate active children (paged 500 rows)
        per-child (try/catch fail-soft):
            expireKey = $"expire:{childId}:{priorCycleId}"
            grantKey  = $"grant:{childId}:{currentCycleId}"
            begin explicit transaction
            call ExpireGrantCommand(childId, expireKey)   // zeros GrantedBalance if any remains
            call GrantCreditCommand(childId, allotment[tier], cycleEndUtc, grantKey)
            commit
            catch unique-constraint violation (23505) → skip (idempotent)
        log summary: (granted, skipped-already, failed)
}
```

Key invariants:
- `ExpireGrant` touches only `GrantedBalance` — **never** `PurchasedBalance`.
- The idempotency key `grant:{childId}:{cycleId}` is different from `expire:{childId}:{priorCycleId}` — they are separate ledger rows.
- Both commands are wrapped in one per-child explicit transaction so the expire+grant pair is atomic.
- A DB unique-constraint violation on *either* key → skip the whole child (idempotent re-run safe).
- `[DisableConcurrentExecution]` prevents two Hangfire workers overlapping on the same job run.

**Gate after Batch 2:** `dotnet build` green; the job runs in Development mode and creates `Grant` + `Expire` ledger rows without concurrency errors; re-running creates zero new rows.

### Batch 4 — SEQUENTIAL — `security-auditor` agent (light gate)

**Depends on:** Batch 3 complete.

Audit focus:
- **No double-grant:** confirm the idempotency key `grant:{childId}:{cycleId}` is DB-enforced (P9-01 unique constraint) and the job catches the duplicate rather than 500-ing.
- **No claw-back of Purchased:** confirm `ExpireGrant` (the `Expire` command) zeroes only `GrantedBalance`, never reads/writes `PurchasedBalance`. A bug here destroys paid-for credits — treat as critical-equivalent.
- **Authorization:** the grant job is server-only (Hangfire). Confirm there is no public endpoint that can trigger a grant (attacker-triggered grant = free credits).
- **Active-only:** confirm cancelled/inactive children (once P9-05 exists) are not granted.

This is a **light gate** — no money moves in P9-02 beyond energy credits from the plan. Critical/High findings still block the reviewer.

### Batch 5 — SEQUENTIAL — `api-tester` agent

**Depends on:** Batch 4 complete.

5. Config-driven: change `FreeMonthlyGrant` in options → next job run grants the new amount.
6. Inactive child (stub returns child as inactive) → no grant row created.
