## How the `IPedagogicalTreeWriter` seam is sequenced (critical path)

1. **Define the contract first** (Batch 2a-0): the interface + DTOs land in `Shared.Contracts/Learning/` as a standalone step, immediately after the migration, **before either consumer or implementer is built**. It mirrors the existing request/response seams already in that folder (`IStudentMasterySummaryQuery` etc.) — established pattern, no new abstraction to approve.
2. **Both sides then build against the frozen interface in parallel within Lane 2a:** the `learning` implementation (`seam-impl`, owns `EnsureXAsync` + SkillKey idempotency + unique constraints) and the curriculum caller (`BE-5`, consumes returned node IDs to link chunks/provenance). Because the interface is fixed first, neither side blocks on the other's internals — only on the signature.
3. **It is synchronous request/response, NOT an `INotification`** — `IsolatedNotificationPublisher` swallows handler exceptions and returns nothing, which is wrong for a must-succeed write that must return node IDs. The seam is an awaited interface call (Q1 decision).
4. **Isolation preserved:** `Shared.Contracts` only; no project reference curriculum→learning. SkillKey ownership + idempotency stays inside `learning`. security-auditor (Batch 4) reviews the cross-module write authz on this seam specifically.
