## Lead decisions honoured

1. Scope is **verify + finish + doc-fix** — the Npgsql provider switch, per-module schemas, and containers are already complete.
2. Real remaining work maps to three work-items: R1 (Redis IDistributedCache), R2 (pgvector demo migration), R3 (smoke verification + doc-fix).
3. The five not-yet-existing module schemas (learning, assessment, gamification, analytics, curriculum) are deferred to their owning feature stories — NOT pre-created here.
4. pg17 compose image is accepted over the story's pg16 requirement.
5. The pgvector proof is a **disposable, clearly-named demo migration** (lead decision per OQ-5) — it proves capability without committing a premature permanent schema; it is reverted/dropped after verification.

## Execution batches

### Batch 1 — parallel (two agents, independent file sets)

Both agents start simultaneously after the lead dispatches. They touch different files with no overlap (see constraint note above).

**Agent: `backend-feature`** — tasks R1-a, R1-b, R1-c, R3-a

Files it modifies:
- `backend/src/Host/Learnexia.Host/Learnexia.Host.csproj` — add `<PackageReference Include="Microsoft.Extensions.Caching.StackExchangeRedis" />` (version from central props)
- `backend/src/Host/Learnexia.Host/Program.cs` — replace line 35 `AddDistributedMemoryCache()` with conditional block:
  ```csharp
  var redisCs = builder.Configuration.GetConnectionString("Redis");
  if (!string.IsNullOrWhiteSpace(redisCs))
      builder.Services.AddStackExchangeRedisCache(o => o.Configuration = redisCs);
  else
      builder.Services.AddDistributedMemoryCache(); // local dev / test fallback
  ```
- `backend/src/Host/Learnexia.Host/appsettings.json` — add `"Redis": ""` under `ConnectionStrings`
- `backend/src/Host/Learnexia.Host/appsettings.Development.json` — add `"Redis": ""` under `ConnectionStrings` with a comment (JSON doesn't support inline comments — use the key value `""` and note in the PR)
- `backend/src/Modules/Identity/Learnexia.Modules.Identity.Infrastructure/DependencyInjection.cs` — delete commented SQL Server block (lines 30-32 approx.)
- `tasks/Backend/Phase-1-Foundation/P1-06-BE.md` — update line 25 stale note ("current code runs on SQL Server") to state the migration is already complete; mark BE-1/BE-2/BE-3/BE-5 as done

**Agent: `db-migration`** — tasks R2-a, R2-b, R2-c

Files it modifies:
- `backend/Directory.Packages.props` — add two new `<PackageVersion>` entries:
  - `Pgvector` (check latest stable; recommend `0.3.x` compatible with .NET 10 / EF 10)
  - `Pgvector.EntityFrameworkCore` (same version family)
- `backend/src/Modules/Catalog/Learnexia.Modules.Catalog.Infrastructure/Learnexia.Modules.Catalog.Infrastructure.csproj` — add `<PackageReference Include="Pgvector.EntityFrameworkCore" />`
- `backend/src/Modules/Catalog/Learnexia.Modules.Catalog.Infrastructure/Persistence/CatalogDbContext.cs` — add `modelBuilder.HasPostgresExtension("vector")` in `OnModelCreating`; add `DbSet<EmbeddingDemo>` property
- `backend/src/Modules/Catalog/Learnexia.Modules.Catalog.Infrastructure/Persistence/Entities/EmbeddingDemo.cs` (new file) — demo entity with `Vector` property; mirror `CatalogDbContext`'s existing entity style. Mark with a prominent `// DEMO ONLY — disposable; remove before curriculum/RAG story` comment.
- Catalog's DI registration (`DependencyInjection.cs`) — add `.UseVector()` inside the `UseNpgsql(...)` options lambda
- Run `dotnet ef migrations add DEMO_PgvectorProof --project ... --startup-project src/Host/Learnexia.Host --context CatalogDbContext` to generate the migration file under the existing `Migrations/` folder

Migration naming convention: `DEMO_PgvectorProof` — the `DEMO_` prefix makes it trivially greppable for removal in the RAG/curriculum story. The migration must use the existing `MigrationsHistoryTable("__EFMigrationsHistory", CatalogDbContext.Schema)` pattern (already set in `CatalogDbContextFactory`; no change needed).

### Batch 2 — sequential (after Reviewer gate 1 passes)

**Agent: `db-migration`** — task R2-d (apply migration against compose Postgres)

Steps:
1. Ensure compose stack is up: `docker compose -f docker/docker-compose.yaml up -d postgres redis`
2. Apply the pgvector demo migration: `dotnet ef database update --project backend/src/Modules/Catalog/Learnexia.Modules.Catalog.Infrastructure --startup-project backend/src/Host/Learnexia.Host --context CatalogDbContext`
3. Confirm via psql or EF log that `CREATE EXTENSION IF NOT EXISTS vector` ran and the `catalog."EmbeddingDemos"` table has a `vector(1536)` column.
4. Run a quick round-trip insert/select of a `float[]` value through EF to confirm read-back.

**Agent: `backend-feature`** — task R3-b (smoke verification: full stack boot + Redis session check)

Steps:
1. With compose stack running (Postgres + Redis), start the API: `dotnet run --project backend/src/Host/Learnexia.Host` (with `ConnectionStrings__Redis=localhost:6379` in env or set in `appsettings.Development.json` for the smoke).
2. Confirm startup logs show `AddStackExchangeRedisCache` path taken (not in-memory).
3. Hit the Identity sign-in endpoint; confirm a session/refresh-token key appears in Redis: `docker exec learnexia-redis redis-cli KEYS *` should return at least one key.
4. Restart the API; confirm the same key is still retrievable (session survived restart — proves Redis persistence vs. in-memory).
5. Confirm all three module migrations applied cleanly (no pending migrations at startup).

Note: the two Batch-2 agents can run in parallel once Reviewer gate 1 passes (R2-d and R3-b are independent), but R3-b depends on the Redis wiring from Batch 1 being merged/present and the compose stack being up. Treat them as parallel-within-Batch-2.

**Light security-auditor pass before the final reviewer gate.** Redis now holds session and refresh-token data (sensitive child/user data per product context). The auditor should confirm:
- No Redis connection string or password is hard-coded in source (compose env injects it; appsettings value is empty string).
- Redis endpoint is not publicly exposed in the compose stack (internal network only; port 6379 should not be mapped to host in production compose overrides).
- No session key contents are written to application logs.
- The `EnableLegacyTimestampBehavior` switch is noted as known tech-debt (out of P1-06 scope; flag for follow-up).

This pass is **not a blocker** per the brief's "light/optional" guidance, but any Critical or High finding blocks the committer.

## Blockers / prerequisites

1. **Pgvector package version** — `Pgvector` and `Pgvector.EntityFrameworkCore` are not yet in `Directory.Packages.props`. The `db-migration` agent must determine the correct versions compatible with EF Core 10.0.8 + .NET 10 before generating the migration. As of May 2026, check NuGet for the latest `pgvector` NuGet package (the project is `pgvector-dotnet`). If a stable release compatible with EF 10 does not exist, the agent should flag this to the lead immediately — the pgvector proof may need to be implemented using raw SQL (`CREATE EXTENSION` + `ALTER TABLE ... ADD COLUMN embedding vector(1536)`) rather than the EF Fluent API, and the Pgvector NuGet tasks become blocked.

2. **Compose stack must be running** for Batch 2. The lead or the implementing agents must ensure `docker compose up -d postgres redis` before Batch-2 steps execute. If Docker Desktop is not running or the compose file has changed, Batch 2 cannot proceed.

3. **Shared-file serialization (Directory.Packages.props)** — per `docs/dev/PARALLELISM.md`, concurrent edits to this file are forbidden. In Batch 1, only `db-migration` touches this file (Redis package is already centralized; `backend-feature` does NOT edit it). This is correctly partitioned — no lead action needed beyond confirming the agents understand the constraint.

4. **No unresolved open questions block the plan.** OQ-1 (stale task wording) is the lead's confirmed scope; OQ-2 (deferred schemas) is lead-decided; OQ-3 (pg17 vs pg16) is lead-accepted; OQ-4 (Catalog/Notifications auto-migration) is out of P1-06 scope; OQ-5 (disposable demo migration) is lead-decided.
