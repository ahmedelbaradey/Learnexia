> Targets (NFR-1): core API **p95 < 500 ms**; AI **< 4 s**. Branch: `feat/P6-01-performance-targets`.

## Locked decisions (lead, 2026-06-21) — resolving the brief's OQs
- **Harness = NBomber**, new project `backend/tests/Learnexia.PerfTests` (package centrally versioned, latest stable).
- **Baseline driver = in-process `WebApplicationFactory` + Testcontainers PG** (reuse `LearnexiaWebAppFactory` from `Learnexia.IntegrationTests` — reference that project, or co-locate). Repeatable, the factory **neutralizes the rate limiter** (avoids the 429 gotcha), real Postgres. **Also document the live-Kestrel run procedure** (`http://localhost:5080`, `ConnectionStrings__Redis` set, rate-limit profile raised) for devops representativeness.
- **Concurrency (directional default):** ~30 concurrent copies, 60 s, 10 s warmup, per core scenario. Documented as directional, not a prod SLA.
- **Seed:** Dev curriculum seed (auto) + a **warmup** that registers parent→child→student via API and generates a modest volume of attempts/answers to exercise the hot loop. **Caveat (document):** Dev data has no large attempt/answer volume, so data-volume/index hotspots won't surface here — that needs a staging seeded dataset (devops).
- **Redis:** baseline runs on the in-memory distributed-cache fallback → gamification numbers are **code-path** measurements, not Redis-hot-path-representative (note in the report).
- **AI <4 s:** NOT produced here (real gateway, no keys → fail-closed). Local AI scenario measures pipeline overhead only; the live <4 s is a **documented devops measurement** (mirror P6-02 EvalLive direct-construction + skip-gate).

## Batches
- **Batch 1 — BE-1 harness:** `Learnexia.PerfTests` (NBomber, references the IntegrationTests factory), config-driven base URL (in-process factory client by default; `PERF_BASE_URL` for Kestrel), auth helper (register-parent→add-child→sign-in to mint student + parent + admin JWTs), `run-perf` script + README, NBomber → `docs/perf/` report sink. Add `NBomber` to `Directory.Packages.props`.
- **Batch 2 — BE-2/BE-3 scenarios:** core-API scenarios (sign-in, StartAttempt `POST /api/Learning/Quizzes/{lessonId}/Attempt`, SubmitAnswer `POST /api/Learning/Quizzes/{attemptId}/Answers`, Learning reads [Subjects/ForGrade, {id}/Lessons, {id}/SkillTree, Dashboard], gamification [Profile, Leagues/Me], parent P5-08 reads) with **p95 < 500 ms** assertions; AI scenario (Explain/Hint overhead, fake/dormant gateway) + the live-<4s devops note.
- **Batch 3 — BE-4 baseline run + report:** run in-process, write `docs/perf/P6-01-baseline.md` (p50/p95/p99 + throughput + error rate per scenario, PASS/FAIL vs 500 ms, ranked hotspots, env caveats).
- **Batch 4 — BE-5 quick-win fixes:** surgical fixes for over-target endpoints (index / N+1 / over-fetch / `AsNoTracking`), re-measure; document the rest. Each fix must keep existing suites green.
- **Batch 5 — reviewer → committer → PR → merge** (HANDOFF entry in the same PR).

## Gates / notes
- Harness must run repeatably (`dotnet run`/test); thresholds match NFR-1; BE-5 fixes don't regress existing integration suites.
- No security-auditor (perf tooling, no auth/child-data/secret surface). No new module. A BE-5 fix that needs an index → a tiny migration (flag it).
- Honesty: local baseline = directional (catches egregious hotspots + validates the harness); authoritative pass/fail + AI<4s = devops staging run.
