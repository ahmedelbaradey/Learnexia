## Lead Decisions (plan is locked to these)

1. **User fields:** add `Grade` (int?) + `Age` (int?) net-new. Reuse existing `PreferredLanguage` for language (no new column). Reuse `Nationality` field for country. Do NOT add a separate `Country` column — `Nationality` (varchar 100, nullable, already exists in entity + DB) covers country for children. No new language column.
2. **Endpoint:** `POST api/Users/Parent/Add-Child` on `ParentController` (Parent-gated). `ParentController.cs` is P1-03's exclusively owned file this wave.
3. **Credential:** parent sets child's initial password in the request body; same password policy as RegisterParent.
4. **Auto-link:** call `ILinkParentStudentService.LinkAsync(parentId, childId)` after `CreateAsync` commits.
5. **Multiple children:** single-child-per-call; idempotent on email (duplicate = specific 400, no account created). FE loops.
6. **Response:** new `AddedChildResponse { Id, FullName, Email, Grade, Language, Country }` — does NOT change `LinkedChildResponse`.
7. **Publish:** `UserRegisteredIntegrationEvent` best-effort after commit (parity with RegisterParent/AddUser).
8. **No designer, no P1-05 conflict:** this story exclusively owns `ParentController.cs`; must not touch `Program.cs`, `IdentityModule.cs`, `Directory.Packages.props`, or `DependencyInjection.cs`.

### Batch 2 — backend-feature (sequential, after Batch 1)

**Agent:** `backend-feature`
**Tasks:** P1-03-BE-2, BE-3, BE-4, BE-5, BE-6, BE-7 (implement as one cohesive unit)

**Folder:** `Features/Family/Commands/AddChild/` (new subfolder, mirrors LinkChild).

**What to produce:**

1. **`AddChildCommand.cs`** at `Features/Family/Commands/AddChild/AddChildCommand.cs`:
   - `public record AddChildCommand : ICommand<BaseResponse<AddedChildResponse>>`
   - Fields: `ChildName (string)`, `LoginEmail (string)`, `Grade (int)`, `Language (string)` — one of "ar"/"en", `Country (string)`, `Password (string)`.
   - **No** `ParentId` field, **no** `Role` field. These are server-assigned.

2. **`AddedChildResponse.cs`** at `Features/Family/Commands/AddChild/AddedChildResponse.cs`:
   - `public record AddedChildResponse { Id, FullName, Email, Grade, Language, Country }`
   - Kept separate from `LinkedChildResponse` — do not modify `LinkedChildResponse`.

3. **`AddChildCommandHandler.cs`** at `Features/Family/Commands/AddChild/AddChildCommandHandler.cs`:
   - Inherits `BaseResponseHandler`, implements `ICommandHandler<AddChildCommand, BaseResponse<AddedChildResponse>>`.
   - Constructor injects: `IIdentityServiceManager`, `ICurrentUserService`, `IMapper`, `IStringLocalizer<SharedResources>`, `ILoggerManager`, `IPublisher`.
   - Handler logic (in order):
     1. Resolve `parentId = _currentUserService.UserId`; if null → `Unauthorized<AddedChildResponse>(...)`.
     2. Pre-check `FindByEmailAsync(request.LoginEmail)` → if found → `BadRequest<AddedChildResponse>(_localizer[SharedResourcesKey.ProfileDuplicateEmail])`.
     3. Build `new User { UserName = request.LoginEmail, Email = request.LoginEmail, FullName = request.ChildName, PreferredLanguage = NormalizeLang(request.Language), Nationality = request.Country, Grade = request.Grade, RegistrationIsCompleted = false, CreatedAt = DateTime.UtcNow, CreatedBy = parentId }`. Do NOT set `Age` (not in the Add-Child request; nullable, so null is fine).
     4. `CreateAsync(user, request.Password)` → on failure, shape error as `BadRequest` with `SystemErrorSavingData` message (do NOT echo raw Identity errors to client).
     5. `AddToRoleAsync(user, Roles.Student.ToString())` — hard-coded, never from request.
     6. `LinkParentStudentService.LinkAsync(parentId.Value, user.Id, cancellationToken)` — call after CreateAsync commits.
     7. `PublishUserRegisteredEventAsync(user, cancellationToken)` — best-effort, same pattern as RegisterParentCommandHandler.
     8. Return `Success(_mapper.Map<AddedChildResponse>(user))`.
   - `NormalizeLang`: maps "ar" → "ar-EG", "en" → "en-US"; if neither (defensive, validator guards this) fall back to "ar-EG".
   - Wrap entire body in try/catch → `ServerError<AddedChildResponse>(_localizer[SharedResourcesKey.SystemErrorSavingData])`.

4. **`AddChildCommandValidator.cs`** at `Features/Family/Validation/AddChildCommandValidator.cs`:
   - `AbstractValidator<AddChildCommand>`, inject `IStringLocalizer<SharedResources>`.
   - Rules:
     - `ChildName`: NotEmpty, `ProfileRequiredField`.
     - `LoginEmail`: NotEmpty + `.EmailAddress()`, using `ProfileRequiredField` / `ProfileInvalidEmailFormat`.
     - `Grade`: `InclusiveBetween(1, 6)` — add key `GradeOutOfRange` to `SharedResourcesKey` if no existing key covers it; use generic `ProfileRequiredField` as fallback if the lead prefers no new key.
     - `Language`: Must(x => x == "ar" || x == "en") — add key `InvalidLanguageCode` to `SharedResourcesKey` if no existing key covers it; `InvalidCultureCode` (already exists) may serve as a fallback.
     - `Country`: NotEmpty, `ProfileRequiredField`.
     - `Password`: NotEmpty + MinimumLength(8) (matching the RegisterParent validator pattern), `PasswordMinimumLength` (already exists).
   - **Do NOT** do a `FindByEmailAsync` in the validator (handler owns uniqueness to avoid enumerating at 422 vs 400 distinction; this is also the pattern in `LinkChildCommandValidator`).

5. **`FamilyProfile.cs`** extension — add a second `CreateMap` inside the existing `FamilyProfile` constructor:
   - `CreateMap<User, AddedChildResponse>()` with:
     - `.ForMember(dest => dest.Email, opt => opt.MapFrom(src => src.Email ?? string.Empty))`
     - `.ForMember(dest => dest.Language, opt => opt.MapFrom(src => src.PreferredLanguage))`
     - `.ForMember(dest => dest.Country, opt => opt.MapFrom(src => src.Nationality ?? string.Empty))`
   - Do NOT modify the existing `CreateMap<User, LinkedChildResponse>()`.

6. **`ParentController.cs`** — add one new action:
   ```csharp
   [HttpPost("Add-Child")]
   [ProducesResponseType(typeof(BaseResponse<AddedChildResponse>), StatusCodes.Status200OK)]
   public async Task<IActionResult> AddChild([FromBody] AddChildCommand command)
       => NewResult(await Mediator.Send(command));
   ```
   - Add `using Learnexia.Modules.Identity.Application.Features.Family.Commands.AddChild;` to the using block.
   - Do NOT change the class-level `[Authorize]`, route, or any other existing actions.

7. **`SharedResourcesKey.cs`** — add new keys if needed for grade-range and language validation messages. Candidate additions (add only what is used in the validator):
   - `GradeOutOfRange` — "Grade must be between 1 and 6".
   - `InvalidLanguageCode` — already have `InvalidCultureCode`; reuse it OR add a distinct key if the lead prefers clearer messaging.
   Add corresponding entries to `SharedResources.resx`, `SharedResources.ar-EG.resx`, `SharedResources.en-US.resx`.

### Batch 4 — security-auditor (sequential, after Batch 3)

**Agent:** `security-auditor`
**Trigger:** api-tester results + code diff from Batch 2.

**Focus areas** (mandatory — creates child/minor accounts):
1. **No privilege escalation:** `AddChildCommand` must have no `Role` or `ParentId` field; `Student` role assignment must be server-side only; verify no client-controlled path to mint Parent/Admin.
2. **Parent-only gating:** `ParentController` is `[Authorize(Roles = "Parent,Admin,SuperAdmin")]`; confirm 403 for other roles (api-tester case f covers this).
3. **JWT-only parent resolution:** `parentId` comes from `ICurrentUserService.UserId` (JWT claim); reject any handler path that reads parentId from the request.
4. **Credential handling:** `Password` field in `AddChildCommand` must not be logged at any level; no raw Identity error echoed to client (which could include password-related detail).
5. **Duplicate-email response:** the specific `ProfileDuplicateEmail` message for Add-Child is acceptable (authenticated parent action, not anonymous enumeration); auditor should confirm it does not leak cross-family email existence (i.e., the same error fires whether the email belongs to a sibling, a foreign child, or a parent — no family-scoping on the 400).
6. **Minor data:** `Grade`, `Age`, `Nationality` of minors stored in `identity.AspNetUsers` — confirm fields are nullable (no accidental not-null constraint introduced by migration) and that the `UserEntityConfig` additions carry no CHECK constraint on grade (app-layer validation only, per CONVENTIONS).
7. **IDOR guard:** after successful Add-Child, verify `LinkAsync` only links to the JWT-resolved parentId, never to a parentId from the request.

**Critical/High findings block the reviewer gate.** Medium/Low findings are flagged as follow-up issues.
