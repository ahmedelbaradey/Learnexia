## Lead decisions applied

1. **FE-only story.** No new backend entities, no migrations, no new endpoints, no db-migration or backend-feature batches. P1-10-BE tasks (BE-1..BE-4) are verification-only: confirm the existing seeded `superadmin` works and `AdminOnly` still denies non-admins. Defer seed of a dedicated `admin` user to follow-up debt.
2. **Admin role gate via JWT-claim decode from profile.** After sign-in the FE calls `GET /api/Users/UserManagement/GetUserProfile?userId={userId}` to read `Roles: string[]` (PascalCase `Admin`/`SuperAdmin`). The gate is **case-insensitive** (`ROLES` constants are lowercase, JWT roles are PascalCase). No call to the AdminOnly `GetUserProfile`-under-policy variant; no dependency on P1-09's `Me` endpoint.
3. **Token storage:** `createWebTokenStorage()` (sessionStorage) from `packages/shared`. Route guard is client-side only (sessionStorage is not readable in Next.js edge middleware). HttpOnly-cookie hardening deferred and noted as debt.
4. **Scope:** `apps/admin-dashboard` is currently a bare stub (`package.json` only). The entire Next.js 15 App Router shell is built here. Auth + shell only; no admin feature logic.
5. **No changes to `packages/*`.** Consume `@learnexia/api-client`, `@learnexia/shared`, `@learnexia/design-system`, `@learnexia/ui` as-is. Any admin-local helper lives inside `apps/admin-dashboard`.
6. **Designer stage REQUIRED** (admin/desktop-first UI surface) before the frontend batch.
7. **Security-auditor REQUIRED** (admin auth, route protection, token storage, seed credentials) before the reviewer gate.
8. **No api-tester batch** (no new/changed endpoints; existing P1-02/P1-05 suites cover the API).

Implementation notes for the frontend agent:

**FE-2 (Login page):**
- Zod schema: `{ userName: z.string().min(1), password: z.string().min(1) }` — no registration fields.
- On `useSignIn` success: `authStore.setTokens({ accessToken, refreshToken: data.refreshToken?.tokenString ?? '' })`, then trigger `useUserProfile(data.userId)` (can be an imperative `queryClient.fetchQuery` since this is inside a mutation callback, not during render). Extract `Roles` from profile. Compare case-insensitively: `roles.some(r => r.toLowerCase() === 'admin' || r.toLowerCase() === 'superadmin')`. If non-admin: call `authStore.signOut()`, display "not authorized" message — do NOT redirect to shell.
- `authStore.setUser({ id: data.userId, roles: profile.roles.map(r => r.toLowerCase() as Role), ... })`. Note: store's `CurrentUser.roles` is typed as `Role[]` (lowercase); normalize on set.
- Redirect to `/(admin)/dashboard` (or `/`) on success.
- No `/register` or `/signup` route anywhere in the app.

**FE-3 (Dashboard shell):**
- `app/(admin)/layout.tsx` is a server component wrapping a client `AdminShell` component.
- `AdminShell` renders: side nav (Curriculum placeholder, Content placeholder — non-functional `<a>` or disabled `Button`), top bar (display `authStore.user?.fullName ?? authStore.user?.userName`, sign-out button that calls `useSignOut()`), and `{children}`.
- Add `app/(admin)/dashboard/page.tsx` as the landing page (simple placeholder heading "Welcome" or equivalent).

**FE-4 (Route guard):**
- `useAdminGuard`: reads `useAuthStore(s => s.status)` and `useAuthStore(s => s.user)`. If `status === 'unknown'` — render loading skeleton (hydration in progress). If `status === 'signed-out'` or user has no admin/superadmin role — `router.replace('/login')`. If `status === 'signed-in'` with valid roles — render children.
- Applied in `app/(admin)/layout.tsx` client component.
- `middleware.ts` can be a no-op stub (or absent) — document the client-only guard limitation as an inline comment + a `TODO: HttpOnly-cookie-auth needed for true server-side protection` note.

**FE-5 (Sign-out):**
- `useSignOut()`: returns an async callback. Calls `client.post('/api/Users/Authentication/Sign-Out', { skipAuth: false })` (fire-and-forget on network error — still sign out locally). Then `authStore.signOut()`. Then `router.replace('/login')`.
- Consumes `useApiClient()` from `@learnexia/api-client` (already exists).

**Reviewer gate after Batch 3:** `reviewer` checks all AC #1–#7 + #9 are covered, no registration route exists, role casing is handled, design spec is reflected, no `packages/*` edits crept in.

### Batch 4 — Security audit

**Sequential — after Batch 3 passes reviewer.**

| Agent | Scope |
|---|---|
| `security-auditor` | Admin auth flow, client-side route guard limitations (no server-side protection), sessionStorage token storage (XSS surface), no public admin registration UI or route, seed credentials (`123Pa$$word!`) documented as must-not-reach-production, role-casing comparison correctness, no token values logged, HTTPS-only posture of admin app, absence of admin self-register path in the route tree. |

Audit checklist the `security-auditor` must verify:
1. No route at `/register`, `/signup`, `/admin/register`, or any creation path for admin accounts.
2. `skipAuth: true` is only set on the sign-in call; no other endpoint bypasses auth.
3. `sessionStorage` is the token store — document as accepted risk (XSS exposure window bounded to tab lifetime); no `localStorage` use anywhere.
4. Token values never appear in `console.*`, error messages, or URL params.
5. `useAdminGuard` correctly handles the `'unknown'` (hydrating) state — no protected content flash.
6. Role comparison is case-insensitive — no path that a parent/student could slip through.
7. Seed password `123Pa$$word!` is flagged — must be rotated before production; not exposed in any FE code.
8. `NEXT_PUBLIC_API_URL` is the only secret-adjacent env var; no access tokens in env.
9. CSP / security headers — not required in this story but flag absence as follow-up if none are present in `next.config.ts`.
10. AC #8 (backend AdminOnly 403) confirmed from BE-VERIFY result.

**Critical/High findings block the reviewer gate.**
