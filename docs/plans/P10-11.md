## Execution batches

### Batch 1 — SEQUENTIAL — `db-migration` agent — BE-1

**Depends on:** P10-01 merged (billing schema exists).
**Agent:** `db-migration`

`BillingConfigVersion` entity (`FullAuditedEntity`, effective-dated):

Columns: `Id` (int PK), `EffectiveFromUtc` (timestamptz, NOT NULL), `PlanPrice` (int, EGP), `FreeMonthlyGrant` (int), `PremiumMonthlyGrant` (int), `FreeDailyCap` (int), `PremiumDailyCap` (int), `PackSize` (int), `PackPrice` (int), `HintCost` (int), `ExplainMistakeCost` (int), `DeepExplanationCost` (int), `PracticeGenerationCost` (int), `Note` (varchar(500) nullable), `CreatedBy` (int), `CreatedAtUtc` (timestamptz).

EF config: `ToTable("BillingConfigVersions", BillingSchema.Name)`; index on `EffectiveFromUtc` (for the "latest ≤ now" lookup — `HasIndex(x => x.EffectiveFromUtc).HasDatabaseName("IX_BillingConfigVersions_EffectiveFromUtc")`); `CreatedBy`/`CreatedAtUtc` from `FullAuditedEntity` (no mutation).

Seed an **initial version** with the story's defaults as part of the migration's `Up()` or via a `BillingConfigSeeder` that runs in `InitializeAsync`. These are the **default** config values — all are admin-tunable without a deploy. **Grant sizes were recalibrated to the revised credit value (1 credit ≈ 1¢; hint = 1 credit) — they reflect the new economy, not the old.**

| Field | Default value |
|---|---|
| PlanPrice | 199 |
| FreeMonthlyGrant | 100 |
| PremiumMonthlyGrant | 5000 |
| FreeDailyCap | 10 |
| PremiumDailyCap | 250 |
| PackSize | 1000 |
| PackPrice | (confirm) |
| HintCost | 1 |
| ExplainMistakeCost | 3 |
| DeepExplanationCost | 5 |
| PracticeGenerationCost | 5 |
| EffectiveFromUtc | epoch (or `DateTime.UnixEpoch`) — always effective |

Migration name: `AddBillingConfig`.

**Gate after Batch 1:** `dotnet build` green; migration applies; `billing.BillingConfigVersions` table appears with the seeded initial row.

### Batch 2 — PARALLEL — `backend-feature` agent — BE-2 ‖ BE-5

**Depends on:** Batch 1 complete.
**Mode:** BE-2 and BE-5 are independent; run in parallel.

**BE-2 — `IBillingConfigReader` + `BillingConfigReader`:**

Interface in `Shared.Contracts/Billing/`:
```csharp
public interface IBillingConfigReader
{
    int GetMonthlyGrant(PlanTier tier);
    int GetActionCost(AiTaskKind actionKind);
    int GetDailyCap(PlanTier tier);
    (int PackSize, int PackPrice) GetPackSizePrice();
    int GetPlanPrice();
}
```

`BillingConfigReader` in `Billing.Infrastructure/Config/`:
- Resolves `BillingConfigVersions.OrderByDescending(v => v.EffectiveFromUtc).First(v => v.EffectiveFromUtc <= utcNow)`.
- Optionally cache the current version in-memory (`IMemoryCache`) with invalidation when `UpdateBillingConfigCommand` runs (OQ-8). If time-pressured, skip the cache initially — read from DB on each call (low-frequency at admin level).
- `PlanTier` enum: `Free`, `Premium`. `AiTaskKind` enum (from `Shared.Contracts/Ai/`).

**BE-5 — `GetBillingConfigQuery` (admin read):**

Returns `BillingConfigDto` with `CurrentValues` (the latest effective config) + `VersionHistory: List<BillingConfigVersionHistoryDto>` (all versions, sorted newest-first, each with `EffectiveFromUtc`, `ChangedBy`, `ChangedAtUtc`, all config fields for old→new comparison by the FE).

`[Authorize("Admin")]`. `ILoggerManager` injected. No `ValidationBehavior` (query, rule 4).

**Gate after Batch 2:** `dotnet build` green; `IBillingConfigReader` is resolvable; `GetBillingConfigQuery` returns the seeded default values.

### Batch 3 — SEQUENTIAL — `backend-feature` agent — BE-3 + BE-4 + BE-6

**Depends on:** Batch 2 complete (reader seam needed for BE-3 auditing).
**Agent:** `backend-feature`

**BE-3 — `UpdateBillingConfigCommand`:**

```csharp
public record UpdateBillingConfigCommand(
    int PlanPrice,
    int FreeMonthlyGrant, int PremiumMonthlyGrant,
    int FreeDailyCap, int PremiumDailyCap,
    int PackSize, int PackPrice,
    int HintCost, int ExplainMistakeCost, int DeepExplanationCost, int PracticeGenerationCost,
    string? Note
) : ICommand<BaseResponse<bool>>;
```

Handler:
1. Validate (BE-4 runs automatically via `ValidationBehavior`).
2. Resolve the current effective config (for the old-values side of the audit record).
3. Create a new `BillingConfigVersion` with `EffectiveFromUtc = UtcNow` and the new payload.
4. Insert the version.
5. Write audit record to `Moderation.AuditLog` via `IAuditLogWriter.WriteAsync(entityType: "BillingConfig", action: "Update", oldValues: ..., newValues: ..., changedBy: currentUserId)`.
6. Commit.
7. Invalidate the in-memory cache (if OQ-8 is implemented).

`[Authorize("Admin")]`. `ILoggerManager`. Explicit transaction (old-values read + new-version insert + audit write are atomic).

**Cross-module audit seam:** `IAuditLogWriter` must live in `Shared.Contracts/Moderation/` (or be the existing P7 seam — confirm with the P7 implementer whether such a seam already exists; if not, declare it). `Billing` must not reference `Moderation.*` projects directly.

**BE-4 — FluentValidation (`UpdateBillingConfigValidator`):**

Runs via `ValidationBehavior` (command is `ICommand<>` per rule 4):
- All int costs/grants/caps: `GreaterThanOrEqualTo(0)`.
- `PlanPrice`, `PackSize`, `PackPrice`: `GreaterThan(0)`.
- `FreeDailyCap <= FreeMonthlyGrant` (cross-field: `Must(...)` with `.WithMessage("Free daily cap must not exceed the monthly grant.")`).
- `PremiumDailyCap <= PremiumMonthlyGrant` (cross-field, same).
- Any additional rules from OQ-5.

**BE-6 — `BillingConfigController` + DI:**

```csharp
[Route("api/Admin/Billing/[controller]")]
[ApiController]
[Authorize("Admin")]
public class BillingConfigController : AppControllerBase
{
    [HttpGet]
    public async Task<IActionResult> Get()
        => NewResult(await Mediator.Send(new GetBillingConfigQuery()));

    [HttpPost]
    public async Task<IActionResult> Update([FromBody] UpdateBillingConfigCommand cmd)
        => NewResult(await Mediator.Send(cmd));
}
```

DI (in `AddBillingInfrastructure`): register `IBillingConfigReader` → `BillingConfigReader`; register `IAuditLogWriter` consume (either the P7 impl or the seam injection); register the FluentValidation validator.

**Gate after Batch 3:** `dotnet build` green; `POST /api/Admin/Billing/Config` creates a new version; `GET` returns the current effective values + history. Validation rejects bad input. A non-admin call returns 403.

### Batch 4 — SEQUENTIAL — `security-auditor` agent (authz gate)

**Depends on:** Batch 3 complete.

**Audit focus (admin-authz gate — medium severity):**
- **Admin-only (CRITICAL):** every config-edit endpoint is behind the admin policy. A parent/student/unauthenticated caller must not edit the economy. Grep for `[Authorize` on `BillingConfigController` methods; confirm the policy name matches the P7 admin policy.
- **Audit completeness:** every `UpdateBillingConfigCommand` execution writes who/when/old→new to `Moderation.AuditLog`. Confirm the handler always writes the audit record, including on validation failure (no — validation failure returns before the audit write, which is correct; the audit should only record successful changes).
- **Server-side validation cannot be bypassed:** the cross-field rules (daily cap ≤ grant, non-negative, pack > 0) run via `ValidationBehavior` (server-side), not only in the admin UI.
- **Never-retroactive:** a `BillingConfigVersion` insert creates a new effective-dated row only; it does not modify any `CreditTransaction.Amount` rows (immutable ledger). Grep for any `UPDATE` on `CreditTransactions` — must find none from this story.
- **No payment secrets in config:** confirm `BillingConfigVersion` stores plan/pack prices (billing economics), never payment-gateway API keys/secrets. Grep for any secret-ish field names in the entity.

### Batch 5 — SEQUENTIAL — `api-tester` agent

**Depends on:** Batch 4 complete (security-auditor PASS).

Integration tests:
1. Admin updates a per-action cost (e.g. `HintCost: 1 → 2`) → a new `BillingConfigVersion` row created; audit record written; `IBillingConfigReader.GetActionCost(Hint)` returns 2 after update; a prior `CreditTransaction.Spend` row for `Amount=1` is **unchanged** (never-retroactive).
2. Admin updates the monthly grant → P10-02's next grant (when P10-02 calls `GetMonthlyGrant(tier)`) uses the new amount; current-cycle already-granted balance unchanged.
3. Validation: negative cost → 422/`Successed=false` + message, no new version created.
4. Validation: zero pack size → rejected with clear message.
5. Validation: `FreeDailyCap > FreeMonthlyGrant` → cross-field rejection.
6. Authz: a non-admin bearer token → 403.
7. Unauthenticated → 401.
8. `GET` history: returns all versions sorted newest-first; the seeded initial version appears.
9. Defaults: the seeded initial version returns 199/100/5000/10/250/1000/1/3/5/5.
