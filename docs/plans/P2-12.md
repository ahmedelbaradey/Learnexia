#### BE-3 — Security: change-password extension + session endpoints

**Existing handler to extend:**
`Application/Features/Users/Commands/ChangePassword/ChangePasswordCommandHandler.cs` (class is named `SetNewPasswordCommandHandler` — note the copy-paste typo; do NOT rename it, just extend the `Handle` method body).

**Changes to `ChangePasswordCommandHandler.cs`:**
After `result.Succeeded`:
1. Get current session id from the JWT claim (`"SessionId"` claim key, same pattern as `SignOutCommandHandler`)
2. Call `ISessionManagementService.GetUserSessionsAsync(userId)` → list of all active sessions
3. For each session whose `SessionId != currentSessionId`, call `TerminateSessionAsync(sessionId, SessionTerminationReason.SecurityRevocation)`
4. Revoke refresh token: `await _distributedCache.RemoveAsync($"userrefreshtoken-{userId}")`
   - Inject `IDistributedCache` into the handler constructor
   - Alternatively: add `Task RevokeRefreshTokenAsync(int userId)` to `IAuthenticationService` if the pattern is cleaner — but do NOT add a design pattern without asking. Inject `IDistributedCache` directly (simplest, mirroring existing code)
5. Inject `ISessionManagementService` into the handler constructor alongside existing deps

**Route check:** `ChangePasswordCommand` currently has no confirmed `AccountController` route. Add to `AccountController`:
```
[Authorize] POST /api/Users/Account/ChangePassword
```
accepting `[FromBody] ChangePasswordCommand` (command body must NOT include `UserId` — verify the command record and strip `UserId` if present, resolving entirely from `ICurrentUserService`).

**New session-management endpoints** on `AccountController`:
- `GET /api/Users/Account/Sessions` — new `GetMySessionsQuery` + handler: calls `ISessionManagementService.GetUserSessionsAsync(userId)` → returns `List<SessionInfo>` (the existing `SessionInfo` record from `Domain/Helpers/SessionModels.cs` is the response type; no new DTO needed)
- `POST /api/Users/Account/Sessions/SignOutOthers` — new `SignOutOthersCommand` + handler: same loop as the change-password session invalidation (all sessions except current `SessionId` claim → `TerminateSessionAsync(..., SecurityRevocation)`); does NOT revoke the refresh token (that is a password-change-specific side-effect)

**New files:**
- `Application/Features/Account/Queries/GetMySessions/GetMySessionsQuery.cs` + Handler
- `Application/Features/Account/Commands/SignOutOthers/SignOutOthersCommand.cs` + Handler + Validator (command = `ICommand<>` so ValidationBehavior fires; validator is minimal — no body fields to validate, just ensuring the caller is authenticated)

**No new DTO** for sessions — reuse `Domain/Helpers/SessionModels.cs`'s `SessionInfo` record directly (it has `SessionId`, `IsActive`, `IsExpired`, `ExpiresAt`, `RemainingSeconds`, `LastActivityAt`, `CreatedAt` — sufficient for the active-sessions tab per lead decision 3).

### Batch 5 — security-auditor (sequential after Batch 4)

**Agent:** `security-auditor`  
**Mode:** mandatory per lead decision 6 and CLAUDE.md rules. Critical/High findings block the reviewer gate.

**Audit scope:**
- All eight new/extended endpoints carry `[Authorize]` — verify no accidental anonymous access
- `ICurrentUserService.UserId` is the only source of truth for identity — no `UserId` accepted from request body or route
- Change-password: verify current-password validated before session invalidation; new == current rejected by ASP.NET Identity policy; `SecurityRevocation` reason used correctly
- Unlink guard: last-parent check cannot be bypassed by race condition (two parents unlinking simultaneously) — flag if the check-then-delete is non-atomic (TOCTOU); recommend: wrap `IsLinkedAsync` + delete in a serializable transaction or handle via unique constraint
- Session invalidation loop: verify the current-session exclusion logic is correct (JWT `SessionId` claim matches the session key used in Redis)
- Refresh-token revocation cache key matches the key used during sign-in (`userrefreshtoken-{userId}`)
- No cross-family data leak: `GetUserSessionsAsync` is scoped to the caller's `userId` from JWT — no admin bypass path in these endpoints
- Notification prefs: no mass-assignment of another user's prefs (UserId in the command must be ignored if present)
- Plan stub: no sensitive data in the hardcoded response

## Persistence shape decision (baked in)

The `NotificationPreference` entity uses **row-per-`(UserId, NotificationCategory)`** with boolean channel flags. Rationale: mirrors `ParentStudentConfig` composite-PK pattern already present in Identity; simpler to query per category; no JSON-column support needed; easy to add a category in a future migration. Shape:

```
identity."NotificationPreferences"
  UserId              int           NOT NULL  -- no FK to another module
  Category            int           NOT NULL  -- NotificationCategory enum stored as int
  EmailEnabled        boolean       NOT NULL  DEFAULT false
  PushEnabled         boolean       NOT NULL  DEFAULT false
  CreatedAt           timestamptz   NOT NULL  DEFAULT now()
  UpdatedAt           timestamptz   NOT NULL  DEFAULT now()
  PK (UserId, Category)
  IX_NotificationPreferences_UserId
```

`NotificationCategory` enum values (Identity-local, in `Domain/Enums/NotificationCategory.cs`):
```
WeeklyReport = 0
StreakAtRisk = 1
ProductAnnouncements = 2
AchievementBadge = 3
```
Decoupled from `Notifications` module delivery enum.

Default on first GET (no rows exist): all four categories returned with `EmailEnabled = true, PushEnabled = false`.
