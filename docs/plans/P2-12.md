## Architecture decisions baked in (do not relitigate)

1. **NEW `Parent` module** (4 projects, schema `parent`) owns `ParentStudent` entity + family CQRS features + `ParentController`. Has zero project references to Identity. Calls Identity-side account operations only through `IChildAccountService` in Shared.Contracts.
2. **Shared.Contracts `IChildAccountService`** (interface only): `CreateChildAsync`, `GetChildrenAsync`, `UpdateChildAsync`. Identity.Infrastructure implements it. Host registers it. Mirrors the existing `IUserLookup` seam.
3. **Identity** loses the family/ParentStudent code; gains `IChildAccountService` implementation + security extensions (sessions, change-password invalidation, plan stub).
4. **Notifications module** gains `NotificationPreference` entity, `NotificationCategory` enum, GET/PUT preferences endpoints. Identity-decoupled.
5. **Migrations**: three separate migrations — Parent (`parent."ParentStudent"`), Identity (DROP `identity."ParentStudents"`), Notifications (`notifications."NotificationPreferences"`). Dev rows are disposable; production data-copy is a follow-up flagged in HANDOFF — NOT a blocker.

### Batch 7 — security-auditor (sequential after Batch 6)

Agent: `security-auditor`
Mandatory (auth, child data, sessions, password, cross-module seam authz). Critical/High findings block the reviewer gate.

Audit scope:

- Refresh-token revoke key `$"userrefreshtoken-{userId}"` matches the key written during sign-in
- `GetUserSessionsAsync` is scoped to the caller's `userId` from JWT; no admin-bypass path for these endpoints
- `IChildAccountService` registration: `AddScoped` (not `AddSingleton`) — `UserManager` is scoped
- No cross-module FK introduced (Parent.ParentStudent.ParentId and StudentId are plain ints, no EF FK to Identity tables)
- `NotificationPreference.UserId` is a plain int with no FK to Identity — confirm no IDOR path (GET returns only the JWT-resolved user's prefs)
