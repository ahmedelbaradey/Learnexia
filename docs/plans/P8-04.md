## Execution batches

### Batch 1 — sequential, single `backend-feature` agent

**Agent:** `backend-feature`
**Mode:** sequential (single working tree; compiler order enforces sequencing)

**Step 1.1 — Event contract (BE-3)**

Create `backend/src/Shared/Learnexia.Shared.Contracts/Identity/LearningLanguageChangedIntegrationEvent.cs`:

```csharp
namespace Learnexia.Shared.Contracts.Identity;

public sealed record LearningLanguageChangedIntegrationEvent(
    Guid EventId,
    DateTime OccurredOnUtc,
    int StudentId,
    string OldLanguage,
    string NewLanguage) : IIntegrationEvent;
```

Mirror of `UserRegisteredIntegrationEvent.cs` in the same folder. No new project reference needed; `Shared.Contracts` already references `Shared.Kernel` for `IIntegrationEvent`.

**Step 1.2 — Parent command + validator (BE-1)**

Create folder `backend/src/Modules/Parent/Learnexia.Modules.Parent.Application/Features/ChangeChildLearningLanguage/`.

Files:
- `ChangeLearningLanguageCommand.cs` — record with `int ChildId`, `string NewLearningLanguage`, `bool ConfirmFreshStart`. Implements `ICommand<BaseResponse<ChangedLearningLanguageResponse>>`. Define `ChangedLearningLanguageResponse` (ChildId, NewLearningLanguage) in the same folder or alongside.
- `ChangeLearningLanguageCommandValidator.cs` — shape-only: `ChildId > 0`; `NewLearningLanguage` must be `"ar"` or `"en"`. **No FluentValidation rule on `ConfirmFreshStart`** — the 424 gate is in the handler.

Mirror: `UpdateChildCommand.cs` + `UpdateChildCommandValidator.cs` in the same Parent.Application tree.

**Step 1.3 — Identity seam extension (part of BE-2/4)**

Extend `IChildAccountService` (Shared.Contracts/Identity/IChildAccountService.cs):
- Add method signature: `Task<ChildLanguageChangeResult> ChangeLearningLanguageAsync(int childUserId, string newLearningLanguage, CancellationToken ct = default);`
- Add shaped-result record: `ChildLanguageChangeResult(bool Succeeded, int ChildUserId, string OldLanguage, string NewLanguage, ChildAccountError ErrorCode = ChildAccountError.None)`.
- Add a new `ChildAccountError` discriminator value if needed (e.g. `LanguageUpdateFailed = 6`) — or reuse `UpdateFailed`.

Implement in `IdentityChildAccountService.cs` (Identity.Infrastructure):
1. `FindByIdAsync(childUserId)` → null → `ChildLanguageChangeResult(false, ..., NotFound)`.
2. Capture `oldLang = child.LearningLanguage`.
3. Same-language no-op: if `oldLang == newLearningLanguage` return `Success` result with old == new (caller short-circuits before here per locked decision 3, but seam should be safe even if called).
4. Set `child.LearningLanguage = newLearningLanguage`; `child.UpdatedAt = DateTime.UtcNow`.
5. `UpdateAsync(child)` → failure → log + return `LanguageUpdateFailed`.
6. Call `PublishLearningLanguageChangedEventAsync(child.Id, oldLang, newLearningLanguage, ct)` — same try/catch/log pattern as `PublishUserRegisteredEventAsync`.
7. Return success result.

Add private method `PublishLearningLanguageChangedEventAsync` mirroring `PublishUserRegisteredEventAsync`.

**Step 1.4 — Parent handler + controller endpoint (BE-2)**

Create `ChangeLearningLanguageCommandHandler.cs` in the same feature folder:
1. Resolve `parentId` from `ICurrentUserService`; null → `Unauthorized`.
2. Check `request.ConfirmFreshStart == false` → return `BusinessValidation<ChangedLearningLanguageResponse>(localizer[...])` immediately (424). **This is the first check — before link query and before mutation.**
3. Same-language no-op: if `request.NewLearningLanguage == currentLanguage` — but the handler does not know current language without a lookup; the seam handles the no-op internally; the handler can return `Success` directly from the seam result.
4. `_linkService.IsLinkedAsync(parentId.Value, request.ChildId)` → false → `Forbidden`.
5. Call `_childAccountService.ChangeLearningLanguageAsync(request.ChildId, request.NewLearningLanguage, ct)`.
6. Map error codes: `NotFound` → `Forbidden`; `UpdateFailed/LanguageUpdateFailed` → `BadRequest`; others → `ServerError`.
7. Return `Success(new ChangedLearningLanguageResponse(childId, newLanguage))`.

Wrap entire body in try/catch → `ServerError`.

Add to `ParentController.cs`:
```csharp
[HttpPut("Change-Learning-Language")]
[ProducesResponseType(typeof(BaseResponse<ChangedLearningLanguageResponse>), StatusCodes.Status200OK)]
public async Task<IActionResult> ChangeLearningLanguage([FromBody] ChangeLearningLanguageCommand command)
    => NewResult(await Mediator.Send(command));
```

Controller-level `[Authorize(Roles = "Parent,Admin,SuperAdmin")]` already covers this endpoint — no additional attribute needed.

**Step 1.5 — Learning consumer + internal reset command (BE-5)**

Create folder `backend/src/Modules/Learning/Learnexia.Modules.Learning.Application/IntegrationEventHandlers/`.

File: `LearningLanguageChangedIntegrationEventHandler.cs`
- `INotificationHandler<LearningLanguageChangedIntegrationEvent>`, fail-soft (try/catch/log — mirror `LessonCompletedIntegrationEventHandler`).
- Dispatches `await _mediator.Send(new ResetMathScienceProgressCommand(notification.StudentId, notification.EventId), ct)`.
- Catch + log; do not rethrow.

Create folder `backend/src/Modules/Learning/Learnexia.Modules.Learning.Application/Features/Progress/Commands/ResetMathScienceProgress/`.

File: `ResetMathScienceProgressCommand.cs`
- `record ResetMathScienceProgressCommand(int StudentId, Guid OriginEventId) : ICommand<BaseResponse<bool>>`.

File: `ResetMathScienceProgressCommandHandler.cs`
- Handler queries `LearningDbContext` (via `ILearningRepositoryManager` or direct DbContext injection consistent with how other Learning handlers access data) for `Attempt` rows where:
  - `Attempt.StudentId == request.StudentId`
  - `Attempt.Lesson.Unit.Subject.SubjectCode ∈ { SubjectCode.MATH, SubjectCode.SCIENCE }`
- Removes the fetched `Attempt` entities from the DbSet (no `SaveChangesAsync` call — `UnitOfWorkBehavior` commits).
- `StudentAnswer` rows cascade per `StudentAnswerConfig` `DeleteBehavior.Cascade` — no explicit delete needed.
- Returns `Success(true)`.
- Idempotent: if the set is already empty, `RemoveRange` on an empty collection is a no-op.

**Step 1.6 — Gamification no-consumer confirmation (BE-6)**

Code inspection: verify no file in `Learnexia.Modules.Gamification.Application.IntegrationEventHandlers/` (or elsewhere in Gamification) implements `INotificationHandler<LearningLanguageChangedIntegrationEvent>`. This is a check, not a code creation. The backend-feature agent records the finding in their implementation report.

- Best-effort publish: is it isolated from the committed User change (cannot fail the save)?
- No Gamification consumer (retained XP/streak/badges): confirmed by BE-6.

**Risk R1 — lost reset on crash (best-effort, pre-Outbox):** a process crash between Identity `UpdateAsync` committing and the event being published leaves `LearningLanguage` changed but Math/Science Attempts un-reset. Acceptable for MVP (rare parent-initiated action, re-runnable by re-issuing the change). Outbox per ADR 0002 §5 is the durable path; deferred. Flag in PR description.

**Risk R2 — no UoW in Identity:** `UpdateAsync` commits immediately (no UoW in Identity module — same as `UpdateChildAsync`). The publish happens strictly after a real commit; ghost-reset risk on rollback is negligible. Mirrors the existing `CreateChildAsync` + `PublishUserRegisteredEventAsync` pattern exactly.
