## Execution batches

### Batch 1 — SEQUENTIAL — `backend-feature` agent — BE-1

**Depends on:** P9-01 merged (the `ICreditSpendService` seam is available). **P3-01 not yet required for this task alone.**
**Agent:** `backend-feature`

Build `CreditCostResolver` — a pure, server-side, I/O-free mapping:

```csharp
// in Ai.Application/Services/ or Ai.Infrastructure/Services/
public class CreditCostResolver
{
    // Injected: IBillingConfigReader (from Shared.Contracts) or IOptions<CreditCostOptions> as fallback
    public int ResolveCost(AiTaskKind taskKind) => taskKind switch
    {
        AiTaskKind.Hint => _config.GetActionCost(AiTaskKind.Hint),            // 1
        AiTaskKind.WhyWrong => _config.GetActionCost(AiTaskKind.WhyWrong),    // 3
        AiTaskKind.Explain => _config.GetActionCost(AiTaskKind.Explain),      // 5
        AiTaskKind.SimilarExample => _config.GetActionCost(AiTaskKind.SimilarExample), // 5
        _ => throw new NotSupportedException($"Unknown task kind: {taskKind}")
    };
}
```

Falls back to a `CreditCostOptions` typed-options class (bound from `Ai:CreditCost` config section) if `IBillingConfigReader` is not yet available (P9-11 not yet built). Swap to the config reader when P9-11 lands — no change to BE-3.

**Note on module isolation:** `CreditCostResolver` lives in the `Ai` module. It consumes `IBillingConfigReader` from `Shared.Contracts/Billing/` — never from `Billing.*` projects directly.

**Gate after Batch 1:** `dotnet build` green; `CreditCostResolver` is unit-testable (pure function); all four intent-to-cost mappings return correct values.

### Batch 2 — SEQUENTIAL — `backend-feature` agent — BE-2 + BE-3 + BE-4 (sequential within)

**Depends on:** Batch 1 complete + **P3-01 + P3-04/05/06 merged** (AI Helper handlers must exist to modify).

The exact insertion points depend on the P3-01 implementation shape — the implementer must read the P3-01 code before touching it (coordinate with the P3-01 owner, OQ-4).

**BE-2 — Pre-check + graceful-decline:**

In the gateway facade or Handler (before the LLM/cache call):
```
childId = (from authenticated JWT claim — never client-supplied)
cost = CreditCostResolver.ResolveCost(taskKind)
balance = await ICreditSpendService.GetBalanceAsync(childId, ct)
if (balance.Total < cost)
{
    // graceful decline — no gateway call, no debit
    var cachedExplanation = TryGetCachedExplanation(skillId, conceptId, language); // P3-04/05 cache lookup
    return AiHelperResponse.LowEnergy(cachedExplanation); // P9-04 low-energy warning state
}
// proceed to LLM/cache call
```

The "degrade to cache" branch reused from the MVP daily-cap guardrail (which BE-4 removes). The **same cache-lookup logic** is repurposed — the trigger changes from "daily-count exhausted" to "insufficient credit balance."

**BE-3 — Debit-on-delivery:**

After the response is produced and P3-02 safety filter passes, and **before** returning the response:
```
idempotencyKey = requestContext.ActionId.ToString(); // server-generated per request, not client-supplied
debitResult = await ICreditSpendService.TryDebitAsync(childId, cost, reasonCode, idempotencyKey, ct);
if (debitResult.IsInsufficientBalance)
{
    // Race: pre-check passed but balance drained concurrently (OQ-5 → graceful decline)
    var cachedExplanation = TryGetCachedExplanation(...);
    return AiHelperResponse.LowEnergy(cachedExplanation);
}
// debit succeeded — return the response
return deliveryResponse;
```

Key constraints:
- The debit is **the last step** of a successful delivery — an earlier branch (refuse/error/safety-rejection) never reaches this code.
- `childId` is from the authenticated JWT claim — never from the request body.
- `idempotencyKey` is a server-generated action id stored in request context — reused on retry, never a new GUID per retry.
- Cache-hit and live-LLM paths both pass through the same debit step (AC-3 — charged the same).

**BE-4 — Remove `IAiUsageBudget` gate:**

Delete/disable the `IAiUsageBudget` daily-count check in the runtime gateway path. The "degrade-to-cache-on-exhaustion" branch is now the "insufficient-credit" branch (BE-2 above). Keep any usage *logging* (analytics — used by P7-11) but remove the *gating*. Document the teardown in the commit message and HANDOFF: "IAiUsageBudget MVP daily-count gate REMOVED — replaced by credit debit in P9-03. Degrade-to-cache branch repurposed as insufficient-credit path."

**Gate after Batch 2:** `dotnet build` green; manual test (or integration test) of happy path: intent → response produced → debit fires → `Spend` ledger row created; and refuse-path: refuse-and-redirect → no debit, no ledger row.

### Batch 3 — SEQUENTIAL — `backend-feature` agent — BE-5

**Depends on:** Batch 2 complete.
**Agent:** `backend-feature`

Unit/integration tests explicitly covering the no-charge-on-refuse/error invariants:
1. **Refuse-and-redirect (out-of-scope / no-context):** mock P3-02 scope guard → returns `Declined` → assert zero `TryDebitAsync` calls on the mock and zero `CreditTransaction` rows with `Type=Spend`.
2. **Provider error:** mock the gateway to throw a provider exception → after error handling → assert zero debit calls.

4. **Idempotency:** deliver the same request (same `ActionId`) twice → assert exactly one `Spend` ledger row (P9-01 DB unique key holds).
5. **Cross-child guard:** authenticate as child A, derive `childId` from JWT → assert `TryDebitAsync` is called with child A's id, not any other id.

### Batch 4 — SEQUENTIAL — `security-auditor` agent (MANDATORY HARD GATE — spend integrity)

**Depends on:** Batch 3 complete.

**This is the most security-sensitive batch in the P9 cluster. Critical/High findings block the reviewer gate.**

Audit:
- **Server-controlled cost (CRITICAL):** cost is resolved from `CreditCostResolver` keyed by a server-determined `AiTaskKind`. The client sends no cost and no action kind that could influence the charge downward. Confirm the `AiTaskKind` is server-derived (from the route / handler type, not client body).
- **No charge without delivery / no double-charge:** debit fires only on the successful-delivery path (last step after safety-pass). Idempotency key prevents double-charge on retry (P9-01 DB unique constraint). Confirm a crash between debit-success and response-return cannot double-charge on retry (same `ActionId` → unique-key violation → idempotent success).
- **No charge on refuse/error/insufficient (AC-4):** walk the code paths — refuse-and-redirect, provider error, safety-filter rejection — and confirm none of them reach the `TryDebitAsync` call site. BE-5 tests are evidence; auditor verifies the code, not just tests.
- **No energy drain via spam:** out-of-scope requests are rejected free (P3-02 scope guard, before the gateway). Confirm an attacker can't force charges by replaying a legitimate request id (idempotency covers this).
- **Insufficient never errors:** the graceful-decline path (BE-2) returns a warm low-energy message + cached canned response, never a 500 or stack trace.
- **Child id is server-derived:** `childId` for the debit comes from the authenticated JWT claim — never a client-supplied field. Confirm no route/query/body parameter can override it.
- **No PII / no prompt text** in the `Spend` ledger row (P9-01 invariant — re-confirm at the spend call site). The row carries `childId`, `amount`, `reasonCode`, `idempotencyKey` only.
- **Module isolation:** `Ai` module references `Shared.Contracts/Billing/ICreditSpendService` only — no `Billing.*` project reference. Confirm (grep `Ai.*.csproj` for any `Billing.` assembly reference).
