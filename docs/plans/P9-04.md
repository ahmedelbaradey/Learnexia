### Batch 2 — SEQUENTIAL — `backend-feature` agent — BE-2 + BE-3 (sequential)

**Depends on:** Batch 1 complete.
**Agent:** `backend-feature`

**BE-2 — `DailyCapHelper`:**

Pure domain service (static helper or instantiable — mirror `StreakDayCalculator`). No I/O. Signature:

```csharp
public static class DailyCapHelper
{
    /// <summary>
    /// Returns the child's local "today" (DateOnly) given their IANA timezone id and the current UTC time.
    /// Falls back to the platform timezone if childTimeZoneId is null/empty.
    /// </summary>
    public static DateOnly Today(string? childTimeZoneId, ISystemClock clock, string platformTimeZoneId)
    {
        var tz = string.IsNullOrWhiteSpace(childTimeZoneId)
            ? TimeZoneInfo.FindSystemTimeZoneById(platformTimeZoneId)
            : TimeZoneInfo.FindSystemTimeZoneById(childTimeZoneId);
        var localNow = TimeZoneInfo.ConvertTimeFromUtc(clock.UtcNow.UtcDateTime, tz);
        return DateOnly.FromDateTime(localNow);
    }
}
```

Unit tests: verify correct local-date computation for UTC+2 (Cairo — `"Africa/Cairo"`), UTC+0 (platform fallback), and a DST boundary case.

**BE-3 — Lazy daily reset integration:**

In both the `SpendCreditCommand` handler (P9-01-BE-5) and the `EnergyStatusQuery` handler (BE-4), before evaluating the daily cap:

```csharp
var localToday = DailyCapHelper.Today(childTimeZoneId, clock, platformTz);
if (account.DailyUsedDateLocal != localToday)
{
    account.DailyUsed = 0;
    account.DailyUsedDateLocal = localToday;
    // save as part of the enclosing transaction (spend) or as a lightweight update (read)
}
```

For the **spend path** (in the debit transaction): the reset is part of the same explicit transaction — atomic with the debit and the `DailyUsed` increment.
For the **read path** (`EnergyStatusQuery`): the reset is a lightweight update (save without a ledger row — the daily counter reset is not a credit event; it doesn't go in `CreditTransaction`).

**Gate after Batch 2:** `dotnet build` green; `DailyCapHelper` unit tests pass (3+ cases including DST boundary).

### Batch 3 — SEQUENTIAL — `backend-feature` agent — BE-4 + BE-5 (sequential)

**Depends on:** Batch 2 complete.
**Agent:** `backend-feature`

**BE-4 — `EnergyStatusQuery`:**

```csharp
public record EnergyStatusQuery(int ChildId) : IQuery<BaseResponse<EnergyStatusDto>>;

public class EnergyStatusQueryHandler : IQueryHandler<EnergyStatusQuery, BaseResponse<EnergyStatusDto>>
{
    // Inject IBillingRepository, ISystemClock, IBillingConfigReader (or IOptions<DailyCapOptions>), ILoggerManager
    public async Task<BaseResponse<EnergyStatusDto>> Handle(...)
    {
        var account = await _repo.GetCreditAccountAsync(childId);  // includes lazy-reset from BE-3
        var config = _configReader.GetDailyCap(planTier);          // from P9-11 or defaults
        var monthlyAllotment = _configReader.GetMonthlyGrant(planTier);

        var dailyCapReached = account.DailyUsed >= config.DailyCap;
        var monthlyRemaining = account.GrantedBalance + account.PurchasedBalance;
        var lowEnergyThreshold = (int)(monthlyAllotment * 0.10m);  // 10% of allotment
        var lowEnergy = monthlyRemaining <= lowEnergyThreshold;

        var warningState = (dailyCapReached, lowEnergy) switch
        {
            (true, _) => WarningState.DailyCapReached,
            (_, true) => WarningState.LowEnergy,
            _ => WarningState.None
        };

        return Success(new EnergyStatusDto
        {
            MonthlyBalance = monthlyRemaining,
            DailyUsed = account.DailyUsed,
            DailyCap = config.DailyCap,
            DailyCapReached = dailyCapReached,
            LowEnergy = lowEnergy,
            WarningState = warningState,
            GrantExpiresAtUtc = account.GrantExpiresAtUtc
        });
    }
}
```

`[Authorize]` (bearer token; child-scoped — `ChildId` from JWT claim, not route param).

**BE-5 — `IncrementDailyUsage` + hard-stop guard:**

In the `SpendCreditCommand` handler (after the debit commits, within the same transaction):
```csharp
account.DailyUsed += cost;  // cost is the debit amount (same units)
```

Hard-stop guard (if `HardStopEnabled = true` in P9-11 config, default false):
```csharp
if (config.HardStopEnabled && account.DailyUsed >= config.DailyCap)
{
    // Block the spend entirely — return a typed "DailyCapHardStop" result
    // (caller degrades to low-energy decline)
    return Fail("Daily energy cap reached.");
}
```

`DailyCapEnforcer.IsHardStopBlocking(account, config)` utility method: `config.HardStopEnabled && account.DailyUsed >= config.DailyCap`.

**Gate after Batch 3:** `dotnet build` green; `EnergyStatusQuery` returns correct `WarningState`; hard-stop flag flips behavior when `HardStopEnabled = true`.

### Batch 4 — SEQUENTIAL — `security-auditor` agent (light gate)

**Depends on:** Batch 3 complete.

Audit:
- **Monthly ceiling is the real limit:** confirm the daily cap is informational only (warning + soft block, never independently draining the monthly pool). The monthly pool (P9-01) is the authoritative ceiling — a child who hits the daily cap and continues still cannot spend below zero (P9-03's insufficient-balance path catches that). Confirm no bug creates a scenario where `DailyUsed > 0` grants "extra" spend beyond the monthly pool.
- **Timezone manipulation:** the child's timezone is server-side (from their profile, set at onboarding, not client-supplied). Confirm no client-sent timezone can trigger early midnight resets. If the timezone is in any request parameter, flag as High.
- **Hard-stop OFF by default:** confirm the code default is `HardStopEnabled = false` and that the soft path (warning + allow) is the default behavior, never the reverse.
- **No PII:** the daily counter stores amounts + dates + loose `ChildId` only.

This is a **light gate** — no money moves; P9-04 is a pacing/warning system. Critical/High findings still block.

### Batch 5 — SEQUENTIAL — `api-tester` agent

**Depends on:** Batch 4 complete.

Integration tests (inject `ISystemClock` for clock-advance cases):
1. Spend below the daily cap (Free: 9 out of 10) → `EnergyStatusQuery` returns `DailyCapReached = false`, `WarningState = None`.
2. Spend up to the cap (10) → `DailyCapReached = true`, `WarningState = DailyCapReached`, and the child **can still spend** (soft — hard-stop is OFF).
3. Hard-stop ON (config flip): at cap → next spend returns `DailyCapHardStop` decline.
4. Low-energy threshold: drive monthly remaining ≤ 10% of allotment → `LowEnergy = true`, `WarningState = LowEnergy`.
5. Daily reset: advance clock past child's local midnight (inject `ISystemClock`) → next read/spend resets `DailyUsed = 0`, `DailyUsedDateLocal = new date`; monthly pool unchanged.
6. Config-driven cap: change cap in P9-11 / options → new cap applies (no redeploy).
7. Monthly ceiling: even past the daily cap, spend stops at `TotalBalance = 0` (P9-03 insufficient → graceful decline).
