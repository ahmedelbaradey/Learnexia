**Critical dependency note — UoW ordering in Identity:** Identity uses `UnitOfWorkBehavior` (registered after `ValidationBehavior`). The `LinkParentStudentService.LinkAsync` must be called after ASP.NET Identity's `CreateAsync` for the child user completes (which commits immediately via `UserManager`), then within the same command transaction for the link row — or as a separate commit. Chosen design: linkage service writes and commits the `ParentStudent` row via a direct `DbContext.SaveChangesAsync(userId)` call (not deferred), since `UserManager.CreateAsync` already committed the child. Document this in the service's XML comment so P1-03's handler knows to call it post-`CreateAsync`.

### Batch 2 — Feature Implementation (two parallel sub-batches after Batch 1)
**Agent: backend-feature**
**Gate: reviewer pass before Batch 3**

Sub-batch 2A and 2B can be built in parallel since both depend only on the entity/migration (Batch 1). They converge at BE-4c (controller), which depends on BE-2.

**Sub-batch 2A — Linkage service + command/endpoint (sequential within 2A):**

1. `P1-04-BE-2` — Create `ILinkParentStudentService` interface (Application Abstractions layer) and `LinkParentStudentService` implementation (Infrastructure Services layer). Method: `Task<bool> LinkAsync(int parentId, int studentId, CancellationToken ct = default)` — idempotent (returns `true` if created, `false` if already linked). Internally: `IdentityModuleDbContext.ParentStudents.AnyAsync(...)` check, then `Add` + `SaveChangesAsync(userId)`. Register in `IdentityServiceManager` via `Lazy<ILinkParentStudentService>` and expose on `IIdentityServiceManager`. Register scoped in `DependencyInjection.cs` (coordinate with P1-02).
2. `P1-04-BE-4a` — Create in `Application/Features/Family/Commands/LinkChild/`:
   - `LinkChildCommand { string ChildEmail }` : `ICommand<BaseResponse<LinkedChildResponse>>`
   - `LinkedChildResponse { int Id, string FullName, int GradeId }` response DTO
   - `LinkChildCommandValidator : AbstractValidator<LinkChildCommand>` — rules: `ChildEmail` not empty, valid email format; include `BaseValidation` if applicable.
   - AutoMapper profile entry (or existing `IdentityProfile`) mapping `User → LinkedChildResponse`.
3. `P1-04-BE-4b` — Create `LinkChildCommandHandler : BaseResponseHandler, ICommandHandler<LinkChildCommand, BaseResponse<LinkedChildResponse>>`. Logic: inject `IIdentityServiceManager`, `ICurrentUserService`, `ILoggerManager`. Steps: (a) get current parent `userId` from `ICurrentUserService`; (b) find child user by email via `UserManager` (fail-closed: if not found or not Student role → `NotFound`/`BusinessValidation` with generic "cannot link" message — no email enumeration); (c) guard self-link; (d) call `ILinkParentStudentService.LinkAsync`; (e) return `Success(linkedChildResponse)`. Wrap in try/catch → `ServerError`.
4. `P1-04-BE-4c` — Create `ParentController.cs` in `…Identity.Api/Controllers/`. Route: `api/Users/Parent/[Action]`. Authorize: `[Authorize(Roles = "Parent,Admin,SuperAdmin")]` (action-level or class-level; use role names matching the `Roles` enum PascalCase). Do NOT inherit from `UserManagementController`. Inherit `AppControllerBase`. Actions: `[HttpPost] LinkChild` (→ `Mediator.Send(new LinkChildCommand(...))`), `[HttpGet] MyChildren` (→ `Mediator.Send(new ListMyChildrenQuery())`).
5. `P1-04-BE-4d` — Create `ListMyChildrenQuery : IQuery<BaseResponse<IEnumerable<LinkedChildResponse>>>` + `ListMyChildrenQueryHandler`. Query: reads `IdentityModuleDbContext.ParentStudents.Where(ps => ps.ParentId == currentUserId)`, joins/includes `User` navigation to project to `LinkedChildResponse`. Note: queries are not auto-validated (CONVENTIONS §4) — validate caller role inside the handler or rely on controller authorization.

**Sub-batch 2B — Family-scope authorization handler (can run in parallel with 2A):**

1. `P1-04-BE-3` — Create in `…Identity.Infrastructure/Authorization/` (new folder):
   - `FamilyScopeRequirement : IAuthorizationRequirement` — marker class, no properties needed.
   - `FamilyScopeAuthorizationHandler : AuthorizationHandler<FamilyScopeRequirement, int>` where the resource `int` is the target `studentId`. Handler logic: succeed if caller is Admin/SuperAdmin (check `ClaimTypes.Role`); OR caller's `Id` == `studentId` (self, for Student role); OR caller is Parent and `ParentStudents.AnyAsync(ps => ps.ParentId == callerId && ps.StudentId == studentId)`. **Fail-closed:** do not call `context.Succeed` unless one condition is met; let the framework deny by default. Handler must be `async`. Inject `IdentityModuleDbContext`.
   - Register in `DependencyInjection.cs`: `services.AddScoped<IAuthorizationHandler, FamilyScopeAuthorizationHandler>();`. This is the **highest merge-overlap risk line** with P1-02 — keep the addition minimal (one `AddScoped` line in the existing `AddIdentityInfrastructure` method).

**Definition of done (Batch 2):**
- AC-1 hook: `ILinkParentStudentService.LinkAsync` is callable by P1-03's `AddChildCommandHandler` (interface is in Application Abstractions, implementation in Infrastructure — correct layer).
- AC-2: `POST api/Users/Parent/Link-Child` with a valid parent JWT and an existing student email returns 200 + `Successed: true` + linked child summary.
- AC-6: Re-posting the same link is a no-op (no duplicate row; response is still success).
- AC-5: Posting a non-existent or non-student email returns an error (no email enumeration).
- AC-7: A parent cannot claim another family's already-linked child (fail-closed with generic error).
- AC-3: `FamilyScopeAuthorizationHandler` compiles; P1-05 can reuse via `IAuthorizationService.AuthorizeAsync(user, studentId, new FamilyScopeRequirement())`.
- `GET api/Users/Parent/My-Children` returns only the calling parent's linked children.
- `dotnet build` passes for all Identity layers and Host.
- `Successed` spelling preserved; `BaseResponse<T>` envelope used; `ILoggerManager` used for logging.
- No cross-module references introduced.

**Reviewer gate 2** — verify: controller does not inherit `AdminOnly` gate; `ICurrentUserService` resolves parent from JWT (not request body); fail-closed error messages do not leak email existence; `FamilyScopeAuthorizationHandler` fails closed by default; module isolation (no cross-module FK/reference); `Successed` spelling; `ILoggerManager`; validation on command only; UoW sequencing documented in `LinkAsync`.

### Batch 4 — Security Audit (BLOCKING — after Batch 3 reviewer pass)
**Agent: security-auditor**
**Findings severity: Critical/High block the pipeline**

Task `P1-04-SEC` — audit the following risk surfaces:

1. **IDOR / family-scope correctness** — can a parent call `Link-Child` and gain access to data for a child they did not create? Verify the fail-closed guard in `LinkChildCommandHandler` prevents claiming another family's child.
2. **Link-by-email enumeration** — does the error response for a non-existent vs existing-but-ineligible email differ? Both must return the same generic message/shape.
3. **`FamilyScopeAuthorizationHandler` fail-closed** — does the handler ever call `context.Succeed` when it should not? Check the async path (no accidental early `Succeed` before DB check completes).
4. **Controller authorization gate** — confirm `ParentController` does NOT inherit `UserManagementController`'s `AdminOnly` policy; confirm it requires at least the `Parent` role; unauthenticated callers get 401.
5. **Parent-id from JWT only** — confirm no handler or service reads `parentId` from the request body; all parent identity flows from `ICurrentUserService.UserId`.
6. **Minors'-data exposure via `My-Children` list** — confirm the list returns only the caller's children and no cross-family data.
7. **Input validation** — can malformed/null `ChildEmail` cause unhandled exceptions? Verify `FluentValidation` catches these at the command level (422 before handler runs).

**Definition of done (Batch 4):**
- Security report produced (inline or as comment to lead).
- No Critical or High findings outstanding — any found must be fixed and re-audited before proceeding.
- Medium findings documented with remediation plan; Low findings logged.

**Reviewer gate 4 (final)** — confirm security audit PASSED, all AC met across all batches, CONVENTIONS.md compliance, no regressions in existing tests. Sign off before committer.
