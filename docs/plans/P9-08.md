## Execution batches

### Batch 1 — SEQUENTIAL (conditional) — `db-migration` — BE-1

**Gate on finance confirmation D1.** If sequential invoice numbers or VAT fields are required and not already on `Payment` from P9-06: add fields + migration. If P9-06 already captured VAT at charge time and no invoice table is needed: **this batch is a no-op — skip to Batch 2.** Coordinate with P9-06 implementer.

### Batch 2 — SEQUENTIAL — `backend-feature` — BE-2, BE-3, BE-4

BE-2 (history query) → BE-3 (receipt query, depends on D2 for HTML vs PDF) → BE-4 (controller). Strictly sequential. Both queries are not auto-validated (`ValidationBehavior` is command-only) — validate ids inside handlers. IDOR defense in BE-3 (re-check ownership).

**DoD:** build green; history endpoint returns paginated list with all payment types + refunds; receipt endpoint returns the correct DTO + printable HTML; IDOR rejected.

### Batch 3 — SEQUENTIAL — `api-tester`

After Batch 2. Cases: history returns chronological list with correct fields (renewals + packs + refunds); receipt has all required fields; cross-account IDOR denied (paymentId belonging to another parent returns 403/404 not 200); empty history → empty list (not error); `BaseResponse<T>`/`Successed`.

**Security-auditor: light/optional** — P9-08 is read-only (no payment mutation). The reviewer confirms IDOR protection is sufficient. If the lead wants a formal light audit on financial PII exposure, insert a `security-auditor (light)` pass between Batch 3 and Batch 4. Planner flags this to the lead.

### Batch 4 — PARALLEL with Batch 3 — `designer` — FE-1

Start as soon as Batch 2 is done. Output: `design-system/ui_kits/parent-app/P9-08-billing-history.md`.

### Batch 5 — SEQUENTIAL (after Batches 3+4) — `frontend` — FE-2, FE-3, FE-4, FE-5

Sequential sub-order: FE-2 → FE-3 → FE-4 (FE-5 alongside FE-3/4). Child name mapped in FE-3 from parent's loaded children list — no extra BE call.

### Batch 6 — SEQUENTIAL — `frontend-e2e-tester` — FE-6

After Batch 5. Note: refund entries in history require P9-09 to be deployed (coordinate with lead — FE-6 may be deferred until P9-09 ships, or run with mocked refund data).

### Batch 7 — SEQUENTIAL — `reviewer` then `committer`

PASS → `committer` → branch `feat/P9-08-billing-history-receipts`, PR to `main`, HANDOFF.md update (VAT field decision, printable-HTML receipt approach, child-name FE mapping). Never merge.
