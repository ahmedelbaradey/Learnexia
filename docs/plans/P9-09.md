## Execution batches

### Batch 1 — SEQUENTIAL — `db-migration` — BE-1

Extend `Subscription` with `FailedAttemptCount`, `NextRetryAt`, `GraceEndsAt`, `PastDue`/`Dunning` status values. Extend `Payment` with refund linkage. Migration `AddDunningAndRefundFields` — serialized after `AddPaymentAndWebhookTables` (P9-06-BE-2). Coordinate per PARALLELISM.md.

**DoD:** migration applies; dunning fields on `billing.Subscriptions`; refund linkage on `billing.Payments`.

### Batch 2 — PARALLEL — `backend-feature` — BE-2, BE-3 (after D1 clawback policy cleared)

BE-2 (`charge.failed` branch) and BE-3 (`refund.succeeded` branch) both extend `HandleProviderWebhookCommand` but in different event-type branches — they can be developed in parallel on the same handler file if coordinated (merge carefully), or sequentially if that is safer. **Block BE-3 on D1 (clawback policy confirmation).** BE-4 follows BE-2; BE-5 is conditional on D2.

**DoD:** build green; `charge.failed` increments count + schedules retry + emits dunning notification event; `refund.succeeded` claws back unspent credits (clamped) + marks refunded — both idempotent.

### Batch 3 — SEQUENTIAL — `api-tester`

After Batch 2. Cases: `charge.failed` webhook → `FailedAttemptCount++`, retry scheduled, notification emitted (idempotent on same event); after N failures → subscription set to downgrade Free at cycle end; **`refund.succeeded` for a pack** claws back unspent credits only (spend some first, then refund → only remainder clawed; never negative); **duplicate refund webhook → no double-claw**; subscription refund per policy; forged/unsigned webhook rejected; `BaseResponse<T>`/`Successed`. **Negative-balance/race test:** concurrent spend + refund webhook — assert final balance ≥ 0.

### Batch 4 — SEQUENTIAL (after Batch 3) — `security-auditor` (MANDATORY)

**Critical/High block.** Focus: idempotent reversal (replayed `refund.succeeded` claws back exactly once), clawback never negative, webhook signature inherited from P9-06, admin-only refund authz (if BE-5), policy enforcement (no over-clawback of granted credits), money-correctness invariants.

### Batch 5 — PARALLEL with Batch 3 — `frontend` — FE-1, FE-2

FE-1 (`DunningBanner`) requires plan tab from P9-05-FE-4. FE-2 (i18n) alongside. Light pass — no new screen.

### Batch 6 — SEQUENTIAL — `frontend-e2e-tester` — FE-3

Light E2E: PastDue/Downgrading banner visible; refund appears as negative entry in billing history (cross-checks P9-08-FE-6). Requires P9-09 BE deployed + P9-08 deployed.

### Batch 7 — SEQUENTIAL — `reviewer` then `committer`

PASS → `committer` → branch `feat/P9-09-failed-payments-refunds`, PR to `main`, HANDOFF.md update (clawback policy confirmed, dunning params, refund trigger). Never merge.
