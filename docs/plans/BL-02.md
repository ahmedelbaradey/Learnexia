### Batch 4 — PARALLEL — `api-tester` + `security-auditor`

**Agent:** `api-tester` + `security-auditor` (parallel)
**Depends on:** Batch 3 complete (.NET) + Python service running (if Q2 = in-scope) or a mocked `IParsingServiceClient` (for CI).

**`api-tester` validations (against mocked parsing client for CI):**
1. A `Received` document → `Processing` → `Done`; `ParsedArtifactObjectKey` stored; parse status visible in GET detail.
2. Parsing-service failure stub → `ParseStatus = Failed`; `ParseDiagnostics` populated; GET detail reflects failure.
3. Re-parse command on a `Failed` doc → returns to `Processing` → `Done`.
4. Re-parse while already `Processing` → 409 conflict envelope.
5. Non-admin re-parse trigger → 403.
6. Response envelope key is `Successed`.

**`security-auditor` checklist (REQUIRED — external service credentials + AI/admin surface):**
- Azure DI API key and parsing-service URL in secrets (env var / key vault), NOT in source.
- No SSRF risk: parsing-service URL is config-driven and not user-controlled.
- Admin-only on re-parse trigger; read endpoints for status/diagnostics appropriately scoped.
- No PII / student data in the documents beyond curriculum content (low risk, but confirm).
- `ParseDiagnostics` field does not expose internal secrets or stack traces in production.

Critical/High findings block the gate.

---

**Agent:** `reviewer`
**Depends on:** Batch 4 PASS.

8. No design pattern introduced without approval.
