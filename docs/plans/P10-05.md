## Execution batches

### Batch 1 — SEQUENTIAL — `db-migration` — BE-1, BE-2, BE-3

**Gate prerequisite:** Lead sign-off D1 cleared; D2, D3 resolved.

Scaffold the `Billing` module (BE-1), add domain entities (BE-2), configure EF + generate `BillingInitialCreate` migration + seed plans (BE-3). These are strictly sequential (each depends on the prior). Shared-file edits (`Program.cs`, `.sln`, `Directory.Packages.props`) must be **serialized** per PARALLELISM.md — do NOT run concurrent with P10-06 db-migration work.

**DoD:** `dotnet build` green; `BillingInitialCreate` migration applies cleanly; `billing.Plans` has 2 rows (Free/Premium); `billing.Subscriptions` table exists with correct schema and filtered unique index.

### Batch 2 — SEQUENTIAL — `backend-feature` — BE-4, BE-5, BE-6 + BE-7 (parallel pair within batch)

After Batch 1 applies. BE-4 (queries) runs first; once done, BE-5 (commands) runs; BE-6 (controller) and BE-7 (Shared.Contracts seam) are **independent of each other** and run in parallel after BE-5.

**DoD:** `dotnet build` green; all 5 endpoints resolve in Swagger; `ValidationBehavior` fires for commands; owning-parent authz enforced; `Shared.Contracts` plan seam compiles.

### Batch 3 — SEQUENTIAL — `api-tester`

After Batch 2. Validate: get current plan (Free default) → `Successed`, get comparison → benefit values match config, upgrade → `PendingPayment` (not Active), downgrade → `Downgrading`, cancel → access-to-cycle-end, **cross-account access denied** (parent A cannot read parent B's plan). Envelope `BaseResponse<T>`/`Successed`/camelCase errors.

### Batch 4 — PARALLEL with Batch 3 start — `designer` — FE-1

The designer can begin as soon as Batch 2 is done (response shapes are known). Run **in parallel with Batch 3** (api-tester and designer are independent). Output: `design-system/ui_kits/parent-app/P10-05-plan-management.md`.

**No security-auditor stage** for P10-05 — no card data, no payment mutation here (the Upgrade command only creates a `PendingPayment` subscription; actual payment is P10-06). The authz check (owning-parent-only) is confirmed by the api-tester and the reviewer.

### Batch 5 — SEQUENTIAL (after Batches 3+4) — `frontend` — FE-2, FE-3, FE-4, FE-5

FE-2 and FE-3 are quick setup tasks (hooks) that run sequentially. FE-4 (screen) and FE-5 (i18n) run together (FE-5 is needed as FE-4 is built). All require the design spec (FE-1 done) and live endpoints (Batch 3 done).

**DoD:** parent plan tab renders real data, Upgrade CTA hands off to P10-06 checkout URL, Downgrade/Cancel modals show correct copy, RTL mirrors correct, all i18n keys present.

### Batch 6 — SEQUENTIAL — `frontend-e2e-tester` — FE-6

After Batch 5. Drive the web PWA — view plan, compare benefits, upgrade/downgrade/cancel flows, cross-account isolation, RTL/ar+en.

### Batch 7 — SEQUENTIAL — `reviewer` then `committer`

Reviewer gates against all ACs + CONVENTIONS. If PASS: `committer` → branch `feat/P10-05-manage-subscription-plan`, PR to `main`, HANDOFF.md update. Never merge.
