### Batch 2 — PARALLEL (two independent threads) — `backend-feature` agent — BE-5 + (BE-6 ‖ BE-7)

**Depends on:** Batch 1 complete (schema gate).
**Mode:** BE-5 first (sequential with Batch 1); then BE-6 and BE-7 in parallel.

#### Sub-batch 2a — SEQUENTIAL — BE-5

`DebitAsync` is the core atomic primitive. Implement before BE-6 (which calls the same explicit-transaction shape). Key contract:
- Open explicit transaction.
- Load `CreditAccount` with concurrency token (`xmin`).
- Pre-check idempotency key (select-before-insert or catch unique violation).
- If `TotalBalance < amount`: return typed `InsufficientBalance`, no write.
- Compute Granted-first split (`fromGranted = min(amount, GrantedBalance)`; `fromPurchased = amount - fromGranted`).
- Call `account.Debit(fromGranted, fromPurchased, reasonCode, idempotencyKey)` — method updates both pools and returns the `CreditTransaction` to insert.
- Insert `CreditTransaction`.
- Commit.
- On `DbUpdateConcurrencyException`: retry with bounded count.
- On unique-key `PostgresException` (code 23505): return idempotent success with prior row's data.
- Return `BaseResponse<DebitResult>`.

#### Sub-batch 2b — PARALLEL — BE-6 ‖ BE-7

Both are unblocked by Batch 1 (schema + BE-5 shape as template). Files are completely independent:
- **BE-6**: Grant, Purchase, Expire, Refund, Adjust commands — each reuses the explicit-transaction + idempotency pattern from BE-5, differing only in pool direction and `Type` enum value.
- **BE-7**: `GetCreditAccountQuery` (child-facing read seam: `{ GrantedBalance, PurchasedBalance, TotalBalance, GrantExpiresAtUtc }`) + `ReconcileAccountQuery` (admin ops: `sum(ledger) vs account.balance` — returns discrepancy, does not heal). Read-only handlers; no `ValidationBehavior` (rule 4); `ILoggerManager` injected.

**Gate after Batch 2:** `dotnet build` green; `dotnet test` passes unit tests for the debit (Granted-first split, insufficient, idempotency, concurrency token retry).

### Batch 4 — SEQUENTIAL — `security-auditor` agent (load-bearing integrity gate)

**Depends on:** Batch 3 complete.

**Scope of audit (ledger tamper-resistance — not yet a hard money gate):**
- **Append-only enforcement:** confirm `CreditTransaction` has zero update/delete paths in code; any correction is a new compensating row.
- **DB-enforced idempotency:** the unique constraint exists at the DB layer (not just app-level). The insert path catches and translates the 23505 violation rather than 500-ing.
- **Atomic debit:** balance update + ledger insert share one explicit transaction. Confirm the concurrency token (`xmin`) prevents two parallel debits from over-drawing (no lost update = no free energy).
- **No PII in the ledger:** `CreditTransaction` rows carry amounts + reason codes + loose `ChildId` only — no child name/email, no AI prompt/response text.
- **Authorization (forward-looking):** the spend seam must be callable only server-side; confirm the `ICreditSpendService` impl is not reachable from any unauthenticated endpoint.

Findings at Critical or High severity block the reviewer gate.

---

### Batch 5 — SEQUENTIAL — `api-tester` agent

**Depends on:** Batch 4 complete.

Integration test coverage (WebApplicationFactory + Testcontainers PostgreSQL — mirror existing api-tester pattern):
1. Debit draws Granted-before-Purchased (GrantedBalance=10, PurchasedBalance=10, debit 15 → Granted=0, Purchased=5; ledger row has `FromGranted=10`, `FromPurchased=5`).
2. Insufficient total → typed `InsufficientBalance`; **no ledger row written**; balances unchanged.
3. Idempotent debit: same idempotency key twice → one ledger row; balance decremented once; second call returns the prior result.
4. Reconciliation: `sum(ledger) == account balances`; inject a manual drift → reconciliation query flags the discrepancy.
5. Concurrency: two parallel debits of the full balance → exactly one succeeds; no over-draw; the other returns `InsufficientBalance` or wins the concurrency retry.
6. Expire: `GrantedBalance=120`, `PurchasedBalance=50` → after `ExpireGrantCommand`, `GrantedBalance=0`, `PurchasedBalance=50`, one `Expire` ledger row.
7. `GET /api/Billing/Credits/account` (if exposed) → `200 OK`, `{ "successed": true, "data": { "grantedBalance": ..., ... } }`.
8. Unauthenticated call → `401`.

### Batch 6 — SEQUENTIAL — `reviewer` gate, then `committer`

**Depends on:** Batch 5 complete (api-tester + security-auditor results available).
**Agent:** `reviewer`

Review against ALL of:
1. **AC-1..AC-6** from the brief: dual pool; append-only ledger with all required fields; reconciliation; DB idempotency constraint; Granted-first + atomic debit; conventions + isolation.
2. **CONVENTIONS.md:** `BaseResponse<T>` envelope via `BaseResponseHandler`; `Successed` spelling; `ILoggerManager` (not `ILogger<T>`); no Unit of Work (explicit transaction per ADR 0001); no cross-module FK (`ChildId` is a loose int with an index, not a FK to Identity); schema `billing` on all new tables; enum `HasConversion<int>()`.
3. **Module isolation (rule 1):** no project reference from `Billing.*` to any other module's projects. `ICreditSpendService` lives in `Shared.Contracts`; the `Ai` module will consume it there.
4. **Ledger append-only:** `CreditTransaction` has no `Update`/`Delete` EF operations anywhere in the codebase (grep). Any correction goes through a new `Adjustment`/`Refund` row.
5. **Idempotency at DB layer:** unique constraint on `IdempotencyKey` exists in the migration. App-layer catch of `PostgresException` 23505 translates to an idempotent success.
6. **Concurrency:** `xmin` concurrency token present in `CreditAccountConfig`; `DbUpdateConcurrencyException` caught + bounded retry in the debit handler.
7. **No design pattern introduced without approval** (CLAUDE.md rule 8 — the explicit-transaction primitive is not a pattern; it is the established ADR 0001 shape).
8. **`docs/dev/HANDOFF.md` updated** with: `Billing` module scaffold; schema `billing`; idempotency key scheme; `ICreditSpendService` seam for P9-03; Granted-first rule; Phase-9 FR family is new-to-SRS (note for SRS-keeper); OQ-3 per-child decision; OQ-4 always-positive amount convention; OQ-5 `xmin` concurrency token.

### Overall story DoD (tied to acceptance criteria)

- AC-1: `CreditAccount` exists per child with `GrantedBalance` + `PurchasedBalance` + derived `TotalBalance`; per-child (one account per `ChildId` unique index).
- AC-2: Every balance change is an append-only `CreditTransaction` carrying all required fields; no mutation methods on `CreditTransaction`.
- AC-3: `ReconcileAccountQuery` recomputes both pools from the ledger and flags drift without healing.
- AC-4: DB unique constraint `UX_CreditTransactions_IdempotencyKey` rejects duplicates; app catches the violation and returns idempotent success.
- AC-5: `DebitAsync` draws Granted-first atomically; concurrent debits do not over-draw (concurrency token + retry); `InsufficientBalance` returns no partial write.
- AC-6: All handlers use `BaseResponse<T>`/`Successed`; `ILoggerManager`; no UoW; child is a loose int ref; `Billing` module lives in `billing` schema.
