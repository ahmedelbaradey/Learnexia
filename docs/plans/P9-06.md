## Execution batches

### Batch 1 — SEQUENTIAL — `db-migration` — BE-1, BE-2

Serialized after P9-05 Batch 1 (`BillingInitialCreate` must be applied first). Extend `BillingDbContext` with `Payment` and `WebhookEvent`. Generate `AddPaymentAndWebhookTables` migration. Confirm no card columns exist.

**DoD:** build green; migration applies; `billing.Payments` + `billing.WebhookEvents` tables with correct indexes; unique index on `ProviderEventId`.

### Batch 2 — SEQUENTIAL then PARALLEL — `backend-feature` — BE-3, then BE-4+BE-5+BE-6 in parallel, then BE-7+BE-8

BE-3 must complete first (adapter is the foundation). Then BE-4 (`StartSubscriptionCheckout`), BE-5 (`HandleProviderWebhook`), BE-6 (`CancelSubscription`) are **independent of each other** — run in parallel. BE-7 depends on BE-5; BE-8 depends on BE-3. **BE-3 is blocked on provider decision D1.**

**DoD:** build green; all endpoints in Swagger; webhook endpoint accepts raw body (no JWT); signature verification in BE-5; dedup on `ProviderEventId`; `SubscriptionActivated`/`PaymentFailed` events compile.

### Batch 3 — SEQUENTIAL — `api-tester`

After Batch 2. Provider sandbox required (D5). Cases: checkout creates `Payment{Initiated}`; webhook success → Active + grant event emitted once; **duplicate webhook → no-op** (no double-activation); bad/missing signature → 401/400; declined → `Payment{Failed}` + `PaymentFailed` event; cross-account checkout denied; `BaseResponse<T>`/`Successed`.

### Batch 4 — SEQUENTIAL (after Batch 3) — `security-auditor` (MANDATORY)

**Critical/High findings block the reviewer gate.** Focus: PCI/no-card-data, webhook signature verification, idempotency (no double-activation/grant), secrets in config not code/logs, owning-parent authz on checkout, server-sets amount (not client).

### Batch 5 — PARALLEL with Batch 3 — `designer` — FE-1

Can start as soon as Batch 2 backend endpoints are live. Output: `design-system/ui_kits/parent-app/P9-06-checkout-flow.md`.

### Batch 6 — SEQUENTIAL (after Batches 4+5) — `frontend` — FE-2, FE-3, FE-4, FE-5

Sequential sub-order: FE-2 → FE-3 → FE-4 (FE-5 alongside FE-4). Requires design spec (FE-1) and security-auditor PASS.

**DoD:** no card form ever renders in the app; redirect flow works; return states show correct UI; RTL correct; price from API not hard-coded.

### Batch 7 — SEQUENTIAL — `frontend-e2e-tester` — FE-6

After Batch 6. Provider sandbox/stub required. Assert no card form, no child-route exposure.

### Batch 8 — SEQUENTIAL — `reviewer` then `committer`

Reviewer gates against all ACs + CONVENTIONS + api-tester results + security-auditor findings (no open Critical/High). PASS → `committer` → branch `feat/P9-06-pay-for-subscription`, PR to `main`, HANDOFF.md update (provider choice, webhook shape, idempotency design, recurring model). Never merge.
