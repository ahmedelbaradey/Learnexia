## Acceptance criteria (verbatim from story)

1. **AC1** — Missions have a type (daily/weekly), an objective, a reward (XP), and an expiry.
2. **AC2** — `StudentMission` tracks status and progress %; progress updates from learning events.
3. **AC3** — Completing a mission grants its reward and reflects on the dashboard.
4. **AC4** — Expired incomplete missions close out and new ones are issued on schedule.

## Batch 6 — security-auditor (SEQUENTIAL)

**Agent:** `security-auditor`
**Mode:** Sequential gate.
**Depends on:** Batch 5 PASS.

Audit surface for this story:
- **IDOR** — `GET /api/Gamification/Missions/Me` and `IStudentMissionsQuery.GetByStudentIdAsync` both resolve identity exclusively from JWT (`_currentUser.UserId`). No `studentId` route/query parameter accepted. Structurally IDOR-proof — verify.
- **PII** — mission ledger carries only int IDs, Guids, enums, timestamps, and string discriminators. No name, email, age, lesson content, answer text. Confirm no PII in `MissionProgressLog.OriginEventType`.
- **Idempotency two-layer** — `HasMissionProgressLogAsync` pre-check + `UX_MissionProgressLogs_StudentMissionId_OriginEventId` DB unique index. Verify both layers present in `IncrementMissionProgressCommandHandler`.
- **No `ex.Message` to client** — all catch blocks must call `ServerError<T>()`, never echo `ex.Message`. Verify all three notification handlers and the command handler.
- **Event-payload `StudentId`, NOT `_currentUser`** in notification handlers — post-commit dispatch scope has no HTTP request context. Verify all three handlers use `notification.StudentId`.
- **Lazy-instantiation row limit** — at most 8 rows instantiated per dashboard load (5 daily + 3 weekly); bounded by catalog size. Not a resource exhaustion risk. Confirm.
- **Hangfire job scope isolation** — `MissionRolloverJob` creates its own `IServiceScopeFactory.CreateAsyncScope()` scope; no ambient HTTP context. Confirm scope lifetime is correct.
- **Unique constraint in lazy-instantiation race** — `UX_StudentMissions_StudentXpProfileId_MissionDefinitionId_PeriodKey` catches concurrent inserts. `DbUpdateException` catch in `StudentMissionsQuery` re-reads instead of propagating. Verify the catch is narrowed correctly.

Critical/High findings block merge. Medium/Low: document and defer if agreed.
