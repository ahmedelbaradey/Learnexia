**CASING NOTE (resolves brief Q3):** The lead decision is "standardize on the enum's PascalCase everywhere." This means:
- `RoleSeeder` must be changed to seed names using `Roles.<X>.ToString()` (PascalCase, e.g. `"Parent"`, `"Admin"`) — removing the current `.ToLower()` call — and wrapped with `if (!await roleManager.RoleExistsAsync(name))` guards.
- The `UserSeeder` calls `AddToRoleAsync(user, Roles.Basic.ToString())` etc. — already PascalCase, already correct; no change needed there.
- The `SeedClaimsForSuperAdmin` call to `FindByNameAsync("SuperAdmin")` is also already PascalCase — correct.
- `RegisterParentCommandHandler` uses `Roles.Parent.ToString()` (= `"Parent"`) for `AddToRoleAsync`.
- The `RoleHelper` string constants (`"superadmin"`, `"basic"`, etc.) are used only for legacy role-check helpers — they are not used in the new Register-Parent flow and need not be changed in this story, but the implementing agent should note the inconsistency and leave it for a dedicated cleanup story.

### Batch 3 — security-auditor (after Batch 1; runs in parallel with or after Batch 2)

**Agent:** `security-auditor`
**Prerequisite:** Batch 1 code complete (source review, not runtime-required). May overlap with api-tester.

Focus areas (from brief handoff):
1. Role is server-assigned — no client path can set/escalate role; `RegisterParentCommand` has no `Roles` field.
2. Password never logged or returned — handler logs user ID only; response is `JwtAuthResponse` (no password field); `ILoggerManager` calls must not include the password string.
3. Account enumeration: duplicate-email validation response reveals that an email is in use. Assess severity and recommend (generic vs. specific messaging trade-off).
4. Anti-automation: anonymous account-creation endpoint has no rate-limiting, CAPTCHA, or email verification. Flag severity and recommendation.
5. Validator–Identity policy alignment: password regex in validator must be at least as strict as the Identity `opt.Password.*` settings in `Infrastructure/DependencyInjection.cs`; confirm no weaker bypass path through the handler.
6. `IsFirstLogin` and session token: verify no information leakage in the JWT payload.

**Critical/High findings block the reviewer gate.** Medium/Low findings are logged as recommendations only.

## Blockers / prerequisites

| Blocker | Impact | Recommendation |
|---|---|---|
| `P1-06-BE-*` (Npgsql / PostgreSQL provisioning) | Runtime-only. Identity schema already exists in code; task BE-2 role seeding requires a live DB at startup. Build (Batch 1) does not require P1-06 to be merged, but api-tester (Batch 2) does require the DB to be up and the Identity migration to be applied. | Confirm P1-06 is merged and DB is running before dispatching Batch 2. Document in api-tester brief. |
| `RoleSeeder` casing change affects all existing seeded roles | Changing `.ToLower()` → PascalCase will rename `"superadmin"` → `"SuperAdmin"` etc. in `AspNetRoles`. If the DB already has rows seeded with lowercase names, they will not be deleted — a duplicate `"SuperAdmin"` (PascalCase) row will be added alongside the old `"superadmin"` row on the next startup. | The implementing agent must handle this: either (a) add a one-time data migration / seed-clean step that renames existing rows before re-seeding, or (b) seed new roles (Parent, Student) with the same casing as existing rows (lowercase) for this story only and file a follow-up for casing standardization. **Lead should decide.** Default: if DB is freshly provisioned (dev environment), option (a) is safe. If DB has live data, option (b) is safer. |
| `UserSeeder.SeedSuperAdminAsync` calls `FindByNameAsync("SuperAdmin")` | If casing is changed and existing row is renamed, this lookup must also be updated consistently. The implementing agent should validate this end-to-end. | Covered by the build + api-tester gates. |
| No rate-limiting / CAPTCHA infrastructure | Anonymous account-creation endpoint. Not a build blocker, but security-auditor will flag it. | Accept as a known gap; document and file a follow-up story. Do not block Batch 4 on infrastructure that is out of scope for P1-01. |
