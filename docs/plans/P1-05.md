**Concrete [Authorize] scheme (lead decision #2 + #3 applied):**

For `AuthorzationController` — role/claim CRUD is highest-risk; class-level `[Authorize(Policy = AuthorizationPolicies.AdminOnly)]` covers all six actions.

For `ProductsController` and `CategoriesController` — Catalog is demo scaffolding; use minimal gating to avoid permission-claim traps (no role currently holds `Catalog.*` claims, so a `[Authorize("Catalog.Create")]` gate 403s everyone including admins until claims are seeded). Use role-based only:

```
// On the class (covers reads — any authenticated caller):
[Authorize]

// Override on mutating actions (Create, Update, Delete):
[Authorize(Policy = AuthorizationPolicies.AdminOnly)]
```

This matches lead decision #2 and the brief's Q3 recommendation.

**BE-4 specifics:** `appsettings.json` already contains the `CHANGE_ME…` placeholder, not a real secret. The agent confirms this is still true, leaves the file unchanged if so, and records the verification in the PR body. `GuardJwtSecret` (DependencyInjection.cs lines 172-202) already enforces Production/Staging fail-fast — the agent does NOT duplicate it. The `.gitignore` already covers `.env` and `appsettings.*.local.json`.

**BE-3 documentation output:** the agent writes the call pattern as a `/// <summary>` block on `FamilyScopeRequirement.cs` (or a markdown comment in the PR body), not a new doc file. The pattern is:
```csharp
var result = await _authorizationService.AuthorizeAsync(User, studentId, new FamilyScopeRequirement());
if (!result.Succeeded) return Forbid();
```

### Gate A — security-auditor (BLOCKING)

**Agent:** `security-auditor`
**Input:** Batch 1 diff + this plan + Pipeline Brief
**Blocking:** Critical or High findings block progression to api-tester.

Mandatory audit checklist (from brief risks):

1. **Authz bypass check:** every newly-attributed endpoint — does the policy name match one registered in `AddAuthorization`? `AdminOnly` is registered; `[Authorize]` (no policy) uses the default require-authenticated policy (correct for reads). Confirm no endpoint has a policy string that resolves to nothing.
2. **Over-permissioning:** do read endpoints allow more roles than intended? `[Authorize]` (any authenticated) is the intentional choice for Catalog reads — confirm the brief and lead decision align.
3. **Under-permissioning:** `AuthorzationController` (role/claim CRUD) was fully anonymous. Confirm `AdminOnly` is now class-level with no overriding `[AllowAnonymous]` on any action.
4. **Family-scope fail-closed:** `FamilyScopeAuthorizationHandler` — confirm `Succeed()` is called ONLY on explicit match (no `else Succeed`, no swallowed exception path). Confirm no caller ignores the `AuthorizationResult` (tests must assert the 403 path).
5. **Secrets:** confirm `JwtSettings.Secret` in `appsettings.json` is the placeholder, not a real value. Confirm `GuardJwtSecret` throws on Production/Staging if the placeholder or empty is supplied.
6. **Legacy role noise:** confirm no new Learnexia policy depends on `FundManager`, `LegalCouncil`, `BoardSecretary`, or other legacy `Roles` enum members.
7. **`RoleHelper` lower-case trap:** confirm no new policy or handler uses `RoleHelper.*` constants (lower-case) for role name comparisons; only PascalCase `Roles.Admin.ToString()` / `Roles.SuperAdmin.ToString()` in the handler and policy registration.
8. **`AllowAnonymous` regression:** confirm `AuthenticationController` anon endpoints and health probes (`/health`, `/health/live`) remain anonymous.
