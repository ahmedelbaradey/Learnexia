## Business context & value
- **Who benefits:** the **admin / support operator** (internal). Indirectly parents + children (faster, scoped support resolution).
- **Value:** find any account by role/status/free-text and inspect it read-only with least-privilege exposure — no cross-family leakage, no destructive capability in this story. Every profile open is auditable (P7-12).
- **Success measure (from AC):** an admin can locate an account by role/status/name/email over a paginated list, open a read-only profile that shows **both** `PreferredLanguage` and `LearningLanguage` distinctly, see the family linkage in both directions, and a recent learning/gamification activity summary — all behind the admin gate, all degrading gracefully when data is absent.

## Acceptance criteria (testable — FE)
Traceable to the story's AC bullets (lines 15–21) and the FE task coverage table:

1. **List + filters + search + pagination (FE-1).** Opening **Users** shows a **server-paginated table** of accounts. Filters: **role** (Parent / Student) and **status** (Active / Suspended), plus a **free-text query** over name/email. Paging is server-side (page/pageSize → `currentPage`/`totalCount`/`totalPages`); changing a filter or the query resets to page 1. Page-size respects the backend cap (≤100).
2. **List states.** The list renders distinct **loading** (skeleton), **empty** ("no results" — backend returns the empty-collection envelope, not an error), **error** (`AdminErrorBanner`, with retry), and **results** states. Free-text input is debounced; in-flight refetch does not blank the table (use `placeholderData`/keepPreviousData).
3. **Read-only profile (FE-2).** Opening a row navigates to `/users/[id]` and shows a **read-only** profile: full name, email, role(s), account status, created date, and the status reason/changed-at when present. **No edit/mutation controls in this story** (those are P7-07/P7-08).
4. **Both language fields shown distinctly (FE-2).** For a **child** (Student role) the profile additionally shows **grade**, **country/nationality**, and **two separately-labeled** language values: **`PreferredLanguage`** (UI / communication language, e.g. `ar-EG`/`en-US`) and **`LearningLanguage`** (medium of instruction for Math & Science, `ar`/`en`). They must not be merged or conflated. For non-children these child-only fields are hidden/labeled as not applicable.
5. **Family panel (FE-3).** For a **parent** the detail view lists **linked children**; for a **child** it lists **linked parent(s)**. Each member deep-links to that member's `/users/[id]` detail. (Note the backend privacy shape: **child emails are null** in the family list — see security section.)
6. **Activity panel (FE-4).** The detail view shows a **recent-activity summary**: XP/level, streak, badge count, missions, league — each rendered best-effort (a `null` section degrades to "no data", never an error). **Last sign-in is labeled "not tracked"** (backend always returns null — see Q1).
7. **Detail states.** The detail view handles **loading**, **not-found** (404 → friendly "user not found", not a crash), and **error**. Family and activity panels load/err **independently** of the core profile (a failing activity seam must not blank the profile).
8. **Admin-only access (FE-5).** Every Users route lives under the `(admin)` group and is gated by `useAdminGuard`; a non-admin / signed-out user is redirected to `/login` and never sees user PII. The backend `AdminOnly` policy is the real gate (401 anon / 403 non-admin) — the FE guard is the UX boundary.
9. **Navigation (FE-5).** A **functional** "Users" item is added to `AdminSideNav` (today the nav items are non-functional placeholders) with an active state on `/users*`, and the `AdminTopBar` title reflects the current page.
10. **i18n + a11y (FE-5).** All new copy is added to the admin `strings.ts` in **both EN and AR**; the surface is RTL-safe (logical layout, no hard left/right) and a11y-correct (table semantics / `scope`, accessible filter controls, `aria-current` on the active nav item, focus management on navigation, `role="alert"` errors via `AdminErrorBanner`).

## Backend contract (already built — what the FE consumes)
Base route `api/Admin/Users`, controller `backend/src/Modules/Identity/Learnexia.Modules.Identity.Api/Controllers/AdminUsersController.cs`. **All endpoints are class-level `[Authorize(Policy = AuthorizationPolicies.AdminOnly)]`** → anonymous = **401**, non-admin = **403**. Responses use the `BaseResponse<T>` envelope; the success flag is **`Successed`** (serialized lowercase `successed`); the api-client unwraps it to `data`.

| # | Verb + path | Query / route params | Success payload (envelope `data`) |
|---|---|---|---|
| 1 | `GET /api/Admin/Users` | `Role?` (string: "Parent"/"Student"/…), `Status?` (int: 0 Active, 1 Suspended, 2 Deleted), `Q?` (free-text over name+email), `PageNumber` (default 1), `PageSize` (default 20, clamp ≤100), `OrderBy?` ("…desc" → desc on FullName) — **PascalCase query keys** | `PaginatedResult<AdminUserListItemDto>` — full paged envelope (`currentPage`, `totalCount`, `totalPages`, `pageSize`, `data[]`). Empty → success envelope with empty `data` (NOT an error). |
| 2 | `GET /api/Admin/Users/{id}` | `id` int (route) | `BaseResponse<AdminUserProfileDto>`. **`id<=0` → 400; not found → 404.** Emits `AdminActionPerformedEvent(UserViewed)` post-read (audit, best-effort). |
| 3 | `GET /api/Admin/Users/{id}/family` | `id` int | `BaseResponse<AdminFamilyDto>`. Not found → 404. |
| 4 | `GET /api/Admin/Users/{id}/activity` | `id` int | `BaseResponse<AdminActivitySummaryDto>`. Not found → 404. Each gamification section is best-effort (null on seam failure); **never 500**. |

**DTO shapes (exact field names — camelCase on the wire):**

- `AdminUserListItemDto` — `id:int`, `fullName:string`, `email:string`, `role:string|null`, `accountStatus:int (enum)`, `createdAt:DateTime`. **Lean by design — no grade/language/country/PII in the list** (privacy decision; those only appear on the single-profile endpoint).
- `AdminUserProfileDto` — `id`, `fullName`, `email`, `role:string|null`, `roles:string[]`, `accountStatus:int`, `isActive:bool`, `lastStatusReason:string|null`, `statusChangedAtUtc:DateTime|null`, `createdAt:DateTime`, `lastSignInAtUtc:null (always)`, `preferredLanguage:string` (culture code), `learningLanguage:string` (`ar`/`en`), `grade:int|null` (child only), `nationality:string|null` (child only), `avatarUrl:string|null`.
- `AdminFamilyDto` — `userId:int`, `userRole:string`, `children:AdminFamilyMemberDto[]` (populated for parents), `parents:AdminFamilyMemberDto[]` (populated for children). `AdminFamilyMemberDto = { id:int, fullName:string, email:string|null, grade:int|null }`. **`email` is null for child members** (parents only) — privacy by design.
- `AdminActivitySummaryDto` — `userId:int`, `lastSignInAtUtc:null (always)`, `xp:{ totalXp, currentLevel }|null`, `streak:{ currentStreak, longestStreak, lastActivityDateUtc:DateOnly|null }|null`, `badges:{ totalCount }|null`, `missions:{ dailyMissionCount, completedDailyMissions }|null`, `league:{ tier:string, weeklyXp, currentRank, groupSize }|null`. Any field can be null → render "no data" for that section.

> **api-client status (verified):** the generated NSwag client (`packages/api-client/src/generated/nswag-client.ts`) does **NOT** yet expose these `api/Admin/Users` endpoints (it only has the legacy `/api/Users/UserManagement/GetUserProfile`). Two viable paths — decide in the plan: **(a)** regenerate the client from the running backend's swagger (`gen:api` flow, per HANDOFF P8-99-FE-0) then add thin typed hooks, or **(b)** hand-write hooks using the existing untyped pattern — `client.getPaginated<AdminUserListItemDto>('/api/Admin/Users', { query: { Role, Status, Q, PageNumber, PageSize, OrderBy }, signal })` for the list and `useApiQuery`/`client.get` for the three detail endpoints, with FE-local DTO types. `useUserList.ts` is the exact reference for the paginated hand-written path. Either way add the keys to `queryKeys.ts`.

## Open questions / assumptions / risks
- **Q1 — last sign-in is unavailable.** `lastSignInAtUtc` is hard-coded null in both the profile and activity DTOs (no `LastSignInAt` column; baked-in decision Q-A6). The story AC mentions "last sign-in." **Assumption:** the FE labels it "Sign-in activity: not tracked" rather than blocking the AC. Confirm this is acceptable for the FE sign-off, or whether the lead wants it dropped from the UI entirely. *(Backend gap — not fixed in this FE wave.)*
- **Q2 — child email hidden in family panel.** The family DTO returns `email = null` for child members by design (an admin must open the child's own profile to see it). **Assumption:** the family panel shows name/grade for children and omits email, with the deep-link as the path to full detail. Confirm.
- **Q3 — api-client generation vs hand-written hooks.** Decide path (a) regenerate NSwag client vs (b) hand-write hooks (see backend-contract note). Recommendation: **(b) hand-write** for this wave to avoid a full regen + its blast radius across the student app, matching `useUserList`'s pattern; revisit a regen when P7-07/08 add mutations. Lead/planner to confirm.
- **Q4 — status-code inconsistency (minor).** `GET /Users/{id}` returns **400** for `id<=0` but **404** for a genuinely missing user, while `/family` and `/activity` return **404** for `id<=0`. The FE should treat both 400-on-detail and 404 as "not found" for the profile route. Flagging so the e2e tester doesn't trip on it; not worth a backend change.
- **Q5 — role/status filter option source.** Roles ("Parent"/"Student") and statuses (0/1/2) are **hardcoded enum-ish** sets in this story (no list endpoint). **Assumption:** FE hardcodes the role + status options (Admin/SuperAdmin excluded from the role filter UI as not a support target — confirm whether admins should be searchable too).
- **Q6 — middleware is a pass-through.** Route protection is **client-side only** (`middleware.ts` is a documented stub; sessionStorage tokens can't be read at the edge). A determined user can momentarily receive shell HTML before the guard redirects. **Pre-existing P1-10 debt, out of scope here** — note it so the security-auditor doesn't re-raise it as new. True server-side enforcement needs HttpOnly-cookie auth (separate backend story).
- **Q7 — audit visibility.** Profile reads emit `AdminActionPerformedEvent(UserViewed)`; the P7-12 audit store consumes it. No FE work — but the security-auditor should confirm the FE adds no extra unaudited PII-exposing path (e.g. caching profile data in a place that survives sign-out).

## Security & privacy considerations (this surface exposes user + child PII)
This is a **security-sensitive** batch — `security-auditor` is **mandatory** before the gate (child + user data). Notes for that audit:
- **Authz:** all four endpoints are `AdminOnly` (401 anon / 403 non-admin); the FE `useAdminGuard` is the UX boundary, the backend policy is the real gate. The FE must never render user PII outside the authorized shell (guard already enforces loading→skeleton, redirecting→null).
- **What PII is exposed:** list = name + email + role + status (lean, **no child grade/language/country**); detail = adds child grade, country, both languages, avatar; family = linked-member names/grades (**child email null by design**). The FE must not surface anything beyond what each endpoint returns, and must not stash list/profile responses in `localStorage` or any store that outlives the session (TanStack cache + sessionStorage tokens are cleared on sign-out — keep it that way).
- **Audit:** every profile open is audited server-side (P7-12 consumer of `AdminActionPerformedEvent`); the FE needs no audit code but must not introduce a PII read path that bypasses the audited endpoints. The search handler deliberately logs **q-length only, not the raw term** (a child name/email) — the FE should likewise avoid echoing PII into client logs/telemetry/URLs beyond what's needed (search term in the query string is acceptable as it's the user's own input, but avoid logging it).
- **No mutations in this story** — confirm the screen exposes no suspend/delete/edit affordance (those are P7-07/P7-08, separately audited).
