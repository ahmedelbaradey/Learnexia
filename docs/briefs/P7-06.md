# Pipeline Brief — P7-06 Search & inspect users (Backend)

> Written by `analyzer` (2026-06-08). Backend-only brief for the Phase-7 Admin Console **User/Account wave**, story **P7-06**. Ground truth = the live **Identity** module on `feat/phase-7-backend` (verified against source, not just task docs). Read-only audit; the only writes were the three brief files.

## Summary & traceability
- **One-line task:** Give admins a paginated/filterable search over parent + child accounts and a read-only profile/family/recent-activity inspect view, reusing the existing Identity admin surface and pulling cross-module activity via `Shared.Contracts` seams only.
- **User story:** `user-stories/Phase-7-Admin-Console/P7-06-search-and-inspect-users.md`
- **BE task file:** `tasks/Backend/Phase-7-Admin-Console/P7-06-BE.md` (BE-1..BE-5)
- **FR / SRS:** **FR-ADM-5** (SRS §4.9), Admin role SRS §3. Goal matrix → admin operability.
- **BRD goal:** supports **G5** (operability / support) — admins resolve support without touching unrelated families.
- **Phase / epic:** Phase 7 — Admin Console · Epic: Admin — User & Account Management · SP 5.
- **Wave position:** first of the user/account wave (P7-06 → P7-07 → P7-08). Read-only; lowest risk; unblocks the two write stories which reuse its profile DTO/controller surface.

## Business context & value
- **Who benefits:** the **admin/support operator**. Indirectly parents/children (faster, scoped support).
- **Value:** investigate accounts and resolve tickets with least-privilege data exposure; no cross-family leakage. Read inspection is itself audited (who viewed whom) per P7-12.
- **Success measure (from AC):** admin can find any account by role/status/free-text, open a read-only profile showing both language fields distinctly, see the family linkage both directions, and a recent-activity summary — all admin-gated, all paginated, all auditable.

## Acceptance criteria (testable)
1. `GET` admin user search returns a **server-paginated** list filterable by **role** (parent/child), **status** (active/suspended), and **free-text** over name + email. Empty filters → first page of all non-deleted users.
2. Opening a result returns a **read-only profile**: name, email, role, status, created + last-active dates; for children also **grade, country, and BOTH `PreferredLanguage` (UI, ar/en) and `LearningLanguage` (medium-of-instruction, ar/en)** shown as two distinct, labeled values.
3. For a parent → list of **linked children**; for a child → list of **linked parent(s)** — sourced from the Parent module's `ParentStudent` linkage via a `Shared.Contracts` seam (no cross-module FK).
4. A **recent-activity summary** (last sign-in + recent learning/gamification activity) is sourced via integration contracts, never direct cross-module FK.
5. Non-admin caller → **403** (authenticated) / **401** (anonymous); endpoints carry `[Authorize(Policy = AuthorizationPolicies.AdminOnly)]`.
6. A profile **read** emits an admin-action/audit signal (`AdminActionPerformedEvent`, publish-only this wave; the P7-12 consumer is deferred).
7. List queries validate paging/filter inputs in the handler (queries are NOT auto-validated — `ValidationBehavior` is `ICommand<>` only). Bad page/size is clamped or 400'd, never 500.

## Affected modules & data
- **Module:** `Identity` only. **No new module, no new entity.** This is a **read-only add** (new queries/DTOs/endpoints) over the existing `User` aggregate + the Parent `ParentStudent` link (via seam) + Gamification/Learning read seams.
- **Existing on disk (verified):**
  - `User : IdentityUser<int>` (`...Identity.Domain/Entities/User.cs`) already has: `FullName`, `PreferredLanguage` (stored as full culture code `ar-EG`/`en-US`), `LearningLanguage` (short `ar`/`en`), `Nationality` (= "country"), `Grade`, `Age`, `CreatedAt`, `IsActive`, `IsDeleted`, `CreatedBy/UpdatedBy/DeletedBy`. **There is NO `LastActiveAt`/`LastSignInAt` field** — only `LastFailedLoginAttempt`. (See "Open questions" Q-A6.)
  - `UserManagementController` (`...Identity.Api/Controllers/UserManagementController.cs`) — **already class-level `[Authorize(Policy = AuthorizationPolicies.AdminOnly)]`** (P1-13 hardening). Route base `api/Users/UserManagement/[Action]`. Already has `UserList` (paginated `ListQuery`), `GetUserById`, `GetUserProfile`, etc. **This is extend, not greenfield** — the BE task's BE-5 "add Authorize" is already satisfied at class level.
  - `ListQueryHandler` (`...Features/Users/Queries/List/ListQueryHandler.cs`) — existing paginated search with role/name/IsActive filters, returns `PaginatedResult<GetUserListResponse>` via `ToPaginatedListAsync`. **Reuse this pattern**; it already excludes `IsDeleted == true` and the current user. Note its free-text `Search` matches `UserName` only and `Name` matches `FullName` — P7-06 wants a single `q` over **both** name + email.
  - Pagination: `Learnexia.Shared.Kernel.Pagination.PaginatedResult<T>` + `ToPaginatedListAsync(pageNumber, pageSize, orderBy)` is the house convention (NOT a bespoke `PagedResult` — the task file's `PagedResult<T>` should map to `PaginatedResult<T>`).
- **Net-new:**
  - `SearchUsersQuery` + handler → `PaginatedResult<AdminUserListItemDto>` (role/status/free-text-over-name+email). Can be a thin specialization of `ListQuery` or a new query; recommend a new query so the admin DTO and the `q`-over-email semantics stay clean.
  - `GetAdminUserProfileQuery` + handler → `BaseResponse<AdminUserProfileDto>` (both language fields surfaced distinctly; for children include grade/country). Note `GetUserProfileQuery`/`UserProfileResponseDto` already exist — confirm whether to extend that DTO or add an admin-specific one (Q-A7).
  - `GetUserFamilyQuery` + handler → `BaseResponse<AdminFamilyDto>` (children[] for a parent, parents[] for a child).
  - `GetUserActivitySummaryQuery` + handler → `BaseResponse<AdminActivitySummaryDto>`.
  - DTOs: `AdminUserListItemDto`, `AdminUserProfileDto`, `AdminFamilyDto`, `AdminActivitySummaryDto`.

## Handoff → db-migration
- **No schema change is strictly required** for read-only search/profile/family — **UNLESS** the lead decides P7-06 must show a real "last-active"/"last sign-in" timestamp (AC-2 + AC-4). `User` has **no** such column today (only `LastFailedLoginAttempt`).
  - If a true last-sign-in is wanted: add `LastSignInAtUtc` (nullable) to `User` + migration, and stamp it in `SignInCommandHandler`/`GoogleSignInCommandHandler` on success. This is a write-path change beyond pure read and should be an explicit lead decision (Q-A6). Otherwise surface "last activity" only from the Gamification/Learning seams + Redis session and label sign-in as "not tracked".
- If no last-active field is added → **db-migration has nothing to do for P7-06** (skip the migration batch).

## Handoff → backend-feature
- **Queries (all `IQuery<>`, NOT auto-validated — validate inputs in-handler):**
  - `SearchUsersQuery(Role?, Status?, Q?, PageNumber, PageSize, OrderBy?)` → `PaginatedResult<AdminUserListItemDto>`. Filter `IsDeleted != true`; map status from the chosen account-status source (today `IsActive`; **after P7-07 lands `AccountStatus`**, switch to that — see dependency note). Free-text `Q` → `FullName.Contains || Email.Contains` (EF-translatable; mirror `ListQueryHandler.ApplyFiltersAsync`). Role filter via `GetUsersByRole`.
  - `GetAdminUserProfileQuery(int UserId)` → `BaseResponse<AdminUserProfileDto>`. Include both `PreferredLanguage` and `LearningLanguage` (do not normalize them together — they're distinct). For non-students, `LearningLanguage` may be the default `ar`; surface as-is but the FE labels it "child only".
  - `GetUserFamilyQuery(int UserId)` → `BaseResponse<AdminFamilyDto>`. **Cross-module:** needs parent→children-ids and child→parents-ids. See the seam gap below.
  - `GetUserActivitySummaryQuery(int UserId)` → `BaseResponse<AdminActivitySummaryDto>`. Compose from existing `Shared.Contracts` read seams: `IStudentXpQuery`, `IStudentStreakQuery`, `IStudentBadgesQuery`, `IStudentMissionsQuery`, `IStudentLeagueQuery` (Gamification) for "recent learning/gamification activity"; last-sign-in from the new field or session store. **No direct cross-module FK.** Each seam call is best-effort; a missing/throwing seam must degrade to "no data", never 500.
- **Cross-module seam GAP (must resolve before BE-3 can be built):** the only `Shared.Contracts/Parent` seam today is `IParentChildQuery` with `ParentHasAnyChildAsync`, `IsParentOfChildAsync`, `FindParentForChildAsync(childId) → single parentId`. There is **no `GetChildIdsForParentAsync(parentId)`** in Shared.Contracts — that list-of-children method exists only inside the Parent module's internal `ILinkParentStudentService.GetLinkedStudentIdsAsync` (NOT a Shared.Contracts seam, so Identity cannot call it). **P7-06 must add a Shared.Contracts method** (e.g. `IParentChildQuery.GetChildIdsForParentAsync(parentId)` and/or `GetParentIdsForChildAsync(childId)` — note `FindParentForChildAsync` returns only ONE parent, but the story says "parent(s)") implemented in `Parent.Infrastructure`. Flag to planner: this is a small Shared.Contracts + Parent.Infrastructure edit (serialized shared-file edit per PARALLELISM.md). Child profile enrichment (name/email of each child) uses the existing `IChildAccountService.GetChildrenAsync(ids)` seam.
- **Controller:** add four `[HttpGet]` actions to the existing `UserManagementController` (already `AdminOnly` at class level) OR a dedicated `AdminUsersController` mirroring the FE contract `GET /api/Admin/Users...`. The task file's FE contract uses `/api/Admin/Users` paths; the live controller is `api/Users/UserManagement/[Action]`. **Decide route shape (Q-A8)** — either is fine but must be locked so FE + api-tester agree.
- **Audit emit (BE-5):** on the profile read handler, publish `AdminActionPerformedEvent` (new `AdminActions.UserViewed` / `UserSearched` constant added to `Shared.Contracts/Admin/AdminActions.cs`). **Mirror the curriculum wave's publish-only pattern.** Carry only opaque ids (the event is PII-free by contract); `AdminUserId` from JWT via `ICurrentUserService`. NOTE the wave-wide tracked follow-up: the event currently publishes **pre-commit** — for a read there's no commit, so publish best-effort after the read succeeds; keep consistent with the curriculum handlers.
- **Conventions:** handlers return `BaseResponse<T>` via `BaseResponseHandler`; success flag spelled `Successed`; controllers use `NewResult(...)`; inject `ILoggerManager`; never echo `ex.Message` to the caller.

## Open questions / assumptions / risks (for the lead)
- **Q-A1 (search scope / child-PII):** "free-text over name/email" — confirm the search matches BOTH parent and child accounts on `FullName` + `Email`, and confirm the **list DTO** exposes only minimal fields (name, email, role, status, created). Should the **list** view omit child grade/languages/country (show them only on the detail profile) to avoid over-exposing child PII in a broad result set? **Recommendation: minimal list DTO; PII only on the single-profile detail.**
- **Q-A6 (last-active source):** there is **no `LastSignInAt`/`LastActiveAt` column on `User`** today (only `LastFailedLoginAttempt`). AC-2 asks for "last-active dates" and AC-4 for "last sign-in". Options: (a) add a `LastSignInAtUtc` column + stamp it in the sign-in handlers (write-path change, needs a migration); (b) derive "last active" only from Gamification/Learning seams + Redis session and label sign-in "not tracked". **Recommendation: decide before BE-2/BE-4 — (a) is cleaner for support but is a write-path + migration scope bump.**
- **Q-A7 (profile DTO reuse):** there is already a `GetUserProfileQuery` + `UserProfileResponseDto`. Extend it with `LearningLanguage` + status, or add an admin-specific `AdminUserProfileDto`? **Recommendation: new admin DTO** (keeps the self-service `/Me`-style profile and the admin-inspect projection independent; avoids leaking admin-only fields to self-service).
- **Q-A8 (route shape):** the FE contract uses `/api/Admin/Users...`; the live admin controller is `api/Users/UserManagement/[Action]`. Add a new `AdminUsersController` with the `/api/Admin/Users` REST shape, or hang new actions off the existing controller? **Recommendation: new `AdminUsersController` with the REST shape the FE contract expects** (cleaner, matches the three stories' shared surface) — but lock it so P7-07/P7-08 hang their writes on the SAME controller.
- **Q-A9 (status source pre-P7-07):** `AccountStatus` does not exist yet (P7-07 introduces it). Until then "status" filtering maps to `IsActive`. **Assumption:** P7-06 ships with `IsActive`-based status and P7-07 migrates the filter to `AccountStatus`. Confirm the wave order (P7-06 before P7-07) so the status enum lands in P7-07 and P7-06's filter is upgraded — OR pull `AccountStatus` forward into P7-06. **Recommendation: keep P7-06 read-only on `IsActive`; P7-07 owns the enum and upgrades the filter.**
- **Q-A10 (Parent seam):** confirm adding `GetChildIdsForParentAsync` (and multi-parent `GetParentIdsForChildAsync`) to `Shared.Contracts/Parent/IParentChildQuery` + `Parent.Infrastructure` is approved (small shared-file edit, serialized per PARALLELISM.md). **Required for BE-3.**
