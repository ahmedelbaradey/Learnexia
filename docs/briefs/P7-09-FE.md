## Business context & value

- **Who benefits:** Admins directly (the reviewers); **children** ultimately — the queue is the human gate ensuring no unsafe AI output (and, later, no unsafe curriculum upload) slips past the automated Safety Layer.
- **Value:** P3-02 already *blocks* unsafe AI output at generation time and records a PII-light safety signal, but there is no human review surface today. This FE wave turns that signal stream into an actionable admin workflow: see the queue → open an item → approve / reject-with-reason / flag-for-escalation, with every action audited (P7-12) and access locked to admins.
- **Success measured by:** admins can find, inspect, and resolve flagged items; resolved (terminal) items are not re-actionable; non-admins are fully locked out; the UI works in EN and AR (RTL).
- **v1 privacy posture (load-bearing):** P3-02 stores **no raw flagged content**. The queue surfaces **reason codes + failed-check names + opaque source refs** only — never the child's prompt or the AI's response text. The FE must present "what failed and why" without ever implying raw content is available (it is not). A full-content quarantine store was explicitly deferred from P3-02 (see OQ-1).

## Acceptance criteria (testable — FE)

1. **Queue list** renders a paginated table from `GET api/Admin/Moderation/Queue` showing, per item: source, content reference, status badge, subject/grade (when present), task kind, and detected-at time. Default order is newest-first (backend orders by `DetectedAt` desc). Server-side pagination; changing any filter/search resets to page 1; previous page stays visible during refetch (`keepPreviousData`).
2. **Filters + search** are wired DB-side via query params: **status** (Pending/Approved/Rejected/Flagged), **source** (AiOutput/CurriculumUpload), **subject** (SubjectCode), **grade** (1–12), **date range** (DateFrom/DateTo on DetectedAt), and free-text **search** (ContentReference, debounced). A "clear filters" affordance appears when any filter is active.
3. **Four list states** are all present and distinct: loading-skeleton, empty (success with empty `data` — NOT an error), error+retry, results. Empty state copy reflects whether filters are active. (Note: the CurriculumUpload source has no live producer yet → filtering by it legitimately yields an empty list — copy must not read as an error.)
4. **Item detail** (`GET api/Admin/Moderation/{id}`) shows: source, status badge, content reference, subject/grade/task kind, detected-at, and the **SafetyVerdict** parsed and rendered as human-readable **failed checks + reason codes + action taken + model id** — explicitly framed as "automated safety signal," NOT raw content. Review fields (reviewed-by user id, reviewed-at, review reason) show when the item has been reviewed. Loading / error / not-found (404) states handled.
5. **Review action** (`POST api/Admin/Moderation/{id}/Review`) offers **Approve / Reject / Flag**. **Reject requires a non-empty reason** (≤ 2000 chars); the confirm button is disarmed until a reason is present. Approve and Flag take an optional reason. Decision is sent as the **`ModerationStatus` enum value** the backend expects (Approved / Rejected / Flagged — see Contract below).
6. **Pending-only-ish gating:** review controls are **enabled only for `Pending` and `Flagged`** items; for terminal items (`Approved`, `Rejected`) the review controls are hidden/disabled. `Flagged → Flagged` is also disallowed (re-flag is rejected by the backend) — the Flag option is hidden/disabled when the item is already `Flagged`. The FE must not present an action the backend will reject with 400.
7. **No optimistic update:** on a successful review the FE **invalidates + refetches** the item detail and the queue list (and shows a success toast/banner); the new status comes from the refetch, never from a hand-rolled local mutation. On failure (400 terminal/already-flagged, 404, 422 validation, network) the dialog stays open and a mapped error message is shown.
8. **AdminOnly access:** `/moderation/*` is behind the existing admin guard (`useAdminGuard` via `AdminShell`) and the route middleware; anonymous → `/login`, non-admin → 403/redirect. A real, active-aware **"Moderation" nav item** is added to `AdminSideNav`.
9. **RTL + i18n + a11y:** all copy (queue, statuses, sources, filters, review actions, errors) is bilingual EN+AR via `lib/strings.ts`; layout is logical-property based (works under `dir="rtl"`); table has caption + `scope="col"` headers + keyboard-activable rows; the review dialog traps focus, ESC cancels, backdrop does not dismiss; status announced via `aria-live`.

## Backend contract (EXACT — verified against merged code)

Route base: **`api/Admin/Moderation`** (resolved — the backend brief's `api/Moderation` OQ-5 is settled to the `Admin` prefix, matching `AuditController`'s `api/Admin/Audit`). All endpoints `[Authorize(Policy = AuthorizationPolicies.AdminOnly)]`. Envelope is `BaseResponse<T>` with success flag spelled **`Successed`**.

### `GET api/Admin/Moderation/Queue` → `BaseResponse<PaginatedResult<ModerationItemDto>>`
Query params (bound from `GetModerationQueueQuery`, **PascalCase** on the wire like the other admin hooks):
- `Status?` — enum `ModerationStatus` (Pending | Approved | Rejected | Flagged). Sent as the string name or int — confirm wire form (see OQ-3); other admin filters send ints for numeric enums, but this is a named enum. **Send the string name** ("Pending") to be safe and mirror persisted form.
- `Source?` — enum `ModerationSource` (AiOutput | CurriculumUpload).
- `SubjectCode?` — string (e.g. "Math", "Arabic").
- `Grade?` — int (1–12).
- `DateFrom?` / `DateTo?` — ISO date-time, inclusive bounds on `DetectedAt`.
- `Search?` — partial match on `ContentReference`.
- `PageNumber` (default 1), `PageSize` (default 20, backend clamps 1–100).

`ModerationItemDto` (list item — `Features/ModerationQueue/Dtos/ModerationItemDto.cs`):
```
{ id: number; sourceEventId: string /*guid*/; source: string; contentReference: string;
  studentId: number | null; taskKind: string | null; subjectCode: string | null; grade: number | null;
  status: string; safetyVerdict: string /*JSON string*/; detectedAt: string /*ISO*/; createdAt: string /*ISO*/ }
```

### `GET api/Admin/Moderation/{id:int}` → `BaseResponse<ModerationItemDetailDto>` (404 if missing)
`ModerationItemDetailDto` = `ModerationItemDto` fields **plus** review fields:
```
{ ...all ModerationItemDto fields,
  reviewedByUserId: number | null; reviewedAtUtc: string | null; reviewDecisionReason: string | null }
```

### `POST api/Admin/Moderation/{id:int}/Review` → `BaseResponse<ModerationItemDto>`
Request body `ReviewModerationItemRequest`:
```
{ decision: ModerationStatus; reason?: string }
```
- `decision` must be **Approved | Rejected | Flagged** — **never Pending** (validator rejects Pending as a decision).
- `reason` **required when `decision == Rejected`** (FluentValidation); max 2000 chars.
- Decision is the enum — send the **string name** ("Approved"/"Rejected"/"Flagged"), matching the persisted-as-string convention. (Confirm enum wire form in OQ-3; if the API binds by int, the order is Pending=0, Approved=1, Rejected=2, Flagged=3.)
- The **review actor is taken from the JWT**, not the body — the FE sends only `{ decision, reason }`, never an admin id.

### Status transitions (RESOLVED in code — `ModerationStatus` enum + handler)
- `Pending` → Approved | Rejected | Flagged
- `Flagged` → Approved | Rejected  (NOT → Flagged again)
- `Approved` and `Rejected` are **terminal** → re-review returns **400** (`ModerationItemAlreadyTerminal`)
- `Flagged` → `Flagged` returns **400** (`ModerationItemAlreadyFlagged`)

### SafetyVerdict JSON shape (the `safetyVerdict` string the FE must parse + render)
Produced by `AiOutputFlaggedEventHandler` for AI-source items:
```json
{ "failedChecks": ["ToxicityCheck", ...], "reasonCodes": ["...", ...],
  "actionTaken": "Blocked|Regenerated|FallbackReturned", "modelId": "..." }
```
- Render defensively: it is a free-form JSON **string** that may be `"{}"`, may have missing keys, and (for a future curriculum source) may differ. Parse safely, fall back to a raw/empty rendering, never crash. **`failedChecks`/`reasonCodes` are arrays of stable check/code names — safe to display; they are NOT raw content.**

## FE screens, components & states

### Routes (App Router, `app/(admin)/moderation/...`)
- `app/(admin)/moderation/page.tsx` — **queue list page** (mirror `app/(admin)/users/page.tsx` four-state pattern). `export const dynamic = 'force-dynamic'`. Self-wraps `<AdminShell title=...>`.
- `app/(admin)/moderation/[id]/page.tsx` — **item detail page** (mirror `app/(admin)/users/[id]/page.tsx`: full route page, self-wraps `AdminShell`, dynamic title). *Recommendation: a full route page, NOT a drawer* — it matches the established users/curriculum detail pattern and is simpler to test/route-guard. (The task file's "drawer/page" is satisfied by the page form; flag if the designer prefers a drawer — OQ-2.)
- Optional `layout.tsx` files mirroring `users/layout.tsx` / `users/[id]/layout.tsx` if a per-route title seam is needed.

### Components (new, mirroring existing shapes — no new abstractions)
- `ModerationQueueTable` (or inline in `page.tsx` like the users page) — table with columns: Source, Content ref, Subject/Grade, Task kind, Status badge, Detected-at; keyboard-activable rows → navigate to detail. Reuse the users-page table chrome (caption, `scope="col"`, shimmer skeleton rows, hover/active row styles, pagination control).
- `ModerationStatusBadge` — **extend the existing `StatusBadge`** with a new `variant="moderation"` (or a thin sibling) mapping `ModerationStatus` → colour (suggest: Pending=amber, Approved=green, Rejected=red, Flagged=indigo/orange). Keep the non-colour dot/shape signal (a11y rule already in `StatusBadge`). A `SourceBadge` (AiOutput / CurriculumUpload) may reuse the same chip shape.
- `ModerationReviewPanel` / detail body — renders item facets + a **SafetyVerdictView** that parses the `safetyVerdict` JSON and lists failed checks + reason codes + action taken + model id, with an explicit "automated safety signal — no raw content stored (v1)" note.
- `ReviewActions` — the Approve / Reject / Flag trigger buttons, gated by status (see AC 6).
- `ReviewItemDialog` (mirror `SuspendUserDialog`) — uses **`AdminConfirmDialog`** + **`ReasonField`** + **`AdminErrorBanner`**. One dialog parameterised by decision, OR three thin wrappers — recommend one dialog with a `decision` prop. `ReasonField` is `required` only when `decision === 'Rejected'`; confirm button disarmed until a reason is present in that case. `AdminConfirmDialog` has no exact-fit variant — add a moderation-appropriate `variant` (e.g. reuse `destructive` for Reject, `reactivate`/green for Approve, `archive`/amber for Flag) or add new additive variants (additive change, no structural rework — same as the P7-05 lifecycle variants did).

### Four-state handling (both list and detail)
Reuse the exact pattern from `users/page.tsx`: `isLoading` → skeleton; `isError` → `AdminErrorBanner` + retry button; success + empty → empty state; success + rows → table. Detail adds a 404/not-found state (item id missing). Use `isFetching && !isLoading` to dim during background refetch.

### Review flow (no optimistic update)
1. Admin opens detail (or acts from the row), clicks Approve/Reject/Flag → `ReviewItemDialog` opens.
2. Reject requires reason; submit calls `useReviewModerationItem`.
3. On success: invalidate `adminModeration.item(id)` + `adminModeration.all` (busts every list cache) → refetch → success banner/toast → dialog closes. New status comes from the refetch.
4. On error: map 400 (terminal / already-flagged) → "this item has already been resolved"; 404 → not found; 422 → validation; network → generic. Dialog stays open.

## Handoff → security-auditor (WARRANTED — flag for the lead)

This surface displays AI-safety flags tied to **children** (a `studentId`, subject, grade) and exposes a **state-changing review action**. Even though v1 shows reason-codes-not-raw-content, the child-safety sensitivity warrants a security pass. Verify:
- **AdminOnly** enforced on every moderation route (guard + middleware) — anonymous → login, non-admin → 403; no protected content flashes pre-guard.
- **PII-light preserved on the wire/UI** — the FE never requests or renders raw prompt/response; only reason codes, check names, opaque content refs, and loose ids are shown. No accidental logging of `studentId`/verdict to console/telemetry.
- **Review actor integrity** — the FE sends only `{ decision, reason }`; the admin id is never sourced from the client (backend reads JWT). No IDOR via body injection.
- **Terminal/immutable-ish review** — the FE must not offer (and the backend rejects) re-review of resolved items or re-flag; confirm the UI cannot construct such a request silently.
- **Reason field** — bounded to 2000 chars client-side (matches server), no injection sink in rendering.
- **Audit awareness** — every successful review emits the P7-12 `AdminActionPerformedEvent` server-side (FE writes no audit); confirm the FE does not assume/duplicate audit responsibility.
- Critical/High findings **block** the batch.

## Open questions / assumptions / risks (for the lead)

- **OQ-1 (raw content — v1 scope, KNOWN):** P3-02 stores no raw flagged content; the queue can only show reason codes + refs. **Assume reason-code-only review is sufficient for v1** (a quarantine store is a deferred separate story). Confirm the FE should clearly communicate "no raw content available (v1)" rather than imply a missing-data bug.
- **OQ-2 (detail: page vs drawer):** Task file says "drawer/page." **Recommend a full route page** (`moderation/[id]/page.tsx`) to match the established users/curriculum detail pattern and simplify route-guarding/e2e. Confirm before the designer commits, or let the designer decide.
- **OQ-3 (enum wire form — needs a quick verify, not a backend change):** `Status`/`Source`/`decision` are C# enums persisted as strings. Need to confirm whether the API binds query/body enums by **string name** ("Pending") or **int** (Pending=0…Flagged=3). **Recommend the FE send string names** (matches persistence + the curriculum hooks' habit of sending what the binder expects); the api-tester/e2e can confirm against the running API. This is a contract clarification, not a backend gap.
- **OQ-4 (subject/grade facets may be sparse):** the AI source currently may not populate `subjectCode`/`grade` (shipped nullable, per the BE OQ-3). The subject/grade **filters still exist** but may match few/no AI items until upstream enrichment lands. Confirm the filters should remain visible (recommend yes — they are spec'd in AC and serve the future curriculum source).
- **OQ-5 (toast vs banner for success):** existing admin dialogs close + the parent shows a banner (no global toast system observed). **Assume the same** (dialog closes → success banner on the detail/list), unless the designer introduces a toast.
- **OQ-6 (empty CurriculumUpload source):** filtering by `Source=CurriculumUpload` yields an empty list today (no producer). Confirm the empty-state copy should read as "no items" (not an error and not "coming soon") — recommend neutral empty copy.
- **Assumption:** mirror `users/page.tsx` (list), `users/[id]/page.tsx` (detail), `SuspendUserDialog` + `AdminConfirmDialog` + `ReasonField` (review), `useSearchUsers`/`useSuspendUser` (hooks) for ALL structure. No new design patterns introduced (CLAUDE.md rule #8).
- **Risk — over-disclosure:** the safety verdict is child-safety-adjacent; rendering must show only stable check/reason-code names, never echo any free-form field that could carry content. Security-auditor gate covers this.
- **Risk — stale status:** because there is no optimistic update, the UI must clearly reflect the refetch (loading state on the action) so an admin doesn't double-submit; the dialog's `isPending` spinner (as in `SuspendUserDialog`) covers this.
