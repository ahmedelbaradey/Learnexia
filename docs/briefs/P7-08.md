# Pipeline Brief — P7-08 Manage child profiles & grade overrides (Backend)

> Written by `analyzer` (2026-06-08). Backend-only brief for the Phase-7 Admin Console **User/Account wave**, story **P7-08**. Ground truth = the live **Identity** module + the merged **P8** learning-language seam on `feat/phase-7-backend`. Read-only audit; only the three brief files were written.

## Summary & traceability
- **One-line task:** Let an admin edit a child's harmless profile fields (UI language / country), override the child's **grade** (re-scopes curriculum, **preserves XP/badges/streaks/mastery history**, emits a new `ChildGradeChanged` event), and change the child's **`LearningLanguage`** through the existing confirm-gated fresh-start seam (`IChildAccountService.ChangeLearningLanguageAsync`) — never a naive field write.
- **User story:** `user-stories/Phase-7-Admin-Console/P7-08-manage-child-profiles-and-grade-overrides.md`
- **BE task file:** `tasks/Backend/Phase-7-Admin-Console/P7-08-BE.md` (BE-1..BE-7)
- **FR / SRS:** **FR-ADM-7** (SRS §4.9), Admin role SRS §3.
- **BRD goal:** **G5** (operability — fix onboarding mistakes without parent redo) + **G1** (correct adaptive scoping after a grade fix).
- **Phase / epic:** Phase 7 — Admin Console · Epic: Admin — User & Account Management · SP 5.
- **Product rules honored:** parent-driven onboarding (admin is a support override, not a new self-serve path); grade transition **preserves history**; learning-language change is the **same destructive confirm-gated flow as P8-04**; 4 subjects, no Social Studies; no teacher role.

## Business context & value
- **Who benefits:** admin/support, and indirectly the parent/child (correct a wrong grade or learning language chosen at onboarding without redoing it).
- **Value:** admin parity with the parent flows (P5-06 grade transition, P8-04 learning-language change) for support cases, with the same safety guarantees (confirm gate, history preservation, audit).
- **Success measure (from AC):** profile edits are harmless field updates; grade override re-scopes curriculum and preserves history via event; learning-language change runs the exact P8-04 fresh-start (hard-delete Math/Science attempts) only when confirmed; everything validated, admin-gated, audited.

## Acceptance criteria (testable)
1. Editing **`PreferredLanguage` (UI)** or **country** → plain field update, saved, reflected on profile, **no progress affected**.
2. Changing **`LearningLanguage`** (ar/en) **+ confirm** → goes through `IChildAccountService.ChangeLearningLanguageAsync` (NOT a field write): **hard-deletes the child's Math/Science attempts** (fresh start in the new-language trees), emits `LearningLanguageChangedIntegrationEvent`, re-stamps the `learning_language` JWT claim. Same warning + typed confirmation as P8-04. Arabic/English subjects pinned by subject, unaffected.
3. A `LearningLanguage` change **not confirmed** → **nothing deleted, field unchanged** (destructive path never runs without confirm) → **HTTP 424**.
4. **Grade override + confirm** → grade updates, curriculum/skill tree **re-scopes to the new grade** (same behavior as parent transition P5-06).
5. **History preserved:** XP, level, badges, streaks, past mastery **carry over, not deleted**; re-scope signaled to learning/gamification via integration event (`ChildGradeChanged`), no cross-module FK.
6. Invalid grade (outside 1–6) / unsupported language (`PreferredLanguage`/`LearningLanguage` outside ar/en) / invalid country → rejected with a clear validation message.
7. Every override/edit — including a `LearningLanguage` change — records **actor, timestamp, old→new, reason**, and is **audited** (P7-12, publish-only this wave).
8. Non-admin → 403 / anonymous → 401. Admin policy on all endpoints.

## Affected modules & data
- **Module:** `Identity` (owner) + `Shared.Contracts` (new `ChildGradeChanged` event) + consumers in `Learning`/`Gamification` (grade re-scope + the EXISTING learning-language fresh-start handlers, reused).
- **Existing on disk (verified — much of this is already built):**
  - `User.Grade` (nullable int), `User.PreferredLanguage` (full culture code), `User.Nationality` (= country), `User.LearningLanguage` (short ar/en) all exist.
  - **`IChildAccountService.ChangeLearningLanguageAsync(childUserId, newLearningLanguage)` is BUILT** (`IdentityChildAccountService.cs`): resolves child, same-language no-op, mutates + commits, **post-commit best-effort publishes `LearningLanguageChangedIntegrationEvent`**. P7-08's admin command **reuses this exact seam** — do NOT reimplement.
  - **`LearningLanguageChangedIntegrationEvent` + its Learning consumer are BUILT** (`Learning/.../LearningLanguageChangedIntegrationEventHandler.cs` → hard-deletes Math/Science attempts; Arabic/English + gamification retained). P7-08 BE-7 "reuse the same downstream handlers" is **already satisfied** — the admin path emits the same event and the same consumer fires.
  - **Confirm-gate (424) pattern is BUILT** in the **parent** flow (`Parent/.../ChangeLearningLanguageCommandHandler.cs`): `ConfirmFreshStart == false → BusinessValidation` (424) FIRST, then JWT parent + `IsLinkedAsync` (IDOR), then the seam. P7-08's admin command **mirrors this** but with **admin authz instead of parent-link IDOR** (an admin acts on any child, gated by `AdminOnly`, not by family link).
  - **`learning_language` JWT claim** is emitted in `AuthenticationIdentityService.GetClaims` and re-issued on every token generation/refresh. There is **no live claim-rewrite on an already-issued token** (stateless JWT — same constraint as P7-07 Q-B2). So "re-stamps the claim" means the NEXT token (refresh/sign-in) carries the new value; existing tokens carry the old value until refresh. Flag this (Q-C3).
  - `UpdateChildAsync` seam exists for FullName/Grade/Language/Country edits, but it mutates Grade as a plain field with **no event** — so it is **not** suitable for the grade-override path (which must emit `ChildGradeChanged`). Use it (or a new path) only for the harmless `PreferredLanguage`/country edit (BE-1).
- **Net-new:**
  - `ChildGradeChanged(ChildId, FromGrade, ToGrade, ChangedAtUtc)` integration event in `Shared.Contracts` (P7-08 **owns** this contract; P5-06 reuses it later) implementing `IIntegrationEvent`.
  - `UpdateChildProfileCommand` (BE-1: UI language + country), `OverrideChildGradeCommand` (BE-3, confirm + reason, emits `ChildGradeChanged`), `AdminChangeLearningLanguageCommand` (BE-6, confirm-gated, reuses the seam) + validators.
  - Grade re-scope **consumer(s)** in Learning (and Gamification if needed) for `ChildGradeChanged` — **net-new** (no consumer exists; P5-06 isn't built). See Q-C2.
  - `AdminActions` constants for grade-override + admin-language-change + profile-edit; `AdminActionPerformedEvent` publish.

- The only `Shared.Contracts` addition is the new event record (no DB).

## Handoff → backend-feature
- **`UpdateChildProfileCommand(int ChildId, string? PreferredLanguage, string? Country)`** (BE-1) → harmless field update. Validator: `PreferredLanguage` ∈ {ar,en} (normalized to culture code via existing `NormalizeLanguage`), country valid. **No event, no progress impact.** Admin-gated; no parent-link IDOR (admin acts on any child). Distinct from `LearningLanguage`.
- **`OverrideChildGradeCommand(int ChildId, int Grade, string Reason, bool Confirm)`** (BE-3/BE-4) → validate grade ∈ 1..6; set `User.Grade`; commit; **post-commit best-effort publish `ChildGradeChanged(ChildId, oldGrade, newGrade, UtcNow)`** (mirror `PublishLearningLanguageChangedEventAsync`). **History preserved** — this is a re-scope signal only; consumers must NOT delete XP/badges/streaks/mastery (contrast with the learning-language fresh-start). Decide whether grade override is confirm-gated (the AC says "confirm"; it's non-destructive, so confirm may be a UX guard rather than a 424 — Q-C1).
- **`AdminChangeLearningLanguageCommand(int ChildId, string LearningLanguage, bool Confirm)`** (BE-6) → **mirror the parent handler's guard order** but swap parent-link IDOR for admin authz:
  1. `Confirm == false` → **424** (BusinessValidation) FIRST — before any mutation/publish (it hard-deletes Math/Science attempts).
  2. Admin already gated by `AdminOnly` policy (no family-link check — admin may act on any child).
  3. Validate `LearningLanguage` ∈ {ar,en}; reject unsupported.
  4. Call `IChildAccountService.ChangeLearningLanguageAsync(childId, lang)` — the seam handles same-language **no-op success**, commit, and the post-commit `LearningLanguageChangedIntegrationEvent` publish (Learning consumer already hard-deletes Math/Science attempts). Map seam `NotFound → NotFound/Forbidden`, `LanguageUpdateFailed → BadRequest`, else success.
  5. Audit + (claim re-stamp is implicit via next token — Q-C3).
- **`ChildGradeChanged` consumer (BE-4 downstream):** add a Learning integration-event handler that re-scopes the child's curriculum/skill tree to the new grade **without deleting history** (e.g. recompute available skill tree for the new grade; mastery/XP rows untouched). Gamification likely needs no action (history preserved) — confirm (Q-C2). This consumer is **net-new** because P5-06 isn't built.
- **Audit (BE-5/BE-6):** publish `AdminActionPerformedEvent` (new `AdminActions.ChildGradeOverridden` / `ChildLearningLanguageChanged` / `ChildProfileUpdated` constants) with actor (JWT), child id, old→new in `Details`. Publish-only; honor the pre-commit→post-commit follow-up (prefer post-commit so a rolled-back change emits no phantom audit).
- **Conventions:** `ICommand<>` (validation fires); `BaseResponse<T>` / `Successed`; `NewResult(...)`; `ILoggerManager`; never echo `ex.Message`; cross-module via `Shared.Contracts` only.

## Handoff → frontend
- **Not in scope.** Later FE contract (`P7-08-FE`): `PATCH .../Users/{childId}/profile {preferredLanguage?, country?}`, `POST .../Users/{childId}/grade {grade, reason, confirm}`, `POST .../Users/{childId}/learning-language {learningLanguage, confirm}` (**unconfirmed → 424**). All `BaseResponse<...>`, admin-gated, validated. Route prefix shared with P7-06 (Q-A8 in P7-06 brief).

## Open questions / assumptions / risks (for the lead)
- **Q-C1 (grade-override semantics) — CLARIFY:** does an admin grade change use the **P8-style fresh-start/reset** (delete progress) or **preserve all progress**? **The story + product rule are explicit: PRESERVE history (XP/level/badges/streaks/mastery), re-scope curriculum only.** So grade override is **non-destructive** — unlike the learning-language change. Confirm the grade override therefore does NOT need a 424 confirm-gate (a plain confirm flag/UX guard suffices), and that no Math/Science attempts are deleted on a grade change. **Recommendation: grade override = re-scope + preserve; confirm is a soft UX gate (200 with confirm flag), not a 424.**
- **Q-C2 (`ChildGradeChanged` consumers):** since P5-06 isn't built, there is **no existing consumer** for the new event. What must actually happen on grade change in **Learning** (recompute skill-tree availability for the new grade — anything to persist?) and **Gamification** (likely nothing, since history is preserved)? **Decision: scope the consumer(s) P7-08 ships.** Recommendation: ship a Learning consumer that is effectively a no-op/recompute marker (the student's reads already scope by `User.Grade` at query time, so re-scoping may be automatic on next read — verify), and document that P5-06 will enrich it. **If learning reads already key off `User.Grade` live, the event may be informational/audit-only for now — confirm whether any persisted state needs grade-scoped rewriting.**
- **Q-C3 (claim re-stamp on grade/language change):** "re-stamps the `learning_language` claim" — verified there is **no live rewrite of an issued token** (stateless JWT; same G2 constraint as P7-07). The new value lands on the **next** token (refresh/sign-in). Confirm this bounded-staleness is acceptable (it matches the parent P8-04 behavior today). Same applies to a grade change reflected in any grade-derived claim (none exists today — grade isn't a claim). **Recommendation: accept next-token semantics, document it; do not block on a token-rewrite mechanism.**
- **Q-C4 (admin vs family-scope):** the parent flow gates on `IsLinkedAsync` (own child only). The admin flow gates on `AdminOnly` and acts on **any** child — confirm there is intentionally **no family-link restriction** for admins (i.e. an admin can change any child's grade/language for support). **Recommendation: yes — admin is unrestricted by family link, gated only by `AdminOnly` + audit. Confirm.**
- **Q-C5 (persisted grade-change history):** the AC says "old→new values … recorded and audited". Is the `AdminActionPerformedEvent.Details` string sufficient (publish-only, P7-12 consumer deferred), or does the lead want a persisted grade-change history row in Identity now? **Recommendation: rely on `AdminActionPerformedEvent` (no new table/migration); P7-12 builds the durable audit store.**
- **Q-C6 (`ChildGradeChanged` field shape):** task file specifies `{ ChildId, FromGrade, ToGrade, ChangedAt }`. Confirm it implements `IIntegrationEvent` (needs `EventId` + `OccurredOnUtc` like the other Identity events) and lives at `Shared.Contracts/Identity/` (alongside `LearningLanguageChangedIntegrationEvent`) rather than the task's suggested `Shared.Contracts/Events/` (that folder doesn't exist; the convention is per-domain folders). **Recommendation: `Shared.Contracts/Identity/ChildGradeChangedIntegrationEvent.cs`, add `EventId`/`OccurredOnUtc`.**
