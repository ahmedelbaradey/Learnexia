# Pipeline Brief — P5-06 Transition a child to a new grade (parent-initiated)

## Summary & traceability
- **Task (one line):** Give parents a self-service endpoint to move one of their linked children to a different grade (1–6), re-scoping the child's curriculum/skill tree to the new grade while **preserving all history** (XP, level, badges, streaks, mastery), with parent→child IDOR authorization and an audit record.
- **User story:** `user-stories/Phase-5-Parent-Analytics/P5-06-grade-transition.md`
- **BE tasks:** `tasks/Backend/Phase-5-Parent-Analytics/P5-06-BE.md` (BE-1..BE-5)
- **FE tasks:** `tasks/Frontend/student-app/Phase-5-Parent-Analytics/P5-06-FE.md` (FE-1..FE-3 — separate FE lead)
- **FR-IDs:** FR-ID-2 (extends — identity/profile grade field) + FR-LR-1 (learning re-scope)
- **BRD goal:** G1 (matched/adaptive learning content) + G4 (parent control/visibility)
- **Phase / Epic:** Phase 5 — Parent + Analytics (Week 8) · Epic: Parent & Analytics · SP 5
- **Module:** **Parent** (new parent-scoped command/endpoint) + **Identity** seam (grade-set + event publish), cross-module via **Shared.Contracts only**. No new module, no DB migration.

### Product-decision alignment
- Re-scope to new grade, **keep history** (story Notes "confirmed during grooming") — matches the CLAUDE.md grade-transition override exactly.
- Parent-driven: a **parent** initiates this, not an admin and not the student. The admin path already exists (P7-08 `OverrideChildGrade`); this is the **parent entry point** for the same mechanics.
- Overlapping mastered-skill auto-complete in the new grade is **DEFERRED** (current rule: new grade unlocks fresh, history retained). Do not implement auto-complete.

---

## Business context & value
- **Who benefits:** the **parent** (controls when a child moves up, e.g. start of a school year) and the **child** (content stays matched to their actual level). Admin already had this via P7-08; parents could not self-serve until now.
- **Value:** keeps adaptive content level-appropriate at year boundaries without support tickets / admin intervention; preserves the child's earned progress so a grade move is non-punitive (history carries over).
- **Success measures:** a linked parent can transition their own child; the child sees the new grade's skill tree on the next session; XP/badges/streaks/mastery rows are intact post-transition; non-owner attempts are rejected; invalid grades are rejected with a clear message.

---

## Acceptance criteria (testable)
1. **Re-scope on transition** — a linked parent confirms a transition → `User.Grade` updates → `ChildGradeChangedIntegrationEvent` fires → child's curriculum/skill-tree reads scope to the new grade on the next query. *(Re-scope is automatic: Learning reads grade at query time — see Handoff → Learning below.)*
2. **History preserved** — XP, level, badges, streaks, and mastery rows are NOT deleted/reset (they are keyed by userId in Gamification/Learning and untouched by a grade change); prior-grade weak areas remain available for spaced-repetition (P3-10).
3. **Authorization (IDOR)** — only a parent linked to that child can transition; a non-owner (or non-existent child) gets a **generic 403** that does not distinguish "not found" from "not yours" (anti-enumeration).
4. **Invalid grade** — target grade outside **1–6** is rejected with a clear, localized message → **HTTP 422**.
5. **Audited** — the transition is recorded with **actor (parent id), childId, old→new grade, timestamp**.
6. **Idempotent same-grade** — target grade == current grade → **success no-op**, no event published, no audit "change" (mirror the admin/no-op guards).
7. **Acting parent from JWT** — the parent id is always resolved from the JWT (`ICurrentUserService`), never from the request body.

---

## Affected modules & data
- **No new entities. No DB migration.** `User.Grade` (nullable `int`) already exists on the Identity `User` and is the only mutated field.
- **Parent module (writes the new feature surface):** new `TransitionChildGrade` command + handler + validator + response DTO + controller action. No new tables — the parent↔child link (`ParentStudent`, schema `parent`) already exists and is queried via `ILinkParentStudentService`.
- **Identity module (extends the existing seam):** add a grade-set method on the existing `IChildAccountService` that mutates `User.Grade` and publishes `ChildGradeChangedIntegrationEvent` (mirrors the existing `ChangeLearningLanguageAsync`).
- **Learning module:** **no change** — the existing `ChildGradeChangedIntegrationEventHandler` already consumes the event (currently a no-op stub because Learning reads scope by grade at query time; history is never touched).
- **Audit:** reuse the existing `AdminActionPerformedEvent` contract (best-effort publish) **or** a Parent-side equivalent — see Open Questions Q2.

### 5. The grade-set seam to call (cleanest reuse)
- **Existing seam interface:** `backend/src/Shared/Learnexia.Shared.Contracts/Identity/IChildAccountService.cs` — implemented by `backend/src/Modules/Identity/Learnexia.Modules.Identity.Infrastructure/Services/IdentityChildAccountService.cs`.
- **Key finding — there is NO grade-set seam that publishes the event yet:**
  - `IChildAccountService.UpdateChildAsync(UpdateChildRequest{...,Grade,...})` **does mutate `User.Grade`** but **does NOT publish `ChildGradeChangedIntegrationEvent`** (see `IdentityChildAccountService.UpdateChildAsync`, lines 107–130 — plain profile write, no publish). **Do NOT route the parent transition through `UpdateChildAsync`** — it would change the grade silently with no re-scope signal and no audit.
  - The closest correct template is **`IChildAccountService.ChangeLearningLanguageAsync(childUserId, newLearningLanguage, ct)`** (`IdentityChildAccountService` lines 160–197): resolve child → **same-value no-op success guard** (returns `IsNoOp = true`, no publish) → mutate + `UpdateAsync` (commits immediately, Identity has no UoW) → **best-effort post-commit publish** of the integration event (try/catch/log; publish failure never rolls back).
- **RECOMMENDED REUSE (cleanest):** add a new method to `IChildAccountService`, e.g.
  `Task<ChildGradeChangeResult> TransitionGradeAsync(int childUserId, int newGrade, int actingParentId, CancellationToken ct = default)`,
  implemented in `IdentityChildAccountService` as a near-clone of `ChangeLearningLanguageAsync`: resolve child (NotFound → mapped to 403 by the Parent handler) → no-op guard (newGrade == current → `IsNoOp=true`, success, no publish) → mutate `User.Grade` + `UpdatedAt`/`UpdatedBy=actingParentId` + `UpdateAsync` → best-effort publish `ChildGradeChangedIntegrationEvent(..., ChangedByAdminUserId: actingParentId)`. Return a shaped `ChildGradeChangeResult` (mirror `ChildLanguageChangeResult`: `Succeeded, ChildUserId, OldGrade, NewGrade, IsNoOp, ErrorCode`).
  - This keeps **all User-table mutation + event publish inside Identity** (where `User` and `IPublisher` live), keeps the Parent module free of Identity entities, mirrors the existing language-change reuse 1:1, and centralizes the publish so the audit + re-scope always travel together.
  - **Why not publish from the Parent handler?** The Parent module must not touch the `User` table and the mutation+publish must be atomic-ish/co-located; the existing convention (language change) publishes from the Identity seam. Keep grade consistent with it.

### 6. Audit pattern for sensitive actions
- **Contract:** `backend/src/Shared/Learnexia.Shared.Contracts/Admin/AdminActionPerformedEvent.cs` — `record (Guid EventId, DateTime OccurredAtUtc, int AdminUserId, string Action, string TargetEntityType, int TargetEntityId, string? Details)`. Best-effort publish, opaque ids only (no PII). Consumer = Moderation audit log (P7-12).
- **Action constants:** `backend/src/Shared/Learnexia.Shared.Contracts/Admin/AdminActions.cs` — existing `ChildGradeOverridden = "Child.GradeOverridden"` (admin). For the parent action, **add a new constant** (e.g. `ChildGradeTransitioned = "Child.GradeTransitioned"`) so the audit log distinguishes parent transitions from admin overrides. Adding a constant touches only `AdminActions.cs` (the file is intentionally string-constants for exactly this).
- **Caveat on the field name `AdminUserId`:** like the integration event, the audit event's actor field is named for the admin origin but is an opaque acting-user id. Pass the **parent** id. (Same semantic note as Q1.) See Open Question Q2 for whether a parent transition should publish `AdminActionPerformedEvent` at all vs a parent-scoped audit; **recommended: reuse `AdminActionPerformedEvent` with a `ChildGradeTransitioned` action + the parent id** — it is the only audit sink wired today.
- **Where to publish:** if the publish is co-located in the Identity seam (recommended), publish the audit event there alongside the integration event (mirror `OverrideChildGradeCommandHandler` which publishes both). Alternatively the Parent handler can publish the audit event after a successful seam call — pick one place; do not double-audit.

### 7. Grade validation (1–6 → 422)
- **Validator pattern:** FluentValidation `AbstractValidator<TCommand>` is auto-discovered for `ICommand<>` via `ValidationBehavior` (`backend/src/Shared/Learnexia.Shared.Kernel/Behaviors/ValidationBehavior.cs`) — **commands only, not queries**. On failure it throws `ValidationException`.
- **422 mapping:** `backend/src/Host/Learnexia.Host/Middleware/ErrorHandlerMiddleWare.cs` (lines 64–69) maps `ValidationException` → **HTTP 422 UnprocessableEntity** with a `BaseResponse` carrying `{ PropertyName, ErrorMessage }` errors. So a validator rule yields the AC4 422 automatically.
- **Rule to copy:** `RuleFor(x => x.Grade).InclusiveBetween(1, 6).WithMessage(SharedResourcesKey.ChildGradeOutOfRange)` + `RuleFor(x => x.ChildId).GreaterThan(0)` — identical to `OverrideChildGradeCommandValidator`. Localized keys already exist: `ChildGradeOutOfRange` (and for the no-op/ownership messages: `ChildGradeUnchanged`, `CannotEditChildNotInFamily`, `ParentChildNotAuthorized`) in `backend/src/Shared/Learnexia.Shared.Resources/SharedResourcesKey.cs` + `.en-US.resx` + `.ar-EG.resx` (ar + en both present).

## Open questions / assumptions / risks
- **Q1 (event field semantic) — RECOMMEND REUSE AS-IS:** `ChildGradeChangedIntegrationEvent.ChangedByAdminUserId` is named for the admin origin. For the parent path the actor is a parent. Recommendation: reuse the same event (do NOT create a parent-specific duplicate) and pass the parent id in that field, documenting that it is "the acting user id". An optional non-breaking doc-comment/param-rename is cosmetic. **Confirm the lead is OK reusing the field for a parent actor.**
- **Q2 (audit sink):** the only wired audit consumer today is `AdminActionPerformedEvent` (Moderation/P7-12). Recommendation: reuse it with a new `Child.GradeTransitioned` action + the parent id as `AdminUserId`. Acceptable to record a parent action through an "AdminAction"-named event, or does the lead want a distinct parent-audit channel? (No parent-side audit entity exists today.)
- **Q3 (route shape):** task suggests `POST /api/Parent/Children/{childId}/Grade`; existing in-module convention is verb-named `PUT api/Parent/Change-Learning-Language` with the id in the body. Recommendation: `PUT api/Parent/Children/{childId}/Grade` (RESTful, id from route, parent from JWT). **Confirm the preferred shape** (POST vs PUT; route id vs body id).
- **Q4 (server-side confirm gate):** the admin path has a soft `Confirm` flag (400 if false); the language-change path has a 424 `ConfirmFreshStart` gate because it is destructive. Grade transition is **non-destructive** (history preserved), so a server-side confirm gate is **not strictly needed** — the FE already mandates a confirmation dialog. Recommendation: **no server confirm flag** (keep the API simple; rely on FE dialog), matching the non-destructive nature. Confirm whether the lead wants a soft `Confirm` flag for parity with the admin path.
- **Q5 (re-scope is automatic, not eager):** AC1 "child sees the new grade's skill tree on their next session" is satisfied because Learning reads grade at query time — there is **no eager rebuild**. If the lead expects an eager/persisted re-scope materialization, that is NOT how the system works today and would be new scope. Recommendation: accept lazy re-scope (verified P7-08 finding); flag if the reviewer expects eager.
- **Assumption:** grade is NOT a JWT claim (verified in `OverrideChildGradeCommandHandler` note), so there is no token-staleness concern; the next read uses the new `User.Grade`. The child does not need to re-login.
- **Risk (IDOR — critical, child data):** the link check MUST run before any mutation and the 403 message MUST be identical for "not found" and "not yours". This is the single most important control; mandatory `security-auditor` per BE-5.

### Test scenarios for api-tester (BE-4)
- **Own child, valid grade → 200:** linked parent transitions own child to a new in-range grade → 200, response `oldGrade`/`newGrade` correct; `ChildGradeChangedIntegrationEvent` fired (skill-tree reads re-scope on next query); `AdminActionPerformedEvent(Child.GradeTransitioned)` fired with parent id + old→new in `Details`.
- **History intact:** after the transition, the child's XP/level/badges/streaks/mastery rows are unchanged (assert via the same Gamification/Learning seams the parent dashboard uses, or directly).
- **Non-owner → 403:** parent A transitions parent B's child → generic 403 (`CannotEditChildNotInFamily`); identical response for a non-existent childId (anti-enumeration — no 404, no distinguishable message).
- **Invalid grade → 422:** target grade 0 or 7 → 422 `ValidationException` envelope with the localized `ChildGradeOutOfRange` message; no mutation, no event.
- **Same-grade idempotent → 200 no-op:** target == current grade → success, `isNoOp = true`, NO `ChildGradeChanged` event published, no audit "change".
- **Unauthenticated / wrong role → 401/403:** no JWT → 401; a Student JWT → blocked by the controller role gate.
- **(ar + en):** error messages localized for both cultures (Accept-Language).
