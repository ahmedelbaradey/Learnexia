## Business context & value

- **Who benefits:** the **parent** (controls how much AI help each child gets, at a predictable monthly price) and the **business** (recurring revenue that funds the AI tutor runtime — the 199 EGP plan is the unit economics anchor in `ai-cost-routing.md`).
- **Value:** the plan is the **single source of truth** for the monthly energy allotment (P9-02 reads it). Without a plan model there is no way to decide how much energy a child gets each cycle. Free = 300, Premium = 3000 (config-driven via P9-11).
- **Family plan** keeps the model simple: a parent on Premium upgrades *all* their children at once. Per-child plans would multiply billing complexity and are deferred.
- **Success measured by:** a parent can read their current plan + compare benefits; upgrade takes effect per the agreed rule (immediate, pending payment) and downgrade at next cycle; P9-02's grant job reads the active plan and grants the right amount.

---

## Acceptance criteria (testable)

1. A parent can **view the current plan** (Free or Premium) and its status (active / pending / canceled / cycle-end date).
2. A parent can **compare Free vs Premium** benefits side by side — at minimum **monthly energy** (300 vs 3000) and **daily soft cap** (20 vs 150) — values read from config (P9-11), never hard-coded in the FE.
3. A parent can **upgrade** to Premium. Upgrade **takes effect immediately on successful payment** (P9-06); **without a successful payment the parent stays on Free** (no Premium entitlement is granted on an unpaid/declined attempt).
4. A parent can **downgrade** to Free; the downgrade **takes effect at the next billing cycle** (Premium access persists until cycle end).
5. The **active plan is the source of truth for the monthly grant** — P9-02's grant job resolves the allotment from the parent's active plan for each of their children.
6. The plan applies to **all of the parent's children** (family plan). Per-child plans are not modeled.
7. Plan and plan-change state are **persisted, family-scoped, and only the owning parent can read/modify their own plan** (no cross-account access).
8. Renders in **Arabic (RTL) and English (LTR)**; the surface lives in the parent area (the existing P2-12 "Plan & billing" settings tab, which today is a read-only stub — see Affected surface).

## Handoff → db-migration

- **New `Billing` module scaffolding** (Domain / Application / Infrastructure / Api projects mirroring Learning or Parent) — **only after lead sign-off**. New `BillingDbContext`, schema `billing`, `MigrationsHistoryTable("__EFMigrationsHistory", "billing")`, `UseNpgsql`, auto-migrate at startup via the module's `InitializeAsync` (mirror `LearningModule`).
- **Entities:** `Plan`, `Subscription` (fields above). All derive from the module's audited base (mirror an existing `AggregateRoot`/`FullAuditedEntity`). `ParentUserId` is a plain int/Guid loose id — **no navigation to Identity**.
- **EF config:** unique index on `Subscription.ParentUserId` (one active subscription per parent — confirm whether you keep history rows; if so the unique should be a filtered index on `Status = Active`). Seed the two `Plan` rows (Free, Premium) idempotently (mirror `LearningSeeder`).
- **No Unit of Work** (ADR 0001) — `GenericRepository` commits per call; for any atomic multi-write (e.g. activate Premium + write subscription) open an explicit transaction.
- This migration is the **foundation for P9-06/07/08/09 tables too** — coordinate with the P9-06 db-migration so the `BillingDbContext` + initial migration are created **once** (serialize the shared-file / module-scaffold edit per PARALLELISM).

## Handoff → backend-feature

- **Queries:** `GetCurrentPlan(parentUserId)` → current `Subscription` + resolved `Plan` benefits DTO; `GetPlanComparison()` → Free vs Premium benefit DTO (values from P9-11 config). Mirror existing CQRS query shape (`record XQuery : IQuery<BaseResponse<T>>`, handler inherits `BaseResponseHandler`, returns `BaseResponse<T>`, try/catch → `ServerError<T>`, inject `ILoggerManager`).
- **Commands:** `RequestUpgrade(parentUserId, planCode=Premium)` — creates/transitions a `Subscription` to `PendingPayment` and hands off to P9-06's checkout (returns a checkout session/redirect ref); on the P9-06 webhook success the subscription flips to `Active`. `RequestDowngrade(parentUserId)` — sets `PendingPlanCode = Free` + `Status = Downgrading`, effective at `CurrentCycleEnd`. `CancelSubscription` — stops future renewals, access to cycle end (coordinate with P9-06's recurring-cancel; may be the same command).
- **Commands are auto-validated** (`ValidationBehavior` runs for `ICommand<>`) — add FluentValidation validators. **Queries are not** — validate the parent id inside the handler.
- **Authz:** `[Authorize]` with a **family-scope / owning-parent** check — a parent may only read/modify their own subscription. Mirror P1-04/P1-05 family-scope semantics referenced by P2-12. **No teacher role.**
- **Contract for P9-02:** expose the active plan + allotment via `Shared.Contracts` (an `IPlanQuery`-style contract or a `PlanActivated` / `PlanChanged` integration event) so the grant job resolves the right amount without referencing Billing internals across a module boundary.

## Open questions / assumptions / risks

1. **NEW `Billing` module — needs lead sign-off** (CLAUDE.md "ask before new modules"). All of P9-05..11 share it. Resolve before any scaffolding.
2. **Proration on upgrade** (story AC + Notes mark it an open question). Does an immediate mid-cycle upgrade grant a prorated top-up of energy now, or only affect the next cycle? P9-02 says "a plan change mid-cycle affects the **next** grant." **Recommendation/assumption:** upgrade activates Premium *access* immediately on payment but the **energy grant difference is applied at the next cycle** (no mid-cycle proration of credits) — simplest and consistent with P9-02. **Confirm with lead.**
3. **Plan source of truth split:** is `Plan` a seeded Billing table or purely the P9-11 config store? Recommend a seeded `Plan` table whose tunable numbers come from P9-11 config. Confirm.
4. **Family plan vs per-child** — story confirms family plan; per-child is out of scope. Flag if product later wants per-child (would change the `Subscription` grain).
5. **Where does the P9-02 grant job live** (inside Billing vs another module)? Affects the `Shared.Contracts` seam. Recommend inside Billing.
6. **Upgrade↔P9-06 ordering:** P9-05 is "blocked by P9-01" and P9-06 is "blocked by P9-05" — they must be built as a tight pair (plan model first, then the paid-activation webhook completes it). Planner should sequence P9-05 → P9-06 and treat the Premium-activation AC as jointly delivered.
