## Business context & value

- **Who benefits:** the **student** directly — the hearts counter introduces a soft, kid-safe consequence for guessing/rushing. The "lose all hearts → Practice Mode" branch keeps them in the app (no hard block, no shame) while protecting the integrity of XP/streak rewards. The 30-minute lazy refill creates a tiny re-engagement nudge.
- **Why it matters now:** without hearts, there is no consequence side to the loop — every Phase-3 reward feels free, and careful answering is unrewarded. P4-09 (re-engagement notifications) can fire "hearts back, come practice" once P4-04 ships the regen timer. P4-08 (gamification screens) renders the heart counter + the Practice-Mode banner. The FE student-app already has a `Hearts` slot in `DashboardHeader` waiting for real data (HANDOFF L15).
- **Success measurement:** every `AnswerSubmittedIntegrationEvent` with `CorrectAnswerCount == 0` writes exactly one `HeartLoss` row AND decrements `Hearts` by 1 (when not already in Practice Mode); a brand-new student starts with `Hearts == Cap == 5`; hearts at 0 = `InPracticeMode == true` and the dashboard's `InPracticeMode` flag flips to `true`; subsequent answers / lessons in Practice Mode do NOT lose further hearts AND do NOT award XP / advance streak; a redelivered event (same `EventId`) is a no-op (idempotent on `(OriginEventId)` unique key); after `RefillIntervalMinutes` (default 30 min) elapses since `LastHeartRefillAtUtc`, the lazy refiller computes `+1` heart on the next read; dashboard's `Hearts` is consistent within p95 < 500ms.
- **Deterministic principle (BRD §8 / FR-AI-6):** the hearts rule is **pure arithmetic + a clock comparison** — no AI, no randomness. The cap + interval are config.

## Acceptance criteria (verbatim from story + testable backend gates)

From `P4-04-hearts-and-practice-mode.md`:

1. **AC1 — A student starts a session with a set number of hearts; a wrong answer deducts one.**
   - Backend gate: brand-new student → `StudentXpProfile.Hearts == Cap == 5` lazily on first read (the profile is created lazily on first XP/streak/hearts event — `Hearts` defaults to `Cap` in the factory `CreateFor(int studentId)` OR is set to `Cap` on first heart-loss via `LazyHeartRefiller`). On a wrong `AnswerSubmittedIntegrationEvent` (`CorrectAnswerCount == 0`), the `AnswerSubmittedIntegrationEventHandler` sends `LoseHeartCommand`; the handler decrements `Hearts` by 1 (floor 0), writes a `HeartLoss` row idempotent on `(OriginEventId)`, and (when `Hearts` reaches 0) raises `HeartsDepletedDomainEvent`. Idempotency: re-delivering the same event leaves `Hearts` unchanged.

2. **AC2 — When hearts reach zero, the student enters Practice Mode rather than being hard-blocked.**
   - Backend gate: **Practice Mode is a computed state**, not a stored flag — `bool InPracticeMode => Hearts == 0` (cheap derived property on `StudentXpProfile`). Lessons remain **fully attemptable** (no 403 / no lesson-start block — Learning module is untouched on that path; see Q4). Inside Practice Mode:
     - **No XP award** — `AwardLessonCompletedXpCommandHandler` and `AwardAnswerSubmittedXpCommandHandler` check `profile.InPracticeMode` before writing the `XpAward` row + `ApplyAward`, and short-circuit with `Success(Unit.Value)` + a log line when true.
     - **No streak advance** — `AdvanceStreakCommandHandler` checks the same flag and short-circuits.
     - **No further heart loss** — `LoseHeartCommandHandler` short-circuits when `Hearts == 0` (no row written, no event raised).
     - **Lessons attemptable** — Learning's `StartAttemptCommandHandler` / `SubmitAnswerCommandHandler` do NOT consult Practice Mode (zero coupling from Learning → Gamification on the write path; module isolation).

3. **AC3 — Hearts-remaining is stored on the profile and shown in the lesson/quiz UI.**
   - Backend gate: `Hearts` (int, 0..Cap) lives on `StudentXpProfile` (mirrors P4-03 precedent of extending vs creating a sibling entity). Dashboard reads via new `IStudentHeartsQuery` in `Shared.Contracts/Gamification/`. The lesson/quiz UI consumes the same `DashboardDto.Hearts` value (P4-08 owns the visual treatment; this story just delivers the data). **The lazy refill is computed at READ time** — `IStudentHeartsQuery.GetByStudentIdAsync` applies `LazyHeartRefiller.Refill(stored, lastRefillAt, now, cap, interval)` before returning the snapshot, and **persists the refill** if it crossed an interval boundary so the next read isn't re-doing the math (Q1 — pull-model).

4. **AC4 — Heart loss is triggered by the `AnswerSubmitted` event (P4-01), consistent with instant feedback (P2-07).**
   - Backend gate: heart-loss path is **exclusively** the `AnswerSubmittedIntegrationEventHandler` → `LoseHeartCommand` → `LoseHeartCommandHandler`. No other code path writes hearts. The handler **subscribes to the existing event** — no new integration event is added (P2-07's contract is sufficient).

   ```csharp
   public static (int Hearts, DateTime? NewLastRefillAtUtc) Refill(
       int storedHearts, DateTime? lastRefillAtUtc, DateTime now, int cap, int intervalMinutes)
   ```
   - If `storedHearts >= cap` → return `(storedHearts, null)` (clock idle).
   - If `lastRefillAtUtc is null` → return `(storedHearts, null)` (clock not running).

## Open questions / assumptions / risks

> Listed in priority order. Defaults are recommendations the lead can `APPROVE DEFAULTS` to greenlight.

**Top open questions (decision-shaping):**

**Q1 — Heart-refill mechanism: pull (lazy on read) vs push (Hangfire job).**
- **Recommend PULL (lazy on read).** Standard for this UX. `IStudentHeartsQuery.GetByStudentIdAsync` computes the current hearts from `(storedHearts, lastRefillAtUtc, now, cap, interval)` via the pure `LazyHeartRefiller`. The write-on-write path (the `LoseHeartCommand` handler) does the same refill before decrementing — so a student who's been idle 90 min sees `5 → 4` instead of `3 → 2`.
- **Why pull over push:** (a) cheaper (no Hangfire job thrashing every 30 min over potentially millions of profiles), (b) consistent (dashboard read = source of truth), (c) reuses the P4-03 sweep-job slot for a future P4-09 nudge job. Push wins only if we need a precise "your hearts are back!" push notification at the exact 30-min mark — that's a P4-09 concern, not P4-04.
- **Q1.bis — persist-on-read?** **Recommend YES** — when the lazy refiller returns a non-zero delta, the query persists `(Hearts, LastHeartRefillAtUtc)` via `ExecuteUpdateAsync` before returning. Avoids the surprise of "dashboard shows 5 but DB shows 3" until the next event lands.

**Q2 — Heart cap + refill interval defaults.**
- **Recommend: `Cap = 5`, `RefillIntervalMinutes = 30`.** Industry-standard Duolingo-style values. **Confirm with lead.** Alternatives: `Cap = 3` (harsher, fewer wrong answers tolerated) or `RefillIntervalMinutes = 60` (slower regen, more notification-bait for P4-09). All config-driven via `HeartsOptions` so the dial is tunable per env without code change.
- **Q2.bis — does losing a heart RESET the refill clock?** **Recommend YES** — `profile.LoseHeart()` updates `LastHeartRefillAtUtc = occurredAtUtc` (Duolingo behavior). Without this, a student at 4 hearts who lost the heart 25 min ago would see the next refill in 5 min from now — surprising. With the reset, the timer is always 30 min from the most recent loss. **Confirm.**

**Q3 — Does correct answer in Practice Mode regen +1 heart?**
- **Recommend YES, default `RegenOnCorrectAnswerInPracticeMode = true`.** "Practice your way out" is kid-friendly + reinforces the learning loop (the punishment teaches without trapping). Single line of code. Toggleable via config so we can A/B later.
- **Alternative: NO** — student waits for the timer, no shortcut. Cleaner separation, but the UX is harsher and the regen-on-correct path is what makes Practice Mode feel rewarding.
- **Alternative: configurable threshold** (e.g., +1 heart per 3 correct answers in Practice Mode). Over-engineered for P4-04; defer.

**Q4 — Where does the Practice-Mode gate live?**
- **Recommend HANDLER-SIDE, in each of the 3 reward command handlers.** Mirrors the existing `if (alreadyAwarded) return Success(0)` pattern in `AwardLessonCompletedXpCommandHandler`. Each handler already loads `StudentXpProfile`; adding `if (profile.InPracticeMode) return Success(0);` is 2 lines. Co-locates the reward suspension with the reward logic.
- **Alternative — Learning-side gate** (lesson START blocked when in Practice Mode): rejected; (a) couples Learning to Gamification (module isolation), (b) story explicitly says "rather than being hard-blocked" — lessons must be ATTEMPTABLE in Practice Mode.
- **Alternative — domain-level gate** (`StudentXpProfile.ApplyAward` refuses when in Practice Mode): rejected; pushes UX policy into the domain entity which then can't be easily turned off for admin paths (future).
- **Alternative — pipeline behavior** (`PracticeModeBehavior<TRequest, TResponse>` in MediatR pipeline): rejected per rule 8 (no new design pattern without lead approval); the handler-side gate is the simpler shape.

**Q5 — Audit table: separate `HeartLoss` vs reuse `XpAward` with `Reason=HeartLoss`?**
- **Recommend separate `HeartLoss` table.** Reasons: (a) `XpAward` semantically writes XP amounts; abusing `Amount = 0` + a new `Reason` value mixes concepts; (b) `HeartLoss` carries data `XpAward` doesn't need (`HeartsAfter` snapshot for forensics); (c) clear single-purpose audit trail; (d) keeps `XpAward` ledger pure (XP-only) for analytics queries; (e) tiny — one table, two indexes; mirrors P4-03's choice to NOT spawn a `StreakActivity` log table (so this is a small departure, but justified by the audit-tier need).
- **Alternative — extend `XpAward`** with `HeartsAfter` etc.: pollutes the table; reject.
- **Alternative — no audit table, just decrement the counter**: no forensics for support cases ("my child was unfairly put in Practice Mode"). Reject; cost is small.
