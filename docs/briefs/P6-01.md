This is a **tooling/perf-harness** brief: no product behaviour changes except surgical BE-5 hotspot fixes (each re-measured, existing suites must stay green). No new module. No migration unless a fix demands an index (flag it).

## Business context & value
- **Who benefits:** students (responsive quiz loop, dashboard, AI helper), and the platform owner (a credible, repeatable performance gate before launch).
- **Value:** NFR-1 is the launch performance contract. A repeatable harness catches egregious hotspots (N+1, missing index, over-fetch) **before** prod and gives devops a ready-made procedure for the authoritative staging/prod-scale + live-AI run.
- **Success measure:** every core-API scenario reports p50/p95/p99 + throughput + error-rate at a documented concurrency; PASS/FAIL vs the 500 ms p95 SLO; ranked hotspot list; quick wins fixed + re-measured; the run is reproducible from a documented script.
- **Honesty caveat (carry into every artifact):** local baseline numbers are **relative/directional** (single box, Testcontainers/seeded PG, in-process-ish). They validate the harness and surface hotspots; the **authoritative** pass/fail is a staging/prod-scale run, and the AI **< 4 s** number needs **live keys** — both are devops.

## How to run the Host locally for a load test (verified)
- **Start Kestrel:** `dotnet run --project backend/src/Host/Learnexia.Host` (env defaults to `Development`).
- **Default URLs (`launchSettings.json`):** `http` profile → `http://localhost:5080`; `https` profile → `https://localhost:7080;http://localhost:5080`. Default solution-run is the `http` profile → **base URL `http://localhost:5080`** (use plain HTTP for the load test to avoid the TLS-handshake tax skewing latency; HTTPS is available but `UseHsts()` is on).
- **Required config (`appsettings.json` / overrides):**
  - `ConnectionStrings:Default` — committed default `Host=localhost;Port=5432;Database=Learnexia;Username=postgres;Password=admin`. Point a local Postgres here (or override via `appsettings.Development.local.json` / `ConnectionStrings__Default` env var; the Host loads a gitignored `appsettings.{Env}.local.json`).
  - `JwtSettings:Secret` — committed dev placeholder is present and usable in **Development** (the `GuardJwtSecret` startup throw only fires in Production/Staging). No action needed locally.
  - `ConnectionStrings:Redis` — **empty by default → in-memory fallback** for distributed cache, `IConnectionMultiplexer`, and rate-limit stores. **Important for the perf story:** Gamification XP/streak/league (#9,#10) use Redis when present. To exercise the **real Redis hot path** (the point of those scenarios), set `ConnectionStrings__Redis=localhost:6379` and run a local Redis; otherwise those endpoints hit the DB/in-memory fallback and the numbers are not representative of the prod hot path. Document which mode the baseline used.
- **Migrations auto-apply on startup — YES.** `Program.cs` (lines ~278-290) runs each module's `InitializeAsync`/`SeedAsync` inside a startup scope; each calls `Database.MigrateAsync()`. So a fresh DB is schema-ready after one `dotnet run`. **A perf run can target a freshly-started Host with no manual `dotnet ef database update`.**
- **Curriculum seed auto-applies in Development only.** `LearningModule.InitializeAsync` calls `LearningSeeder.SeedAsync` **only when `env.IsDevelopment()`** — it seeds all 6 grades × 6 subject trees (Math/Science in ar+en, Arabic ar, English en), units/lessons, skill graph, demo lesson content, and boss lessons. So running the Host in Development gives you a realistic curriculum read surface (subjects/lessons/skill-tree) for free. Identity seeds roles + `superadmin` (and dev `basicuser`) at startup.

**Rate-limit gotcha (load-bearing for the harness):** the global IP rule is `Endpoint "*", Limit 200, Period "1m"` in **every** environment including Development (`ServiceExtensions.ConfigureRateLimitingOptions`). A single-box NBomber run that exceeds ~200 req/min from one source IP **will get 429s** and corrupt the numbers. Three mitigation options (pick one, document it):
  1. Run the Host in the **`Testing`** environment — but note: the **integration-test factory** neutralises the limiter (`IpRateLimitOptions` → `int.MaxValue`), *not* `appsettings`. There is no committed `appsettings.Testing.json` that disables it, so `ASPNETCORE_ENVIRONMENT=Testing dotnet run` does **not** by itself lift the cap. (Also: Testing skips the Dev-only curriculum seed.)
  2. Add a gitignored `appsettings.Development.local.json` (or a dedicated perf profile) that sets a very high `*` limit for the perf run only — non-committed, dev-only, mirrors the existing local-override mechanism.
  3. Run NBomber **in-process via `WebApplicationFactory`** (the factory already lifts the limiter) — see the in-process vs Kestrel recommendation below.

## Realistic seed data — how a scenario gets what it needs (verified)
The canonical, code-proven flows (mirrored from `P2_06_StartAttempt_Tests`):

- **Curriculum (lessons/subjects/skill-tree):** running the Host in **Development** auto-seeds the full tree via `LearningSeeder`. For the in-process factory route (which uses the `Testing` env and does **not** run the Dev seed), the harness must seed its own minimal hierarchy in a warmup step — the test does this with a `SeedLessonAsync` (Grade→Subject→Unit→Lesson) + `SeedQuestionsAsync` against `LearningDbContext` via a DI scope.
- **A valid student account (with grade):** **parent-driven onboarding** is the only path. Warmup:
  1. `POST /api/Users/Authentication/Register-Parent` body `{ Email, Password, AcceptedTerms:true }` → returns `data.accessToken` (parent JWT) + `data.userId`.
  2. `POST /api/Parent/Add-Child` (parent JWT) body `{ FullName, Email, Password, Grade, Language:"ar", Country:"EG", LearningLanguage:"ar" }` → creates a Student-role account, returns `data.id` (childId).
  3. `POST /api/Users/Authentication/Sign-In` `{ UserName:<childEmail>, Password }` → Student JWT.
- **A lesson/quiz with questions to StartAttempt against:** in Development, use a seeded lesson id (resolve via `GET /api/learning/Subjects/ForGrade` → `GET /api/learning/Subjects/{id}/Lessons`). For the in-process route, seed a lesson + ≥1 `QuizQuestion` directly via `LearningDbContext` in warmup (the StartAttempt handler does an existence `AnyAsync` on the lesson; SubmitAnswer needs a real `questionId`).
- **A parent with a linked child:** the Register-Parent → Add-Child flow above already produces a linked (parent, child) pair; the parent JWT + returned `childId` drive endpoints #11/#13. `GET /api/Parent/My-Children` can re-discover linked child ids during warmup.
- **Admin JWT:** sign in as the seeded `superadmin` / `123Pa$$word!` (constants used across the integration suite).

**Most reliable recipe:** a one-time **warmup phase** in the harness that (a) registers 1 parent + N children via API, (b) seeds (or resolves) 1 lesson with M questions, (c) signs in to collect student/parent/admin JWTs, (d) caches `{studentToken, studentId, parentToken, childId, lessonId, questionId, subjectId}` for the load phase. Register-via-API is the most robust because it works identically in-process and against Kestrel and never depends on the Dev seed being present.

## AI-path scenario (< 4 s is devops — be explicit)
- The AI gateway is **real** (Claude/OpenAI providers); with **no API keys** it **fails-closed** → `AiError.Unavailable`, surfaced as an SSE `event: error` frame. So a live-Host AI scenario without keys measures the **refuse/redirect/error pipeline overhead** (auth → validation → rate-limit → safety-layer fail-closed → SSE write), **not** model latency.

## "What good looks like" per scenario (api-tester-style)
- **Sign-In (#1):** p95 < 500 ms at target concurrency; ~0% errors; returns 200 + `data.accessToken`. (BCrypt/Identity password verify is the likely cost — watch tail latency.)
- **StartAttempt (#2):** p95 < 500 ms; resume path (existing attempt) should be cheap; watch for N+1 across questions and the lesson-existence check.
- **SubmitAnswer (#3):** p95 < 500 ms; server-side correctness + persistence; watch the per-answer write + any mastery/event fan-out cost.
- **ForGrade / Lessons / SkillTree (#4–6):** reads p95 < 500 ms; **SkillTree (#6) is the heaviest** (per-student engine-derived NodeState) — prime hotspot candidate; verify `AsNoTracking` + a server-side projection (no client-eval), index on the filter columns.
- **Dashboard (#7):** p95 < 500 ms; composes XP/streak/missions/league/continue — watch for multiple sequential cross-aggregate reads (candidate for parallelism or caching). Redis-on vs off changes this materially.
- **Gamification XP/League (#9,#10):** p95 well under 500 ms with **Redis on** (hot path); with Redis off these read the DB/in-memory — document which.
- **Parent reads (#11,#12,#13):** p95 < 500 ms; each runs the IDOR guard (`IsParentOfChildAsync`) + seam fan-out — watch for serial seam calls.
- **AI Explain/Hint (#15,#16):** local = pipeline overhead only (target small, non-blocking); errors are expected SSE `error` frames when keys absent (that is the correct dormant behaviour). Live < 4 s = devops.
