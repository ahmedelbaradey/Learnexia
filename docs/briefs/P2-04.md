# Pipeline Brief — P2-04 Unlock lessons by prerequisite / mastery (Learning Path Engine)

## Summary & traceability
- **Task (one line):** Build a deterministic **Learning Path Engine** that derives each lesson's lock/unlock state for a given student from the **P2-11 prerequisite graph** (`KnowledgeNode` / `KnowledgeEdge`) and the **P2-08 mastery signal** (per-skill accuracy from `StudentAnswer` aggregates), explains which prerequisite is missing, and is reproducible for the same inputs — replacing the static `Lesson.IsLocked` placeholder that P2-02 currently surfaces through `NodeState`.
- **User story (source of truth):** `user-stories/Phase-2-Learning-Core/P2-04-unlock-rules-learning-path-engine.md`
- **Task file:** `tasks/Backend/Phase-2-Learning-Core/P2-04-BE.md` (BE-1..BE-5; **backend/infra only — no Frontend tasks**)
- **FR-IDs:**
  - **FR-LR-3** (primary) — "Lessons shall unlock based on mastery/prerequisite rules from the Learning Path Engine."
  - **FR-AI-6** (constraint) — "AI shall **not** decide progression, difficulty, or unlocking — only generate content." → P2-04 is deliberately rule-based.
  - **FR-AD-3** (signal) — "Mastery shall be rule-based: ≥80% = mastered, <50% = needs remediation." → P2-04 reads `Skill.MasteryThreshold` per-skill (seeded values are 70–85, see Risks); the 80/50 in FR-AD-3 is the Phase-3 mastery-state machine baseline, not a hardcoded gate here.
  - **FR-CI-3** (seam consumed) — the P2-11 prerequisite graph; P2-04 is its first real consumer.
  - **FR-LR-2** (surfaced) — node states locked/unlocked/completed (P2-02 placeholder; P2-04 replaces the derivation).
- **BRD goal / epic:** **G2** Learning outcomes (primary). Epic: Learning Module / Curriculum & Learning Core.
- **Phase / sprint:** Phase 2 — Learning Core (Week 3–4). **SP 5.** Wave 8 (parallel sibling: P2-07 instant answer feedback).
- **Product-decision context:** 4 subjects (Math/Science/Arabic/English); no Social Studies; no teacher role; parent-driven onboarding (irrelevant here — the engine only needs StudentId). **Per-child grade transition preserves history** — this engine is stateless per call, so a grade change re-scopes which lessons are evaluated but does not invalidate captured mastery signals.

## Business context & value
- **Who benefits:** the **student** (clear "next thing to do," no random/sequence-only locking; missing-prereq message explains *why* something is locked) and indirectly the **parent** (the dashboard surfaces a sensible progression) and **content/admin** (validates that the P2-11 hand-authored graph is doing real work).
- **Why it matters:** P2-04 is the **first integration point** of three Wave-7-merged seams (P2-11 prereq graph, P2-08 mastery signal, P2-02 skill-tree query) — without it, those seams are unused, and the platform still locks/unlocks lessons via the static `Lesson.IsLocked` boolean from the demo seed. It is the **core differentiator** called out in the user story (and worth 5 SP for a backend-only deterministic engine).
- **Why deterministic (no AI):** FR-AI-6 architectural principle — *engines* decide progression, AI only generates content. The same `(studentId, subjectId)` inputs must always produce the same outputs (AC4) so the system is debuggable, explainable, and re-computable on demand.
- **Success measure (testable):** for a seeded student in a seeded subject, the engine returns `NodeState` per lesson; mastering all prereq skills of a skill flips its dependents from `Locked` → `Available`; locked lessons carry a `MissingPrerequisites` list naming each unmet skill + current/required accuracy. Repeated calls return identical responses.

## Acceptance criteria (testable)
Restated verbatim + clarifications:

1. **AC1 — Deterministic engine.** The Learning Path Engine determines lock/unlock state from prerequisite and mastery rules (deterministic, not AI). *(verbatim)*
2. **AC2 — Mastery flips dependents.** Given a student completes a lesson **and** meets a skill's mastery threshold, dependent lessons (lessons whose skill is downstream in the prereq graph) become `Available`. *(verbatim; "meets … mastery threshold" interpreted per Q2 default below)*
3. **AC3 — Missing-prereq explanation.** Given prerequisites are unmet, the lesson stays `Locked` and the engine can **explain which prerequisite is missing** (per-locked-skill list of `{prereqSkillId, prereqSkillName, requiredAccuracy, currentAccuracy}`).
4. **AC4 — Reproducible.** Unlock decisions are reproducible for the same inputs — i.e. given identical `(studentId, subjectId)` and identical underlying state (StudentAnswers + Skill thresholds + KnowledgeEdges), the engine returns identical output (no clock-dependent / no random / no AI in the path). Unit tests exercise this.

## Open questions for the lead — recommended defaults
> Default recommendation: **"approve all defaults"** ships a coherent v1; pick differently only where noted.

### Q1 — Unlock formula: AND across prerequisites? Or weighted by Strength?
**Recommended default:** **AND** — a lesson is `Available` iff **all** Prerequisite-typed `KnowledgeNode`s of its skill's node are mastered (per Q2's mastery definition). `Strength` is ignored in v1 (always treated as a hard prerequisite even when < 1.0); the field stays on the schema for future weighted-unlock experiments (e.g. P3-08 adaptivity).
**Why:** simplest deterministic rule, matches what the P2-11 seed authored (all edges Strength=1.0), aligns with FR-AD-3's binary mastered/not-mastered framing, easiest to explain to a student ("you still need X"). Weighted unlocks open a tunable surface the product hasn't specified.

### Q2 — "Mastered" definition for a skill (the mastery threshold semantics)
**Recommended default:** a skill is **Mastered for a student** iff **`GetSkillStatsQuery.AccuracyPercentage >= Skill.MasteryThreshold`** AND **`TotalAnswers >= 1`**. `MasteryThreshold` is an **int 0..100 interpreted as a percentage** (confirmed by reading `LearningSeeder`: values are 70/75/80/85).
**Why:** reuses the P2-08 signal verbatim, no new aggregation path; the `TotalAnswers >= 1` guard avoids "0% accuracy on 0 answers" being treated as below threshold for `MasteryThreshold == 0`. **Note:** FR-AD-3 says ≥80% = mastered — the seeded thresholds (70..85) are subject-tuned and *override* the 80% baseline per-skill, which is the correct design (P3-09 will formalize the mastery state machine).
**Alternative if rejected:** require N correct answers minimum (e.g. ≥3 correct AND accuracy ≥ threshold) to avoid "1 lucky answer = mastered."

### Q3 — Lessons without a `SkillId` (nullable in seed: 3 Math lessons per grade)
**Recommended default:** lessons with `SkillId == null` are **`Available` by default** — there is no skill to gate on, so they cannot be locked by mastery rules.
**Why:** the seed treats them as fill-in content; locking them would require inventing a non-skill prerequisite (sequence-order? unit completion?), which the user story does not ask for. **Caveat:** their `Completed` state is still derivable from any `Attempt` for that `LessonId` (Q5).
**Alternative if rejected:** fall back to sequence rule — locked unless the previous lesson (by `Unit.SequenceOrder` × `Lesson.SequenceOrder`) is Completed.

### Q4 — Lessons whose skill has no Prerequisite edges
**Recommended default:** **`Available` by default** — no prereqs to satisfy means the lesson is an entry point.
**Why:** matches the P2-11 seed model where root nodes (e.g. "Count to 1000 (G1)") have no inbound prereq edges and are deliberate starting points; matches the user story phrase "always have a clear next step." Without this rule, an empty graph would lock everything.

### Q5 — `Completed` state derivation for a lesson
**Recommended default:** a lesson is **`Completed`** for a student iff there exists **at least one `Attempt` with `LessonId == lessonId` AND `StudentId == studentId` AND `Status == AttemptStatus.Completed`**. Accuracy on the attempt is **not** required for `Completed` — accuracy gates *mastery* (Q2), which is the skill-level signal that drives downstream unlocks.
**Why:** `Status == Completed` is the explicit terminal state P2-08 sets; coupling `Completed` to accuracy would conflate two concepts (the student finished the quiz vs. they're good at the skill). A low-accuracy `Completed` attempt still results in "lesson Completed, skill not yet Mastered, downstream lessons stay Locked" — which is the right behavior.
**Alternative if rejected:** Completed requires `Status == Completed AND AccuracyPercentage >= SomeBar` (e.g. 50%). Not recommended — muddies the model.

### Q6 — Where the engine lives (shape + location)
**Recommended default:** a **plain static domain service** at `Learning.Domain/Services/LearningPathEngine.cs`, mirroring `SkillGraphValidator` (P2-11). Public surface:
- `LearningPathEngine.ComputeStates(studentId, lessons, skills, edges, skillStats) → IReadOnlyDictionary<int /*lessonId*/, LessonUnlockResult>`
- `LessonUnlockResult` = `{ NodeState State, IReadOnlyList<MissingPrerequisite> MissingPrerequisites }`.

The engine is **pure** — no DB, no DI, no IO — fed pre-fetched inputs by the caller (the CQRS query handler in Q7). This keeps it (a) testable with in-memory fixtures (BE-5), (b) reproducible (AC4), and (c) trivially batchable.

**Why this shape:** mirrors `SkillGraphValidator` (already PASSed review). **Pattern caution per CLAUDE.md rule 8:** a pure static computation service is *not* a "design pattern" — it is a plain helper. If the implementer is tempted to add Strategy / Visitor / Chain-of-Responsibility for "future extensibility," they **must stop and ask the lead first**. Default = simplest plain method.

**Alternative if rejected:** instance class with DI'd dependencies (closer to a service); only justified if we later need to switch backing stores (no current need).

### Q7 — Where the engine is surfaced (new endpoint vs. extend existing queries)
Two viable shapes, with clear trade-offs:

**Option A (recommended):** **Extend the two existing P2-02 queries** to compute real per-student state when a `studentId` is provided (from JWT):
- `GetSubjectSkillTreeQuery` — replace `DeriveNodeState(skill)` placeholder with engine-derived `NodeState` per skill (folded up from its lessons).
- `GetSubjectLessonsQuery` — augment `LessonInUnitDto` with a new `State: NodeState` field (keep `IsLocked` for one wave for back-compat, **mark obsolete via doc comment**, plan removal in P2-03 or a follow-up).

**Option B:** add a **dedicated** `GET /api/Learning/LearningPath/{studentId}/Subject/{subjectId}` returning a flat lesson-state dictionary.

**Trade-offs:**
- A keeps the FE call shape stable (P2-02's two endpoints already exist; FE wires through one place) — *but* requires `studentId` to enter those queries (from JWT — IDOR-guarded; queries already use `ICurrentUserService` in P2-08 pattern).
- B is cleaner (single-purpose endpoint, easier perf tuning, doesn't change anonymous P2-02 endpoints into Auth-required ones — see HANDOFF: "Endpoints are anonymous-callable today — no `[Authorize]` yet").

**Recommendation:** **Option A**, with **`[Authorize]` added to both P2-02 endpoints in this story** (deferred follow-up from P2-02 anyway — see HANDOFF). When `_currentUser.UserId is null` (unauthenticated), fall back to the static derivation (= P2-02 today) so anonymous browsing still works for a marketing surface; when authenticated, run the engine. Document this branch clearly.
**Alternative if rejected:** Option B (dedicated endpoint) — also fine and arguably cleaner; lead picks.

### Q8 — Bulk vs per-lesson evaluation
**Recommended default:** **Bulk** — the engine is called **once per subject** for a student, taking pre-fetched bulk inputs (all lessons + skills + edges for the subject, plus all of the student's relevant `StudentAnswer` rows aggregated per skill). Internally it builds the per-skill mastery map once, walks the graph once, returns a `Dictionary<lessonId, LessonUnlockResult>`.
**Why:** a Grade 1 Math subject has **15 lessons / 15 skills / ~7 edges**; N-call shape would be 15×(prereqs query + skill-stats query) = ~30+ round-trips per page load. Bulk = 3 queries total (skills+lessons, edges, answers) + in-memory computation. Performance and reproducibility both win.

### Q9 — Explainability shape (AC3 — "explain which prerequisite is missing")
**Recommended default:** per-locked-lesson response includes:
```
MissingPrerequisites: [
  { PrereqSkillId, PrereqSkillName, PrereqNodeId, RequiredAccuracy, CurrentAccuracy, IsMastered=false }
]
```
Empty list when the lesson is `Available` or `Completed`. **Only includes the immediate prerequisites that are unmet** — not the transitive closure (the student needs to fix the closest gap first; transitive explanation is noise).
**Why:** matches AC3 verbatim ("explain which prerequisite is missing") with enough fidelity that a FE can render "You need 80% on Compare Fractions — you're at 62%". Keeps response size bounded.
**Alternative if rejected:** include transitive ancestors when the immediate prereqs themselves have unmet ancestors (BFS up).

### Q10 — Cycle defense (defense-in-depth against malformed graphs)
**Recommended default:** **memoize visited nodes per traversal** (visited-set guard in DFS). `SkillGraphValidator.AssertAcyclic` runs at seed time, but P7-03 admin authoring (post-MVP) will let humans add edges; a runtime engine that infinite-loops on a cycle is unacceptable. The visited-set is cheap (Dictionary<int,bool> per call) and turns "infinite loop" into "node skipped, logged".
**Why:** belt-and-suspenders — seed-time validation can be bypassed by direct DB writes; the engine is the hot path.

### Q11 — Data-fetch strategy
**Recommended default:** **bulk fetch + in-memory compute**, three queries per engine call:
1. `Concept + Skill + Lesson` tree for the subject (already done by `GetSubjectSkillTreeQueryHandler` — reuse the projection).
2. `KnowledgeEdge` rows for nodes whose `SkillId` belongs to this subject's skills (one IN-query joined on `KnowledgeNode.SkillId`).
3. `StudentAnswer` aggregated to per-skill `{SkillId, TotalAnswers, CorrectAnswers}` for this student in one grouped query (`StudentAnswer.Attempt.StudentId == studentId AND StudentAnswer.Question.SkillId IN (...)`). Plus the `Attempt`-by-`LessonId` set for `Completed` derivation (one query, `Attempt.StudentId == studentId AND Attempt.LessonId IN (...) AND Status == Completed`).

Repository extensions on `ILearningRepository`:
- `GetSubjectEdgesAsync(subjectId, ct)` — returns `KnowledgeEdge` for nodes whose `SubjectId == subjectId`.
- `GetSkillMasteryForStudentAsync(studentId, skillIds, ct)` — returns `Dictionary<int, (int total, int correct)>` for the requested skills.
- `GetCompletedLessonIdsForStudentAsync(studentId, lessonIds, ct)` — returns `HashSet<int>`.

These are the only repository additions; the engine itself stays pure.

## Risks & assumptions
1. **`MasteryThreshold` units (int 0..100 = percent).** Confirmed by reading `Skill.cs` (`public int MasteryThreshold`) and `LearningSeeder.cs` (values 70/75/80/85). If the field is ever reinterpreted as a 0..1 fraction, the engine breaks silently. **Mitigation:** an XML-doc comment on `LearningPathEngine` stating the contract + a guard `Debug.Assert(threshold >= 0 && threshold <= 100)`.
2. **Seed coverage of `Lesson.SkillId` is partial.** Per the P2-10 seed: Math has 3 lessons per grade with `SkillId = null` (Word Problems: Add/Sub, Division as Equal Groups, Word Problems: Mul/Div). Q3 default handles them as `Available`. Demo will show those as unlocked even when the rest of the unit is locked — confirm with lead this is acceptable for the v1 demo (it is — they're "fill" lessons).
3. **`Lesson.IsLocked` bool is now misleading.** It was the P2-02 placeholder; P2-04 replaces it with engine-derived state. **Recommendation:** keep the column for one wave (back-compat with any external readers), document it as deprecated in the entity XML-doc, and remove in the next wave (P2-03 or a dedicated cleanup task). Do **not** silently drop it in P2-04.
4. **Anonymous P2-02 endpoints become Authz-required if we go Option A (Q7).** Marketing-site or pre-login flows that hit `GetSubjectSkillTree` will lose access. Mitigation: support both paths (anonymous → static derivation; authenticated → engine), or pick Option B (dedicated endpoint) so P2-02 stays anonymous.
5. **Cross-subject edges in the seed.** P2-11 only seeded **within-subject** edges (Math G1→G6 chain). The engine should still work if cross-subject edges appear later (e.g. an English skill prereq for a Math word-problem skill); no special handling needed because the engine iterates by edge, not by subject. Worth a unit test asserting cross-subject edges resolve correctly.
6. **P2-07 sibling story (Wave 8) may also touch SubmitAnswer.** P2-04 only **reads** the resulting state; no write conflict expected. The two batches can run in parallel.
7. **Performance: N+1 risk in `GetSubjectSkillTreeQueryHandler` if the engine is folded in naively.** The current handler uses `Include(c => c.Skills).ThenInclude(sk => sk.Lessons)` — adding the engine's three extra queries is 4 round-trips per request, acceptable. Avoid per-skill or per-lesson queries.
8. **`Attempt` rows have a `Kind=Local` UTC quirk** (HANDOFF P2-08 bugfix note) — irrelevant here because the engine doesn't subtract timestamps, but worth noting if anyone adds a "time-since-last-attempt" feature later.

## Out of scope
- **Frontend.** No FE task file for P2-04 — task file explicitly says "Backend/infra only." FE consumption lands in P2-03 (skill-tree navigation) and P2-09 (home dashboard).
- **Admin authoring** of the prereq graph (P7-03) — admin console post-MVP.
- **AI-driven adaptivity** (P3-08) — FR-AI-6 forbids; that's a separate engine that *reads* the unlock state but does not write it.
- **Spaced-repetition / remediation scheduling** (P3-10) — a different engine; will read the same prereq graph.
- **Full mastery state machine** `not_started/in_progress/mastered/needs_review` (FR-AD-2 → story P3-09). P2-04 only needs the binary mastered/not-mastered signal per skill.
- **Event-driven recompute** ("on lesson completion → push new unlock state somewhere"). Default Q10 = on-demand recompute on every query; no event listener, no cache. If P2-04-BE-3's "recompute hook" is read as event-driven, ask the lead — recommend deferring an event-bus integration to Phase 4 (XP/gamification already plants `LessonCompleted` integration-event stubs per P2-08 notes).
- **Persisted unlock state** (no new table caching `(studentId, lessonId, state)` rows). Recompute is cheap (Q11); persistence introduces staleness + invalidation work. Defer until measured need.

### Handoff → api-tester
Story exposes (or extends) **HTTP endpoints**, so api-tester runs after backend-feature. Validate against running API + Testcontainers Postgres + the seeded P2-11 graph + a real Student-role JWT (use the existing parent→child onboarding flow per P2-08 test setup):

**Happy paths:**
- Student with **no attempts** in subject Math G1: root skills (`Count to 1000`) → `Available`; downstream skills (`Compare and Order Numbers`, `Add Single-Digit Numbers`) → `Locked`; lessons mirror their skill's state.
- Student completes Lesson for `Count to 1000` with high accuracy → on next call, `Compare and Order Numbers` flips to `Available`; its lesson likewise.
- Same student calls the endpoint twice with no DB changes between → byte-identical responses (AC4 reproducibility).
- Cross-grade edge (G2 → G3): mastering G2 `Subtract Within 100` unlocks G3 `Multiply Single-Digit Factors`. (P2-11 seed authors this chain.)

**Edge cases:**
- Lesson with `SkillId == null` → always `Available` (Q3 default).
- Skill with no prereq edges → always `Available` until completed (Q4 default).
- Locked lesson response includes `MissingPrerequisites` with `RequiredAccuracy`/`CurrentAccuracy` (AC3).
- Skill with `TotalAnswers == 0` for student → `IsMastered == false` (Q2 guard).
- `Status == Completed` attempt with low accuracy → lesson `Completed`, skill **not** Mastered, dependents stay `Locked` (Q5 separation).
- Unknown `subjectId` → 404 (not 500).
- Unauthenticated → either 401 (Option B) or fallback to static derivation (Option A).
- Another student's `studentId` not addressable (IDOR guard via JWT).

**Envelope:** `"successed":` camelCase (HANDOFF load-bearing); `NodeState` serializes as int (no `JsonStringEnumConverter` registered per P2-02 confirmation).
