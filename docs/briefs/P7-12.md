## Business context & value

- **Who benefits:** Admins (accountability + compliance review), the platform owner (G2 trust/governance, regulatory defensibility for a child-data product), indirectly parents/children (privileged actions on their accounts are traceable).
- **Value:** An immutable, queryable system-of-record for every admin mutation — who did what, to which target, when, with a PII-safe before/after summary. Required for compliance (NFR-4) and for investigating any abuse of admin power (suspend/delete accounts, grade overrides, language changes that hard-delete attempts, gamification overrides).
- **Success measure:** Every admin mutation across modules lands exactly one audit row, only after the mutation has actually committed (no phantom rows on rollback); the log can never be edited or deleted via API/UI/handler; admins can filter + export; non-admins get 403.

## Acceptance criteria (testable)

1. A new `Moderation` module exists (4 projects + full host wiring) and its endpoints/handlers load at runtime (a smoke call to `GET /api/Audit/Log` returns 200 for an admin, not 404).
2. `AdminActionPerformedEvent` is published **only after the producing transaction commits** — a rolled-back admin command produces **zero** audit rows. (Verified by forcing a post-publish failure / rollback in a producing handler and asserting no row.)
3. Every existing P7-01..08 admin mutation that currently publishes the event still results in exactly one audit row on success (no double-write, no lost write).
4. The `AuditLog` entity derives from the audited base (`FullAuditedEntity`) and stores `AdminUserId`, `Action`, `TargetEntityType`, `TargetEntityId`, `Details`, `OccurredAtUtc` (sourced from the event, not re-derived).
5. The consumer is an `INotificationHandler<AdminActionPerformedEvent>` in `Moderation.Application` that persists one row; it is **fail-soft** (a persistence failure logs but does not crash the publisher / sibling handlers) and **idempotent** on `EventId` (a redelivery does not duplicate).
6. The table is **append-only / immutable**: no Update or Delete command/handler/endpoint exists; immutability is additionally enforced at the DB layer (insert-only — see Q3).
7. `GET /api/Audit/Log` is paginated and filterable by `actor`, `actionType`, `target`, `dateFrom`, `dateTo` (DB-side filtering + paging, not in-memory), returning `BaseResponse<PagedResult<AuditLogDto>>` with success flag spelled `Successed`.
8. `GET /api/Audit/Log/Export` streams the filtered log as CSV/JSON (file-based export uses `Shared.Kernel.Storage.IStorageService`, no module-local MinIO).
9. All endpoints are `[Authorize(Policy = AuthorizationPolicies.AdminOnly)]`; non-admin → 403. No mutation endpoints exist.
10. `Details` / before-after content is **PII-safe**: ids + enum/state values only — no child names, emails, or raw quiz answers. (The existing producers already honour this; the store must not add PII.)

## Piece 1 — `AdminActionPerformedEvent` post-commit publishing (the load-bearing prerequisite)

### How it is published today (pre-commit)
`AdminActionPerformedEvent` is an `IIntegrationEvent` (`Shared.Contracts/Admin/AdminActionPerformedEvent.cs`) published **directly via `IPublisher.Publish(...)` inside the command-handler body**, wrapped in a try/catch (best-effort). Example — `Modules/Learning/.../Subjects/Commands/Add/AddSubjectCommandHandler.cs`:

```csharp
var result = await _service.SubjectService.AddAsync<AddSubjectCommand>(request, cancellationToken);
if (result.Successed)
{
    try { await _publisher.Publish(new AdminActionPerformedEvent(...), cancellationToken); }
    catch (Exception publishEx) { _logger.LogError(publishEx, "...publish failed..."); }
}
return result;
```

The handler returns; **only then** does the module's `UnitOfWorkBehavior` call `SaveChangesAsync` + `transaction.CommitAsync`. So in the **Learning** curriculum handlers the event fires **before** commit — on a rollback you would get a phantom audit row. HANDOFF flags this explicitly ("`AdminActionPerformedEvent` publishes PRE-commit … fix to post-commit before P7-12 builds the audit-log consumer"). ~24 Learning handlers + the Identity user/account handlers all follow this in-body publish shape.

**Important nuance for the Identity producers.** The Identity user/account handlers (`SuspendAccount`, `DeleteAccount`, `ReactivateAccount`, `AdminChangeLearningLanguage`, `OverrideChildGrade`, `UpdateChildProfile`) mutate users through ASP.NET Identity's `UserManager.UpdateAsync`, which commits to the **Identity store immediately** — it is *not* enrolled in the `IdentityModuleDbContext` UoW transaction. So for those, the user mutation is **already committed** when the event publishes (the handler comment in `SuspendAccountCommandHandler` even calls this out). The pre-commit hazard is therefore concentrated in the **Learning** curriculum wave, where the UoW genuinely wraps the writes. This matters for sizing the fix: the Identity producers are nearly post-commit already; the Learning producers are the real problem.

### Post-commit mechanisms the codebase ALREADY has

1. **After-commit DOMAIN-event dispatch (the blessed pattern, ADR 0002 §2).** Each module's `UnitOfWorkBehavior` (verbatim-identical in Learning + Identity + Parent + Gamification) does, **after** `SaveChangesAsync` + `CommitAsync`:

   ```csharp
   await _db.SaveChangesAsync(...);
   await transaction.CommitAsync(cancellationToken);          // commit boundary
   var aggregates = _db.ChangeTracker.Entries<AggregateRoot>()
       .Where(e => e.Entity.DomainEvents.Count > 0).Select(e => e.Entity).ToList();
   if (aggregates.Count > 0) {
       var domainEvents = aggregates.SelectMany(a => a.DomainEvents).ToList();
       foreach (var a in aggregates) a.ClearDomainEvents();
       await _dispatcher.DispatchAsync(domainEvents, cancellationToken);  // AFTER commit
   }
   ```
   `IDomainEventDispatcher` → `InProcessDomainEventDispatcher` → `IPublisher.Publish` (cross-module fan-out via the host's unified MediatR + `IsolatedNotificationPublisher`). Aggregates raise events via `AggregateRoot.RaiseDomainEvent(...)`. **Gamification already uses this for real** (`XpAwardedDomainEvent`, `StreakAdvancedDomainEvent`, etc.). This is the only true post-commit seam in the codebase and it is per-module-DbContext scoped.

2. **No outbox.** ADR 0002 §5 explicitly **defers the Outbox** ("Outbox is deferred for P4-01"; "Until the Outbox lands, dispatch is in-process and best-effort"). The `IDomainEventDispatcher` seam exists *so an outbox can be added later without changing callers*, but no outbox table or dispatcher loop exists today.

3. **How other integration events publish.** They are published **inline via `IPublisher.Publish`** in the handler/service body — there is no deferred integration-event collector. But the genuinely post-commit ones do it from a service that has *already* committed:
   - `IdentityChildAccountService.ChangeLearningLanguageAsync` calls `UserManager.UpdateAsync` (immediate commit) **then** `PublishLearningLanguageChangedEventAsync` — comment: *"Best-effort post-commit publish … A publish failure must NEVER roll back the already-committed User change (ADR 0002 §3)."* Same for `PublishUserRegisteredEventAsync` after a committed child create.
   - So `LearningLanguageChanged` / `UserRegistered` are **effectively post-commit** because Identity has no deferred UoW around the write. The Learning curriculum producers are **not**, because their UoW defers the commit until after the handler returns.

   **Net:** the codebase has exactly one general post-commit primitive — the domain-event-on-aggregate → after-commit dispatch path. Integration events are otherwise published inline and happen to be post-commit only when the writing path commits eagerly.

### Options to make `AdminActionPerformedEvent` fire only after commit

| # | Option | New pattern? (Rule #8) | Touches ~20 handlers? | Module-isolation notes |
|---|---|---|---|---|
| **(a)** | **Raise an `AdminActionPerformedDomainEvent` (`IDomainEvent`) on the mutated `AggregateRoot`** → existing after-commit dispatch in each module's `UnitOfWorkBehavior` → a per-module `INotificationHandler` re-publishes the `AdminActionPerformedEvent` integration event (which the Moderation consumer reads). | **Reuses** the blessed ADR-0002 pattern — not a new abstraction. But it adds a domain-event→integration-event relay handler per producing module (small, mirrors Gamification). | Yes — every producer swaps `IPublisher.Publish(integrationEvent)` for `aggregate.RaiseDomainEvent(domainEvent)`. Mechanical but broad. **Blocked for Identity producers** that mutate via `UserManager` (those entities aren't tracked `AggregateRoot`s in the UoW DbContext) — they would keep the eager pattern (already effectively post-commit). | Clean. Domain event stays intra-module; only the `Shared.Contracts` integration event crosses. |
| **(b)** | **Transactional outbox table** in each module: producers write an outbox row in the same transaction; a dispatcher flushes post-commit. | **New pattern + new infra** (table, dispatcher loop). ADR 0002 §5 explicitly defers this. **Needs lead approval.** | Yes + new infra per module. Heaviest option. | Strongest durability (survives crash). Overkill for best-effort audit at this stage. |
| **(c)** | **Small deferred-publish collector flushed by the UoW behavior post-commit:** a scoped `IDeferredEventCollector` the handler enqueues into; `UnitOfWorkBehavior` drains + publishes it right after `CommitAsync` (next to the existing domain-event dispatch). | **New abstraction** (a deferred integration-event queue) — **Rule #8 ask-first**, though it is small and localized to Shared.Kernel + the 4 UoW behaviors. | Yes — but a *minimal* change per handler (enqueue instead of publish); no per-module relay handler needed. Does **not** help the Identity `UserManager` producers (they bypass the UoW DbContext entirely). | Clean; symmetric with the existing post-commit domain-event drain. |
| **(d)** | **Accept pre-commit + make the consumer tolerant.** Keep producers as-is; the audit consumer dedupes on `EventId` and the system tolerates rare phantom rows on rollback. | No new pattern. | No handler changes. | Violates AC #2 and ADR 0001 §4 / ADR 0002 ("publish after commit, never before"). Phantom rows in an *immutable audit log of record* are the worst place to tolerate them — you cannot delete them later. **Not recommended.** |

### Recommendation (open question for the lead — Q1)
**Prefer (a)** for the **Learning** curriculum producers — it reuses the already-accepted ADR-0002 after-commit domain-event mechanism (no new abstraction, no Rule-#8 gate), at the cost of a mechanical edit across the Learning handlers plus one tiny relay handler in `Learning.Application`. For the **Identity** user/account producers, **leave them as-is** (their `UserManager.UpdateAsync` writes commit eagerly, so their `IPublisher.Publish` is already post-commit — same shape as `LearningLanguageChanged`/`UserRegistered`). This keeps the whole change inside accepted patterns and avoids touching the heavier outbox.

**If** the lead wants one uniform mechanism across both modules, **(c)** is the smallest new primitive — but it is a new abstraction and triggers Rule #8. **(b)** (outbox) is the "correct" long-term answer but is explicitly deferred by ADR 0002 and is out of proportion for best-effort audit today. **This is the single biggest decision in P7-12 and should be made before the planner sequences the work.**

## Piece 3 — P7-12 audit-log feature

### Entity — `AuditLog` (`Moderation.Domain`)
Derive from `FullAuditedEntity` (per story AC "derives from `FullAuditedEntity`"; note the task file says `FullAuditedEntity` — use that, not `AggregateRoot`, since the entity raises no events). Fields sourced directly from `AdminActionPerformedEvent`:

| Field | Type | Source | Notes |
|---|---|---|---|
| `Id` | int | base | PK |
| `EventId` | Guid | event.EventId | **unique** — idempotency key for redelivery dedupe |
| `AdminUserId` | int | event.AdminUserId | acting admin (from JWT upstream) — id only, no PII |
| `Action` | string | event.Action | `AdminActions.*` constant string |
| `TargetEntityType` | string | event.TargetEntityType | e.g. "Subject", "User" |
| `TargetEntityId` | int | event.TargetEntityId | 0 for batch/multi-row |
| `Details` | string? | event.Details | PII-safe summary (ids + enum states only) |
| `OccurredAtUtc` | DateTime | event.OccurredAtUtc | event time, NOT row-insert time |

> The current event has **no separate Before/After fields** — it carries a single `Details` string (the task's BE-1 row names `BeforeJson`/`AfterJson`, but the shipped `Shared.Contracts` event only has `Details`). **Reconcile:** either store `Details` as-is (recommended — matches the shipped contract; the story's "before/after snapshot" is satisfied by the `Details` summary), or extend the event with `BeforeJson`/`AfterJson` (a `Shared.Contracts` change that ripples to all ~20 producers). **Flag to lead/planner — likely keep `Details`.** Audit base columns (`CreatedAt`/`CreatedBy`) record insertion; `OccurredAtUtc` records the action time.

### Consumer — `AuditLogEventHandler` (`Moderation.Application`)
`INotificationHandler<AdminActionPerformedEvent>` mirroring `UserRegisteredIntegrationEventHandler`:
- Inject `IModerationDbContext` + `ILoggerManager`.
- **Idempotency:** `if (await _db.AuditLogs.AnyAsync(a => a.EventId == evt.EventId, ct)) return;`
- Map event → `AuditLog`, `Add`, `SaveChangesAsync(ct)`.
- **Fail-soft:** wrap in try/catch + log (the `IsolatedNotificationPublisher` already isolates per-handler failures, but log here for observability — and a failure must never propagate to abort the producing command).
- No command path to mutate — this is the only write to the table.

### Read side
- `GetAuditLogQuery` → `GET /api/Audit/Log?actor=&actionType=&target=&dateFrom=&dateTo=&page=&pageSize=` → `BaseResponse<PagedResult<AuditLogDto>>`. **DB-side** filtering + paging (no in-memory). `AuditLogDto { id, actor, actionType, target, occurredAt, details }` (the FE contract names `before`/`after`; map `details` → keep the single field, or split — tie to the Before/After reconcile above). Queries are NOT auto-validated (ValidationBehavior is command-only) — validate filter inputs in the handler.
- `ExportAuditLogQuery` → `GET /api/Audit/Log/Export?<same filters>&format=csv|json` → file stream. If file-based (staging a temp blob), use `Shared.Kernel.Storage.IStorageService` — no module-local MinIO.
- Indexes (migration): on `AdminUserId`, `Action`, `TargetEntityType`+`TargetEntityId`, `OccurredAtUtc`, and **unique** on `EventId`.

### Immutability enforcement
- API/handler layer: **no** Update/Delete command, handler, or endpoint exists (AC #6). This is the primary guarantee.
- DB layer: append-only. Options — (i) revoke UPDATE/DELETE grants on the table for the app role via a raw-SQL migration step; (ii) an insert-only repository that exposes no update/delete; (iii) a DB trigger blocking UPDATE/DELETE. **Q3 for the lead** (also a retention-window decision). The task's BE-2 calls for "revoke UPDATE/DELETE (DB grants or insert-only repository)".

### PII safety
The shipped producers already keep `Details` to ids + enum states (HANDOFF: *"`AdminActionPerformedEvent` Details … carry NO names/emails/free-text (ids + enum states only) — preserve this when P7-12 builds the durable audit store"*). The audit store **must not** enrich rows with PII (no join-in of user names/emails at read time beyond the id). Export must likewise emit ids only.

### Auth
`[Authorize(Policy = AuthorizationPolicies.AdminOnly)]` on the controller/all endpoints (the constant lives in `Shared.Kernel/Abstractions/AuthorizationPolicies.cs`; registered in Identity Infrastructure's `AddAuthorization`). Non-admin → 403.

- **Q1 (the big one — Rule #8) — post-commit mechanism.** Choose (a) reuse ADR-0002 domain-event after-commit dispatch for the Learning producers + leave Identity producers as-is (recommended, no new abstraction), (b) outbox (new infra, deferred by ADR 0002), (c) a deferred-publish collector in the UoW behaviors (new small abstraction, Rule-#8 gated), or (d) accept pre-commit + tolerant consumer (violates AC #2 / ADR 0001 §4 — not recommended for an immutable log). **Must be decided before planning.**
- **Q2 — Moderation module name/scope.** Confirm one `Moderation` module owning both the P7-12 audit log (now) and the future P7-09 moderation queue. Sub-question: scaffold the module's `UnitOfWorkBehavior` + repository now (future-ready for P7-09 write commands), or keep P7-12 minimal (read + event-consumer only, no UoW)? **Recommend: scaffold full Learning-shaped wiring incl. UoW guard now**, so P7-09 doesn't re-touch the serialization points.
- **Q3 — Immutability + retention.** Append-only is mandated. How to enforce at DB layer — revoke UPDATE/DELETE grants (raw-SQL migration) vs insert-only repository vs trigger? And is there a **retention window** (regulatory) or is the log kept indefinitely? Append-only conflicts with any "purge old rows" requirement — clarify.
- **Q4 — Backfill / interim of existing producers.** The P7-01..08 producers already publish pre-commit on `main`/`feat/phase-7-backend`. When the consumer goes live: do we (i) keep the curriculum-wave pre-commit publishes working in the interim (accept rare phantom rows until the post-commit fix lands), or (ii) gate the consumer behind the post-commit fix so no audit row is written until producers are corrected? No historical backfill is possible (events weren't stored). **Recommend: land the post-commit fix and the consumer in the same P7-12 work, so the first row ever written is already post-commit.**
- **Q5 — Before/After vs Details contract mismatch.** The shipped `AdminActionPerformedEvent` has a single `Details` string; the task/story language says "before/after snapshot" and the task's BE rows name `BeforeJson`/`AfterJson`. Keep `Details` (recommended — no `Shared.Contracts` churn across ~20 producers) or extend the event (ripples everywhere)? **Recommend: keep `Details`; document that the story's before/after is captured in the PII-safe `Details` summary.**
- **Assumption:** P7-13 (gamification overrides) and P7-08 producers referenced in BE-7 are **out of P7-12's immediate scope** — they publish their own events when those stories land; P7-12 only builds the store + consumer + fixes existing producers. BE-7 is a forward-looking note, not a P7-12 deliverable.
- **Risk — silent no-load:** the `MediatRExtensions` registration (shared-file edit #3) is the highest-risk omission — miss it and the audit log silently stays empty with no error. The reviewer/api-tester must assert an actual row is written end-to-end, not just that the endpoint returns 200.
