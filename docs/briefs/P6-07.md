# Pipeline Brief — P6-07 Access-token revocation (per-request SessionId validation)

## Summary & traceability
- **Task (one line):** Make an already-issued JWT stop working the moment the user signs out / changes password / is reset / suspended / deleted — by validating the token's `"SessionId"` claim against the Redis-backed session store on every authenticated request (`JwtBearerEvents.OnTokenValidated`), instead of accepting tokens for their full 30-minute lifetime.
- **User story:** `user-stories/Phase-6-Stabilization/P6-07-access-token-revocation.md` (SP 5, Status Backlog). Split out of **P6-06 AC6**.
- **Tasks:** `tasks/Backend/Phase-6-Stabilization/P6-07-BE.md` (BE-1..BE-6).
- **Provenance:** Phase-1 auth audit finding **G2** (`docs/briefs/P1-12-password-reset-security-audit.md`). Today logout/password-change only delete the refresh-token cache entry and bump the (unread) SecurityStamp; the access token survives.
- **Requirements:** NFR-4 (security), FR-ID-1 / FR-ID-4. **BRD goal:** G2 (trust/security of the platform).
- **Phase/Sprint:** Phase 6 — Stabilization, Week 9. Epic: Stabilization & Hardening.
- **Chosen design (lead 2026-06-21, NOT to be re-opened):** SessionId per-request validation via `OnTokenValidated`. **Explicitly NOT** ASP.NET security-stamp validation (would also kill the caller's current device on password change → breaks P2-12 keep-current behavior; and is per-user, can't power per-device sign-out).
- **Scope:** Identity + Host only. No cross-module references, **no new module, no DB migration** (sessions are in Redis via `IDistributedCache`). No Unit of Work. No new NuGet package.

## Business context & value
- **Who benefits:** every account holder (parent / student / admin) and the platform owner. Logout, "sign out other devices", password change/reset, and admin suspend/delete become **real** revocations rather than cosmetic ones with a ≤30-minute window where a leaked or stolen token still works.
- **Value / why now:** this is the load-bearing G2 audit finding deliberately deferred from P6-06 so it could run its own full pipeline. Without it, the entire session-termination machinery built across P1-02 / P2-12 / P7-07 is effectively a no-op (see the verified mismatch bug below) — every `TerminateSessionAsync(...)` call silently misses.
- **Success measure (testable):** after a revoking action, the same unexpired access token returns **401** on its next call; un-revoked tokens keep authenticating; current device survives a password change.

## VERIFICATION of the lead's findings (independently confirmed against source)

**1. No `OnTokenValidated` today — CONFIRMED.**
`Identity.Infrastructure/DependencyInjection.cs` `AddJwtBearer` (lines 171-189) sets only `TokenValidationParameters` (issuer/signing-key/audience/lifetime) and `SaveToken`/`RequireHttpsMetadata`. **No `x.Events` / `JwtBearerEvents` is wired.** A repo-wide grep for `OnTokenValidated` / `JwtBearerEvents` finds zero usages. Access tokens are accepted on signature + `ValidateLifetime` only. `JwtSettings.AccessTokenExpireMinutes` drives a `DateTime.UtcNow.AddMinutes(...)` expiry in `AuthenticationIdentityService.GenerateJwtToken` (line 183) — story states 30 min.

**2. The SessionId mismatch bug — CONFIRMED (precise).**
- `AuthenticationIdentityService.GetClaims` mints the claim as a fresh GUID:
  - line 193: `var sessionId = Guid.NewGuid().ToString();`  → call it **GUID-A**
  - line 202: `new("SessionId", sessionId),` (this value goes into the JWT)
- `SessionManagementService.CreateSessionAsync(int userId, string jwtTokenId)` **ignores any caller-supplied id** and generates its own key:
  - line 32: `var sessionId = GenerateSessionId();`  → **GUID-B** (`Guid.NewGuid().ToString("N")`, line 273)
  - line 38: `SessionId = sessionId` (GUID-B is stored as the Redis key, `session:{GUID-B}`)
  - line 40: `JwtTokenId = jwtTokenId` (the Jti passed in)
- Result: the **JWT carries GUID-A**, **Redis is keyed GUID-B**. Every termination path looks up the claim value (GUID-A) and misses:
  - `SignOutCommandHandler.GetCurrentSessionId()` returns `GetClaimValue("SessionId")` = GUID-A (line 117) → `TerminateSessionAsync(GUID-A)` → `GetSessionAsync` returns null → no-op (silently returns false).
  - `ChangePasswordCommandHandler.InvalidateOtherSessionsAsync` compares `session.SessionId` (GUID-B) against `currentSessionId = GetClaimValue("SessionId")` (GUID-A) — they **never** match, so "keep current" logic is moot today (and termination of others depends on the GUID-B records existing, which they do, but the keep-current guard can't fire correctly because the current session's claim is GUID-A).
  - `SignOutOthersCommandHandler` has the same GUID-A vs GUID-B comparison flaw (line 45/52).
  - Interesting nuance: `SignOut`/`ChangePassword` today *also* delete the refresh-token cache entry, which is what actually makes those flows partly effective — but the **access-token** is never revoked, which is exactly what P6-07 fixes.

**3. The three token-issuance paths — CONFIRMED, with an important correction.**
All three already call `CreateSessionAsync`, and all three already **extract** the token's `"SessionId"` claim but then **discard it** (because the 2-arg signature has no slot for it):
- `SignInCommandHandler` (line 89-95): `ExtractSessionInfoFromToken` reads both `Jti` and `SessionId`, then calls `CreateSessionAsync(user.Id, sessionInfo.JwtId)` — passes Jti, **drops `sessionInfo.SessionId`**, then sets `accessToken.SessionId = session.SessionId` (= GUID-B, the wrong one).
- `RegisterParentCommandHandler` (line 104-110): identical pattern — creates a session, drops the claim's SessionId.
- `GoogleSignInCommandHandler` (line 85-91): identical pattern — creates a session, drops the claim's SessionId.
- All three wrap the create in `try { } catch { /* session created by middleware later */ }` — note there is **no such session-creating middleware** today; that comment is stale. Once OnTokenValidated rejects missing sessions, a swallowed create failure means that user's first call 401s. **Keep the swallow but it is now load-bearing — see Open Question OQ-3.**
- **Correction to the lead's finding:** the question "VERIFY whether each currently creates a session at all" → **yes, all three already do.** The fix is not "add a CreateSessionAsync call" to register/Google; it is "thread the claim's SessionId into the existing call" in all three.

**4. Revoke-all paths — CONFIRMED, with per-path nuance.**
- `ResetPasswordCommandHandler` (anonymous reset): **does NOT terminate any tracked sessions today.** `InvalidateOtherSessionsAsync` (line 73-93) only (a) bumps the SecurityStamp and (b) deletes `userrefreshtoken-{userId}`. It has the `user` (hence `user.Id`) in hand (line 41). **Must add a terminate-all-sessions call.** No current session to preserve (anonymous path).
- `SuspendAccountCommandHandler`: **already terminates all sessions** via `GetUserSessionsAsync` + `TerminateSessionAsync(AdminTermination)` (line 127-161) plus deletes the refresh token. Best-effort, won't abort the status change. **No change strictly required for correctness once BE-1 lands** (because the stored sessions will now be keyed on the claim) — but see note: `GetUserSessionsAsync` only returns **active, non-expired** sessions (lines 88), which is fine for revoke-all.
- `AccountDeletedDomainEventHandler` (post-commit): **already terminates all sessions** for the primary user and each cascaded child (line 50-55, helper 100-136) plus deletes refresh tokens. **No change required.**
- **`TerminateAllUserSessionsAsync(userId)` helper does NOT exist today — CONFIRMED.** `ISessionManagementService` (the interface, 17 lines) has `CreateSessionAsync`, `GetSessionAsync`, `GetUserSessionsAsync`, `ExtendSessionAsync`, `ValidateSessionAsync`, `TerminateSessionAsync`, `GetSessionInfoAsync`, `UpdateSessionActivityAsync` — **no terminate-all.** Suspend/Delete hand-roll the loop. **Recommend adding `TerminateAllUserSessionsAsync(int userId, SessionTerminationReason reason)`** to the interface + impl (iterating `GetUserSessionsAsync`), use it in `ResetPasswordCommandHandler`, and optionally DRY the two hand-rolled loops in Suspend/Delete.

**5. Hot-path cost / fail-mode — CONFIRMED.**
- `ValidateSessionAsync(sessionId, updateActivity=true)` (line 121-160) **writes back on the sliding-expiration branch** (lines 138-146): when `EnableSlidingExpiration && updateActivity` it sets `LastActivityAt`/`ExpiresAt`, calls `StoreSessionAsync` + `UpdateActivityTrackingAsync` (two Redis writes per request). `EnableSlidingExpiration` defaults to **true** (`SessionSettings`, line 6). **So `OnTokenValidated` must NOT call `ValidateSessionAsync(..., true)`.** It must do a **read-only** check.
  - Even `ValidateSessionAsync(sessionId, updateActivity:false)` still has a write side-effect: if the session is expired it calls `TerminateSessionAsync` (line 134) — acceptable (lazy GC), but the cleaner read-only primitive is `GetSessionAsync(sessionId)` + an in-memory `IsActive && !IsExpired` check (no writes at all). **Recommended: validate via `GetSessionAsync` (single Redis GET) and inspect `IsActive`/`IsExpired` in memory**, or add a dedicated read-only `IsSessionValidAsync`. Decide in BE-2 (see OQ-2).
- **Cost:** one `IDistributedCache.GetStringAsync("session:{sessionId}")` per authenticated request — bounded, no per-request write. Acceptable.
- **Fail-mode is an open decision (AC6)** — fail-closed vs fail-open on Redis error. `GetSessionAsync` currently **swallows exceptions and returns null** (line 68-72), which would make a naive `null → Fail()` implicitly **fail-closed** (Redis blip ⇒ everyone 401s). The handler must make the policy **explicit** rather than rely on that swallow. See OQ-1.

### Net contradictions to the lead's findings
- **One correction:** finding 3 asked to verify "whether each path creates a session at all" — **all three already create sessions**; the work is to *thread the claim's SessionId in*, not to add missing CreateSessionAsync calls. (Register-parent and Google were built at "exact parity with SignIn" and already wired.)
- Everything else (1, 2, 4, 5) is confirmed exactly as described. Plus two extras worth flagging: (a) the "session will be created by middleware" catch comment is **stale** — no such middleware exists, and the swallowed failure is now load-bearing; (b) `GetSessionAsync`'s exception-swallow already biases toward fail-closed, so the AC6 policy must be made explicit, not left to that accident.

## Acceptance criteria (testable — mirrors the story's 7 ACs)
1. **Revoked token rejected fast.** After `Sign-Out`, the *same* unexpired access token on any `[Authorize]` endpoint returns **401**, not 200.
2. **Password change keeps current, kills others.** After `ChangePassword`, the caller's current token still works (P2-12 preserved) while a token issued for an *other* session of the same user is **401** on its next call.
3. **Anonymous reset revokes everything.** After a completed `Reset-Password`, every previously-issued access token for that user is **401** (no current to preserve).
4. **Admin suspend / delete revokes everything.** After `SuspendAccount` (and after account delete), the target's outstanding access tokens are **401** on the next call.
5. **Mismatch fixed, no false rejections, read-only hot path.** The JWT `"SessionId"` claim equals the persisted `UserSession` key; a normal un-revoked token authenticates (200); the validation path performs **no write** (no sliding-expiration write on validation).
6. **Fail-soft, bounded cost.** Documented store-outage policy (fail-closed chosen — see OQ-1) implemented explicitly in `OnTokenValidated`; exactly one Redis read per authenticated request (no per-request write).
7. **security-auditor PASS (Critical/High block) + existing auth integration suite stays green.**

## Affected modules & data (new vs existing)
- **Module:** Identity (Application + Infrastructure) + Host wiring. No other module touched.
- **Entities/data:** **No new entity, no schema, no migration.** `UserSession` already exists (Domain) and is persisted only in Redis (`session:{sessionId}`, `user_sessions:{userId}`, `activity:{sessionId}`). `UserSession.SessionId` is the key (string). `IsExpired`/`IsActive` already on the entity.
- **Changed seam:** `ISessionManagementService` — change `CreateSessionAsync` signature (+ optional new `TerminateAllUserSessionsAsync`). This is an internal Identity abstraction (not in `Shared.Contracts`), so no cross-module break.

## Handoff → db-migration
- **None.** No relational schema change; sessions live in Redis/`IDistributedCache`. Skip this stage for P6-07.

## api-tester scenarios (BE-5 — integration; in-memory `IDistributedCache`, single-process, fully deterministic)
Model on `P1_02_RefreshAndSignOut_Tests.cs` (sign-in → bearer header → call `[Authorize]` endpoint). The in-memory distributed cache is per-factory-process, so session create/terminate are observable.
1. **Baseline:** sign-in → use token on an `[Authorize]` endpoint → **200** (no false rejection; proves BE-1 keyed the session correctly).
2. **Revoke on sign-out:** sign-in → `Sign-Out` → reuse the *same* access token → **401** (AC1).
3. **Change-password keep-current vs kill-others:** sign-in device A → sign-in device B (same user) → from A call `ChangePassword` → A's token still **200**, B's token **401** (AC2). (Requires two distinct sessions; each sign-in mints a distinct SessionId now.)
4. **Anonymous reset revokes all:** sign-in → complete `Reset-Password` (valid token) → original access token **401** (AC3).
5. **Admin suspend revokes:** admin suspends user → user's outstanding token **401** (AC4). (Optionally account-delete path too.)
6. **No false reject under normal use:** sign-in → several `[Authorize]` calls in a row all **200**, and assert the session's `ExpiresAt`/`LastActivityAt` did **not** advance per request (proves read-only hot path, AC5).
7. **(Optional) fail-mode:** if feasible to simulate a cache fault, assert the documented policy (fail-closed ⇒ 401) — otherwise cover by unit-level reasoning + auditor review.

## security-auditor focus areas (BE-6)
- **Access control / fail-mode:** confirm the chosen store-outage policy is implemented as decided (no accidental fail-open via a swallowed exception); confirm `context.Fail` is reached on absent/terminated/expired session.
- **No enumeration / no detail leak:** 401 reason text must not distinguish "no session" vs "expired" vs "terminated" to the client; log detail server-side only.
- **No token/secret leakage** in logs from the new handler (don't log the raw token or SessionId at info level in prod).
- **DoS / cost:** exactly one Redis read per request; no per-request write; verify no amplification (e.g., the lazy `TerminateSessionAsync`-on-expired write does not become a hot-loop).
- **Scope correctness:** scoped `ISessionManagementService` resolved from `RequestServices`, not captured in the singleton options closure (a captured-scope bug would be a correctness + security issue).
- **Prereq integrity (BE-1):** verify all three issuance paths persist a session under the claim key before merge — a miss = mass lockout (availability) on that path.

## Open questions / assumptions / risks
- **OQ-1 (AC6 — decide before BE-2/BE-4):** store-outage policy — **fail-closed** (Redis error ⇒ reject; safest, but a Redis blip logs everyone out for the blip's duration) vs **fail-open** (allow on error; availability-first, but a revoked token slips through during the outage). **Recommendation: fail-closed in Production/Staging, fail-open-with-warning-log in Development/Testing** (mirrors the existing `IsProtectedEnvironment` pattern used by `GuardJwtSecret`/`GuardCaptcha`/`RequireHttpsMetadata`). Lead to confirm.
- **OQ-2 (BE-2):** read-only primitive — call `GetSessionAsync` + in-memory `IsActive/IsExpired` (zero writes, recommended) vs `ValidateSessionAsync(..., updateActivity:false)` (still lazily writes on expired). Recommend the former; confirm we're OK losing per-request sliding-expiration *refresh* on the validation path (sliding refresh, if still wanted, would have to move to an explicit activity endpoint — but note AC5 forbids the hot-path write anyway, so sliding expiration on every request is being intentionally dropped). **Assumption:** dropping per-request sliding refresh is acceptable (session TTL is 30 min and access tokens are 30 min — effectively aligned). Flag if the product wants idle-timeout independent of token lifetime.
- **OQ-3 (BE-1):** the three handlers swallow `CreateSessionAsync` failures with a now-stale "middleware will create it" comment. Under OnTokenValidated a swallowed failure ⇒ the issued token's first call 401s. Options: (a) keep swallow + log error (minimal); (b) in protected envs, fail the sign-in if session creation fails (no token that can't authenticate). **Recommendation: log loudly now; defer hard-fail to lead.**
- **OQ-4 (rollout):** existing live access tokens minted *before* this deploy carry GUID-A with no matching Redis session ⇒ they will **all 401** at deploy (forced re-login for everyone currently signed in). For a Phase-6 stabilization release this is likely acceptable; **confirm** it's an accepted one-time logout-all on deploy (and note refresh tokens also rotate). Tests run on a fresh process so won't surface this.
- **Risk — mass lockout (highest):** if BE-1 doesn't persist the session under the claim key on any one issuance path, every token from that path is rejected. Mitigated by BE-5 scenario 1 (baseline 200 on each path) and the auditor's prereq check. **Gate: do not merge until sign-in, register-parent, AND Google sign-in each prove a 200 baseline.**
- **Assumption:** `IConnectionMultiplexer`/Redis is not needed — `IDistributedCache` (already registered, Redis-when-present else in-memory) is sufficient. Confirmed by existing session code.
