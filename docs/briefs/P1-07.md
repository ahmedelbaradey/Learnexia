# Pipeline Brief — P1-07 (Backend) Docker & CI/CD

## Summary & traceability
- **Task (1 line):** Deliver a one-command local Docker environment for the full stack and an automated build/test/deploy pipeline, plus the runtime plumbing the platform will need later (health checks + background-jobs host).
- **User story:** `user-stories/Phase-1-Foundation/P1-07-docker-and-cicd.md` ("Dockerized environment & CI/CD pipeline").
- **Task file:** `tasks/Backend/Phase-1-Foundation/P1-07-BE.md` (BE-1…BE-5).
- **Requirement:** **NFR-3** (SRS non-functional — operability/deployability). No specific functional FR-IDs; this is a Technical Enabler.
- **BRD goal:** Indirect — supports all of G1–G5 by making the platform reliably shippable/runnable; primary driver is delivery reliability, not a customer-facing goal.
- **Epic / Phase / Sprint:** DevOps · Phase 1 — Foundation (Week 1–2) · SP 5.
- **Deps:** Builds on **P1-06** (Wave 0) which already provisioned Postgres (pgvector) + Redis + MinIO in `docker/docker-compose.yaml`. **Build on that compose — do not duplicate the data services.**

## Business context & value
- **Who benefits:** the engineering team (and indirectly every downstream story). No end-user (student/parent/admin) surface.
- **Value:** a clean checkout runs the whole stack with `docker compose up`; every push is built and tested automatically with a hard fail on test failure; a staging target exists so changes can be demoed/validated; the background-jobs host is in place so Phase 4 (streaks/leagues — B5.6) and Phase 5 (reports — B6) jobs have a home without a later re-plumbing.
- **Success measured by:** the four acceptance criteria below — all green in CI and reproducible locally.

## Acceptance criteria (testable)
1. **AC-1 — Full-stack compose.** From a clean checkout, `docker compose up` starts: **API (Learnexia.Host)**, **PostgreSQL (pgvector)**, **Redis**, an **AI-Gateway placeholder**, and the **web frontend** — all on one network, with the API reachable and dependent on healthy Postgres + Redis. (BE-1)
2. **AC-2 — Health endpoint.** `GET /health` on the API returns **HTTP 200** when the app + DB + Redis are reachable, and a non-200 (503) when a dependency is down. (BE-2)
3. **AC-3 — CI build/test.** A CI pipeline builds the solution and runs tests **on every push**, and **fails the build when any test fails**. (BE-3)
4. **AC-4 — Staging deploy target.** A deploy target (Azure / Railway / Render — TBD, see open questions) is configured for at least a **staging** environment. (BE-4)
5. **AC-5 — Background-jobs host.** Background-job infrastructure (**Hangfire or Quartz** — TBD) is **hosted in the API** and resolvable, ready for later streak/league/report jobs (no actual jobs implemented in this story). (BE-5)

## Handoff → db-migration
- **No migration expected.** Health checks and the jobs host do not introduce EF entities.

## Handoff → backend-feature (the bulk of this story)
This is an **infra + host** story; backend-feature owns all five tasks. Concrete work items:

**BE-2 — Health checks (`Program.cs` + csproj):**
- Add ASP.NET Core health checks: `builder.Services.AddHealthChecks()` with:
  - DB check against `ConnectionStrings:Default` (Npgsql health check — `AspNetCore.HealthChecks.NpgSql`, or a custom `IHealthCheck` opening an Npgsql connection if avoiding a new external package family is preferred).
  - Redis check against `ConnectionStrings:Redis` (`AspNetCore.HealthChecks.Redis`, or custom against `StackExchange.Redis`) — **must be conditional/degraded-tolerant** the same way `Program.cs` treats Redis as optional locally (when `ConnectionStrings:Redis` is empty, either skip the Redis check or report Degraded, not Unhealthy — decide and document; AC-2 only requires 200 when deps are reachable).
- Map `app.MapHealthChecks("/health")`. Consider also a lightweight liveness `"/health/live"` (no deps) vs readiness `"/health/ready"` (deps) split — recommended for the compose/orchestrator healthcheck to avoid restart loops, but AC only mandates `/health`.
- Place mapping so it is **not** blocked by auth/rate-limit middleware (map before/independent of `UseAuthorization`; ensure rate limiter `*` rule or `[AllowAnonymous]` semantics don't 429/401 the probe).
- Add the chosen health-check package(s) to `backend/Directory.Packages.props` (central versioning) + `Learnexia.Host.csproj` `PackageReference` (no version attr).

**BE-5 — Background-jobs host (`Program.cs` + csproj + Directory.Packages.props):**
- Register the chosen scheduler (**Hangfire** or **Quartz** — open question) in the Host so it starts with the app. **No jobs are implemented now** — only the host + a verifiable registration (e.g. Hangfire dashboard mapped behind admin auth, or a no-op Quartz scheduler that starts).
- Add package(s) to `Directory.Packages.props` + `Learnexia.Host.csproj`.
- If Hangfire dashboard is exposed, gate it (admin-only) — see security note.
- Follow CONVENTIONS.md / FEATURE_PLAYBOOK.md for any DI registration; use `ILoggerManager` (not `ILogger<T>`) if logging is added.

**BE-1 — Compose + Dockerfile (infra):**
- Rewrite `docker/Dockerfile` for **.NET 10** + the modular layout (multi-stage: `sdk:10.0` build → `aspnet:10.0` final; restore via `backend/Learnexia.Modular.sln` or the Host csproj graph; copy `Directory.Packages.props` + `Directory.Build.props`; entrypoint `Learnexia.Host.dll`).
- In `docker-compose.yaml`: rename `jadwa-api` → a Learnexia-named API service, fix `build.context`/`dockerfile` to reach `backend/`, keep its dependency on healthy `postgres` + started `redis`, keep the existing `ConnectionStrings__*` env injection. Add a compose-level `healthcheck` hitting `/health`.
- Add an **AI-Gateway placeholder** service (e.g. a stub image or a tiny container exposing a port — define what "placeholder" means; see open question) on the same network.
- Add a **web frontend** service (the Expo/Turborepo app is built in P1-08/P1-09; here it is just a compose service entry — likely a placeholder/build stub until the FE Dockerfile lands). Confirm scope with planner — the story lists it but the FE app isn't dockerized yet.
- Decide naming of the shared network (currently `jadwa-network`) — recommend renaming for brand consistency, but that is cosmetic.

**BE-3 — CI pipeline (`.github/workflows/`):**
- GitHub Actions workflow (repo has no existing CI; assume GitHub Actions unless the lead says otherwise — open question) triggered `on: push` (and ideally `pull_request`).
- Steps: checkout → setup .NET 10 SDK → `dotnet restore`/`build` on `backend/Learnexia.Modular.sln` (Release) → `dotnet test` → **non-zero exit fails the job**.
- **Testcontainers requirement:** `Learnexia.IntegrationTests` uses **Testcontainers.PostgreSql**, which needs a **Docker daemon available on the CI runner**. Use a Linux runner (`ubuntu-latest`, Docker preinstalled). Ensure the integration test project runs in CI, or split unit vs integration test jobs if integration tests are flaky/slow.
- Consider building the Docker image in CI to validate the Dockerfile (optional but recommended given the Dockerfile is being rewritten).

**BE-4 — Staging deploy (deploy config):**
- Configure a staging deploy target. Target platform is an **open question** (Azure / Railway / Render). Deliverable is config (workflow job + provider config/manifest) that deploys the built image to a staging env. May require provider secrets — coordinate with the lead (do not commit secrets).

## Handoff → security-auditor
- **Recommended to run** — this story touches infra/secrets and may expose a Hangfire dashboard:
  - Hangfire dashboard (if used) must be **admin-gated**, never anonymous.
  - `/health` must not leak sensitive detail (don't expose connection strings / internal exceptions in the response body; default ASP.NET health UI is fine).
  - Staging deploy must use **secrets/env**, not committed credentials. Note existing `appsettings.json` already ships a `CHANGE_ME` JWT secret and compose ships hardcoded `postgres/admin` + `minioadmin` — flag for staging hardening (env-injected secrets).

## Open questions / assumptions / risks
1. **Deploy target (BE-4): Azure vs Railway vs Render?** — needs a product/infra decision. Affects deploy config + required secrets. **Ask the lead.**
2. **Scheduler (BE-5): Hangfire vs Quartz?** — Hangfire gives a dashboard + persistent jobs (needs storage, ideally Postgres/Redis); Quartz can run in-memory now. Recommend deciding based on whether persistence/visibility is wanted in Phase 4/5. **Ask the lead.** (Affects whether any storage bootstrap is needed.)
3. **Jobs storage** — if Hangfire: in-memory vs Postgres vs Redis storage? In-memory is simplest for "host it now," but loses jobs on restart. **Assumption (flag):** start with the lightest option that satisfies "hosted," defer durable storage to when real jobs land.
4. **AI-Gateway placeholder definition** — what image/behavior? A no-op stub container, a reserved service name, or a minimal echo service? **Assumption:** a placeholder stub service on the network with a documented port; confirm scope.
5. **Web frontend service in compose now vs P1-08** — the FE app isn't dockerized yet. **Assumption:** add a placeholder/commented service or a build stub; the real FE image lands in P1-08/P1-09. Confirm with planner.
6. **CI provider** — assume **GitHub Actions** (repo is git, main branch on what looks like GitHub). Confirm if GitLab/Azure DevOps is intended instead.
7. **Testcontainers in CI** — integration tests need Docker on the runner; assume `ubuntu-latest`. Risk: integration tests may be slow/flaky in CI → consider separate job or `--filter` for unit vs integration.
8. **HTTPS in compose** — current compose mounts `aspnetapp.pfx` with a hardcoded password for Kestrel HTTPS. Decide whether the dev/staging stack should keep HTTPS-in-container or terminate TLS at a reverse proxy. **Assumption:** keep as-is unless it blocks the health probe.
9. **`/health` and rate limiting** — the IP rate limiter applies to `*`; container/orchestrator probes could be throttled. Ensure the probe path is excluded or tolerant.
10. **Health endpoint auth/anonymity** — `/health` must be anonymous (no JWT). Confirm placement vs the middleware pipeline.
