## ⚠️ DECISION: payment provider — Paymob vs Fawry (FLAGGED, needs lead)

- **Stripe does not fully serve EGP** → out. The choice is **Paymob vs Fawry** (Egypt). This is a **product + commercial decision the lead must make** (settlement, fees, recurring-billing support, card-on-file/tokenization capability, webhook model, Egypt market fit). **Surface it; do not pick it.**
- **Recurring billing caveat (RISK):** not every Egyptian provider supports true card-on-file recurring (subscriptions) the same way Stripe does. Fawry is strong on cash/reference payments; recurring card billing may need Paymob's tokenization or a "save card" flow. **The provider choice directly constrains how AC4 (recurring renewal) is implemented** — confirm the chosen provider supports the recurring model before committing to "auto-renew." If neither cleanly supports auto-renew, fall back to **provider-initiated renewal reminders + a re-checkout link** (dunning-adjacent) — flag this to the lead.
- The story is a **split candidate**: (A) one-off hosted checkout that activates Premium for one cycle, and (B) recurring renewal. Planner may split into P10-06a (checkout + activation webhook) and P10-06b (recurring renewal + cancel).

## ⚠️ Web checkout only — NO native IAP (compliance flag)

- The purchase/checkout path is **web checkout** (parent dashboard / provider hosted page). **No native in-app purchase (Apple IAP / Google Play billing).** The native student app does not sell digital goods — it links out to / defers to web.
- **COMPLIANCE — launch-gating:** Apple App Store + Google Play normally **require IAP for digital goods sold inside native apps**; routing to external web checkout is a deliberate PWA-first / "reader-app"-style strategy that **must be validated against current App/Play Store policy before native launch**. Tag the `security-auditor` to flag it. This gates **native** distribution, not the web PWA.

## Business context & value

- **Who benefits:** the **parent** (pays securely, Premium activates and renews without re-entering card details) and the **business** (recurring revenue; PCI scope minimized so we never store card data).
- **Value:** this is the money-in path. Without it, Premium (P10-05) can never activate — the plan stays Free. A successful payment is what flips `Subscription` to `Active` and triggers the first/next P10-02 monthly grant.
- **Success measured by:** a successful payment activates Premium + triggers the grant; a declined payment leaves the plan unchanged with a clear error (handed to P10-09); webhooks reconcile idempotently (no double-activation, no double-grant); no card data ever touches our servers.

---

## Acceptance criteria (testable)

1. Payment runs through an **Egypt payment provider behind an `IPaymentProvider` abstraction**. **No card data touches our servers** — hosted-page/redirect or tokenized flow only (PCI-safe; we never receive/store PAN/CVV).
2. A **successful payment activates Premium** (flips the `PendingPayment` subscription from P10-05 to `Active`, sets cycle dates) and **triggers the next monthly grant (P10-02)** for each of the parent's children.
3. A **declined / failed payment leaves the plan unchanged** (parent stays on Free / prior plan) and surfaces a **clear error**; the failure is handed to **P10-09** (dunning/retry).
4. **Recurring billing:** the subscription **renews on the chosen cadence — monthly (199 EGP) or annual (1990 EGP)**; the charged amount is set **server-side** from `Subscription.BillingPeriod` + the P10-12 config keys (`subscription.monthlyPriceEgp` / `subscription.annualPriceEgp`), never client-supplied. The parent can **cancel** (stops future renewals but **keeps access to the end of the paid cycle**). *(Auto-renew depends on the chosen provider's recurring support — see the flagged decision.)*
5. Provider **webhooks reconcile provider state with our subscription state idempotently** — the same webhook event delivered twice produces **no double-activation and no double-grant** (idempotency key on the provider event id / our payment reference).
6. A **`Payment`** record is created for every charge attempt with the provider reference, amount, currency (EGP), status, and timestamps; state transitions are auditable.
7. **Webhook endpoint is authenticated by provider signature** (HMAC/secret verification), rejects unsigned/forged calls, and is the **only** trusted source for marking a payment succeeded (never trust the client redirect alone).

## Affected modules & data

### Module — `Billing` (schema `billing`) — the same NEW module as P10-05 (lead sign-off)
- All payment entities live in `Billing`. No cross-module FK; the **parent** is a loose id. The **P10-02 grant** is triggered via `Shared.Contracts` (a `SubscriptionActivated` integration event the grant handler consumes), not by a direct cross-module call.

### New entities (this story)
- **`Payment`** — one row per charge attempt: `Id`, `SubscriptionId` (FK within Billing) or `ParentUserId` loose id, `ProviderPaymentRef` (provider's id), `Amount` (decimal), `Currency` (`EGP`), `Status` (enum `Initiated` / `Pending` / `Succeeded` / `Failed` / `Refunded`), `Kind` (`Subscription` vs `Pack` — shared with P10-07), `IdempotencyKey`, `CreatedAt`, `UpdatedAt`. **No card fields** — only the provider token/ref.
- **`WebhookEvent`** (idempotency ledger) — `Id`, `ProviderEventId` (**unique** — the idempotency anchor), `EventType`, `RawPayloadHash`/`Payload`, `ProcessedAt`, `Status`. Recommended so duplicate webhooks are detected and replays are reconcilable. *(Confirm with planner: dedicated table vs reuse the idempotency key on `Payment`.)*
- **`ProviderCustomer` / `PaymentToken`** *(only if the chosen provider needs a stored token for recurring)* — `ParentUserId`, `ProviderCustomerRef`, `ProviderTokenRef` (a token/reference, **never the card**). Needed for card-on-file recurring; not needed for redirect-per-charge. Depends on provider choice.

### Reused from P10-05
- `Subscription` (status transitions `PendingPayment → Active`, renewal extends `CurrentCycleEnd`, cancel sets `Status = Canceled` effective cycle end).

## Handoff → db-migration

- Extend the `BillingDbContext` (created in P10-05) with `Payment`, `WebhookEvent`, and (if needed) `PaymentToken` — schema `billing`. **Coordinate with the P10-05 migration** so the context/initial migration is created once (serialize shared-file edits per PARALLELISM).
- **Unique index on `WebhookEvent.ProviderEventId`** (idempotency) and on `Payment.IdempotencyKey`. Index `Payment.ProviderPaymentRef` and `Payment.SubscriptionId`.
- **No card columns** anywhere — store provider references/tokens only.
- No UoW; for "mark payment succeeded + activate subscription + emit grant event" use an **explicit transaction** so the activation is atomic with the payment row.

## Handoff → backend-feature

- **`IPaymentProvider` abstraction** (in `Billing.Application` or a `Billing.Infrastructure` adapter). **DESIGN-PATTERN NOTE:** an abstraction with a single Paymob/Fawry implementation behind an interface is acceptable mirroring; if the planner/implementer is tempted to build a **provider Strategy/Factory** to swap providers at runtime, **stop and ask the lead first** (CLAUDE.md rule 8). For now: one interface, one concrete adapter for the chosen provider, registered in DI.
  - Methods (shape): `CreateCheckoutSession(parent, plan, idempotencyKey)` → returns a hosted-page URL / redirect token; `VerifyWebhookSignature(headers, body)`; `ParseWebhookEvent(body)`; `CreateRecurringMandate`/`ChargeSavedToken` (only if provider supports card-on-file recurring); `Refund(paymentRef, amount)` (used by P10-09).
- **Commands:** `StartSubscriptionCheckout(parentUserId)` (called by P10-05's upgrade) → creates `Payment{Status=Initiated}` + returns the redirect URL. `HandleProviderWebhook(signedPayload)` → verifies signature, dedups on `ProviderEventId`, transitions `Payment`/`Subscription`, emits `SubscriptionActivated` (P10-02 grant) on success / `PaymentFailed` (P10-09) on failure. `CancelSubscription` → stops renewal, access to cycle end.
- **Idempotency:** every webhook handler checks the `WebhookEvent`/idempotency table first; a duplicate event id is a no-op success. Activation + grant emission happen exactly once.
- **Reconciliation:** a scheduled (Hangfire) reconcile job (story AC5 — "reconcile provider state with our state") queries the provider for payments we have in a non-terminal state and corrects drift. *(Confirm Hangfire is the infra per P10-02's note.)*
- **Secrets:** provider API keys + webhook signing secret come from config/secret store (never committed). `ILoggerManager` for logging — **never log card data, full payloads with PII, or secrets**.
- **Envelope:** `BaseResponse<T>` / `Successed`; commands auto-validated via `ValidationBehavior`.

## Handoff → security-auditor (MANDATORY — Critical/High block the gate)

Audit before the reviewer gate. Focus:
- **PCI / no-card-data:** confirm no PAN/CVV ever reaches our servers/logs/DB; redirect or tokenized only.
- **Webhook security:** signature verification is mandatory and correct; unsigned/forged/replayed events are rejected; the webhook is the only trusted success source (client redirect alone never activates).
- **Idempotency:** no double-activation / double-grant on replayed events; idempotency key is provider-event-scoped.
- **Secrets handling:** API keys + signing secret in secret store, not in code/logs.
- **Authz:** only the owning parent can start checkout for their own subscription; the webhook endpoint is provider-authenticated (signature), not user-JWT.
- **Amount/currency integrity:** the charged amount = the configured plan price (199 EGP); the server, not the client, sets the amount.

## Handoff → designer + frontend + frontend-e2e-tester

- **Surface:** parent area only — the **upgrade/checkout flow** launched from the P10-05 "Plan & billing" tab. Because the provider hosts the card page (redirect), the FE work is the **pre-checkout summary, redirect-out, return/landing (success/pending/failed), and the "manage/cancel subscription" control** — not a card form (we never render one).

- **frontend-e2e-tester:** parent web PWA — start checkout (provider stub/sandbox), success return activates Premium, declined return leaves plan unchanged + shows error, cancel keeps access to cycle end, RTL/ar+en.

## Handoff → api-tester

- Endpoints (checkout-start, webhook, cancel) → api-tester after backend-feature.
- Cases: start checkout returns a redirect ref + creates `Payment{Initiated}`; **webhook success** activates subscription + emits the grant event **once**; **duplicate webhook** is a no-op (no double-activation/grant); **webhook with bad/missing signature is rejected** (401/400); **declined webhook** leaves plan unchanged + records `Payment{Failed}` (hands to P10-09); cross-account checkout denied; `BaseResponse<T>`/`Successed` envelope. Use a provider **sandbox/stub** — never real card data in tests.
