# Pipeline Brief — P3-04: Explain a concept on demand

> **AI Helper MVP context:** See `docs/briefs/ai-helper-mvp.md`. P3-04 implements **intent #1 — "اشرح السؤال" (explain the active skill/question)**.
> **Eval Gate:** Runtime `Explain` calls use `claude-sonnet-4-6` (Sonnet floor) pending the AI evaluation gate. The Sonnet floor may only be lowered to Haiku after Gate A passes. See **[docs/briefs/ai-eval-gate.md](ai-eval-gate.md)** — do not trust the 80% Haiku target for Arabic pedagogy until measured. Scope is constrained to the ACTIVE skill or question only — not "explain anything in the world." Grounding is fetched via `ILearningContextProvider` (`SeededCorpusContextProvider` at MVP; `RagContextProvider` later via config swap). If `ILearningContextProvider` returns no approved context, the handler returns the refuse-and-redirect response (not an explanation). Instrumentation events `HelpRequested`, `HelpDelivered`, and `HelpDeclined` are emitted here. Build order is parallel with Gamification-FE / Parent work — NOT gated on BL-*.

## Summary & traceability
- **Task (1 line):** Expose a student-facing **"explain this concept"** endpoint (intent: "اشرح السؤال") that fetches grounding via `ILearningContextProvider` (seeded corpus at MVP) → scope-guards via P3-02 intent validator → orchestrates **Prompt Builder (P3-03) → AI Gateway (P3-01) → Safety Layer (P3-02)**, returns an age/grade/language-appropriate explanation scoped to the ACTIVE skill/question, **streams** it to the UI, and stays within the < 4 s AI latency target — without the AI deciding progression or difficulty. If no context is available, returns a redirect response instead of an explanation.

- **FR-IDs:** **FR-AI-1** (explain a concept on demand). Exercises **FR-AI-4** (Safety, mandatory), **FR-AI-5** (Prompt Builder context injection), **FR-AI-6** (AI generates content only — no progression/difficulty decisions), **NFR-1** (< 4 s).
- **BRD goal:** **G2 (Learning outcomes)** — understanding a lesson in the student's language and level.

## Business context & value
- **Who benefits:** the **student** (on-demand, level-appropriate explanations in Arabic or English) and the **parent** (trust — explanations are curriculum-grounded and safety-filtered).
- **Value:** "explain" is the core tutor interaction — the moment a stuck child gets unstuck. Grounding (P3-07) + personalization (P3-03) + safety (P3-02) are what make it trustworthy; streaming is what makes it feel conversational (NFR-1, P3-12).
- **Success measure:** a student requests an explanation of a concept/lesson → receives a grounded, age/grade/language-appropriate explanation that has passed the Safety Layer → it streams to the UI and completes within the latency target → the AI made no progression/difficulty decision.

## Current-state findings (reality in code)
1. **None of the dependencies exist yet:** no AI Gateway (P3-01), Safety Layer (P3-02), Prompt Builder (P3-03), or RAG retrieval (P3-07) in `backend/src`. **P3-04 is an orchestration over a stack that must be built first.**
2. **No streaming primitives in the backend today** — all controllers return `BaseResponse<T>` via `NewResult(...)` (buffered JSON). Streaming (SSE / chunked transfer / `IAsyncEnumerable`) is a **new pattern** here → **CLAUDE.md rule 8 (ask-first)** applies to *how* streaming is implemented (OQ-1).
3. **The `BaseResponse<T>` envelope is buffered by design** — it doesn't naturally express a token stream. The team must decide whether the streaming response bypasses the envelope (raw SSE) while errors still use it (OQ-1/OQ-2).
4. **Typed-HttpClient + fail-soft pattern exists** (`ExpoPushSender`, `TurnstileCaptchaVerifier`) to mirror for the Gateway client.
5. **`AITutorBubble` component already exists** in `@learnexia/ui` and is rendered statically in the lesson screen today (W12 brief: "AI Tutor bubble slot rendered with the explanation text — no live AI until P3-04"). P3-04 is what makes that bubble live.
6. **Child auth model is in place** — quiz endpoints already use `[Authorize(Roles="Student")]` with the child JWT (parent-driven onboarding). The explain endpoint should resolve grade/age/language from the **authenticated child**, not client input.

## Acceptance criteria (testable)
1. **AC-1 (grounded + appropriate):** Given a lesson/concept, requesting an explanation returns an **age- and grade-appropriate** explanation **in the student's language** (Arabic or English), driven by the Prompt Builder (P3-03) injecting grade/age/language/curriculum-context/child-safe tone. Explanation is scoped to the **active skill/question** — the prompt does not invite the model to explain general world topics.
2. **AC-2 (context-grounded + safe):** The explanation is grounded in context from `ILearningContextProvider` (seeded corpus at MVP) and passes the **Safety Layer (P3-02)** before any token reaches the student — no bypass path.
3. **AC-3 (refuse-and-redirect — hard criterion):** When `ILearningContextProvider` returns no approved context (empty), the handler returns the redirect response ("خلينا نكمل تحدي [skill] الحالي...") and does NOT call the LLM. Test: ask about a topic outside the active skill → redirect returned, no AI call made.
4. **AC-4 (streaming + latency):** The response **streams** to the UI (token/chunk streaming) and completes within the **< 4 s** AI latency target (NFR-1) for typical requests.
5. **AC-5 (no progression decisions):** The AI only generates the explanation — it does **not** decide progression, difficulty, or unlocking (FR-AI-6). The endpoint returns text only; no mastery/XP/unlock side effects.
6. **AC-6 (graceful errors):** A provider/gateway error returns a **typed, gentle error** (no raw stack trace), surfaced to P3-12 as a retry-able state.
7. **AC-7 (instrumentation):** `HelpRequested`, `HelpDelivered`, or `HelpDeclined` events are emitted (fire-and-forget) for every explain request, including the no-context redirect case. These events feed P5-03 analytics and P6-02 eval.
8. **AC-8 (conventions):** `[Authorize(Roles="Student")]`; grade/age/language resolved from the child JWT (not client-supplied); `ILoggerManager`; module isolation. Streaming-vs-envelope decision (OQ-1) reflected consistently.

## Affected modules & data
- **Orchestration location (OQ-3):** an explain command/handler that composes retrieval (P3-07) → prompt (P3-03) → gateway stream (P3-01) → safety (P3-02). Likely lives in the **tutor/AI surface** — either the new `Curriculum` module, a dedicated `AiTutor` slice, or `Learning`. Resolve the seam (OQ-3) — but it must reach `QuizQuestion`/lesson context only by id/contract, never cross-module FK.
- **No new persisted entity strictly required** for the explanation itself. **Tutor-interaction logging** (which concept, when, model, safety verdict) may be wanted for analytics/cost (P7-11) and to feed adaptivity — but the *content* is ephemeral (OQ-4).
- **Consumes (cross-cluster):** P3-07 (retrieval), P3-03 (prompt), P3-01 (gateway/stream), P3-02 (safety). All must exist first.

## Handoff → backend-feature
- **Request:** `ExplainConceptCommand { LessonId | ConceptId | SkillId, Question?/free-text? }` — grade/age/language resolved from `ICurrentUserService` (child JWT), **not** the body.
- **Handler orchestration:**
  1. **Retrieve** (P3-07) curriculum context for the concept + the child's grade/subject (+ weak-area if available from P3-09 later).
  2. **Build prompt** (P3-03) injecting grade/age/language/context/child-safe tone + the subject-specific explain template.
  3. **Generate** (P3-01 Gateway) — request a **streamed** completion (model routed cheap/premium per NFR-9).
  4. **Safety** (P3-02) — apply the Safety Layer to the output. **Streaming + mandatory safety is in tension** (you can't show tokens you haven't safety-checked): decide buffer-then-filter-then-stream, chunk-level filtering, or stream + post-hoc redaction (OQ-2). The headline tension of this story.
  5. **Stream** the pre-checked text to the client using the **pinned SSE wire contract** (see Handoff → frontend section above).
- **Streaming mechanism (OQ-1 — ask-first):** SSE (`text/event-stream`) confirmed per task file. The pinned wire contract is: `event: message` / `event: redirect` / `event: error` / `event: done` — details in the "Handoff → frontend (contract for P3-12)" section above.
- **No progression side effects** (AC-4): the handler writes no mastery/XP/unlock. If interaction logging is added (OQ-4), it is fire-and-forget and never blocks the stream.
- **DI:** gateway/safety/prompt/retrieval clients registered in the owning module's Infrastructure (mirror `ExpoPushSender` typed-HttpClient + fail-soft).

## Handoff → frontend (contract for P3-12)
- **Endpoint:** `POST /api/{tutor}/Explain` (or similar), `[Authorize(Roles="Student")]`, **streaming response** (SSE/chunked per OQ-1). Body carries the concept/lesson id (+ optional free-text question); no grade/age/language (server-derived).
- **Stream contract (PINNED — do NOT deviate):** `event: message` + `data: {"content":"<token>"}` for each content chunk; `event: redirect` + `data: {"type":"lesson","targetId":"<skillId>"}` for the no-context refuse-and-redirect; `event: error` + `data: {"code":"<ErrorCode>","message":"<safe message>"}` for failures; `event: done` + `data: [DONE]` as the stream terminator. **Safety rule: provider output is buffered → safety-filtered (P3-02) → only then streamed as `event: message`. Never raw-passthrough unfiltered tokens to a child.** Pin this contract in HANDOFF.md before P3-12 FE dispatch. P3-12's brief specifies the FE side.
- **Error shape:** typed gentle error (AC-5) → P3-12 shows a "tap to retry" state, not a crash.

## Handoff → security-auditor (AI-safety — HARD GATE)
- AI text **shown to children** → hard gate. Audit:
  - **No Safety-Layer bypass** under streaming (AC-2) — the resolved streaming strategy (OQ-2) must guarantee no unfiltered token reaches the child.
  - **Prompt-injection** via the free-text question / retrieved chunks can't subvert the child-safe system prompt or exfiltrate the prompt.
  - **Child-data minimization** — grade/age/language come from the JWT; the request and logs don't leak more child PII than needed.
  - **No secret leakage** in gateway/safety adapter logs.
  - **Abuse/cost** — rate-limit explain requests (a child can't spam expensive premium-model calls).

## Handoff → api-tester
- Happy path: explain a seeded concept → streamed, grounded, language-correct (Arabic + English) output. Safety-block path: a forced-unsafe generation never streams to the client. Empty-retrieval path: explanation degrades gracefully (no fabrication — depends on the OQ on declining vs general-explain, see OQ-5). Provider-error path: typed gentle error, no stack trace. Auth: non-Student JWT → 401/403. Use **stubbed gateway + safety** for determinism (don't hit live LLMs in CI). Test the streaming wire format end-to-end.

## Open questions / assumptions / risks
- **OQ-1 (STREAMING MECHANISM — ask-first, KEY):** SSE vs `IAsyncEnumerable` chunked vs WebSocket? This is a **new backend pattern** (everything is buffered `BaseResponse<T>` today) → **CLAUDE.md rule 8 requires lead approval before implementing.** Recommend **SSE**. Gates both backend-feature and P3-12.
- **OQ-2 (streaming vs mandatory safety — KEY):** the Safety Layer is mandatory (FR-AI-4) but streaming shows tokens before the full response exists. Options: (a) **buffer fully → safety-filter → then "stream" the pre-checked text** (safest, slight latency cost — easiest to satisfy "no bypass"); (b) **chunk-level safety filtering** as tokens arrive (lower latency, harder to guarantee); (c) stream + post-hoc redaction (risky). Recommend **(a)** at MVP to make AC-2 provably true, accepting the latency hit (still target < 4 s). Confirm.
- **OQ-3 (orchestration location/seam):** which module owns the explain handler, and how does it reach retrieval (Curriculum) + lesson context (Learning) without a cross-module FK? Recommend a dedicated **AI-tutor slice** (or in `Curriculum`) consuming Learning/Curriculum via `Shared.Contracts`. Resolve before backend-feature.
- **OQ-4 (tutor-interaction logging):** persist explain interactions (concept, model, safety verdict, latency) for cost/quality (P7-11) and adaptivity? Recommend a lightweight log at MVP; a table only if a dashboard needs it.
- **OQ-5 (empty-retrieval behavior for explain):** unlike P3-06 (which must decline), should *explain* still produce a general grounded-in-prompt-context explanation when retrieval is thin, or also decline? Recommend: explain may proceed with reduced grounding (the prompt still carries grade/age/language + lesson title), since declining to explain a real lesson is poor UX — but it must NOT fabricate specific curriculum facts. Confirm the line.
- **Risk — hard blockers:** needs P3-01/02/03/07 all merged. Same blocker profile as P3-05.
- **Risk — latency under safety-buffering (OQ-2a):** buffering the full response before streaming eats into the 4 s budget; mitigate with model routing (cheap model for simple explains) and a streamed-typing illusion over the pre-checked text.

## Cost & model routing (cache-primary architecture)

> **See the authoritative strategy:** [docs/briefs/ai-cost-routing.md](ai-cost-routing.md). This section captures P3-04's specific responsibilities.

### ConceptExplanationCache is the PRIMARY served path

Pre-generated concept explanations (produced OFFLINE via the Batch API) are served as the first response. The runtime LLM call is a cache-miss fallback for the dynamic ~10-20% only.

**Lookup key:** `(ConceptId, GradeId, Language, Difficulty)` — every combination is finite and pre-generable.

**Handler orchestration — revised with cache-first:**

1. **Cache lookup first:** query `ConceptExplanationCache` by `(ConceptId | LessonId, GradeId, Language, Difficulty)`. On **cache hit** → stream the cached content immediately (zero LLM cost). Skip steps 2-6 below.
2. **On cache miss only:** call P3-07 retrieval to get curriculum chunks; proceed with reduced grounding if empty (OQ-5).
3. Build prompt via P3-03 Prompt Builder.
4. Call P3-01 Gateway (Sonnet `claude-sonnet-4-6` via `AiModelRouter` — NOT Opus; runtime default is Sonnet for Explain). Apply prompt-caching `cache_control` on the static system-prompt + curriculum-context portions.
5. **Check quota (P3-01 gateway):** if student is out of runtime budget → return the best cached canned response (see [ai-cost-routing.md §5](ai-cost-routing.md)), never an error.
6. Buffer full response (OQ-2a); apply P3-02 Safety Layer; stream pre-checked text.
7. **Write result to `ConceptExplanationCache`** async (fire-and-forget) so the next student gets a cache hit.

**Student-answer-specific explains** ("why is my specific wrong answer wrong") have no stable cache key (the student's answer is unique) → always runtime lane, Sonnet, with quota check.

### New db-migration requirement

`ConceptExplanationCache` is a new table. Module placement: `ai` schema (the `Ai` module owns AI-generated artifacts; `Curriculum` owns the source curriculum data). This needs a db-migration task (flag to planner).

See [ai-cost-routing.md §4](ai-cost-routing.md) for the full table schema.

### Offline batch pre-generation job (P3-04 trigger)

An offline background job (Hangfire or hosted service — confirm with lead) enumerates all `(ConceptId, GradeId, Language, Difficulty)` combinations not yet in cache and submits them to the Anthropic Batch API:
- Generation model: Sonnet (`claude-sonnet-4-6`).
- QA pass model: Opus (`claude-opus-4-8`), sets `QaPassedAt` on the cache row.
- This job is part of P3-04's scope (or broken out as a sub-task by the planner).

Always verify current Anthropic pricing/model IDs before launch.
