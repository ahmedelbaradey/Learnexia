# Pipeline Brief — P8-04 Change a child's learning language (parent-only, fresh start)

## Summary & traceability
- **Task (1 line):** Let a **parent** change their **own child's** `User.LearningLanguage` (parent-only, student cannot), gated behind an **explicit confirm flag**; on commit, publish a `LearningLanguageChangedIntegrationEvent` that the **Learning** module consumes to **reset the child's Math/Science attempts (+ derived mastery)** while leaving Arabic/English progress and all gamification untouched.
- **User story:** `user-stories/Phase-8-Localization/P8-04-change-child-learning-language.md` (SOURCE OF TRUTH).
- **Task file:** `tasks/Backend/Phase-8-Localization/P8-04-BE.md` (BE-1..BE-7).
- **Requirements / SRS:** NFR-5 (child-data protection), Phase-8 localization FRs; design of record: `docs/architecture/localization-architecture.md` §5.
- **BRD goal:** G1 (personalized/adaptive learning — correct medium of instruction) + G2 (trust/safety — destructive change is parent-gated & confirmed).
- **Phase / epic:** Phase 8 — Localization · Epic: Localization · SP 5.
- **Depends on (merged):** P8-01 (`User.LearningLanguage` + `learning_language` JWT claim), P8-02 (`Subject.SubjectCode` + `Subject.Language`), P8-03 (`SubjectLanguageResolver` + language guard). Also P1-04 (ParentStudent link / family scope).
- **Product-decision overrides honored:** parent-driven (no student self-service), 4 subjects, no teacher role.

## Business context & value
- **Who benefits:** the **parent** (corrects a mis-set medium of instruction deliberately, normally at start of school year) and the **child** (gets curriculum in the right language).
- **Value:** a wrong learning language makes Math/Science unusable; this is the only safe path to fix it. It is **destructive** (Math/Science progress no longer maps to the new-language trees and is reset), so it must be **parent-only + explicitly confirmed**, never a silent toggle.
- **Success measured by:** change is rejected without confirm (424); after confirm, the child sees the new-language Math/Science trees from a clean slate on next sign-in (new `learning_language` claim, P8-01), Arabic/English progress is intact, and XP/streak/badges/level are retained.

## Acceptance criteria (testable)
1. Only a **parent** linked (family-scoped) to the target child can change `LearningLanguage`; a non-linked parent → **Forbidden (403)**; a student/other role → blocked by role auth.
2. Request **without the confirm flag** → **`BusinessValidation` (HTTP 424 / `FailedDependency`)**, and **no** change is made and **no** event is published.
3. Request **with confirm flag = true** and a **valid new language** (`ar`|`en`) **different from current** → `User.LearningLanguage` updated; success envelope returned.
4. After the User update **commits**, a `LearningLanguageChangedIntegrationEvent` (studentId, old, new, eventId, occurredOnUtc) is **published** (post-commit, best-effort).
5. The **Learning** consumer **deletes the child's Math/Science `Attempt` rows** (StudentAnswers cascade) so derived mastery resets; **Arabic/English `Attempt`/`StudentAnswer` rows are untouched**.
6. The consumer is **idempotent** (re-delivery of the same event causes no error and no extra effect).
7. **No Gamification consumer** is added — XP/streak/badges/level are **retained**.
8. On the child's **next sign-in**, the JWT carries the new `learning_language` (already covered by P8-01-BE-4 token re-issue; verify, do not re-implement).
9. (Optional, lead to confirm) Changing to the **same** language → no-op success or a benign validation message (see Open Questions).

## Affected modules & data
- **Parent module** (`Learnexia.Modules.Parent.*`) — NEW command/handler/validator + 1 controller endpoint. This is where family-scope auth already lives (mirrors `UpdateChild`).
- **Identity module** (`Learnexia.Modules.Identity.Infrastructure`) — extend the `IChildAccountService` seam to mutate `User.LearningLanguage` and **publish** the integration event after the User save (mirrors `CreateChildAsync` → `PublishUserRegisteredEventAsync`). `User.LearningLanguage` already exists (P8-01).
- **Shared.Contracts** (`Learnexia.Shared.Contracts/Identity`) — NEW `LearningLanguageChangedIntegrationEvent`.
- **Learning module** (`Learnexia.Modules.Learning.Application`) — NEW `IntegrationEventHandlers/` folder + consumer; reset logic via the existing Attempt→Lesson→Unit→Subject join.
- **NO new entities, NO schema change expected.** `StudentSkillMastery` does **NOT** exist — mastery is a **computed** `SkillMastery` record (`Learning.Domain/Services/SkillMastery.cs`) derived from `StudentAnswer`/`Attempt`. "Reset mastery" therefore = delete the underlying Math/Science `Attempt` rows (StudentAnswers cascade per `StudentAnswerConfig`, `DeleteBehavior.Cascade`). **db-migration is almost certainly NOT needed** (confirm during planning).

## Handoff → db-migration
- **Expected: NO migration.** All required fields exist:
  - `User.LearningLanguage` (Identity schema, P8-01).
  - `Subject.SubjectCode` (enum int: MATH=0, SCIENCE=1, ARABIC=2, ENGLISH=3) + `Subject.Language` (ContentLanguage int) — P8-02.
  - `Attempt` (StudentId int loose-ref, LessonId int loose-ref) + `StudentAnswer` (cascade on Attempt) — already migrated.
- **Only** create a migration if planning decides the reset must mark rows (e.g. a soft-delete/`ResetAt` column) instead of hard-deleting — that is an Open Question; default is hard delete (no migration).

## Handoff → backend-feature
**1. Parent command (BE-1, BE-2) — `Learnexia.Modules.Parent.Application/Features/ChangeChildLearningLanguage/`**
- `ChangeChildLearningLanguageCommand : ICommand<BaseResponse<...>>` with: `int ChildId`, `string NewLearningLanguage` (`"ar"|"en"`), `bool ConfirmFreshStart`. **No ParentId in the body** (resolved from JWT — IDOR rule, mirror `UpdateChildCommand`).
- `...Validator` (shape-only): `ChildId > 0`; `NewLearningLanguage` ∈ {`ar`,`en`}; `ConfirmFreshStart` is shape-validated only if you want shape-level rejection — **but the 424 confirm gate belongs in the handler** (validator failures return 422 via `ValidationBehavior`; the confirm gate must be `BusinessValidation` = **424**). Recommend: validator checks language/childId only; handler enforces confirm.
- `...Handler : BaseResponseHandler` (mirror `UpdateChildCommandHandler`):
  1. resolve `parentId` from `ICurrentUserService` → null ⇒ `Unauthorized`.
  2. `ConfirmFreshStart == false` ⇒ **`BusinessValidation<T>(...)` (424)** — return before any link check/mutation/publish.
  3. `_linkService.IsLinkedAsync(parentId, ChildId)` false ⇒ `Forbidden` (`CannotEditChildNotInFamily`).
  4. call the seam (below) to mutate + publish; map shaped result (`ChildAccountError.NotFound` → `Forbidden`, others → `BadRequest`/`ServerError`); wrap in try/catch → `ServerError`.
- **Endpoint:** add to `ParentController` (`api/Parent`), `[Authorize(Roles = "Parent,Admin,SuperAdmin")]` (controller-level already), e.g. `PUT api/Parent/Change-Learning-Language`. `=> NewResult(await Mediator.Send(command))`.

**2. Identity seam + publish (BE-1, BE-3, BE-4) — `IChildAccountService` / `IdentityChildAccountService`**
- Add a seam method, e.g. `Task<ChildLanguageChangeResult> ChangeLearningLanguageAsync(int childUserId, string newLearningLanguage, CancellationToken ct)`. (`UpdateChildAsync` deliberately does NOT touch `LearningLanguage`, so a dedicated method is correct.)
- Impl: `FindByIdAsync` → null ⇒ `NotFound`; capture `oldLang = child.LearningLanguage`; set `child.LearningLanguage = newLang`; `child.UpdatedAt = UtcNow`; `UpdateAsync` (Identity persists immediately — no UoW in Identity, same as `UpdateChildAsync`). On success, **publish after the save** via the existing best-effort pattern (mirror `PublishUserRegisteredEventAsync`: try/catch, log, never fail the committed change). Return shaped result incl. old/new.
- **Module isolation:** Parent calls Identity only via this `Shared.Contracts` seam (it already does for create/update); no project reference added.

**3. Integration event (BE-3) — `Learnexia.Shared.Contracts/Identity/LearningLanguageChangedIntegrationEvent.cs`**
```csharp
public sealed record LearningLanguageChangedIntegrationEvent(
    Guid EventId,
    DateTime OccurredOnUtc,
    int StudentId,
    string OldLanguage,
    string NewLanguage) : IIntegrationEvent;
```
- Mirror `UserRegisteredIntegrationEvent`: carry **only** what the consumer needs (studentId + old/new language). No PII beyond the studentId.

**4. Learning consumer (BE-5, BE-6) — `Learnexia.Modules.Learning.Application/IntegrationEventHandlers/LearningLanguageChangedIntegrationEventHandler.cs`**
- `INotificationHandler<LearningLanguageChangedIntegrationEvent>`, **fail-soft** (try/catch/log — mirror Gamification's `LessonCompletedIntegrationEventHandler`; `IsolatedNotificationPublisher` already isolates at publisher level).
- **Pattern (consistency):** mirror Gamification's "send an internal command so the write runs through the module's `UnitOfWorkBehavior`" — i.e. a `ResetMathScienceProgressCommand(StudentId, OriginEventId)` handled inside Learning, so the delete commits through `UnitOfWorkBehavior` (ADR 0001) with audit stamping and a clean boundary. (Do NOT write to `LearningDbContext` directly from the notification handler.)
- **What to delete — identify Math/Science attempts for the student:** reuse the existing join shape (`LearningRepository`): `Attempt.LessonId → Lesson.Unit.SubjectId → Subject` where `Subject.SubjectCode ∈ {MATH, SCIENCE}`. Collect those `Attempt` ids for `StudentId` and **remove them**; `StudentAnswer` rows cascade (`StudentAnswerConfig` `DeleteBehavior.Cascade`). Stage deletes via `ILearningRepository.DeleteRangeAsync` (no `SaveChangesAsync` in repo — UoW commits).
- **Note on language scope:** because Math/Science attempts are filtered by `SubjectCode` (not by `Subject.Language`), this deletes **all** Math/Science attempts for the student regardless of which language tree they belong to. That is the simplest correct interpretation of "fresh start" — but confirm vs "prior-language tree only" (Open Question Q1). The `OldLanguage`/`NewLanguage` payload is included so the consumer *can* scope to the prior-language subjects if the lead chooses that.
- **Idempotency (BE-5):** deleting a set that is already empty is naturally idempotent (re-delivery deletes nothing). No extra dedupe table required. If the lead chooses soft-delete/marking instead (Q1), add an idempotency guard. Keep `EventId` available as the dedupe key either way.
- **DI registration:** the host-level unified MediatR config (ADR 0002 §4) already scans all module assemblies, so the new `INotificationHandler` is discovered automatically. Verify the Learning Application assembly is in the host MediatR scan (it is — Learning already has handlers); no new registration expected.

**5. Gamification (BE-6):** **confirm there is NO consumer** of `LearningLanguageChangedIntegrationEvent` in Gamification — XP/streak/badges/level are retained. This is a decision check, not code.

## Handoff → frontend
- **Not in this brief's scope (backend-only story).** The "very clear fresh-start warning" copy lives in the parent app (FE) and is a separate FE task; the backend contract for FE is: `PUT api/Parent/Change-Learning-Language` with `{ childId, newLearningLanguage, confirmFreshStart }`; `confirmFreshStart=false` ⇒ 424. No Design Spec / `designer` stage needed for the backend story.

## Open questions / assumptions / risks
- **Q1 (reset scope — for lead):** delete **ALL** the student's Math/Science attempts, or **only the prior-language tree's** Math/Science attempts? Default assumption: **ALL Math/Science** (simplest, and after a switch the old-language progress is the only progress that exists for those subjects, since the student only ever sees one language tree at a time). The event carries `OldLanguage` so prior-language-only is implementable if preferred.
- **Q2 (delete vs soft-delete — for lead):** **hard delete** `Attempt` rows (default — no migration, StudentAnswers cascade) vs **soft-delete/mark reset** (audit-preserving, requires a schema column + migration). Default: hard delete. Note: this conflicts slightly with the product-wide "grade transition preserves history" principle — confirm that a *language* change is intentionally destructive for Math/Science (the story explicitly says it resets, so assumed yes).
- **Q3 (same-language request):** if `NewLearningLanguage == current`, return benign success (no event, no reset) or a validation message? Default assumption: treat as no-op success and skip publish (avoids a needless destructive reset).
- **Q4 (confirm-flag transport):** confirm `ConfirmFreshStart` is a request-body boolean (assumed) vs a header. Default: body field.
- **Risk (R1 — lost reset on crash):** in-process best-effort dispatch (Outbox deferred, ADR 0002 §5) means a process crash between User commit and event dispatch leaves Math/Science progress un-reset while the language is already changed. Acceptable for MVP (rare, parent-initiated, re-runnable); flag for the lead. A manual re-publish or re-issuing the change recovers it.
- **Risk (R2 — ghost reset on rollback):** Identity has no UoW; `UpdateAsync` commits immediately, so the publish happens strictly after a real commit — low risk, mirrors `CreateChildAsync`.
- **Assumption:** `learning_language` JWT re-issue on next sign-in is fully delivered by P8-01-BE-4; this story only verifies it (api-tester), does not modify token issuance.

## Design-pattern check (rule #8)
- **No NEW design pattern required.** Every piece mirrors an existing shape: command/validator/handler (Parent `UpdateChild`), cross-module seam + best-effort publish (Identity `CreateChildAsync`), integration-event contract (`UserRegisteredIntegrationEvent`), notification consumer → internal command → UoW (Gamification `LessonCompletedIntegrationEventHandler`), and the Attempt→Lesson→Unit→Subject join (`LearningRepository`). If the implementer feels tempted to introduce an abstraction, stop and ask the lead.

## Recommended pipeline order (first cut — planner finalizes)
1. **db-migration:** likely **SKIP** (confirm no schema change; only needed if Q2 → soft-delete).
2. **backend-feature (batch B1 — Shared.Contracts + Identity + Parent):** `LearningLanguageChangedIntegrationEvent` (BE-3) → `IChildAccountService.ChangeLearningLanguageAsync` + publish (BE-1, BE-4) → Parent command/validator/handler/endpoint with confirm gate (BE-1, BE-2). These can be built together (one module-isolation-respecting unit).
3. **backend-feature (batch B2 — Learning consumer, BE-5/BE-6):** consumer + internal reset command; depends only on the event contract (BE-3), so it can run **in parallel** with the Identity/Parent publisher work once the contract type exists.
4. **security-auditor (gate, BE-7):** REQUIRED — privilege-sensitive (parent-only/family-scope) + destructive (child-data reset). Critical/High block the reviewer gate.
5. **api-tester (BE-7):** running-API tests — confirm-flag gate (424 + no change/no event), parent-only/family-scope (403), Math/Science reset, Arabic/English untouched, gamification (XP/streak/badge) retained, idempotency on re-delivery, same-language no-op (per Q3).
6. **reviewer** gates against the acceptance criteria above + CONVENTIONS.md.
7. **committer** after PASS — `feat/P8-04-…` branch + PR.
