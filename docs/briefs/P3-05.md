# Pipeline Brief — P3-05: Progressive hints & simpler re-explanations

> **AI Helper MVP context:** See `docs/briefs/ai-helper-mvp.md`. P3-05 implements two of the four allowed helper intents: **intent #2 — "اديني تلميح" (give me a hint)** and **intent #3 — "ليه إجابتي غلط" (why is my answer wrong)**.
> **Eval Gate:** Runtime `Hint` and `WhyWrong` calls use `claude-sonnet-4-6` (Sonnet floor) pending the AI evaluation gate. The Sonnet floor may only be lowered to Haiku after Gate A passes. See **[docs/briefs/ai-eval-gate.md](ai-eval-gate.md)** — do not trust the 80% Haiku target for Arabic pedagogy until measured. Intent #2 is the cached/seeded-first escalating hint. Both intents fetch grounding via `ILearningContextProvider`. Refuse-and-redirect applies to both: no context = redirect, not a hint. Instrumentation events `HelpRequested`, `HelpDelivered`, `HelpDeclined` are emitted here. Build order is parallel with Gamification-FE / Parent work — NOT gated on BL-* or P3-07.

## Business context & value
- **Who benefits:** the **student** (scaffolded help that builds understanding instead of giving answers) and the **parent** (pedagogically sound, not a cheat machine).
- **Value:** progressive hints are the difference between a tutor and an answer key. The escalation ladder (nudge → specific → simpler re-explanation) is the core scaffolding loop; recording hint usage (P2-08) feeds the behavioral model (P3-08) so the system learns where each child struggles.
- **Success measure:** a wrong-answer hint nudges **without revealing** the answer; a second hint is **more specific**; a "simpler" request returns a **lower-complexity** re-explanation; all output passes Safety and respects the child's language/grade; hint usage is recorded for the answer (P2-08 seam).

## Acceptance criteria (testable)
1. **AC-1 (hint nudges, no reveal — intent #2):** Given a wrong answer, requesting a hint ("اديني تلميح") returns a hint that **nudges without revealing the full answer**. The prompt (P3-03) explicitly forbids stating the answer; a post-generation check guards against the model leaking it (OQ-4). Hint is scoped to the active question/skill — not a general hint about the subject.
2. **AC-2 (why-wrong — intent #3, always runtime):** Requesting "ليه إجابتي غلط" with the student's specific wrong answer as input generates a **response that explains why THAT specific answer is wrong** — using the student's actual wrong answer as the dynamic input. This intent always calls the gateway (no cache key — the wrong answer is unique). Test: two different wrong answers to the same question produce different why-wrong responses.
3. **AC-3 (refuse-and-redirect — hard criterion):** When `ILearningContextProvider` returns no approved context for the active skill, the handler returns the redirect response and does NOT call the LLM. Applies to both the hint intent and the why-wrong intent. Test: student in Fractions asks about Atoms → redirect response, no LLM call.
4. **AC-4 (escalation):** Requesting another hint **escalates** to more specific guidance (hint level 2 > level 1 in specificity). The handler knows the current hint level (OQ-2) and prompts accordingly.
5. **AC-5 (simpler re-explanation):** Requesting a simpler explanation returns a **re-explanation at a lower complexity level** (reuses the P3-04 explain pipeline with a "simplify / lower reading level" instruction).
6. **AC-6 (safety + personalization):** All hint/simplify/why-wrong output passes the **Safety Layer (P3-02)** and respects the child's **language/grade** (P3-03). No bypass.
7. **AC-7 (usage recorded):** A delivered hint or why-wrong response is **recorded per answer** (P2-08 seam — `StudentAnswer.HintUsed=true`, `Attempt.HintsUsedCount++`) so it feeds adaptivity (P3-08). Confirm the recording happens (OQ-3). Record even on cache-hit path.
8. **AC-8 (instrumentation):** `HelpRequested { Intent=Hint|WhyWrong }`, `HelpDelivered { Intent, ContextSource }`, or `HelpDeclined` events are emitted for every request (fire-and-forget). These events feed P5-03 and P6-02 — specifically the closed-loop metric: `PostHelpRetry` and `PostHelpSuccess` (emitted by the quiz submit handler when a retry follows a hint).
9. **AC-9 (conventions):** `[Authorize(Roles="Student")]`; grade/age/language from JWT; streaming/error pattern consistent with P3-04; `ILoggerManager`; module isolation; no progression decisions by the AI (FR-AI-6).

## Cost & model routing (cache-primary architecture)

> **See the authoritative strategy:** [docs/briefs/ai-cost-routing.md](ai-cost-routing.md). This section captures P3-05's specific responsibilities. Always measure real prompts with `count_tokens` (model: `claude-haiku-4-5`) before locking pricing estimates.

### `AiResponseCache` (Type=Hint) is the PRIMARY served path for the Hint intent (R2)

The 3 hint levels per question are FINITE and pre-generable offline. Pre-generate them via the Batch API and store in `ai.AiResponseCache` (the single unified cache table — replaces the former `HintCache`) with `Type = Hint`. Serve from cache at runtime. The runtime LLM call is a cache-miss fallback only.

**Primary cost lever:** a Redis read-through layer (keyed by `CacheKey`) in front of `ai.AiResponseCache`. A cache HIT costs $0 AI tokens. Anthropic prompt-caching (`cache_control`) is a secondary lever on the miss path.

**Lookup key for Hint:** `CacheKey = SHA256(QuestionId, HintLevel, Language, PromptVersion, CurriculumVersion)` — fully enumerable over the question bank.

**ReviewStatus gate (R5):** only `ReviewStatus = Approved` entries are served as cache hits. `PendingReview` entries are stored but not amplified to other students until approved (see `ai-cost-routing.md §5`).

**Revised handler orchestration for `GetHintCommandHandler` — cache-first + review gate:**

1. **Cache lookup first:** query `AiResponseCache` by `CacheKey` WHERE `Type = Hint` AND `ReviewStatus = Approved` AND `InvalidatedAt IS NULL`. On **hit** → stream immediately (zero LLM cost). Publish `HintUsedIntegrationEvent` as usual.
2. **On cache miss only:** proceed with the runtime pipeline (resolve escalation level → retrieve chunks → build prompt → call P3-01 Gateway with Sonnet `claude-sonnet-4-6` via `AiModelRouter`). Apply prompt-caching `cache_control` breakpoints on the repeated system-prompt + question-context portions (secondary lever).
3. **Check quota (P3-01 gateway):** if student is out of runtime budget → return the closest `Approved` cached hint for this question (any level), or a generic nudge. Never a hard error.
4. Buffer full response; apply post-generation no-reveal check (OQ-4); apply P3-02 Safety Layer.
5. **Store in `AiResponseCache`** async (fire-and-forget): read `autoApprovalThreshold = IGlobalSettingsProvider.GetDecimal("ai.cache.autoApprovalConfidence", 0.85m)` — if `Confidence ≥ autoApprovalThreshold` AND safety passed → `ReviewStatus = Approved`; else `ReviewStatus = PendingReview`. Bootstrap default = 0.85 (Decision 1/OQ-F resolved); DB-backed / admin-editable via P10-12. The current student receives the response; only `Approved` entries are amplified to subsequent students.
6. Stream pre-checked response.

**Simplify (`SimplifyExplanationCommand`):** reuses the `AiResponseCache` (Type=Explain) lookup from P3-04 with a "lower reading level" directive; the `CacheKey` includes a `simplified=true` flag or a Difficulty step-down in the canonical key tuple.

**Runtime model:** Sonnet (`claude-sonnet-4-6`) for hints — NOT Opus. Haiku is insufficient for Arabic pedagogical hint quality pending P6-02 eval gate. Always verify current Anthropic model IDs before launch.

### WhyWrong intent — cacheable by compound key (R3, NEW)

"Why is my answer wrong" is cacheable — kids repeat the same mistakes on fixed-curriculum questions (80–95% reuse potential). WhyWrong entries use `Type = WhyWrong` in `ai.AiResponseCache`.

**Cache key for WhyWrong:** `CacheKey = SHA256(QuestionId, SHA256(NormalizedWrongAnswer), Language, AgeBand, PromptVersion, CurriculumVersion)`

- **`NormalizedWrongAnswer`** = `WrongAnswerNormalizer.Normalize(answer, subjectType, grade, questionType)` — subject-aware canonicalization (trim/lowercase/unicode-NFC/Arabic numeral conversion; **Decision 5/normalizer flag resolved:** tashkeel stripped for Math/Science but **preserved** for Arabic-language subject — see `WrongAnswerNormalizer` in P3-05-BE-14). The normalization step ensures that "٣" and "3" and " 3 " all map to the same canonical form for Math/Science, while "عَلِمَ" and "عَلَم" remain distinct for Arabic language questions.
- **`AgeBand`** = derived from grade (e.g. bands: 1-4 / 5-8 / 9-12) — enables cross-student reuse within the same age group without losing pedagogical appropriateness.

**WhyWrong flow (cache-first):**
1. Normalize the wrong answer → compute `CacheKey` (using subject-aware `WrongAnswerNormalizer` — Decision 5).
2. Lookup `AiResponseCache WHERE Type = WhyWrong AND CacheKey = ? AND ReviewStatus = Approved AND InvalidatedAt IS NULL`.
3. On hit → stream immediately (zero LLM cost).
4. On miss → generate (Sonnet, runtime) → Safety Layer → compute `Confidence`; read `variantCap = IGlobalSettingsProvider.GetInt("ai.cache.whyWrongVariantCap", 50)` and `autoApprovalThreshold = IGlobalSettingsProvider.GetDecimal("ai.cache.autoApprovalConfidence", 0.85m)` — store with `ReviewStatus = Approved` if `Confidence ≥ autoApprovalThreshold` (bootstrap default 0.85, Decision 1), else `PendingReview` → stream to current student. **Decision 2 (OQ-G resolved):** before inserting, check the count of distinct `InvalidatedAt IS NULL` WhyWrong entries for this `QuestionId`; if count ≥ `variantCap` (bootstrap default 50), evict the LRU entry (oldest `CreatedAt` with no recent lookup) before inserting the new row. Both thresholds are read via `IGlobalSettingsProvider`; bootstrap defaults apply until P10-12 delivers DB-backed values. Cap enforced in P3-05-BE-15.

**Task additions required:** a `WrongAnswerNormalizer` service (normalization task) and the `AgeBand` derivation utility. Add these as new tasks in `P3-05-BE.md` (IDs P3-05-BE-14 and P3-05-BE-15 continuing the numbering).

**Decision 2 (OQ-G resolved) — WhyWrong cache cap:** store a maximum of **`IGlobalSettingsProvider.GetInt("ai.cache.whyWrongVariantCap", 50)` distinct normalized wrong-answer variants per `QuestionId`**; LRU eviction beyond that cap. Bootstrap default = 50. DB-backed / admin-editable via P10-12 — no code change required to adjust the cap post-launch. This prevents unbounded cache growth while preserving the highest-frequency error patterns. The cap is enforced in P3-05-BE-15 (WhyWrong compound-key cache lookup/storage).

**Decision 5 (normalizer flag resolved) — Subject-aware Arabic normalization:** `WrongAnswerNormalizer` is PARTIAL / subject-aware, NOT always-strip-tashkeel:
- **Math / Science:** strip tashkeel ("ثَلاثة" == "ثلاثة").
- **Arabic-language subject:** PRESERVE tashkeel — عَلِمَ vs عَلَم differ in meaning; stripping collapses distinct answers.
- The normalizer takes **`SubjectType` + `Grade` + `QuestionType`** as inputs to decide the normalization level. See P3-05-BE-14.

### Cache invalidation for Hint and WhyWrong (R6)

Set `InvalidatedAt = NOW()` on `AiResponseCache` rows WHERE applicable:

- **`CorrectAnswer` change on a `QuizQuestion`:** **Decision 4 (OQ-F/BE-16 catch resolved):** invalidate by the `QuestionId` column — `UPDATE ai_response_cache SET InvalidatedAt = NOW() WHERE QuestionId = <affected id> AND Type IN (2, 3) AND InvalidatedAt IS NULL`. This is a precise, indexed operation — no scanning of `CacheKey` hashes required. Populated on `Hint` and `WhyWrong` rows; null on `Explain`/`Practice` rows (which are invalidated by other triggers).
- **PromptVersion bump:** invalidate rows with `PromptVersion = old_version`.
- **CurriculumVersion switch:** invalidate rows with `CurriculumVersion = archived_version`.
- **Manual "reported-bad" purge:** admin action sets `ReviewStatus = Rejected` + `InvalidatedAt`.

### Offline batch pre-generation job (P3-05 trigger)

An offline job enumerates all `(QuestionId, HintLevel 1-3, Language ar/en)` combinations not yet in `AiResponseCache` (Type=Hint) (or where `InvalidatedAt IS NOT NULL`):
- Generation model: Sonnet (`claude-sonnet-4-6`).
- QA pass model: Opus (`claude-opus-4-8`); on pass → sets `ReviewStatus = Approved`.
- Entries enter as `PendingReview`; only the Opus QA pass promotes to `Approved`.
- Submitted via Anthropic Batch API.
- Run at content-load time and whenever a question's `CorrectAnswer` changes (triggers invalidation + re-generation).

**WhyWrong is NOT pre-generated offline** — it is student-answer-specific. It is cached on-the-fly from runtime generations (R3). The batch job explicitly excludes `Type = WhyWrong`.
