## Business context & value

- **Who benefits:** the **admin** (curriculum operator) directly; **students** indirectly (correctly ordered, vetted, language-correct trees; inactive items hidden but not lost). No parent/child data is touched.
- **Value:** removes the developer-in-the-loop for top-of-tree curriculum curation. Today subjects/units are seeded by `LearningSeeder` (6 language-tagged roots per grade); this story turns that into an admin self-service screen. The backend already enforces the rules; this is the **operator UI** that makes them usable.
- **Success measure:** an admin can (1) see all **6 roots per grade** distinguishably by `SubjectCode` + `Language`, (2) scope the view/reorder to one language tree, (3) see coverage gaps per grade, (4) create/edit subjects + units, (5) reorder within one tree, (6) deactivate (soft) and soft-delete, and is blocked by clear errors from duplicate/5th-tree creation and from deleting a non-empty unit — all admin-only.

### The bilingual parallel-tree model (load-bearing — the whole screen is shaped by it)

A `Subject` is identified by **`SubjectCode`** (`MATH`/`SCIENCE`/`ARABIC`/`ENGLISH`) **+ `Language`** (`Ar`/`En`), unique per `(GradeId, SubjectCode, Language)`. Each grade has **6 expected roots**: MATH×{Ar,En}, SCIENCE×{Ar,En}, ARABIC-Ar (pinned), ENGLISH-En (pinned). Arabic/English are pinned to one language; Math/Science exist in both. **Children (Units) inherit language from the owning Subject — there is no language column below Subject.** Therefore the UI must:
- Use **`SubjectCode` for identity + icon**, never the free-text display `Name` (two roots can share a name across grades).
- Show **`Language` (ar/en)** as a first-class column/badge.
- Never mix languages in a single reorder or coverage view — reorder is scoped to one `(GradeId, Language)` tree; units reorder is scoped to one `SubjectId` (which is inherently one language).
- Note: `Language` here is the **content/learning** language (`ContentLanguage`), distinct from the admin/student **UI** language. The admin shell currently renders in a single locale (`ADMIN_LOCALE`, EN-first) — do not conflate the two.

## Acceptance criteria (testable — reviewer checks against these)

1. **Subject list (FE-1).** Curriculum → Subjects renders a table of subjects with columns: **SubjectCode** (icon/badge by code, not display name), **Language** (ar/en badge), **Name**, **Grade**, **SequenceOrder**, **Active** state. For a given grade all 6 roots are visible and distinguishable. Server-paginated via `GET /api/learning/Subjects/List`. Four states present: loading-skeleton / empty / error+retry / results (mirror the Wave-1 users page).
2. **Language scope (FE-2).** A language filter/tabs control (ar / en / all) scopes the grid; selecting a language constrains both the visible rows and the reorder operation to that language tree. (Client-side filter on the `language` field is acceptable since `List` has no `Language` param — see contract notes.)
3. **Per-grade coverage (FE-5).** A grade selector drives a coverage panel that calls `GET /api/learning/Subjects/Coverage?gradeId=` and shows, for each of the 6 expected `(SubjectCode, Language)` slots, whether the tree **Exists**, its name + active state if present, and **flags gaps** (Exists=false) distinctly. `GapCount` is shown/derivable.
4. **Subject create/edit (FE-3).** A modal/drawer form creates/edits a subject with `name`, `gradeId`, `subjectCode`, `language`, `sequenceOrder`, `isActive`. For `subjectCode = ARABIC` the language is pinned `Ar`; for `ENGLISH` pinned `En` (control disabled/locked); MATH/SCIENCE allow either. Wired to `POST /Create` (create) / `PUT /Update` (edit). On success the list invalidates and the form closes.
5. **Unit list + create/edit (FE-3/FE-4).** Selecting a subject shows its units (`GET /api/learning/Units/List?SubjectId=`), each with name, sequence order, and active state. A form creates/edits a unit with `name`, `subjectId` (fixed to the selected subject), `sequenceOrder`, `isActive` via `POST`/`PUT`. The unit form never lets the admin pick a language (units inherit it).
6. **Reorder (FE-4).** Drag-to-reorder persists the new order within a single tree: subjects via `PUT /api/learning/Subjects/Reorder` with `{ subjectIds: [...] }` (all in the same `(GradeId, Language)` tree); units via `PUT /api/learning/Units/Reorder` with `{ unitIds: [...] }` (all under one subject). Order survives reload. Reorder UI is disabled in the "all languages" view (cannot reorder across trees).
7. **Activate/deactivate (FE-6).** A toggle calls `PUT /api/learning/Subjects/{id}/Active` `{ subjectId, isActive }` or `PUT /api/learning/Units/{id}/Active` `{ unitId, isActive }`. Inactive items are visibly marked (badge) but remain in the admin list. Cache invalidates so the new state shows. (Optimistic update optional — see open question Q4.)
8. **Soft-delete with guard (FE-7).** Deleting a subject/unit calls `DELETE /api/learning/Subjects?id=` / `DELETE /api/learning/Units?id=` (id as **query param**, not route). A confirm dialog precedes it. A non-empty target (unit with lessons / subject with units) returns `Successed=false` with a clear message — the UI surfaces that "not empty" error and does NOT remove the row.
9. **Admin-only access.** Every curriculum route self-wraps `AdminShell` (runs `useAdminGuard`); non-admin/signed-out → redirect to `/login`. (Backend `AdminOnly` is the real gate; the guard is a UX boundary.)
10. **Nav + i18n + a11y.** The `Curriculum` side-nav item becomes a **real, active-aware** link to `/curriculum/subjects` (replacing the current placeholder). All copy is added to `AdminStrings` (EN + AR). Layout is RTL-safe; tables/dialogs/forms meet the a11y bar set by Wave 1 (labels, focus, `aria-live`, keyboard).

## Contract corrections — task file / prompt drift vs the MERGED backend (read carefully)

The FE task file's "Contract from Backend" section and the prompt's framing predate the merged code in places. **Trust the controllers/DTOs below, not the task file**, on these points:

1. **No `LifecycleState` in P7-01.** The prompt mentions "lifecycle state transitions Draft→Published→Archived" for P7-01. The merged P7-01 controllers/DTOs expose **only `IsActive` (bool)** — `SubjectDto`/`UnitDto` carry no `LifecycleState` field, and there are no publish/archive endpoints here. Draft/Published/Archived is a **separate axis owned by P7-05** (`docs/briefs/P7-01.md`; HANDOFF "Phase 7 — Curriculum wave"; `Domain/Enums/LifecycleState.cs`). **P7-01-FE must NOT build a Draft→Published→Archived control** — that belongs to the P7-05 FE story (open question Q3). The only state transition in scope is active ⇄ inactive.
2. **List is paginated, not a flat list.** `GET /api/learning/Subjects/List` returns `BaseResponse<PaginatedResult<SingleSubjectResponse>>` (envelope flattened: `data: []` + `currentPage`/`totalCount`/`totalPages`/`pageSize`). Same for units. Use `client.getPaginated<T>` (Wave-1 pattern), not `client.get`.
3. **Units are NOT fetched via `Subjects/{id}/Units`.** That route does not exist on the admin side (`SubjectsController` only has student `{id}/Lessons`). List units via **`GET /api/learning/Units/List?SubjectId={id}`** (`UnitsController`, paginated).
4. **IDs are `int`, not `Guid`.** All Subject/Unit ids are `int` (`BaseDto.Id : int`). The task file's `BaseResponse<Guid>` is wrong — creates/updates/deletes/reorders/active return **`BaseResponse<string>`** (a localized success message), like the Wave-1 suspend/delete hooks. Refetch via invalidation; do not read new state from the mutation result.
5. **Reorder body shape.** `{ subjectIds: number[] }` / `{ unitIds: number[] }` — position in the array becomes the new `SequenceOrder` (0-based). Not an array of `{id, order}` objects.
6. **SetActive body shape.** Subject: `{ subjectId, isActive }`; Unit: `{ unitId, isActive }`. The route also carries the id (`/{id}/Active`); the backend overwrites the body id from the route, but send both to match the merged contract.
7. **Delete takes id as a query param.** `DELETE /api/learning/Subjects?id={id}` and `DELETE /api/learning/Units?id={id}` (the `[HttpDelete]` action binds `int id` from query). No request body required (unlike the user-delete flow).

> **DTO shapes (mirror as FE-local interfaces — these admin DTOs are NOT in the NSwag client):**
> - `SubjectDto`/`SingleSubjectResponse`/`AddSubjectDto`/`EditSubjectDto` = `{ id: number; name: string; country?: string|null; gradeId: number; subjectCode: number; language: number; sequenceOrder: number; isActive: boolean }`. (Add/Edit reuse the same shape; create ignores `id`, edit requires it.)
> - `UnitDto`/`SingleUnitResponse`/`AddUnitDto`/`EditUnitDto` = `{ id: number; name: string; sequenceOrder: number; subjectId: number; isActive: boolean }`.
> - `SubjectLanguageCoverageReportDto` = `{ gradeId: number; gradeNumber: number; coverage: SubjectLanguageCoverageDto[]; gapCount: number }` where `SubjectLanguageCoverageDto` = `{ subjectCode: number; language: number; exists: boolean; subjectId: number|null; name: string|null; isActive: boolean|null }`. The 6 slots are returned in fixed order: MATH/Ar, MATH/En, SCIENCE/Ar, SCIENCE/En, ARABIC/Ar, ENGLISH/En.
> - `PaginatedResult<T>` (from `@learnexia/shared`) = `{ data: T[]; currentPage; totalCount; totalPages; pageSize; successed; message?; ... }`.

### Backend validation rules to mirror in form UX (parity, fail fast before the round-trip)
- Subject: `name` required (non-empty); `gradeId > 0`; `subjectCode` ∈ {MATH,SCIENCE,ARABIC,ENGLISH}. (No min/max length on name in the validator — `AddSubjectValidation`/`SubjectBaseValidation`.)
- Unit: `name` required; `subjectId > 0` (`UnitBaseValidation`).
- Reorder: list non-empty; **subjects ≤ 12**, **units ≤ 200** per request (`ReorderSubjectsCommandValidator`/`ReorderUnitsCommandValidator`); every id `> 0`.
- Server-side rejections to surface as inline/banner errors (HTTP 400, `Successed=false`): **duplicate `(GradeId, SubjectCode, Language)` tree** (live or soft-deleted), **invalid SubjectCode**, **grade not found**, **"unit not empty"**, **"subject not empty"**. Map by reading `error.message` from the envelope (see `mapDeleteError` in `DeleteUserDialog.tsx` for the pattern) — there are no stable error codes, so match on the localized message or just show the server message.

## Security & audit (admin curriculum writes)

- **AdminOnly is enforced server-side** on every Subject/Unit write + read used here (verified in both controllers). The FE `useAdminGuard` is a UX boundary only — the access-token role claim gate. **No new authz logic on the FE.**
- **P7-12 audit is already emitted by the backend** for all P7-01 writes via `AdminActionPerformedDomainEvent` (Subject/Unit Created/Updated/Deleted/Reordered/Activated/Deactivated — `AdminActions.cs`), dispatched **post-commit** by `UnitOfWorkBehavior` (the Bucket-C fix in HANDOFF is applied). **The FE does nothing extra to emit audit** — simply calling the endpoints produces audit rows. Audit detail strings are PII-light (action + entity id + admin id; no curriculum names/content).
- **Soft-delete, not hard-delete** is the backend behavior (`IsDeleted = true` + non-empty guard). The FE delete is therefore reversible-in-data; copy should say "remove from curriculum" / "hidden", **not** "permanently deleted". Do not imply irreversibility.
- **`security-auditor` is NOT required for this story.** Rationale: the surface touches **curriculum content only — no user/child PII, no auth/authz changes, no file upload, no AI prompts, no secrets, no payments**. This is the documented trigger set; curriculum admin writes fall outside it. (Contrast Wave-1 P7-07/08, which DID require it because they touched user + child data.) If the planner disagrees, flag it — but the default here is **skip**.
- **a11y/RTL is a quality gate, not a security one**, but call it out: drag-reorder must have a keyboard path; dialogs trap focus + ESC-cancels (reuse `AdminConfirmDialog`); forms have labelled fields + inline errors; `dir`-aware layout; technical strings stay `ltr`.

## Open questions / assumptions / risks (flag — do not guess)

- **Q1 — Lifecycle scope (HIGH, resolve before designer).** Confirm P7-01-FE ships **only the `IsActive` (active/inactive) toggle** and does **NOT** build a Draft→Published→Archived control. The merged P7-01 backend exposes no `LifecycleState` on its DTOs/endpoints; that axis is P7-05. **Assumption:** active/inactive only; Draft/Published/Archived is deferred to the P7-05 FE story (which the planner may sequence to own a shared lifecycle control). The prompt's mention of lifecycle transitions appears to be cross-wiring P7-05 into P7-01.
- **Q2 — List page size / "show all".** `Subjects/List` is paginated and the list is small (≤ 6 roots per grade × N grades). Confirm whether the subjects screen should page or just request a large `PageSize` per grade (e.g. filter by grade and request `PageSize=12`). **Assumption:** scope by grade (grade selector) and request a generous page size so all 6 roots show without paging; keep pagination wiring as a fallback. Coverage panel uses the dedicated `Coverage` endpoint regardless.
- **Q3 — Language filter is client-side.** `Subjects/List` has **no `Language` query param** (only `GradeId`/paging/search). **Assumption:** fetch per grade and filter ar/en/all on the client. If the lead wants a server param, that's a backend change (out of scope) — flag rather than add.
- **Q4 — Delete/deactivate confirm depth.** **Assumption:** a plain confirm dialog (no reason field, no typed-confirm) is sufficient for curriculum (non-PII, soft + reversible). Confirm we do NOT want the Wave-1 two-gate (reason + typed-confirm) treatment here. Also confirm whether deactivate needs a confirm at all (it's reversible) — **assumption:** no confirm for toggle, confirm only for delete.
- **Q5 — Optimistic updates.** Wave-1 mutations used **invalidate-and-refetch, no optimism**. **Assumption:** follow that for create/edit/delete; for the active toggle and reorder, optimistic UX is nicer but adds rollback complexity. Recommend invalidate-only for v1 (FE-6 task says "optimistic" — but Wave-1 precedent + the `string`-message return argue for invalidate-only; flag the deviation).
- **Q6 — `[id]` route vs inline units.** **Assumption:** a dedicated `curriculum/subjects/[id]` route for the units view (mirrors `users/[id]`, keeps reorder scope unambiguous). Designer may instead choose inline expand — needs a decision before the FE batch.
- **Risk — reorder scoping.** Mixing languages or subjects in a reorder request is a real footgun: the backend assigns order by array position and assumes a single tree. The UI must hard-prevent assembling a cross-tree reorder list (disable reorder in "all languages" view; units reorder always scoped to one subject). Cover in e2e: reordering the ar tree must not perturb the en tree.
- **Risk — display name vs code identity.** Two roots can share a `Name` (e.g. "Mathematics" Ar and En, or the same code across grades). The UI must key rows/icons off `(subjectCode, language, gradeId)` + `id`, never the name. React keys = `id`.
- **Dependency — sibling curriculum stories.** **P7-02** (lessons) lives under units — the subject/unit detail route should leave a seam to drill into a unit's lessons later, but P7-01-FE must not build lesson UI. **P7-05** (publish/lifecycle) likely owns the shared Draft/Published/Archived control and may refactor the active/inactive UI into a broader state control — keep the `IsActive` toggle isolated so P7-05 can extend it. **P7-12** (audit log FE) will read the audit rows these writes produce — no coupling needed now.
- **Note — backend follow-ups (not blocking, do NOT fix here):** HANDOFF lists minor wave-wide backend follow-ups (P7-05 preview serialization). None affect P7-01-FE.
