## Summary & traceability

- **Task (1 line):** Add a Redis read-model layer for the six existing Gamification query seams (`IStudentXpQuery`, `IStudentStreakQuery`, `IStudentHeartsQuery`, `IStudentBadgesQuery`, `IStudentMissionsQuery`, `IStudentLeagueQuery`) — using **decorators** registered as the resolved seam in DI so the dashboard handler does not change — with **read-through caching + invalidation on the existing domain/integration events** (XP / streak / hearts / badge / mission / league events); add a **Redis sorted-set leaderboard** (`ZADD` on every league XP increment, `ZREVRANGEBYSCORE` for standings) backing P4-07's `GetMyLeagueQueryHandler` so per-cohort ranking is O(log n) instead of two Postgres scans; add a **reconciliation/rebuild service** that reconstructs the Redis state for a student (and for a cohort sorted-set) from the Postgres ledger after cache loss, exposed as a manual on-demand operation **and** an idempotent Hangfire job; ensure **per-student / per-membership concurrency** is correct under contention via `INCRBY` on the sorted-set + Lua scripts (or Redis transactions) where compound updates are needed. **Postgres remains the durable ledger — Redis is never the source of truth**, every mutation writes Postgres first (existing path is untouched), Redis is updated/invalidated in the same flow via the post-commit domain-event dispatch (ADR 0002 §2). **No contract change for FE** — dashboard DTOs are byte-identical, the only observable change is lower p95 latency (the BE task file's `Contract for Frontend` line confirms this).

## Business context & value

- **Who benefits:** the **student** directly — every tap on the dashboard, the league screen, the profile screen, every badge popup, every streak-advance animation needs the read to return inside the next frame budget (~16ms for jank-free 60fps motion; 100-200ms feels instant; >500ms feels broken). Postgres reads with cold cache + 6 cross-module fan-out + lazy-write side-effects today are at the threshold under no load and **will exceed it under realistic concurrent load** (P6-01 will prove this — that's the trigger for this story landing now). **Secondary — the BE service-level**: under load, the Postgres connection pool is the bottleneck; offloading the hot read to Redis preserves DB headroom for writes (every XP / streak / hearts / badge / mission / league mutation still hits Postgres). **Tertiary — the operations story**: a cache layer with TTL is a much cheaper scaling lever than read-replica Postgres.
- **Why it matters now:** Phase-3 has built six engagement engines (XP / streak / hearts / badges / missions / leagues). Every one of them is read by the dashboard on **every** screen-mount. The story description quotes the strategy bluntly: *"the dopamine loop the strategy depends on"* needs the feedback to be **instant**. Without P4-10, P6-01 (the perf-test story in Phase 6) **fails NFR-1** on the dashboard endpoint under realistic load (the SRS rider explicitly anticipates this — that's why it names P4-10 in the FR text). P4-08 (the gamification motion + animations) and P4-09 (the in-app inbox feed) both expect a tightening of the read budget; the architecture also says (`docs/architecture.md` §16 row 360) that the leaderboard read becomes O(scan-of-cohort) without sorted sets — for 30-row cohorts today that's negligible, **but** the architecture is forward-leaning to 100+ row cohorts (and per-grade leagues if Q-grade-segregation ever resurfaces).
- **Success measurement:**
  - `GET /api/Learning/Dashboard` p95 < 500ms under N=100 concurrent students (P6-01 to validate; P4-10 only has to enable the number).
  - `GET /api/Gamification/Leagues/Me` standings read returns in O(log n) on cohort size — measured at the Redis call boundary; Postgres cohort scan becomes a fallthrough, not a hot path.
  - Cache hit ratio (per seam, exposed via structured log marker `cache.gamification.{seam}.hit/miss`) — target > 80% after warm-up window under steady load; brand-new students always cause a miss (acceptable).
  - **Every Postgres mutation is unaffected** — the ledger is byte-identical with and without P4-10. The reconciliation/rebuild job is the proof: re-running it from a wiped Redis must reproduce the exact snapshot the previous cached state held.
  - **Cache loss never causes user-visible data loss** — a `FLUSHALL` on Redis followed by a dashboard fetch returns a correct (cold) snapshot from Postgres; the next fetch returns the same snapshot from Redis (rebuild on read).
  - **Concurrency-correct under contention** — N concurrent `XpAwardedDomainEvent` for the same student must invalidate / write the cache deterministically. The sorted-set leaderboard write is atomic (`ZINCRBY league:{leagueId}:standings amount member`) — no lost XP per AC5.
- **Deterministic principle (BRD §8 / FR-AI-6):** caching policy is **deterministic** — TTL is a constant per seam; invalidation is event-driven; rebuild is a pure projection of the Postgres ledger. No AI, no heuristics, no randomness.

## Acceptance criteria (verbatim from story + testable backend gates)

From `P4-10-redis-realtime-gamification.md`:

1. **AC1 — XP totals, current streak counters, and league leaderboards are read from Redis in the hot path; reads meet NFR-1 (<500ms) under the target concurrent load.**
   - Backend gate:
     - The DI-resolved `IStudentXpQuery` / `IStudentStreakQuery` / `IStudentLeagueQuery` are the **decorator** classes; the Postgres impl is resolved indirectly via the decorator's inner-seam dependency.
     - Decorator order: **(1)** check Redis; on hit, return; **(2)** on miss / Redis error, delegate to the inner Postgres impl; **(3)** populate Redis with the resolved snapshot under the configured TTL; **(4)** return.
     - The league sorted-set is the leaderboard backing: `ZADD league:{leagueId}:standings score member` on every membership join + `ZINCRBY league:{leagueId}:standings amount member` on every XP increment.
     - p95 < 500ms under load is a P6-01 obligation — this story only has to make it possible.
   - **api-tester gate** (Q7): mock Redis hit / miss + assert one Postgres call on miss, zero on hit (verifies the decorator path); standalone hit-ratio test with N requests.

2. **AC2 — Postgres remains the durable ledger — every XP/streak mutation is written through to Postgres; Redis is a derived cache, never the source of truth.**
   - Backend gate:
     - **No new write path in this story** — all mutation goes through the existing Postgres command handlers untouched.
     - Invalidation handlers (`INotificationHandler<XpAwardedDomainEvent>` etc.) run **after** the Postgres UoW commits per ADR 0002 §2.
     - The invalidation handler updates Redis (either `KeyDelete`-then-let-next-read-repopulate, OR `KeySet`-with-new-snapshot — see Q4). On Redis error, the handler logs WARN and returns without throwing (fail-soft — Postgres is the source of truth, the next read will re-cache, and the nightly rebuild job is the safety net).
     - The reconciliation/rebuild service is a **read-only projection** of Postgres into Redis — it never mutates Postgres.

3. **AC3 — Leaderboards use a Redis sorted-set (or equivalent) so ranking is O(log n), not a Postgres scan, for P4-07 leagues.**
   - Backend gate:
     - **Key:** `league:{leagueId}:standings`. Type: `ZSET`.
     - **Member:** `LeagueMembership.Id.ToString()` (Q8 — alternative: `StudentXpProfileId`; recommend MembershipId because it is unique-per-week and avoids cross-week collision when a membership is preserved post-rollover).
     - **Score:** primary `WeeklyXp` DESC + tiebreak `JoinedAtUtc` ASC encoded as a composite double (see Q5 for the encoding scheme — recommend `WeeklyXp * 1e10 - epochSecondsSinceJoin` so earlier joiners win ties; epochSeconds is small enough to fit without precision loss within `int * 1e10`).
     - **Operations:**
       - On membership creation (lazy placement in `LeaguePlacementService.PlaceStudentAsync`): `ZADD league:{leagueId}:standings encoded(0, joinedAtUtc) membershipId`.
       - On `XpAwardedDomainEvent` AFTER the originating UoW commits: invalidation handler computes the new encoded score (read `WeeklyXp` from Postgres OR `ZSCORE` then add amount — both safe under atomic `ZINCRBY`; recommend `ZADD CH` with the freshly-computed score from Postgres to keep the cache aligned with the ledger, Q9).
       - On standings read in `StudentLeagueQuery` / `GetMyLeagueQueryHandler`: `ZRANGE league:{leagueId}:standings 0 29 REV WITHSCORES` for the top-30, `ZREVRANK key member` for the caller's rank, `ZCARD key` for the cohort size.
       - On `LeagueRolloverJob` (Monday 00:15 UTC): the job already mutates Postgres correctly — P4-10 simply lets the previous-week sorted-set expire via TTL (Q11) or explicitly `KeyDelete` it after the rollover commits (cleaner — recommend KeyDelete in the rollover post-commit hook).
     - **Rank is O(log n)** — `ZREVRANK` is O(log n). The two Postgres scans in `GetMyLeagueQueryHandler` (cohort-members ORDER BY + count) become a single sorted-set range op + a `ZCARD`.

4. **AC4 — A reconciliation/rebuild path can reconstruct Redis state from the Postgres ledger after cache loss, with no permanent data loss.**
   - Backend gate:
     - **`GamificationCacheRebuilder` service** (new, in `Gamification.Infrastructure/Services/`): three methods —
       - `RebuildStudentAsync(int studentId, CT)` — re-reads all 6 per-student snapshots from Postgres and `SET`s them in Redis under the configured TTL. Used by ops and tests.
       - `RebuildLeagueAsync(int leagueId, CT)` — re-reads all `LeagueMembership` rows for the cohort, `DEL`s the sorted-set, then `ZADD`s every member with the encoded score. Idempotent (DEL+ADD is naturally idempotent).
       - `RebuildAllAsync(CT)` — pages through profiles (Take 500) + cohorts (current and previous period) and rebuilds each. Called by the nightly Hangfire job.
     - **`GamificationCacheRebuildJob`** (Hangfire recurring) — cron `"0 3 * * *"` (03:00 UTC daily) — runs `RebuildAllAsync` so any cache drift accumulated during the day is corrected nightly. Idempotent. Documents the "Redis as derived" promise operationally.
     - **No permanent data loss** is enforced by AC2 — Postgres is the source. Cache loss is an availability event, not a data event.

5. **AC5 (story para 4) — Updates are driven by P4-01 domain events; concurrent updates to the same student are correct (no lost XP) under contention.**
   - Backend gate:
     - Every XP-affecting mutation already raises `XpAwardedDomainEvent` (P4-07 Batch 0 chokepoint refactor — HANDOFF top). Cache invalidation handlers subscribe to that event.
     - **Per-student key cache:** invalidation handler does `KeyDelete student:{id}:xp` AFTER the originating commit. **Two concurrent commits race the DELETE** — the worst case is the second DELETE is a no-op (key already gone) and the next read repopulates from Postgres. No data loss.
     - **Per-cohort sorted-set:** **atomicity matters** — two concurrent XP awards for the same membership must both be reflected. Either (a) use `ZINCRBY` (atomic by-amount) — but this drifts if Postgres + Redis ever disagree (the rebuild job corrects); or (b) use `ZADD CH` with the **freshly-read-from-Postgres** `WeeklyXp` (cache mirrors ledger exactly) — last-writer-wins under concurrent invalidation, but each handler reads the *committed* post-write value, so last-writer-wins == correct-final-value. **Recommend (b)** for the strongest "Redis mirrors Postgres" guarantee (Q9).
     - **Cache stampede / thundering herd** — on cache miss, multiple concurrent readers all hit Postgres + write Redis. For dashboard reads this is fine (the queries are cheap). For an actively-empty cohort sorted-set, recommend lazy rebuild on first read (the existing `LeaguePlacementService` already serializes via the unique constraint; the sorted-set rebuild on first read can read all cohort members in one go and ZADD them — single Postgres query, single Redis pipeline).

### B. Sorted-set leaderboard (P4-10-BE-3)

1. **`RedisLeagueLeaderboard`** in `Gamification.Infrastructure/Services/`. Composes `IGamificationCache` (sorted-set methods).
2. **Score encoding** (Q5 — pin):
   ```csharp
   // WeeklyXp in [0, ~10^7) and JoinedAtUtc as seconds-since-epoch in [10^9, ~10^10).
   // Encoded score = WeeklyXp * 1e10 - secondsSinceEpoch
   //   → higher WeeklyXp wins outright; earlier joiners win ties (smaller seconds → larger encoded).
   // Double has ~15-16 significant digits; WeeklyXp * 1e10 ≤ 10^17 → exceeds double precision.
   // Safer: encoded = WeeklyXp * 1e6 + (1e6 - (secondsSinceEpoch - 10^9) % 1e6)
   //   → keeps within double precision; tiebreak ambiguity only on >10^6 seconds gap (~11 days).
   ```
   **Recommend a 24-bit packed encoding** that fits double precision safely:
   `score = WeeklyXp * 16777216 + (16777215 - joinOrder)` where `joinOrder` is the per-cohort `JoinOrder` already on `LeagueMembership` (HANDOFF top). Higher `WeeklyXp` ranks higher; smaller `joinOrder` (= earlier joiner) wins ties. `WeeklyXp` up to `2^31 / 2^24 ≈ 127` per cohort is the only theoretical ceiling — well above realistic weekly XP. **Final decision must be locked in Q5.**
3. **`JoinAsync(leagueId, membershipId, joinOrder, ct)`** — `ZADD gamification:league:{leagueId}:standings encoded(0, joinOrder) membershipId`.
4. **`UpdateScoreAsync(leagueId, membershipId, weeklyXpAfter, joinOrder, ct)`** — `ZADD CH gamification:league:{leagueId}:standings encoded(weeklyXp, joinOrder) membershipId` (the `CH` flag returns 1 if changed, useful for log). Recommend this over `ZINCRBY` (Q9).
5. **`GetRankAsync(...)`** — `ZREVRANK key member`, returns 0-based; add 1 for 1-based display.
6. **`GetTopAsync(leagueId, count, ct)`** — `ZRANGE key 0 (count-1) REV WITHSCORES`.
7. **`ResetAsync(leagueId, ct)`** — `KeyDelete key`. Called by `LeagueRolloverJob` post-commit.

### C. Decorator wiring (P4-10-BE-6)

For each of the 6 seams, ship a `Cached*Query` class + inner Postgres rename:

```csharp
public sealed class CachedStudentXpQuery : IStudentXpQuery
{
    private readonly IStudentXpQuery _inner;
    private readonly IGamificationCache _cache;
    private readonly GamificationCacheOptions _opts;
    private readonly ILoggerManager _logger;

    public CachedStudentXpQuery(
        IStudentXpQuery inner,
        IGamificationCache cache,
        IOptions<GamificationCacheOptions> opts,
        ILoggerManager logger) { _inner = inner; _cache = cache; _opts = opts.Value; _logger = logger; }

    public async Task<StudentXpSnapshot?> GetByStudentIdAsync(int studentId, CancellationToken ct = default)
    {
        if (!_opts.Enabled) return await _inner.GetByStudentIdAsync(studentId, ct);

        var key = $"{_opts.KeyPrefix}student:{studentId}:xp";
        var cached = await _cache.TryGetAsync<StudentXpSnapshot?>(key, ct);
        if (cached.HasValue) { _logger.LogInfo($"cache.gamification.xp.hit student={studentId}"); return cached.Value; }

        _logger.LogInfo($"cache.gamification.xp.miss student={studentId}");
        var fresh = await _inner.GetByStudentIdAsync(studentId, ct);
        await _cache.SetAsync(key, fresh, TimeSpan.FromSeconds(_opts.XpTtlSeconds), ct);
        return fresh;
    }
}
```

DI registration is the load-bearing detail — **the inner Postgres impl must NOT be registered as `IStudentXpQuery`** (otherwise the consumer resolves the inner directly and bypasses the cache). Two clean approaches (Q12):

- **(Recommended)** Rename `StudentXpQuery -> PostgresStudentXpQuery`; register `PostgresStudentXpQuery` as itself (concrete); register `IStudentXpQuery` as a factory `sp => new CachedStudentXpQuery(sp.GetRequiredService<PostgresStudentXpQuery>(), ...)`.
- **Alternative** Add `Scrutor` package + `services.Decorate<IStudentXpQuery, CachedStudentXpQuery>()`. Cleaner DSL but new dependency.

Repeat for the other 5 seams. The two lazy-write seams (`StudentHeartsQuery`, `StudentMissionsQuery`, `StudentLeagueQuery`) need extra care — **the lazy-write side-effect must run on cache miss (before SetAsync), and must NOT run on cache hit** (the cached snapshot is the post-side-effect state). Concretely, the inner `PostgresStudentMissionsQuery` already runs the lazy-instantiation inside `GetByStudentIdAsync`, so calling it on miss is correct; the decorator just needs to be sure to call inner *exactly once* and then cache the result.

### D. Cache invalidation handlers (P4-10-BE-2)

Each invalidator class in `Gamification.Application/Features/Cache/Invalidators/`:

```csharp
public sealed class XpAwardedCacheInvalidator : INotificationHandler<XpAwardedDomainEvent>
{
    private readonly IGamificationCache _cache;
    private readonly RedisLeagueLeaderboard _leaderboard;
    private readonly IGamificationRepository _repo;
    private readonly GamificationCacheOptions _opts;
    private readonly ILoggerManager _logger;
    // ... constructor

    public async Task Handle(XpAwardedDomainEvent ev, CancellationToken ct)
    {
        try
        {
            await _cache.RemoveAsync($"{_opts.KeyPrefix}student:{ev.StudentId}:xp", ct);
            // Sorted-set update: read fresh membership from Postgres + ZADD CH.
            var profile = await _repo.GetProfileByStudentIdAsync(ev.StudentId, ct);
            if (profile is null) return;
            var (periodKey, _, _) = MissionPeriodCalculator.GetCurrentPeriod(MissionType.Weekly, ev.OccurredAtUtc);
            var membership = await _repo.GetMembershipForStudentAsync(profile.Id, periodKey, ct);
            if (membership is null) return;  // lazy placement hasn't happened yet — sorted-set is empty, no-op
            await _leaderboard.UpdateScoreAsync(membership.LeagueId, membership.Id, membership.WeeklyXp, membership.JoinOrder, ct);
        }
        catch (Exception ex)
        {
            _logger.LogWarn($"P4-10: cache invalidation failed for XpAwarded studentId={ev.StudentId} — Postgres remains authoritative, nightly rebuild will reconcile.");
            _ = ex;  // do NOT echo
        }
    }
}
```

### F. Concurrency-correct sorted-set updates (P4-10-BE-5)

Recommended approach (Q9 — pin): `ZADD CH` with the freshly-read-from-Postgres `WeeklyXp`. This is **last-writer-wins under concurrent invalidation**, but because each invalidator reads the *committed post-write* value, the last writer's value IS the correct latest value. No Lua required. The `LeagueXpDeltaLog` table (P4-07) is the idempotency layer on the Postgres side; Redis just mirrors the result.

**If the lead prefers `ZINCRBY` for write-during-event semantics** (cheaper, but drifts from Postgres on any sync edge case), document the rebuild job as the corrector. Recommend ZADD-with-readback for the strongest guarantee.

### G. Hardening (do NOT skip)

- **Fail-open / fail-soft on Redis errors** — Postgres is the source of truth; every Redis op is wrapped, logs WARN with a static message, never throws to the caller.
- **`Enabled = false` kill-switch** — flipping the config sets every decorator to pass-through; production-safe ops switch.
- **No PII in keys or values** — keys hold `studentId` (int, already an internal id, not the JWT subject directly), values hold gamification snapshots (no name, no email, no answer text). Sorted-set members are `membershipId` strings; no display name.
- **No PII in WARN logs** — log marker only (`cache.gamification.xp.hit student={id}` is acceptable, `studentId` is internal); never log Redis endpoint, socket, exception message (F-09).
- **Module isolation (rule 1)** — all P4-10 code lives in Gamification (Domain/Application/Infrastructure/Api). No cross-module project reference. Learning consumes the decorated seam through `Shared.Contracts` unchanged.
- **No design pattern beyond decorator** (rule 8) — decorator is approved by the story shape (BE-6); no Strategy / Factory / etc.

**Must-pass cases (>= 16):**

6. **Sorted-set tiebreak.** Two students with equal `WeeklyXp` -> earlier joiner has higher rank (lower `ZREVRANK`).
7. **Sorted-set leaderboard endpoint integration.** `GET /api/Gamification/Leagues/Me` returns the standings ordered by sorted-set rank (not by Postgres scan).
8. **Streak invalidation.** `StreakAdvancedDomainEvent` -> `student:{id}:streak` key removed.
9. **Hearts invalidation + lazy refill.** Lazy refill on read populates cache with the post-refill snapshot; subsequent reads serve the cached value without re-running the side-effect (Postgres write count assertion).
10. **Missions invalidation.** `MissionCompletedDomainEvent` -> daily missions cache key removed; next read returns updated `Completed` status.
11. **Badge invalidation.** `BadgeEarnedDomainEvent` -> `student:{id}:badges:3` key removed; next dashboard fetch shows the new badge.
12. **Concurrent XP awards no-lost-data.** Two concurrent XP awards for the same student (different `OriginEventId`) -> Postgres + sorted-set both reflect the sum.
13. **Redis unavailable -> Postgres fallthrough.** Disconnect / nullify `IConnectionMultiplexer` mid-test -> dashboard reads continue to succeed (degraded latency, no error to the client).
14. **Rebuild after `FLUSHALL`.** Flush Redis, call `RebuildAllAsync` -> all known snapshots re-cached; spot-check XP / streak / sorted-set rank match Postgres.
15. **Nightly rebuild job is idempotent.** Run the job twice in succession -> second run produces no observable change (counts / logs).
16. **`Enabled = false` bypasses cache.** Set the config flag -> every read hits Postgres; no Redis traffic.
17. **Cache kept stale within TTL.** Manually mutate Postgres without raising the event (test seam) -> dashboard returns the cached (stale) value until TTL expiry; rebuild corrects it. *(This proves the cache mirrors writes through the event path, not direct DB inspection — important for understanding the consistency model.)*
18. **Envelope sanity.** `"successed":` lowercase-d camelCase preserved.
19. **No PII in keys.** Inspect actual Redis keys after a full dashboard load -> no email, no display name, only int IDs.
20. **Decorator preserves null-for-new-student semantics.** `IStudentXpQuery.GetByStudentIdAsync(newStudentId)` returns `null` both on cache miss and cache hit.

## Open questions / assumptions / risks

### Open questions (priority order — pin BEFORE backend-feature batch)

**Q1 — Cache scope: all 6 seams, or only the 3 SRS-named ones?**
The SRS rider names XP totals, streak counters, and league leaderboards by-name. Hearts / badges / missions are inferred scope (story description "XP, streak, and league standing" + 4 ACs). Decision:
- **Recommended:** cache **all 6 seams**. Marginal Redis cost is trivial (small JSON snapshots, short TTL); the dashboard fans out to all 6 on every read, so leaving 3 of them on Postgres only saves 3 Redis ops while still hitting Postgres twice; clearer mental model ("all gamification reads cached") wins.
- Alternative: cache only XP / streak / leaderboard (literal SRS rider); leave hearts / badges / missions on Postgres. **Smaller blast radius**, but partial.

**Q2 — Badges decorator: cache only `recentTake=3`?**
The interface takes `recentTake` as a parameter. Dashboard always calls with 3; no other caller exists today. **Recommend** cache only when `recentTake==3` (key `:badges:3`); other values pass through. If a future caller wants a different N, add it then.

**Q3 — Lazy-write seams (hearts / missions / league): where does the side-effect run?**
The hearts / missions / league queries write to Postgres on first read of a period. The decorator must NOT skip the side-effect when the cache hits. Two options:
- **(Recommended)** Side-effect runs **only on cache miss** (inner is called, the write happens, the snapshot is cached). Cache hits skip the side-effect (it already ran the first time). Correctness: as long as the period boundary is part of the cache key (`{dailyKey}`, `{weeklyKey}`), the cache naturally rotates at the boundary and the new-period side-effect runs on the first miss after rotation.
- Alternative: refactor the lazy write into a separate `EnsureXxxCommand` called by the decorator on every read, independent of cache hit/miss. **More invasive** — recommend skip.

**Q4 — Invalidation strategy: write-around (DEL on event) vs write-through-on-event (SET fresh snapshot on event)?**
- **(Recommended) Write-around with TTL for all per-student keys** — handler does `KeyDelete`; next read repopulates from Postgres. Simplest, no consistency surprises.
- Write-through-on-event — handler re-reads Postgres and SETs the new snapshot. Eliminates the next-read latency penalty, but doubles the per-event work. Hybrid (use write-through only for the sorted-set, where the value is small and the read is hot) is the recommended sweet spot.
- For the **sorted-set**, write-through is mandatory (otherwise the leaderboard rank drifts until rebuild). Recommend `ZADD CH` with the freshly-read `WeeklyXp` from Postgres (Q9).

**Q5 — Sorted-set score encoding.**
Two viable schemes:
- **(Recommended) Packed integer**: `score = WeeklyXp * 16777216 + (16777215 - JoinOrder)` — fits double precision, supports up to ~2^7 `WeeklyXp` per cohort with all 30 distinct `JoinOrder`s. Suitable for current scale.
- Time-based tiebreak: `score = WeeklyXp * 1e10 - secondsSinceEpoch` — risks double-precision drift for large `WeeklyXp`. Document the precision boundary.
- Two separate sorted-sets (one scored by `WeeklyXp`, tiebreak resolved at read time by another `ZSCORE` on a secondary set) — over-engineered.

**Q6 — Per-event invalidation: which keys does each event clear?**
Suggested map:
- `XpAwardedDomainEvent` -> `student:{id}:xp`, sorted-set `ZADD CH`.
- `StudentLeveledUpDomainEvent` -> `student:{id}:xp` (idempotent overlap with XpAwarded).
- `StreakAdvancedDomainEvent` / `StreakBrokenDomainEvent` -> `student:{id}:streak`.
- `HeartsDepletedDomainEvent` / `HeartsRefilledDomainEvent` -> `student:{id}:hearts`.
- `BadgeEarnedDomainEvent` -> `student:{id}:badges:3`.
- `MissionCompletedDomainEvent` -> `student:{id}:missions:{dailyKey}` + `:missions:{weeklyKey}`.
Confirm completeness; question whether `LeagueRolloverJob` should DEL the per-student league cache key (recommend yes, otherwise stale rank lingers until TTL).

**Q7 — Test infra: real Redis via Testcontainers, or mock `IGamificationCache`?**
Recommend a mix: unit-test the decorators with a mock `IGamificationCache` (cheap, fast, deterministic); add ~5 integration tests with a real Testcontainers Redis instance to validate the sorted-set ops (`ZADD`, `ZREVRANK`, `ZRANGE`) end-to-end. Testcontainers.Redis package addition needed.

**Q8 — Sorted-set member: `MembershipId` or `StudentXpProfileId`?**
- **(Recommended) MembershipId.ToString()** — unique per week, naturally separated across rollovers. Cleaner.
- StudentXpProfileId — survives across weeks (one member per student per cohort), but we'd need to ensure the sorted-set is per-week-key (it already is via the `leagueId` segment which is per-week).
Either works; recommend MembershipId for unambiguous one-to-one mapping.

**Q9 — Sorted-set update op: `ZINCRBY` vs `ZADD CH` (read-from-Postgres).**
- **(Recommended) ZADD CH** with `WeeklyXp` freshly read from Postgres after each `IncrementLeagueXpCommand` commit. Sorted-set mirrors Postgres exactly. Last-writer-wins under concurrency = correct-final-value (each writer reads the post-commit value).
- ZINCRBY — atomic by-amount, doesn't require a Postgres re-read in the handler. Drifts if any sync edge case lets the two diverge (e.g., handler dies after Postgres commit but before Redis op). The nightly rebuild corrects, but the window is wider.

**Q10 — Default TTLs.**
Suggested: XP 60s, streak 60s, hearts 30s (refill timing makes a short TTL safer), badges 300s, missions 60s, league snapshot 30s, league sorted-set 8 days (survives the week + Monday rollover + buffer). All overridable per env via config. Confirm.

**Q11 — Per-week sorted-set lifecycle.**
- **(Recommended) Explicit DEL on `LeagueRolloverJob` post-commit** + a long TTL (8 days) as a safety net.
- TTL-only — relies on every previous-week cohort actually being read at least once per 8 days; otherwise the key lingers (small leak).

**Q12 — Decorator DI: factory delegate vs `Scrutor.Decorate`.**
- **(Recommended) Factory delegate** — one `sp => new Cached*(new Postgres*(...), ...)` per seam in `AddGamificationCache`. No new package. Explicit. Verbose (6 registrations).
- `Scrutor` — `services.Decorate<IStudentXpQuery, CachedStudentXpQuery>()`. Two lines, but adds a NuGet package. Per CONVENTIONS we mirror existing shapes — no decorator package is in use today.

**Q13 — League rank source: cached snapshot vs always re-derive from sorted-set?**
- **(Recommended) Always derive rank via `ZREVRANK` on every read.** The sorted-set is hot, the op is O(log n), and the rank is always correct (no drift). The cached snapshot only stores (Tier, WeeklyXp, GroupSize); rank is re-computed.
- Cache rank in the snapshot — stale within TTL window; faster on hit but wrong-by-design under load.

**Q14 — `GetMyLeagueQueryHandler`: Postgres bulk-read on rank list, or pack everything into sorted-set member?**
- **(Recommended) Trust the sorted-set for rank, single Postgres bulk-read for `JoinOrder` and `IsMe`** — cleanest separation. Cache surface stays small.
- Pack `{membershipId}:{joinOrder}` into the sorted-set member string — zero Postgres read on standings build, but couples the data layout to the leaderboard.

**Q15 — Test config: `Enabled = false` vs Testcontainers Redis.**
- `Enabled = false` in `appsettings.Test.json` lets every test path exercise the Postgres-only behavior unchanged (regression-safe for the 100+ existing P4-* integration tests).
- A dedicated P4-10 test fixture flips `Enabled = true` + spins up Testcontainers.Redis for the 20 new cases.
- Recommend BOTH.

**Q16 — Missions invalidation: clear daily key only, or daily + weekly?**
The `StudentMissionsSnapshot` carries both daily and weekly missions. `MissionCompletedDomainEvent` could affect either. **Recommend invalidate both `:missions:{dailyKey}` and `:missions:{weeklyKey}`** — cheap and correct.

### Risks (top 3)

- **R1 — Lazy-write seam consistency.** `IStudentHeartsQuery` / `IStudentMissionsQuery` / `IStudentLeagueQuery` have **write side-effects on first read of a period.** If the decorator wraps incorrectly (e.g., serves a cached null and skips inner call), the side-effect never runs and the student's state is stuck. Mitigation: write side-effect runs **inside the inner** (today's behavior), decorator only caches the post-inner snapshot, and the cache key includes the period boundary so rotation forces a miss + re-run. Tests must explicitly verify the post-rotation behavior (P4-10 case 9 + 10 above).
- **R2 — Sorted-set drift under concurrent XP awards.** If two `XpAwardedDomainEvent`s for the same student commit nearly-simultaneously, the two invalidation handlers race to update the sorted-set. With `ZADD CH` + Postgres re-read, both read the (final) post-commit value, so last-writer-wins == correct. With `ZINCRBY`, both add their delta, but if either handler dies after commit, the sorted-set drifts. Mitigation: use `ZADD CH` (Q9); nightly rebuild job corrects any drift; structured log marker on `ZADD` lets us monitor.
- **R3 — Decorator DI mis-registration.** If the inner Postgres impl is also registered as `IStudentXpQuery` (e.g., by an old AddScoped left over from before the decorator change), the consumer resolves the inner directly and bypasses the cache — **silent bug** (correctness preserved, but no perf win). Mitigation: integration test asserts the resolved type is the decorator (`sp.GetRequiredService<IStudentXpQuery>().GetType().Name == "CachedStudentXpQuery"`); reviewer gate.
