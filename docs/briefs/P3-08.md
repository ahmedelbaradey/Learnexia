# Pipeline Brief — P3-08 Adjust difficulty adaptively (Adaptivity Engine)

## Summary & traceability
- **Task (one line):** Build a deterministic, reproducible **Adaptivity Engine** that, for a given student + skill, computes a target difficulty (`easy`/`medium`/`hard`) from four signals — **accuracy, response time, retry/attempt count, and hint usage** (drawn from P2-08 granular answers + P3-09 mastery) — sustained high performance raising difficulty and repeated struggle lowering it, and exposes that decision to the quiz-selection (P3-11) and question-generation (P3-06) paths.
- **User story (source of truth):** `user-stories/Phase-4-AI-Tutor/P3-08-adaptivity-engine.md`
- **Task file:** none yet (Phase-4 task breakdown pending — HANDOFF). **`planner` decomposes BE tasks from this brief.** Flag to lead.
- **FR-IDs:**
  - **FR-AD-1** (primary) — "The Adaptivity Engine shall adjust difficulty (easy/medium/hard) from accuracy, response time, retry count, and hint usage." *(G2)*
  - **FR-AI-6** (constraint, explicit in AC2) — AI shall **not** decide progression/difficulty; the engine is **deterministic, not AI-driven**.
  - **FR-QZ-3** (downstream) — adaptive quizzes consume this engine's difficulty.
- **BRD goal / epic:** **G2** Learning outcomes. Epic: **Adaptivity & Student Modeling**. Barrier-to-entry **BE5** ("core differentiator"). Covers **B4.2**.
- **Phase / sprint:** Phase 4 — AI Tutor (Week 6–7). **SP 5** — "deterministic engine combining several signals; core differentiator, needs tuning."
- **Product-decision context:** 4 subjects, no Social Studies, no teacher role. **Grade transition preserves history** — engine is stateless per call; a grade change re-scopes which skills are evaluated but the signals it reads (answers/mastery) persist.

## Business context & value
- **Who benefits:** the **student** (kept in a productive learning zone — challenged but not overwhelmed; the user story's core promise); **quiz selection** (P3-11 reads the target difficulty); **question generation** (P3-06 reads it once the AI module lands). Indirectly the **parent** (a child who isn't bored or frustrated retains better → habit).
- **Why it matters:** This is the moat the BRD names "core differentiator." Mastery (P3-09) says *what* the student knows; the Adaptivity Engine decides *how hard to push next*. Without it, every quiz serves the same fixed question set (today `StartAttempt` returns **all** a lesson's Published questions regardless of difficulty — see Affected modules) and the platform feels flat.
- **Why deterministic (no AI):** FR-AI-6 + AC2 — same inputs must always produce the same difficulty, so the decision is debuggable, explainable, and tunable. AI generates *content*; engines decide *difficulty/progression*.
- **Success measure (testable):** for a student with a high-accuracy/fast/no-hint history on a skill, the engine returns `Hard`; for a struggling history (low accuracy, slow, many hints/retries) it returns `Easy`; a new student with no history returns the default (`Medium` — see Q4); the same input signals always return the same difficulty (AC2 reproducibility); the chosen difficulty is retrievable by P3-11.

## Acceptance criteria (testable)
1. **AC1 — Four-signal difficulty.** The engine sets difficulty (`easy`/`medium`/`hard`) from **accuracy, response time, retry count, and hint usage**. *(verbatim FR-AD-1.)*
2. **AC2 — Deterministic & reproducible.** The decision is deterministic and reproducible for the same inputs (not AI-driven, per FR-AI-6). *(verbatim.)*
3. **AC3 — Monotonic response.** Sustained high performance raises difficulty; repeated struggle lowers it. *(verbatim — unit-testable as a monotonicity property.)*
4. **AC4 — Exposed downstream.** The chosen difficulty is exposed to the quiz-selection (P3-11) and question-generation (P3-06) paths. *(verbatim — in-process seam, see Q6.)*

## Affected modules & data
**Module:** **Learning only** (schema `learning`). Reads P2-08 answer signals + P3-09 mastery (both Learning). **No new module.** **No new table required for the core engine** (it computes from existing signals on demand — like P2-04). See Q5 on whether to persist a difficulty snapshot.
> **Ask-the-lead:** could live in a dedicated `adaptivity` module. **Recommendation: keep in `learning`** for the same reasons as P3-09 (it reads Learning answer/mastery data in-process; a separate module forces event plumbing for a read). Flag, recommend `learning`.

### Existing signals consumed (read-only)
- **P3-09 `StudentSkillMastery`** — `MasteryPercentage`, `Status` (the accuracy backbone; **P3-08 depends on P3-09**).
- **`StudentAnswer` / `Attempt`** (P2-08) — `IsCorrect` (accuracy), `TimeSpentSeconds` (response time), `HintUsed`/`HintsUsedCount` (hint usage), and **retry/attempt count** (number of `Attempt` rows for the lesson/skill, or repeated answers). The `GetSkillStats` aggregation already exposes `AvgTimeSpentSeconds` and `HintUsageRate` — **reuse it**; it's almost exactly P3-08's signal vector.
- **`QuizQuestion.Difficulty`** (`DifficultyLevel` enum: the easy/medium/hard target maps to this) — the engine's *output* aligns with this enum so P3-11 can filter by it.
- **`Skill.MasteryThreshold`** — reference point for "high performance."
- **P3-13 `StudentProfile`** (when built) — fatigue/attention signal *may* shorten sessions or shift difficulty; **P3-13 feeds P3-08** but P3-08 must work without it (cold-start). Keep the P3-13 hook optional.

## Open questions for the lead — recommended defaults
> "Approve all defaults" ships a coherent v1.

### Q1 — The difficulty decision rule (THE algorithm — flag explicitly)
- **Recommended default: a deterministic weighted-score band.** Compute a normalized `performanceScore ∈ [0,1]` from the four signals, then band it:
  - `score ≥ highBand` (e.g. 0.8) → **Hard**; `score ≤ lowBand` (e.g. 0.5) → **Easy**; otherwise **Medium**.
  - `performanceScore = w_acc·accuracyNorm + w_time·timeNorm + w_hint·(1 − hintRate) + w_retry·(1 − retryNorm)`, weights summing to 1 (suggest accuracy-dominant, e.g. `0.5/0.2/0.2/0.1`). `timeNorm` and `retryNorm` need a reference (e.g. `Skill.EstimatedTimeMinutes`, expected attempts) to normalize — see Q3.
- **Why:** deterministic, monotonic by construction (AC3), explainable, tunable via the weights/bands (the SP-5 "needs tuning" note). All four FR-AD-1 signals participate.
- **The weights/bands are tunables the product has NOT specified** — flag to lead; ship sensible defaults in an **options object** (`AdaptivityOptions` bound from config, mirror Gamification's `StreakOptions`/`MissionOptions` pattern) so tuning is a config change, not a redeploy of logic.
- **Alternative (simpler):** a rule-ladder ("if accuracy≥85% AND hintRate<10% → Hard; if accuracy<50% OR hintRate>50% → Easy; else Medium") — even more explainable, less smoothly tunable. Acceptable v1 if the lead prefers no weights.
- **Do NOT** introduce an ML/contextual-bandit difficulty model (black box, violates FR-AI-6/AC2). **Flag any such temptation.**

### Q2 — Granularity: difficulty per-skill, per-lesson, or per-session?
- **Recommended default: per-`(student, skill)`** — mastery (P3-09) is per-skill, and difficulty naturally tracks the skill being practiced. P3-11 selects questions per lesson, and a lesson maps to a skill (`Lesson.SkillId`), so per-skill difficulty resolves cleanly for a lesson's quiz.
- **Alternative:** per-lesson (some lessons have null `SkillId` — those fall back to default difficulty, Q4).

### Q3 — Normalizing response time & retries (no absolute "good time" exists)
- **Recommended default:** normalize **response time** against `Skill.EstimatedTimeMinutes` (or the student's/cohort's rolling average answer time if available) — faster-than-expected → higher time score, capped. Normalize **retries** against a small expected baseline (e.g. ≤1 attempt = full score, degrading with each extra). Keep these bounded so an outlier (one very slow answer) can't dominate.
- **Flag:** if no good per-skill time baseline exists in the seed, default time weight low (or 0) and rely on accuracy+hints for v1; document the degradation. Avoid pretending precision we don't have.

### Q4 — Cold-start (new student, no signals)
- **Recommended default: `Medium`** — the neutral starting difficulty. AC of P3-11 ("falls back to a sensible default when no model exists") aligns: P3-08 returns `Medium`, P3-11 serves a balanced mix. The engine returns a flag/enum value distinguishing "computed" vs "default" so P3-11 can apply its own fallback policy if desired.

### Q5 — Persist a difficulty snapshot, or compute on demand?
- **Recommended default: compute on demand** (stateless, like P2-04 + the cold-start to recompute). No new table. P3-11 calls the engine at quiz-build time. **AC4 of P3-11** ("the chosen difficulty mix is recorded with the attempt") means the *resulting selection* is stored on the **`Attempt`** (a new column there — owned by P3-11), not that P3-08 persists state. So **P3-08 needs no migration.**
- **Alternative:** cache the latest difficulty on `StudentSkillMastery` (a `CurrentDifficulty` column) for fast reads / display. Defer unless a perf or UI need appears.

### Q6 — How AC4 "exposed to selection & generation" is wired
- **Recommended default: an in-process service/query method** in the Learning module: `IAdaptivityService.GetTargetDifficulty(studentId, skillId) → AdaptivityDecision { DifficultyLevel Difficulty, bool IsDefault, ... }`. P3-11's quiz builder calls it directly (same module — no HTTP, no event). P3-06 (AI question generation, **not yet built**) will call the same method once the AI module lands. **Optionally** expose a `GET /api/Learning/Adaptivity/Skill/{skillId}` debug/inspection endpoint (Authorize Student, IDOR-guarded) — useful for the api-tester and a future "why is this hard?" UI; recommend including it for testability.

### Q7 — Engine shape (pattern caution, rule 8)
- **Recommended default:** pure static `AdaptivityEngine.DecideDifficulty(AdaptivitySignals signals, AdaptivityOptions options) → AdaptivityDecision` (mirror `LearningPathEngine`). `AdaptivitySignals` = the pre-fetched `{accuracy, avgTime, hintRate, retryCount, masteryPct}` vector. No DB/DI in the engine; a thin `AdaptivityService` fetches signals + options and calls it.
- **Pattern caution (this is THE place someone reaches for it):** difficulty/state adjustment invites **Strategy** ("pluggable difficulty policy") or **State** ("easy/medium/hard state machine"). **Do NOT introduce either without asking the lead** (CLAUDE rule 8). The default is a plain pure function + an `Enum` + a config-bound options object. The tunability AC5/SP-note wants is satisfied by `AdaptivityOptions` (config), not by a pattern.

## Risks & assumptions
1. **Tuning is real work** (SP-5 note). Defaults will need calibration against real data; isolating weights/bands in `AdaptivityOptions` makes that a config change. Flag that initial weights are best-guess.
2. **Time normalization is the weakest signal** (Q3) — no reliable absolute baseline. Don't over-weight it; degrade gracefully.
3. **Depends on P3-09 mastery** — P3-08 must merge *after* P3-09. It also reads raw answer aggregates (P2-08, already built).
4. **P3-06 consumer not built** (AI module absent). AC4 is satisfied by exposing the in-process seam + P3-11 consuming it; P3-06 wiring is deferred until the AI module lands — note it, don't block.
5. **Reproducibility vs. time-window signals** — if the rule uses "recent N answers," ensure the window is deterministic (e.g. by answer Id/timestamp ordering), not wall-clock-relative, so AC2 holds.
6. **P3-13 fatigue hook optional** — engine must not hard-depend on the (later) behavioral profile; keep that input nullable with a safe default.

## Out of scope
- AI-driven difficulty (FR-AI-6 forbids).
- The mastery model itself (P3-09 — consumed here).
- Selecting/serving the actual questions (P3-11 — *consumes* this engine).
- Question generation (P3-06 — later, AI module).
- Recording the chosen mix on the attempt (P3-11's AC4, P3-11's migration).
- Behavioral/fatigue profile (P3-13 — optional feed-in).
- Frontend.

## Per-agent handoffs

### Handoff → db-migration
**Expected: NO migration** (engine computes from existing P2-08 + P3-09 signals on demand — Q5). Do not commit an empty migration. (The "record difficulty mix with the attempt" column belongs to **P3-11**, not here.) If Q5-alternative (cache `CurrentDifficulty` on `StudentSkillMastery`) is chosen, that adds a column to the P3-09 table — flag and coordinate with P3-09's migration.

### Handoff → backend-feature
Mirror **P2-04 (`LearningPathEngine`)** + **P3-09 (`MasteryEngine`)** + Gamification options pattern.
- **`AdaptivityEngine`** pure static domain service (Q7) + `AdaptivitySignals` + `AdaptivityDecision` records + `AdaptivityOptions` (config-bound, mirror `StreakOptions`).
- **`AdaptivityService`** (in-process) — fetches signals (reuse `GetSkillStats` aggregation + P3-09 mastery) + options, calls the engine, returns the decision. This is the AC4 seam P3-11 calls.
- **Optional** `AdaptivityController` `GET /api/Learning/Adaptivity/Skill/{skillId}` (`[Authorize(Roles="Student")]`, IDOR-guarded) for inspection/testing.
- `BaseResponse<T>`/`Successed`, `ILoggerManager`, no `ex.Message` leak, queries not auto-validated.
- **Pattern caution (rule 8):** plain function + enum + options. No Strategy/State without asking.

### Handoff → api-tester
If the inspection endpoint is included, validate against running API + seeded data + Student JWT:
- New student → `Medium` + `IsDefault=true`.
- Seeded high-performance history (high accuracy, low hints) → `Hard`.
- Seeded struggle history (low accuracy, high hints/retries) → `Easy`.
- Monotonicity: improving one signal never lowers difficulty, all else equal (AC3).
- Reproducibility: same signals → identical decision (AC2).
- IDOR: another student's difficulty not addressable.
If no endpoint, AC1–AC3 are covered by **unit tests** on the pure engine; api-tester validates AC4 indirectly via **P3-11's** integration tests (difficulty actually changes the served question mix).

### Handoff → security-auditor
**Low** — per-student read, no PII/upload/AI-prompt/secrets. IDOR guard + no `ex.Message` leak only. Likely skippable if reviewer confident.

### Handoff → reviewer
Gate on: all 4 ACs; pure engine + monotonicity + reproducibility + cold-start unit tests; tunables in `AdaptivityOptions` (config, not hardcoded); **no Strategy/State pattern** (rule 8); deterministic windowing (no wall-clock); P3-09 dependency satisfied; CONVENTIONS (envelope, `ILoggerManager`, module isolation); HANDOFF updated with the Q1 rule + default weights/bands.
