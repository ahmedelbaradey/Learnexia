## Business context & value

- **Who benefits:** the **student** directly — personalization is what makes the tutor feel like *theirs*: an explanation pitched at their grade/age, in their language, targeting their weak areas, in a kind tone. This is the differentiation BRD §26 names (*"adaptive AI personalization + behavioral/emotional design + Arabic-first"*). Secondarily the **business** — personalization quality is the product's moat (not raw model strength).
- **Why it matters now:** it is the third foundational brick — every tutoring feature (explain P3-04, hints P3-05, generate questions P3-06) constructs its prompt through this builder. Without it, each feature would hand-roll prompts, drift in tone/safety, and duplicate context assembly. Centralizing it guarantees consistent child-safe tone + consistent personalization + a single place to tune prompt quality.
- **Success measurement (from AC):**
  - A prompt for a Grade-4 Arabic-preference student injects grade, age, language=ar, the retrieved curriculum context, the student's weak areas (or nothing if none), and the child-safe tone frame.
  - Asking for a Math explanation uses the step-by-step Math template; Science uses the visual template; Arabic/English use the vocab/grammar template — and there is no Social-Studies template.
  - Arabic-preference → the assembled prompt instructs Arabic output (verified the model responds in Arabic downstream).
  - A brand-new student with no weak areas yet → the prompt still assembles correctly (no null/empty-section breakage) and is sensible.
- **Deterministic boundary (BRD §97 / FR-AI-6):** the builder is **pure, rule-based assembly** — no AI, no learning decision. It requests *content*; it never asks the model to decide progression/difficulty.

2. **AC2 — Subject-specific templates exist for the 4 MVP subjects: Math step-by-step, Science visual, Arabic & English vocab/grammar.**

3. **AC3 — Given Arabic language preference, then prompts produce Arabic output.**
   - Backend gate: the builder selects the ar template variant + adds an explicit "respond in Arabic" instruction when `language == ar`; en otherwise. Unit test on both language paths. (Localization per NFR-5 — Arabic-first.)
4. **AC4 — Missing optional context (e.g., no weak areas yet) degrades gracefully without breaking the prompt.**
   - Backend gate: weak areas + RAG curriculum context are **optional** inputs; when absent, the builder omits those sections cleanly (no empty-header artifacts, no null-ref). Unit test with empty/absent weak areas + empty RAG chunks → a valid, sensible prompt. This is the seam that lets P3-03 ship **before** P3-07 (RAG) and P3-09 (weak areas) are complete.

## Handoff → security-auditor

**Mandatory run — security-sensitive (prompt-injection surface + child PII flowing into outbound prompts).** Per CLAUDE.md, Critical/High findings block. Focus:

- **Prompt-injection hardening:** the fixed system frame must instruct the model to **ignore instructions embedded in retrieved curriculum context or student-supplied input** that attempt to change its persona/safety. Verify retrieved context + any student free-text is inserted as clearly-delimited *data*, not as instructions. This is the primary finding category.
- **Child PII minimization in prompts:** the builder injects grade/age/language/weak-areas — it must **not** inject the child's name, email, exact birthdate, parent info, or any unnecessary PII into the outbound prompt. Inject *age* (or grade) not *birthdate*; no direct identifiers. Verify the minimal-PII assembly.
- **No PII in logs:** the builder must not log assembled prompt bodies (they may carry weak-area / context data) at info level.
- **FR-AI-6:** confirm no template asks the model for a progression/unlock decision (keeps AI on the content-only side of the deterministic boundary — a safety + correctness invariant).
- **Tone-frame integrity:** the child-safe tone frame cannot be omitted/overridden by any caller (it is unconditionally prepended).
