# Pipeline Brief — P3-11 Serve adaptive quizzes (adaptive question selection)

## Summary & traceability
- **Task (one line):** Make quiz generation **adaptive** by selecting question difficulty from the student's adaptivity model (P3-08) at quiz-start time — favouring easier/reinforcement questions for a struggling student and harder ones for a strong student, falling back to a sensible default for new students, and **recording the chosen difficulty mix on the attempt**.
- **User story (source of truth):** `user-stories/Phase-4-AI-Tutor/P3-11-adaptive-quiz-selection.md`
- **Task file:** none yet (Phase-4 task breakdown pending — HANDOFF). **`planner` decomposes BE tasks from this brief.** Flag to lead.
- **FR-IDs:**
  - **FR-QZ-3** (primary) — "Quizzes shall be adaptive in difficulty per student model." *(G2)*
  - **FR-AD-1** (consumed) — the P3-08 difficulty decision.
  - **FR-AI-6** (constraint) — selection is rule-based (the engine decides difficulty; AI only *generates* the questions in the pool).
- **BRD goal / epic:** **G2** Learning outcomes. Epic: **Assessment Module**. Barrier-to-entry **BE5**. Covers **B3.3**.
- **Phase / sprint:** Phase 4 — AI Tutor (Week 6–7). **SP 3** — "selection hook joining quiz engine to adaptivity; moderate integration."
- **Product-decision context:** 4 subjects, no Social Studies, no teacher role. Grade transition preserves history (irrelevant to selection mechanics).

## Business context & value
- **Who benefits:** the **student** (each quiz feels appropriately challenging — not too easy/hard, the story's core promise); the platform's **retention/habit** (right difficulty = flow, not frustration/boredom). The **content team** later sees which difficulties get served (the recorded mix).
- **Why it matters:** This is where P3-08's difficulty decision and P3-09's mastery become *visible to the student*. **Today `StartAttemptCommandHandler` returns ALL Published+Active questions for a lesson, with no difficulty filtering** (see `QuizQuestion.Difficulty` is ignored at selection). P3-11 is the hook that turns the engine's decision into the actual question set the student sees. It is "moderate integration" precisely because the engine (P3-08) and signal (P3-09) already exist — this story joins them to the quiz path.
- **Why rule-based:** FR-AI-6 — the *selection* is deterministic (driven by P3-08's deterministic difficulty); AI's only role is generating the candidate questions (P3-06, later). Selection from an existing pool is pure rule logic.
- **Success measure (testable):** for a student modeled as struggling on a skill, the served question set skews `Easy`/reinforcement; for a strong student it skews `Hard`; a new student gets a sensible default mix; the chosen difficulty mix is stored on the `Attempt` and retrievable.

## Acceptance criteria (testable)
1. **AC1 — Selection uses the adaptivity model.** When a quiz is generated, question difficulty is selected using the student's adaptivity model (P3-08). *(verbatim.)*
2. **AC2 — Direction is correct.** A student modeled as struggling on a skill gets easier/reinforcement questions favoured; a strong student gets harder ones. *(verbatim — testable as a skew, see Q2.)*
3. **AC3 — Cold-start fallback.** Selection falls back to a sensible default when no model exists yet (new student). *(verbatim — P3-08 returns `Medium`+`IsDefault`; selection serves a balanced mix.)*
4. **AC4 — Mix recorded with the attempt.** The chosen difficulty mix is recorded with the attempt. *(verbatim — new column(s) on `Attempt`, see Q3.)*

### AC → expected work mapping
| AC | Delivered by |

## Affected modules & data
**Module:** **Learning only** (schema `learning`). Quiz, `Attempt`, `QuizQuestion`, and P3-08/P3-09 are all in Learning — **no new module, no cross-module work.**

### Existing entities consumed / extended
- **`QuizQuestion`** — `Difficulty` (`DifficultyLevel` enum), `LessonId`, `SkillId?`, `IsActive`, `LifecycleState` (selection only from Published+Active, preserving the existing `StartAttempt` filters).
- **`Attempt`** — **extended (AC4):** add a column to record the served difficulty mix (Q3).
- **P3-08 `IAdaptivityService.GetTargetDifficulty(studentId, skillId)`** — the difficulty decision (in-process call). **P3-11 depends on P3-08.**
- **P3-09 `StudentSkillMastery`** — read transitively via P3-08 (P3-11 doesn't read mastery directly; it asks P3-08 for the difficulty).
- **The seam:** `StartAttemptCommandHandler` — today loads **all** Published+Active questions for the lesson. P3-11 inserts a **selection step** between "load candidate questions" and "build the response" (Q1).

## Open questions for the lead — recommended defaults
> "Approve all defaults" ships a coherent v1.

### Q1 — Where the selection happens (hook point)
- **Recommended default: inside `StartAttemptCommandHandler`** — after loading the lesson's candidate questions, call `IAdaptivityService.GetTargetDifficulty(studentId, lesson.SkillId)`, then pass the candidate pool + target difficulty to a pure `QuizSelectionEngine.Select(candidates, target, options)` that returns the chosen subset/order. Minimal new surface; reuses the existing resume/new-attempt paths and the existing question filters (`IsActive && LifecycleState == Published`). Apply selection on **both** the new-attempt and resume branches consistently (or freeze the selection at first start — see Q4).
- **Alternative:** a new `GET .../Quizzes/{lessonId}/AdaptiveSet` endpoint. Heavier; not recommended — `StartAttempt` is already the quiz-build entry point.

### Q2 — Selection policy: filter, skew, or weighted mix?
- **Recommended default: a difficulty-weighted mix centered on the target.** Given target `Hard`, favour Hard questions but include some Medium (e.g. 70/30) so a single bad day doesn't wall the student off; target `Easy` favours Easy + reinforcement (Medium), avoiding pure-Hard. Target `Medium` → balanced. **AC2 is satisfied as a measurable skew, not a hard filter** — robust to a lesson pool that lacks enough questions at the exact target difficulty (Q5).
- **Reinforcement nuance (AC2 "reinforcement"):** for a struggling student, "reinforcement" = re-serving Easy questions on the **prerequisite skills** the student hasn't mastered (read from the P2-11 graph via P2-04's prereq query) OR simply Easy questions on the current skill. **Recommend the simpler interpretation for v1 (Easy on current skill)**; prereq-pulled reinforcement is a richer follow-up (ties to P3-10 spaced repetition). Flag the choice.
- **Alternative:** hard filter to exactly the target difficulty (simpler, but brittle when the pool is thin at that level).

### Q3 — How AC4 "record the chosen mix" is stored
- **Recommended default:** add a column to **`Attempt`** capturing the served distribution + the target. Two viable shapes:
  - **(A, recommended)** `Attempt.ServedDifficultyMix` (jsonb) = `{"Easy":n,"Medium":n,"Hard":n,"Target":"Hard","WasDefault":false}` — flexible, one column, queryable in Postgres jsonb. Plus optionally `Attempt.TargetDifficulty` (enum→int) for cheap indexing/reporting.
  - **(B)** discrete columns (`EasyCount`, `MediumCount`, `HardCount`, `TargetDifficulty`). More rigid; avoid unless reporting needs columnar.
- **This is the only migration P3-11 needs.** Backfill-safe: existing rows get null/empty mix.

### Q4 — Selection timing: at first start, or re-selected on resume?
- **Recommended default: select once at first `StartAttempt` and freeze it for the attempt** — store the chosen question set's difficulty mix on the `Attempt`; on resume, return the **same** questions (don't re-roll difficulty mid-attempt). Cleaner UX (questions don't change underneath the student) and makes AC4's recorded mix stable/accurate. Requires persisting which questions were chosen, not just the counts — either store chosen `QuestionIds` on the attempt (new) or make selection deterministic given `(attemptId, candidates, target)` so resume reproduces it. **Recommend deterministic-given-seed selection** so resume reproduces the set without a second table.
- **Alternative:** re-select on every resume (simpler, but the question set can shift, which is confusing and makes AC4's recorded mix a snapshot-in-time).

### Q5 — Thin question pool at the target difficulty
- **Recommended default: graceful degradation** — if the lesson lacks enough questions at the target, the weighted mix naturally pulls adjacent difficulties; if the pool is tiny, serve whatever exists (never fail to start a quiz). Log a content-gap warning (server-side) so the content team can fill it. Never 500 / never empty when questions exist.

### Q6 — Engine shape (pattern caution, rule 8)
- **Recommended default:** pure static `QuizSelectionEngine.Select(IReadOnlyList<QuizQuestion> candidates, DifficultyLevel target, QuizSelectionOptions options) → IReadOnlyList<QuizQuestion>` (mirror `LearningPathEngine`). Deterministic given inputs (Q4). Mix ratios live in `QuizSelectionOptions` (config-bound). No DB/DI in the engine.
- **Pattern caution:** "pluggable selection strategy" is the obvious Strategy-pattern temptation. **Do NOT introduce Strategy/Factory without asking the lead** (rule 8). Default = plain function + config options.

## Risks & assumptions
1. **Depends on P3-08 (and transitively P3-09)** — merge order: P3-09 → P3-08 → **P3-11**.
2. **`StartAttempt` is a hot, already-secured path** — adding the selection step must not break the resume/language-guard/lifecycle filters already there (P7-04/P7-05/P8-03). Keep the selection step additive and after those guards.
3. **Lesson `SkillId` may be null** (3 Math lessons/grade per seed) — no skill → P3-08 returns default → balanced mix (AC3 path). Handle explicitly.
4. **Question pool difficulty coverage** — the seed must have questions at varied difficulties for selection to do anything visible; if every question is the same `Difficulty`, selection is a no-op. **Flag to lead / content:** verify seeded `QuizQuestion.Difficulty` spread; otherwise the feature works but is unobservable in the demo.
5. **AC4 jsonb on `Attempt`** — coordinate the migration with any other in-flight `Attempt` changes (serialize shared-file edits per PARALLELISM).
6. **Reproducibility on resume (Q4)** — deterministic selection seed must be stable across requests.

## Out of scope
- The difficulty *decision* (P3-08 — consumed).
- The mastery model (P3-09 — consumed via P3-08).
- AI question *generation* (P3-06 — the pool is human/seeded today; P3-11 selects from whatever exists). When P3-06 lands, generation can read P3-08's difficulty too, but that's P3-06's wiring.
- Spaced-repetition review sets (P3-10 — different scheduler; may later supply reinforcement candidates).
- Frontend (the student app already calls `StartAttempt`; the response shape stays compatible — questions list — so no FE change is forced; a "this quiz is tuned to you" UI affordance is optional FE follow-up).
