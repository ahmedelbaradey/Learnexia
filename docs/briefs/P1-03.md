# Pipeline Brief — P1-03 (Backend) — Parent onboarding & add children

## Summary & traceability
- **Task (one line):** Let an authenticated parent provision one or more child (Student-role) accounts during onboarding, each with a parent-assigned login email and per-child grade/language/country, auto-linking each child to the parent.
- **User story:** `user-stories/Phase-1-Foundation/P1-03-complete-onboarding.md` (SP 5).
- **Task file:** `tasks/Backend/Phase-1-Foundation/P1-03-BE.md` (tasks BE-1 … BE-7).
- **FR-ID:** FR-ID-2 (**modified** — actor changed from student to parent; captured fields unchanged). This product-decision override **wins** over the SRS wording.
- **BRD goal:** G1 (acquisition / activation — getting families onboarded and learning).
- **Epic / Phase:** Identity & Onboarding · Phase 1 — Foundation.
- **Base branch:** `feat/P1-03-onboarding` cut off `feat/wave-3`. P1-01/P1-02/P1-04 are merged into this base. **Worktree:** `E:\Wrokspace\Learnexia.worktrees\P1-03`.

## Business context & value
- **Who benefits:** the **parent** (sets up children without each child self-registering — the COPPA-aligned, parent-driven model) and the **student** (gets a ready account scoped to the right grade/language and just logs in). Admin is not involved in this flow.
- **Value:** removes the child-self-registration path entirely (a minor-safety + abuse concern), and front-loads grade/language/country so Phase-3 AI prompt building (FR-AI-5) and the Phase-1 locale/RTL behavior have the data they need at first login.
- **Success measure:** a parent can add N children in one session; each child can later sign in with the assigned email; invalid grade / duplicate email are rejected with a clear message and create no account; every added child appears under `My-Children` (linkage created).

## Acceptance criteria (testable)
1. **AC-1 (add child + profile):** A Parent-authenticated `Add-Child` call with `{ childName, loginEmail, grade(1–6), language(ar|en), country, ...credential }` creates a `User` with the **Student** role, persists grade/language/country on that child, and returns the created child profile. → BE-2, BE-3.
2. **AC-2 (multiple children):** The parent can add more than one child (sequential calls and/or a batch array); each gets a distinct account + profile. → BE-5.
3. **AC-3 (assigned login email):** The child's login email is the value the parent assigned; the child later authenticates with it (P1-01 sign-in). UserName is set to the email. → BE-2.
4. **AC-4 (parent action only):** The endpoint is gated to the **Parent** role (Admin/SuperAdmin may also call for support). The acting parent id is resolved **server-side from the JWT (`ICurrentUserService.UserId`)** — never from the request body. A child has no path to self-create. → BE-2 + P1-05 enforcement.
5. **AC-5 (auto-link):** Each successfully created child is linked to the acting parent via `ILinkParentStudentService.LinkAsync(parentId, childId)`; the child then appears in `GET /api/Users/Parent/My-Children`. → BE-4.
6. **AC-6 (validation → 422):** grade outside 1–6, missing/blank required fields, malformed email, and language not in {ar,en} are rejected by the `ICommand<>` validator (`ValidationBehavior` → 422), creating no account. → BE-6.
7. **AC-7 (duplicate email):** A `loginEmail` already in use is rejected with a specific "email in use" message and no account created; in batch mode this child entry fails without rolling back already-created siblings (partial-failure safe). → BE-5, BE-6.
8. **AC-8 (locale):** The child's stored language drives app locale/RTL at first login (consumed by P1-09; this story only persists the value). → BE-3.

## Affected modules & data
- **Single module:** Identity. No cross-module work. Schema **`identity`**.
- **Entity changes — `User` (existing, extended):** add four fields per BE-1 and architecture.md §16 (where these are not yet present):
  - `Grade` — `int?` (nullable; parents have no grade; child 1–6). Map to `integer NULL` with a comment.
  - `Age` — `int?` (nullable).
  - `LanguagePreference` — **decision point:** `User` already has `PreferredLanguage` (string `"ar-EG"`/`"en-US"`, default `ar-EG`, configured in `UserEntityConfig`). The story's `language(ar|en)` requirement is **already covered by `PreferredLanguage`**. Recommend mapping child `language` → existing `PreferredLanguage` and **only adding a distinct `LanguagePreference` column if the lead confirms it is semantically different** (otherwise it duplicates). **Flag as open question Q1.**
  - `Country` — **decision point:** `User` already has `CountryCode` (dial code, default `+20`) and `Nationality`. `Country` (an ISO country, e.g. `EG`) is *not* the same as `CountryCode`. Recommend adding `Country` as `string?` (maxlen ~2–100). **Flag overlap as Q1.**
- **No new entities.** `ParentStudent` (P1-04) is reused as-is.
- **`LinkedChildResponse` (existing):** currently exposes `Id, FullName, Email` and its doc comment says grade is "intentionally NOT surfaced." With grade now living on the Identity `User` (not Curriculum), that rationale is **stale**. Recommend either (a) returning a new `AddedChildResponse` from Add-Child that includes grade/language/country, or (b) extending `LinkedChildResponse`. Recommend (a) to avoid changing the P1-04 contract used by `My-Children`. **Flag as Q2.**

## Handoff → backend-feature
- **New command:** `AddChildCommand : ICommand<BaseResponse<AddedChildResponse>>` (or `BaseResponse<List<...>>` if batch — see Q3) under `Features/Family/Commands/AddChild/` (group with Family, alongside LinkChild — same domain).
  - **Fields:** `ChildName` (→ `FullName`), `LoginEmail`, `Grade (int)`, `Language (string, ar|en)`, `Country (string)`, plus the **credential field per Q4** (e.g. `Password` if parent sets it).
  - **No `ParentId` field** — resolve from `ICurrentUserService.UserId` (mirror `LinkChildCommand`, AC-4 / IDOR defence).
- **Handler `AddChildCommandHandler` (mirror `RegisterParentCommandHandler` + `LinkChildCommandHandler` patterns):**
  1. Resolve `parentId` from `ICurrentUserService`; `Unauthorized` if null.
  2. Pre-check `FindByEmailAsync(loginEmail)` → if exists, `BadRequest` duplicate-email (race backstop behind the validator, like RegisterParent).
  3. Build `User { UserName = LoginEmail, Email = LoginEmail, FullName = ChildName, PreferredLanguage = mapped(Language), Country = Country, Grade = Grade, CreatedBy = parentId, RegistrationIsCompleted = false }`.
  4. `UserManagmentService.CreateAsync(user, password)` — Identity commits immediately. On failure return `BadRequest` with localized message (mirror RegisterParent error shaping; do NOT echo raw Identity errors to client — security).
  5. `AddToRoleAsync(user, Roles.Student.ToString())` — role is **server-assigned**, never client-supplied (mirror RegisterParent's Parent assignment).
  6. **AFTER** CreateAsync commits, call `LinkParentStudentService.LinkAsync(parentId.Value, user.Id, ct)` (the auto-link hook; it commits immediately — sequencing per `ILinkParentStudentService` doc remarks: link only after the child user exists).
  7. Optionally publish `UserRegisteredIntegrationEvent` (best-effort, after commit) for parity with RegisterParent/AddUser — confirm whether students should fan out (Q5).
  8. Return `Success(mapped AddedChildResponse)`.
- **Multiple children (BE-5):** support a batch by either repeated calls (simplest, idempotent per child) or an array command returning per-item results. **Partial-failure safety:** each child is its own immediate commit (no UoW), so a later failure must not undo earlier successes — return a per-child result list when batch. **Confirm batch vs single in Q3.**
- **Validator `AddChildCommandValidator : AbstractValidator<AddChildCommand>`** (runs via `ValidationBehavior` for `ICommand<>`):
  - `ChildName` not empty; `LoginEmail` not empty + `.EmailAddress()`; `Grade` `InclusiveBetween(1,6)`; `Language` must be `ar` or `en`; `Country` not empty (confirm format). Use `IStringLocalizer<SharedResources>` like existing validators. **Do not** do an email-existence lookup in the validator (handler owns uniqueness → consistent message; see LinkChild validator note).
- **Response:** new `AddedChildResponse { Id, FullName, Email, Grade, Language, Country }` + AutoMapper profile (extend `FamilyProfile`).
- **Endpoint (BE-2):** add to **`ParentController`** (Parent-gated, `[Authorize(Roles = "Parent,Admin,SuperAdmin")]`, route `api/Users/Parent`) — **NOT** the AdminOnly `UserManagementController`. Recommended: `POST api/Users/Parent/Add-Child`. The task file's *assumed* path (`/api/Users/UserManagement/Add-Child`) is on the AdminOnly controller and would force admin-only — **reject that assumption**; ParentController is the correct home (its header comment already documents why parent actions are separate from admin actions).
- **Localization:** reuse existing `SharedResourcesKey` entries (`ProfileDuplicateEmail`, `ProfileRequiredField`, `ProfileInvalidEmailFormat`, `SystemErrorSavingData`). Add a new key only if grade-range / language messages have no existing match.

- **Cases:** (a) Parent token + valid child → 200, child created with Student role, appears in My-Children; (b) grade 0 / 7 → 422; (c) duplicate email → specific rejection, no account; (d) malformed email → 422; (e) unauthenticated → 401; (f) authenticated non-Parent (e.g. Student) → 403; (g) multiple children in one session all linked; (h) batch with one bad entry → siblings still created (partial-failure). Verify the child can subsequently sign in with the assigned email (P1-01).

## Handoff → security-auditor (REQUIRED — security-sensitive batch)
This batch **creates child/minor accounts** and assigns roles, so a security pass is mandatory before the gate. Focus areas:
- **No privilege escalation:** role is hard-coded `Student` server-side; `AddChildCommand` must have **no** role/parentId field. Confirm a parent cannot mint a Parent/Admin via this path.
- **Parent-only gating:** endpoint lives on the Parent-gated controller; acting parent from JWT only.
- **Email enumeration:** duplicate-email response — story explicitly wants a *specific* duplicate message (AC-7), which differs from LinkChild's deliberately-generic anti-enumeration stance. Flag the tension: Add-Child is an authenticated parent action so a specific message is acceptable, but auditor should confirm it does not leak cross-family info.
- **Credential provisioning (Q4):** whichever path is chosen (parent-set password vs set-password link) must not log or echo the credential; temp passwords (if generated like AddUser) must be transmitted securely.
- **Minor-data handling:** grade/age/country of minors stored — confirm consistent with BRD §10 consent posture.

## Open questions / assumptions / risks
- **Q1 (field overlap — important):** `User` already has `PreferredLanguage` (ar-EG/en-US) and `CountryCode` (+20 dial code) + `Nationality`. Does the lead want **new** `LanguagePreference`/`Country` columns, or should `language` map to existing `PreferredLanguage` and `Country` be a new ISO field (recommended: reuse `PreferredLanguage`, add only `Country` + `Grade` + `Age`)? Adding duplicate language columns risks drift.
- **Q2 (response contract):** Extend `LinkedChildResponse` (changes the P1-04 My-Children contract) or introduce a new `AddedChildResponse`? Recommend a new response to keep P1-04 stable. Note: `LinkedChildResponse`'s "grade is a Curriculum concept, not surfaced" comment is now stale.
- **Q3 (batch shape):** Single-child endpoint called N times, or one batch endpoint accepting an array with per-item results? Both satisfy AC-2; batch better matches "in the same onboarding flow" + partial-failure semantics. **Lead to decide.**
- **Q4 (BE-7 — credential provisioning, OPEN in the task file):** Does the **parent set the child's initial password** in the Add-Child request, or does the system generate a temp credential / emit a child set-password link (mirroring `SetNewPasswordCommand` / AddUser's temp-password+notification flow)? This changes the command shape and the security surface. **Must be decided before backend-feature starts.**
- **Q5 (integration event):** Should adding a child publish `UserRegisteredIntegrationEvent` (as RegisterParent/AddUser do) so other modules learn of the new student? Likely yes (Curriculum/Gamification will need to know the student exists), but confirm.
- **Q6 (DB guard):** Confirm no DB CHECK constraint for grade 1–6 (validation in app layer per CONVENTIONS) — assumed.
- **Risk — wave overlap with P1-05 (cross-cutting `[Authorize]` work):** P1-05 runs in parallel and adds/normalizes `[Authorize]` across controllers. **Files this story touches that P1-05 is also likely to touch:**
  - `ParentController.cs` (we add the `Add-Child` action; P1-05 may re-touch the class-level `[Authorize]`). **Highest merge-overlap risk.**
  - Possibly `UserManagementController.cs` (only if the lead overrules and puts the endpoint there — recommend NOT, partly to avoid this overlap).
  - `IdentityModule.cs` / `Program.cs` / Claims / `Directory.Packages.props` are **shared-file edits** — per PARALLELISM.md these must be serialized; this story should not need them unless a new policy is introduced. Flag to lead to sequence ParentController edits with P1-05.
