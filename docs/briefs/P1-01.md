# Pipeline Brief — P1-01 (Backend) Register as a parent

## Summary & traceability
- **Task (1 line):** Add an `AllowAnonymous` parent self-registration endpoint that creates a Parent-role Identity `User`, validates email/password, hashes the password, and returns a JWT.
- **User story:** `user-stories/Phase-1-Foundation/P1-01-register-student-or-parent.md` (source of truth).
- **Task file:** `tasks/Backend/Phase-1-Foundation/P1-01-BE.md` (tasks P1-01-BE-1 … BE-5).
- **FR-ID:** FR-ID-1 (Identity & Onboarding). **BRD goal:** G1 (acquire/onboard families — parent-led signup gates the whole funnel). **Epic:** Identity & Onboarding. **Phase/Sprint:** Phase 1 — Foundation (Week 1–2). **SP:** 3.
- **Product overrides applied:** parent-driven onboarding (parents register; students do NOT self-register — children are parent-provisioned in P1-03/P1-09); no teacher role.
- **Dependency:** task file lists `P1-06-BE-*` (Npgsql migration) as a dep. The `identity` schema already exists in code (`Migrations/20260520084838_InitialIdentity.cs`), so **no new migration is required for this story** — see "Affected modules & data". Confirm P1-06 is merged/available before runtime.

## Business context & value
- **Who benefits:** the parent (account holder/decision-maker) directly; the child indirectly (a parent account is the prerequisite for provisioning child learner accounts in P1-03). Admin benefits from a clean, single registration entry point.
- **Value:** the parent account is the top of the acquisition funnel. Without it no child can be onboarded, no learning happens, no monetization. Self-service registration removes a manual onboarding bottleneck.
- **Success measures (from BRD/SRS context):** successful parent registrations, registration→first-child-provisioned conversion, zero plaintext-password incidents, duplicate-account rate ≈ 0.

## Acceptance criteria (testable)
1. **AC-1 — Happy path:** `POST` to the parent-registration endpoint with a valid unique email + policy-compliant password creates a `User` assigned the **Parent** role and returns `BaseResponse<JwtAuthResponse>` with `Successed=true`, HTTP 200, and a non-empty `AccessToken`.
2. **AC-2 — No anonymous child registration:** there is no anonymous path to create a Student/child account. The registration command can only ever assign the **Parent** role (role is server-decided, never client-supplied). Child accounts remain parent-provisioned (P1-03).
3. **AC-3 — Duplicate email rejected:** registering with an email already in use (parent OR existing/child user) is rejected with a clear error and no second account is created.
4. **AC-4 — Weak password blocked:** a password failing the policy (min length 6, requires digit + uppercase + lowercase + non-alphanumeric) is rejected with a specific message before any user is created.
5. **AC-5 — Password hygiene:** password is stored hashed by ASP.NET Identity; the request DTO/response never echoes the password (response is `JwtAuthResponse` only — no password field).
6. **AC-6 — Validation envelope:** validation failures surface as HTTP **422** `BaseResponse` with `Errors[]` items shaped `{ PropertyName, ErrorMessage }` (existing `ErrorHandlerMiddleWare` + `ValidationException` path) so the FE can map duplicate-email / weak-password.

## Affected modules & data
- **Module:** Identity only (`Learnexia.Modules.Identity.*`). No other module touched; no cross-module FK or contract change required by this story.
- **Entities — all EXISTING, no schema change:**
  - `User : IdentityUser<int>` (`Domain/Entities/User.cs`) — note `FullName` is **non-nullable** (`= default!`), and `UserName`, `PreferredLanguage` (`ar-EG`), `CountryCode` (`+20`) exist. See open question Q1 about `FullName`/`UserName` sourcing.
  - `Role`, `UserRefreshToken`, `UserSession`, ASP.NET Identity tables — all created by `Migrations/20260520084838_InitialIdentity.cs`.
- **Data (seed) change — NET-NEW:** add `Parent` and `Student` to the `Roles` enum (`Domain/Constants/Roles.cs`) and seed both idempotently. **Current `RoleSeeder.SeedAsync` is NOT idempotent** — it calls `roleManager.CreateAsync(...)` unconditionally for every role and ignores the result, which produces duplicate-name errors on re-run. BE-2 should add an existence check (e.g. `if (!await roleManager.RoleExistsAsync(name))`) for the new roles (and ideally retrofit the existing ones).
- **DB migration:** none expected — Identity schema is data-seeded, not schema-changed. **db-migration agent is NOT needed for this story.** Confirm during implementation that adding enum values + seed rows requires no EF migration (it does not — `AspNetRoles` rows are data, not schema).

## Handoff → db-migration
- **No work.** Identity schema already migrated (`20260520084838_InitialIdentity`). Roles are seed data, not schema. Do not generate a migration. If implementation discovers an unexpected schema need (it should not), escalate to the lead.

## Handoff → backend-feature
Mirror the **AddUser** feature folder layout and the **SignIn** controller/response style.

- **Command (BE-1):** `RegisterParentCommand : ICommand<BaseResponse<JwtAuthResponse>>` under `Application/Features/Authentications/Commands/RegisterParent/`.
  - Fields: `Email`, `Password`. Add `FullName` and/or `UserName` per Q1 resolution (do NOT accept a client `Roles` field — role is fixed to Parent server-side, satisfying AC-2).
  - **Never** include a password in any response or log line.
- **Handler (BE-1):** `RegisterParentCommandHandler : BaseResponseHandler` —
  1. Check `UserManagmentService.FindByEmailAsync(Email)` (and by username if used) → if exists, `BadRequest<JwtAuthResponse>(localizer[...DuplicateEmail])` (AC-3).
  2. Build `User` (set `PreferredLanguage="ar-EG"`, `CountryCode="+20"`, `RegistrationIsCompleted=false`, `CreatedAt`); `UserManagmentService.CreateAsync(user, password)` — surfaces Identity password-policy failures too (defense in depth behind the validator).
  3. Ensure Parent role exists then `AddToRoleAsync(user, Roles.Parent.ToString())` (use the same casing convention the seeder/`AddUser` uses — verify lower-case vs PascalCase; `RoleSeeder` stores `.ToLower()` but `UserSeeder` adds PascalCase — **resolve casing consistently**, see Q3).
  4. Issue token: `AuthenticationService.GetJwtToken(user)`; set `UserId`, `IsFirstLogin=true` (mirror SignIn's "registration not completed" behavior). Return `Success(jwt)`.
  5. (Optional, follow AddUser) publish `UserRegisteredIntegrationEvent` via `IPublisher` after create — confirm with lead whether P1-01 should emit it (Q4).
- **Endpoint (BE-1):** add `[AllowAnonymous] [HttpPost("Register-Parent")]` to `AuthenticationController` → final route `POST /api/Users/Authentication/Register-Parent` (matches the FE contract base). `ProducesResponseType(typeof(BaseResponse<JwtAuthResponse>), 200)`.
- **Roles + seed (BE-2):** add `Parent`, `Student` to `Roles` enum; make role seeding idempotent (existence-checked) in `RoleSeeder`/`IdentitySeeder`. Seed both even though Student is parent-provisioned later (P1-03 needs the role to exist).
- **Validation (BE-3):** `RegisterParentCommandValidator : AbstractValidator<RegisterParentCommand>` — `Email` NotEmpty + `EmailAddress()` + unique (async check via `IUserManagmentService.FindByEmailAsync`); `Password` NotEmpty + policy regex matching the configured Identity policy (≥6, digit, upper, lower, non-alnum). Use `IStringLocalizer<SharedResources>` messages (mirror `SignInValidatior`). Validator auto-runs (ICommand) → 422 (AC-4, AC-6).
- **Guard (BE-5):** keep the command role-agnostic from the client; assign Parent server-side only. Confirm no other anonymous endpoint can create a Student. This is a code-review/authz assertion, not new runtime code.
- **Conventions:** return `BaseResponse<T>` via `BaseResponseHandler`; success flag spelled `Successed`; inject `ILoggerManager` (not `ILogger<T>`); no Unit of Work (Identity `CreateAsync` commits immediately). Follow FEATURE_PLAYBOOK / CODE_TEMPLATES.

## Handoff → frontend
Not in scope for this backend brief (FE is `P1-01-FE`, separate pipeline). Backend contract the FE depends on:
- `POST /api/Users/Authentication/Register-Parent` → `BaseResponse<JwtAuthResponse>`.
- `JwtAuthResponse` fields available: `AccessToken`, `refreshToken` (see Q2 — may be empty on register), `UserId`, `IsFirstLogin`, `SessionId`, `SessionTimeout`.
- Errors: 422 with `Errors[]` of `{ PropertyName, ErrorMessage }` for validation; business failures (duplicate email) come back as `BadRequest` `BaseResponse` with `Successed=false` + `Message`. **FE must map both shapes** — flag this inconsistency (Q5).

## Open questions / assumptions / risks
- **Q1 (input fields):** The FE register form (P1-01-FE) collects only **email, password, confirm** — but `User.FullName` is non-nullable and `UserName` is required by Identity. Options: (a) derive `UserName = Email`; (b) add a name field to the form; (c) default `FullName` to email local-part. **Recommend lead decide.** Assumption if unanswered: `UserName = Email`, `FullName = Email` placeholder until profile completion (P1 onboarding).
- **Q2 (refresh token on register — likely defect to mirror):** `AuthenticationService.GetJwtToken` returns **only** `AccessToken`; it does NOT populate `refreshToken` (only the `RefreshToken` flow does, and `ValidateDetails` reads refresh tokens from `IDistributedCache`, not the `UserRefreshToken` table). SignIn has the same behavior. So Register will return an empty `refreshToken`. The FE contract says "access + refresh token." **Decide:** ship parity-with-SignIn (access only) now, or extend issuance to mint+persist a refresh token. Recommend access-token-only for P1-01 to match existing behavior, and file a follow-up — do not silently diverge.
- **Q3 (role-name casing):** `RoleSeeder` seeds names `.ToLower()`; `UserSeeder` calls `AddToRoleAsync(user, Roles.Admin.ToString())` (PascalCase). Inconsistent. RegisterParent must use whatever casing the Parent role is actually seeded with, or role assignment silently fails. Recommend standardizing on the seeded (lower-case) name and asserting existence first.
- **Q4 (integration event):** Should parent registration publish `UserRegisteredIntegrationEvent` (as `AddUser` does)? If notifications/welcome flows should fire for parents, yes. Assumption if unanswered: publish it (best-effort, non-blocking) for consistency.
- **Q5 (error-shape consistency):** Validation errors return 422 with `Errors[]`; business errors (duplicate email via `BadRequest`) return a different shape (`Message`, empty `Errors`). FE needs both. Consider routing duplicate-email through the validator (async unique rule) so it also lands as 422 `Errors[]` — cleaner for the FE. Recommend: enforce uniqueness in the validator (422) AND keep the handler check as a race-safe backstop.
- **Risk — non-idempotent existing seeder:** retrofitting idempotency to `RoleSeeder` touches startup seeding for all roles; keep the change minimal and existence-checked to avoid regressing existing seed behavior.
- **Risk — security sensitivity:** anonymous endpoint that creates accounts + issues tokens. Enumeration risk (duplicate-email response reveals account existence), no rate-limiting/CAPTCHA mentioned, password handling. See security-auditor handoff.

## Handoff → api-tester (runs AFTER backend-feature)
This story exposes an HTTP endpoint → api-tester REQUIRED. Cover:
- 200 happy path: valid unique email + strong password → `Successed=true`, non-empty `AccessToken`, user has Parent role (assert via a follow-up authenticated call or DB).
- 422 weak password (each rule: too short, no digit, no upper, no lower, no non-alnum) → `Errors[]` populated.
- 422/400 duplicate email (register same email twice; also collide with seeded `basicuser@gmail.com`/`superadmin@gmail.com`).
- 422 invalid email format / empty fields.
- Response NEVER contains the password (assert no password field in body).
- No anonymous route creates a Student/Parent-other role (negative: command cannot escalate role via extra JSON fields).

## Handoff → security-auditor (audits BEFORE the reviewer gate)
Security-sensitive (auth, anonymous registration, password policy, child-account protection) → REQUIRED. Focus:
- Confirm role is server-assigned (Parent only); no client-controlled role/privilege escalation; no anonymous child/Student creation path (AC-2).
- Password never logged/returned; stored only as Identity hash (AC-5).
- Account-enumeration via distinct duplicate-email messaging — assess and recommend (generic message vs. UX).
- Missing anti-automation controls (rate limit / CAPTCHA / email verification) on an anonymous account-creating endpoint — flag severity + recommendation.
- Validator/Identity password policy alignment (no weaker path through the handler).
- Critical/High findings BLOCK the reviewer gate.
