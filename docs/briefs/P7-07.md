# Pipeline Brief — P7-07 Suspend, reactivate & delete accounts (Backend)

> Written by `analyzer` (2026-06-08). Backend-only brief for the Phase-7 Admin Console **User/Account wave**, story **P7-07**. Ground truth = the live **Identity** module on `feat/phase-7-backend`. Read-only audit; only the three brief files were written.

## Summary & traceability
- **One-line task:** Add an admin-driven account lifecycle (Active → Suspended → Reactivated; Active/Suspended → Deleted) on Identity accounts with typed confirmation + reason, **active-session revocation** on suspend, parent→children cascade, and best-effort integration-event fan-out so Learning / Gamification / Parent clean up their own state.
- **User story:** `user-stories/Phase-7-Admin-Console/P7-07-suspend-reactivate-delete-accounts.md`
- **BE task file:** `tasks/Backend/Phase-7-Admin-Console/P7-07-BE.md` (BE-1..BE-6)
- **FR / SRS:** **FR-ADM-6** (SRS §4.9), Admin role SRS §3.
- **BRD goal:** **G2** (trust & safety — abuse/policy enforcement, COPPA data-removal) + **G5** (operability).
- **Phase / epic:** Phase 7 — Admin Console · Epic: Admin — User & Account Management · SP 5.
- **Wave position:** second of the user/account wave (after P7-06; before/parallel to P7-08). Hangs its write endpoints on the same admin-users controller P7-06 establishes.

## Business context & value
- **Who benefits:** admin/support + the platform's safety posture. Protects children (suspend abusive accounts) and meets data-removal obligations (delete/anonymize).
- **Value:** a deliberate **governance** state machine distinct from the automatic P1-13 failed-login lockout — so support can intentionally block, restore, or erase accounts with an audit trail.
- **Success measure (from AC):** suspend flips status + actually stops the account from holding a valid token, reactivate restores, delete (two-step) anonymizes/removes and notifies other modules, every action records actor/timestamp/target/reason and is audited, and already-deleted accounts are rejected.

## Acceptance criteria (testable)
1. **Suspend:** `AccountStatus` → `Suspended`; **active sessions/tokens are revoked** (cannot sign in AND any issued access token stops validating); requires typed confirmation + a **reason**. Distinct from the P1-13 `LockoutEnd` mechanism (different field/lifecycle).
2. **Reactivate:** `Suspended` → `Active`; sign-in restored; prior reason/history retained and visible.
3. **Cascade:** suspending/deleting a **parent** warns about and can cascade to **linked children** (P1-04 family scope).
4. **Delete:** two-step confirm + reason; account removed/anonymized; other modules notified via integration events to clean their own data (no direct cross-module writes).
5. Every lifecycle action records **actor, timestamp, target, reason** and is **audited** (P7-12, publish-only this wave); suspending/deleting an **already-deleted** account → rejected with a clear message.
6. Non-admin → 403 / anonymous → 401. Endpoints `[Authorize(Policy = AuthorizationPolicies.AdminOnly)]` (already class-level on the admin controller).
7. Commands are `ICommand<>` → auto-validated (`ValidationBehavior`): reason required, confirm required for delete, status-transition legality enforced.

## Affected modules & data
- **Module:** `Identity` (owner) + integration-event **consumers** in `Learning`, `Gamification`, `Parent`. No new module.
- **Existing on disk (verified):**
  - `User` has `IsActive` (checked at sign-in: `SignInCommandHandler` returns "account deactivated" when `!IsActive`) and `IsDeleted`/`DeletedAt`/`DeletedBy` (soft-delete columns) — but **NO `AccountStatus` enum field** and **no reason/actor-of-last-status field**.
  - **Session/token model (LOAD-BEARING — verified):** JWT bearer is configured in `Identity.Infrastructure/DependencyInjection.cs` with a plain `TokenValidationParameters` and **NO `OnTokenValidated` / security-stamp / session re-validation hook**. Access tokens are **stateless and valid until expiry**; only sign-in checks `IsActive`. Refresh tokens live in Redis (`userrefreshtoken-{userId}`); `SessionManagementService` tracks sessions in `IDistributedCache` (Redis) keyed `user_sessions:{userId}` with `TerminateSessionAsync`. **There is currently no mechanism to invalidate an already-issued access JWT mid-flight** (this is the documented G2 follow-up). This directly constrains AC-1 "revoke active sessions" — see Q-B2.
  - `UserManagementController` already `AdminOnly` + has a `DeleteUser`/`DeleteUserCommand` (soft `IsDeleted`) — P7-07 lifecycle is richer (status + reason + cascade + events), so add new commands rather than overloading the existing delete.
- **Net-new:**
  - `AccountStatus` enum (Active / Suspended / Deleted) + `User.AccountStatus`, plus `LastStatusReason` (string?) and `StatusChangedBy` (int?) / `StatusChangedAtUtc` (DateTime?). Migration. Backfill existing rows → `Active` (DB `DEFAULT`), mirroring the curriculum wave's lifecycle backfill pattern.
  - `SuspendAccountCommand` / `ReactivateAccountCommand` / `DeleteAccountCommand` + handlers + validators.
  - Three integration events in `Shared.Contracts` (e.g. `AccountSuspendedIntegrationEvent`, `AccountReactivatedIntegrationEvent`, `AccountDeletedIntegrationEvent`) carrying only `StudentId/UserId` + minimal metadata (PII-free, mirroring `LearningLanguageChangedIntegrationEvent`).
  - Per-module consumers: `Learning`, `Gamification`, `Parent` `INotificationHandler`/integration-event handlers (each reacts in its own schema).
  - `AdminActions` constants for the three actions + `AdminActionPerformedEvent` publish.

## Handoff → db-migration
- Add to `User`: `AccountStatus` (int, NOT NULL, DB `DEFAULT` = Active), `LastStatusReason` (nullable string, bounded length — add `MaximumLength` in validator too), `StatusChangedBy` (nullable int), `StatusChangedAtUtc` (nullable timestamptz). Configure in `UserEntityConfig`.
- **Backfill:** existing rows → `Active`. Consider whether existing `IsActive == false` rows should map to `Suspended` (Q-B5) — recommend NOT auto-mapping (keep `IsActive` and `AccountStatus` orthogonal at first, or fold `IsActive` into `AccountStatus` — see Q-B6).
- Follow the curriculum wave's migration-naming convention (`P7_07_AddAccountStatus...`). Migrations are generated but applied only via `dotnet ef database update` / the deploy migrator (per HANDOFF load-bearing note) — do not assume auto-apply.
- **timestamptz/Npgsql note:** under `EnableLegacyTimestampBehavior=true`, persist `DateTime.UtcNow` and apply `.ToUniversalTime()` at mapping boundaries (per the P4-11 HANDOFF gotcha).

## Handoff → backend-feature
- **SuspendAccountCommand(int UserId, string Reason):** set `AccountStatus = Suspended`, stamp reason/actor/time, and **revoke sessions** — at minimum: (a) set `IsActive = false` so the next sign-in is blocked (existing check), (b) `SessionManagementService.TerminateSessionAsync` for the user's tracked sessions, (c) **invalidate the Redis refresh token** so the token can't be rotated. **Caveat:** none of these invalidate an already-issued ACCESS token before expiry — that needs the revocation hook in Q-B2. Validator: reason required + bounded; reject if already `Deleted`.
- **ReactivateAccountCommand(int UserId, string? Reason):** `Suspended → Active`, restore `IsActive = true`, keep prior reason in history. Reject if `Deleted` (deleted is terminal unless lead says otherwise — Q-B1).
- **DeleteAccountCommand(int UserId, string Reason, bool Confirm, bool? CascadeChildren):** two-step confirm gate (Confirm false/absent → BusinessValidation, mirror the P8-04 424/confirm pattern — confirm whether 424 or 400 here, Q-B7). For a **parent** with `CascadeChildren = true`, cascade to linked children — needs the parent→children-ids Parent seam (same gap as P7-06 BE-3). Multi-row write across parent + children → **explicit transaction** (no UoW). "Removed/anonymized" semantics pending Q-B1.
- **Events (BE-5):** publish `AccountSuspended/Reactivated/Deleted` **post-commit, best-effort** (mirror `PublishLearningLanguageChangedEventAsync`). Consumers: **Gamification** freezes/cleans XP/streak/league state; **Parent** updates family/linkage views; **Learning** cleans/locks learning state. Each consumer is isolated (own try/catch per ADR 0002 §3) and idempotent.
- **Audit (BE-6):** publish `AdminActionPerformedEvent` (new `AdminActions` constants) with actor (JWT), target id, action, reason in `Details`. Publish-only this wave; honor the tracked **pre-commit-publish** follow-up (the curriculum wave publishes before commit — for P7-07 prefer post-commit so a rolled-back lifecycle change doesn't emit a phantom audit/event; flag to planner whether to fix-forward here or stay consistent with the wave).
- **Conventions:** `ICommand<>` so validation fires; `BaseResponse<T>` / `Successed`; `NewResult(...)`; `ILoggerManager`; no `ex.Message` leakage.

## Handoff → frontend
- **Not in scope.** Later FE contract (`P7-07-FE`): `POST .../Users/{id}/suspend {reason}`, `POST .../Users/{id}/reactivate {reason?}`, `DELETE .../Users/{id} {reason, confirm, cascadeChildren?}`, all `BaseResponse<...>`, admin-gated, validated. Route prefix shared with P7-06 (Q-A8 in P7-06 brief).

## Open questions / assumptions / risks (for the lead)
- **Q-B1 (delete semantics) — DECISION REQUIRED:** does "delete account" mean **hard-delete**, **soft-delete/disable** (set `AccountStatus = Deleted`, keep the row), or **anonymize/GDPR-erase** (scrub PII, keep an anonymized shell + learning history)? The story says "removed/anonymized". **What happens to a deleted parent's linked children and their learning history?** The product rule is that grade transition preserves history — but account delete is a different axis. Sub-questions: does deleting a parent delete the children, orphan them, or just unlink? Does deleting a child purge its Math/Science/gamification history (vs. P8-04's scoped reset)? **Recommendation: soft-delete + anonymize PII by default (`AccountStatus = Deleted`, scrub email/name, retain anonymized learning aggregates); parent-delete defaults to unlink-not-delete-children unless `CascadeChildren` is set. Needs explicit lead sign-off given COPPA/child-data sensitivity.**
- **Q-B2 (session/token revocation) — DECISION REQUIRED (security-critical):** AC-1 requires suspend to "revoke active sessions … it can no longer hold a valid token." **Verified: there is NO per-request access-token revocation today** (no `OnTokenValidated` hook, no security-stamp check, no JWT blocklist; access tokens are valid until expiry — the known **G2** follow-up). Options: (a) accept the residual window — suspend blocks next sign-in + kills refresh token + terminates tracked sessions, but an already-issued access JWT survives until its (short) expiry; (b) implement real revocation now via an `OnTokenValidated` hook that checks `AccountStatus`/a security stamp on each request (broader auth change, affects every request, larger blast radius). **Recommendation: scope decision explicitly. If AC-1 "no valid token" is hard, this needs the revocation hook (b); if a bounded short-lived window is acceptable for MVP, ship (a) and document the residual window.** Do not silently ship (a) while the AC claims full revocation.
- **Q-B3 (suspend vs lockout precision):** confirm `AccountStatus.Suspended` is a separate field from P1-13 `LockoutEnd` (it is — keep them separate). Suspend must block sign-in regardless of lockout state and must NOT use the temporary `LockoutEnd` path. **Assumed locked per task file.**
- **Q-B4 (cascade granularity):** can children be **independently** suspended (a child account suspended without the parent), and does suspending a parent auto-suspend children or only offer the cascade? Does reactivating a parent reactivate cascaded children, or are they independent thereafter? **Recommendation: children independently suspendable; parent-suspend offers an explicit opt-in cascade; reactivation is per-account (no auto-reactivate of cascaded children).**
- **Q-B5 / Q-B6 (`IsActive` vs `AccountStatus` overlap):** `User.IsActive` already gates sign-in. Do we (B6) fold `IsActive` into `AccountStatus` (Active⇔IsActive=true) to avoid two sources of truth, or keep both with `AccountStatus` as the governance layer and `IsActive` as the mechanical gate? And (B5) do pre-existing `IsActive=false` rows backfill to `Suspended`? **Recommendation: keep `AccountStatus` authoritative for governance and derive/sync `IsActive` from it (suspend/delete set `IsActive=false`); backfill existing rows to `Active` and do NOT auto-map legacy `IsActive=false` to Suspended (those were deactivations, not admin suspensions) — but confirm.**
- **Q-B7 (confirm-gate status code):** P8-04 uses **424** for the unconfirmed destructive change. Should `DeleteAccountCommand` unconfirmed return **424** (consistent with P8-04) or **400/422**? **Recommendation: 424 for consistency.**
- **Q-B8 (event consumers exist?):** the three `Account*` events are net-new; **no consumers exist yet** in Learning/Gamification/Parent. Confirm scope: ship the events + at least the Parent (family view) consumer this story, and stub/document Gamification + Learning consumers, OR build all three. **Recommendation: ship events + Parent + Gamification consumers (they hold per-student state); Learning consumer can be a thin lock/no-op if delete semantics (Q-B1) defer learning-data purge.**
