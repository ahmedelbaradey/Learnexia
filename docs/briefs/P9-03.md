# Pipeline Brief — P9-03: Spend energy on AI help (charge-on-delivery)

> **Phase 9 credit economy — the demand side + the AI-gateway integration.** Energy is debited **on successful delivery** of an AI Helper response (after the safety filter), never on request, never on a refusal/error, and never on insufficient balance. This story **wires the P9-01 atomic debit into the AI Gateway (P3-01)** and **replaces the AI-Helper MVP daily-request guardrail** (`ai-cost-routing.md §6` / `ai-helper-mvp.md`). It is the **most security-sensitive story in the cluster** — spend integrity (no charge without delivery, no double-charge, no client-controlled cost) is a hard gate. **Read `docs/briefs/P9-01.md`, `docs/briefs/P3-01.md`, `docs/briefs/ai-cost-routing.md`, and `docs/briefs/ai-helper-mvp.md` before any code.**

## Summary & traceability

- **Task (1 line):** Charge a child's energy **on successful delivery** of an AI Helper response — per-action cost (config-driven: hint = 1, explain-mistake = 3, deep-explanation = 5, practice-generation = 5), debited **after** the safety filter passes and the response is produced (live **or** cache-hit, charged the **same**), with **no charge** on refuse-and-redirect / error / insufficient balance, where **debit + delivery are atomic** (no charge without delivery; no delivery — when balance suffices — without charge) and insufficient balance degrades gracefully (low-energy message P9-04 + cached canned explanation) — **never blocking learning** — by wiring P9-01's `ICreditSpendService` into the **AI Gateway (P3-01)** and **removing** the MVP daily-request cap guardrail.

- **BRD goal:** **G5** (the spend side closes the cost loop — energy charged ≈ AI runtime cost, keeping the 199 EGP plan viable) + **G1/G2** (charge-on-delivery + never-block-learning protect the learning experience: a child is never charged for a refusal and never hard-stopped from getting help).

## Business context & value

- **Who benefits:** the **business** (energy spent maps to AI runtime cost — this is the meter that makes per-student AI economics work, `ai-cost-routing.md §1`), the **child** (charge-on-delivery means they're never charged for a refusal/error, and insufficient balance never produces a dead end — they still get cached help), and the **parent** (predictable, fair consumption they can see in billing history later, P9-08).
- **Charge-on-delivery (lead-confirmed):** the child pays for **value received**, not for asking. A refusal (out-of-scope → refuse-and-redirect, `ai-helper-mvp.md §4`), a provider error, or an empty-context decline costs **nothing**. This is both fair and abuse-resistant (you can't drain a child's energy by spamming out-of-scope requests — they're rejected free, before the gateway).
- **Cache-hit charged the same (lead-confirmed):** a cached response costs the child the same as a live one. Predictability for the child (cost doesn't depend on invisible cache state) and **margin for the business** (cache hits cost ~$0 to serve but still charge — this is the profit lever in `ai-cost-routing.md`). The child cannot tell, and shouldn't have to.
- **Never block learning (hard AC):** insufficient balance does **not** error or hard-stop. The Helper declines gracefully (low-energy copy, P9-04) and serves a cached canned explanation when one exists. This preserves the AI-Helper MVP invariant ("never return a hard error to the student — degrade to cache") and FR-AI-6 (AI/economy never gates progression).
- **Replaces the MVP guardrail:** `ai-cost-routing.md §6` and `P3-01.md` explicitly scope the daily-request count cap as a temporary cost-safety guardrail that **Phase 9 supersedes**. P9-03 removes that `IAiUsageBudget` daily-count check from the gateway hot path and replaces it with the credit debit. **This is a deliberate teardown — coordinate with whoever owns the P3-01 gateway code.**
- **Success measure (from AC):** correct per-action cost charged on delivery; cache-hit charged same; no charge on refuse/error/insufficient; insufficient → graceful decline + cached canned response; debit+delivery atomic.

## Current-state findings (reality in code)

1. **The AI Gateway (P3-01) is NOT built** — no `Ai` module exists (modules: Identity, Catalog, Learning, Gamification, Parent, Moderation, Notifications). So both the **gateway seam** and the **MVP daily-cap guardrail** P9-03 is meant to wire into / replace **do not exist yet**. P9-03 is **hard-blocked on P3-01** delivering `IAiGateway` + the Helper handlers (P3-04/05/06) + the `IAiUsageBudget` guardrail it replaces. **This is the dominant sequencing risk.**
2. **P9-01 supplies the debit primitive** — `ICreditSpendService.TryDebitAsync(childId, amount, reasonCode, idempotencyKey, CT)` (defined in `Shared.Contracts/Billing` per the P9-01 handoff), atomic Granted-first, idempotent. The `Ai` module consumes this contract **without referencing `Billing` projects** (module isolation rule 1).
3. **The charge-on-delivery ordering is the crux:** per `ai-helper-mvp.md §4` and `ai-cost-routing.md`, the gateway pipeline is `scope-guard → cache lookup / LLM call → safety filter → deliver`. The debit must sit **after** "response produced and safety-filter passed" and **before/at** delivery, atomically. A pre-check ("does the child have ≥ cost?") gates *whether to attempt*, but the actual debit happens at delivery so an error/refusal after the pre-check still costs nothing.
4. **Idempotency key for spend** is the AI request id / Helper action id (one debit per delivered response). Mirrors P9-01's DB-unique-key dedupe — a retried delivery must not double-charge.
5. **Per-action cost is config (P9-11)** — the gateway/Helper resolves cost from the `BillingConfig` store keyed by action kind, **server-side**. The client never sends a cost. (Critical security invariant — see security-auditor.)

## Acceptance criteria (testable)

1. **AC-1 (per-action cost, config-driven):** Charge hint = 1, explain-mistake = 3, deep-explanation = 5, practice-generation = 5 — **resolved from P9-11 config by action kind, server-side**. Changing the config changes the cost without redeploy.
2. **AC-2 (charge on delivery, not request):** The debit fires **only after** the response is produced and the safety filter passes, at delivery — **never** at request receipt.
3. **AC-3 (cache-hit charged same):** A cache-hit response charges the same per-action cost as a live LLM response. No discount, no surcharge, indistinguishable to the child.
4. **AC-4 (no charge on refuse / error / insufficient):** A refuse-and-redirect (out-of-scope / no-context decline), a provider/processing error, or insufficient balance results in **zero** debit — **no ledger row written.**
5. **AC-5 (insufficient → graceful, never block):** Insufficient balance → the Helper declines with the low-energy message (P9-04) **and** serves a cached canned explanation when available; learning is never hard-blocked, no raw error surfaces.
6. **AC-6 (atomic debit + delivery):** No charge without delivery, and no delivery (when balance suffices) without charge — the debit and the response-return are coupled so a crash between them cannot leave one without the other (see OQ-2 for the exact coupling mechanism).
7. **AC-7 (replaces MVP guardrail):** The P3-01 `IAiUsageBudget` daily-request-count check is removed from the runtime gateway path; the credit debit is the sole runtime cost gate.

## Handoff → backend-feature

- **Spend-on-delivery wiring (the core change):** in the Helper response pipeline (gateway facade or P3-04/05/06 handlers), after the response is produced and the safety filter passes:
  1. Build idempotency key = the AI request/action id (one charge per delivered response).
  2. Resolve cost = P9-11 config lookup by action kind (server-side; never a client value).
  3. Call `ICreditSpendService.TryDebitAsync(childId, cost, reasonCode, idempotencyKey, CT)`.
  4. Couple debit and delivery (OQ-2): **recommended order** = produce response → safety-pass → debit → on debit success return response; on `InsufficientBalance` (shouldn't happen if the pre-check passed, but possible under a race) → return graceful-decline + cached canned response **without** charging.
- **Pre-check + graceful decline (AC-5):** before attempting an LLM/cache call, read balance via `GetBalanceAsync`; if `< cost`, **short-circuit to the graceful low-energy decline** (P9-04 copy) and serve a cached canned explanation if available — **no gateway call, no debit, no error.** This is the same "degrade to cache" branch the MVP guardrail used; reuse that branch, swap the trigger from daily-count-exhausted to insufficient-credit.
- **No charge on refuse/error (AC-4):** ensure the debit is unreachable on the refuse-and-redirect path (`ai-helper-mvp.md §4` — empty context decline) and on any exception/error path. The debit is the **last** step of a successful delivery, so an earlier branch never charges. **Test this explicitly.**
- **Cache-hit charged same (AC-3):** the debit step runs identically whether the response came from cache or the LLM — it is downstream of the cache/LLM fork. Do not special-case cache.
- **Remove the MVP guardrail (AC-7):** delete/disable the `IAiUsageBudget` daily-count check in the runtime gateway path. Keep any usage *logging* (analytics) but remove the *gating*. Coordinate with the P3-01 owner so the teardown is clean (the guardrail's "degrade to cache on exhaustion" branch is **repurposed**, not deleted — it's now the insufficient-credit branch).
- **Conventions:** `BaseResponse<T>` / `Successed`; `ILoggerManager`; the `Ai` module consumes `ICreditSpendService` via `Shared.Contracts` only (no `Billing` project ref); no UoW (the atomicity is inside P9-01's `TryDebitAsync` explicit transaction — P9-03 does not open its own).

## Handoff → security-auditor (MANDATORY HARD GATE — spend integrity)

**This is a security-sensitive batch (money/credit movement + child data + AI path). Critical/High findings block the gate.** Audit:
- **Server-controlled cost (CRITICAL):** the per-action cost MUST be resolved server-side from P9-11 config keyed by a server-determined action kind. The client must **not** be able to send/influence the cost or the action kind in a way that lowers the charge. A client-supplied cost = an economy bypass.
- **No charge without delivery / no double-charge:** confirm the debit fires only on the successful-delivery path and that the idempotency key prevents a retried delivery from charging twice (P9-01's DB-unique key). Confirm a crash between debit and return cannot double-charge on retry (idempotent) nor charge-without-deliver (OQ-2 coupling).
- **No charge on refuse/error/insufficient (AC-4):** verify there is **no** code path where a refuse-and-redirect, an exception, or an insufficient-balance branch reaches the debit. This is the fairness invariant and a direct AC.
- **No energy drain via spam:** out-of-scope requests are rejected free (by the P3-02 scope guard, before the gateway). Confirm an attacker can't force charges by replaying or racing requests (idempotency + the refuse-free rule cover this).
- **Insufficient never errors:** verify the insufficient path degrades to cache + low-energy copy, never a 500/stack trace, never a hard block (AC-5 — also a learning-integrity invariant per FR-AI-6).
- **Child id is server-derived:** the `childId` for the debit comes from the authenticated session, never a client-supplied id (a child must not be able to spend another child's energy). Confirm.
- **No PII / no prompt text** persisted in the `Spend` ledger row (P9-01 invariant — re-confirm at the spend call site).

- Cross-child guard: a request authenticated as child A cannot debit child B.
- Guardrail removed: the old daily-request-count cap no longer blocks at high request volume (only credit balance does).

## Open questions for the lead

- **OQ-1 (BLOCKER — cross-cluster sequencing):** P9-03 hard-depends on P3-01 + the AI Helper handlers (P3-04/05/06), none of which are built. Confirm the sequencing: is the AI Helper cluster delivered before P9-03, and who owns the gateway code P9-03 modifies? **Recommend P9-03 is scheduled after the P3-* Helper is merged**; until then it cannot be implemented (only its P9-01 dependency can).
- **OQ-2 (debit↔delivery coupling mechanism):** how exactly are debit and delivery made atomic given the LLM call sits between them? Options: (a) **debit last** — produce + safety-pass → debit → return (on rare post-debit failure, the response is still returned; the charge stands because value was delivered); (b) reserve-then-confirm (hold credit before the call, confirm on delivery, release on failure — more complex). **Recommend (a) debit-as-the-final-delivery-step** with the idempotency key making retries safe — simplest, and a post-debit return failure is acceptable (value was produced). Confirm.
- **OQ-3 (intent→action-cost mapping):** the story names costs for *hint / explain-mistake / deep-explanation / practice-generation*; the AI-Helper MVP has intents *Explain / Hint / WhyWrong / SimilarExample*. Map them: Hint→1, WhyWrong→3 ("explain-mistake"), Explain(concept)→5 ("deep-explanation"), SimilarExample→5 ("practice-generation")? **Recommend that mapping** — confirm with the lead/content team; it drives every charge.
- **OQ-4 (guardrail teardown ownership):** removing the P3-01 `IAiUsageBudget` daily-count gate touches P3-01-owned code. Who makes that edit — the P9-03 implementer or the P3-01 owner? **Recommend the P9-03 implementer**, coordinated, since it's a coherent swap (guardrail out, credit in; degrade-to-cache branch repurposed). Confirm to avoid two agents editing the gateway.
- **OQ-5 (insufficient pre-check vs debit-fail race):** if the cheap pre-check passes but a concurrent spend drains the balance before this debit, `TryDebitAsync` returns `InsufficientBalance` at delivery time. Confirm the desired behavior: **serve the response anyway for free, or fall back to the graceful decline?** **Recommend the graceful decline** (consistent with "no delivery without charge when balance suffices" — here it no longer suffices) — but this is an edge UX call. Flag.
- **OQ-6 (free actions / first-help-free?):** are any AI actions free (e.g. the first hint), or is everything charged? The story implies all four are charged. **Recommend all-charged for MVP**; confirm no free-tier carve-outs are expected.

### Risks (top 3)
- **R1 — cross-cluster block on P3-01/Helper** (doesn't exist yet) stalls P9-03. **Mitigation:** schedule P9-03 after the P3-* Helper; build P9-01 + P9-04 + P9-11 first so only the thin wiring remains.
