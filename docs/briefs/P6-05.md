# Pipeline Brief — P6-05 Observability (logging, tracing, health checks, metrics)

## Summary & traceability
- **Task (one line):** Wire OpenTelemetry tracing + metrics (OTLP exporter, **config-gated** / no-op when unset), add an **AI-Gateway readiness health check**, configure **NLog targets + trace-id/span-id correlation**, and document the **dashboard/alerts-are-devops** boundary on top of the existing P5-03 admin analytics endpoints.
- **User story:** [user-stories/Phase-6-Stabilization/P6-05-observability.md](../../user-stories/Phase-6-Stabilization/P6-05-observability.md) — "As an operator, I want logging, tracing, health checks, and KPI dashboards in place, so that I can monitor uptime and learning KPIs once we launch."
- **Task file:** [tasks/Backend/Phase-6-Stabilization/P6-05-BE.md](../../tasks/Backend/Phase-6-Stabilization/P6-05-BE.md) (6 tasks: BE-1 OTel, BE-2 AI-gateway health check, BE-3 NLog correlation, BE-4 docs boundary, BE-5 api-tester, BE-6 reviewer).
- **Requirements:** NFR-3 (99.5% availability), FR-PA-3 (parent/admin analytics). Epic: DevOps / Observability. Covers O2.1 + O2.2.
- **Phase/sprint:** Phase 6 — Stabilization (Week 9). **SP: 3.**
- **Chosen approach (DECIDED by the lead — do NOT re-open):** OTLP exporter, **config-gated** — wire OTel tracing + metrics exporting via OTLP to a configurable endpoint, NO-OP when `OpenTelemetry:Otlp:Endpoint` is unset (mirrors the codebase's Redis-when-present / AI flip-to-live pattern). The Grafana dashboard + alerts are **devops**, not backend code in this story.
- **Scope:** Host (`Learnexia.Host`) + one **read-only AI-readiness seam** in `Shared.Contracts`/`Shared.Kernel`. **No new module, no DB migration, no new NuGet** (OTel + health-check packages already centrally versioned).

## Business context & value
- **Who benefits:** Operators/devops (uptime + KPI monitoring at launch), Admins (the P5-03 KPI dashboard the analytics endpoints feed), and indirectly all users (faster incident detection → the 99.5% NFR-3 availability target).
- **Value:** Today the platform is observability-blind — NLog has **no configured targets** (logs go nowhere), there is **zero OpenTelemetry wiring** (no distributed traces/metrics), and the readiness probe cannot tell whether the AI Tutor dependency is configured. This story closes those gaps so a launch can be monitored and an SLO defended.
- **Success measure:** `/health` reports DB + Redis + **AI-Gateway** status; traces+metrics flow to an OTLP collector when one is configured (and the app runs unchanged when none is); logs carry `traceId`/`spanId` so logs join traces; the existing P5-03 KPI endpoints remain the dashboard data source.

## Acceptance criteria (testable)
Mapped to the story's four ACs:

1. **AC-1 — NLog targets + OTel tracing wired (was "referenced but unused").**
   - `nlog.config` exists at the Host with concrete targets (at minimum console + rolling file) and is loaded at startup. (Today there is **no `nlog.config` at all** — see Verification.)
   - `AddOpenTelemetry().WithTracing(...).WithMetrics(...)` is wired in `Program.cs` with ASP.NET Core + HttpClient + Runtime instrumentation and a `Resource` (service name/version/env). (Npgsql/EF instrumentation: see Open Question.)
   - The OTLP exporter is registered **only when `OpenTelemetry:Otlp:Endpoint` is configured**; with no endpoint the app starts and runs with zero behaviour change (local dev + the integration suite run with no collector).
   - Each log line carries the active `traceId`/`spanId` (and request path/status where available) so NLog logs correlate with OTel traces. No second `ILoggerManager` registration (CONVENTIONS §11; CLAUDE rule #5).

2. **AC-2 — Health-check endpoints report API + DB + Redis + AI Gateway.**
   - `/health/live` → always 200 (unchanged).
   - `/health` → readiness; reports entries for `database` (hard-fail → 503), `redis` (Degraded-tolerant, only when configured), and a **new `ai-gateway` entry** (config-readiness; **Degraded-tolerant**, never a hard 503).
   - The AI-gateway check reports **configuration readiness only** (provider selected + provider API key present + RAG/TEI endpoint configured) and **makes NO paid live model call** and requires **no real keys** in CI/dev.

3. **AC-3 — KPI/analytics dashboard surfaces P5-03 events (DAU/WAU, accuracy, retention).**
   - No new product endpoint. The backend already exposes the data via `GET api/Admin/Analytics/kpis` (and `/notifications`); the **dashboard + alerts are devops** (Grafana/Tempo/Prometheus on the OTLP stream + those endpoints).
   - HANDOFF documents the boundary, the OTLP env vars, and that `/health` is the 99.5%-uptime probe.

4. **AC-4 — Visible signal for the 99.5% uptime target.**
   - OTel metrics (request rate/latency/errors via ASP.NET Core instrumentation) export over OTLP when an endpoint is set; `/health` is the orchestrator/uptime probe. Alerts themselves are devops.

Cross-cutting:
- **Security:** no secrets/PII (child names, emails, tokens, prompts/responses, connection-string passwords, API keys) emitted into spans, metrics, or logs. `/health` body must not leak passwords or stack traces (already covered by an existing test — keep it green).
- **No regression:** the full integration suite (env `Testing`, no Redis, no OTLP endpoint) passes unchanged.

## Handoff → backend-feature

### BE-1 — Wire OpenTelemetry (tracing + metrics), OTLP config-gated
- **File:** `src/Host/Learnexia.Host/Program.cs` (+ a small `OpenTelemetrySettings` class; recommend `src/Host/Learnexia.Host/SystemConfiguration/` next to `SystemConfigurationOptions`).
- **Packages (add `PackageReference` to `Host.csproj`; versions are already in `Directory.Packages.props`):**
  - `OpenTelemetry.Extensions.Hosting` 1.11.2
  - `OpenTelemetry.Exporter.OpenTelemetryProtocol` 1.11.2
  - `OpenTelemetry.Instrumentation.AspNetCore` 1.11.1
  - `OpenTelemetry.Instrumentation.Http` 1.11.1
  - `OpenTelemetry.Instrumentation.Runtime` 1.11.1
- **Settings POCO** bound from `OpenTelemetry` config section:
  - `Otlp:Endpoint` (string, default empty → **gate**), `ServiceName` (default "Learnexia"), `SamplingRatio` (double, default 1.0 — see Open Question on default).
- **Shape (config-gated, mirrors the Redis block at `Program.cs` lines 63–81):**
  ```
  var otlpEndpoint = builder.Configuration["OpenTelemetry:Otlp:Endpoint"];
  builder.Services.AddOpenTelemetry()
      .ConfigureResource(r => r.AddService(serviceName, serviceVersion: ..., ...))   // + deployment.environment
      .WithTracing(t => {
          t.AddAspNetCoreInstrumentation();
          t.AddHttpClientInstrumentation();
          // optional Npgsql/EF instrumentation — see Open Question
          t.SetSampler(...);                                  // ratio from settings (default 1.0)
          if (!string.IsNullOrWhiteSpace(otlpEndpoint)) t.AddOtlpExporter(o => o.Endpoint = new Uri(otlpEndpoint));
      })
      .WithMetrics(m => {
          m.AddAspNetCoreInstrumentation();
          m.AddHttpClientInstrumentation();
          m.AddRuntimeInstrumentation();
          if (!string.IsNullOrWhiteSpace(otlpEndpoint)) m.AddOtlpExporter(o => o.Endpoint = new Uri(otlpEndpoint));
      });
  ```
  - **Critical:** the OTLP exporter must be registered **only** when `Otlp:Endpoint` is non-empty. With it absent, OTel runs (collects in-process, no export) and the app starts normally — the integration suite (env `Testing`) and local dev have no collector. Place the registration anywhere before `builder.Build()`; the Redis block (lines 63–81) is the precedent for the config-gate idiom.
  - **ASP.NET Core instrumentation must filter health probes** (`/health`, `/health/live`) out of traces/metrics to avoid noise — use the instrumentation `Filter`.
  - **Secret/PII guard:** do NOT enable request/response body capture; do NOT add header enrichment that could carry `Authorization`. Default instrumentation is span-name + route + status only — keep it that way.

### BE-2 — AI-Gateway readiness health check (+ read-only seam)
- **The "AI is configured" signal (VERIFIED against `AiModule.InitializeAsync`):**
  - **Provider key present:** `Ai:Providers:Claude:ApiKey` non-empty (and/or `Ai:Providers:OpenAi:ApiKey`). Keys are NOT in `AiGatewayOptions` — they live at these config paths (env/secret only).
  - **Default provider:** `Ai:Gateway:DefaultProvider` (default "Claude").
  - **RAG/TEI readiness (optional dimension):** `AiHelper:ContextProvider == "Rag"` AND `Curriculum:Embedding:BaseUrl` set AND `Curriculum:Embedding:ModelVersion` set. When `ContextProvider` is absent/non-Rag, RAG is intentionally dormant (`EmptyLearningContextProvider`) — that is a **healthy/degraded-info** state, **not** Unhealthy.
- **Recommended seam (cleanest, mirrors `IAiSafetyEvalResultsQuery`):**
  - New interface in `src/Shared/Learnexia.Shared.Contracts/Ai/` — e.g. `IAiReadinessProbe` returning a small record, e.g. `AiReadinessStatus(bool ProviderConfigured, string DefaultProvider, bool RagConfigured)`. **The record carries booleans/enum only — never key values.**
  - Implemented in `src/Modules/Ai/Learnexia.Modules.Ai.Infrastructure/` (e.g. `AiReadinessProbe`), reading `IConfiguration` for the keys above; registered **Scoped** in `AddAiInfrastructure` (next to the other read-seam registrations at `DependencyInjection.cs` lines 88–96). It does **NOT** call `IAiGateway.CompleteAsync`/`StreamAsync` — config inspection only, so no cost, no live key needed.
- **Health check (lives in the Host — it's a Host concern):**
  - New `AiGatewayHealthCheck : IHealthCheck` in `src/Host/Learnexia.Host/` (e.g. a `HealthChecks/` folder). It resolves `IAiReadinessProbe` and maps:
    - provider configured → `Healthy`;
    - provider NOT configured → **`Degraded`** (AI Tutor dormant, but the platform is up — NOT a hard 503). Use `failureStatus: HealthStatus.Degraded`, matching the Redis registration at `Program.cs` line 103.
  - Register in `Program.cs` alongside the existing checks: `healthChecks.AddCheck<AiGatewayHealthCheck>("ai-gateway", failureStatus: HealthStatus.Degraded, tags: ["ready"])`. Add it whether or not keys are present (the check itself reports the state).
  - **Why the Host can do this without breaking module isolation:** the Host already references `Shared.Contracts` (`Host.csproj` line 26) and injects the seam interface only — never an Ai-module internal type. `AiModule.InitializeAsync` already reads exactly these keys at startup, so the readiness logic is a proven, key-value-free pattern.
  - **Degraded does not fail `/health`:** ASP.NET Core maps Degraded → 200, Unhealthy → 503 (confirmed by the existing Redis-degraded test AC-2e). So an unconfigured AI Tutor must never 503 the readiness probe.

### BE-3 — NLog targets + trace correlation
- **VERIFIED current state — this is bigger than "extend":** there is **NO `nlog.config` anywhere in the repo** (CONVENTIONS §13 confirms: *"No `nlog.config` — NLog has no targets; logs may go nowhere"*). `LoggerManager` uses `LogManager.GetCurrentClassLogger()` with NLog's default (unconfigured) behaviour; `AddLoggerServices` only registers the `ILoggerManager` singleton. So BE-3 must **create `nlog.config` from scratch**, not merely add a layout.
- **Files:** new `src/Host/Learnexia.Host/nlog.config` (mark `CopyToOutputDirectory`). Ensure NLog loads it — NLog auto-discovers `nlog.config` in the app base dir, so no programmatic load is strictly required, but confirm at startup.
- **Targets:** at minimum a `ColoredConsole` target and a rolling `File` target. An OTLP/JSON log target is **optional/deferred** (see Open Question BE-3).
- **Correlation:** include `traceId`/`spanId` in the layout. With OTel wired, `System.Diagnostics.Activity.Current` carries `TraceId`/`SpanId`. Use NLog's `${activity:property=TraceId}` / `${activity:property=SpanId}` layout renderers (or `${aspnet-traceidentifier}`) so every line joins the trace. Add request path/status where available.
- **CONVENTIONS §11 / CLAUDE rule #5 (HARD):** inject `ILoggerManager`, not `ILogger<T>`. Do **not** add a second/third logger registration — there is already a known duplicate `ILoggerManager` (Singleton in `AddLoggerServices` + Singleton in `AddAiInfrastructure`); do not add another. BE-3 changes **config**, not registrations.
- **Depends on BE-1** (the `Activity` ambient state that the layout reads is established by OTel's ActivitySource/instrumentation).

### BE-4 — Dashboard/alerts boundary + uptime signal (docs only)
- **No code, no new endpoint.** Document in `docs/dev/HANDOFF.md`:
  - The KPI/uptime **dashboard + alerts are devops** (Grafana/Tempo/Prometheus on the OTLP stream + the existing admin analytics endpoints).
  - **The real endpoints that already surface DAU/WAU/accuracy/retention (VERIFIED):**
    - `GET api/Admin/Analytics/kpis?from=&to=` — `AdminAnalyticsController` (`[Authorize(AdminOnly)]`, route `api/Admin/Analytics`). Returns `PlatformKpiSummaryDto`: Learning (`lessonsCompleted`, `totalAttempts`, `distinctActiveStudents` = DAU/WAU/MAU activity proxy, subject/grade breakdowns), Engagement (`missionsCompleted`, `xpEarnedInWindow`), Subscriptions, AI safety counts, and **session duration + retention** (`AvgSessionDurationSeconds`, `AvgActiveDaysPerStudent`, `ReturningStudentRate`) sourced from the P5-03 analytics backbone via `IPlatformAnalyticsQuery`.
    - `GET api/Admin/Analytics/notifications?from=&to=&category=` — notification lifecycle aggregates.
  - **`/health` is the 99.5%-uptime probe** for the orchestrator/uptime monitor.
  - **OTLP/observability env vars for devops:** `OpenTelemetry__Otlp__Endpoint`, `OpenTelemetry__ServiceName`, `OpenTelemetry__SamplingRatio` (final names per BE-1's settings POCO). Note the no-op-when-unset behaviour.
- **Depends on BE-1, BE-2.**

## Open questions / assumptions / risks

### Open questions for the lead (decide before/at planning)
1. **OTel sampling default (BE-1).** Task file recommends a configurable ratio defaulting to **1.0** (always-on; devops tunes down via `OpenTelemetry:SamplingRatio`). Confirm 1.0 default, or prefer a parent-based always-on sampler? **Recommendation: configurable ratio, default 1.0** — simplest, devops dials back in prod.
2. **MinIO readiness check — yes/no (BE-2).** Story AC names only "API, DB, Redis, AI Gateway" (no storage). MinIO is wired (`AddMinIODependencies`, `MinIOConfiguration` with `Enabled` flag, `IStorageService` in Shared.Kernel). Task file recommends adding it (cheap). **Recommendation: add a Degraded-tolerant `minio` check only if it's a quick `BucketExists`/liveness probe gated on `MinIOConfiguration:Enabled`** — but it is **beyond the story AC**, so flag for explicit lead go/no-go. Defer if it risks scope creep.
3. **OTLP-log target now vs deferred (BE-3).** Add an OTLP/JSON **log** exporter target in `nlog.config` this pass, or ship console+file+trace-correlation now and let the collector scrape file logs (logs via traces+metrics this pass)? **Recommendation: correlation + console/file now; OTLP-log target deferred** (devops can scrape or add later) — matches the task file.
4. **Npgsql/EF tracing instrumentation (BE-1).** The task file names "Npgsql instrumentation," but no `OpenTelemetry.Instrumentation.*Npgsql*`/EFCore package is in `Directory.Packages.props` (only AspNetCore/Http/Runtime). Adding DB tracing would require a **new NuGet**, which the story explicitly forbids ("no new NuGet"). **Recommendation: ship ASP.NET Core + HttpClient + Runtime instrumentation only this pass; treat Npgsql/EF tracing as a deferred follow-up** (it also needs a config-driven decision on capturing SQL text vs PII). Confirm.
5. **Health response writer.** The existing probes use ASP.NET Core's default (text) writer. Scenario 3 (assert per-dependency entries incl. `ai-gateway`) is easiest with a small JSON `ResponseWriter` on `/health`. Add a JSON writer (recommended — better for devops/uptime tooling and clean api-tester assertions) or keep the default text writer and assert on substrings? **Recommendation: add a minimal JSON writer that emits status + per-check name/status only (no exception/description, to avoid PII/secret leakage).**

### Assumptions
- The 5 OTel packages at the listed versions (1.11.2 / 1.11.1) are .NET 10 compatible (they target net8.0+ and resolve via fallback, consistent with how Pgvector/EFCore resolve in this repo). If any fails to restore on net10.0, raise it — but this is the only realistic build risk and it is a pinned, already-curated set.
- `Activity.Current` is populated by the OTel ASP.NET Core instrumentation, so NLog's `${activity}` renderer has data on request-scoped log lines (BE-3 depends on BE-1).
- The integration suite never sets `OpenTelemetry:Otlp:Endpoint`, so the no-op path is the default tested path.

### Risks
- **Startup regression:** any OTel mis-wire that throws at `builder.Build()` breaks every integration test (the WebAppFactory boots the full host). Mitigate by strict config-gating and running the full suite (BE-5/BE-6).
- **PII/secret leakage in telemetry:** the single highest-risk area. Span attributes, metric tags, and the health-response body must never carry tokens, API keys, child names/emails, prompts/responses, or connection-string passwords. Reviewer (BE-6) must check this explicitly; the existing leak test must stay green and be extended for API keys.
- **Module isolation:** the AI seam must be the only cross-module touch and must expose booleans/enums only (no key values). Host must inject the `Shared.Contracts` interface, not an Ai-module type.
