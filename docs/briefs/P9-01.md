# Pipeline Brief — P9-01: Credit (energy) account & append-only ledger

> **Phase 9 credit-economy FOUNDATION.** This is the first brick of the Phase 9 credit economy — `CreditAccount` (dual-pool balance) + an append-only `CreditTransaction` ledger with DB-enforced idempotency. **P9-02 (monthly grant), P9-03 (spend on AI), P9-04 (daily soft cap)** all hard-depend on the entities and the atomic-debit primitive defined here. It **promotes the MVP daily-request guardrail** described in `docs/briefs/ai-cost-routing.md §6` (which explicitly defers the full ledger to Phase 9) into a first-class accounting system. **Two blocking module/schema decisions must be resolved by the lead before any migration — see Open Questions OQ-1/OQ-2.**

## Summary & traceability

- **Task (1 line):** Stand up a per-child **`CreditAccount`** carrying **two balances** — `GrantedBalance` (perishable, expires monthly) and `PurchasedBalance` (never expires) — backed by an **append-only `CreditTransaction` ledger** (Grant / Spend / Purchase / Expire / Refund / Adjustment) where balance is always reconstructable as `sum(ledger)`, every row carries an **idempotency key** (DB unique constraint), and a single atomic primitive (`DebitAsync`) draws **Granted-before-Purchased** under an explicit transaction — so that every credit movement is auditable, reconciliation can detect drift, and no double-grant / double-spend is possible.

## Business context & value

- **Who benefits:** the **business/operator** directly (auditable, tamper-resistant accounting is the basis of any monetization + every dispute/refund investigation), the **parent** indirectly (their plan funds the child's energy; billing trust depends on an accurate ledger), and the **child** indirectly (the meter they see in P9-10 is `GrantedBalance + PurchasedBalance` off this account).
- **Parent-driven monetization (hard constraint):** the account **belongs to the child** but is **funded by the parent's plan/purchases**. There is **no purchase or payment surface in the student app** — the child only **spends** (P9-03) and **reads** the meter (P9-10). All grant/purchase/refund writes originate parent-side or from the scheduled grant job. The ledger is the shared truth both sides read.
- **Why a ledger and not a mutable counter:** a bare `balance` integer is unauditable and corrupts silently under concurrency. An append-only ledger makes every movement explainable (who/when/why/resulting-balance), supports reconciliation (`balance == sum(ledger)`), and is the only defensible basis for refunds and disputes. This mirrors the **already-shipped `XpAward` append-only ledger** in Gamification (DB-unique idempotency key, `FullAuditedEntity`, no mutation methods) — the project pattern exists; this story applies it to credits.
- **Success measure (from AC):** (1) every child has a `CreditAccount` with the two balances; (2) every change is an append-only `CreditTransaction` with type/amount/reason/resulting-balance/UTC/idempotency-key; (3) `account.balance == sum(ledger)` holds and a reconciliation check can detect drift; (4) spends draw Granted-first; (5) lives in the agreed module/schema with the child as a loose id reference (no cross-module FK).

## Acceptance criteria (testable)

1. **AC-1 (account + dual pool):** A `CreditAccount` entity exists per child with `GrantedBalance` (int ≥ 0) and `PurchasedBalance` (int ≥ 0); `TotalBalance` is a derived read (`Granted + Purchased`). One account per child (OQ-3 — per-child vs shared family pool).
2. **AC-2 (append-only ledger):** Every balance change is an append-only `CreditTransaction` row carrying: `Type` (Grant / Spend / Purchase / Expire / Refund / Adjustment), `Amount` (signed or typed by direction — OQ-4), `Pool` (Granted / Purchased — which pool moved), `Reason`/`ReasonCode`, **`ResultingGrantedBalance` + `ResultingPurchasedBalance`** (snapshot after the row), `OccurredAtUtc`, and an **`IdempotencyKey`**. The ledger has **no mutation methods** (mirror `XpAward`).
3. **AC-3 (balance = sum of ledger + reconciliation):** `account.GrantedBalance == sum of granted-pool ledger deltas` and likewise for purchased; a reconciliation routine recomputes both pools from the ledger and **flags drift** (returns the discrepancy; does not silently auto-heal).
4. **AC-4 (idempotency):** A **DB unique constraint** on the idempotency key rejects a duplicate grant/spend/expiry/purchase at the database layer (mirror `UX_XpAwards_OriginEventId_Reason`). Re-running the same logical operation is a no-op, not a double-write.
5. **AC-5 (Granted-before-Purchased + atomic debit):** A `DebitAsync(childId, amount, reason, idempotencyKey)` primitive draws from `GrantedBalance` first, then `PurchasedBalance`; the balance update **and** the ledger insert occur in a **single explicit transaction** (ADR 0001) — either both commit or neither. On insufficient total balance it returns a typed "insufficient" outcome (no partial debit, no exception leak). Concurrent debits do not over-draw (row lock / `xmin` concurrency token — OQ-5).
6. **AC-6 (conventions + isolation):** Handlers return `BaseResponse<T>` (`Successed` spelling); `ILoggerManager` injected; lives in the agreed module/schema (OQ-1/OQ-2); child is a **loose int reference**, no cross-module FK; no Unit of Work — explicit transaction only.

## Handoff → backend-feature

Mirror Gamification's 4-layer shape. `BaseResponse<T>` (`Successed`); `ILoggerManager`; no UoW (explicit transaction for the debit); no `ValidationBehavior` on queries (rule 4).

- **Domain primitive (the heart of the story):** `CreditAccount` mutation methods (`ApplyGrant`, `Debit`, `ApplyPurchase`, `Expire`, `Refund`, `Adjust`) that each update the balance(s) **and** return/append the matching `CreditTransaction` carrying the resulting-balance snapshot — so balance and ledger are written together, never separately.
- **`DebitAsync` service / `SpendCreditCommand` (the atomic primitive P9-03 calls):** input `(childId, amount, reasonCode, idempotencyKey)`; algorithm: open explicit transaction → load account `FOR UPDATE` (or rely on the concurrency token) → if `idempotencyKey` already present (unique-constraint pre-check or catch-on-insert) return the prior result idempotently → compute Granted-first split → if insufficient total, return typed `InsufficientBalance` (no write) → else update both pools + insert ledger row → commit. Return `BaseResponse<DebitResult>` carrying `{ Charged, FromGranted, FromPurchased, ResultingTotal }`. **Catch the unique-constraint violation** and translate to an idempotent success (mirror how `XpAward` redelivery is rejected at the DB).
- **`GrantCreditCommand` / `ApplyPurchaseCommand` / `ExpireGrantCommand` / `RefundCommand` / `AdjustCommand`:** each the same explicit-transaction + idempotency-key shape, differing only in which pool moves and the `Type`. P9-02 calls Grant + Expire; parent payment (P9-06/07) calls ApplyPurchase; P9-09 calls Refund; admin calls Adjust.
- **`GetCreditAccountQuery` (read seam for P9-10 meter + parent surfaces):** returns `{ GrantedBalance, PurchasedBalance, TotalBalance, GrantExpiresAtUtc }` — **read-only**, never exposes raw ledger to the child app. (A parent-facing ledger/history read is P9-08.)
- **`ReconcileAccountQuery` (AC-3):** recompute both pools from the ledger and return any drift — for an admin/ops check (not student-facing).
- **Spend seam for the AI gateway (`Shared.Contracts`):** declare an `ICreditSpendService` (or `IEnergyWallet`) contract in `Shared.Contracts/Billing/` — `Task<DebitResult> TryDebitAsync(int childId, int amount, string reasonCode, string idempotencyKey, CT)` and a `Task<EnergyBalance> GetBalanceAsync(int childId, CT)` — implemented in `Billing.Infrastructure`. **This is the seam P9-03 wires into the gateway without referencing the `Billing` projects** (module isolation). Define the contract here; P9-03 consumes it.
- **DI:** `AddBillingApplication` (AutoMapper + validators; do **not** `AddMediatR` per the module convention) and `AddBillingInfrastructure` (DbContext + repos + `ICreditSpendService` impl). Mirror Gamification's two `DependencyInjection.cs`.

## Handoff → security-auditor (ledger tamper-resistance — light-to-medium gate)

P9-01 is the **integrity foundation** for all money/credit movement, so audit the invariants even though there is no external surface yet:
- **Append-only enforcement:** confirm `CreditTransaction` has no update/delete path in code; the ledger is insert-only. Any "correction" is a new compensating row (`Adjustment`/`Refund`), never an in-place edit.
- **Idempotency is DB-enforced, not app-only:** the unique constraint must exist at the DB layer (an app-level check alone is racy). Verify the constraint and that the insert path catches and translates the violation rather than 500-ing.
- **Atomic debit:** confirm the balance-update + ledger-insert share one transaction; a crash mid-debit must not leave balance and ledger divergent. Confirm the concurrency token prevents two parallel debits over-drawing (no lost update → no free energy).
- **No PII in the ledger:** rows carry credit amounts + reason codes + loose child id only — no child name/email, no AI prompt/response text.
- **Authorization (forward-looking):** the spend seam must be callable only by the gateway/server, never by a child-supplied amount from the app. Flag that P9-03 must derive the cost from server-side config (P9-11), not trust a client-sent cost.
- This is **not yet a hard payment gate** (no money moves in P9-01) — the hard gate is P9-03 (spend integrity) and the payment stories (P9-06/07/09). But the ledger-integrity findings here are load-bearing for all of them.

## Handoff → api-tester

Only if P9-01 exposes an HTTP read endpoint this cycle (likely just `GetCreditAccountQuery` behind `[Authorize]`, or none — confirm seam). Core coverage is **unit/integration** on the primitive:
- Debit draws Granted-before-Purchased (granted=10, purchased=10, debit 15 → granted 0, purchased 5, two-pool ledger reflects the split).
- Insufficient total → typed `InsufficientBalance`, **no ledger row written**, balance unchanged.
- Idempotent debit: same idempotency key twice → one ledger row, charged once (DB unique constraint holds).
- Reconciliation: `sum(ledger) == account balances`; inject a manual drift → reconciliation flags it.
- Concurrency: two parallel debits of the full balance → exactly one succeeds, no over-draw (lock/concurrency-token test).
- Expire moves remaining Granted → 0 with an `Expire` row; Purchased untouched.

### Risks (top 3)
- **R1 — balance/ledger divergence under concurrency** (lost update → free or lost energy). **Mitigation:** atomic explicit transaction + concurrency token; api-tester concurrency case; security-auditor verifies.
- **R2 — module/schema thrash:** building before OQ-1/OQ-2 are settled risks a rework of the entire phase's boundary. **Mitigation:** hard lead gate before db-migration.
- **R3 — idempotency-key design leaking:** a weak/ambiguous key (e.g. reused across grant and spend) could collide or fail to dedupe. **Mitigation:** define the key scheme per operation type up front (grant = `child+cycle`; spend = `actionId`/request id; purchase = payment id) and make the unique constraint composite with `Type` if needed.
