---

## Business context & value

- **Who benefits:** the **parent** (a clear record of what they paid, downloadable receipts for their own bookkeeping/reimbursement) and the **business** (transparency lowers chargebacks + support tickets; legally compliant receipts).
- **Value:** read-only reporting over the `Payment` ledger built by P9-06/P9-07/P9-09. Low engineering risk; the main complexity is **receipt generation** (PDF/printable) with the **legally required fields** (seller, amount, tax/VAT, date, reference) — which depends on a **finance confirmation** of Egypt EGP/VAT requirements.
- **Success measured by:** the parent sees every charge chronologically with date/amount/status/(child for packs); each successful payment yields a downloadable receipt with the required fields; refunds show as linked negative entries; no cross-account access.

---

## Acceptance criteria (testable)

1. A parent sees a **chronological list of charges** (subscription renewals + energy packs) with **date, amount, status, and the child** (for packs).
2. Each **successful payment has a downloadable receipt/invoice** (PDF or printable) carrying the **legally required fields**: seller (legal entity), amount, **tax/VAT**, date, and the payment reference.
3. **Refunds (P9-09) appear as linked negative entries** tied to the original payment.
4. Only the **owning parent** can view their own history — **no cross-account access** (family-scope authz).
5. Renders **EN (LTR) + AR (RTL)**; empty state (no payments yet) handled gracefully.

---

## Affected modules & data

### Module — `Billing` (schema `billing`)
- Read-only over `Payment` (P9-06), `Payment{Kind=Pack, TargetChildId}` (P9-07), and refund entries (P9-09). The **child name** for a pack is **not** in Billing (no cross-module FK) — resolve the child's display name via `Shared.Contracts` (a `IChildDirectory`-style query against Identity/Parent) or by passing child ids the FE already has. **Recommendation:** the history DTO returns `TargetChildId`; the FE maps it to the child name from the parent's already-loaded children list (P1-04/P5-05). Confirm.

### New / reused entities
- **No new core entity required** — history is a projection over `Payment` + refund rows.
- **`Invoice` / `Receipt`** *(optional)*: a generated receipt may be produced on-the-fly (render PDF per request) or persisted as an `Invoice` row + stored file. **Recommendation:** generate on demand from the `Payment` row + config seller/VAT fields (no PII file storage); persist an `InvoiceNumber` sequence on `Payment` if finance requires sequential invoice numbering. Confirm with finance/lead.
- **Receipt fields source:** seller legal name, tax id, VAT rate/amount come from **config (P9-11 / a billing-settings store)** — never hard-coded.

## Handoff → db-migration

- Likely **no new table** — but if finance requires **sequential invoice numbers** or persisted invoices, add `InvoiceNumber` (sequence) and/or an `Invoice` table to `BillingDbContext` (schema `billing`). Confirm before building.
- Add any **VAT fields** to `Payment` (e.g. `NetAmount`, `VatAmount`, `GrossAmount`) **if** receipts must break out tax — this depends on the finance answer and ideally was captured at charge time in P9-06. **Flag:** if P9-06 did not record net/VAT split, P9-08 must reconstruct it from config — coordinate so VAT is captured at charge time in P9-06 rather than reverse-computed.

## Handoff → backend-feature

- **Queries:** `GetBillingHistory(parentUserId, paging)` → chronological list of `Payment` + refund entries (DTO: date, kind, amount, currency, status, targetChildId?, providerRef, refund link). `GetReceipt(parentUserId, paymentId)` → receipt DTO / PDF stream with seller/VAT/date/reference fields.
- **Receipt generation:** PDF or printable HTML. **DESIGN-PATTERN/LIBRARY NOTE:** adding a PDF library (QuestPDF, etc.) is a dependency + a potential pattern decision — **ask the lead first** (CLAUDE.md rule 8) before introducing it. A simpler v1 is a **printable HTML receipt** (FE renders + browser print-to-PDF) — recommend confirming scope with the lead (true PDF generation vs printable view).
- **Authz:** family-scope — the query filters to `parentUserId` from the JWT; a parent can never read another parent's payment/receipt (defense-in-depth: re-check ownership inside `GetReceipt`).
- **Queries not auto-validated** — validate ids in the handler. Envelope `BaseResponse<T>`/`Successed`; `ILoggerManager`.

## Handoff → designer + frontend + frontend-e2e-tester

- **Surface:** parent area — the **"Billing history" section** of the P2-12 "Plan & billing" tab / parent settings. **Never on a child route.**
- **Designer** (light): history list (rows with date/amount/status/child badge for packs; negative refund rows linked to their original), receipt download/print affordance, empty state. EN+AR, RTL, tokens only.
- **Frontend:** `useBillingHistory`, `useReceipt(paymentId)` (download/print). Map `targetChildId` → child name from the parent's children list. EN+AR.
- **frontend-e2e-tester:** parent web PWA — history lists renewals + packs + refunds chronologically, receipt downloads with required fields, child name shown for packs, owning-parent-only access, empty state, RTL/ar+en.

## Handoff → api-tester

- Cases: history returns the parent's payments chronologically with status + targetChildId for packs; refunds appear as linked negative entries; **cross-account access denied** (parent A cannot read parent B's history or receipt); receipt contains seller/amount/VAT/date/reference; empty history → empty list (not error); `BaseResponse<T>`/`Successed`.

## Handoff → security-auditor (light)

- Not a payment-mutation story, but it exposes **financial PII** → confirm strict **family-scope** on both history and receipt endpoints (no IDOR — fetching `GetReceipt(otherParentsPaymentId)` must 403/404). Receipts must not leak card data (there is none). Planner decides if a full audit is needed or if the reviewer covers the authz check.

## Open questions / assumptions / risks

1. **Receipt/VAT requirements (Egypt EGP) — needs FINANCE confirmation.** Exact legally required fields, sequential invoice numbering, VAT rate, seller legal-entity details. **Block receipt-field finalization on this.** (Story Notes explicitly say "confirm with finance.")
2. **True PDF vs printable HTML** for v1 — recommend printable HTML (browser print-to-PDF) to avoid a PDF library/pattern decision; confirm with lead. If true PDF, ask before adding the library.
3. **VAT captured at charge time (P9-06) vs reconstructed in P9-08** — strongly prefer capturing net/VAT/gross at charge time in P9-06 so receipts are exact. Coordinate; flag if P9-06 already shipped without it.
4. **Child name resolution** across the module boundary — FE-side mapping from the parent's children list (recommended) vs a `Shared.Contracts` child-directory query. Confirm.
5. **Persisted `Invoice` table + invoice-number sequence** — only if finance requires it. Confirm before adding to the migration.
