# Pipeline Brief — BL-01 Upload curriculum documents with metadata

> **Cross-cutting system decisions (A–E) are in `docs/briefs/curriculum-system-of-record.md` — read that first.**

## Summary & traceability
- **Task (one line):** Let an **admin** upload curriculum files (PDF/DOCX/images) with metadata (grade, subject, language, country), validate + store them durably, and place each upload on an **ingestion queue** with a visible status (received → processing → done → failed) — the entry point of the 3-stage curriculum pipeline.
- **User story:** `user-stories/Backlog-Phase-2-Plus/BL-01-upload-curriculum-documents.md` (source of truth).
- **Task file:** `tasks/Backend/Backlog-Phase-2-Plus/BL-01-BE.md` (BE-1..8; exists). Frontend task file (`BL-01-FE.md`) is deferred — admin UI not started.
- **FR-IDs:** FR-CI-1 (admins upload curriculum with metadata).
- **BRD goal:** **G5** (scalable curriculum platform — getting real curriculum into the system).
- **Phase / Epic:** Backlog Phase 2+ — Curriculum Intelligence. **SP 3.** Story Note: *"upload + metadata endpoints; structuring/OCR are separate (BL-02). Triggers BL-02 processing."*
- **Product-decision context:** 4 subjects (Math, Science, Arabic, English); no Social Studies; no teacher role; **Admin-role-only** (SRS §3, FR-CI-1).

## Business context & value
- BL-01 is the **front door** of the curriculum-intelligence pipeline (`info/Multimodal_Parsing_vs_Curriculum_Ingestion_vs_Knowledge_Graph.md`). Without it, there is no real curriculum to parse/ingest/graph.
- **Who benefits:** admins/content team (upload real textbooks); downstream, students (the tutor eventually grounds on real curriculum).
- **Success measured by:** an admin can upload PDF/DOCX/image with metadata; type/size validated; stored durably; only admins can upload; the upload appears on an ingestion queue with a visible status lifecycle.
- **Moderation / review-before-publish (pipeline-wide default):** documents uploaded via BL-01 enter the pipeline with `Status = Received`. No uploaded or ingested content is ever auto-published to students — the downstream pipeline (BL-05) enforces a mandatory human-review gate before any ingested Arabic curriculum is visible to students. BL-01 itself does not publish anything; it only stores and queues. This is documented here for end-to-end traceability.
- This is a **Phase-7-style admin surface** — the UI is an admin-console feature, almost certainly **deferred FE** (admin console FE is not started; this is post-MVP). The **backend upload + queue + status** is the buildable core.

## Affected modules & data

### Module — depends on BL-04's decision
- Lands in the **curriculum module** (new, option A in BL-04) **or** `learning` (option B). **Do not decide independently** — inherits BL-04's module decision. If a separate `curriculum` module is approved, BL-01's `CurriculumDocument` entity + upload feature live there.
- **No cross-module references** beyond `Shared.Contracts` (CLAUDE.md rule 1). Admin authorization reuses the existing Identity/RBAC (Admin role) via JWT claims — not a cross-module FK.

### Existing infrastructure to reuse (confirmed in code — do NOT reinvent)
- **`IStorageService`** (`backend/src/Shared/Learnexia.Shared.Kernel/Abstractions/Storage/IStorageService.cs`) — platform-wide, stream-based file storage backed by MinIO (S3 API, SigV4). Registered once at the Host; injectable by any module. **This is the durable-storage seam BL-01 must use.** Note: object **DELETE is not in the contract** (MVP trade-off).
- **Upload reference implementation:** `UploadAvatarCommandHandler` (`backend/src/Modules/Identity/.../Account/Commands/UploadAvatar/`) — the canonical pattern: presence/size check → content-type allow-list → **magic-byte signature** verification → `_storageService.UploadFileAsync(stream, objectKey, contentType, length, bucket)` → store the **object key** (not a URL) → presign on read. Mirror this for curriculum uploads (different allow-list: PDF/DOCX/images).
- Response envelope `BaseResponse<T>` / `Successed`, `ILoggerManager`, deferred-commit UoW.

### New entities (this story)
- **`CurriculumDocument`** (name TBD) — `Id`, `FileName`, `ObjectKey` (storage key), `ContentType`, `FileSize`, metadata: `GradeId`/`Grade`, `SubjectId`/`Subject`, `Language` (enum — reuse `ContentLanguage`), `Country`, plus **`Status`** (enum: Received/Processing/Done/Failed) and timestamps. The **ingestion queue** is most simply modelled as the set of documents in `Received`/`Processing` status (status field doubles as the queue), unless the lead wants a separate queue/job table.
- **Provenance link (Decision B):** when a document is uploaded, it becomes the root of a provenance tree. After parsing (BL-02), a `ContentSource` record is created (type based on the file — Book for PDFs/DOCX) linked to this document. BL-01 itself only creates the `CurriculumDocument`; the `ContentSource` is created by BL-02/BL-05. This is documented here for end-to-end traceability.
- **Version-awareness (Decision C):** uploaded documents are associated with a `CurriculumVersion` (Draft status) during ingestion (BL-05). BL-01 does not set the version — it only stores and queues. Documents enter the pipeline in a Draft version context; nothing is Active (published) until an explicit publish action (P7-05).

## Acceptance criteria (testable)
1. An admin can upload **PDF/DOCX/image** files and attach metadata: grade, subject, language, country.
2. Uploads are **validated** for type (allow-list + magic-byte signature, mirroring avatar upload) and **size**; invalid → 422 with the localized envelope, not a 500.
3. **Only admins** can upload — `[Authorize]` with the Admin role/policy (deliberate per CLAUDE.md rule 6; admin console is Admin-only per SRS §4.9).
4. Files are **stored durably** via `IStorageService` (MinIO bucket, e.g. `curriculum`); the stored **object key** (not a URL) is persisted on `CurriculumDocument`.
5. The upload appears in an **ingestion queue** (a document in `Received` status) and **triggers BL-02 processing** (an integration event / queued job — see boundary note).
6. **Upload status** (received / processing / done / failed) is **visible** via a read endpoint (list/detail of documents with status).

## Handoff → db-migration
- New entity `CurriculumDocument.cs` (chosen module's `Domain/Entities/`), `AggregateRoot` base. Add a `DocumentStatus` enum (`Received`, `Processing`, `Done`, `Failed`) in `Domain/Enums/`.
- EF config: index on `Status` (queue scans) and on `(GradeId, SubjectId)` (admin filtering). DbSet on the chosen DbContext; Npgsql migration in the chosen schema.
- If a new `curriculum` module/schema (BL-04 option A) was approved, this rides on that module's DbContext + `InitializeAsync` migrate hook.

## Handoff → backend-feature
- **`UploadCurriculumDocumentCommand`** (`ICommand<BaseResponse<...>>`, FluentValidation runs for commands): accepts the file (`IFormFile` at the controller, passed into the command) + metadata. Validate type allow-list (`application/pdf`, DOCX, image MIME types) + **magic bytes** (extend the `AvatarImageValidator` approach to PDF/DOCX/image signatures) + size cap (config-driven, e.g. a `CurriculumUploadConfiguration.MaxFileSize`). Upload via `IStorageService` to a `curriculum` bucket under a GUID object key; persist `CurriculumDocument` with `Status = Received`.
- **Trigger BL-02:** on successful save, publish a `CurriculumDocumentUploaded` integration event (via `Shared.Contracts` / the existing messaging seam) **or** enqueue a job — see the .NET-vs-Python boundary open question; the consumer (parser) is BL-02.
- **Queries:** `ListCurriculumDocuments` (admin, paged, filter by status/grade/subject) and `GetCurriculumDocument` (detail with status) → DTOs + AutoMapper `ProjectTo`. Queries are not auto-validated.
- **Endpoints:** an admin controller (`CurriculumDocumentsController`) under `api/curriculum/documents` (or `api/learning/...` in option B), `[Authorize(Roles="Admin")]` or the admin policy; `NewResult(await Mediator.Send(...))`. Register the controller's assembly part in the module's `AddXModule`.
- Mirror the avatar handler's structure exactly (validation order, `ServerError<T>` on exceptions, store key not URL).

## Handoff → frontend (deferred — confirm with lead)
- **Admin-console surface** (Phase-7-style): an upload form (file picker + grade/subject/language/country metadata) and an **ingestion-queue table** showing status. The admin console FE is **not started** and BL-01 is post-MVP → **almost certainly deferred FE**. If built: designer produces a Design Spec; flow = pick file → fill metadata → upload (progress) → see it in the queue with live status.
- API shapes: POST multipart `api/curriculum/documents`; GET list/detail with `Status` field.

## Handoff → api-tester
- Story exposes HTTP endpoints → api-tester runs after backend-feature:
  - Admin uploads a valid PDF → 200, document persisted with `Status = Received`, object key stored, BL-02 trigger fired.
  - Oversized / wrong-type / spoofed-content-type (good extension, bad magic bytes) → 422 envelope, not 500.
  - Non-admin / unauthenticated → 401/403.
  - List/detail returns the document with correct status; status transitions are reflected.

## Handoff → security-auditor (REQUIRED — file upload + admin authz)
- File upload is a security-sensitive surface: enforce magic-byte validation (not just MIME/extension), size caps, admin-only authz, GUID object keys (no path traversal / user-controlled filenames), and confirm uploaded files are **not executed/served inline** without content-type pinning. Critical/High findings block the gate.
