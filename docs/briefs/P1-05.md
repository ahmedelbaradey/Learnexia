## Business context & value
- **Who benefits:** Students (their data + other students' data stays isolated), Parents (can reach only their own children's data; cannot act as a learner), Admins (curriculum/admin endpoints locked to them), and the platform owner (defensible least-privilege posture over minors' data — the most sensitive data class).
- **Value:** The permission-policy + family-scope machinery already exists but is enforced almost nowhere (architecture.md §9, §14 flags). This story flips it from "built but dormant" to "enforced," closing anonymous-access and IDOR holes. It is the access-control backbone every later phase (learning, assessment, reports, gamification) inherits.
- **Success measures (from the story AC):** wrong-role call → 403; unauthenticated call to a protected endpoint → 401; a student cannot read another student or parent reports; a parent cannot act as a learner; admin-only endpoints reject non-admins; the JWT signing secret is no longer a committed value.

## Acceptance criteria (testable)
1. **AC-1 — Wrong role → 403.** An authenticated user lacking the required role/policy on a gated endpoint receives **403 Forbidden** (not 200, not 401). (BE-2, BE-5)
2. **AC-2 — Unauthenticated → 401.** A request with no/invalid bearer token to a protected endpoint receives **401 Unauthorized**. (BE-5)
3. **AC-3 — Admin-only endpoints reject non-admins.** Already true for `UserManagementController` and `NotificationsController.List` (both `AdminOnly`); extend the same gate to the still-anonymous admin-surface endpoints (`AuthorzationController` role/claim management, Catalog write endpoints) so non-admins get 403. (BE-2)
4. **AC-4 — Family/self scope.** Where an endpoint targets a specific `studentId`, a parent linked to that child or the student themself succeeds; any other authenticated user is denied (403); Admin/SuperAdmin always allowed — by **reusing** `FamilyScopeAuthorizationHandler` via `IAuthorizationService.AuthorizeAsync(User, studentId, new FamilyScopeRequirement())` in the handler/controller. (BE-3) — *Note: there is no per-`studentId` endpoint in the backend today (see Affected surface); confirm scope with the lead — see Q1.*
5. **AC-5 — Parent is not a learner.** Parent-role tokens cannot reach learning-content/learner endpoints. *No learning module exists yet*, so this AC is satisfiable today only by (a) not granting Parent any learner permission claims and (b) documenting the gating convention for the future learning module. (BE-2, BE-3 — see Q1/Q2)
6. **AC-6 — Permission claims scoped to real modules.** `Claims.GenerateModules()` generates `{Module}.{Action}` policies only for modules that exist today; no policies are registered for non-existent future modules. (BE-1)
7. **AC-7 — JWT secret out of source.** `JwtSettings.Secret` (and any provider keys) are read from environment / secret store, not a committed real value; Production/Staging fail-fast if the default/empty is supplied (already implemented in P1-01 — build on it). (BE-4)
8. **AC-8 — Authn endpoints stay anonymous.** `Register-Parent`, `Sign-In`, `Validate-Token`, `Refresh-Token` remain `[AllowAnonymous]`; health probes remain anonymous. No regression. (BE-2)

### Roles & claims — verified facts
- Roles emitted into the JWT as `ClaimTypes.Role` verbatim from the role Name (`AuthenticationIdentityService.GetClaims`). `RoleSeeder` standardizes Names to PascalCase; `AdminOnly` policy and `FamilyScopeAuthorizationHandler` compare against `Roles.Admin`/`Roles.SuperAdmin` PascalCase — **use PascalCase role strings everywhere** (not `RoleHelper`'s lower-case constants, which drive only legacy helpers and are not used by Learnexia flows).
- Permission claims: per-role `RoleClaims` are emitted as `CustomClaimTypes.Permission` claims; one policy per permission is registered in `Identity Infrastructure/DependencyInjection.cs::AddIdentityService` (lines 141-160).
- `Claims.GenerateModules()` currently returns only **`"Catalog"`** → policies `Catalog.View/List/Create/Edit/Delete` exist. The task text lists future modules (learning, assessment, parent, curriculum) — **none of those modules exist in code.** **Recommendation: do NOT add claims for non-existent modules** (AC-6). Registering policies whose claims no one can ever hold is dead config and a future-misconfiguration trap. Defer until each module ships and add its claims with that module's story.

## Handoff → backend-feature
This is the bulk of the work. No new commands/queries/DTOs are expected; the work is attributes + DI config + secrets.

- **BE-1 (roles + claims):**
  - Confirm the 3 product roles (Student, Parent, Admin) + SuperAdmin exist in the `Roles` enum and are seeded (they are). No new role needed.
  - **Do not** extend `Claims.GenerateModules()` with non-existent modules (learning/assessment/parent/curriculum). If anything, leave it returning real modules only. Document the deferral in the PR body. (See AC-6, Q2.)
- **BE-2 (apply `[Authorize]`):** Edit these controllers (PascalCase roles / existing policy constant `Learnexia.Shared.Kernel.Abstractions.AuthorizationPolicies.AdminOnly`):
  - `AuthorzationController.cs` → add class-level `[Authorize(Policy = AuthorizationPolicies.AdminOnly)]` (role/claim management is admin-only).
  - `ProductsController.cs` + `CategoriesController.cs` → gate reads to authenticated (or `Catalog.View`/`Catalog.List` policy) and writes to `AdminOnly` (or `Catalog.Create/Edit/Delete`). **Pick one consistent scheme — see Q3.** Catalog is demo scaffolding (architecture.md §16) slated to be replaced by `learning`; recommend the *minimal* gate (authenticated for reads, AdminOnly for writes) rather than investing in permission-claim wiring on throwaway controllers.
  - Verify `AuthenticationController` anonymous endpoints and health probes are untouched (AC-8).
- **BE-3 (family/self scope):** Reuse the existing handler — do **not** write a new one. Pattern (from P1-04 brief / handler doc):
  - Inject ASP.NET's `Microsoft.AspNetCore.Authorization.IAuthorizationService` into the controller/handler, call `await _authz.AuthorizeAsync(User, studentId, new FamilyScopeRequirement())`, and return 403 (`Forbid()` / a Forbidden `BaseResponse`) when `!result.Succeeded`.
  - **Caveat:** there is currently **no endpoint that takes a `studentId`** to wire this onto (`ListMyChildren` derives the parent from the JWT; no per-child read exists yet). So BE-3 today is: (a) verify the handler + DI registration are correct and fail-closed; (b) optionally add an integration test proving cross-family / cross-student denial via the handler; (c) document the call pattern for the first per-child endpoint (likely P1-03 add-child detail or Phase-5 reports). **Confirm with the lead whether BE-3 should retro-fit an existing endpoint or is "infra-verified + documented" — see Q1.**
- **BE-4 (secrets):**
  - Remove the real secret value from `appsettings.json`. P1-01 already added `GuardJwtSecret` (Production/Staging fail-fast on empty/default) in `Identity Infrastructure/DependencyInjection.cs` — **do not duplicate it.** Recommended approach: leave the `CHANGE_ME…` placeholder (or empty) in `appsettings.json` for local/dev/test, document supplying `JwtSettings__Secret` via env var / `.env` / secret store for Staging/Prod, and ensure `.env`/secret files are git-ignored. Verify no other provider keys (e.g. future OAuth/SMTP/MinIO) sit in committed config; if found, surface them.
  - Update architecture.md §14 "Secrets" row from flag → resolved once done (optional, nice-to-have).
- **BE-5 (401 vs 403):** Verification + tests, likely no code change. Confirmed wiring: `app.UseAuthentication()` then `app.UseAuthorization()` (Program.cs 163-164); default JWT bearer challenge returns **401** for missing/invalid token and **403** for authenticated-but-forbidden. `ErrorHandlerMiddleware` maps thrown `UnauthorizedAccessException` → 401 but the framework's policy denials don't throw — they short-circuit with the correct status, so the two paths don't conflict. **Risk to check:** `AuthorizationLoggingMiddleware` runs before auth and is pass-through (no status mutation) — fine. Confirm no global filter coerces 403→401 or vice-versa.

## Open questions / assumptions / risks
- **Q1 (scope of BE-3) — for the lead/user.** There is no endpoint accepting a `studentId` in the current backend, so family-scope cannot be "applied" to a live route. Should P1-05 (a) only verify + unit/integration-test the existing handler and document the call pattern, or (b) also retro-fit a per-child read endpoint? Recommend (a) — wiring the handler onto its first real consumer belongs to the story that introduces that endpoint (P5 reports / per-child dashboard).
- **Q2 (future-module claims) — recommendation, confirm.** Task BE-1 says generate claims for learning/assessment/parent/curriculum. Those modules don't exist. **Assumption:** defer them (AC-6). Confirm the lead/reviewer accept deferral rather than registering dead policies.
- **Q3 (Catalog gating scheme) — recommendation, confirm.** Catalog is demo scaffolding to be replaced by `learning`. **Assumption:** gate it minimally (authenticated reads, `AdminOnly` writes) rather than building out `Catalog.*` permission-claim assignments to roles (no role currently *holds* `Catalog.*` claims, so a `[Authorize("Catalog.Create")]` gate would 403 *everyone* including admins until claims are seeded). **This is a real correctness trap** — if permission-claim policies are used, the seeding of those claims to Admin/SuperAdmin MUST ship in the same batch, or every gated endpoint 403s. Recommend role-based (`AdminOnly`) gating to avoid it.
- **Q4 (SRS §3 permission matrix) — assumption.** The story cites "per SRS §3 permission matrix." Confirm whether a formal matrix doc must be authored, or whether the role/policy attributes themselves are the matrix-of-record for this thin product (Student/Parent/Admin). Recommend the latter for SP-3 scope; capture the mapping in the PR body.
- **Risk — over-/under-permissioning (BLOCKING via security-auditor):** the central failure mode is a `[Authorize("X")]` gate whose backing claim no role holds (locks out everyone) or a too-broad role gate (locks out no one). Auditor must verify each gate's policy resolves to a claim/role actually issued.
- **Risk — fail-closed verification:** `FamilyScopeAuthorizationHandler` is fail-closed by construction (Succeed only on explicit match). Auditor must confirm no caller treats `AuthorizeAsync` result as "allow on error."
- **Risk — legacy `Roles` enum noise:** fund-management roles (FundManager etc.) are seeded and could be accidentally referenced. Ensure no Learnexia policy depends on them.

Reuse the `WebApplicationFactory` harness (env "Testing", default secret tolerated).

5. **`committer`:** only after PASS, on `feat/P1-05-rbac`.

**No `designer`, no `db-migration`.** Security-sensitive → `security-auditor` is mandatory and blocking.
