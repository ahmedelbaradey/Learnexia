### CRITICAL reconciliation — story/task docs are STALE vs the shipped backend
The story and both task files describe a **standalone Quiz aggregate** (`GET /api/Learning/Quizzes`, quiz title/description, `Quizzes/{id}/Attach` to lesson/skill, language inheritance from Subject tree). **None of that shipped.** The merged reality (confirmed in code + `HANDOFF.md` line 969 and the locked lead decision line 974) is:

- **Quiz is IMPLICIT per-lesson — there is NO `Quiz` entity, no `QuizzesController` admin authoring, no quiz title/description, no Attach endpoint, no language picker.** Questions attach directly to a **lesson** (`LessonId`, loose int) with an optional `SkillId`.
- The real admin surface is **`QuestionsController`** at `api/Learning/Questions` (all `AdminOnly`). The unit of work is "the questions under a lesson," not "a quiz."
- There is **no language column** on a question; language is inherited from the lesson's Subject tree and is **not** part of any question endpoint. The "attach quiz to same-language lesson/skill" AC and the FE-4 "AttachQuizDialog" task **do not apply** — drop them.

**Therefore the FE scope is: a per-lesson question manager.** This brief specs against the shipped endpoints. The acceptance criteria below are rewritten to match reality; the original story ACs are mapped where they still hold (4 types + per-type shape + invalid-shape error + edit/remove updates order + admin-only) and explicitly retired where they don't (standalone quiz CRUD, attach, language picker). **The planner/lead should confirm this scope correction** (see Open Questions Q1).

## Business context & value
- **Who benefits:** the **Admin / content team** (authoring) and, downstream, **students** (better-curated quizzes) and **parents** (quality of assessment). No teacher role.
- **Value:** moves quiz authoring from seed scripts into the dashboard so non-engineers can curate the 4 question types safely with per-type validation; closes the "curriculum is seeded" gap (G4). Correct-answer integrity is preserved (admin-only DTO; never leaked to students).
- **Success meas:** an admin can, from the dashboard, open a lesson, add/edit/delete/reorder/activate questions of all 4 types, see per-type validation enforced both client-side and server-side, and the resulting questions grade correctly for students (the `CorrectAnswer` round-trip is the make-or-break).

## Acceptance criteria (testable — rewritten to the shipped backend)
1. **Questions list under a lesson.** Given a `lessonId`, the admin sees all non-deleted questions (incl. inactive) ordered by `SequenceOrder`, each showing type, text (Arabic or English), difficulty, active/inactive state, and a position. Empty lesson → empty state (not an error). 404 (lesson not found) and generic error → distinct states.
2. **Add a question, pick 1 of 4 types, editor enforces that type's shape.** A type selector switches the sub-form: MCQ (≥2 option strings + one correct choice), TrueFalse (correct = true/false), FillBlank (non-empty correct answer; no options), Matching (paired left/right items + the correct pairing). New question appends to the end of the lesson's sequence.
3. **Per-type client validation mirrors the BE rules**; on submit, a server per-type rejection (`successed === false` + localized message) is surfaced inline near the relevant field, not as a generic toast. (Exact rules in "Per-type contract" below.)
4. **`CorrectAnswer` round-trips correctly per type** (LOAD-BEARING — see dedicated section). Create → list/get → edit → save must preserve the answer so students grade correctly. A wrong encode here silently breaks grading.
5. **Edit a question.** Loading an existing question repopulates the editor in the correct per-type shape; saving updates type/text/options/correctAnswer/difficulty. (LessonId, SkillId, SequenceOrder, IsActive are NOT editable here — dedicated actions own those.)
6. **Soft-delete a question** behind a confirm dialog; on success the row disappears from the list (global soft-delete filter) and the list refetches.
7. **Reorder questions** within the lesson; the new order persists (`SequenceOrder`) and the list reflects it after invalidation. All ids must belong to the anchor lesson (backend enforces; FE only ever reorders within one lesson).
8. **Activate / deactivate a question** (lifecycle toggle); inactive questions stay visible to the admin (distinct visual state) but are hidden from students. Confirm copy must say "hidden from students," not "deleted."
9. **Admin-only access.** Non-admin → redirected by `useAdminGuard`; the backend is the real gate (401 anonymous / 403 non-admin). No student-facing route ever renders `CorrectAnswer`.
10. **RTL + bilingual.** Question text/options are authored content that may be Arabic — inputs must support RTL content entry and the editor must render correctly under the admin chrome. Admin chrome copy is bilingual (EN+AR slots in `lib/strings.ts`), though runtime locale is currently a build-time constant (see Open Questions Q5).

> **Retired from the original story (do NOT build):** standalone Quiz CRUD with title/description; `QuizzesController` admin routes; `Quizzes/{id}/Attach` to lesson/skill; same-`(SubjectCode, Language)`-tree attach validation; the language picker / `AttachQuizDialog` (FE-4) and the quiz-list page / `QuizForm` (FE-1 as written). The "quiz" is the lesson's question set.

## Exact endpoints (shipped — `QuestionsController`, all `[Authorize(Policy = AdminOnly)]`)
Base route: **`/api/Learning/Questions`**. All return the `BaseResponse<T>` envelope; success flag is **`Successed`** (the FE `ApiClient` already unwraps this and throws `ValidationError` on 422 / `ApiEnvelopeError` on `successed===false`).

| Verb | Route | Body / params | Returns | Purpose |
|---|---|---|---|---|
| GET | `/ByLesson/{lessonId:int}` | path `lessonId` | `BaseResponse<List<AdminQuestionDto>>` (ordered by `SequenceOrder`, includes inactive + `CorrectAnswer`) | List questions for a lesson |
| GET | `/{id:int}` | path `id` | `BaseResponse<AdminQuestionDto>` | Single question (admin, includes `CorrectAnswer`) |
| POST | `` (root) | `AddQuestionCommand` (see below) | `BaseResponse<string>` (message) | Add question (appends at end) |
| PUT | `` (root) | `EditQuestionCommand` (see below) | `BaseResponse<string>` (message) | Edit type/text/options/correctAnswer/difficulty |
| DELETE | `/{id:int}` | path `id` | `BaseResponse<string>` (message) | Soft-delete (IsDeleted=true) |
| PUT | `/Reorder` | `{ lessonId:int, questionIds:int[] }` | `BaseResponse<string>` (message) | Batch reorder (position = new SequenceOrder, 0-based) |
| PATCH | `/{id:int}/SetActive` | `{ isActive:boolean }` (id from path; controller merges) | `BaseResponse<string>` (message) | Activate/deactivate |

Mutations return a **message string**, not a DTO — the FE must **refetch via query invalidation**, never read new state from the mutation result (same rule as Wave 1's `useSuspendUser`).

### `AdminQuestionDto` (GET responses — hand-write this FE-local interface)
`{ id:int, lessonId:int, skillId:int|null, questionType: QuestionType, questionText:string, options:string (JSON), correctAnswer:string (per-type, see below), difficulty: DifficultyLevel, generatedBy: GeneratedBy, sequenceOrder:int, isActive:boolean }`

### `AddQuestionCommand` body
`{ lessonId:int, skillId?:int|null, questionType, questionText, options:string(JSON), correctAnswer:string(per-type), difficulty, generatedBy }` — `SequenceOrder`/`IsActive` are server-set (do NOT send). `GeneratedBy` should be sent as **`Curated` (=1)** for admin-authored questions.

### `EditQuestionCommand` body
`{ id:int, questionType, questionText, options:string(JSON), correctAnswer:string(per-type), difficulty }` — note `lessonId`/`skillId`/`sequenceOrder`/`isActive` are intentionally absent (the backend ignores them on edit).

### Enums (backend serializes as **int**, no string converter — mirror Wave-1 `ACCOUNT_STATUS` constant style)
- `QuestionType`: **MCQ=1, TrueFalse=2, Matching=3, FillInBlank=4**
- `DifficultyLevel`: **Easy=1, Medium=2, Hard=3**
- `GeneratedBy`: **Curated=1, AI=2**

Put these as `as const` maps in `@learnexia/shared/constants` (or a local admin const), matching the established no-magic-number pattern. **Send/compare the int values.**

## LOAD-BEARING: `CorrectAnswer` + `Options` jsonb encode/decode per type
`CorrectAnswer` and `Options` are stored as **jsonb** on the entity. The backend has a deliberate asymmetry that the FE must respect exactly, or grading silently breaks. Two bugfixes are baked into the backend (`AddQuestionCommandHandler`/`EditQuestionCommandHandler` "P7-04 bugfix", and `QuizProfile` "DEF-P7-04-READ-PATH"). Net effect for the FE:

### Non-Matching types (MCQ / TrueFalse / FillInBlank) — `CorrectAnswer` is a RAW SCALAR on the wire
- **WRITE (POST/PUT):** send `CorrectAnswer` as the **raw scalar string** — e.g. MCQ `"Paris"` (the exact text of the chosen option), TrueFalse `"true"` / `"false"` (lowercase), FillBlank `"photosynthesis"`. **Do NOT JSON.stringify it yourself.** The backend wraps it (`JsonSerializer.Serialize("Paris")` → stores `"\"Paris\""`).
- **READ (GET):** the backend **decodes** it back to the raw scalar before returning (`QuizProfile.DecodeJsonScalar`). So `AdminQuestionDto.correctAnswer` comes back as `"Paris"` / `"true"` / `"photosynthesis"` — **already the raw value, NOT JSON-quoted.** The FE can bind it straight into the editor. **Do NOT JSON.parse it.**
- **Round-trip is symmetric for the FE:** what you read is what you send. No client-side JSON wrap/unwrap for non-Matching `CorrectAnswer`.

### Matching — both `Options` and `CorrectAnswer` are JSON OBJECT strings (passthrough, no scalar encoding)
The backend stores Matching `CorrectAnswer` **as-is** (no `JsonSerializer.Serialize` wrap on write; no decode on read). So the FE must send/receive the **full JSON object as a string**. The **authoritative wire contract** is defined on `AnswerComparator` (CO-BE-1/CO-BE-2, "locked decision — do not redesign") and the `QuizQuestion` entity doc — use these shapes, NOT the looser one the validator happens to accept:

- **`Options` (student-visible, jsonb string):**
  `{"left":[{"id":"l1","text":"…"},…],"right":[{"id":"r1","text":"…"},…]}` — stable item `id`s + localized display `text`. Author should store `right` in a non-aligned order (so array position never leaks the pairing; the student app shuffles too).
- **`CorrectAnswer` (never sent to students, jsonb string):**
  `{"pairs":[{"leftId":"l1","rightId":"r1"},…]}` — references the `Options` item ids. Grading is order-independent pair-set equality; a duplicate `leftId` or missing/extra pair grades wrong.
- **FE responsibility:** the Matching sub-form must let the admin define N left items and N right items (each with a stable id the FE generates, e.g. `l1..ln` / `r1..rn`) and the correct pairing, then **serialize `Options` and `CorrectAnswer` to these exact JSON shapes** before send, and **parse them back** on edit-load.

### `Options` for the other types
- **MCQ:** `Options` = a JSON array of strings, e.g. `["Paris","London","Cairo"]` (≥2). `CorrectAnswer` (raw scalar) must be **exactly equal** (ordinal) to one of those strings.
- **TrueFalse:** entity convention is `Options` = `["True","False"]` (fixed); the validator does NOT check Options for TrueFalse, but send the fixed pair for consistency. `CorrectAnswer` = `"true"`/`"false"`.
- **FillInBlank:** `Options` is not used — entity convention is store `[]` (empty JSON array). `CorrectAnswer` = the non-empty answer string.

> **DISCREPANCY to flag (Open Q3):** the BE FluentValidation (`QuizQuestionTypeValidation.ValidateMatching`) only checks that `Options` has equal-length `left`/`right` arrays — it does NOT validate the `{id,text}` item shape and does NOT validate Matching `CorrectAnswer` at all. So a malformed Matching question can pass validation but grade wrong forever. The FE MUST author the full authoritative shape regardless, and the `qc-test-designer`/`reviewer` should treat "Matching grades correctly end-to-end" as a must-prove case (see test-designer handoff). This is a latent BE gap, not a blocker for the FE if the FE emits the correct shape.

### Per-type CLIENT validation (mirror BE `QuizQuestionTypeValidation` so the user gets fast feedback; BE is still the authority)
- MCQ: ≥2 non-empty options; exactly one selected as correct; correct value ∈ options.
- TrueFalse: a choice is selected (true/false).
- FillBlank: non-empty correct answer.
- Matching: ≥1 left and ≥1 right item, equal counts, every item has non-empty text, every left is paired to exactly one right, no duplicate pairing. (Stricter than BE — that's intentional, see Q3.)
- Shared: `questionText` non-empty, ≤4096; `options` serialized ≤16384; `correctAnswer` serialized ≤4096 (the BE DoS bounds — mirror so the user isn't surprised by a 422).

## Security & audit
- **AdminOnly is enforced server-side on every endpoint** (`QuestionsController`); `useAdminGuard` is a UX boundary only (client-side, decodes JWT role). Do not rely on it for security.
- **`CorrectAnswer` exposure is intentional and admin-only:** `AdminQuestionDto` includes it; the student-facing `QuizQuestionDto` excludes it (mapping profile `ForSourceMember(... DoNotValidate)`). The FE must **never** render `CorrectAnswer` on any non-admin/student route, never log it, and never put it in a URL. The security-auditor should confirm the new hooks only ever call the `AdminOnly` admin routes and that no admin DTO leaks into shared/student code paths.
- **P7-12 audit is LIVE.** Every mutation (Add/Edit/Delete/Reorder/SetActive) raises `AdminActionPerformedDomainEvent` → dispatched post-commit → Moderation audit log. **FE does nothing extra** for audit — but be aware two handlers record `TargetEntityId: 0` (Add — id not flushed pre-event; Reorder — batch op), so the audit row for those won't carry the question id. Note as a known BE limitation; not an FE blocker.
- **Soft-delete only** — Delete sets `IsDeleted=true` (global filter hides it); there is no hard delete and no clawback. Confirm copy must reflect that delete is reversible-by-DB-only / not a hard purge, and deactivate ≠ delete.
- **Input bounds (DoS):** the BE bounds `questionText`≤4096, `options`≤16384, `correctAnswer`≤4096; mirror client-side so the admin isn't surprised by a 422.
- This batch touches **admin curriculum writes** → it is security-sensitive; run **security-auditor** before the reviewer gate.
