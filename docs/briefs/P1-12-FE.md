## Summary & traceability
- **Task (1-line):** Light up the P1-11 UI-first account surfaces against the now-merged P1-12 backend — profile save + avatar upload/remove, social (Google) sign-in, forgot/reset password, edit-child save, and register country + terms-consent wiring.
- **User story (source of truth):** `user-stories/Phase-1-Foundation/P1-12-web-account-backend-batch2.md` (children P1-12a…f). FE task file: `tasks/Frontend/student-app/Phase-1-Foundation/P1-12-FE.md` (P1-12-FE-1…7).

- **Phase / batch:** Phase 1 — Foundation · **Batch 2 (deferred carry-forward)**. App: `apps/student-app` (Expo web PWA).
- **Backend status:** ✅ built & merged (P1-12-BE + P1-13 hardening). The typed `api-client` is already **regenerated** and exposes every endpoint. Product overrides apply (parent-driven onboarding, 4 subjects, no teacher role, grade transition preserves history).

## Business context & value
Parents are the only self-registering actor (parent-driven onboarding). These features complete the parent account experience the P1-11 redesign promised but shipped as disabled/placeholder affordances:
- **Profile + avatar** — account feels personal and correct (P1-12a/b).
- **Google sign-in** — lower sign-in friction (P1-12c).
- **Password reset** — self-service account recovery (P1-12d), with anti-enumeration carried over from P1-13.
- **Edit child** — parents correct child details after onboarding (P1-12e).
- **Register country + consent** — persists data the form already collects; COPPA-relevant consent auditability (P1-12f).
Success = each affordance is functional end-to-end against the real API, in en (LTR) + ar (RTL), dark + light, with proper success/error states.

## Acceptance criteria (testable)
**A. Profile save (P1-12-FE-1)**
- Settings → Profile loads `fullName / phone / country / avatarUrl` from `useMyProfile` (already wired).
- Save persists `{ fullName, phone, country }` via `useUpdateProfile` (already wired); success + error banners; Cancel resets. (This is already DONE in `SettingsWeb.tsx` — verify only.)

**B. Avatar upload / remove (P1-12-FE-2)**
- "Upload photo" opens an image picker, uploads the file, and the avatar refreshes to the returned `avatarUrl`; the disabled state is removed.
- "Remove" clears the avatar and falls back to initials.
- Client-side validates type (image/*) and a reasonable size cap before upload; server errors surface inline.
- `useMyProfile` (and `/Me`) reflect the new/cleared `avatarUrl` after the mutation (cache invalidation).

**C. Google sign-in (P1-12-FE-3)**
- The Login Google button initiates a Google OAuth flow that yields an `idToken`, posts it to `googleSignIn`, and on success persists tokens (mirror `useSignIn` → `authStore.setTokens` → `router.replace('/')`).
- The Google button is no longer a no-op; failure surfaces a banner with no account-enumeration leak.
- Apple / Microsoft remain UI-only placeholders unless the lead confirms scope (BE only ships Google — see open questions).

**D. Forgot / reset password (P1-12-FE-4)**
- New `(auth)/forgot-password.tsx` (email → `forgotPassword`) and `(auth)/reset-password.tsx` (email + token + newPassword → `resetPassword`).
- The Login "Forgot password?" link routes to forgot-password (replaces the no-op handler).
- Forgot-password always shows a generic "if an account exists…" confirmation (no enumeration). Reset enforces the password policy and surfaces token-invalid/expired errors.

**E. Edit child (P1-12-FE-5)**
- A parent can open an existing linked child from My Children (web) and edit `fullName / grade / language / country`, saving via `useUpdateChild` (hook exists); the list refreshes (cache invalidation already in the hook).
- Family-scope authz is server-side; client never sends a parent id. Grade constrained 1..6.

**F. Register country + terms-consent (P1-12-FE-7)**
- The Register form sends the collected `country` + `acceptedTerms` (remove the client-only TODOs); field validation errors surface.
- `captchaToken` is config-gated (P1-11-FE-16, separate) — confirm whether in scope here.

**G. QA (P1-12-FE-6)** — all new/wired surfaces verified in en/ar + dark/light, RTL correct.

|---|---|---|---|---|---|---|
| Profile read | `profileGET()` | — | `AccountProfileResponse` `{fullName,phone,country,avatarUrl}` | `GET /api/Users/Account/Profile` | `SettingsWeb` ProfilePanel | ✅ `useMyProfile` |

## Handoff → api-client (new hooks — mirror existing thin TanStack wrappers)
Add under `packages/api-client/src/hooks/` and export from `hooks/index.ts`:
- `useUploadAvatar` — wraps `avatarPOST(FileParameter)`; on success invalidate `queryKeys` for profile + `Me` so `avatarUrl` refreshes.
- `useRemoveAvatar` — wraps `avatarDELETE()`; same invalidation.
- `useGoogleSignIn` — wraps `googleSignIn`; returns `JwtAuthResponse`; caller persists tokens (mirror `useSignIn`, do **not** persist inside the hook).
- `useForgotPassword` — wraps `forgotPassword`; anonymous.
- `useResetPassword` — wraps `resetPassword`; anonymous.
- Reuse existing `useUpdateChild`, `useUpdateProfile`, `useMyProfile`, `useRegisterParent`.

**LOAD-BEARING transport gap (must fix in `packages/api-client/src/client/apiClient.ts`):** `ANONYMOUS_PATH_SUFFIXES` currently lists only `Sign-In`, `Register-Parent`, `Refresh-Token`. The new unauthenticated flows — `/Authentication/Google-SignIn`, `/Authentication/Forgot-Password`, `/Authentication/Reset-Password` — are **NOT** in the list, so today they would attach a stale/absent auth header and trigger the 401-refresh retry. Add all three suffixes (verified paths above). This is required for FE-3 and FE-4 to work.

## Handoff → security-auditor (audit before the gate — security-sensitive batch)
1. **Avatar upload (FE-2):** client file-type + size validation (defense-in-depth; BE validates too — MinIO presign TTL 60m per HANDOFF). No SVG/executable; cap size. Confirm the returned `avatarUrl` origin is trusted (MinIO) before rendering.
2. **Google OAuth (FE-3):** `idToken` handled client→BE only, never logged; token persistence mirrors the vetted `authStore`; watch for **account linking/takeover** (BE links/creates parent by Google email — confirm it cannot hijack an existing password account). PKCE/redirect-URI integrity for the chosen flow. Google client ID is public but must be config, not hardcoded.
3. **Password reset (FE-4):** no account enumeration on forgot (generic confirmation); reset token only in the reset request body/deep link, never logged; enforce password policy client-side as UX only (BE authoritative). Aligns with P1-13 uniform sign-in errors.
4. **Consent capture (FE-7):** `acceptedTerms` must be a genuine user action (gate submit), sent truthfully; not auto-set.
5. **Transport anonymous-path fix:** ensure the three new auth paths do not leak the existing user's bearer token (the fix above).

## Open questions / assumptions / risks (for the lead → user)
1. **Social scope:** BE shipped **Google only** (`googleSignIn`). Are Apple/Microsoft buttons in scope for FE-3, or do they stay disabled placeholders? (FE task says "Google/Apple/Microsoft"; backend story title says all three but only Google has an endpoint.) **Recommend: Google only now; keep Apple/MS as labeled placeholders.**
2. **OAuth library/flow convention:** no existing OAuth flow in the app. Which library (`expo-auth-session`) and does web need a dedicated callback route? Where does the **Google client ID** config live (env / `app.config`)? Needs a decision before FE-3.
3. **OAuth = sign-in only, or also account-linking in Settings?** The story mentions "links/creates the parent account"; FE-3 is framed as login-only. **Assumption: sign-in only; no Settings linking UI in P1-12-FE.**
4. **Edit-child entry point:** `MyChildrenWeb.tsx` has no edit button today, and `EditChildSheet` is onboarding/in-memory only. Where does web edit-child launch from (per-card menu? card tap?) and do we adapt `EditChildSheet` for the backend-wired case or build new? Needs a design decision (FE-5).
5. **CAPTCHA on register (`captchaToken`):** the field exists and P1-13-BE-4 (Turnstile, config-gated, default off) is merged, but CAPTCHA FE is tracked as **P1-11-FE-16**, separate from P1-12-FE-7. Confirm whether to fold it into this story or leave for FE-16. **Assumption: out of scope here.**
6. **Profile `email`:** `AccountProfileResponse` has no `email`; `SettingsWeb` reads it defensively as display-only. Confirm BE intends to add it, or that email stays display-only sourced from `/Me`.
7. **Reset deep-link format:** what does the reset email link look like (route + `email`/`token` query params)? Drives the `reset-password.tsx` param parsing. The reset email is currently English-only (HANDOFF: P6-06 localization follow-up) — acceptable for now.
