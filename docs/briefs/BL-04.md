# Pipeline Brief — BL-04 Curriculum, knowledge-graph & vector schema (Technical Enabler)

> **Cross-cutting system decisions (A–E) are in `docs/briefs/curriculum-system-of-record.md` — read that first. This brief encodes its schema implications.**

## Summary & traceability
- **Task (one line):** Define the persistent schema for the curriculum-intelligence pipeline — `CurriculumChunk` (with a separate **`chunk_embeddings`** table for pgvector, not an inline column), `ContentSource`/`Chapter`/`ProvenanceMapping` (provenance tree), `CurriculumVersion` (immutable-publish versioning), `KGSuggestion` (KG suggestion queue) — so that BL-01/02/05/03 and RAG retrieval (P3-07) all have a place to write. `KnowledgeNode`/`KnowledgeEdge` remain physically in `learning` (P2-11); `Curriculum` is their logical owner/validator only.
- **User story:** `user-stories/Backlog-Phase-2-Plus/BL-04-curriculum-vector-schema.md` (source of truth).
- **Task file:** none yet (`tasks/Backend/Backlog-Phase-2-Plus/BL-04-BE.md` does **not** exist — the `planner` produces the task breakdown; this brief feeds it). **Flag to lead.**
- **FR-IDs:** FR-CI-4 (vector store for chunk embeddings). Underpins FR-CI-1/2/3.
- **BRD goal:** **G5** (scalable curriculum platform) + **G2** (learning outcomes — the graph powers adaptivity/remediation).
- **Phase / Epic:** Backlog Phase 2+ — Curriculum Intelligence. **SP 3.** Story Note: *"Schema is designed during MVP (P3) even though the pipeline is Phase 2+."*
- **Product-decision context:** 4 subjects (Math, Science, Arabic, English; no Social Studies); no teacher role. PostgreSQL + pgvector + .NET 10 (confirmed, SRS §6/§7).

## Business context & value
- This is the **load-bearing data foundation** for the entire 3-stage curriculum pipeline (see `info/Multimodal_Parsing_vs_Curriculum_Ingestion_vs_Knowledge_Graph.md`). Nothing in BL-01/02/05/03 can persist without it.
- **Who benefits:** indirectly students (grounded AI tutor via RAG over `CurriculumChunk`; adaptive paths via the graph) and admins (real ingested curriculum). Directly, the backend engineers building BL-01..03/05.
- **Strategic framing:** the SRS deliberately mandates modelling this schema **now** (during MVP) so the relational graph slice (P2-11) and the future ingestion pipeline share one shape and the move to a graph DB (Neo4j, Phase 3+) is an extension, not a rewrite.
- **Success measured by:** entities + migrations exist; `chunk_embeddings` table provides a separate versioned pgvector store (NOT an inline column on `CurriculumChunk`); `ContentSource`/`Chapter`/`ProvenanceMapping` provenance tree is in place; `CurriculumVersion` entity models the immutable-publish lifecycle; `KGSuggestion` queue entity is defined; schema matches SRS §6 (FKs, metadata, difficulty); migrations apply cleanly on PostgreSQL.

## What P2-11 already delivered (the delta this story actually owns)
**Critical:** `KnowledgeNode` and `KnowledgeEdge` **already exist and are built** in the **`learning`** module (P2-11, status ✅ audited 2026-06-07). BL-04 must **not** re-create them. Confirmed in code:
- `backend/src/Modules/Learning/Learnexia.Modules.Learning.Domain/Entities/KnowledgeNode.cs` — `Name`, `NodeType` (`KnowledgeNodeType` enum), `SubjectId`, `GradeId`, `Difficulty` (int 1–5), nullable `SkillId` (wraps a Skill via filtered unique index), `SourceEdges`/`TargetEdges` nav collections.
- `backend/src/Modules/Learning/Learnexia.Modules.Learning.Domain/Entities/KnowledgeEdge.cs` — `SourceNodeId`, `TargetNodeId`, `RelationshipType` (`EdgeRelationshipType` enum: Prerequisite/Related), `Strength` (`decimal(5,4)`, default 1.0), self-referential FKs with `DeleteBehavior.Restrict`.
- EF configs (`KnowledgeNodeConfig`/`KnowledgeEdgeConfig`), `AddSkillGraphTables` migration, `SkillGraphValidator` (acyclic DFS) + tests, seeded edges, `GetPrerequisitesOf`/`GetUnlockedBy` query API (`KnowledgeGraphController`), and `LearningPathEngine` consuming the edges — **all done**.

**Therefore BL-04's real, remaining scope is:**
1. **`CurriculumChunk`** entity — WITHOUT an inline pgvector column (Decision D: embeddings live in a separate `chunk_embeddings` table). The chunk carries Content, Metadata, Difficulty, ConceptId, and a `ProvenanceRef` linking to the provenance tree.
2. **`chunk_embeddings`** table — separate versioned embedding store: `(Id, ChunkId FK, Model, Version, Dimension, Vector vector(1024))`. This enables dual-model coexistence during embedding model migrations. BGE-M3 / N=1024 is the default.
3. **Provenance tree:** `ContentSource` (types: Book, Image, Worksheet, VideoTranscript) + `Chapter` + `ProvenanceMapping (ChunkId, PageOrBlockRef, PedagogicalNodeId, NodeType)`. These are Decision B.
4. **`CurriculumVersion`** entity with status {Draft, Active, Archived} — Decision C. Connects to P7-05 (the admin publish/version story for the UI surface). BL-04 models the entity + status; P7-05 owns the admin surface that switches versions.
5. **`KGSuggestion`** entity — the suggestion queue for auto-inferred KG edges before human approval (Decision E). Keeps inferred edges separate from the published `KnowledgeEdge` table.
6. **`SkillKey` column on `KnowledgeNode`** (add to `learning` module) — stable semantic identifier that survives version switches so student mastery/XP/streaks are not orphaned. Format: `{SubjectCode}.{GradeLevel}.{UnitSlug}.{SkillSlug}`. This is a **small migration to the `learning` module** (not a new module), coordinated with the Learning team.
7. The **architectural decision** of whether the curriculum-intelligence tables live in a **new `curriculum` module** or are folded into `learning`. This is the single biggest open question — see Open Questions and CLAUDE.md "ask before new modules". **Regardless of placement, `KnowledgeNode`/`KnowledgeEdge` stay in `learning`** — the `Curriculum` module is their logical owner/validator, not their physical home. This ownership-vs-location split is decided and must not be re-litigated. See `docs/briefs/curriculum-system-of-record.md` §2.

2. A separate **`chunk_embeddings`** table exists with `(Id, ChunkId FK, Model varchar, Version varchar, Dimension int, Vector vector(1024))`, enabling multi-model coexistence during migrations (Decision D). pgvector extension is enabled. A round-trip write/read of a `chunk_embeddings` row passes.

7. `KnowledgeNode`/`KnowledgeEdge` requirements in the story are satisfied by the **existing P2-11 tables** — BL-04 adds nothing that conflicts. The `curriculum` module is their logical owner/validator; they remain physically in `learning`.

## Affected modules & data

### Module — DECISION REQUIRED
- The story says "a **new `curriculum` module**". CLAUDE.md and the user's standing memory both say **never scaffold a new backend module without asking the lead/user first**. **The new-module decision must be made by the lead before db-migration runs.** Two viable shapes:
  - **(A) New `curriculum` module** (`curriculum` schema): owns `CurriculumChunk`. `KnowledgeNode`/`KnowledgeEdge` **stay in `learning`** (they are live and consumed by P2-04/P3-08/P3-10). Cross-module needs go through `Shared.Contracts` integration events / interface seams — **no cross-module FK** (CLAUDE.md rule 1). The SRS §6 `CurriculumChunk.ConceptId → Concept` FK then becomes a **plain int reference**, not an EF FK (since `Concept` lives in `learning`).
  - **(B) Fold `CurriculumChunk` into `learning`** (`learning` schema), next to the already-built graph. Keeps the `ConceptId` FK real and avoids a new module entirely. Cleanest given the graph already lives there; the cost is a heavier `learning` module.
- **Recommendation:** lead decides. Option B is the lower-risk path that respects "ask before new modules" and keeps the SRS `Concept→CurriculumChunk` FK enforceable; option A matches the literal story text but introduces a cross-module boundary that the SRS ERD's FKs don't respect.

### Existing entities (do not modify)
- Learning hierarchy: `Grade → Subject → Unit → Lesson`, `Concept → Skill`, `Lesson —o1 Skill` (P2-01).
- Graph: `KnowledgeNode`, `KnowledgeEdge` (P2-11, **built**).
- `LearningDbContext` (`learning` schema, Npgsql, deferred-commit UoW, audit stamping). Migrations auto-apply via `LearningModule.InitializeAsync`.

### New entities (this story)

- **`CurriculumChunk`** — SRS §6 fields: `Id PK`, `ConceptId FK` (or plain int per module decision), `Content` string, `Metadata` string, `Difficulty` string, `ProvenanceRef` (FK/string ref to the provenance Block — see below). **No inline vector column** (Decision D — embeddings live in `chunk_embeddings`). Mirror `AggregateRoot` base.

- **`chunk_embeddings`** — `(Id bigserial PK, ChunkId int FK → CurriculumChunk, Model varchar(64), Version varchar(32), Dimension int, Vector vector(1024), CreatedAt timestamptz)`. The default dimension is 1024 for BGE-M3 / Cohere embed-multilingual-v3. A different-dimension model would require a separate table (see `docs/briefs/curriculum-system-of-record.md` §4). ANN (HNSW/IVFFlat) index goes on `chunk_embeddings.Vector` — deferred to BL-05/P3-07.

- **`ContentSource`** — `(Id PK, Type enum {Book,Image,Worksheet,VideoTranscript}, Title string, Publisher string nullable, Edition string nullable, Language ContentLanguage, GradeId int)`. Provenance tree root (Decision B).

- **`Chapter`** — `(Id PK, ContentSourceId FK, Number int, Title string, PageStart int nullable, PageEnd int nullable)`. One chapter has many Blocks/Pages.

- **`ProvenanceMapping`** — `(Id PK, ChunkId FK → CurriculumChunk, ContentSourceId FK, ChapterId FK nullable, PageOrBlockRef string, PedagogicalNodeId int, PedagogicalNodeType string)`. The many-to-many link between the provenance tree and the pedagogical tree (a chapter feeds multiple lessons; a concept may source from multiple books).

- **`CurriculumVersion`** — `(Id PK, SubjectCode string, Language ContentLanguage, Status enum {Draft,Active,Archived}, CreatedAt, PublishedAt nullable, PublishedByUserId int nullable, ArchivedAt nullable)`. Links to P7-05 (that story's admin surface switches Status; BL-04 just models the entity). Exactly one Active version per (SubjectCode, Language) is enforced by a filtered unique index.

- **`KGSuggestion`** — `(Id PK, SourceNodeId int FK → KnowledgeNode, TargetNodeId int FK → KnowledgeNode, RelationshipType EdgeRelationshipType, Strength decimal(5,4), SourceCurriculumDocumentId int FK nullable, InferenceModel string, Status enum {Pending,Approved,Rejected}, ReviewedAt nullable, ReviewedByUserId int nullable, CreatedAt)`. The human-review queue for LightRAG-inferred edges (Decision E). Lives in chosen module (same schema as the rest of BL-04).

- **`SkillKey` column on `KnowledgeNode`** — add `SkillKey varchar(200)` nullable initially (for backfill), with a unique partial index on non-null values. Format: `{SubjectCode}.grade{N}.{unitSlug}.{skillSlug}`. This migration touches the `learning` module — coordinate with the Learning team.

## Handoff → db-migration
- **New entities** in the chosen module's `Domain/Entities/`: `CurriculumChunk`, `ChunkEmbedding`, `ContentSource`, `Chapter`, `ProvenanceMapping`, `CurriculumVersion`, `KGSuggestion`. All derive from `AggregateRoot`, mirror `Concept.cs`/`Skill.cs`.
- **`CurriculumChunk`:** NO `EmbeddingVectorRef` inline vector column (Decision D). Fields: `Id`, `ConceptId` (FK or plain int per module decision), `Content`, `Metadata`, `Difficulty`, `ProvenanceRef` (string or FK to a provenance block). Add `DbSet<CurriculumChunk>` to chosen DbContext.
- **`chunk_embeddings`:** add the `pgvector` PostgreSQL extension (`CREATE EXTENSION IF NOT EXISTS vector;` before this table) and the **`Pgvector` + `Pgvector.EntityFrameworkCore`** packages (add to `Directory.Packages.props` — **shared file, serialize per PARALLELISM**). Configure Npgsql with `o.UseVector()` on the chosen DbContext. `ChunkEmbedding` entity: `(Id bigserial, ChunkId FK → CurriculumChunk ON DELETE CASCADE, Model varchar(64), Version varchar(32), Dimension int, Vector vector(1024), CreatedAt)`. EF config: map `Vector` to pgvector type. Add a code comment: "Default dimension=1024 for BGE-M3/Cohere-embed-multilingual-v3. A different-dimension model requires a new table — see curriculum-system-of-record.md §4." ANN index (HNSW/IVFFlat) deferred to BL-05/P3-07.
- **Provenance tree EF configs:** `ContentSourceConfig`, `ChapterConfig`, `ProvenanceMappingConfig`. Indexes: FK indexes on `ChapterId`, `ContentSourceId`; composite index on `(ChunkId, ContentSourceId)` on `ProvenanceMapping`.
- **`CurriculumVersion` config:** filtered unique index on `(SubjectCode, Language)` where `Status = 'Active'` — enforces exactly one Active version per tree.
- **`KGSuggestion` config:** indexes on `Status` (queue scans), on `(SourceNodeId, TargetNodeId, RelationshipType)` (idempotency checks). FK to `KnowledgeNode` — note: if `KGSuggestion` is in the `curriculum` module and `KnowledgeNode` is in `learning`, this is a cross-module reference; use plain int columns (no EF nav), document the constraint. If option B (fold into `learning`), use real FKs.
- **`SkillKey` on `KnowledgeNode` (learning module migration):** `ALTER TABLE learning."KnowledgeNodes" ADD COLUMN "SkillKey" varchar(200) NULL;` + unique partial index `WHERE "SkillKey" IS NOT NULL`. This migration touches the `learning` module's migration history — must be sequenced carefully (BL-04 adds it via a `learning` module migration, not a `curriculum` migration).
- **Migration sequencing:** (1) enable vector extension; (2) create curriculum tables (CurriculumChunk, chunk_embeddings, ContentSource, Chapter, ProvenanceMapping, CurriculumVersion, KGSuggestion); (3) add SkillKey to learning's KnowledgeNode. Three migrations may be needed (or two if combining curriculum tables).
- **No changes to `KnowledgeNode`/`KnowledgeEdge` structure** beyond adding `SkillKey` — they are built and consumed; touching them risks P2-04/P3-08/P3-10.
