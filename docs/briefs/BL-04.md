## Summary & traceability

- **Task (one line):** Extend the already-scaffolded `Curriculum` module's persistence with the provenance tree, version lifecycle fields, and the KG suggestion queue, and add a stable `SkillKey` column to `learning.KnowledgeNode` — so the BL-01..05 ingestion pipeline + RAG retrieval + KG review share one complete schema.
- **User story:** BL-04 (Technical Enabler, SP 3). **Requirement:** FR-CI-4 (underpins FR-CI-1/2/3).
- **BRD goal:** G3 — adaptive/personalized learning (curriculum intelligence is the data substrate for RAG + the prerequisite graph that drives learning paths).
- **Epic / phase:** Curriculum Intelligence · Backlog Phase 2+ (schema modeled during MVP so P3-07 retrieval and the BL pipeline share one schema).
- **Pipeline shape:** `analyzer → planner → db-migration (all tasks) → reviewer`. No designer (no UI). No api-tester (BL-04 adds zero controllers — BE-6 persistence smoke test substitutes). No security-auditor (no auth/authz, no PII, no upload, no AI prompts, no secrets; the SkillKey data migration touches structural seed rows only, not user/child data).

## Business context & value

- **Who benefits:** indirectly the student (RAG-grounded explanations + a validated prerequisite graph → correct unlock/remediation) and the admin/content team (provenance traceability — "this chunk came from Chapter 5, p.47 of the Grade-4 Math textbook"; immutable publish/versioning; a human review queue that keeps the KG a product moat). No direct end-user surface in BL-04.
- **Success measure:** all migrations (curriculum + learning) apply cleanly on PostgreSQL+pgvector; the persistence smoke test round-trips a chunk + a 1024-d embedding and proves the fixed-dimension constraint; `KnowledgeNode.SkillKey` exists and (per Q3) is populated. Success = structural readiness for BL-01/02/03/05 and the already-built P3-07 retrieval.

## Open questions / assumptions / risks

**Q1 (new module) — RESOLVED:** option A; module built by P3-07 (OQ-6 CLOSED). BE-1 skipped.

**Q2 (embedding model) — RESOLVED:** BGE-M3, vector(1024), separate `chunk_embeddings_bge_m3` table — already shipped. BE-7 skipped.

**Q3 — SkillKey backfill + NOT NULL scope → RECOMMEND: keep backfill (BE-13) in BL-04; DEFER the NOT NULL flip.** Rationale: P2-11 seed rows need keys so the cross-version history-preservation guarantee (Decision C) holds — that belongs with column introduction. But NOT NULL now is risky: (a) slug derivation may need `Skill→Lesson→Unit` joins; any un-slugifiable seed row aborts the whole deploy; (b) all future `KnowledgeNode` writers (BL-03 KG approval) must set `SkillKey` before NOT NULL is safe. Recommend nullable column + partial-unique index in BL-04; a follow-up (or BL-03) adds NOT NULL once all writers confirmed. **Lead to confirm.**

**Q4 — CurriculumVersion vs P7-05 → FINDING: NOT the same entity; complementary layers.** Verified: P7-05 (`20260608155437_P7_05_AddLifecycleStateAndContentVersions`) created `learning.ContentVersions` (`EntityType`, `EntityId`, `VersionNumber`, `Snapshot` jsonb, `PublishedByUserId`, `PublishedAtUtc`, `Language`) + per-entity `LifecycleState` — a per-content-entity snapshot log in the **learning** schema. BL-04's `CurriculumVersion` (curriculum schema) is a **tree-level** publish unit keyed on `(SubjectId, Language)` with `{Draft,Active,Archived}`. The task file's "same entity P7-05 uses" is **incorrect against shipped code.** **Recommend:** treat `CurriculumVersion` as the curriculum-tree publish unit; do NOT merge into `learning.ContentVersions`. `Active = Published` is a conceptual alignment only. **Lead to confirm** the two-layer interpretation (recommended).

**Q-A (new, from code) — `SubjectCode` vs `SubjectId` on CurriculumVersion.** P3-07 shipped `SubjectId`(int) and keys the Active-unique index on `(SubjectId, Language)`. The task file + system-of-record §3 specify `SubjectCode`(string)/`(SubjectCode, Language)`. **Risk:** adding a `SubjectCode` column duplicates the keying dimension and makes the filtered-unique index ambiguous. **Recommend:** keep `SubjectId` canonical (already indexed + seeded); treat `SubjectCode` as documentation-only or skip. Do NOT add a second unique index. **Lead to confirm** before BE-9.

**Q-B (new, from code) — `EdgeRelationshipType` reuse across modules.** `KGSuggestion.RelationshipType` is specced to reuse learning's `EdgeRelationshipType`, but isolation forbids curriculum referencing a learning enum. **Recommend:** define a local curriculum enum with identical members (or store int with a documented mapping). **Confirm** the mirror approach.

**Q-C (new, from code) — `SourceCurriculumDocumentId` FK target absent.** Specced as FK→`CurriculumDocument`, a BL-01 entity NOT in the codebase. **Recommend:** model as nullable plain int (no FK) in BL-04; BL-01 adds the FK later. Avoids a forward-reference that breaks the migration.

**Assumptions:** compose dev DB has pgvector (proven by `InitialCurriculum`); `Curriculum.IntegrationTests` has (or can add) the Testcontainers pg+pgvector harness — verify the image tag includes pgvector before writing BE-6.

**Risks:**
- **Re-create-table failure (highest):** any migration re-creating `CurriculumChunks`/`CurriculumVersions`/`chunk_embeddings_bge_m3` fails on a DB where `InitialCurriculum` ran. BE-9 MUST be ALTER-only; reviewer diffs the generated migration for `CreateTable` against those three names.
- **Learning-snapshot drift:** BE-11/12 regenerate `LearningDbContextModelSnapshot`; conflicts with any concurrent learning-model story → serialize.
- **Slug-derivation gaps (BE-13):** un-slugifiable seeds → duplicate/empty keys → partial-unique-index violation. Deferring NOT NULL (Q3) contains the blast radius.
