## Business context & value

- **Who benefits:** the **student** directly — answer a question → see XP tick → cross a threshold → level up → dopamine. The dashboard goes from "0 XP" placeholder to "real XP earned in your last session." This is the headline FR-GM-1 reward loop.
- **Why it matters now:** without XP, every Phase-3 follow-on is hollow. Streaks (P4-03) award `StreakBonus` XP, badges (P4-05) include "XP earned" rules, missions (P4-06) reward XP, leagues (P4-07) rank by weekly XP, the Redis read model (P4-10) is *primarily* an XP/leaderboard cache, the dashboard XP-bar (P4-08) renders this number. **P4-02 is the keystone of Phase 3.**
- **Success measurement:** every `AnswerSubmittedIntegrationEvent` with `CorrectAnswerCount=1` writes exactly one `XpAward(reason=CorrectAnswer, amount=10)`; every `LessonCompletedIntegrationEvent` writes exactly one `XpAward(reason=LessonCompleted, amount=50)`; the dashboard's `Xp` field reflects the running total within p95 < 500ms; a duplicate event (same `EventId`) does NOT double-award; a brand-new student starts at XP=0, Level=1.
- **Deterministic principle (BRD §8 / FR-AI-6):** the XP rule is a constant table + a pure function — no AI, no randomness, no probabilistic engine. The level curve is a deterministic formula or lookup table (open question Q3).

## Acceptance criteria (verbatim from story + testable backend gates)

From `P4-02-xp-and-levels.md`:

1. **AC1 — XP is awarded per event** (e.g., correct +10, quiz +20, lesson +50, streak bonus +30) **via event handlers.**
   - Backend gate: `INotificationHandler<AnswerSubmittedIntegrationEvent>` in Gamification awards `XpReason.CorrectAnswer = +10` when `CorrectAnswerCount > 0` (i.e., the answer was correct). `INotificationHandler<LessonCompletedIntegrationEvent>` awards `XpReason.LessonCompleted = +50`. `QuizCompleted` and `StreakBonus` paths are **stubs awaiting P4-03/quiz-boundary** (return without write; log a TODO).
   - The handler is in `Gamification.Application/IntegrationEventHandlers/` (mirrors Notifications pattern).

2. **AC2 — Each award writes an `XPTransaction` ledger entry** (amount, reason, timestamp).
   - Backend gate: every successful XP write inserts one append-only `XpAward` row (amount, reason enum, created-at, `StudentId`, plus the `OriginEventId` for idempotency). The ledger is append-only — no `UpdateAsync`, no `RemoveAsync`. (Story uses `XPTransaction`; the entity name `XpAward` is a stylistic recommendation per the `XpReason.cs` comment that already uses "XP award" language — see Open Question Q1.)

3. **AC3 — Level is computed from total XP and updates immediately on the dashboard/XP bar.**
   - Backend gate: a per-student snapshot (`StudentXpProfile`: `StudentId, XpTotal, Level, UpdatedAt`) is upserted in the **same UoW** as the `XpAward` insert. The level is recomputed from `XpTotal` via a pure `LevelCurve.LevelFor(int xp)` function. The dashboard's existing `GET /api/Learning/Dashboard` is extended to read `StudentXpProfile.XpTotal` (and optionally `Level`) instead of returning hard-coded `0`. **Open question Q2** — how the dashboard reaches the Gamification module's read model is a cross-module concern (NOT a cross-module FK; recommend a `Shared.Contracts` query seam or the future P4-10 Redis read model).

4. **AC4 — XP totals are consistent (no double-award for the same event).**
   - Backend gate: each `XpAward` row carries `OriginEventId : Guid` with a **unique index per `(OriginEventId, Reason)`**. On a duplicate event delivery, the handler attempts the insert, catches the unique-constraint violation (or pre-checks `Any(... == eventId)`), logs `"P4-02: duplicate event ignored"`, and returns silently. Tested by an integration test that submits the same event twice.

### C. Integration-event handlers (`P4-02-BE-3` + `P4-02-BE-4`)

Both handlers live at `Gamification.Application/IntegrationEventHandlers/` and follow the **established `UserRegisteredIntegrationEventHandler` shape** (own DbContext, idempotency check, fail-soft logging).

**Critical decision (Open Question Q5):** the cross-module event arrives at the handler **inside the producer's DbContext request scope**. The handler must NOT write through `GamificationDbContext` synchronously inline (that would couple Gamification's commit to Learning's UoW). Two valid patterns:

- **Pattern A (recommended) — handler sends an internal `ICommand` via `IMediator`:** `Handle(LessonCompletedIntegrationEvent e, CT ct) => await _mediator.Send(new AwardLessonCompletedXpCommand(e.EventId, e.StudentId, e.LessonId, e.SkillId), ct);`. The command runs through Gamification's `UnitOfWorkBehavior` — clean commit boundary, transactional within Gamification, decoupled from Learning's UoW. **Matches the pattern recommended in the original `uow-and-gamification` brief §C.** **Use this.**
- **Pattern B (rejected) — handler writes directly via `GamificationDbContext`:** mirrors the Notifications pattern but skips the UoW behavior, which (a) breaks the audit-stamping path (uses `SaveChangesAsync` directly instead of the audited overload), (b) skips after-commit domain-event dispatch (no `StudentLeveledUpDomainEvent` dispatch path), (c) re-introduces the per-handler save coupling ADR 0001 was written to remove. **Reject for P4-02.**

**Award commands (Pattern A — recommended):**
- `AwardLessonCompletedXpCommand : ICommand<BaseResponse<int>>` — fields `(Guid OriginEventId, int StudentId, int LessonId, int SkillId)`. Handler steps:
  1. `if (await _repo.AnyXpAwardWithOriginEventAsync(eventId, XpReason.LessonCompleted, ct)) return Success(0);` — **AC4 idempotency** — log info "duplicate event ignored," do nothing else.
  2. `var profile = await _repo.GetXpProfileByStudentIdAsync(studentId, ct) ?? StudentXpProfile.CreateFor(studentId);` (lazy on first event).
  3. `var amount = GamificationConstants.XpRewards.For(XpReason.LessonCompleted);`
  4. `var award = XpAward.Create(studentId, amount, XpReason.LessonCompleted, eventId, originLessonId: lessonId, originSkillId: skillId);` → `await _repo.AddXpAwardAsync(award, ct);` (stage only).
  5. `var newTotal = profile.XpTotal + amount; var newLevel = LevelCurve.LevelFor(newTotal); profile.ApplyAward(amount, newLevel);` → either `await _repo.UpsertXpProfile(profile)` (stage only) or attach as new if it was created in step 2.
  6. `return Success(amount);`. The UoW commits both rows + dispatches `StudentLeveledUpDomainEvent` if a level changed.

- `AwardAnswerSubmittedXpCommand : ICommand<BaseResponse<int>>` — same shape, except: skip when `CorrectAnswerCount == 0` (the answer was wrong → no XP for incorrect answers per FR-GM-1 "correct +10"). The notification handler short-circuits before even sending the command in that case (cheaper).

**Validators:** FluentValidation `IValidator<AwardLessonCompletedXpCommand>` checking positive IDs and non-zero `OriginEventId`. (Defends against malformed cross-module payloads even though `IIntegrationEvent` is producer-side.)

### D. Dashboard read seam (`P4-02-BE-5` — touches Learning module)

**Open Question Q2 — pick one.** The dashboard handler today returns `Xp = 0` (verified at `GetDashboardQueryHandler`). To put a real number there without violating module isolation:

- **Q2-Option A (recommended) — `Shared.Contracts/Gamification/IStudentXpQuery`:** one-method interface `Task<StudentXpSnapshot?> GetForStudentAsync(int studentId, CT)` returning `(int XpTotal, int Level)`. Implement in `Gamification.Application/Queries/StudentXpQuery.cs` against `GamificationDbContext`. Register in `AddGamificationApplication()`. Learning's `GetDashboardQueryHandler` injects `IStudentXpQuery` (defaulting to `(0, 1)` when null — first-ever student with no XP yet). Mirrors `IParentChildQuery` precedent in `Shared.Contracts/Parent/IParentChildQuery.cs`. **No cross-module DbContext reference, no cross-module project reference, no cross-module FK.** This is the established pattern.
- **Q2-Option B (rejected) — Learning's dashboard reads `GamificationDbContext` directly:** breaks module isolation rule 1.
- **Q2-Option C (deferred) — Redis read model from P4-10:** out of scope; P4-02 ships Postgres-only reads, P4-10 swaps in Redis behind the same `IStudentXpQuery` seam.
- **Q2-Option D (rejected) — Publish a `StudentXpUpdatedIntegrationEvent` and let Learning maintain a denormalized cache:** over-engineered for Phase 3; ghost-event risk doubles.

In Learning's `GetDashboardQueryHandler`, after the existing logic, before constructing `DashboardDto`, call `IStudentXpQuery.GetForStudentAsync(studentId, ct)` and use the returned `(XpTotal, Level)`. Remove the `// TODO P4-02` comment. **The `DashboardDto.Xp` field is already `int` (non-nullable) — no DTO contract change.** A `Level` field may need to be added to `DashboardDto`; see **Open Question Q6**.

### E. Optional read controller (`P4-02-BE-6` — see Q4)

`GET /api/Gamification/Xp/Me` `[Authorize]` returning `BaseResponse<StudentXpDto>` `(int XpTotal, int Level, int XpToNextLevel)`. Lets FE poll the XP bar directly without going through the dashboard endpoint. **Recommended** because the P4-08 XP-bar (and P4-10 Redis read model) will need a dedicated endpoint anyway. Skip if lead defers.

### F. Hardening (do NOT skip)

- **`OriginEventId` idempotency** — pre-check via `AnyXpAwardWithOriginEventAsync` AND a DB unique index (defense-in-depth). The pre-check is a fast happy path; the unique index protects against the race window between two concurrent deliveries of the same event.
- **Race condition under concurrent events for the same student** — two answers in flight could read the same `XpTotal` and race to upsert different totals. **Recommendation:** open the Gamification UoW transaction with `IsolationLevel.RepeatableRead` (or use a row-level lock via `Database.ExecuteSqlInterpolated($"SELECT 1 FROM \"gamification\".\"StudentXpProfiles\" WHERE \"StudentId\"={studentId} FOR UPDATE", ct)` before the read). Document the choice; verify no deadlock under the integration tests. **Open Question Q7** — confirm strategy.
- **No `ex.Message` echoed** to clients in any controller's `ServerError<T>()` path (rule from P2-08 security audit).
- **Conventions:** module isolation (no cross-module FKs, no cross-module project refs except via `Shared.Contracts`); `ILoggerManager` only; `BaseResponse<T>` envelopes via `BaseResponseHandler` if any controller; `Successed` spelling preserved.

**Must-pass cases:**

1. **Happy path — correct answer awards CorrectAnswer XP.** Seed student → submit a correct MCQ answer (question with non-null `SkillId`) → poll dashboard → assert `Xp == 10`, `Level == 1`. (Tests AC1 + AC2 + AC3 end-to-end.)
2. **Happy path — wrong answer awards NO XP.** Submit a wrong answer → poll dashboard → assert `Xp == 0`. (Negative case for FR-GM-1's "correct +10".)
3. **Happy path — lesson completion awards LessonCompleted XP.** Complete an attempt → poll → assert `Xp == 50` (or 60 if a prior correct answer is already in the attempt: 10 + 50).
4. **End-to-end accumulation.** Complete a lesson with 5 correct + 2 wrong answers → assert `Xp == 50 (lesson) + 5*10 (correct) = 100`.
5. **Idempotency — duplicate event delivery does NOT double-award.** Test infra hook: subscribe to the event and re-publish it once via `IPublisher.Publish(...)` from the test host (same `EventId`). Assert `XpAwards` row count = 1, `Xp` unchanged. (Tests AC4 + the unique-index gate.)
6. **Idempotency — null SkillId path.** The producer (P2-07) already skips publication when `Lesson.SkillId IS NULL`; assert: completing a lesson whose skill is null produces **zero** XP rows (no consumer reaction because no event was published). Belt-and-suspenders documentation.
7. **Level boundary crossing.** Seed a student to `XP = 99`, submit a correct answer → `XP = 109`, `Level = 2` (crosses the `100` threshold). Defaults: per the table-based curve.
8. **Brand-new student zero-state.** Fresh student, never submitted anything → `GET /api/Learning/Dashboard` returns `Xp=0, Level=1`. **No `StudentXpProfile` row exists yet** — `IStudentXpQuery.GetForStudentAsync` returns `null`, Learning falls back to `(0, 1)`. Verified by querying the DB after the call.
9. **Cross-student isolation.** Two students; one earns XP, the other doesn't. Assert their dashboards are independent (no leak). Tests the per-`StudentId` index/key.
10. **Handler isolation — a throwing sibling handler does not break the XP award.** Register a throwing in-test `INotificationHandler<LessonCompletedIntegrationEvent>` alongside the real Gamification handler; complete an attempt → XP is still awarded (the isolated publisher works for Gamification's handler too).
11. **Ghost-event-on-rollback (R1 documentation).** Force the Learning UoW to roll back AFTER publishing the event (an artificial throw in a test-only behavior post-publish). Assert: XP IS awarded for the rolled-back attempt (the acknowledged ADR-0002 trade-off). This isn't a "fix this" test — it documents the known limitation so a reviewer doesn't open a bug. Skip if too fragile to wire up cleanly; document inline instead.
12. **Envelope sanity.** `"successed":` lowercase-d camelCase preserved in all new responses.
13. **`AwardLessonCompletedXpCommand` skipped when `CorrectAnswerCount == 0` is N/A** — the `Lesson` event always carries `CorrectAnswerCount` from the actual answer-count; for an all-wrong lesson the lesson XP STILL fires (story says "lesson +50" unconditionally on completion). Confirm this with the lead — **Open Question Q3.bis**.

## Handoff → security-auditor

**Recommend running it.** Small but real attack surface:

- New cross-module event consumer running deterministic writes — confirm no PII in `XpAward` (only int IDs + amount + enum + Guid; **no name, email, age**).
- Confirm no client-controllable XP grant path — `XpAward` is **only** written from the integration-event handlers; no admin/manual endpoint this cycle (Q4 read-only).
- IDOR — the optional `GET /api/Gamification/Xp/Me` endpoint is JWT-derived (`_currentUser.UserId`), no `studentId` route/query param. Same IDOR-proof-by-construction as P2-09.

- No `ex.Message` echo from any new controller path (preserve P2-08 audit invariant).
- Cross-module event handler runs under the **publisher's JWT scope** — confirm the handler does NOT inadvertently leak the JWT's `_currentUser.UserId` into the `XpAward.StudentId` field. **`StudentId` MUST come from the event payload, NOT from `_currentUser`** (the event was raised under the student's own action, but module-isolation principle says: trust the payload, not the ambient scope). **Q1 — Module placement: NEW Gamification module vs. fold into Learning. [HIGHEST PRIORITY — CLAUDE.md rule "ask before scaffolding a new backend module" applies.]**

**Q2 — Dashboard read seam: how does Learning read XP from Gamification without violating module isolation?**
- **Recommend Option A — `IStudentXpQuery` in `Shared.Contracts/Gamification/`.** One-method interface, Gamification implements, Learning injects. Mirrors `IParentChildQuery` in `Shared.Contracts/Parent/`. Future P4-10 swaps the implementation for a Redis-backed one without changing the dashboard handler. Clean module isolation; established precedent.
- **Alternatives:** B (Learning reads Gamification's DbContext directly — rejects rule 1), C (Redis from P4-10 — deferred), D (publish a `StudentXpUpdatedIntegrationEvent` and Learning maintains a denormalized cache — over-engineered).

**Q3 — XP rule values & level curve formula.**
- **Recommend FR-GM-1 example values as defaults:** `CorrectAnswer = +10`, `QuizCompleted = +20` (stub — no producer this cycle), `LessonCompleted = +50`, `StreakBonus = +30` (stub — no producer this cycle). These are *example values* in SRS, not authoritative; using them as MVP defaults follows the precedent set by the `uow-and-gamification` brief.
- **Recommend table-based level curve:** thresholds `[0, 100, 250, 500, 1000, 2000, 4000, 7000, 11000, 16000]` for L1–L10; L11+ = `10 + floor((xp - 16000) / 5000)`. Rationale: kid-friendly early-game (L2 in ~10 correct answers), smooth long-game. **Lead-decision** — alternatively a pure formula (e.g. `level = floor(sqrt(xp / 100)) + 1` — open-ended but rougher early-game; or `level = floor(xp / 100) + 1` — too linear).
- **Q3.bis — does `LessonCompleted` XP fire when the student got 0 correct answers?** SRS says "lesson +50" with no qualifier. **Recommend YES (unconditional on completion)** — finishing a lesson is itself worthy of recognition; granularity is in the `CorrectAnswer` per-answer awards. **Confirm.**

**Q4 — Do we ship `GET /api/Gamification/Xp/Me` in this story?**
- **Recommend YES.** P4-08 (XP bar UI) and P4-10 (Redis hot path) both expect a dedicated XP endpoint; shipping it now means P4-08-FE doesn't have to wait for it, and P4-10 has a swap-point. Light cost: one controller, one query handler, mirrors `DashboardController`. Skip only if scope-trimming.

**Q5 — Cross-module handler pattern: send `ICommand` to MediatR, or write directly in the handler?**
- **Recommend Pattern A — send `ICommand` from the notification handler.** Runs through Gamification's `UnitOfWorkBehavior` (clean commit, audit, after-commit dispatch). Decoupled from the producer's UoW. The `uow-and-gamification` brief recommended exactly this. **Pattern B (direct write via DbContext, like `UserRegisteredIntegrationEventHandler`)** is rejected here because Notifications' write is single-row and idempotent-by-business-key, while Gamification's write is multi-row (ledger + profile) + raises a domain event, which is what UoW exists to handle.

**Q6 — Add `Level` to `DashboardDto`?**
- **Recommend YES.** AC3 says "Level is computed from total XP and updates immediately on the dashboard." The current `DashboardDto` has `Xp` but no `Level`. Add `int Level` to `DashboardDto` (non-nullable, default `1` for brand-new students). FE concern in P4-08 / P2-09-FE follow-up. No breaking change — additive field on a positional record (must verify the record-constructor signature remains compatible — alternatively use `init`-only properties).

**Q7 — Concurrency strategy under two simultaneous events for the same student.**
- **Recommend explicit `SELECT ... FOR UPDATE` on `StudentXpProfile` row** inside the command handler, before the read. Reliable, simple in PostgreSQL, no Npgsql gotchas. Alternative: rely on the `UnitOfWorkBehavior`'s transaction's default isolation (READ COMMITTED in PG) + a CAS update — race-prone.

**Q8 — `XpReason` enum: keep `QuizCompleted = 2` even though there's no quiz boundary?**

**Q9 — `StreakBonus = 4` — does this story award streak bonuses at all?**

**Q10 — Per-stack task files** (BE-1/BE-2/…) for `tasks/Backend/Phase-3-Gamification/P4-02-BE.md`?
