## Business context & value
- **Who benefits:** the admin/support operator and the platform's safety posture. Suspend lets support intentionally block an abusive or compromised account; reactivate restores it after review; delete satisfies data-removal/COPPA requests. Children are the sensitive beneficiaries — the UI must make destructive blast radius (cascade) explicit.
- **Value:** a deliberate **governance** state machine surfaced in a console — **distinct from the automatic P1-13 failed-login lockout** (temporary, throttling). The UI copy must never conflate "Suspended" with "temporarily locked."
- **Success measure (from AC):** an admin can suspend (with reason + confirm) and the account can no longer sign in; reactivate restores sign-in and prior reason/history is visible; delete is two-step (typed confirm + reason) and for a parent can cascade to linked children with a clear warning; status badges reflect Active/Suspended/Deleted; already-deleted/illegal transitions are rejected with a clear inline message; only admins can reach any of this.

## Acceptance criteria (testable — the reviewer checks against these)
1. **Lifecycle actions menu** on the user detail (and/or list row) shows only the **legal** actions for the current `AccountStatus`: Active → {Suspend, Delete}; Suspended → {Reactivate, Delete}; Deleted → none (terminal; actions hidden/disabled with an explanatory label). (FE-1)
2. **Suspend** opens a dialog requiring a **non-empty reason** (≤ 500 chars, enforced client-side to match the BE validator) + an explicit confirm; on success the user's status refreshes to **Suspended** and a Suspended badge shows. Copy states this is a **governance** action that **revokes sessions/tokens and blocks sign-in until reactivated**, and is **not** the P1-13 failed-login lockout. (FE-2)
3. **Reactivate** opens a confirm dialog (reason **optional**); surfaces the **prior reason/history** (`lastStatusReason` + `statusChangedAtUtc` from the profile); on success status refreshes to **Active**. (FE-3)
4. **Delete** opens a **two-step** dialog: required reason + a **typed confirmation** (e.g. type the email or `DELETE`) gating the destructive button; for **parent** targets a **cascade-children checkbox** with explicit child-data warning. Sends `confirm: true` only on the final destructive action. On success status refreshes to **Deleted** and the account becomes read-only/terminal. (FE-4)
5. **Errors** from the `BaseResponse` envelope surface **inline** in the dialog, not as silent failures: already-deleted / already-suspended / already-active (400), validation (422), self/SuperAdmin protection (400), and network/5xx — each mapped to clear admin copy (EN + AR). The dialog stays open on error so the admin can retry/cancel. (FE-2/3/4)
6. **Admin-only:** the whole surface sits under the `(admin)` group guarded by `useAdminGuard`; non-admin/anonymous → redirect to `/login`. The backend `AdminOnly` policy is the real gate (the FE guard is UX only). (existing shell)
7. **Mutation hooks** (`useSuspendUser`, `useReactivateUser`, `useDeleteUser`) live in `packages/api-client`, return unwrapped data, and **invalidate** the user profile + user list queries on success so the detail/list re-fetch the new status. (FE-5)
8. **RTL/ar + en + a11y:** all dialog copy is bilingual; dialogs are focus-trapped, labelled, `role="dialog"` + `aria-modal`, ESC/cancel closes, the destructive button is disabled until the gate is satisfied, and errors use `role="alert"` (reuse `AdminErrorBanner`). Logical-edge layout flips correctly under `dir="rtl"`.

## Live backend contract (verified against `AdminUsersController.cs` + handlers — DO NOT change)
All endpoints are class-level `[Authorize(Policy = AuthorizationPolicies.AdminOnly)]` under route base **`api/Admin/Users`**. Anonymous → 401; non-admin → 403. Bodies are JSON; responses are the `BaseResponse<T>` envelope with the success flag spelled **`Successed`** (`successed` in the unwrapped JSON the FE sees).

### Suspend
- **`POST /api/Admin/Users/{id}/suspend`**, body `{ "reason": string }` (reason **required**, max 500).
- Returns **`BaseResponse<string>`** — `data` is a localized success **message string**, NOT the updated profile DTO.
- Behaviour: `AccountStatus → Suspended`, `IsActive = false`; **revokes the Redis refresh token + terminates all tracked sessions** (sign-in blocked going forward). **Residual window (G2):** an already-issued access JWT survives until natural expiry — there is no per-request revocation hook. Emits `AccountSuspendedIntegrationEvent` + `AdminActionPerformedEvent` (P7-12 audit).
- Rejections (HTTP 400, `successed=false`): target already `Deleted` (terminal), already `Suspended`, admin's **own** account, or **SuperAdmin** account. 404 if user not found.

### Reactivate
- **`POST /api/Admin/Users/{id}/reactivate`**, body `{ "reason"?: string | null }` (reason **optional**).
- Returns **`BaseResponse<string>`** (success message string).
- Behaviour: `Suspended → Active`, `IsActive = true`; **no new tokens issued** (the user signs in fresh). Prior `lastStatusReason`/`statusChangedAtUtc` remain on the profile until overwritten. Emits `AccountReactivatedIntegrationEvent` + `AdminActionPerformedEvent`.
- Rejections (400): target is `Deleted` (terminal — cannot reactivate), or already `Active`. 404 if not found.

### Delete (soft-delete)
- **`DELETE /api/Admin/Users/{id}`**, body `{ "reason": string, "confirm": boolean, "cascadeChildren": boolean }`.
- Returns **`BaseResponse<string>`** (success message string), NOT `BaseResponse<bool>`.
- **Two-step confirm gate:** `confirm: false` → **HTTP 424 (FailedDependency)**, no mutation. The FE's final destructive button always sends `confirm: true`, so 424 should not occur in the normal flow — but the hook/dialog must still degrade gracefully if it does.
- Behaviour: `Active|Suspended → Deleted` (terminal), `IsActive = false`, soft-delete only (row retained, **learning history preserved**; **PII anonymization is deferred to a later GDPR/COPPA sweep** — delete here does NOT scrub email/name yet — see Q-4). For a **Parent** target with `cascadeChildren: true`, all linked children are soft-deleted **in the same transaction** (rolls back together on failure). Emits `AccountDeletedIntegrationEvent` + `AdminActionPerformedEvent` **post-commit** (no phantom events on rollback).
- Rejections (400): already `Deleted`, admin's **own** account, **SuperAdmin**. 404 if not found.

> **Contract correction for FE-5:** the task file `P7-07-FE.md` "Contract from Backend" lists `BaseResponse<AdminUserProfileDto>` for suspend/reactivate and `BaseResponse<bool>` for delete. The **live handlers return `BaseResponse<string>` for all three** (success message). The FE must **refetch** the profile/list after success (the response does not carry the new state) — it cannot read the updated `AccountStatus` off the mutation result. Type the hooks as `string` (or `void`) output and rely on query invalidation.
