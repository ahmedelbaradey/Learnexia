## Summary & traceability

- **Task (1 line):** Layer three daily-habit mechanics onto the existing Phase-3 Gamification module — (a) **streak freeze**: a consumable freeze inventory (default cap=2) earned at 7-day streak milestones and auto-consumed by `StreakSweepJob` before a missed-day breaks the streak, raising `StreakFreezeConsumedDomainEvent`; (b) **timed events**: a `TimedEvent` catalog with `StartUtc`/`EndUtc`/`Multiplier`/`Scope`, applied as a MediatR pipeline behaviour over the single `StudentXpProfile.ApplyAward` chokepoint so all XP-awarding paths (lesson, quiz, streak, badge, mission, league) inherit the boost without per-handler edits; (c) **weekly challenges**: a *new mission-catalog dimension* — reuse the P4-06 `MissionDefinition`/`StudentMission`/`MissionProgressLog` schema with a fresh `MissionType.WeeklyChallenge` (or repurpose the existing `MissionType.Weekly` — Q3) and a separate FE/dashboard surface; no schema duplication. All three mechanics close the BRD §10 #4 / FR-GM-2 / FR-GM-3 *"open dials"* note (per FR-GM-9), emit events through P4-01 backbone, and award rewards through the existing XP/badge engine — **no parallel reward path**.

## Business context & value

- **Who benefits:** the **student** directly across all three concerns:
  - **Streak freeze** — the *safety net* half of the daily habit loop. A student who misses a single day after a 14-day streak does NOT lose the entire 14-day arc; the freeze auto-consumes and the streak survives. Pure retention win — converts the *"I broke my streak, why bother starting again"* lapse moment into a *"phew, my streak is safe, I'll be back tomorrow"* recovery moment. Industry-standard Duolingo behaviour.
  - **Timed events** — *chase windows*. Limited-time bonuses (e.g., +100% XP this weekend; +50% league XP Ramadan week) create artificial scarcity-driven engagement spikes. Marketing/ops can fire them ad-hoc to drive DAU/MAU on slow days. Without admin UI in Phase 3, events are seeded + activated via DB/config — but the engine is ready for the P7 admin editor that *will* add UI.
  - **Weekly challenges** — *per-week anchors* distinct from daily missions. Daily missions reset every 24h (commit-then-flip); weekly challenges run Mon-Sun and reward longer-term consistency. Examples: *"complete 25 lessons this week"*, *"answer 100 questions correctly"*, *"maintain a 5-day streak"*. Pairs with the leagues weekly window (P4-07 already uses ISO weeks) so the entire weekly cadence is unified.
- **Why it matters now:** P4-11 is **the last Phase-3 backend story**. The Phase-3 reward economy (XP/streak/hearts/badges/missions/leagues) is complete; P4-11 supplies the *protective* layer (freeze) and the *time-bounded boost* layer (events + weekly challenges). After P4-11, BE4 (Daily Habit System) is fully scoped per the BRD gap analysis. The P4-09 re-engagement nudges already in `main` will gain a fourth signal (*"your freeze saved your streak — keep going"*) once `StreakFreezeConsumedDomainEvent` exists. P4-08 FE motion will have actual data for the freeze counter UI + timed-event banner.
- **Success measurement:**
  - **Streak freeze:** Student who completes 7 consecutive days earns +1 freeze (capped at `MaxFreezeInventory` = 2). When `StreakSweepJob` would otherwise break a streak with `FreezeBalance > 0`, it consumes 1 freeze, shifts `LastActivityDateUtc = yesterday`, raises `StreakFreezeConsumedDomainEvent`, leaves `CurrentStreak` unchanged. Re-engagement nudge fires *"your freeze saved your streak"*. Dashboard shows `FreezeBalance` and the streak survives intact.
  - **Timed events:** When an event is active (window covers `occurredAtUtc`), any XP-awarding command flowing through `ApplyAward` gets `amount * multiplier` (max of overlapping events — Q11). Active events are visible on dashboard banner. When event ends, multiplier reverts to 1× and the cached active-events seam invalidates.
  - **Weekly challenges:** Same shape as missions (instantiated lazily per week, progress logged idempotently, completion awards XP + raises `MissionCompletedDomainEvent`). Distinct from classic weekly missions only by Code prefix (or distinct enum, Q3).
- **Deterministic principle (BRD §8 / FR-AI-6):** every mechanic is **pure arithmetic + a clock comparison**. No AI, no randomness. All dials (`MaxFreezeInventory`, freeze cadence/milestone, multiplier ceiling, event windows) are config-driven via `FreezeOptions` + `TimedEventOptions`, tunable per-env without code change. SRS §4.6 *"dials tunable, not a blocker"* satisfied.

## Acceptance criteria (verbatim from story + testable backend gates)

From `P4-11-streak-freeze-timed-events.md`:

1. **AC1 — Streak freeze: a student can hold a limited number of freezes (earned and/or purchasable with XP/coins per the economy decision); a freeze auto-consumes to preserve the streak on a missed qualifying day. This resolves the `P4-03` open "grace-period" question — `P4-03` and this story must agree on one rule.**
   - Backend gate: `StudentXpProfile.FreezeBalance (int, default 0)` column. New domain methods `GrantFreeze(int delta, int cap)` (additive, raises `StreakFreezeGrantedDomainEvent`) and `ConsumeFreeze()` (decrement-or-throw, raises `StreakFreezeConsumedDomainEvent`). Freezes are **earned, NOT purchased** in Phase 3 (no coins/IAP system — Q2 lock). Earning trigger: every N-day streak milestone via a new `StreakAdvancedFreezeGrantHandler : INotificationHandler<StreakAdvancedDomainEvent>` (Q6 — recommend N=7, cap=2). `StreakSweepJob` modified: for each candidate (`CurrentStreak > 0 AND LastActivityDateUtc < threshold`), if `FreezeBalance > 0` consume one + shift `LastActivityDateUtc = threshold` + raise `StreakFreezeConsumedDomainEvent`; else reset to 0 + publish `StreakBrokenIntegrationEvent` (P4-09 path). **Story explicitly says this story RESOLVES the P4-03 grace question** — closure: no grace window, only freeze (Q1 lock — already aligned with SRS FR-GM-2 rider).

2. **AC2 — Timed events: a scheduled, limited-window event (e.g. weekend XP boost, themed challenge) is configurable with start/end, eligibility, and rewards; it surfaces in the UI with a countdown and ends cleanly.**
   - Backend gate: new `TimedEvent : FullAuditedEntity` catalog (`Code`, `TitleKey`, `Description`, `StartUtc`, `EndUtc`, `Multiplier (decimal)`, `Scope (TimedEventScope enum)`, `IsActive` derived). New `TimedEventOptions` config. **Effect application via MediatR pipeline behaviour** (`XpMultiplierBehavior`) wrapping any command that ultimately calls `ApplyAward` — boost the `amount` parameter before the inner write. Behaviour reads active events via the new `IActiveTimedEventsQuery` (cached). **Eligibility:** Phase 3 = all students (no segmentation); the `Eligibility` field on `TimedEvent` is reserved nullable for P7 admin extension (e.g., `TierFilter`, `GradeFilter`). **Surfaces in UI:** dashboard banner via `DashboardDto.ActiveTimedEvents` populated from the cached query. **Ends cleanly:** new `TimedEventSweepJob` (cron `"*/2 * * * *"` — every 2 min — Q12) fires `TimedEventEndedDomainEvent` exactly once per event transition, which (a) invalidates the active-events cache key and (b) triggers a one-shot re-engagement signal if Q13 = yes.

3. **AC3 — Weekly challenges: a recurring weekly goal (distinct from daily missions `P4-06` and leagues `P4-07`) with progress tracking and a reward on completion.**
   - Backend gate: **reuse the P4-06 mission engine** — `MissionDefinition` with `Cadence` (Q3 — recommend keep `Weekly` AND add `MissionTargetType.WeeklyChallenge` to distinguish from classic weekly missions; OR add a new `MissionType.WeeklyChallenge = 3` enum value and reuse the same engine). Progress tracked via existing `StudentMission.Progress` + `MissionProgressLog` idempotency. Completion awards XP + raises `MissionCompletedDomainEvent` — already wired. **No new tables, no new command handlers** — just 2-3 new seeded definitions in `MissionCatalog.Defaults()` + (optionally) 1 new enum value. The story's *"distinct from daily missions and leagues"* requirement is satisfied by Code-prefix differentiation (`CHALLENGE_*` vs `WEEKLY_*` vs `DAILY_*`) — FE renders them in a separate section.

4. **AC4 — All three emit/consume `P4-01` domain events and grant rewards through the existing XP/badge engine — no parallel reward path.**
   - Backend gate: every XP grant flows through `StudentXpProfile.ApplyAward` (P4-07 refactor). New domain events (`StreakFreezeGrantedDomainEvent`, `StreakFreezeConsumedDomainEvent`, `TimedEventStartedDomainEvent`, `TimedEventEndedDomainEvent`) all derive from `IDomainEvent` and dispatch via the existing `UnitOfWorkBehavior` / `IsolatedNotificationPublisher`. Weekly challenges reuse `MissionCompletedDomainEvent`. **No parallel reward path** asserted by the lack of any new `XpReason` value for timed events (the boost is a multiplier on existing reasons, not a new reason).

5. **AC5 — Mechanics dials (freeze count, event cadence, challenge targets) are config-driven so they can be tuned without a deploy.**
   - Backend gate: `FreezeOptions` (`MaxInventory = 2`, `EarnEveryNStreakDays = 7`), `TimedEventOptions` (`SweepCron`, `TimeZoneId`, `MaxMultiplierCeiling` — Q11), challenge targets live in seeded `MissionDefinition.Target` rows + reseed-on-startup via `MissionSeeder.UpdateMetadata`. All three values are `IOptions<T>`-bound from `appsettings.json:Gamification:Freeze` / `Gamification:TimedEvent` and the seeder runs every startup. No code changes required to retune.

## Handoff → security-auditor

**Mandatory run — child-data + child-safety + economy implications.**

- **No new PII** — `FreezeBalance` is an int counter; `TimedEvent` carries display strings + decimals + datetimes; no personal data.
- **Authorization** — `GET /api/Gamification/TimedEvents/Active` is `[Authorize]` (any authenticated user). No JWT-scoping needed (events are global). The `IXpBoostCalculator` is called inside handlers that already trust the event payload's `StudentId` (per P4-02..P4-07 invariant).
- **No client-controllable freeze grant** — `GrantStreakFreezeCommand` is sent only by `StreakAdvancedFreezeGrantHandler` (an internal notification handler); no public endpoint for granting freezes. Future parent/admin grant endpoints will need their own audit.
- **`TimedEvent` admin/seed surface** — Phase 3 has no admin UI; rows are seeded or inserted via direct SQL. **No tampering risk** since the multiplier ceiling is enforced by a DB check constraint AND by the boost calculator's `Math.Min(maxMultiplier, options.MaxMultiplierCeiling)` clamp (defence-in-depth).
- **Boost computation under DoS** — every XP-awarding handler now calls the boost calculator. The calculator is backed by `CachedActiveTimedEventsQuery` (Redis, ~30s TTL); fail-soft path returns 1.0× on cache miss to Postgres miss. Latency overhead < 5ms per XP grant. Acceptable.
- **Sweep job runs without user scope** — same precedent as `StreakSweepJob`/`MissionRolloverJob`/`LeagueRolloverJob`. Audit-stamping behaviour stamps `UpdatedBy = 0` (system).
- **No `ex.Message` echo** from any new path.
- **Multi-event interaction** — `max(multipliers)` semantic prevents compound exploits. Even if a hostile actor inserts overlapping events, the effective rate stays bounded.
- **`StreakSweepJob` row-by-row branch** — does not introduce N+1 query; each row has its own DbContext-scoped lock. Could become a perf hot path at scale but not a security concern.
- **Out-of-order event delivery** — `TimedEvent*DomainEvent` are domain events, not integration events; raised via change tracker after commit; no replay risk. Active-events cache might briefly return stale data within TTL (≤30s).

Findings ≥ High block the gate.

### Top open questions (decision-shaping)

**Q0 — Scope: ship all three concerns in one PR OR split into 2-3 PRs?**
- **Recommend SINGLE PR** containing all three (streak freeze + timed events + weekly challenges). Rationale: the story is 5 SP and explicitly scopes all three; weekly challenges are the cheapest concern (2 mission seeds); freeze + events together touch the same `StudentXpProfile` migration and the same `StreakSweepJob` modification — splitting would require two migrations. **Counter-argument:** the timed-event multiplier touches 5-6 handlers (handler-side calculator) and is the riskiest change; could ship freeze + weekly challenges first (low risk, schema-only), then timed events (cross-cutting). **Lead call.**

**Q1 — Streak-freeze model: consumable token (recommended) vs grace window.**
- **Recommend consumable token** — locked by SRS FR-GM-2 rider + FR-GM-9 + story Notes. The story explicitly says *"a freeze auto-consumes to preserve the streak on a missed day"* → consumable, not a passive grace period. Resolves the P4-03 *"open grace question"* in favour of freeze tokens. **APPROVED by SRS rider** — proceed.

**Q2 — Freeze acquisition: earned-only vs purchasable.**
- **Recommend earned-only** in Phase 3. The story says *"earned and/or purchasable with XP/coins per the economy decision"* but the *"economy decision"* (coin/XP-shop) is not in scope and there's no coin system in `main`. Task file flags *"economy decision needs lead sign-off"*. Lock to earned-only via 7-day streak milestone (Q6). Forward-compat: `Source` field on `StreakFreezeGrantedDomainEvent` allows future `"purchase"` source without schema change.
- **Alternative:** earn-only + parent-grant via Parent app — defer to a P4-11.1 follow-up; the `GrantStreakFreezeCommand` is reusable.

**Q3 — Weekly challenges: reuse `MissionType.Weekly` or add `MissionType.WeeklyChallenge = 3`?**
- **Recommend reuse `Weekly`** with `Code` prefix `CHALLENGE_*`. Pros: zero enum change, zero `IStudentMissionsQuery` snapshot shape change, zero new rollover job registration. Cons: classic weekly missions and challenges share a list on the dashboard snapshot — FE differentiates by Code prefix. **The story's "distinct from daily missions and leagues" is a UX requirement, not a schema one.**
- **Alternative:** add `WeeklyChallenge = 3`; pros: explicit, type-safe; cons: more migration + snapshot churn.

**Q4 — Freeze storage: simple `int FreezeBalance` column on `StudentXpProfile` (task-file model) OR separate `StudentFreeze` audit entity.**
- **Recommend simple int column** (task file BE-1 specifies this). Mirrors `Hearts` precedent. If audit-trail demand emerges later (e.g., parent dashboard needs *"freezes earned + spent history"*), add the entity in a P4-11.x follow-up. Q4 lock — proceed with column.

**Q5 — `StreakSweepJob` modification: bulk SQL CASE OR two-pass (bulk + per-row).**
- **Recommend two-pass.** Pass 1: bulk `ExecuteUpdateAsync` for `FreezeBalance == 0` victims (existing fast path, single SQL statement). Pass 2: row-by-row for `FreezeBalance > 0` (load profile → `ConsumeFreeze` via domain method → save → domain event raised). The two-pass preserves the existing happy-path performance AND raises `StreakFreezeConsumedDomainEvent` via the change tracker (a SQL CASE bypasses change tracker — no event).
- **Alternative:** single SQL with CASE expression + capture-before-bulk → publish events manually (mirrors existing `StreakBrokenIntegrationEvent` pattern in `StreakSweepJob`). Simpler perf, but requires manual event-raising and loses the `RaiseDomainEvent` semantic on the aggregate.

**Q6 — Freeze earning cadence: every N-day streak milestone (N=7) and cap = 2.**
- **Recommend N=7, cap=2.** Earn one freeze on streak days 7, 14, 21... up to cap=2. After 14 days at cap, no more grants until one is consumed. Duolingo-precedent: every 10 days, cap 2 — close enough. Both values are `FreezeOptions` config-driven so lead can re-tune.
- **Q6.bis — does `GrantFreeze` raise `StreakFreezeGrantedDomainEvent` when the grant is a no-op (cap hit)?** Recommend **no** — only raise on positive transitions. Avoids noise + spurious cache invalidations.

**Q7 — XP multiplier integration: MediatR pipeline behaviour vs handler-side calculator.**
- **Recommend handler-side `IXpBoostCalculator`** (Approach B). Rationale: CLAUDE.md rule 8 *"design patterns — ask first"* — `IPipelineBehavior<,>` is a MediatR pattern; Gamification only uses `UnitOfWorkBehavior` today (a precedent the lead approved). Adding a second pipeline behaviour for boost is "introducing a pattern unilaterally" by rule 8. The calculator approach is "an additional injected service used in handlers" — not a pattern, just plumbing. **5-6 handlers gain one constructor param + one new line each.**
- **Alternative:** MediatR pipeline behaviour wrapping every `ICommand` whose handler eventually calls `ApplyAward`. Elegant — one place to maintain, no per-handler edits. **Requires lead sign-off** per rule 8. If lead approves, the brief flexes — pipeline behaviour is technically cleaner.

**Q8 — `IStudentStreakQuery` snapshot extension: additive `FreezeBalance` field.**
- **Recommend additive int field** on `StudentStreakSnapshot`. Breaking change risk: positional record extension might break `IStudentStreakQuery` consumers that destructure positionally. Mitigation: switch to named-property record OR put the new field at the end with a default value. Cached decorator unaffected (the cache stores the serialised object). **Coordinate with frontend's api-client regen.**

**Q9 — Active-events cache TTL.**
- **Recommend 30 seconds.** The sweep job runs every 2 minutes (Q12), so events transition on ≤ 2-min boundaries. A 30s TTL means a worst-case 2.5-min lag from event start to visible-on-dashboard. Acceptable. The `TimedEventStartedCacheInvalidator` DELs the key immediately on `TimedEventStartedDomainEvent`, so the only stale window is between the sweep firing the event and the post-commit dispatch invalidating the cache — typically < 1 second.
- **Alternative:** 5-second TTL (more responsive, more Postgres hits) or 60s (less responsive). 30s is balanced.

**Q10 — `TimedEventScope`: ship `AllXp` only OR also `MissionXp`, `LeagueXp`, `HeartsCadence`?**
- **Recommend ship `AllXp` only.** `MissionXp` and `LeagueXp` are forward-compat — the calculator's filter is trivial to extend later. `HeartsCadence` is genuinely deferred (boost would interact with `LazyHeartRefiller`'s lazy arithmetic; complex). The enum declares all 3 values; the calculator only honours `AllXp` in Phase 3.
- **Alternative:** also ship `MissionXp` (cheap) and `LeagueXp` (cheap). Add 10 lines to the calculator. Could fit in this story if lead wants.

**Q11 — Multi-event interaction: max vs multiplicative vs additive.**
- **Recommend max(multipliers)**. Two overlapping 2× events → effective 2×, not 4×. Prevents compound inflation that would break the level curve assumptions (P4-02 `LevelCurve` table is calibrated against base XP rates). Simplest semantic for QA, marketing, and ops. **Also recommend `TimedEventOptions.MaxMultiplierCeiling = 5.0`** as a hard cap on any single event's multiplier — defends against ops typos (e.g., setting `Multiplier = 50.0`).
- **Alternatives:** multiplicative (2× + 2× = 4×) — chaos at scale; additive (2× + 2× = 3× = (2-1) + (2-1) + 1) — confusing semantic; first-wins (just take whichever active event was created first) — unintuitive.

**Q12 — `TimedEventSweepJob` cadence: every 2 minutes vs every minute vs Hangfire scheduled triggers.**
- **Recommend every 2 minutes** (cron `"*/2 * * * *"`). Trade-off: granularity vs Hangfire load. With 30s cache TTL (Q9), a 2-min sweep means events are visible within ~2.5 min of their `StartUtc`. Marketing ops can adjust by scheduling events with `StartUtc = intended_visible_time - 2.5 min` buffer.
- **Alternative:** every minute — finer granularity, more Hangfire churn. Or Hangfire scheduled jobs per event (set at admin-create time) — more complex, but precise; requires re-scheduling on admin edit.

**Q13 — Re-engagement nudge on `StreakFreezeConsumedDomainEvent` — fire a *"your freeze saved your streak"* push?**
- **Recommend define the event, defer the nudge to P4-09 follow-up.** P4-09 (re-engagement) is on `main`; the new event type extends naturally — but adding a nudge handler in this story bloats scope. The event is raised + cache-invalidated; a P4-09.1 follow-up adds the notification template + handler.

**Q14 — Ship a demo `TimedEvent` seed?**
- **Recommend YES — one seeded "Welcome Boost" event** active for the first week post-deploy (e.g., `StartUtc = deploy_time, EndUtc = deploy_time + 7 days, Multiplier = 1.5x`). Helps QA + ops + FE visual testing. Seeder upserts by `Code = "WELCOME_BOOST"`; idempotent across deploys.
- **Alternative:** ship empty; QA + ops seed manually via SQL. Acceptable but introduces friction.

**Q15 — XP ledger transparency: split boosted amount into two `XpAward` rows (base + boost) OR single row at boosted amount?**
- **Recommend single row at boosted amount** (`XpAward.Amount = base * multiplier`). Cleaner. The audit trail comes from joining the `XpAward.OccurredAtUtc` against `TimedEvents` table.
- **Alternative:** add `XpReason.TimedEventBonus = 7` + write a second row for the bonus portion. More transparent in the ledger but doubles the row count. Defer to P5 analytics if needed.

**Q16 — Endpoint shape: `GET /api/Gamification/TimedEvents/Active` only OR also `GET /api/Gamification/StreakFreeze/Me`?**
- **Recommend `Active` endpoint only.** `FreezeBalance` is already on the dashboard via `IStudentStreakQuery`. A dedicated freeze endpoint adds zero value in MVP. P4-08 motion can read from dashboard.

### Risks

- **R1 (HIGH) — Multi-event interaction unbounded.** Without `max(multipliers)` + `MaxMultiplierCeiling`, ops typos or overlapping campaigns could inflate XP 100× → bricks the level curve and league standings. **Mitigation:** Q11 lock (max + ceiling). Test case 12 explicitly covers this.
- **R2 (HIGH) — Cache freshness around event boundaries.** Events transitioning during a cached read window could leave the dashboard out of sync with reality for up to 30s + 2min sweep lag. **Mitigation:** Q9 30s TTL + immediate `TimedEvent*CacheInvalidator` DEL on event start/end. Worst-case lag is 1-2 seconds in normal operation; up to 2.5 min only if the sweep job is down. Document.
- **R3 (HIGH) — Streak-freeze + `StreakSweepJob` lazy-write seam consistency.** The two-pass sweep (Q5) introduces a window between Pass 1 (bulk update zero-freeze victims) and Pass 2 (per-row freeze consumers). During the window, a Pass 1 row might be queried by another transaction in the "broken" state while a Pass 2 row hasn't yet committed. **Mitigation:** wrap both passes in the same DbContext-scoped transaction (`db.Database.BeginTransactionAsync`); commit once at end. Domain events still raise post-commit via UoW.
- **R4 (MED) — Pipeline behaviour vs calculator decision blocks all 5 handlers.** Q7 must be locked before backend-feature can start. Whichever choice the lead makes, the 5-6 affected handlers are co-touched. **Mitigation:** ask lead Q7 first.
- **R5 (MED) — `TimedEventSweepJob` missing a transition during deploy/restart.** If the sweep is down at the exact minute an event activates, the `IsAnnouncedActive` column remains false past the activation time, and the boost calculator (reading directly from the table via `StartUtc <= now AND EndUtc > now`) STILL boosts XP correctly — but no `TimedEventStartedDomainEvent` fires for analytics/nudges. **Mitigation:** the boost calculator's source-of-truth query does NOT depend on `IsAnnouncedActive`; only the FE banner + analytics events do. Accept the gap; document in HANDOFF.
- **R6 (MED) — Concurrency: two `StreakSweepJob` runs at the exact same minute.** Hangfire serializes recurring jobs by ID, but a misconfiguration could spawn two. **Mitigation:** the existing `[Hangfire.DisableConcurrentExecution]` attribute (or equivalent in P4-03 sweep) — verify in code; if absent, add.
- **R7 (LOW) — `MissionCatalog.Defaults()` extension breaks existing seed.** Adding new rows is additive; `MissionSeeder.UpdateMetadata` already idempotent. Confirmed safe.
- **R8 (LOW) — `FreezeBalance` column default 0 backfill on production data.** Adding a column with `default 0` is non-blocking and instantaneous in PG. Existing rows get 0. No backfill query needed.
- **R9 (LOW) — Forward-compat enum values (`TimedEventScope.MissionXp`, `LeagueXp`) might be set in seed but not honoured.** Mitigation: calculator throws on unknown scope IF it encounters one outside `AllXp` in MVP, OR logs warn + treats as 1.0×. Recommend latter (fail-soft).
- **R10 (LOW) — Dashboard performance — extra IActiveTimedEventsQuery on every dashboard read.** Cache hit rate should be ≥95% (events transition infrequently). No measurable regression expected. Monitor.
