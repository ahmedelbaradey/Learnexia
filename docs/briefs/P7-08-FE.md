## Business context & value
- **Who benefits:** the **admin/support operator** directly; parents/children indirectly (a support agent fixes a wrong grade or mis-set language without making the parent redo onboarding).
- **Value:** least-privilege support correction. Grade fix is non-destructive (history preserved); language fix is deliberately destructive and must be impossible to trigger by accident.
- **Success measure (from AC):** an admin can, from a child's detail view, change UI language/country with no progress impact; override grade 1–6 behind a confirm and see history-preserved + re-scope messaging; change learning language only after an explicit fresh-start confirmation; and every edit is admin-gated, validated, and audited.

## Acceptance criteria (testable — FE lens)
1. **Child-only surface.** Profile-edit + grade + learning-language controls render **only for accounts holding the Student role**; never for parents/admins. (Detail DTO exposes `roles[]`/`grade`; gate on Student.)
2. **Edit profile (harmless).** Editing `PreferredLanguage` (UI locale select: ar / en) and/or country and saving calls `PATCH /api/Admin/Users/{childId}/profile`; on success the detail view reflects the change; **no progress-impact warning** is shown (it's harmless). No event/destructive copy here.
3. **LearningLanguage is a separate, clearly-labelled control** — visually distinct from `PreferredLanguage` so they are never confused (UI language vs medium-of-instruction). Changing it opens the fresh-start dialog (AC-4); it is **not** part of the plain profile PATCH.
4. **LearningLanguage change is confirm-gated + destructive.** The fresh-start dialog states clearly "this resets the child's **Math & Science** progress — it cannot be undone" and requires an **explicit/typed confirmation** before the action is enabled. On confirm, calls `POST /api/Admin/Users/{childId}/learning-language` with `confirmFreshStart: true`. Arabic/English subjects are unaffected (copy should say so).
5. **No confirm ⇒ nothing happens.** If the admin does not confirm, the destructive call is never sent; if the backend is reached without confirm it returns **HTTP 424** and the UI surfaces the gate message (no optimistic mutation, no cache wipe).
6. **Grade override + re-scope/preserve messaging.** The grade dialog offers grade **1–6**, an **optional reason** (free-text, ≤500 chars), and a **confirm**; copy states **curriculum re-scopes to the new grade while XP / level / badges / streaks / mastery are preserved**. On confirm, calls `POST /api/Admin/Users/{childId}/grade` with `{ grade, reason, confirm: true }`.
7. **Validation + envelope errors surface inline.** Invalid grade (outside 1–6) → **HTTP 422**; unsupported language/country → **422**; grade-unchanged (same as current) → **400**; grade confirm missing → **400**; learning-language confirm missing → **424**. The FE maps each to a clear inline message (Arabic + English copy), never a raw stack/`ex.Message`. Backend message strings are user-safe (see contract table) and can be shown directly or mapped to local copy.
8. **Admin-only access.** All three actions live behind `useAdminGuard`; a non-admin is redirected to `/login`; the backend is the real gate (every endpoint is class-level `AdminOnly` → 401 anon / 403 non-admin).
9. **Cache coherence.** On success the detail/profile query is invalidated; the **learning-language** success additionally invalidates any child progress/activity caches (Math/Science) so stale progress isn't shown after the reset.
10. **RTL/i18n + a11y.** All copy bilingual (ar + en), dialogs RTL-correct; dialogs are focus-trapped, ESC/overlay-dismiss the *cancel* path (never the confirm), confirm buttons are keyboard reachable, and destructive actions are visually distinguished (not color alone).

### Verified backend contract (live source — `AdminUsersController.cs`, route base `api/Admin/Users`, all class-level `[Authorize(AdminOnly)]`)

| Action | Verb + path | Request body | Success → | Notable status codes |
|---|---|---|---|---|
| Edit profile (harmless) | `PATCH /api/Admin/Users/{childId}/profile` | `{ preferredLanguage?: "ar"\|"en"\|"ar-EG"\|"en-US", country?: string≤100 }` (both nullable = no-change) | `BaseResponse<string>` (200, **no DTO payload** — message only) | 400 (bad), 404 (not found / not a child), 422 (unsupported language/country) |
| Override grade (non-destructive) | `POST /api/Admin/Users/{childId}/grade` | `{ grade: 1..6, reason?: string≤500, confirm: bool }` | `BaseResponse<ChildGradeOverrideResponseDto>` = `{ childUserId, oldGrade, newGrade }` | **confirm=false → 400** (soft guard, *not* 424); same grade → **400**; grade out of 1–6 → **422**; 404 (not found / not a child) |
| Change learning language (DESTRUCTIVE) | `POST /api/Admin/Users/{childId}/learning-language` | `{ learningLanguage: "ar"\|"en", confirmFreshStart: bool }` | `BaseResponse<AdminChangedLearningLanguageResponseDto>` = `{ childId, newLearningLanguage }` | **confirmFreshStart=false → 424** FailedDependency (no mutation, no reset); unsupported language → **422**; same language → 200 no-op; 404 (not found / not a child) |

- **Field-name gotchas (do not guess):**
  - Profile body uses **`preferredLanguage`** + **`country`** (the entity field is `Nationality`, but the request DTO is `country`).
  - Grade body confirm flag is **`confirm`**; learning-language confirm flag is **`confirmFreshStart`** (NOT `confirm`).
  - The admin learning-language body uses **`learningLanguage`** — different from the **parent** P8-04 hook which uses `newLearningLanguage`. They are **different endpoints**; build a dedicated admin hook, do not reuse the parent one.
- **Read endpoints for the host detail view (already built, P7-06):**
  - `GET /api/Admin/Users/{id}` → `BaseResponse<AdminUserProfileDto>` — carries `id, fullName, email, role, roles[], accountStatus, isActive, preferredLanguage` (culture code), `learningLanguage` (ar/en), `grade` (nullable; child-only), `nationality` (country), `avatarUrl`, `createdAt`, `lastSignInAtUtc` (**always null** — not tracked).
  - `GET /api/Admin/Users/{id}/family` → `BaseResponse<AdminFamilyDto>` — for a child, `parents[]` is populated (parent↔child context); each `AdminFamilyMemberDto` is `{ id, fullName, email?, grade? }`. **Child email is omitted in the family list** (privacy) — open the individual profile for it.
- **Envelope:** success flag is `Successed` (note spelling); `unwrapEnvelope` already handles it. Validation detail is in the `errors[]` array on 422.
- **Backend message strings (user-safe — may be shown directly or mapped):**
  - 422 grade: `"Grade must be between 1 and 6."`
  - 400 grade confirm: `"Please confirm the grade override by setting Confirm=true."` (FE should render its own friendlier confirm copy; this is the fallback).
  - 400 grade no-op: `"The child's grade is already set to the requested value. No change was made."`
  - 422 language: `"Language must be \"ar\" or \"en\"."`
  - 424 learning-language: `"You must confirm the fresh start to change the learning language. This will reset Math and Science progress."`
  - 404/role: `"The target user is not a child account. This operation requires a Student role."`

## Security / privacy & audit (load-bearing — editing CHILD records as admin)
- **AdminOnly everywhere.** Every P7-08 endpoint is class-level `[Authorize(Policy = AuthorizationPolicies.AdminOnly)]`; anon → 401, non-admin → 403. The FE `useAdminGuard` is a **UX boundary only** — the backend is the real gate. Do not rely on the client guard for protection; the security-auditor must confirm no action path bypasses it.
- **Child-privacy / COPPA-style care.** This wave **edits children's records**. Keep child PII off the wire where the backend already does: the family list omits child email by design; do **not** add client-side calls or logs that broadcast child PII; keep child identifiers out of console logs, analytics, and error toasts. Response DTOs (`ChildGradeOverrideResponseDto`, `AdminChangedLearningLanguageResponseDto`) are intentionally PII-free (ids + codes only) — surface those, not raw user objects, in confirmations.
- **Destructive action safety.** The learning-language change **hard-deletes Math/Science attempts**. The 424 confirm-gate fires **before any mutation** server-side; the FE must (a) never send `confirmFreshStart: true` without the explicit typed confirmation, (b) never optimistic-update or pre-emptively clear caches before success, and (c) clearly distinguish this destructive action from the harmless profile PATCH and the non-destructive grade override. Grade override is **non-destructive** — its confirm is a softer guard (400, not 424); copy must not imply data loss.
- **Audit (P7-12).** Every action emits an `AdminActionPerformedEvent` server-side (verified in handlers): `Child.ProfileUpdated`, `Child.GradeOverridden` (Details `oldGrade=…;newGrade=…`), `Child.LearningLanguageChanged` (Details `oldLang=…;newLang=…`) — actor from JWT, timestamp, old→new. **Audit `Details` carries ids + values only, NOT the free-text reason** (the grade `reason` is captured by the command but the immutable audit `Details` stores ids/values only — see HANDOFF P7-13 note). FE need not implement audit, but the **reason field is still required UX** (story AC) and the e2e/security tests should assert the actions are admin-gated and that the destructive path cannot fire without confirm.
- **Token staleness (known, documented).** `learning_language` is a JWT claim; the child's new value lands on their **next** token (refresh/sign-in), the issued access token keeps the old value until expiry (stateless JWT, same bounded-staleness as parent P8-04). This is a backend-documented G2 follow-up — the FE should not try to "fix" it; just be aware activity reads may briefly reflect the old language until the child's token rotates. Grade is **not** a JWT claim, so no grade-staleness.
- **`security-auditor` is MANDATORY for this batch** (child data + destructive operation + authz). Critical/High findings block the gate.

## Open questions / assumptions / risks
1. **(BLOCKER) P7-06 FE prerequisite.** The child user-detail host page does not exist. Decide: build P7-06 FE first, or fold a minimal child-detail slice into this wave. P7-08 cannot ship without a host screen. → **Ask the lead.**
2. **Locale toggle.** The admin app is English-first with no live locale switcher (`ADMIN_LOCALE='en'`). Assumption: author bilingual copy + RTL-ready, but a user-facing ar/en toggle is **out of scope** for P7-08 (consistent with P1-10). Confirm.
3. **Typed-confirm gesture for learning-language.** The story/task say "typed/explicit confirm" and "same as P8-04". Exact gesture (type a phrase vs checkbox + explicit button) is a **designer** decision; recommend mirroring the parent P8-04 spec (`design-system/ui_kits/parent-settings/P8-04-FE.md`) for consistency. Confirm whether admin should match parent exactly or use a lighter explicit-checkbox gate.
4. **Codegen vs raw-path.** The P7-08 (and P7-06) admin endpoints are **not in the generated NSwag client** (`packages/api-client/src/generated/nswag-client.ts`). Two options: (a) regen the typed client from the running backend OpenAPI (preferred for type-safety; a small shared-file change), or (b) hand-write raw-path hooks (faster, mirrors `useUserList`). Recommend (a) if a regen script exists; flag to planner which to use so FE + e2e agree on shapes.
5. **Profile PATCH returns no DTO.** `UpdateChildProfile` returns `BaseResponse<string>` (message only), not the updated profile. So after a profile save the FE must **invalidate/refetch** the detail query to reflect changes (can't read the new state from the response). Assumption baked into FE-4 invalidation.
6. **Required reason scope.** The lead's request says grade override needs a **required reason**; the backend treats `reason` as **optional** (nullable, ≤500). Decide whether the **FE enforces required** (stricter UX than the API) — recommend yes for support-traceability, but the backend will accept null, so it's a pure FE rule. Note the reason is **not persisted in the immutable audit Details** (ids/values only) — if a durable reason trail is wanted, that's a backend follow-up, not this wave. → **Confirm.**
7. **"Users" nav entry.** The shell nav (`lib/strings.ts` → `navCurriculum`/`navContent`) has no "Users" item. Adding one is really P7-06 scope; flag so it isn't silently dropped.
