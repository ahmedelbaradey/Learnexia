- **User story:** `user-stories/Backlog-Phase-2-Plus/BL-03-knowledge-graph.md` (source of truth).
- **Task file:** none yet (`tasks/.../BL-03-BE.md` does **not** exist — planner generates it). **Flag to lead.**
- **FR-IDs:** FR-CI-3 (knowledge graph of concepts/skills with prerequisite/related edges).
- **BRD goal:** **G2** (learning outcomes — adaptivity/remediation/learning paths) + **G5** (scalable platform). The skill graph is *"the most important asset in the whole company."*
- **Phase / Epic:** Backlog Phase 2+ — Curriculum Intelligence. **SP 5.** **Stage 3 of 3.** Built with **LightRAG** assistance; target store **Neo4j (Phase 3+)**, modeled **relationally** in Phase 2 (SRS §6).
- **Product-decision context:** 4 subjects; no teacher role; relational-now/Neo4j-later (SRS §6 assumption).

## Business context & value
- BL-03 is **Stage 3** (`info/...Knowledge_Graph.md`): *"فهم العلاقات التعليمية بين المفاهيم"* — understanding how concepts/skills relate (dependencies, prerequisites, related). It is the **Adaptive Intelligence** tier — it powers adaptive learning, learning paths, recommendations, quiz generation, remediation, and student modeling.
- The classic value case (from the explainer): a student weak in **Fractions** → the graph knows to review **Division** first. Remediation targets the *real* gap, not sequence order.
- **Who benefits:** students (better adaptivity/remediation/paths); the platform (the defensible curriculum asset). Consumed by P2-04 (Learning Path Engine), P3-06 (question generation), P3-08 (adaptivity), P3-09 (student modeling), P3-10 (spaced repetition/remediation).

## What P2-11 already delivered (BL-03's delta is mostly the *automated build*, not the model)
**Critical reuse fact:** the relational knowledge-graph **model, validator, and query API already exist and are built** in the `learning` module from **P2-11** (status ✅ audited 2026-06-07). BL-03 must **not** rebuild them. Confirmed in code:
- **Entities:** `KnowledgeNode` (Name, NodeType, SubjectId, GradeId, Difficulty, nullable `SkillId`) + `KnowledgeEdge` (SourceNodeId, TargetNodeId, `RelationshipType` = Prerequisite/Related, `Strength` decimal default 1.0) — `backend/src/Modules/Learning/.../Domain/Entities/KnowledgeNode.cs`, `KnowledgeEdge.cs`.
- **Acyclic validation:** `SkillGraphValidator` (DFS over Prerequisite edges) + unit tests.
- **Query API (already exists):** `KnowledgeGraphController` with `GetPrerequisitesOf(skillId)` and `GetUnlockedBy(skillId)` (CQRS). `AddKnowledgeEdgeCommand` (author an edge).
- **Consumption:** `LearningPathEngine` already reads edges from the graph for unlock/remediation.

**Therefore BL-03's genuine, remaining scope is the DELTA over P2-11:**
1. **Automated graph construction** — *building* the graph from BL-05's structured curriculum (LightRAG-assisted inference of prerequisite/related edges), instead of P2-11's hand-authored seed. This is the new work.
2. **`Related` edges + per-edge strength** at scale (P2-11 has the model; BL-03 populates Related edges and meaningful strengths from ingestion, not just hard-coded 1.0 prerequisites).
3. **Richer query API** — AC asks for prerequisites **and dependents and related concepts** in one response; P2-11 has prerequisites (`GetPrerequisitesOf`) + dependents (`GetUnlockedBy`) but **`Related`-concept retrieval may be a gap** to add. Plus the explicit **remediation-traversal** endpoint (weak skill → upstream prerequisite to review) — partially covered by `GetPrerequisitesOf`; confirm depth (transitive vs. immediate).
4. **Neo4j (Phase 3+)** is explicitly out of scope here — stays relational in Phase 2 (SRS §6). BL-03 builds the **relational** graph.

So BL-03 is **not** "create the knowledge graph"; it is **"populate the existing relational graph automatically from ingested curriculum + fill query-API gaps."**

## The .NET-vs-Python / LightRAG reality
- AC: *"the graph is built with **LightRAG** assistance."* LightRAG is a **Python** library. So edge **inference** (which concept is a prerequisite of which) routes through the **Python AI Gateway / Curriculum-Intelligence service** (SRS §2). The **.NET backend** then manages the suggestion queue and persists admin-approved edges into the existing `learning` graph tables and serves the query API.
- **Boundary open question (same as BL-02/BL-05):** Python infers edges + strengths from the structured hierarchy; .NET receives suggestions → human-review queue → admin approves → validate acyclic → persist. Surface, don't assume.

## Decision E — KG as suggestions, not truth (CRITICAL — reshapes BL-03 scope)

This is decided and must not be re-litigated. See `docs/briefs/curriculum-system-of-record.md` §5.

**Auto-extracted graph edges are NEVER auto-published to `KnowledgeEdge`.** The two-phase build:

1. **Phase 1 — Auto-suggest (Python/LightRAG):** LightRAG infers candidate edges from BL-05 structured curriculum and writes them to the **`KGSuggestion` queue** (status: Pending). `KGSuggestion` is defined in BL-04; BL-03-PY-2 writes to it, NOT to `KnowledgeEdge`.
2. **Phase 2 — Human/admin approval (new .NET endpoints):** admin reviews suggestions in the queue. Approve → validate acyclic → write to `KnowledgeEdge` via the Shared.Contracts seam. Reject → discard.

**Therefore BL-03 gains new tasks:** admin endpoints to list `KGSuggestion` rows, approve/reject them, and the approval action that writes the approved edge to `KnowledgeEdge`. This is the "review queue" surface for the graph.

## Decision A — KG ownership-vs-location split (CRITICAL — do not re-litigate)

The `curriculum` module is the **logical owner** (it authors/validates the graph via the suggestion queue and approval workflow). `KnowledgeNode`/`KnowledgeEdge` stay **physically in `learning`**. Cross-module writes from BL-03's approval action go through the Shared.Contracts seam (or a `learning` command seam). See `docs/briefs/curriculum-system-of-record.md` §2.

If BL-03's graph-build orchestration lives in the `curriculum` module (option A): approval emits a `CurriculumEdgeApproved` integration event → `learning` module handles it → validates acyclic → persists.
If everything is in `learning` (option B): the approval command writes directly to `LearningDbContext` (simpler).

## Acceptance criteria (testable)
1. A graph of `KnowledgeNode` + `KnowledgeEdge` is **built from the structured curriculum (BL-05)** — not from raw parsed files (BL-02).
2. Edges capture **prerequisite and related** relationships, each with a **strength** value.
3. A query API returns, for a given node: its **prerequisites, its dependents, and related concepts**.
4. **Remediation traversal:** given a weak skill (e.g. *Fractions*), the API returns the **upstream prerequisite(s) to review first** (e.g. *Division*).
5. The graph is built with **LightRAG** assistance; target store **Neo4j (Phase 3+)**, **modeled relationally in Phase 2** (SRS §6) — i.e. BL-03 delivers the **relational** build, not Neo4j.

## Handoff → backend-feature
- **Phase 1 — Suggestion ingestion:** `BuildKnowledgeGraphSuggestionsCommand` (or an event handler on BL-05's "ingested" event): call `IGraphInferenceClient.InferEdgesAsync` (LightRAG service), receive candidate edges + strengths, write each to `KGSuggestion` (Status=Pending). Idempotent: skip if `(SourceNodeId, TargetNodeId, RelationshipType)` already has a Pending or Approved suggestion. Admin/system-only. **Do NOT write to `KnowledgeEdge` at this stage (Decision E).**
- **Phase 2 — Suggestion review (new tasks BE-7, BE-8, BE-9):**
  - `ListKGSuggestionsQuery`: list Pending suggestions (paged, filterable by subject/grade). Admin-only.
  - `ApproveKGSuggestionCommand`: given a suggestion ID, validate the edge is acyclic (via `SkillGraphValidator`), then write to `KnowledgeEdge` via the existing `AddKnowledgeEdgeCommand` / Shared.Contracts seam (Decision A). Mark suggestion Approved. Reject cycles: return a domain error, do not commit.
  - `RejectKGSuggestionCommand`: mark suggestion Rejected. No edge written.
  - Extend `KnowledgeGraphController` (or a new `KGSuggestionsController`) with endpoints for list/approve/reject. Admin-only.
- **Query-API delta:** add `GetRelatedConcepts(nodeId)` if missing; confirm/extend remediation traversal (immediate vs. transitive prerequisite chain). Mirror the existing `GetPrerequisitesOfQueryHandler` shape (`BaseResponseHandler`, `IQueryHandler`, `BaseResponse<T>`, `ILoggerManager`).
- **Authz:** read queries (prerequisites/related/remediation) likely student-readable; build trigger + suggestion management admin-only. Decide `[Authorize]` deliberately (CLAUDE.md rule 6).
- LightRAG inference client lives in Infrastructure (typed, mockable).

## Handoff → api-tester
- Endpoints (build trigger, suggestion queue, approve/reject, query API) → api-tester after backend-feature, against a **mocked inference client**:
  - Build from a stubbed structured curriculum produces suggestions in `KGSuggestion` (Status=Pending); **no edges are written to `KnowledgeEdge` at this stage (Decision E)**.
  - `ListKGSuggestions` returns the pending suggestions.
  - `ApproveKGSuggestion` for a valid (acyclic) suggestion → edge appears in `KnowledgeEdge`; suggestion status = Approved.
  - A cycle in the suggestion → `ApproveKGSuggestion` returns a domain error; `KnowledgeEdge` is unchanged.
  - `RejectKGSuggestion` → suggestion status = Rejected; no edge written.
  - Idempotent re-build: no duplicate suggestions for the same (Source, Target, Type).
  - `GetPrerequisitesOf` / `GetUnlockedBy` / (new) `GetRelatedConcepts` return correct results for a known seeded chain (e.g. Fractions → Division).
  - Remediation traversal returns the upstream prerequisite for a weak skill.
- Reuse the existing P2-11 integration-test coverage as the baseline; BL-03 adds suggestion-queue + approve/reject + related-concept + traversal cases.

## Handoff → security-auditor (REQUIRED — AI/LLM + writes to the core asset)
