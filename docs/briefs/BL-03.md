## Business context & value
- Stage 3 = "understanding how concepts relate" — the **adaptive intelligence** tier that powers Learning Path Engine (P2-04), question generation (P3-06), adaptivity (P3-08), student modeling (P3-09), spaced-repetition / remediation (P3-10).

## The inference → suggestion → approve → publish → query flow (grounded in shipped code)

**Producer side (BE-2 + BE-3 + PY-1/2/3) — writes ONLY to `KGSuggestion{Pending}`:**
1. Trigger: BL-05's ingestion-complete (a `Done` `ingest` job, handled by `IngestJobAdvanceService`) **OR** an admin `POST /Build`. The .NET `BuildKnowledgeGraphSuggestionsCommand` loads the `KnowledgeNode` rows for the ingested document's subject/grade (cross-module read — see seam Q below), shapes them as `KnowledgeNodeDto`, and calls `IGraphInferenceClient.InferEdgesAsync`.
2. **The transport question (open):** BL-02/BL-05 deliberately use the **DB-outbox + Python poller** (ADR-0004 §2, system-of-record §4b) — NOT a synchronous .NET→Python HTTP call — because a long LLM job must not block a request and .NET cannot reliably reach the Python process. The BL-03 task file (BE-2) specifies a **synchronous typed HTTP client** (`IGraphInferenceClient`). These conflict. **Recommendation: reuse the outbox** — add a `JobType='infer_edges'` lane on `curriculum.PipelineJobs`, Python polls it, writes inferred edges to `ResultJson`, and a `.NET` advance poller (mirroring `IngestJobAdvanceService`) reads the result and writes `KGSuggestion{Pending}`. Keep `IGraphInferenceClient` only as the mockable seam shape for unit tests / a future synchronous path. Confirm with lead (Q-Transport below).
3. Each inferred edge is idempotency-checked on `(SourceNodeId, TargetNodeId, RelationshipType)` — skip if a Pending or Approved `KGSuggestion` already exists; re-build after a Rejection creates a fresh suggestion. Server-side **clamp Strength to [0,1]** (mirror `IngestJobAdvanceService.ClampConfidence` — never trust the LLM value).
4. **Decision E invariant:** this stage NEVER touches `KnowledgeEdge`. Suggestions sit in the queue Pending.

**Approval side (BE-7/8/9) — the ONLY path to `KnowledgeEdge`:**
5. Admin lists Pending suggestions (`GET /suggestions`), reviews, and approves one. `ApproveKGSuggestionCommand` (in `curriculum`) loads the suggestion, opens an explicit transaction, calls the cross-module **edge-publish seam** which: (a) loads existing Prerequisite edges, (b) runs `SkillGraphValidator.AssertAcyclic` with the proposed edge appended, (c) on success persists the `KnowledgeEdge` (reusing `AddKnowledgeEdgeCommand`'s exact guard chain — node existence, **cross-language reject**, duplicate, acyclic), (d) returns. Then stamps `KGSuggestion.Status=Approved`, `ReviewedAt`, `ReviewedByUserId`. Cycle → domain error, neither edge nor status committed. **This mirrors `ApproveIngestionReviewItemCommandHandler` exactly** (transaction + seam + stamp, atomic).
6. Reject → `Status=Rejected`, no edge. Idempotent — re-approving/re-rejecting a resolved suggestion → 409 (mirror `IngestionReviewItemAlreadyResolved`).

**Query side (BE-4/5/6) — over the PUBLISHED graph in `learning`:**
7. `GetRelatedConcepts` + remediation traversal read **`learning.KnowledgeEdge`** (the published, approved graph) — NOT `KGSuggestion`. They extend the existing `KnowledgeGraphController` next to `GetPrerequisites`/`GetUnlockedBy`, reusing the student-safe inactive-skill filtering already in `GetPrerequisitesQueryHandler`.

## Cross-module edge-publish seam — THE key architectural item (Decision A)

`KGSuggestion` lives in the **`curriculum`** module (verified: `Learnexia.Modules.Curriculum.Domain.Entities.KGSuggestion`). `KnowledgeNode`/`KnowledgeEdge` live in **`learning`** (P2-11). Module isolation (CLAUDE.md rule 1) forbids `curriculum` referencing `learning`'s DbContext. `ApproveKGSuggestionCommand` therefore CANNOT write `KnowledgeEdge` directly — it crosses the boundary and needs a `Shared.Contracts` seam, exactly as BL-05's approve handler uses `IPedagogicalTreeWriter`.

**Two seam needs, both currently absent from `Shared.Contracts`:**
1. **Read seam (BE-3):** `BuildKnowledgeGraphSuggestionsCommand` in `curriculum` must read `learning.KnowledgeNode` rows (id, name, node_type, subjectCode, grade, difficulty) to feed inference. Today `IPedagogicalTreeWriter` only WRITES (Ensure*). Either extend it with a read method or add a small `IKnowledgeNodeReader` (e.g. `GetNodesForSubjectAsync(subjectCode, gradeId) → KnowledgeNodeDto[]`).
2. **Write seam (BE-8):** publishing an approved edge. **Recommendation: a new `IKnowledgeEdgeWriter` in `Shared.Contracts.Learning`, implemented in `learning` Infrastructure** (mirroring `PedagogicalTreeWriterAdapter`), with one method that encapsulates the full publish — e.g. `Task<EdgePublishResult> PublishApprovedEdgeAsync(int sourceNodeId, int targetNodeId, int relationshipType, decimal strength, ct)` that internally runs the cross-language + duplicate + acyclic guards (the exact logic in `AddKnowledgeEdgeCommandHandler`) and returns `{Published, Cycle, CrossLanguage, Duplicate}` so the curriculum approve handler can map to the right envelope. This keeps acyclic validation + cross-language enforcement INSIDE the `learning` module (where the live edge set is) and gives the security-auditor a single, auditable publish chokepoint.
   - **Alternative (system-of-record §2):** emit a `CurriculumEdgeApproved` integration event → `learning` handles it async. **Rejected for the approve action** because the admin needs the synchronous outcome (acyclic-pass vs cycle-reject) to return a 200/409/422 — the same reason BL-05's seam is synchronous (`IPedagogicalTreeWriter` doc: "Not an INotification"). A synchronous seam is the established precedent.

This seam (its existence + shape) is the single most important architectural decision in BL-03 — flagged as an open question with a recommendation below.

## Acceptance criteria (testable)
1. A graph of `KnowledgeNode` + `KnowledgeEdge` is **built from the structured curriculum (BL-05)** — not raw parsed files (BL-02). → suggestions produced from learning nodes that ingestion populated.
2. Edges capture **prerequisite and related** relationships, each with a **strength** value (decimal [0,1]). → `KGSuggestion.RelationshipType` + `Strength`; on approval copied to `KnowledgeEdge.Strength`.
3. A query API returns, for a node: its **prerequisites, its dependents, and related concepts**. → `GetPrerequisites` ✅ + `GetUnlockedBy` ✅ + **new `GetRelatedConcepts`**.
4. **Remediation traversal:** weak skill → **upstream prerequisite(s) to review first** (Fractions → Division). → new `GetRemediationPath` (depth per Q3).
5. Built with **LightRAG**; target **Neo4j (Phase 3+)**, modeled **relationally** in Phase 2. → PY-2 LightRAG; **relational only now**, no Neo4j.
6. **(Decision E)** Inferred edges enter `KGSuggestion{Pending}` and ONLY admin approval (with acyclic validation) publishes to `KnowledgeEdge`. No auto-publish path exists. → BE-3 writes suggestions; BE-8 is the sole publish path; security-auditor verifies the invariant.

## Handoff → api-tester (after backend-feature, mocked inference)
- Build from a stubbed node set → suggestions land in `KGSuggestion{Pending}`; **`KnowledgeEdge` is unchanged at this stage** (Decision E assertion).
- `ListKGSuggestions` returns Pending; filters by subject/grade/status.
- `ApproveKGSuggestion` (acyclic) → edge appears in `KnowledgeEdge`, suggestion Approved; strength copied.
- Cycle-creating suggestion → approve returns domain error, `KnowledgeEdge` unchanged, suggestion still Pending.
- **Cross-language suggestion → approve rejected** (cross-language guard).
- `RejectKGSuggestion` → Rejected, no edge. Re-approve/re-reject resolved → 409.
- Idempotent re-build → no duplicate suggestions for the same triple.
- `GetPrerequisites`/`GetUnlockedBy`/`GetRelatedConcepts` correct on a seeded chain; remediation traversal returns the upstream prerequisite for a weak skill. Reuse the P2-11 integration-test baseline.

## Handoff → security-auditor (REQUIRED — AI inference + writes to the core asset)
- **Decision E invariant (primary):** prove NO code path writes `KnowledgeEdge` except `ApproveKGSuggestionCommand` → the edge-publish seam, and that path always runs `SkillGraphValidator.AssertAcyclic` first (no bypass).
- **Cross-module authz:** all suggestion-management + `/Build` endpoints `AdminOnly`; query endpoints student-readable but with the inactive-skill filter (no hidden-skill disclosure via traversal).
- **LLM/prompt-injection:** curriculum text cannot inject arbitrary edges — the approval gate + acyclic check + admin review is the mitigation; the Python inference output is untrusted (bound/clamp strength server-side like `IngestJobAdvanceService`).
- **Graph-traversal DoS:** remediation transitive walk must be depth-bounded / cycle-guarded (the graph is acyclic by construction, but defend against unbounded BFS on a large graph) and the `/Build` trigger rate-limited / system-gated.
- **Secrets:** inference-service URL/key in the secret store, never in source (ADR-0004 posture).

## Devops / runtime gates
- **LightRAG live model** is devops-gated (no resource/key provisioned) — same posture as Azure DI (BL-02) and BGE-M3 (P3-07). Build + CI run against the mock; devops flips config live later.
- New `curriculum-intelligence` graph endpoint/lane runs in the existing Python service container (ADR-0004); HANDOFF must record any new env keys (inference URL/secret) + the `infer_edges` job lane if adopted.

## OPEN QUESTIONS FOR THE LEAD (each with a recommendation)
1. **[ARCHITECTURE — highest priority] Cross-module edge-publish seam.** Approving a `KGSuggestion` (curriculum) must publish into `KnowledgeEdge` (learning) across the module boundary. **Recommend a NEW synchronous `Shared.Contracts.Learning.IKnowledgeEdgeWriter`, implemented in `learning` Infrastructure** (mirroring `IPedagogicalTreeWriter`/`PedagogicalTreeWriterAdapter`), encapsulating the cross-language + duplicate + **acyclic** guards (the exact `AddKnowledgeEdgeCommandHandler` chain) and returning a typed publish result. Reject the async `CurriculumEdgeApproved` event for the approve action — the admin needs the synchronous accept/cycle-reject outcome (BL-05 precedent: the seam is explicitly synchronous, "Not an INotification"). **Also confirm a node-READ seam** (extend `IPedagogicalTreeWriter` or add `IKnowledgeNodeReader`) for BE-3 to load learning nodes for inference.
2. **[TRANSPORT] Synchronous HTTP vs DB-outbox for inference.** BE-2 specifies a synchronous `IGraphInferenceClient` HTTP call; BL-02/BL-05 + system-of-record §4b + ADR-0004 mandate the **DB-outbox + Python poller** (no synchronous .NET→Python call; long LLM jobs must not block). **Recommend reusing the outbox** — add a `JobType='infer_edges'` lane + a `.NET` advance poller (mirror `IngestJobAdvanceService`) that writes `KGSuggestion{Pending}` from the Python `ResultJson`; keep `IGraphInferenceClient` only as the mockable test seam. Confirm.
3. **[SCOPE] Is edge INFERENCE (LightRAG) in BL-03 scope, or is BL-03 the suggestion→approve→publish→query plumbing with inference mocked/seeded?** **Recommend: build the .NET plumbing + the Python service scaffold (PY-1/3/4) fully against a deterministic mock now; gate the LIVE LightRAG model (PY-2) behind devops activation** — exactly the Azure-DI/BGE-M3 precedent. BL-03 ships and is testable end-to-end on the mock; the real model flips live later. This keeps BL-03 unblocked while honoring AC-5.
4. **[QUERY API] Query-API gaps + remediation depth.** Confirmed `GetRelatedConcepts` is a real gap (only prereqs + dependents exist). Is remediation traversal **immediate** (direct prerequisites) or **transitive** (multi-hop BFS chain)? **Recommend transitive with a configurable max depth (default 3) and a cycle guard**, returning `RemediationPathDto{NodeId,Name,Depth,Strength}` ordered by depth — it directly serves the Fractions→Division→… remediation case. Both query endpoints live in `learning`'s `KnowledgeGraphController` (Decision A: learning is the physical home + query owner); reuse P2-11/P5-09 traversal if `LearningPathEngine` already has a transitive walk to avoid duplication — confirm whether to extend `LearningPathEngine` vs add a fresh query.
5. **[CONSTRAINT] Per-language edge enforcement.** Approval must REJECT cross-language edges (P7-03 note). **Recommend the edge-publish seam reuse the existing cross-language guard from `AddKnowledgeEdgeCommandHandler`** (both nodes' subjects must share `Language`, fail-closed if a subject can't resolve) — already implemented and tested in `learning`; the seam just calls into it. No new logic, just routed through the seam.
6. **[CONFIRM] Neo4j deferred.** BL-03 stays **relational** (writes to `KnowledgeEdge`); Neo4j is Phase 3+ (SRS §6). **Recommend: confirm, do NOT introduce Neo4j now.** `KGSuggestion` + `KnowledgeEdge` are designed to be Neo4j-migratable later.
7. **[CONFIRM] Reuse + coexistence.** BL-03 builds on the P2-11 graph and does NOT create a second graph (Decision A). Hand-authored P2-11 seed edges coexist via the existing unique constraint `UX_KnowledgeEdges_SourceTarget_Type` (approve is insert-or-ignore on duplicate). **Recommend: confirm sufficient.**
