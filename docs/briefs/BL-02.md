## Business context & value
- BL-02 is **Stage 1** of the pipeline (`info/Multimodal_Parsing_vs_Curriculum_Ingestion_vs_Knowledge_Graph.md`): *"فهم الملفات نفسها"* — understanding the raw files. It is **Infrastructure** in the importance ranking (Parsing = Infrastructure, Ingestion = Educational Intelligence, Graph = Adaptive Intelligence).
- It converts a PDF/DOCX/image into `{ text, images, tables, equations, layout }` so BL-05 has **clean, machine-readable material** to organize into the educational hierarchy.
- **Who benefits:** the pipeline (BL-05 consumes the artifact); ultimately the AI tutor (grounded on real, accurately-extracted curriculum).
- **Success measured by:** documents (incl. scanned Arabic PDFs) are OCR'd via **Azure Document Intelligence**; text/images/tables/equations/layout are separated into a normalized representation; output is a structured artifact (per-document JSON) preserving source references; failures surface with diagnostics and can be re-run per document.

## The hard architectural reality — .NET vs Python (the central question)
- **This story is Python-pipeline-heavy.** Story tools: **RAG-Anything** (multimodal parsing orchestration), **Azure Document Intelligence** (PRIMARY OCR — Arabic-capable, diacritics-preserving), **Claude** (VLM for diagram/image captioning in the offline lane). The SRS §2 system context shows the **Python FastAPI AI Gateway (`aigw`)** calling **Curriculum Intelligence (RAG-Anything / LightRAG)** and **Azure Document Intelligence (OCR)**. These are **Python/external services**, not .NET libraries.
- **Therefore the realistic architecture is:** the **.NET backend orchestrates** (picks up a `Received` document from BL-01, calls the parsing service, stores the resulting artifact + status), and an **external Python ingestion/parsing service does the actual OCR + multimodal parsing**. The .NET role is *trigger + store + status + traceability*, not implementing OCR in C#.
- **This boundary is an open question the lead must resolve** before planning — it determines whether BL-02 is (a) a thin .NET orchestration story + a separate Python service story, or (b) attempts OCR inside .NET (not recommended — Azure DI/RAG-Anything are Python-first). **Surface, don't assume.** Most likely BL-02 is split: a .NET orchestration/storage slice (buildable in this repo) and a Python parsing-service slice (a separate component/repo, possibly out of this pipeline's scope).

## Lead-approved Arabic-content stack (encode as decided; do not re-litigate)
- **Orchestration framework:** RAG-Anything (HKUDS; built on LightRAG). Verify MIT license before adopting.
- **Primary OCR/parser:** Azure Document Intelligence (`prebuilt-layout` model). Plugged into RAG-Anything as a **custom parser** — the framework provides pipeline orchestration; Azure DI provides Arabic-accurate OCR + layout recognition. **Diacritics/tashkeel MUST be preserved** end-to-end (extraction → artifact serialization → ingestion).
- **Fallback / benchmark comparison:** RAG-Anything's default parsers (MinerU, PaddleOCR). NOT the default path; wired as fallback if Azure DI is unavailable or fails; also used for benchmark comparison.
- **Diagram / image understanding:** Claude (Opus/Sonnet-Vision) as the VLM for Arabic-capable diagram and image captioning. Offline, async work — expensive models cost-justified (offline lane per `docs/briefs/ai-cost-routing.md`).
- **Benchmark-first gate:** before dispatching PY-2 (Azure DI integration), run a 20–30 page Arabic benchmark set (dense text, diacritized pages, geometry diagrams, equation-heavy Math, scanned worksheet) measuring Azure DI vs MinerU vs PaddleOCR + Claude diagram-captioning on real Arabic accuracy. Results stored in `python/curriculum_intelligence/benchmarks/`. **This benchmark gates BL-02 dispatch.** See task BL-02-PY-1b and BL-02-PY-7.
- All specifics are "recommended-and-benchmark-to-confirm," not absolute guarantees. Verify licenses (RAG-Anything, LightRAG: MIT — confirm before adopting).

## Affected modules & data

### Module
- Inherits BL-04's curriculum-module decision (new `curriculum` module vs `learning`). The parsing **artifact** is stored against the `CurriculumDocument` from BL-01.
- **No cross-module FK**; any call to the external Python service goes through an HTTP client / integration seam (config-driven base URL + auth), not a module reference.

### Existing / prior entities
- `CurriculumDocument` (BL-01) — gains a parsing-result reference + status transitions (`Processing` → `Done`/`Failed`).
- `IStorageService` (MinIO) — store the structured artifact (per-document JSON) and any extracted image assets as objects, same pattern as the original upload.

### New entities / fields (this story)
- **`ParsedArtifact`** (or a `ParsedArtifactObjectKey` + `ParseStatus` + `ParseDiagnostics` on `CurriculumDocument`) — the normalized representation reference (likely the JSON stored as a storage object, with the object key + metadata persisted relationally). Keep the large JSON in object storage (MinIO), the pointer + diagnostics in Postgres.
- **Provenance tree initialization (Decision B):** BL-02 is where the `ContentSource` record (and its `Chapter` records) should be created, because parsing extracts the chapter structure from the raw document. When Azure DI returns the document layout, the .NET orchestrator creates:
  - One `ContentSource` record (linked to `CurriculumDocument`) with type `Book` (or `Image`/`Worksheet` based on content type).
  - One `Chapter` record per detected chapter/section in the parsed artifact (chapter number, title, page range).
  This provenance tree creation is a .NET orchestration task — the Python parsing service returns chapter-structure metadata alongside the artifact JSON; .NET persists it. Add `BL-02-BE-6` for this.
- **No embedding involvement (Decision D):** BL-02 does not produce or reference embeddings. The `chunk_embeddings` table is populated only after BL-05 (chunking) by BL-05-PY-4b or P3-07.

## Acceptance criteria (testable)
1. Documents (PDF/DOCX/images), **including scanned Arabic PDFs**, are OCR'd via **Azure Document Intelligence**.
2. The parser **extracts and separates** text, images, tables, equations, and layout structure into a **normalized representation**.
3. Output is a **structured artifact** (e.g. per-document JSON) that **preserves source references** (page/region) for traceability.
4. **Failures surface with diagnostics** and can be **re-run per document** (idempotent re-parse; status returns to `Processing` then resolves).

## Handoff → db-migration
- Add to `CurriculumDocument` (or a new `ParsedArtifact` entity): `ParsedArtifactObjectKey` (storage key for the JSON), `ParseStatus`/diagnostics, `ParsedAt`. Migration in the chosen schema. Index on parse status for re-run/queue scans.
- **`ContentSource` + `Chapter` entities are defined in BL-04** — BL-02's migration only needs to add parse-result fields to `CurriculumDocument`. The provenance entities (`ContentSource`, `Chapter`) already exist from BL-04; BL-02 writes rows into them (no new schema additions needed if BL-04 has run first).

## Handoff → backend-feature (the .NET orchestration slice)
- **`ParseCurriculumDocumentCommand`** (or an event handler reacting to `CurriculumDocumentUploaded` from BL-01): sets status `Processing`, calls the parsing service (HTTP client with config base URL + key, or enqueues for the Python service), on success stores the artifact via `IStorageService` and the pointer + `Done`, on failure stores diagnostics + `Failed`.
- **`ReparseCurriculumDocumentCommand`** — admin-triggered per-document re-run (AC4); idempotent (overwrites the prior artifact).
- **Provenance tree population (Decision B — new task BL-02-BE-6):** on successful parse, the Python service returns chapter-structure metadata alongside the artifact JSON (chapter number, title, page range from the Azure DI layout analysis). The .NET orchestrator creates one `ContentSource` record (linked to `CurriculumDocument`, type `Book`/`Image`/`Worksheet` based on content type) and one `Chapter` record per detected chapter. Idempotent: re-parse overwrites prior chapter records. This is a .NET orchestration responsibility — the provenance tree schema is defined in BL-04 (entities already exist when BL-02 runs).
- **Query:** parse status/diagnostics on the document detail endpoint (extends BL-01's read).
- Mirror existing handler shape (`BaseResponseHandler`, `ILoggerManager`, `ServerError<T>`); the external-service call goes through a typed client registered in the module's Infrastructure.

## Handoff → api-tester
- Endpoints (re-parse trigger, status/diagnostics read) → api-tester after backend-feature:
  - A `Received` document moves to `Processing` then `Done` (with a stubbed/mocked parsing service) and the artifact pointer is stored.
  - A parsing failure → `Failed` + diagnostics visible; re-parse returns it to `Processing`.
  - Admin-only on the re-parse endpoint.
- **Note:** real Azure-DI OCR (esp. Arabic) cannot be asserted in CI without the external service; api-tester validates the **.NET orchestration** against a **mocked/stubbed parsing client**. The Python service's OCR accuracy is validated separately.

## Handoff → security-auditor (REQUIRED — AI/external service + admin)
- External-service credentials (Azure DI key, parsing-service auth) must be in a secret manager / env, not source (architecture §14 flags `CHANGE_ME` secrets). No user PII in documents beyond curriculum content. Admin-only triggers. SSRF/abuse considerations if the parsing-service URL is ever config/user-influenced.
