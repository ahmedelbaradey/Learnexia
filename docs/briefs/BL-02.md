## Business context & value

- **Who benefits:** the **admin / content team** directly — clean, machine-readable extraction from real Arabic textbooks/worksheets instead of hand-seeded chunks, plus re-run + diagnostics when a parse fails. The **student** benefits indirectly — every parsed document widens the corpus that BL-05 chunks/embeds and that the AI tutor (P3-07) retrieves from, and grounds the prerequisite graph (BL-03). No parent/student surface.
- **Value:** BL-02 is the **extraction layer** — it understands the *files*, not the teaching. First consumer of the BL-01 outbox; producer of the structured artifact + provenance tree that BL-05 (ingestion) and BL-03 (KG) build on. Nothing downstream can run without a parsed artifact.
- **Success measure:** a `parse` job written by BL-01 upload is claimed by the Python worker; the source file is read from the `curriculum` bucket; OCR/extraction produces a per-document JSON artifact written to MinIO with the `chapters[]` summary inline in `ResultJson`; the .NET advance poller flips the document parse status to `Done` (+ stores `ParsedArtifactObjectKey`, `ParsedAt`) and creates one `ContentSource` + N `Chapter` rows; on failure parse status = `Failed` + diagnostics is set and an admin can `POST /{id}/reparse`; the **Arabic OCR benchmark (PY-1b + PY-7)** confirms Azure DI superiority on Arabic (tashkeel U+064B–U+065F survives end-to-end) before PY-2 is dispatched.

## Acceptance criteria (testable — reviewer checks against these)

1. A `Pending` `parse` `PipelineJobs` row is **atomically claimed** by exactly one Python worker (`UPDATE ... SET Status='Processing', ClaimedAt=now() WHERE Id=? AND Status='Pending' RETURNING *`); a concurrent worker claiming the same row gets 0 rows and skips. (PY-9)
2. The worker reads `PayloadJson` (`{object_key, content_type}`), downloads the object from the **`curriculum`** MinIO bucket, and parses it. (PY-2/PY-9)
3. Scanned/diacritized Arabic pages are OCR'd via Azure DI (`prebuilt-layout`, `ar` locale); tashkeel (U+064B–U+065F) survives extraction → artifact serialization (asserted by PY-6 + PY-8). (PY-2/PY-3/PY-4)
4. The artifact is a normalized JSON separating text / images / tables / equations / layout, each chunk carrying `source_page`, `source_region`, `parser_used` (`azure_di`|`mineru`|`paddleocr`), and the artifact carries a `chapters[]` array `[{number,title,page_start,page_end}]`. (PY-3/PY-4)
5. The large artifact is written to the `curriculum` bucket (object); the worker writes back `Status='Done'`, `ResultJson={artifact_key, chapters[], parse_status, diagnostics}`, `CompletedAt=now()`. On failure `Status='Failed'` + `ErrorMessage`. (PY-4/PY-5)
6. Azure DI failure triggers the MinerU fallback path, and the fallback is recorded per chunk in `parser_used`. (PY-5)
7. The .NET advance `BackgroundService` polls `PipelineJobs WHERE Status IN ('Done','Failed') AND JobType='parse'` (using `FOR UPDATE SKIP LOCKED`), reads `ResultJson`, and on success sets parse status `Done`, `ParsedArtifactObjectKey`, `ParsedAt`; on failure parse status `Failed` + diagnostics. (BE-7 + BE-3)
8. On successful parse the provenance tree is initialized: one `ContentSource` (Book/Image/Worksheet) linked to the document + one `Chapter` per detected chapter; re-parse is idempotent (upsert on `(ContentSourceId, Number)`). (BE-6)
9. `POST /api/curriculum/documents/{id}/reparse` (admin-only) resets parse status to `Pending` and writes a fresh `Pending` `parse` job; calling while already `Processing` returns a 409 conflict envelope. (BE-4/BE-5)
10. The Arabic OCR benchmark report (`benchmarks/results/benchmark_report.md`) exists and confirms Azure DI superiority on Arabic (or escalates to the lead) — this **gates** PY-2 dispatch. (PY-1b/PY-7)
11. No secrets in source: Azure DI key, Claude key, Postgres conn string, MinIO creds all from env/secret store. (PY-1/PY-2/security-auditor)

## The DB-outbox contract (the BL-02 seam — grounded in shipped BL-01 schema)

The precise contract the Python worker and the .NET advance poller operate on — the load-bearing part of this brief.

```
┌─ .NET (BL-01, shipped) ─────────────────────────────────────────────────────┐
│ On upload success: INSERT curriculum."PipelineJobs"                          │
│   (JobType='parse', Status='Pending', DocumentId=<id>,                       │
│    PayloadJson='{"object_key":"<guid>.pdf","content_type":"application/pdf"}',│
│    CreatedAt=now, RetryCount=0)                                              │
└──────────────────────────────────────────────────────────────────────────────┘
                                   │ (Python polls)
┌─ Python worker (BL-02-PY-9, NEW) ───────────────────────────────────────────┐
│ poll:   SELECT * FROM curriculum."PipelineJobs"                              │
│         WHERE "Status"='Pending' AND "JobType"='parse'                       │
│ claim:  UPDATE curriculum."PipelineJobs"                                     │
│         SET "Status"='Processing', "ClaimedAt"=now()                         │
│         WHERE "Id"=<id> AND "Status"='Pending' RETURNING *                   │
│         (0 rows → another worker won the race → skip)                        │
│ work:   download object_key from MinIO `curriculum` bucket;                  │
│         Azure DI (prebuilt-layout, ar) → RAG-Anything extraction →           │
│         Claude diagram captions → normalize → serialize artifact JSON;       │
│         PUT artifact JSON to `curriculum` bucket as <artifact_key>;          │
│ done:   UPDATE ... SET "Status"='Done',                                      │
│         "ResultJson"='{"artifact_key":"...","chapters":[...],                │
│                        "parse_status":"done","diagnostics":null}',           │
│         "CompletedAt"=now()                                                  │
│ fail:   UPDATE ... SET "Status"='Failed', "ErrorMessage"='...',              │
│         "CompletedAt"=now()                                                  │
└──────────────────────────────────────────────────────────────────────────────┘
                                   │ (.NET polls)
┌─ .NET advance BackgroundService (BL-02-BE-7, NEW) ──────────────────────────┐
│ poll:   SELECT ... FROM curriculum."PipelineJobs"                            │
│         WHERE "Status" IN ('Done','Failed') AND "JobType"='parse'            │
│         FOR UPDATE SKIP LOCKED      (multi-instance safety)                  │
│ on Done:  read ResultJson → ParseCurriculumDocumentResultHandler (BE-3):     │
│           document parse status=Done, ParsedArtifactObjectKey, ParsedAt;     │
│           + BE-6 build ContentSource + Chapter[] from chapters[];            │
│           then mark the job processed (delete vs archive — Open Q6).         │
│ on Failed: parse status=Failed, diagnostics=ErrorMessage;                    │
│            increment RetryCount; if RetryCount>=MaxRetries (default 3) →      │
│            Status='PermanentlyFailed' + alert.                               │
└──────────────────────────────────────────────────────────────────────────────┘
```

**Idempotency / retry:** the atomic `WHERE Status='Pending'` claim is the single-claim guarantee. Re-parse (BE-4) writes a brand-new `Pending` row (does not mutate the old one). `RetryCount`/`MaxRetries` live on the .NET advance side. **Who increments `RetryCount` is ambiguous** — the entity XML comment says "incremented by the Python poller on each claim attempt", BE-7 says the .NET poller increments it on failure. See **Open Q7**.

**Artifact storage:** large parsed JSON → MinIO object (`artifact_key`); the small `chapters[]` summary returned inline in `ResultJson`. `CurriculumDocument.ParsedArtifactObjectKey` holds the pointer. NOT a Postgres JSONB column (textbooks are many MB → row bloat). Task Q3 is effectively decided this way; confirm in Open Q6/storage below.

### Key dependency relationship (the crux)

- The Python worker is the **processor** of the seam (claims + parses + writes results). The .NET `ParseJobAdvanceService` (BE-7) is a **separate** consumer that advances document status after the Python worker finishes — **the two never call each other**; they meet only at the `PipelineJobs` table rows. This is why BE-3 was revised from a MediatR event handler to a result-reader, and why `IParsingServiceClient` (BE-2) is retained only as a test mock (api-tester simulates a completed job without a real Python service).
- **Cross-stack ordering for the planner:** `BL-01-BE-9` (done) is the prerequisite for both PY-9 and BE-7. BE-1 (parse fields migration) gates BE-3/BE-7. The **benchmark gate (PY-1b → PY-7) gates PY-2** and therefore the whole Python parse pipeline. The .NET batch and the Python batch are largely **independent** and can run in parallel once BE-1's migration lands — they meet only at the table contract (fully specified above, which lets each side be built + tested against a seeded/mocked counterpart).

The PY tasks already exist, so a separate "Python bootstrap" *story* is not strictly required — BUT this is the first Python service in a .NET monorepo, so add a **short ADR** (`docs/dev/adr/0004-python-curriculum-intelligence-service.md`) capturing: same-repo location, DB-outbox-poller-not-HTTP transport, runtime/deploy shape, secret handling, test strategy, general-purpose-agent build decision. **Lead to confirm:** (a) general-purpose agent is acceptable; (b) ADR-0004 before code; (c) no new subagent.

**Q4 — Python testing strategy + CI.** **Recommendation:** `pytest` for PY-6/PY-7/PY-8; a **contract test for the poller claim/idempotency against a Testcontainers Postgres** (+ optionally MinIO) proving the atomic claim race; Azure DI + Claude calls **mocked** in CI (cost + availability), with the benchmark runner (PY-7) run **manually/offline** against the real services (it is the gate, run once, report committed). The .NET side gets an **api-tester integration test** seeding `Done`/`Failed` job rows (above). **Lead to confirm** whether a Python CI job is added now or the Python tests run locally/offline for MVP.

**Q5 — Azure DI account / cost / availability (devops-gated, like the BGE-M3 endpoint was).** Task Q4 asks: is an Azure Document Intelligence resource + key provisioned (Arabic OCR), and where do secrets live? Claude VLM (offline lane) also needs an `ANTHROPIC_API_KEY` + cost budget. **Recommendation:** treat Azure DI provisioning + the benchmark corpus (PY-1b sample files the lead provides) as a **devops/lead blocker that gates PY-2** — the same pattern the BGE-M3 TEI endpoint followed (config present, empty until provisioned; see `Curriculum:Embedding` in appsettings). The .NET orchestration + PY-9 poller + bootstrap can be built and tested (mocked) **without** Azure DI. **Lead to confirm** the Azure DI resource availability + secret-store location, and provide the benchmark sample files.

**Q6 — Completed-job disposition (delete vs archive).** §4b + BE-7 both leave "delete or archive the completed job row" to the lead. **Recommendation:** **archive in place** (`Status='Done'`/`PermanentlyFailed` + `CompletedAt` is the audit trail; add no new column) rather than hard-delete, so re-parse history + diagnostics survive; prune later if volume warrants. **Lead to confirm** (low-stakes; affects BE-7 only).

**Q7 — Who increments `RetryCount`, and what is the retry semantics?** The shipped entity XML comment says "incremented by the Python poller on each claim attempt"; BE-7 says the .NET advance poller increments it on `Failed`. These conflict. **Recommendation:** the **.NET advance poller** owns `RetryCount`/`MaxRetries`/`PermanentlyFailed` (single owner of the failure-retry policy); the Python worker only sets `Status='Failed'`+`ErrorMessage`. A retry = the .NET side resets a `Failed` job to `Pending` (incrementing `RetryCount`) until `MaxRetries`, then `PermanentlyFailed`. **Lead to confirm** and have the planner reconcile the entity XML comment.

**Q8 — Dead-letter / alerting on `PermanentlyFailed`.** BE-7 "logs an alert"; no admin dead-letter endpoint exists. **Recommendation:** MVP = log + the existing `GET /{id}` detail surfaces the failed parse status/diagnostics; defer a dedicated dead-letter admin endpoint to the Phase-7 admin console. **Lead to confirm** defer.

**Q9 — New `ParseStatus`/`ParseDiagnostics` vs existing `Status`/`StatusReason`.** BL-01 already shipped `CurriculumDocument.Status` (`DocumentStatus {Received,Processing,Done,Failed}`) + `StatusReason`. BE-1 adds `ParseStatus` + `ParseDiagnostics`, which substantially overlap. **Recommendation:** **reuse** the existing `Status`/`StatusReason` for the parse lifecycle (Received→Processing→Done/Failed already models it) and add only `ParsedArtifactObjectKey` + `ParsedAt`; OR, if BL-05's ingest lifecycle needs a *separate* axis, introduce `ParseStatus` deliberately and document why two status fields coexist. **Lead to confirm** to avoid a redundant/confusing dual-status model (real design-clarity issue — flag to planner + reviewer; it gates BE-1's migration shape).

**Q10 — `IParsingServiceClient` / typed HTTP client purpose.** BE-2 creates a typed HTTP client to "the Python service", but the decided transport is DB-outbox polling — the Python service exposes only a health endpoint, not a parse endpoint. **Recommendation:** keep `IParsingServiceClient` as a **pure test-seam interface (no live HTTP registration on the parse path)**, or drop the HTTP client and keep only the interface for mocking. The task already notes it's "retained as a mockable abstraction"; confirm we are NOT wiring a live HTTP call .NET→Python (there is nothing to call). **Lead to confirm** the interface is mock-only.

## Risks

- **Azure DI Arabic accuracy + diacritics (highest, product risk):** all of AC1 hinges on Azure DI preserving tashkeel. The benchmark gate (PY-1b/PY-7) exists to de-risk this *before* PY-2 — but it depends on the lead providing real Arabic sample files + a provisioned Azure DI resource. If the benchmark fails, escalate (MinerU/PaddleOCR fallback or a different OCR).
- **First Python service in a .NET monorepo (process/tooling risk):** no Python CI, no Python agent, no Dockerfile pattern to mirror. Mitigated by ADR-0004 (Q3) + general-purpose agent + Testcontainers contract test (Q4).
- **Dual-status confusion (Q9):** adding `ParseStatus` alongside the existing `Status` risks two diverging lifecycles. Resolve before db-migration.
- **Poller double-processing:** mitigated by the atomic claim (Python) + `FOR UPDATE SKIP LOCKED` (.NET) — both must actually be implemented, not assumed.
- **RetryCount ownership conflict (Q7):** shipped entity comment vs BE-7 disagree — reconcile before backend-feature.
- **Cost (Azure DI + Claude offline lane):** offline batch, but per-page Azure DI + per-image Claude captioning on full textbooks adds up; benchmark on a small corpus first (already the plan).
- **Snapshot conflict:** BE-1's migration mutates `CurriculumDbContextModelSnapshot.cs` — single-threaded db-migration pass; serialize against any concurrent curriculum story (none expected — BL-05 follows).
