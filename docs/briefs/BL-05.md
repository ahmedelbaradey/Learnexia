## Summary & traceability
- **Task (one line):** Take the parsed artifact from BL-02 and use **AI (LLM extraction + semantic classification)** to structure it into **Grade → Subject → Unit → Lesson → Concept → Skill**, semantically **chunk** it into `CurriculumChunk` records prepared for embedding (RAG / P3-07), flag low-confidence items for review, and make re-ingestion idempotent — the **educational-intelligence layer**: it turns content into a learning system.
- **User story:** `user-stories/Backlog-Phase-2-Plus/BL-05-curriculum-ingestion.md` (source of truth).
- **Task file:** none yet (`tasks/.../BL-05-BE.md` does **not** exist — planner generates it). **Flag to lead.**
- **FR-IDs:** FR-CI-2 (structuring portion). Feeds FR-CI-4 (chunk embeddings) and FR-CI-3 (the graph, BL-03).
- **BRD goal:** **G5** (scalable curriculum) + **G2** (the structured hierarchy + chunks power adaptivity/tutoring).
- **Phase / Epic:** Backlog Phase 2+ — Curriculum Intelligence. **SP 5** (AI-driven, quality-sensitive). **Stage 2 of 3.**
- **Product-decision context:** 4 subjects (Math, Science, Arabic, English; **no Social Studies** — ingestion must respect the subject set); no teacher role.

## Business context & value
- BL-05 is **Stage 2** (`info/Multimodal_Parsing_vs_Curriculum_Ingestion_vs_Knowledge_Graph.md`): *"تحويل الملفات إلى Educational Knowledge System"* — turning raw extracted content into structured lessons & skills. It is the **Educational Intelligence** tier (the highest-value/most quality-sensitive of the three).
- It produces the `Grade → Subject → Unit → Lesson → Concept → Skill` hierarchy (the same entities P2-01 hand-models) **automatically** from real curriculum, plus the `CurriculumChunk` records (BL-04 schema) that RAG retrieval (P3-07) embeds and searches.
- **Who benefits:** the platform (real curriculum becomes a structured learning system); the AI tutor (grounded retrieval); admins (auto-built hierarchy instead of hand-authoring everything — though low-confidence items are flagged for human review).
- **Success measured by:** parsed output is structured into the hierarchy with metadata; content is semantically chunked into `CurriculumChunk` and embedding-prepared; low-confidence extractions are **flagged for review** (not silently mis-classified); re-running ingestion is **idempotent** and updates the structured output.

## The .NET-vs-Python reality — DB-outbox + Python poller (DECIDED, continues from BL-02)
- **AI-heavy and Python-first.** Story tools: **RAG-Anything** (chunking/embedding pipeline orchestration), **Claude** (custom hierarchy mapping — offline lane, Sonnet/Opus), **BGE-M3** (embeddings, 1024-dim multilingual). The LLM-extraction/semantic-classification work routes through the **Python AI Gateway** (SRS §2 `aigw` → RAG-Anything / LightRAG / LLM providers), not C#.
- **The cross-process seam is DB-outbox + Python poller (DECIDED — same pattern as BL-02).** See `docs/briefs/curriculum-system-of-record.md` §4b. When BL-02's .NET job-advance poller marks a `parse` job `Done`, it writes a new `PipelineJobs` row (`JobType='ingest'`, `Status='Pending'`). The Python ingestion service polls for `Pending` ingest jobs, claims them atomically, runs LLM extraction + chunking + confidence scoring, and writes results back (`ResultJson`, `Status='Done'`). A .NET `BackgroundService` (BL-05-BE-13, new) then reads the result and advances `CurriculumDocument.IngestionStatus` + writes hierarchy/chunk rows. **MediatR integration events are NOT the transport** — do not add a MediatR event handler as the ingestion trigger.
- A subtle tension: ingestion **writes into the curriculum hierarchy** (`Subject/Unit/Lesson/Concept/Skill`) which **lives in the `learning` module** (P2-01). If a separate `curriculum` module owns ingestion, writing Learning's hierarchy is a **cross-module write** — forbidden directly (CLAUDE.md rule 1). This must go through `Shared.Contracts` integration events / a published Learning command seam, **not** a cross-module FK/DbContext. **Flag prominently.**

## Lead-approved Arabic-content stack (encode as decided; do not re-litigate)
- **Chunking/embedding orchestration:** RAG-Anything (verify MIT license). Handles the chunk pipeline. Grade-scoped chunking: a chunk MUST NOT span content from different grade levels. Arabic-boundary chunking: split on Arabic sentence/paragraph boundaries — never naive token count. Diacritics/tashkeel must survive chunking AND embedding.
- **Embedding model:** BGE-M3 (multilingual, open-weight, 1024-dim). Vectors stored in the `vector(1024)` column (BL-04). Cohere `embed-multilingual-v3` is the paid alternative (also 1024-dim — column-compatible). Verify BGE-M3 license before adopting. Do not normalize/strip tashkeel before embedding.
- **Hierarchy mapping:** custom Claude-driven layer (Sonnet/Opus offline lane). RAG-Anything/LightRAG provides document graph + retrieval context; it does NOT know pedagogical prerequisites ("Fractions depends on Division"). Our custom Claude prompting + post-processing owns the Grade→Subject→Unit→Lesson→Concept→Skill mapping AND prerequisite edges. The two layers are distinct and must not be conflated.
- **Human review before publish — ON by default (mandatory):** Arabic OCR + LLM structuring error rates are higher than English. Low-confidence items MUST be flagged and withheld from students until an admin approves. Auto-publish of ingested Arabic content to students is NEVER done. The review queue (BE-6, BE-7, BE-8) is the enforcement mechanism, not an optional add-on.
- All specifics are "recommended-and-benchmark-to-confirm," not absolute guarantees. Verify licenses (RAG-Anything, LightRAG, BGE-M3) before adopting.

## Affected modules & data

### Module
- Inherits BL-04's curriculum-module decision. **Key complication:** ingestion's *output* (the hierarchy) belongs to `learning`, while its *chunks* (`CurriculumChunk`) belong to the curriculum schema (BL-04). If those are two modules, ingestion must:
  - write `CurriculumChunk` into its own (curriculum) schema directly, **and**
  - request hierarchy creation in `learning` via an integration event / a Learning-module command — not a direct write.
- Option B (everything in `learning`) sidesteps the cross-module write entirely. This strengthens the case for the lead to weigh option B in BL-04.

### Existing / prior entities
- `Subject/Unit/Lesson/Concept/Skill` (P2-01, `learning`) — ingestion populates these (auto-authored hierarchy). Must respect the 4-subject set + grade scoping.
- `CurriculumChunk` (BL-04) — ingestion **writes** these (Content, Metadata, Difficulty, ConceptId link, EmbeddingVectorRef populated/prepared).
- `CurriculumDocument` + parsed artifact (BL-01/BL-02) — the input.

### New entities / fields (this story)
- A **review-flag** mechanism for low-confidence extractions: either a `ReviewStatus`/`Confidence` field on the created hierarchy/chunk rows, or a small `IngestionReviewItem` entity (recommended — a queue of flagged items with the source reference + suggested classification + confidence). The planner should pick one; recommend the explicit review-item entity so the admin review surface (and FR-CI's human-in-the-loop) is clean.
- Ingestion run/status tracking on `CurriculumDocument` (e.g. `IngestionStatus`, `IngestedAt`).
- **Provenance mapping (Decision B — new in BL-05):** when BL-05 creates a `CurriculumChunk`, it must populate the `ProvenanceRef` field (a reference to the source `Page`/`Block` within the `ContentSource`/`Chapter` tree created by BL-02). It must also create a `ProvenanceMapping` record linking the chunk to its pedagogical node (`ConceptId`) and its provenance block. Both the `ProvenanceRef` and `ProvenanceMapping` entity are defined in BL-04; BL-05 writes to them.
- **Version association (Decision C — new in BL-05):** when BL-05 creates hierarchy nodes and chunks, they are associated with a `CurriculumVersion` (Status=Draft). BL-05's ingestion-service creates or reuses a Draft version for the `(SubjectCode, Language)` tree being ingested. Chunks are not visible to students until the version is switched to Active (by P7-05's publish action). BL-05-BE-5 must set the version reference on each new `CurriculumChunk` row.
- **Embeddings in separate table (Decision D — impacts BL-05):** `CurriculumChunk.EmbeddingVectorRef` does NOT exist (removed by Decision D). `CurriculumChunk` rows are created without any embedding field. If BL-05-PY-4b is in scope (lead Q6), it writes embedding vectors to `chunk_embeddings_bge_m3` (the physical 1024-dim table defined in BL-04-BE-7, C# entity `ChunkEmbeddingBgeM3`), not to a column on `CurriculumChunk`. If BL-05-PY-4b is not in scope, P3-07 writes to `chunk_embeddings_bge_m3`. Note: `vector(1024)` is the fixed physical dimension — a different-dimension future model uses a new physical table. Update BE-5 and PY-4b accordingly.

## Acceptance criteria (testable)
1. Parsed output (BL-02) is **structured into Grade → Subject → Unit → Lesson → Concept → Skill** via the ingestion pipeline, with prerequisite edges, using a custom Claude-driven hierarchy mapping layer.
2. Lessons, concepts, and skills are **extracted with metadata** (grade/subject/language/difficulty) using **AI** (Claude offline lane, custom prompting).
3. Content is **grade-scoped** and **Arabic-boundary semantically chunked** (via RAG-Anything) into `CurriculumChunk` records with diacritics/tashkeel preserved; each chunk carries a **`ProvenanceRef`** (Decision B — reference to source `Page`/`Block` in the `ContentSource`/`Chapter` tree); **prepared for BGE-M3 embedding** (1024-dim vectors; P3-07 or BL-05-PY-4b writes to the `chunk_embeddings_bge_m3` physical table — Decision D; NOT a column on `CurriculumChunk`).
4. Given **low-confidence extraction**, the item is **flagged for human review** and **withheld from students** — never auto-published. Human review before publish is ON by default.
5. **Re-running ingestion** for a document is **idempotent** and **updates** the structured output.
6. All ingested hierarchy nodes and chunks are **associated with a `CurriculumVersion` in Draft status** (Decision C) — content is not Active (student-visible) until P7-05's publish action switches the version. No ingested content is ever Active without an explicit publish.

## Handoff → backend-feature (the .NET orchestration slice)
- **`IngestCurriculumDocumentCommand`** (or an event handler on BL-02's "parsed" event): call the ingestion service, then **idempotently upsert** the hierarchy + chunks.
  - **Idempotency** (AC5): use stable natural keys (e.g. subject name + grade, unit name + sequence, lesson name + unit, skill name) — **mirror the P2-10 `LearningSeeder` natural-key upsert pattern** (`EnsureSkillAsync` etc.). Re-running updates, not duplicates.
  - **Cross-module hierarchy writes** (if curriculum ≠ learning): publish a `Shared.Contracts` integration event / call a Learning command seam to create/update hierarchy rows — **never** a direct cross-module DbContext write.
  - **CurriculumChunk writes:** within the curriculum schema directly. Each chunk must carry: `ConceptId` (link to pedagogical tree), `ProvenanceRef` (Decision B — link to `ContentSource`/`Chapter` block), `CurriculumVersionId` (Decision C — the Draft version for this ingest run). **No embedding vector on the chunk row (Decision D).**
  - **ProvenanceMapping creation (Decision B):** for each chunk written, also create a `ProvenanceMapping` record linking the chunk to its pedagogical node and its provenance block. Idempotent on `(ChunkId, ContentSourceId, PageOrBlockRef)`.
  - **Version management (Decision C):** before writing chunks/hierarchy nodes, resolve the `CurriculumVersion` for this ingest run — find or create a Draft version for the `(SubjectCode, Language)` tree. Associate all created chunks and hierarchy nodes with this version via `CurriculumVersionId`. Never create an Active version here — Draft only.
  - **Review routing** (AC4): when the service returns low confidence, create an `IngestionReviewItem` instead of committing the hierarchy node.
- **Queries:** list flagged review items; ingestion status on the document detail.
- Mirror existing handler shapes; typed ingestion-service client in Infrastructure (mockable for tests).
