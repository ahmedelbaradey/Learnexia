## Summary & traceability

- **Task (one line):** Add the `ingest` stage to the curriculum pipeline — a .NET parse-Done→ingest hand-off + an ingest-advance poller, plus a Python ingestion worker that claims `JobType='ingest'` jobs, reads the BL-02 artifact from MinIO, runs custom Claude-driven hierarchy extraction + grade-scoped Arabic-boundary semantic chunking + confidence scoring (+ optional BGE-M3 embedding), and returns structured `{nodes, chunks, flags}` that .NET idempotently upserts into `CurriculumChunk`/provenance/version rows and (the open question) the LEARNING-module pedagogical tree, with low-confidence items routed to a human review queue.
- **User story:** BL-05 (Story, SP 5). **Requirement:** FR-CI-2 (structuring half); feeds FR-CI-4 (RAG retrieval, P3-07) + FR-CI-3 (KG, BL-03). Covers **A4.2** (structuring/chunking).
- **BRD goal:** **G3** — adaptive/personalized learning (structured hierarchy + embedded chunks are what the AI tutor (P3-07) grounds on and what the prerequisite graph (BL-03) is inferred from). Secondary **G5** — scalable curriculum platform (auto-ingestion replaces hand-seeding).
- **Epic / phase:** Curriculum Intelligence · Backlog Phase 2+ (post-MVP).
- **Pipeline shape:** `analyzer → planner → [Gate 0: lead answers Q1, Q3, Q4] → db-migration → backend-feature ‖ python-worker (general-purpose) → api-tester (.NET outbox) + pytest (Python) → security-auditor (REQUIRED) → reviewer`. **No designer / no frontend / no frontend-e2e-tester** — no student-facing UI; the admin review-queue UI is a deferred Phase-7 admin-console story (BE endpoints here are the future contract).

## Business context & value

- **Who benefits:** the **admin / content team** directly — raw parsed textbooks become a navigable Grade→Subject→Unit→Lesson→Concept→Skill tree + retrievable chunks, with low-confidence extractions surfaced for human approval instead of silently polluting the curriculum. The **student** benefits indirectly and decisively — this is the stage that makes the AI tutor (P3-07) groundable and the prerequisite graph (BL-03) inferable. No parent/student-facing surface.
- **Value:** BL-05 is the **educational-intelligence layer**. BL-02 understood the *files*; BL-05 understands the *teaching*. It is the bridge between the extraction layer and everything the learning platform serves. Nothing in RAG (P3-07) or the KG (BL-03) can run on real (non-seeded) content without it.
- **Success measure:** a `parse`-Done document triggers a new `ingest` `PipelineJobs` row; the Python ingest worker claims it, reads the artifact from MinIO, produces `{nodes, chunks, flags}`; the .NET ingest-advance poller upserts hierarchy + `CurriculumChunk` rows (Draft version, provenance-linked) idempotently, routes sub-threshold items to `IngestionReviewItem` (withheld), sets `IngestionStatus=Done`; an admin can list/approve/reject review items and re-ingest; re-running does not duplicate nodes or clobber P2-10 demo data; ingested chunks are invisible to students until P7-05 publishes (Draft→Active).

## Acceptance criteria (testable — reviewer checks against these)

1. On a `parse` job reaching Done, a new `ingest` `PipelineJobs` row is enqueued (`JobType='ingest'`, `Status='Pending'`, `DocumentId`, `PayloadJson` carrying the `artifact_key`). **Verify ownership:** BL-02's shipped `ParseJobAdvanceService` does NOT do this today — BL-05 adds the hand-off (see § The ingest hand-off contract).
2. A `Pending` `ingest` job is **atomically claimed** by exactly one Python worker (`SELECT … FOR UPDATE SKIP LOCKED` then `UPDATE … WHERE Status='Pending'`); a concurrent claimer gets 0 rows and skips. (PY-6, reuses `PipelineJobRepository.claim_next(job_type='ingest')`)
3. The worker reads the artifact JSON from the `curriculum` MinIO bucket via the `artifact_key` in `PayloadJson` and runs: Claude hierarchy extraction (PY-2) → grade-scoped Arabic-boundary chunking (PY-3) → confidence scoring (PY-4) → optional BGE-M3 embedding (PY-4b, Q4). (PY-1/PY-6)
4. Extracted hierarchy nodes carry metadata (grade_level, subject ∈ {Math, Science, Arabic, English}, language, difficulty) and prerequisite edges; the 4-subject set is enforced (no Social Studies). (PY-2)
5. Chunks are **grade-scoped** (a chunk never spans two grade levels) and **tashkeel-preserving** (U+064B–U+065F survive chunking AND embedding — no Arabic normalization). (PY-3, PY-4b, PY-5)
6. `ResultJson` is `{ nodes:[…], chunks:[…], flags:[…] }` (+ embeddings inline if Q4 in scope); the worker writes `Status='Done'`/`'Failed'`. (PY-1)
7. The .NET ingest-advance `BackgroundService` (BE-13) polls `PipelineJobs WHERE Status IN ('Done','Failed') AND JobType='ingest'` (`FOR UPDATE SKIP LOCKED`), reads `ResultJson`, and on Done dispatches the idempotent upsert (BE-5) + review routing (BE-6) + provenance (BE-11) + version association (BE-12); sets `CurriculumDocument.IngestionStatus=Done` + `IngestedAt`; on Failed sets `IngestionStatus=Failed` + diagnostics with the same retry/PermanentlyFailed policy as the parse poller. (BE-4, BE-13)
8. Hierarchy upsert is **idempotent on stable natural keys** — `(SubjectName,GradeId)`, `(UnitName,SubjectId)`, `(LessonName,UnitId)`, `(ConceptName,LessonId)`, `(SkillName,ConceptId)` — mirroring `LearningSeeder.EnsureXAsync`; re-ingest does not duplicate nodes and does NOT clobber P2-10 hand-seeded demo data. `SkillKey` anchors identity across re-ingest (Decision C). (BE-5, BE-9)
9. `CurriculumChunk` rows are created with `Content`, `Metadata`, `Difficulty`, `GradeId`/`SubjectId`/`ConceptId`/`SkillId`, `SkillKey`, `Language`, `ProvenanceRef`, and `CurriculumVersionId` = the resolved **Draft** version. **No embedding field is set on `CurriculumChunk`** (Decision D — the column does not exist). (BE-5, BE-12)
10. A `ProvenanceMapping` row is created per chunk linking `(ChunkId, ContentSourceId, ChapterId, PageOrBlockRef, PedagogicalNodeId=ConceptId, NodeType)`; `ContentSourceId` resolved from the document's BL-02 `ContentSource`; `ChapterId` matched by `source_page` against `Chapter.PageStart/PageEnd`; idempotent on `(ChunkId, ContentSourceId, PageOrBlockRef)`. (BE-11)
11. Sub-threshold items (`confidence < threshold`, config default 0.7) are NOT committed as hierarchy nodes — instead an `IngestionReviewItem` (`Pending`) is created carrying `SuggestedClassification` + `Confidence`. Admin can list (`GET review-items`), approve (commits the node via the BE-5 seam) or reject (discards). Approve/reject is idempotent (cannot re-resolve a resolved item). All admin-only. (BE-6, BE-7, BE-8, BE-10)
12. If Q4 in scope: embeddings are written to `chunk_embeddings_bge_m3` (entity `ChunkEmbeddingBgeM3`) with `Provider`/`Model='bge-m3'`/`ModelVersion`/`IsActive`, **diacritics preserved**, **same model+version as the runtime TEI endpoint** (parity). If deferred: chunks land with no embedding; P3-07 backfills. (PY-4b, BE-13→BE-5)
13. All ingested content is **Draft-version-only**; nothing is Active. P3-07 retrieval filters `CurriculumVersion.Status='Active'`, so BL-05 output is invisible to students until P7-05 publishes. (BE-12)
14. No secrets in source: `ANTHROPIC_API_KEY`, BGE-M3/TEI endpoint, `DATABASE_URL`, MinIO creds all from env/secret store. (PY-1/PY-2/security-auditor)

│ ParseJobAdvanceService Done path vs a dedicated step). Re-ingest (BE-9)      │
│ also writes such a row directly.                                            │
└──────────────────────────────────────────────────────────────────────────────┘
        │ (Python ingest poller polls)
        ▼
┌─ Python ingest worker (BL-05-PY-6/1, NEW lane) ─────────────────────────────┐

│ work:   download artifact_key from `curriculum` bucket;                      │
│         PY-2 Claude hierarchy+prereq extraction →                            │

│ done:   mark_done(job, ResultJson={ "nodes":[…], "chunks":[…],               │
│                                     "flags":[…], "embeddings"?:[…] })        │

│         FOR UPDATE SKIP LOCKED  (claim CTE, same shape as ParseJobAdvance)   │
│ on Done: IngestCurriculumDocumentResultHandler (BE-4) reads ResultJson →     │

On the Python side, `PipelineJobRepository.claim_next` already accepts a `job_type` argument and `PipelinePoller.poll_once` already takes a configurable `poller.job_type` — the ingest poller is a second instance/config, not a rewrite.

## Cross-module write-path analysis (THE KEY ARCHITECTURAL QUESTION — Open Q1)

**The problem.** BE-5 must create/update `Subject`/`Unit`/`Lesson`/`Concept`/`Skill` (and, downstream, `KnowledgeNode`) rows that physically live in the **`learning`** schema/module. The `curriculum` module must not reference `learning`'s projects or write its DbContext (CLAUDE.md rule 1; Decision A/B). Three candidate paths:

- **(a) Direct cross-module DbContext write — FORBIDDEN.** Rejected by rule 1 + Decision A/B. Not on the table.
- **(b) `Shared.Contracts` seam — integration event or published Learning command.** The repo's integration events are **in-process MediatR `INotification`** (`IIntegrationEvent : INotification`, dispatched via `IsolatedNotificationPublisher`). Because BOTH modules run in the same .NET host, a `Curriculum → Learning` event/command IS reachable in-process (unlike the .NET↔Python seam, which had no shared bus). Pattern precedent exists (`LessonCompletedIntegrationEvent` fan-out; `ICurriculumContextQuery`/`IParentChildQuery` query seams). **This is the canonical Decision-A/B path.** Caveats: (i) the seam must be a *command* with a synchronous, awaited result (so BE-5 knows the created node IDs to link chunks/provenance), NOT a fire-and-forget `INotification` — `IsolatedNotificationPublisher` swallows handler exceptions, which is wrong for a write that must succeed; recommend a dedicated request/response interface (e.g. `IPedagogicalTreeWriter` in `Shared.Contracts`, implemented in `learning`) rather than an event. (ii) The natural-key idempotent upsert (`EnsureXAsync` semantics) must execute INSIDE the Learning handler so the unique constraints + SkillKey logic stay owned by Learning.
- **(c) Curriculum-owned staging table, promoted later.** BE-5 writes proposed hierarchy into curriculum-local tables; a separate admin/P7 action promotes approved nodes into `learning` via path (b). This DEFERS the cross-module write to the approval step and aligns with the "human review before publish is ON by default" rule (sub-threshold items already wait for approval; this would make ALL ingested nodes wait). Lowest-coupling, but adds a promotion stage and a second representation of the tree.

**Recommendation (for the lead to confirm — do NOT decide unilaterally):** path **(b)** with a **synchronous request/response Learning command seam** in `Shared.Contracts` (an interface like `IPedagogicalTreeWriter` implemented by `learning`, returning created/updated node IDs), invoked by BE-5 — NOT an `INotification`. **Q2 — Auto-ingested vs P2-10 hand-seeded demo data coexistence.** Does ingested curriculum extend or replace the hand-seeded MVP hierarchy? ## Risks

- **Cross-module write coupling (highest, architectural):** the Learning seam (Q1) is genuinely new surface; getting it wrong either violates isolation or strands node IDs. Resolve Q1 before BE-5; security-auditor reviews it.
- **Demo-data corruption (high):** a bad idempotency key could duplicate or overwrite P2-10/P2-11 seeds, breaking the MVP. Mirror `EnsureXAsync` exactly; api-tester runs the upsert twice and asserts no dupes.
- **Arabic LLM/extraction quality (product):** Claude structuring of OCR'd Arabic has higher error rates — the confidence/review gate (PY-4/BE-6) is the mitigation and is ON by default; nothing auto-publishes.
- **Embedding parity (correctness):** a model/version mismatch between BL-05-written embeddings and the P3-07 query-time TEI model makes cosine search invalid. `ChunkEmbeddingBgeM3.ModelVersion` + the fail-fast provider mitigate; enforce via Q4.
- **Dropped hand-off (Q8):** if no one enqueues the ingest job after parse-Done, the pipeline silently stalls. Make BE-13/ParseJobAdvanceService ownership explicit and api-test it.
- **Cost (Claude + BGE-M3 on full textbooks):** offline batch, but per-document LLM extraction + per-chunk embedding adds up; mock now, gate live behind devops + a cost ceiling.
- **Snapshot conflict:** BE-1/BE-2 mutate `CurriculumDbContextModelSnapshot.cs` — single-threaded db-migration pass; no concurrent curriculum story expected (BL-03 follows).
- **ContentSource filename collision (Q9):** carried nit from BL-02; could mis-link provenance.
