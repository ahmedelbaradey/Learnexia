## Business context & value

- **Who benefits:** the **student** directly — leagues are the **first competitive layer** of the platform. XP, streak, hearts, badges, missions all measure the student against their past self. Leagues introduce *"you are rank 7 of 30 this week — promotion at rank 7, demotion at rank 26"* — the first system that makes Friday's grind about *passing other kids*. Duolingo's leagues are widely credited as the single most retention-impactful gamification mechanic; story description ("friendly competition motivates me to keep learning") reflects this. **Secondary — the parent**: parent weekly reports (P5-04) can surface "your child finished rank 4 in Silver this week — promoted to Gold." **Tertiary — the system**: P4-09 nudges gain a *"close-to-promotion"* trigger; P4-11 weekly challenges layer ON TOP of league rhythm.
- **Why it matters now:** the dashboard has had a `LeaguePreview = null` placeholder since P2-09 (~3 months of dead UI surface). P4-08's gamification mockup explicitly includes a League screen (`P4-08-gamification-screens-and-motion.md` line 15). P4-10 (Redis realtime) **depends** on P4-07 — it's the story that ships the leaderboard read path P4-10 then swaps to Redis sorted-sets (BE task file Note line 30; P4-10 story Notes line 24 explicitly lists P4-07 as a dependency). P4-11 weekly challenges share the weekly cron rail. This is the last brick in the Phase-3 reward economy and the **only** brick that creates a social loop.
- **Success measurement:**
  - Brand-new student loads dashboard → `LeaguePreview` populated with `(Tier: Bronze, Rank: <last>, TotalPlayers: <cohort size>, XpThisWeek: 0)` — membership instantiated lazily, cohort found-or-created at Bronze.
  - Student earns +50 XP via `LessonCompleted` → `XpAwardedDomainEvent` raised post-commit → `XpAwardedLeagueHandler` increments active membership's `WeeklyXp` from 0 → 50; dashboard preview reflects within the next read.
  - Same `LessonCompletedIntegrationEvent` redelivered → no double-count (XP idempotency upstream means `ApplyAward` only fires once for the same `(OriginEventId, Reason)` per the existing P4-02 unique key — the event is naturally one-per-XP-write).
  - Monday 00:15 UTC rollover → last week's cohorts ranked, top-7 promoted (`TierAfter = nextTier`, `ParticipantStatus = Promoted`), bottom-5 demoted (`TierAfter = prevTier`, `ParticipantStatus = Demoted`), middle 18 stayed (`ParticipantStatus = Stayed`); `StudentXpProfile.CurrentTier` updated to `TierAfter`; **last week's membership rows preserved** (history feeds parent reports).
  - First dashboard read after rollover → new membership instantiated for current week at `CurrentTier`; `WeeklyXp = 0`.
  - `GET /api/Gamification/Leagues/Me` returns the 30-row standings with rank, anonymized display name, weekly XP, isCurrentStudent flag, plus promotion cutline (rank ≤ 7) and demotion cutline (rank ≥ 26), week-ends-at timestamp.
- **Deterministic principle (BRD §8 / FR-AI-6):** league grouping is **pure** — first-fit assignment to any `(Tier, WeekKey)` cohort with `participants < CohortSize`; new cohort when none has capacity. Ranking is a deterministic ORDER BY (Q3 — tie-break). Promotion/demotion is a deterministic cutline. No AI, no randomness.

## Acceptance criteria (verbatim from story + testable backend gates)

From `P4-07-leagues.md`:

1. **AC1 — Students are grouped into leagues (Bronze → Silver → Gold → Diamond) and ranked by weekly XP.**
   - Backend gate:
     - `LeagueTier` enum already encodes the 4 tiers in promotion order (verified above).
     - `League` row exists for `(Tier, PeriodKey)` once one student lands at that tier in that week (lazy create).
     - **Cohort cap = 30** (Q3). When a placement seeks a cohort and all existing cohorts at `(Tier, PeriodKey)` are full, a new cohort is created with `GroupIndex = MAX + 1`.
     - **Brand-new students start in Bronze** (`StudentXpProfile.CurrentTier` defaults `Bronze` on profile create).
     - Ranking: `LeagueMembership.WeeklyXp DESC, JoinedAtUtc ASC (tiebreak: earliest joiner wins)` — Q3.

2. **AC2 — A weekly background job promotes top performers and demotes the bottom per tier rules.**
   - Backend gate: `LeaguePromotionJob` (Hangfire recurring, `"15 0 * * 1"` = Monday 00:15 UTC).
     - For each `(Tier, PeriodKey = last week)` cohort:
       - Order members by `WeeklyXp DESC, JoinedAtUtc ASC`.
       - **Top-7 promote** (`TierAfter = NextTier`, `ParticipantStatus = Promoted`).
       - **Bottom-5 demote** (`TierAfter = PrevTier`, `ParticipantStatus = Demoted`).
       - Middle-18 stay (`TierAfter = SameTier`, `ParticipantStatus = Stayed`).
     - **Diamond (top tier):** top-7 stay (nowhere up) — `ParticipantStatus = Stayed`. Bottom-5 still demote to Gold.
     - **Bronze (bottom tier):** bottom-5 stay (nowhere down) — `ParticipantStatus = Stayed`. Top-7 still promote to Silver.
     - Small cohort handling: if `cohort.Members.Count < 12` (would cause overlap between top-7 and bottom-5), recommend **"promote `floor(N * 7/30)`, demote `floor(N * 5/30)`"** (Q3.b — confirm). Defaults 0/0 for `N < 5`.
     - **Updates `StudentXpProfile.CurrentTier`** so next placement reads it directly.
     - **Idempotent:** re-running the job for the same `(Tier, PeriodKey)` is a no-op once `TierAfter` is non-null on all members (handler short-circuits per-cohort).

3. **AC3 — The league standings are visible with the student's current position.**
   - Backend gate:
     - `GET /api/Gamification/Leagues/Me` returns `BaseResponse<LeagueStandingsDto>` with: caller's tier + cohort group index + week-ends-at, the full sorted standings (up to 30 entries: `Rank, DisplayName (anonymized — Q5), WeeklyXp, IsCurrentStudent`), promotion cutline (top-7 rank), demotion cutline (bottom-5 rank), and caller's own `Rank` + `WeeklyXp`.
     - JWT-only (mirrors `BadgesController`/`MissionsController` exactly — no `studentId` route/query param; IDOR-proof by construction).
     - Dashboard `LeaguePreview` populated via `IStudentLeagueQuery` (replaces `null` placeholder).
     - **Anonymization rule:** display first-name-or-`"Student #<sequence>"` — Q5. Decision MUST be locked before backend-feature batch.

4. **AC4 — The promotion/demotion job is idempotent and runs reliably on schedule.**
   - Backend gate:
     - Idempotency layer 1 (correctness): per-cohort handler short-circuits when all members already have `TierAfter != null`.
     - Idempotency layer 2 (data): processing a cohort is a single atomic UoW write — re-running mid-failure either rolls back (nothing persisted) or completes (next pass skips).
     - Reliability: cron `"15 0 * * 1"` (Monday 00:15 UTC) — strictly after `StreakSweepJob` (00:05) and `MissionRolloverJob` daily/weekly (00:05 / 00:10 Monday). 15-minute buffer absorbs the lazy-evaluation hot path.
     - Hangfire `RecurringJob.AddOrUpdate` is idempotent across restarts; `TimeZoneInfo.Utc` pin matches the other two jobs.

### E. IncrementLeagueXp command + handler (P4-07-BE-2)

`IncrementLeagueXpCommand : ICommand<BaseResponse<Unit>>` runs through `UnitOfWorkBehavior`. Handler:
1. Load membership by ID (no need for row lock — single-writer per student per week from a single domain-event chain).
2. Call `membership.AddWeeklyXp(amount)`.
3. UoW commits. **No domain event raised** (league standings are read-only-projection; rank changes are computed at read-time, not event-driven).

### F. Lazy-placement query (P4-07-BE-3, BE-7)

`StudentLeagueQuery` in `Gamification.Infrastructure/Queries/`. Algorithm:
1. Resolve `StudentXpProfile.Id` via `studentId`; if profile is null → return sentinel.
2. Compute current week via `MissionPeriodCalculator.GetCurrentPeriod(MissionType.Weekly, _clock.UtcNow)`.
3. Look up `LeagueMembership` for `(profileId, periodKey)`. If found → skip to 6.
4. Otherwise placement: load `existingCohortsForKey = await _repo.GetCohortsForPeriodAsync(periodKey, ct).Where(c => c.Tier == profile.CurrentTier)`; load participant counts via `GetCohortParticipantCountsAsync(periodKey, tier, ct)`; call `LeaguePlacementService.FindOrCreateCohort(...)`.
5. If `createdNew` → `_repo.AddLeagueAsync(cohort, ct)`. Then `_repo.AddLeagueMembershipAsync(LeagueMembership.Create(profile, cohort, _clock.UtcNow), ct)`. Save. **Catch `DbUpdateException`** narrowed to `UX_LeagueMemberships_StudentXpProfileId_LeagueId` (race tie-break) and re-read.
6. Read current `WeeklyXp`; compute rank as `1 + COUNT(m WHERE LeagueId = membership.LeagueId AND (m.WeeklyXp > membership.WeeklyXp OR (m.WeeklyXp == membership.WeeklyXp AND m.JoinedAtUtc < membership.JoinedAtUtc)))`. Read cohort size as `COUNT(LeagueId = membership.LeagueId)`.
7. Return `(Tier: LeagueTierDto.From(profile.CurrentTier), Rank, WeeklyXp, CohortSize)`.

### G. Standings endpoint (P4-07-BE-4, BE-6)

`GetLeagueStandingsQuery` + handler. Algorithm:
1. JWT-scoped via `_currentUser.UserId`.
2. Same lazy-placement steps 1–5 as the dashboard query.
3. Load all cohort members ordered `WeeklyXp DESC, JoinedAtUtc ASC` (LIMIT 30 defensively).
4. Resolve display names via `IUserLookup` (batched — Q5).
5. Mark `IsCurrentStudent` for the caller's row.
6. Compute promotion/demotion cutlines from `LeagueOptions.PromoteCount` / `DemoteCount`.
7. Return `LeagueStandingsDto`.

### H. Promotion job (P4-07-BE-5)

`LeaguePromotionJob` (Hangfire recurring; Transient registration mirroring `MissionRolloverJob`). `RunAsync(CT)`:
1. `var lastWeekUtc = _clock.UtcNow.AddDays(-3);` (Monday 00:15 minus 3 days lands in last Thursday — guaranteed inside last ISO week).
2. `var (lastWeekKey, _, _) = MissionPeriodCalculator.GetCurrentPeriod(MissionType.Weekly, lastWeekUtc);`
3. `var cohorts = await _repo.GetCohortsForPeriodAsync(lastWeekKey, ct);` — paged if needed (Q7).
4. Per cohort, open its own UoW scope (CreateAsyncScope) — keeps per-cohort failure isolated. Load members ordered; short-circuit if `members.Any(m => m.TierAfter != null)` (idempotency).
5. Apply per-tier rules (small-cohort scaling per Q3.b); for each member, set `FinalRank` + `TierAfter` + `ParticipantStatus`; update `StudentXpProfile.CurrentTier = tierAfter` for promoted/demoted members.
6. Save per cohort.
7. Log per-cohort summary.

### I. Hardening (do NOT skip)

- **Per-member idempotency on rollover** — `TierAfter != null` short-circuit; idempotent re-run.
- **Per-handler isolation** — `XpAwardedLeagueHandler` wrapped in try/catch (fail-soft); `IsolatedNotificationPublisher` isolates at publisher level too.
- **Lazy-placement race** — `UX_LeagueMemberships_StudentXpProfileId_LeagueId` backstop. **Per-cohort capacity race (R1):** two concurrent placements could each pick the same nearly-full cohort and push it to `count + 2`. Acceptable for MVP (cohort might briefly be 31, doesn't break anything; rollover doesn't care about cap mid-week). Document.
- **No `ex.Message` echoed** — `ServerError<T>()`.
- **JWT-derived StudentId in queries** — controller uses `_currentUser.UserId`; no `studentId` route/query parameter (IDOR-proof by construction).
- **Trust the event payload's `StudentId`** in notification handlers — not `_currentUser` (null in post-commit dispatch scope). Same invariant as P4-02..P4-06.
- **Anonymization layer (Q5)** — never echo `User.FullName` directly in the standings response (PII risk for child accounts). Server-side projection only.
- **Cross-grade competition:** for MVP, cohorts are grade-agnostic. Document in HANDOFF.
- **Conventions:** module isolation (no cross-module project ref — `IUserLookup` is in `Shared.Contracts.Identity`, fine), `ILoggerManager` only, `BaseResponse<T>`, `Successed`, no design pattern (rule 8).

## Handoff → security-auditor

**Mandatory run** — new endpoint + new cross-module read + new domain event raised from XP chokepoint + new ledger surface (membership) + new Hangfire job + **child PII at risk via anonymization choice (Q5)**.

- **PII risk (HIGH for child safety) — standings expose a list of other students' display names.** Anonymization is load-bearing. The decision (first-name vs `"Student #N"`) determines whether this is a Low or Medium finding. **Recommend `"Student #N"` for max safety** — Arabic-first audience + parent-driven onboarding + COPPA-style guardrails make any name exposure across student boundaries a risk. First-name-only is the Duolingo pattern but Duolingo is teen+ adult; Learnexia is K-12. **Q5 priority 1.**
- **IDOR** — `GET /api/Gamification/Leagues/Me` and `IStudentLeagueQuery` both use `_currentUser.UserId`. **No route/query `studentId` accepted.** IDOR-proof by construction.
- **Cross-tier lookup IDOR** — could a caller infer cohort sizes / tier distribution by repeatedly hitting `/Me` with different JWTs? Not a privacy concern in MVP — cohort sizes are 30 by design; the endpoint only returns caller's own cohort. Document.
- **Trust the event payload's `StudentId`, NOT `_currentUser`** in notification handlers — post-commit dispatch scope has no HTTP request user context. Invariant from P4-02..P4-06. **`XpAwardedLeagueHandler` MUST use `ev.StudentId`.**
- **Hangfire job auth** — `LeaguePromotionJob` runs in Hangfire worker; no HTTP scope; scope-factory pattern (same as `StreakSweepJob`/`MissionRolloverJob`); no auth concerns.
- **Resource exhaustion** — lazy placement creates ≤ 2 rows per dashboard load (League + LeagueMembership when both new). Cheap. Hot path stays p95 < 500ms.
- **Anti-scraping** — `/Leagues/Me` should be rate-limited via the existing P1-13b rate-limiter (if enforced) — but the data is the caller's own cohort, so scraping is bounded by cohort size 30. Not a major concern.
- **No new secrets** — config is plain options.

Findings ≥ High block the gate. **Specifically:** if Q5 is unresolved at audit time, that's an automatic High finding ("anonymization rule undefined" — fail).

**Q4 — Stream-mode XP tracking via new `XpAwardedDomainEvent` — single chokepoint refactor (Option 1) vs three raise sites (Option 2).**
- **Critical finding:** `ApplyAward` is NOT currently the single chokepoint — `RecordBadgeEarned` (P4-05) and `RecordMissionCompleted` (P4-06) bypass it by mutating `TotalXp` directly. To get full coverage, either:
  - **(Option 1, recommended)** Refactor `ApplyAward(amount, newLevel)` to `ApplyAward(amount, newLevel, XpReason reason, DateTime occurredAtUtc)` and call it from `RecordBadgeEarned` / `RecordMissionCompleted`.   - **(Option 2)** Raise `XpAwardedDomainEvent` independently from each of `ApplyAward` / `RecordBadgeEarned` / `RecordMissionCompleted`. No signature churn, but duplicated raise sites; future-developer footgun (adding a fourth XP path without raising the event would silently break league XP).
- **Recommendation: Option 1 (single chokepoint).** Long-term hygiene. Test impact is mechanical.
- **Lead confirm.**

**Q5 — Anonymization in leaderboard standings.**

  - **(c) Username-based** — `User.UserName` (currently in `IUserLookup`). Risk: usernames may carry identifying info; needs an explicit "league display name" derivation rule.
- **Recommendation: (a) `"Student #N"`** for MVP. Safest. Can be revisited in P4-08 if FE/UX wants warmer copy (then we'd extend `IUserLookup` properly with a `DisplayName` field server-side-derived).

## Concrete tier ladder + week schedule + promotion/relegation rules (summary)

- **Tiers (4, fixed):** Bronze → Silver → Gold → Diamond.
- **New students start:** Bronze. `StudentXpProfile.CurrentTier` defaults `Bronze`.
- **Week boundary:** ISO 8601 — Monday 00:00 UTC start, next Monday 00:00 UTC end. Reuses `MissionPeriodCalculator.GetCurrentPeriod(MissionType.Weekly, ...)`.
- **Cohort size:** 30 (configurable via `LeagueOptions.CohortSize`).
- **Promote (top):** rank 1..7 → next tier; at Diamond → stayed.
- **Demote (bottom):** rank 26..30 → previous tier; at Bronze → stayed.
- **Stay (middle):** rank 8..25.
- **Small cohort (< 12 members):** scale proportionally: `floor(N * 7/30)` promote, `floor(N * 5/30)` demote (Q3.b).
- **Tiebreak:** `WeeklyXp DESC, JoinedAtUtc ASC` (earliest joiner wins).
- **Rollover schedule:** Monday 00:15 UTC (`"15 0 * * 1"`) — after streak sweep (00:05) and mission rollover (00:05 / 00:10 Monday). 15-minute buffer for any tail transactions.
- **Lazy placement:** first dashboard read of the week per student creates `(Tier, PeriodKey)` membership; finds existing cohort with capacity or creates a new one (`GroupIndex = MAX + 1`).
- **XP source for WeeklyXp:** ALL `XpReason` values via the new `XpAwardedDomainEvent` raised from `StudentXpProfile.ApplyAward` (single chokepoint per Q4 Option 1) — `CorrectAnswer`, `QuizCompleted`, `LessonCompleted`, `StreakBonus`, `BadgeEarned`, `MissionCompleted`.
- **Practice Mode:** XP gates upstream (P4-04) prevent most XP in PM, so WeeklyXp naturally doesn't accumulate. No special handling.
- **Anonymization:** `"Student #N"` placeholder per cohort (Q5 recommendation) — server-side projection; no `User.FullName` ever in the standings response.
