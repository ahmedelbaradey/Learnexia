# Pipeline Brief — P2-11 Author the skill dependency graph (relational, hand-authored)

## Summary & traceability
- **Task (one line):** Add a relational, hand-authored, acyclic **skill dependency graph** (`KnowledgeNode` + `KnowledgeEdge`) to the **Learning** module so prerequisite-based unlocks and remediation rest on real edges, not flat ordering — the MVP "launch bridge" for the deferred OCR Curriculum-Intelligence pipeline.
- **User story:** `user-stories/Phase-2-Learning-Core/P2-11-author-skill-dependency-graph.md` (source of truth).
- **Task file:** `tasks/Backend/Phase-2-Learning-Core/P2-11-BE.md` (6 BE tasks, backend/infra only — no FE).
- **FR-IDs:** FR-CI-3 (MVP slice — knowledge graph of concepts/skills with prerequisite/related edges), FR-AD-1 (adaptivity reads prereqs), FR-QZ-3 (adaptive quizzing leans on the graph). Forward-compatible with FR-ADM-2 (P7-03 admin authoring surface).
- **BRD goal:** **G2** (learning outcomes) + **G5** (curriculum scale). The barrier-to-entry strategy names this graph *"the most important asset in the whole company."*
- **Phase / Epic:** Phase 2 — Learning Core (Week 3–4) · Epic: Curriculum & Learning Core · SP 5.
- **Product-decision context:** 4 subjects (Math, Science, Arabic, English; no Social Studies); full OCR/Curriculum-Intelligence pipeline (BE1) stays post-MVP in backlog `BL-01..05`. This story records that deferral.

## Business context & value
- Today the MVP relies on the **P2-10 hand-seeded demo trees** which have a flat `Lesson.SequenceOrder` + `Lesson.IsLocked` flag but **no prerequisite edges**. "Fractions depends on Division" cannot be expressed.
- P2-11 pulls forward a thin, **hand-authored** slice of the knowledge graph so the platform can:
  - **P2-04 (Unlock rules / Learning Path Engine):** decide lock/unlock from real prerequisite edges + mastery, and *explain which prerequisite is missing* (P2-04 AC3).
  - **P3-08 (Adaptivity) / P3-10 (prerequisite review / remediation):** when a student struggles, point them at the actual prerequisite skill ("review the prerequisite") instead of guessing from sequence order.
- **Strategic framing:** this is the launch bridge. It deliberately ships *only* a relational, seedable, validated-acyclic graph — **no OCR, no Azure Document Intelligence** — and is designed as a **superset** of the future `BL-04` schema so the eventual ingestion pipeline is an extension, not a rewrite.
- **Who benefits:** students (sensible progression + targeted remediation), content authors/admins (a real graph to author against — P7-03), and the product (the defensible curriculum asset).
- **Success measured by:** edges exist within and across lessons for the MVP subjects/grades; the graph is provably acyclic; P2-04/P3-08/P3-10 read prerequisites from it; and "prerequisites of X" / "unlocked by X" are queryable.

## Acceptance criteria (testable)
1. **New relational entities** `KnowledgeNode` and `KnowledgeEdge` exist in the Learning domain (`learning` schema), matching the SRS §6 relational shape (see field list below). The shape is a forward-compatible superset of `BL-04` (no rename/rewrite later).
2. **Prerequisite edges** can be expressed **within and across lessons** (and the planner must confirm: within/across **units and subjects** too — see open questions).
3. Edges are **hand-authored / seedable** — the P2-10 seeder is extended to attach prerequisite edges for the MVP subjects & grades. **No OCR / Azure DI dependency** anywhere in the path.
4. The graph is **validated as acyclic**: a cycle is **rejected at author/seed time** with a clear domain error (not a generic 500). Unit-tested cycle detection.
5. The graph is **queryable**: `GetPrerequisitesOf(skillId/nodeId)` and `GetUnlockedBy(skillId/nodeId)` return correct results (CQRS queries + endpoints).
6. **P2-04 / P3-08 / P3-10 read prerequisites from this graph**, not from ad-hoc `SequenceOrder`/`IsLocked` ordering. *(See open question on P2-04 not yet existing — BE-6 likely splits into a seam + a follow-up wiring task.)*
7. Deferral of full Curriculum Intelligence (BE1 / `BL-01..05`) is recorded in `user-stories/README.md` (story Notes mandate this).

## Affected modules & data

### Module
- **Learning module only** (schema `learning`). All graph work lives here — same module as the curriculum hierarchy (P2-01) and the quiz entities (P2-06, folded into Learning per lead decision; **do not create a new module — ask first**).
- No cross-module FKs, no cross-module references (CLAUDE.md rule 1). The graph is entirely within `learning`.

### Existing entities (do NOT modify their shape unnecessarily)
All derive from `AggregateRoot` (via `FullAuditedEntity`), int surrogate keys, schema `learning`:
- `Grade` (Number, DisplayName) → `Subject` (Name, Country, GradeId) → `Unit` (Name, SequenceOrder, SubjectId) → `Lesson` (Name, Difficulty, SequenceOrder, IsLocked, UnitId, **nullable SkillId**).
- `Subject` → `Concept` (Name, Description, DifficultyLevel, SubjectId) → `Skill` (Name, MasteryThreshold, EstimatedTimeMinutes, ConceptId).
- `Lesson` *—o1 `Skill` (a lesson optionally teaches one skill).
- Quiz: `QuizQuestion`, `Attempt`, `StudentAnswer` (P2-06).
- DbContext: `backend/src/Modules/Learning/Learnexia.Modules.Learning.Infrastructure/Persistence/LearningDbContext.cs` — DbSets registered here; `OnModelCreating` calls `ApplyConfigurationsFromAssembly`; `SaveChangesAsync(int userId)` stamps audit. **Deferred-commit UoW** module (per ADR 0001): repositories Add/Update only; `UnitOfWorkBehavior` commits once per command.

### New entities (this story)
- **`KnowledgeNode`** — a graph node. SRS §6 fields: `Id PK`, `Name`, `Type` (string/enum — skill vs concept), `SubjectId FK`, `Grade` (int), `Difficulty` (string). **The node represents a Skill (and optionally a Concept).**
- **`KnowledgeEdge`** — a directed edge. SRS §6 fields: `Id PK`, `SourceNodeId FK`, `TargetNodeId FK`, `RelationshipType` (string/enum — `Prerequisite` / `Related`), `Strength` (float). Self-referential to `KnowledgeNode` (both FKs point at `KnowledgeNode`).

## Handoff → db-migration (BE-1, BE-2)
- **Two new entities** in `Learnexia.Modules.Learning.Domain/Entities/`: `KnowledgeNode.cs`, `KnowledgeEdge.cs`. Both derive from `AggregateRoot` (mirror `Skill.cs` / `Concept.cs`).
- **`KnowledgeNode`** properties (per SRS §6): `Name` (string), `Type` (recommend an enum `KnowledgeNodeType { Skill, Concept }` in `Domain/Enums/` — mirrors existing `DifficultyLevel` enum usage), `SubjectId` (int, plain int — **no cross-subject ambiguity**, points at `learning.Subject`), `Grade` (int), `Difficulty` (reuse existing `DifficultyLevel` enum). **Decision needed (see open Q):** whether the node also carries a `SkillId`/`ConceptId` link to the existing `Skill`/`Concept` rows (recommended so the seeder can map by skill name) or stands alone.
- **`KnowledgeEdge`** properties: `SourceNodeId` (int FK → KnowledgeNode), `TargetNodeId` (int FK → KnowledgeNode), `RelationshipType` (recommend enum `EdgeRelationshipType { Prerequisite, Related }`), `Strength` (float / `double`, 0–1).
- **EF configuration** (`Persistence/Configurations/KnowledgeNodeConfiguration.cs`, `KnowledgeEdgeConfiguration.cs`): conventions handle most of it (Catalog/Learning style), **but the self-referential double-FK on KnowledgeEdge needs explicit config** to avoid EF cascade/shadow-property ambiguity:
  - Two relationships from `KnowledgeEdge` to `KnowledgeNode` (Source + Target). Configure both with `.OnDelete(DeleteBehavior.Restrict)` (do **not** cascade — a node deletion must not silently chain-delete edges in unexpected directions; Restrict is the safe default for a self-referential graph).
  - **Indexes:** non-unique index on `(SourceNodeId)` and on `(TargetNodeId)` (per task BE-2). Strongly recommend an additional **unique composite index on `(SourceNodeId, TargetNodeId, RelationshipType)`** to prevent duplicate edges — flag for planner to confirm.
- **DbSets:** add `DbSet<KnowledgeNode>` and `DbSet<KnowledgeEdge>` to `LearningDbContext`.
- **Migration:** one Npgsql migration in `Learnexia.Modules.Learning.Infrastructure/Migrations/`, schema `learning`, `MigrationsHistoryTable("__EFMigrationsHistory", "learning")`. Name suggestion: `AddSkillGraphTables`. Tables `knowledge_nodes`, `knowledge_edges` (match existing snake/Pascal table-naming used by prior Learning migrations — check the latest migration for the convention; P2-06 used `quiz_questions` style).
- **Provider:** `UseNpgsql` (PostgreSQL). Learning migrations auto-apply at startup via `LearningModule.InitializeAsync` → `dbContext.Database.MigrateAsync()`.
- **No pgvector** — this is the relational slice; embeddings stay post-MVP.

## Handoff → backend-feature (BE-3, BE-4, BE-5, BE-6)

### BE-3 — Acyclic validation (`Domain/Services/SkillGraphValidator.cs` + tests)
- A domain service that, given the prerequisite edges, runs a **DFS cycle check** over the directed graph (Prerequisite edges only — Related edges are non-directional/non-blocking and should be excluded from the acyclic constraint; confirm with planner).
- On a detected cycle, throw a **clear domain error** (use the existing error/response conventions — surface as a business/validation error, not a raw 500). The seeder (BE-4) and any future author command (P7-03) call this before persisting.
- **Unit-tested** in `Modules.Learning.UnitTests` (mirror `QuizQuestionTypeValidationTests.cs`): cycle present → rejected; acyclic graph → passes; self-loop → rejected; cross-lesson chain stays valid.
- **Pattern caution:** a graph DFS validator is a plain domain service, not a new "design pattern" — mirror existing helper/service shapes. If anything richer (Strategy/visitor) is contemplated, **stop and ask the lead** (CLAUDE.md rule 8).

### BE-4 — Seed/author path (extends `LearningSeeder`)
- Extend `backend/src/Modules/Learning/Learnexia.Modules.Learning.Infrastructure/Persistence/Seed/LearningSeeder.cs` (the P2-10 idempotent seeder).
- **Critical reuse fact (from HANDOFF P2-10):** Skill `Name` strings are **stable lookup keys** — P2-11 maps prerequisite edges by skill name. **Do NOT rename any seeded skill name string.** The seed creates one `KnowledgeNode` per skill (idempotent natural-key check, mirror `EnsureSkillAsync`), then attaches `KnowledgeEdge` rows between nodes.
- **Idempotent** (re-run adds zero rows; natural-key check on node identity + on `(Source, Target, Type)`). Uses `SystemUserId = 0`.
- Author **prerequisite edges within and across lessons** for the MVP subjects (Math is the deepest tree — natural chains like Counting → Place Value → Addition → Multiplication → Division → Fractions). Must run the **BE-3 validator before saving** so the demo graph is provably acyclic.
- **No OCR / Azure DI** — pure hand-authored seed data.
- Runs Development-only via `LearningModule.InitializeAsync` (env check stays in the module, seeder stays env-neutral so unit tests call it directly).

### BE-5 — Query API (CQRS)
- Two queries under `Application/Features/<SkillGraph or KnowledgeGraph>/Queries/`:
  - `GetPrerequisitesOf` (input: skill/node id) → nodes that are sources of `Prerequisite` edges targeting the given node ("what must I master first").
  - `GetUnlockedBy` (input: skill/node id) → nodes reachable as targets when the given node is mastered ("what does mastering X unlock").
- Mirror the existing Learning query shape: `record XQuery : IQuery<BaseResponse<T>>`, handler inherits `BaseResponseHandler` + `IQueryHandler<,>`, returns `BaseResponse<T>`, try/catch → `ServerError<T>`, inject `ILearningServiceManager` + `ILoggerManager`. Reference: `GetSkillQueryHandler.cs`.
- **Queries are NOT auto-validated** (CONVENTIONS §4/§13) — validate the id inside the handler or accept unvalidated.
- For custom graph traversal not covered by `BaseService`, use the **`IRepositoryManager`** path (typed repository) — mirror `ICategoryRepository`/Catalog. DTOs in `Features/.../Dtos/`; AutoMapper profile + `ProjectTo` for projection.
- **Endpoints:** add to a controller (likely a new `SkillGraphController` or extend `SkillsController`) under `api/learning/...`, using `NewResult(await Mediator.Send(query))`. Register its assembly part in `LearningModule.AddLearningModule` if a new controller class is added. **`[Authorize]` is deliberate** — confirm with planner whether these are public-to-students or admin-only (P7-03 authoring is admin; read queries likely student-readable). Decide intentionally (CONVENTIONS §13).

### BE-6 — Wire P2-04 / P3-08 / P3-10 (RISK — see open questions)

## Open questions / assumptions / risks
1. **Does `KnowledgeNode` replace or wrap `Skill`?** — RECOMMENDATION/assumption: it **wraps** (sits alongside). `Skill` stays the curriculum-hierarchy entity (Concept→Skill, taught by Lessons, has MasteryThreshold); `KnowledgeNode` is a separate graph projection that **links to `Skill` via a `SkillId`** so the seeder can map nodes to skills by name and queries can join back. SRS §6 models `KnowledgeNode` as its own entity with `SubjectId`/`Grade`/`Difficulty` (overlapping Skill data) — it is **not** an FK on Skill. **Confirm with lead:** add a nullable `SkillId` (and/or `ConceptId`) link on `KnowledgeNode`, or keep it fully standalone and map purely by name? (The SRS field list does not include a SkillId; adding one is a forward-compatible superset and makes BE-4/BE-5 cleaner.)
2. **Graph scope — within-subject only, or cross-subject?** Story says "within and across lessons." Lessons can cross units within a subject. Does the MVP graph also cross **subjects** (e.g. an English skill prereq for a Math word-problem skill)? RECOMMENDATION: allow cross-unit and within-subject edges; keep cross-subject edges *possible in the model* (SubjectId on node, no constraint forbidding it) but **don't author cross-subject edges in the demo seed** unless the lead wants them. Confirm.
3. **Acyclic-check scope.** Is the acyclic constraint over **all** edges or **Prerequisite edges only**? RECOMMENDATION: enforce acyclicity over `Prerequisite` edges only (the directional, blocking relationship); `Related` edges are advisory and excluded. Confirm.
4. **BE-6 dependency inversion (highest risk).** `P2-04` (and P3-08/P3-10) are not yet implemented. BE-6's dep `P2-04-BE-*` cannot be satisfied within P2-11. RECOMMENDATION: deliver the seam (BE-5 + repository/query interface) in P2-11 and **defer the consuming-engine wiring** to P2-04/P3-08/P3-10, with a documented integration contract + TODO. **The lead should confirm** whether to (a) descope BE-6 to "seam only," or (b) hold P2-11 until P2-04 lands (not recommended — P2-11 is the *foundation* for P2-04). Planner must resolve this before batching.
5. **Edge uniqueness / duplicate prevention.** Recommend a unique composite index `(SourceNodeId, TargetNodeId, RelationshipType)`. Confirm with planner.
6. **`Strength` semantics & default.** SRS defines `float Strength` but no scale. Assume 0.0–1.0, default 1.0 for hand-authored hard prerequisites. Confirm.
7. **Authz on the read queries.** Student-readable vs admin-only? `[Authorize]` is not enforced by default — decide intentionally. Assume read queries are authenticated-readable; authoring (P7-03) is admin.
8. **architecture.md is stale on the DB** (says SQL Server) — trust the code: PostgreSQL/Npgsql everywhere (CONVENTIONS §13).
