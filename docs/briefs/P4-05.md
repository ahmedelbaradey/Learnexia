## Summary & traceability

- **Task (1 line):** Add a per-student **badge engine** to the Gamification module - introduce a small `BadgeDefinition` catalog (seeded ~10 rows) + a `StudentBadge` ledger, subscribe to the existing in-module domain events (`StreakAdvancedDomainEvent`, `StudentLeveledUpDomainEvent`) and the cross-module `LessonCompletedIntegrationEvent`, deterministically evaluate badge predicates after each event, award unlocked badges (at most once per student per badge - DB unique key (StudentId, BadgeDefinitionId)), expose `IStudentBadgesQuery` cross-module so Learning's dashboard can show "X badges earned" + a recent-3 list, and surface a `GET /api/Gamification/Badges/Me` collection endpoint returning both earned and locked badges (for the future P4-08 collection screen). No new module, no new schema.
- **User story (source of truth):** `user-stories/Phase-3-Gamification/P4-05-badges.md` - 3 SP, Phase 3 Gamification (Week 5), Epic = Gamification Module, FR-GM-4. ## Business context & value

- **Who benefits:** the **student** directly - badges are the long-tail, visible status symbol that XP can't be ("you have 1,250 XP" vs "you earned the Math Master badge"). They reward milestones the student can name, screenshot, and tell their parent about. **Secondary - the parent**: badges are the most legible signal of progress in a weekly report. **Tertiary - the system**: badges create a content-finishable goal beyond "keep grinding XP."
- **Why it matters now:** XP (P4-02), streaks (P4-03), hearts (P4-04) are all *counters*. Without badges, every Phase-3 reward feels continuous - there is no *moment* of "I just unlocked something." Badges create the unlock-moment that closes the dopamine loop. **P4-08 (the gamification UI motion)** can't render badge-pop-in animations without rows to render; **P5-04 (parent weekly report)** lists "Badges earned this week"; **P4-09 (re-engagement nudges)** can use "you're 1 day from the 7-day streak badge" as a soft prompt. P4-05 unblocks all three.
- **Success measurement:**
  - Every `LessonCompletedIntegrationEvent` runs the badge evaluator; first-lesson badge fires once per student.
  - Every `StreakAdvancedDomainEvent` runs the streak-threshold predicates (3/7/14/30-day badges); each fires once per student when the threshold is crossed.
  - Every `StudentLeveledUpDomainEvent` runs the level-threshold predicates (Level 5/10/20 badges); each fires once per student.
  - Award writes exactly one `StudentBadge` row per (StudentId, BadgeDefinitionId); a redelivered/re-evaluated event is a no-op (DB unique key is the backstop + handler pre-check).
  - `GET /api/Learning/Dashboard` returns `BadgesCount = N` and `RecentBadges = [top 3 by AwardedAtUtc DESC]`.
  - `GET /api/Gamification/Badges/Me` returns all 10 badge definitions, each with an `IsEarned` flag and `AwardedAtUtc?` for earned rows (no PII, IDOR-proof by JWT-scoping).
- **Deterministic principle (BRD §8 / FR-AI-6):** badge predicates are **pure boolean functions** over `(event, profile snapshot, already-earned set)`. No AI, no randomness. The catalog is config-as-code (seeded), tunable per env at deploy time only.

## Acceptance criteria (verbatim from story + testable backend gates)

From `P4-05-badges.md`:

1. **AC1 - Badges are awarded by rule (e.g., skill mastered, N-day streak, quiz master) evaluated on relevant events.**
   - Backend gate: three new `INotificationHandler<>` classes in `Gamification.Application/Features/Badges/EventHandlers/` subscribe respectively to `LessonCompletedIntegrationEvent` (cross-module), `StreakAdvancedDomainEvent` (in-module, fired after `AdvanceStreakCommandHandler` commits), and `StudentLeveledUpDomainEvent` (in-module, fired after `ApplyAward` commits). Each handler loads the student's earned-badge set + relevant snapshot fields (streak/level/lesson-count), calls `BadgePredicateEvaluator.Evaluate(event, profile, earnedIds, catalog)` which returns the **list of BadgeDefinition IDs to award**, then for each, sends an `AwardBadgeCommand`. The command runs through `UnitOfWorkBehavior` -> atomic write -> after-commit dispatch of (future) `BadgeEarnedDomainEvent`.
   - Per-event handler isolation: a crash in the streak-badge handler must not kill the XP write nor the level-badge handler (`IsolatedNotificationPublisher` guarantees this at the publisher level; each handler also wraps its `mediator.Send` in try/catch for observability).

2. **AC2 - Earning a badge writes a `StudentBadge` record and triggers a reward popup.**
   - Backend gate: `AwardBadgeCommandHandler` writes one `StudentBadge` row with `(StudentId, BadgeDefinitionId, AwardedAtUtc = event.OccurredOnUtc, OriginEventId, OriginEventType)`. Raises `BadgeEarnedDomainEvent(StudentId, BadgeCode, BadgeName, BadgeRarity, AwardedAtUtc)` for the popup - **defined, no consumer this cycle** (P4-08 owns the FE pop-in animation). The popup itself is a P4-08 surface; this story ships the data signal.

3. **AC3 - A badge is awarded at most once per its condition (no duplicates).**
   - Backend gate: **two layers**:
     - (a) **DB unique constraint** `UX_StudentBadges_StudentId_BadgeDefinitionId` - the backstop.
     - (b) **Handler pre-check** via `HasBadgeAsync(studentId, badgeDefinitionId, ct)` BEFORE staging the insert; short-circuits + logs `"P4-05: badge already earned"` and returns Success without write.
   - `DbUpdateException` catch on the unique-constraint violation also short-circuits to Success (idempotency race tie-break - mirrors P4-03's `UX_XpAwards_OriginEventId_Reason` catch).

4. **AC4 - Earned and locked badges are visible in a badge collection screen.**
   - Backend gate: `GET /api/Gamification/Badges/Me` returns `BadgeCollectionDto { IReadOnlyList<BadgeCollectionItemDto> Badges }` where each item carries `(Code, Name, Description, IconKey, Rarity, IsEarned, AwardedAtUtc?)` - the full catalog, ordered by Rarity ASC then SortOrder. Earned rows have `IsEarned = true` + `AwardedAtUtc`; locked rows have `IsEarned = false` + null. JWT-scoped (uses `_currentUser.UserId`); no `studentId` route param (IDOR-proof by construction). **The collection screen itself is P4-08 FE** - this story ships the API.

   ```csharp
   public static IReadOnlyList<int> Evaluate(
       BadgeEvaluationContext ctx,
       IReadOnlyList<BadgeDefinition> catalog,
       IReadOnlySet<int> alreadyEarnedBadgeDefinitionIds)
   {
       var matches = new List<int>();
       foreach (var def in catalog)
       {
           if (alreadyEarnedBadgeDefinitionIds.Contains(def.Id)) continue;
           if (def.TriggerType != ctx.Source) continue;
           bool eligible = ctx.Source switch
           {
               BadgeTriggerType.FirstLesson      => (ctx.LessonCount ?? 0) >= 1,
               BadgeTriggerType.StreakThreshold  => (ctx.StreakValue ?? 0) >= (def.Threshold ?? int.MaxValue),
               BadgeTriggerType.LevelThreshold   => (ctx.LevelValue  ?? 0) >= (def.Threshold ?? int.MaxValue),
               _ => false,
           };
           if (eligible) matches.Add(def.Id);
       }
       return matches;
   }
   ```

### C. Three notification handlers (P4-05-BE-5, BE-6, BE-7)

Each in `Gamification.Application/Features/Badges/EventHandlers/`. Pattern identical, only the event type + context-builder differ.

```csharp
public sealed class BadgeEvaluationOnStreakAdvancedHandler
    : INotificationHandler<StreakAdvancedDomainEvent>
{
    private readonly IMediator _mediator;
    private readonly IGamificationRepository _repo;
    private readonly ILoggerManager _logger;

    public async Task Handle(StreakAdvancedDomainEvent ev, CancellationToken ct)
    {
        try
        {
            var earnedIds = (await _repo.GetEarnedBadgeIdsAsync(ev.StudentId, ct)).ToHashSet();
            var catalog   = await _repo.GetAllBadgeDefinitionsAsync(ct);
            var ctx       = new BadgeEvaluationContext(
                ev.StudentId, BadgeTriggerType.StreakThreshold,
                StreakValue: ev.NewStreak, LevelValue: null, LessonCount: null);

            var toAward = BadgePredicateEvaluator.Evaluate(ctx, catalog, earnedIds);

            foreach (var badgeDefId in toAward)
            {
                await _mediator.Send(new AwardBadgeCommand(
                    StudentId: ev.StudentId,
                    BadgeDefinitionId: badgeDefId,
                    OriginEventId: ev.EventId,
                    OriginEventType: nameof(StreakAdvancedDomainEvent),
                    AwardedAtUtc: ev.OccurredOnUtc), ct);
            }
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, $"P4-05: Error evaluating streak badges " +
                $"(studentId={ev.StudentId}, newStreak={ev.NewStreak}).");
        }
    }
}
```

`BadgeEvaluationOnLessonCompletedHandler` mirrors with `BadgeTriggerType.FirstLesson` and loads `LessonCount` via `_repo.GetCompletedLessonCountAsync(StudentId, ct)`. `BadgeEvaluationOnStudentLeveledUpHandler` mirrors with `BadgeTriggerType.LevelThreshold`.

All three handlers run AFTER the originating UoW commit (domain events dispatched post-commit per ADR 0002 §2); each `await _mediator.Send(AwardBadgeCommand)` opens its OWN UoW transaction - **independent failure domains**.

### H. Hardening (do NOT skip)

- **Per-(StudentId, BadgeDefinitionId) idempotency** - two layers: `HasBadgeAsync` pre-check + DB unique constraint. Defense-in-depth.
- **Per-handler isolation** - each notification handler wrapped in try/catch (fail-soft). `IsolatedNotificationPublisher` also isolates at the publisher level.
- **Per-AwardBadgeCommand UoW** - each `_mediator.Send` from an event handler opens its own transaction; one badge failure doesn't roll back siblings.
- **No `ex.Message` echoed** to clients (catch in handler returns `ServerError<T>()`).
- **JWT-derived StudentId in queries** - `GetMyBadgesQueryHandler` uses `_currentUser.UserId`; **no `studentId` route/query parameter** (IDOR-proof by construction). Mirrors `GetDashboardQuery`.
- **Trust the event payload's `StudentId`** in notification handlers - not `_currentUser` (which is null in the post-commit dispatch scope). Same invariant as P4-02/03/04.
- **Catalog tampering** - `BadgeDefinition` rows are seeded; no public mutation path until P7-03. No risk from this cycle.
- **Conventions:** module isolation (no cross-module project ref), `ILoggerManager` only, `BaseResponse<T>`, `Successed`, no design pattern (rule 8).

**Q3 - Catalog copy: store English+Arabic on the row, or store i18n keys only and resolve client-side / via resx?**

**Q6 - How does `BadgeEarnedDomainEvent` get raised? On a no-op aggregate, or via direct dispatcher call from the handler?**

The handler doesn't have a `StudentXpProfile` in scope by default; **load it cheap + Q5-FK-it, then `profile.RaiseBadgeEarnedDomainEvent(...)`**.
- **Option C**: Inject `IDomainEventDispatcher` directly into `AwardBadgeCommandHandler` and dispatch immediately after `SaveChangesAsync` - bypasses the aggregate seam. Cleanest in code; small departure from convention.
- **Recommend Option B** - keep `StudentBadge` as a ledger (audit-integrity argument from P4-04 holds), load `StudentXpProfile` (we need it for the Q5 FK anyway), call a small `profile.RecordBadgeEarned(badgeDefinition, awardedAt)` method that raises `BadgeEarnedDomainEvent` without mutating profile state.
