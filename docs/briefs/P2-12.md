# Pipeline Brief — P2-12 Parent account settings APIs (Identity, backend)

## Summary & traceability
- **Task (one line):** Extend the existing **Identity** module with the four remaining parent-settings backend surfaces — notification preferences, linked-children management, security (change-password + other-session invalidation), and a read-only plan/billing stub — reusing P1-02/P1-04/P1-05/P1-12 building blocks rather than duplicating them.
- **User story:** `user-stories/Phase-2-Learning-Core/P2-12-account-settings-tabs.md` (child stories P2-12a notifications, P2-12b linked children, P2-12c security, P2-12d plan & billing). This story is the **source of truth**.
- **Task file:** `tasks/Backend/Phase-2-Learning-Core/P2-12-BE.md` (BE-1…BE-5).
- **FR-IDs (SRS):** account/profile management + family link/RBAC (FR-AUTH / FR-USR family-scope), notification preferences (FR-NOTIF), subscription/plan read (FR-BILL — out-of-scope beyond read stub). Reviewer should confirm exact FR-IDs against `docs/SRS.md §6` during the gate; the story acceptance criteria are the binding contract.
- **BRD goal:** G1 (parent control/engagement) — parents self-manage their account, family, and alerts.
- **Phase/Epic:** Phase 2 — Learning Core sprint (placed here by product owner); Epic = Parent web app, extends P1-11 settings shell.

## Business context & value
- **Who benefits:** the **parent** (primary). Parents need to fully self-serve their account from the web settings page: control how/when they get alerted, manage which children are linked, keep the account secure (rotate password, kill stray sessions), and understand their current plan.
- **Value:** completes the settings surface carved out of P1-11; reduces support load (self-service unlink, self-service password/session control); sets up a future payments story without committing to a provider now.
- **Success measures:** each tab's acceptance criteria pass; prefs persist per user; family-scope authz blocks cross-family access; password change invalidates *other* sessions; plan read returns a deterministic DTO.

## Acceptance criteria (testable)
**Notification preferences (BE-1)**
- `GET` returns the authenticated parent's preferences (per type × channel); first read for a user with no row returns sensible **defaults** (not 404).
- `PUT` upserts the parent's own preferences; returns the updated set; persisted per user; `[Authorize]` self-scope (id from JWT, never body).
- Response is `BaseResponse<T>`, camelCase, `Successed` flag.

**Linked children (BE-2)**
- `GET` lists only the caller's own linked children (reuse `ListMyChildrenQuery` semantics — `ParentStudent.ParentId == callerId`).
- `link` (by child email) and `unlink` enforce **family scope** — a parent can only link/unlink their own children; cross-family attempts fail closed with a generic message (mirror `LinkChildCommandHandler` enumeration defence).
- `unlink` removes the `ParentStudent` row for (callerId, childId); idempotent (unlinking a non-link is a no-op success or 404 — decide in planning, see open Q).
- Acting parent always resolved from JWT; no `ParentId` in the body.

**Security (BE-3)**
- `change-password` validates the current password, enforces the configured Identity password policy, rejects new == current; returns clear success/error.
- On success, **other** sessions are invalidated while the current session remains valid (active-sessions list shrinks to just the current one); refresh tokens for the user are revoked.
- (If exposed) `active-sessions` returns the caller's own sessions; `sign-out-others` terminates all sessions except the current one.

**Plan & billing (BE-4)**
- `GET` current plan returns a read-only DTO for the caller (e.g. `{ planName, status, since/renewsAt? }`). No payment-provider calls. Stub data acceptable (hardcoded "Free" if no subscription model exists).

**Migration (BE-5)**
- Npgsql migration adds the new persistence (notification prefs table; plan table only if BE-4 is modeled rather than hardcoded) in the `identity` schema; `dotnet ef database update` applies cleanly; model snapshot updated.

## Affected modules & data (new vs existing)
**Module:** Identity only. No cross-module project references; any cross-module need goes through `Shared.Contracts`. No Unit of Work — `GenericRepository`/DbContext commits per call; open an explicit transaction only for atomic multi-writes.

**New entities/fields**
- **`NotificationPreference`** (new) — per-user preferences. Recommended shape: one row per `(UserId, NotificationCategory)` with boolean channel flags (`EmailEnabled`, `PushEnabled`), or a single JSON column. **Shape is an open question** — see below. Table in `identity` schema, `UserId` → `AspNetUsers.Id`, `DeleteBehavior.Restrict` (matches module default), index on `UserId`.
- **Plan/subscription** — likely **no new entity** (BE-4 is a stub). If a row is needed later, defer to a payments story.

**Existing entities/services reused (extend, do not duplicate)**
- `ParentStudent` (P1-04) + `LinkParentStudentService` (`LinkAsync`, `IsLinkedAsync`, `StudentHasAnyParentAsync`, `GetLinkedStudentsAsync`) — **needs a new `UnlinkAsync`** method for BE-2.
- `FamilyScopeAuthorizationHandler` / `FamilyScopeRequirement` (P1-05) — reuse for unlink authz (resource = target studentId).
- `LinkChildCommand`/`Handler` + `LinkedChildResponse` + `ListMyChildrenQuery` (P1-04) — reuse directly for BE-2 list/link.
- `ChangePasswordCommand`/Handler + `IAuthenticationService.ChangePasswordAsync` (P1-12) — reuse; **extend** the handler to invalidate other sessions. NOTE: the existing handler lives under `Features/Users/Commands/ChangePassword` but the class is named `SetNewPasswordCommandHandler` and currently is **not wired to a self-service controller route** — verify where/if it is exposed (see open Q).
- `ISessionManagementService` (P1-02): `GetUserSessionsAsync(userId)`, `TerminateSessionAsync(sessionId, reason)` — sessions are **Redis/`IDistributedCache`-backed, not a DB table**. Current-session id comes from the `"SessionId"` JWT claim (see `SignOutCommandHandler.GetCurrentSessionId`). Refresh-token revocation = `IDistributedCache.RemoveAsync($"userrefreshtoken-{userId}")`. Use `SessionTerminationReason.SecurityRevocation` for password-change invalidation.
- `AccountController` (`api/Users/Account/...`) — the natural home for self-scoped settings endpoints; mirror its `[Authorize]` + JWT-resolved-id pattern.

## Handoff → db-migration
- Add **`NotificationPreference`** entity + an `IEntityTypeConfiguration<NotificationPreference>` mirroring `ParentStudentConfig` (table in `IdentityModuleDbContext.Schema = "identity"`, `Restrict` delete, index on `UserId`, `CreatedAt`/`UpdatedAt` with `now()` default if tracked). Register a `DbSet<NotificationPreference>` on `IdentityModuleDbContext`.
- Generate the Npgsql migration against `IdentityModuleDbContext` (factory: `IdentityModuleDbContextFactory`); update `IdentityModuleDbContextModelSnapshot`.
- **No FK to other modules.** No plan table unless BE-4 is modeled (default: do not create one).
- Depends on the final entity shape from BE-1 (resolve the open Q first).

## Handoff → backend-feature
Commands/queries (MediatR; commands = `ICommand<BaseResponse<T>>` so `ValidationBehavior` runs; queries not auto-validated). Controllers return `NewResult(...)`; success flag is `Successed`.
- **BE-1:** `GetMyNotificationPreferencesQuery` + `UpdateMyNotificationPreferencesCommand` (upsert) + DTO `NotificationPreferencesResponse` (per category × channel) + FluentValidation + AutoMapper profile. Endpoints on `AccountController`: `GET /api/Users/Account/NotificationPreferences`, `PUT /api/Users/Account/NotificationPreferences`. `[Authorize]`, id from `ICurrentUserService`.
- **BE-2:** Reuse `ListMyChildrenQuery` for `GET /api/Users/Parent/My-Children` (already exists — confirm it covers the list AC, may need no new code). Reuse `LinkChildCommand` for link. Add `UnlinkChildCommand` + handler + `UnlinkAsync` on `LinkParentStudentService`; endpoint `DELETE`/`POST` `api/Users/Parent/Unlink-Child`. Family scope enforced in-handler (JWT parent id + `ParentStudent` check) consistent with existing handlers; consider invoking `FamilyScopeAuthorizationHandler` for the resource check.
- **BE-3:** Extend the change-password handler to, on success, terminate the user's *other* sessions (`GetUserSessionsAsync` minus current `SessionId` claim → `TerminateSessionAsync(..., SecurityRevocation)`) and revoke the refresh token. Expose a self-scoped `POST /api/Users/Account/ChangePassword` if not already routed. Optionally add `GET /api/Users/Account/Sessions` (`active-sessions`) + `POST /api/Users/Account/Sessions/SignOutOthers` backed by `GetUserSessionsAsync`/`TerminateSessionAsync`. Drop `UserId` from the command surface — resolve from JWT (current command carries a `UserId` that must NOT be honored from the body).
- **BE-4:** `GetMyPlanQuery` + `CurrentPlanResponse` DTO; handler returns a hardcoded "Free" plan (status `Active`) keyed on the caller. Endpoint `GET /api/Users/Account/Plan`. No payment provider.

## Handoff → frontend (FE is a separate P2-12-FE story)
Out of scope for this backend brief, but the BE contract the FE consumes:
- Notification prefs DTO: per category (e.g. weeklyReport, streakAtRisk, product) × channel (email, push) booleans.
- Linked-children list (`{ id, fullName, email }[]`) + link-by-email result + unlink result.
- Change-password result (success/error message); active-sessions list (`SessionInfo` shape) + sign-out-others result if exposed.
- Current-plan DTO (`{ planName, status, ... }`). Design source of truth: `design-system/screenshots/web/07-settings.png`.

## Open questions / assumptions / risks
1. **Notification preferences shape (BLOCKER for BE-1/BE-5).** The story's FE-facing categories are *weekly report, streak/at-risk, product* (email/push), but the existing Notifications module enum is `System | Welcome | Reminder` (Guid-keyed, different concept). These do not align. **Recommend:** define an Identity-local `NotificationCategory` enum for *parent preference* purposes (WeeklyReport, StreakAtRisk, Product — confirm the exact set with the product owner) decoupled from the Notifications module's delivery enum. Need product sign-off on the canonical category list and channels (email + push only? in-app?).
2. **Plan/subscription model.** No subscription/Plan entity exists in the codebase today (only the Notifications `SendNotificationCommand` matched the search). **Assumption:** BE-4 returns a hardcoded "Free" plan DTO, no table, no migration row. Confirm acceptable; flag the follow-up payments story for upgrade/checkout (story explicitly defers it).
3. **Change-password reuse vs new.** A change-password command + `IAuthenticationService.ChangePasswordAsync` already exist (P1-12), but the handler (`SetNewPasswordCommandHandler`) does **not** currently invalidate other sessions and its self-service controller route is unconfirmed. **Recommend:** extend the existing handler (add session invalidation + refresh-token revoke) and ensure a self-scoped route exists, rather than creating a parallel command. Also remove reliance on the body `UserId`.
4. **Sessions are cache-backed, not DB.** Active-sessions/sign-out-others are feasible via `ISessionManagementService` (Redis). `SessionInfo` has no device/IP/user-agent metadata — the FE "active sessions" list will be minimal (created/last-activity/expiry only). Confirm that's acceptable for the security tab, or scope active-sessions UI to "sign out others" only.
5. **Unlink idempotency + last-parent guard.** Define unlink behavior when the child has no other parent (orphaned child account) — is that allowed, or must a child always retain ≥1 parent? Product decision needed; default assumption: unlink allowed, child simply becomes unlinked (re-linkable later).
6. **Security-sensitive pipeline.** This batch touches **user data + auth/sessions + password change**. Per CLAUDE.md, **`security-auditor` must run before the reviewer gate**; Critical/High findings block. Also confirm endpoints carry deliberate `[Authorize]` (policies exist but aren't auto-enforced).
