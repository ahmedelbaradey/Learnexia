> **Contract correction vs the FE task file.** The task file's "Contract from Backend" was written against the *predicted* BE shape and is now **stale** in several places. The merged controller is the source of truth — differences the FE MUST follow:
> - Activate/deactivate is **`PATCH .../Badges/{id}/active`** and **`PATCH .../Missions/{id}/active`** with body `{ isActive }` — **not** `DELETE`. There is **no DELETE** for badges/missions at all (deactivate is the soft-retire; preserves earned ledger rows).
> - All catalog/event IDs are **`int`**, not `Guid`.
> - League-tier body field is **`newTier`** (`OverrideLeagueTierBody.NewTier`), values `Bronze=1..Diamond=4`, **not** a free-form `tier`.
> - Timed-event create/update bodies carry **bilingual** `nameEn/nameAr` + optional `descriptionEn/descriptionAr` (the BE is the i18n store for event copy — distinct from FE UI i18n).
> - There is **no `GET` for timed events on `AdminGamificationController`** — the list lives on a **separate controller**: `GET api/admin/timed-events` (returns `TimedEventListItemDto`).

## Business context & value
- **Who benefits:** the **admin/ops** persona (only privileged role — no teacher role). Downstream value to **students/parents** is indirect: corrected league standings, fixed catalog metadata, promo timed events, support-case streak-freeze grants — all without hand-editing seed data or the DB.
- **Value:** Phase-4 gamification shipped read-only for admins; this FE is the operational lever. Every write is **AdminOnly + audited** (P7-12), so ops actions are traceable.
- **Success measure:** an admin can perform each of the five overrides from the console; child-affecting actions require a typed Reason + explicit confirm; the UI reflects the new state after invalidate/refetch (no optimistic writes); non-admins never reach the screens.

## Acceptance criteria (FE-testable)
1. **Nav + guard** — a "Gamification" entry appears in `AdminSideNav`; `/(admin)/gamification/*` routes are wrapped by `AdminShell` and gated by `useAdminGuard` (loading → skeleton; non-admin/signed-out → redirect to `/login`; authorized → content). No protected content flashes before the guard resolves.
2. **Badge catalog** — list page shows all badges (active + inactive, from `GET .../Badges`) with `ActiveBadge` status; create + edit via a `BadgeForm` (code [create-only, immutable on edit], name, description, iconKey, rarity, triggerType, threshold, rewardXp); activate/deactivate via `PATCH .../active` behind a confirm. Loading/empty/error+retry states. After any mutation, list invalidates + refetches (no optimistic). Deactivation never removes earned badges (BE-enforced; UI copy says "retire / hide from catalog", not "delete").
3. **Mission catalog** — list (all, from `GET .../Missions`) + create/edit via `MissionForm` (code [create-only], iconKey, titleKey, cadence [Daily/Weekly], targetType [CompleteLessons/CorrectAnswers/MaintainStreak], target, rewardXp, sortOrder); activate/deactivate via `PATCH .../active`. Same states + invalidate/refetch.
4. **Timed events** — list (from `GET api/admin/timed-events`) with a status badge (Scheduled / Active / Expired derived from `isActive` + `startUtc`/`endUtc` vs now); create/edit via `TimedEventForm` (code [create-only], nameEn/nameAr, descriptionEn/descriptionAr, startUtc, endUtc, multiplier 1.00–5.00, scope [AllXp/MissionXp/LeagueXp]); activate (`POST .../{id}/activate`) and expire (`POST .../{id}/expire`) behind confirm. Validation: start strictly before end, multiplier in range. Same states + invalidate/refetch.
5. **League-tier override** — admin picks a **student** (student-picker — see Q1), the dialog shows the student's current tier (from `useUserActivity` → `league.tier`, see Q1 caveat), selects a new tier (Bronze/Silver/Gold/Diamond), enters a **required Reason** + confirm; submit calls `POST .../children/{childId}/league-tier {newTier, reason, confirm:true}`. Same-tier no-op disabled in the UI; envelope `Successed=false` surfaced as an inline error. Uses `AdminConfirmDialog` + `ReasonField`.
6. **Streak-freeze grant** — admin picks a student, enters a count (1..`MaxFreezes`=2), required Reason + confirm; submit calls `POST .../children/{childId}/streak-freeze {count, reason, confirm:true}`. Current freeze balance display is a known gap (Q2). Uses `AdminConfirmDialog` + `ReasonField`.
7. **Reason-required pattern** — both child-affecting overrides gate the confirm button until Reason is non-empty (≤500 chars) and `confirm` is set; reason is sent trimmed. (Catalog/timed-event edits are platform-config and do **not** require a Reason — the BE validators do not demand one there.)
8. **RTL + bilingual** — all labels, enum option labels (tiers, rarities, cadences, scopes, statuses), dialog copy, dates and numbers render correctly in `ar` (RTL) and `en` via `lib/strings.ts` (the admin app uses a single build-time `ADMIN_LOCALE`, mirroring Waves 1–2). Numbers/dates use `dir="ltr"` spans + tabular-nums per the existing pattern.
9. **Audit** — no FE work beyond calling the audited endpoints; every write is recorded by P7-12 and will appear in the audit log. (The FE does not display the audit trail in this story.)
10. **No optimistic mutations** — every mutation `onSuccess` invalidates the relevant `adminGamification.*` key(s) and lets TanStack refetch; the table reflects server truth.

## Exact backend contract per the 5 areas (source of truth = the merged controller)
Base route: **`api/Admin/Gamification`**, every action `[Authorize(Policy = AdminOnly)]`. All responses are the `BaseResponse<T>` envelope (`Successed`/`Message`/`Data`); the `apiClient` already unwraps to `Data` and throws a typed error when `Successed === false`.

### Area 1 — League-tier override (child-affecting; Reason required)
- `POST api/Admin/Gamification/children/{childId}/league-tier` → `BaseResponse<bool>`
  - body: `{ newTier: LeagueTier, reason: string, confirm: boolean }`
  - `LeagueTier`: `Bronze=1, Silver=2, Gold=3, Diamond=4`
  - BE validator: `childId>0`, `newTier` in enum, `reason` NotEmpty + max 500, `confirm == true`.
- **Read current tier:** no dedicated gamification read; reuse `GET api/Admin/Users/{id}/activity` → `league.tier` (string name) via `useUserActivity`. **Caveat Q1:** that field is the *weekly cohort* tier and is `null` when the seam has no data; it is not guaranteed to equal `StudentXpProfile.CurrentTier`.

### Area 2 — Badge catalog
- `GET api/Admin/Gamification/Badges` → `BaseResponse<List<BadgeDefinitionDto>>` (includes inactive).
- `POST api/Admin/Gamification/Badges` body = `CreateBadgeDefinitionCommand` → `BaseResponse<int>` (new id; see Q3 — may return 0 pre-fix, so refetch rather than trust it).
- `PUT api/Admin/Gamification/Badges/{id}` body = `UpdateBadgeDefinitionBody` → envelope.
- `PATCH api/Admin/Gamification/Badges/{id}/active` body = `{ isActive: boolean }` → envelope.
- **`BadgeDefinitionDto`:** `{ id:int, code:string, name:string, description:string, iconKey:string, rarity:BadgeRarity, sortOrder:int, triggerType:BadgeTriggerType, threshold:int|null, rewardXp:int, isActive:bool }`.
- **Create body fields:** `code, name, description, iconKey, rarity, sortOrder, triggerType, threshold?, rewardXp`. **Update body fields:** same minus `code` (code immutable; route id targets the row).
- **Enums:** `BadgeRarity`: Common=1, Rare=2, Epic=3, Legendary=4. `BadgeTriggerType`: FirstLesson=1, StreakThreshold=2, LevelThreshold=3.
- **BE validation (mirror in form):** code NotEmpty ≤64; name NotEmpty ≤80; description NotEmpty ≤240; iconKey NotEmpty ≤128; rarity/triggerType in enum; rewardXp >0; sortOrder ≥0. (`threshold` is nullable — relevant for StreakThreshold/LevelThreshold triggers; FirstLesson typically null.)

### Area 3 — Mission catalog
- `GET api/Admin/Gamification/Missions` → `BaseResponse<List<MissionDefinitionDto>>` (includes inactive).
- `POST api/Admin/Gamification/Missions` body = `CreateMissionDefinitionCommand` → `BaseResponse<int>` (Q3).
- `PUT api/Admin/Gamification/Missions/{id}` body = `UpdateMissionDefinitionBody` → envelope.
- `PATCH api/Admin/Gamification/Missions/{id}/active` body = `{ isActive }` → envelope.
- **`MissionDefinitionDto`:** `{ id, code, iconKey, titleKey, cadence:MissionType, targetType:MissionTargetType, target:int, rewardXp:int, sortOrder:int, isActive:bool }`.
- **Create body:** `code, iconKey, titleKey, cadence, targetType, target, rewardXp, sortOrder`. **Update body:** same minus `code`.
- **Enums:** `MissionType` (cadence): **Daily=1, Weekly=2 ONLY** (no "weekly-challenge" value exists — see Q4; do not put a third option in the picker). `MissionTargetType`: CompleteLessons=1, CorrectAnswers=2, MaintainStreak=3.
- **BE validation:** code NotEmpty ≤40; iconKey NotEmpty ≤60; titleKey NotEmpty ≤80; cadence/targetType in enum; target >0; rewardXp >0; sortOrder ≥0. Note `titleKey` is an i18n **key** (not display text) — the BE stores keys; the FE form should label it as such.

### Area 4 — Timed events
- **List (separate controller):** `GET api/admin/timed-events` → `BaseResponse<IReadOnlyList<TimedEventListItemDto>>`, ordered StartUtc DESC, cap 200.
  - **`TimedEventListItemDto`:** `{ id:int, code:string, nameEn:string, nameAr:string, multiplier:decimal, startUtc:string(ISO), endUtc:string(ISO), isActive:bool, scope:string }` — note `scope` here is the **string name** ("AllXp"), and **description fields are NOT in the list DTO** (only on create/update bodies).
- `POST api/Admin/Gamification/TimedEvents` body = `CreateTimedEventCommand` → `BaseResponse<int>` (Q3).
- `PUT api/Admin/Gamification/TimedEvents/{id}` body = `UpdateTimedEventBody` → envelope.
- `POST api/Admin/Gamification/TimedEvents/{id}/activate` (no body) → envelope.
- `POST api/Admin/Gamification/TimedEvents/{id}/expire` (no body) → envelope.
- **Create body:** `code, nameEn, nameAr, descriptionEn?, descriptionAr?, startUtc, endUtc, multiplier, scope`. **Update body:** same minus `code`.
- **`TimedEventScope`:** AllXp=1, MissionXp=2, LeagueXp=3 (only AllXp is honored by the engine today; MissionXp/LeagueXp are forward-compat — surface them but the form copy can note they are AllXp-only effective).
- **BE validation:** code NotEmpty ≤64; nameEn/nameAr NotEmpty ≤128; description ≤512 when present; multiplier 1.0–5.0; startUtc strictly before endUtc; scope in enum.
- **Status badge derivation (FE):** Expired if `now > endUtc`; Active if `isActive && startUtc ≤ now ≤ endUtc`; Scheduled if `now < startUtc`. (The list DTO has no explicit status — derive client-side; the activate/expire buttons set the underlying `isActive`.) Times are UTC ISO strings — render with explicit timezone handling and `dir="ltr"`.

### Area 5 — Streak-freeze grant (child-affecting; Reason required)
- `POST api/Admin/Gamification/children/{childId}/streak-freeze` → `BaseResponse<bool>`
  - body: `{ count: int, reason: string, confirm: boolean }`
  - BE validator: `childId>0`, `count >0 && ≤ MaxFreezes(=2)`, `reason` NotEmpty ≤500, `confirm == true`.
- **No freeze-balance read endpoint exists** (Q2). `useUserActivity` exposes streak length but **not** `FreezeBalance`.

## Security / audit
- **All five surfaces are AdminOnly** at the BE; the FE guard (`useAdminGuard`) is a UX boundary only (sessionStorage tokens; middleware can't enforce server-side) — the real gate is the merged `[Authorize(AdminOnly)]`. The FE must still never render gamification pages for non-admins (guard → redirect) and must surface 403 gracefully if a token expires mid-session.
- **Child-data exposure:** league-tier override and streak-freeze grant target a **specific student** and read that student's activity (`useUserActivity`) — student PII (name + gamification stats) appears in those dialogs. Keep displayed data minimal (tier/streak only; no email needed in the override dialog). Audit `Details` are PII-safe on the BE (ids + values).
- **Abuse vectors the FE must bound (defense-in-depth, BE already validates):** freeze count clamped to 1..2 in the input; tier no-op disabled; Reason required + ≤500; confirm required. These mirror the BE validators so the user gets immediate feedback, but the BE remains authoritative.
- **`security-auditor` recommendation:** **YES, warranted** — this batch mutates student rewards/economy and exposes per-student data through the two child-affecting overrides. Run `security-auditor` on the FE batch (focus: guard correctness + redirect, no student PII leakage in the dialogs/console logs, Reason/confirm enforcement, 403 handling, no token in logs). Catalog/timed-event pages alone are platform-config and lower-risk, but the student overrides tip the whole batch into security-sensitive. Critical/High findings block the gate.

## Open questions / assumptions / risks
- **Q1 (real, design-blocking-ish) — Student picker + current-tier read for league/freeze.** The two child-affecting overrides need a `childId` and ideally show current state. There is **no gamification endpoint to read a single student's current tier or freeze balance**; the only admin read is `GET api/Admin/Users/{id}/activity` (`useUserActivity`), which gives `league.tier` (weekly cohort tier, may be `null`, not guaranteed == `CurrentTier`) and streak length but **not** `FreezeBalance`. **Recommendation:** launch both dialogs from the existing `users/[id]` student detail page (childId + activity already in hand). Decide with the lead/designer whether a standalone search-backed picker on the gamification hub is also wanted. **Assumption used in this brief:** entry from user-detail; current tier shown best-effort from activity with a "may differ from placement" note.
- **Q2 (real BE gap) — No streak-freeze balance read.** The grant dialog cannot show "current N freezes" because no endpoint exposes `FreezeBalance` to admins. **Recommendation:** ship the grant with balance shown as "not available" (do not block the story); flag to the lead whether a tiny BE read (`GET .../children/{childId}/streak-freeze` or extend `AdminActivitySummaryDto` with freeze balance) should be added later. Does not block the FE build.
- **Q3 (carryover defect) — create endpoints may return `Id = 0`.** HANDOFF follow-up #2 flags `CreateBadge/Mission/TimedEvent` handlers reading `entity.Id` before commit (possible 0). **FE mitigation (do regardless):** never navigate-by-returned-id or optimistically insert; always invalidate+refetch the list after create. Worth confirming the BE fix status with the lead, but the FE is safe either way.
- **Q4 — "weekly-challenge" cadence.** Story/task mention daily/weekly/weekly-challenge, but `MissionType` is **Daily/Weekly only**. Do **not** add a third cadence option. If product wants weekly-challenge it's a BE enum change (out of scope here) — flag to lead.
- **Q5 — Where league-tier override writes (mid-week vs next placement).** The BE writes `StudentXpProfile.CurrentTier` and (per backend brief Q-tier) possibly the active membership; the FE only displays tier and submits the new value, so this does not change FE work — but the "current tier" shown from activity may lag the override target. Note in copy that the override applies to the student's tier and is audited.
