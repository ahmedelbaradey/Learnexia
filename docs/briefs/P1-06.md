## Business context & value
- **Who benefits:** indirectly all users; directly the backend team. This is a pure technical enabler — it is the foundation every other backend epic builds on.
- **Value:** A working, RAG-capable datastore (pgvector) + a distributed cache (Redis) so sessions/token cache survive multiple instances, plus schema-per-module isolation that enforces the modular-monolith boundary at the DB level.
- **Success measure:** API boots, applies all module migrations against PostgreSQL, sessions/tokens persist in Redis across restarts, and a `vector` column can be created and round-tripped.

There is **no `ConnectionStrings:Redis` in appsettings.json** (only in the compose env), so local `dotnet run` has no Redis endpoint configured today.

8. **Catalog/Notifications migrations are not auto-applied at startup.** Only Identity's seeder runs `MigrateAsync`. ## Open questions / assumptions / risks
- **OQ-1 (RESOLVED, but confirm with lead):** Task file says "SQL Server → Npgsql switch needed." Reality: switch is already complete (see findings). **Assumption:** P1-06 is now a *verify + finish (Redis wiring + pgvector proof) + doc-correction* story, not a full migration. Confirm the lead agrees so we don't waste a batch re-doing a done migration.
- **OQ-2:** AC names six schemas (`identity, learning, assessment, gamification, analytics, curriculum`) but only `identity/catalog/notifications` exist. The naming diverges (`catalog`/`notifications` vs `learning`/`curriculum`/etc.). Should P1-06 (a) only verify the convention and defer the other schemas to their owning modules, or (b) pre-create empty schemas now? **Recommend (a)** — schemas are owned by their modules per the modular-monolith rule. Confirm the canonical schema name list / mapping (e.g. is `catalog` the same as the AC's `curriculum`?).
- **OQ-3:** Compose uses **PostgreSQL 17** (`pgvector/pgvector:pg17`); story/BRD say **16**. Is pg17 acceptable (recommend yes — pgvector + Npgsql 10 fully support it), or must we pin pg16?
- **OQ-4:** Only Identity auto-migrates at startup. Should Catalog/Notifications (and future modules) also `MigrateAsync` on boot to fully satisfy "API starts → migrations run successfully," or is migration applied out-of-band (CI/CD)? Affects AC-1's literal reading.
- **OQ-5:** Where should the pgvector proof live and should it persist? Options: (a) permanent groundwork in a future `curriculum` module (cleanest for RAG), (b) a sample column in `Catalog` (reference module), (c) a disposable demo migration reverted after verification. **Recommend (c)** for P1-06 (prove capability without committing a premature schema), with the real embedding table built in the RAG/curriculum story.
- **Risk — `Npgsql.EnableLegacyTimestampBehavior=true`** (`Program.cs:16`) is set because seed/audit stamp `DateTime.Now` (Local kind). This is a known tech-debt carryover from SQL Server; not in P1-06 scope but worth flagging to the lead as a follow-up (move to `DateTime.UtcNow`).
- **Risk — connection-string casing:** appsettings key is `Default`, DI reads `default`; works due to case-insensitive config but is fragile. Optional tidy-up.
