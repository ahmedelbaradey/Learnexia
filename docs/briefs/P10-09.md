# Pipeline Brief — P10-09 Failed payments & refunds (dunning + clawback)

> Phase 10 — Payment, Billing & Credits. **Dunning** (retry + notify → downgrade) for failed recurring charges, and **refunds** that reverse entitlement — pack refunds **claw back unspent** purchased credits; subscription refunds follow a stated policy. ## Business context & value

- **Who benefits:** the **business** (revenue + entitlement correctness — a parent shouldn't keep Premium after payment fails, nor keep credits they were refunded) and the **parent** (clear notification + retry window before losing access; fair clawback of only *unspent* credits).
- **Value:** closes the money-correctness loop. Failed renewals can't silently keep Premium; refunds can't leave granted credits behind. The hardest correctness property is **idempotent reversal** — a refund webhook delivered twice must claw back credits exactly once, and a clawback can never drive a balance negative beyond what's actually unspent.
- **Success measured by:** N failed retries → parent notified → downgrade to Free at cycle end (configurable grace); pack refund claws back **unspent** purchased credits only; subscription refund follows the stated policy; all reversals idempotent + reconciled.

---

## Acceptance criteria (testable)

1. A **failed recurring charge triggers a dunning flow**: a **retry schedule** + **parent notification**; after **N failures** (configurable) the plan **downgrades to Free at cycle end** (configurable **grace period**).
2. A **refund reverses entitlement**:
   - **Pack refund** → claws back **unspent** purchased credits (clamped to what remains — never negative; if the child already spent some/all of the pack, only the unspent remainder is clawed back, per the policy in OQ1).
   - **Subscription refund** → follows the stated policy (**no mid-cycle clawback of granted credits beyond policy**).
3. All refunds are **idempotent ledger entries** (`Refund` `CreditTransaction`) **linked to the original payment**; a replayed refund webhook reverses exactly once.
4. Provider **webhook events** (`charge.failed`, `refund.succeeded`) are processed **idempotently** and **reconciled** with our `Payment`/`Subscription`/ledger state.

## Affected modules & data

### Module — `Billing` (schema `billing`)
- Operates on `Payment`/`Subscription` (P10-06) + `CreditAccount`/`CreditTransaction` (P10-01). Clawback writes a negative-effect `Refund` ledger row against the target child's `PurchasedBalance`. **Atomic** via explicit transaction (no UoW, ADR 0001).
- **Parent notifications** for dunning go through the **existing Notifications module** via `Shared.Contracts` (an integration event the Notifications module consumes) — no cross-module FK, mirror how other modules raise notifications.

### New / reused entities + fields
- **Reuses** `Payment` (add/confirm `Status` values `Failed` / `Refunded`; a `RefundedPaymentId` link on refund rows or a separate `Refund` row linked to the original `Payment`).
- **Reuses** `Subscription` (dunning state: `Status = PastDue`/`Dunning`, `FailedAttemptCount`, `NextRetryAt`, `GraceEndsAt`; downgrade to Free at cycle end).
- **Reuses** `CreditTransaction` type `Refund` (P10-01) with `IdempotencyKey` = the provider refund event id, and a link to the original `Purchase` transaction / `Payment`.
- **Config (P10-11):** retry count N, retry schedule, grace period, subscription-refund policy parameters.

## Handoff → db-migration

- Extend `Subscription` with dunning fields (`FailedAttemptCount`, `NextRetryAt`, `GraceEndsAt`, dunning status). Extend `Payment` with refund linkage (`RefundedPaymentId` / refund status) if not present.
- Ensure `CreditTransaction.IdempotencyKey` (from P10-01) is **unique** so a replayed refund is a no-op. Index refund rows by original payment/transaction.
- Schema `billing`; no card columns; loose child id. No UoW — clawback (ledger row + balance decrement) is one explicit transaction.

## Handoff → backend-feature

- **Dunning:** a scheduled (**Hangfire**, per the infra decision) job processes `charge.failed` webhooks / non-terminal renewals: increment `FailedAttemptCount`, schedule the next retry, emit a **parent dunning notification** (`Shared.Contracts` → Notifications). After N failures, set the subscription to downgrade to **Free at cycle end** (respect grace). Idempotent per (subscription, cycle, attempt).
- **Refund (extend the P10-06 webhook handler):** on `refund.succeeded`:
  - **Pack refund** → compute **unspent** purchased credits for the pack (clamp ≥ 0), append a `Refund` `CreditTransaction` decrementing `PurchasedBalance` by the unspent amount, mark `Payment.Refunded`. **Idempotent** on the provider refund event id + `CreditTransaction.IdempotencyKey`.
  - **Subscription refund** → apply the stated policy (e.g. revoke Premium access; **do not** claw back already-granted monthly credits beyond policy). Mark `Payment.Refunded`.
- **Refund initiation:** is a refund triggered **only** by the provider (admin issues it in the provider dashboard → webhook), or also via an in-app admin action calling `IPaymentProvider.Refund`? **Confirm (OQ2).** Either way the **state change is driven by the idempotent webhook**, never the client.
- **Reconciliation:** the P10-06 reconcile job covers refunds/failures too — correct drift between provider + our state.
- **No new design pattern** — extend the existing webhook handler with event-type branches; if a richer dunning state machine / Strategy is contemplated, **ask the lead first** (CLAUDE.md rule 8).
- Envelope `BaseResponse<T>`/`Successed`; `ILoggerManager` (never log card/PII/secrets); commands auto-validated.

## Handoff → security-auditor (MANDATORY — Critical/High block)

- **Idempotent reversal:** a replayed `refund.succeeded` claws back **exactly once**; clawback never drives `PurchasedBalance` negative; "unspent only" is enforced server-side.
- **Webhook security:** signature verification (reuse P10-06), forged/replayed `charge.failed`/`refund.succeeded` rejected; webhook is the only trusted source for refund/downgrade state.
- **Authz:** if an in-app admin refund action exists, it's **admin-only** (behind the P7 console) + audited; parents/children can never trigger a refund or a downgrade-skip.
- **Policy enforcement:** subscription-refund clawback is bounded by the stated policy (no over-clawback of granted credits). Money-correctness invariants are the core audit target.

## Handoff → api-tester

- Cases: `charge.failed` webhook increments attempt + schedules retry + emits notification (idempotent); after N failures the subscription is set to downgrade to Free at cycle end (grace respected); **`refund.succeeded` for a pack** claws back **unspent** credits only (spend some first, then refund → only remainder clawed back; never negative); **duplicate refund webhook** does not double-claw; **subscription refund** revokes access per policy without over-clawing granted credits; forged/unsigned webhook rejected; `BaseResponse<T>`/`Successed`. Use the provider sandbox — no real card data.

## Open questions / assumptions / risks

1. **Clawback policy — needs LEAD confirmation (story Notes).** For a **partially-spent pack**: claw back only the **unspent remainder, clamped ≥ 0** (recommended/assumed). For a **subscription refund**: the policy on **already-granted monthly credits** (recommended: revoke Premium access but **do not** claw back granted credits beyond policy). **Block on lead.**
2. **Refund trigger:** provider-dashboard-only (→ webhook) vs in-app admin refund action (P7 console) calling `IPaymentProvider.Refund`. Confirm; affects whether an admin endpoint + authz is needed.
3. **Dunning parameters (N, retry schedule, grace):** config-driven via P10-11 — confirm the defaults with the lead.
4. **Recurring-renewal dependency:** dunning only makes sense if P10-06 implements true auto-renew; if the chosen provider can't auto-renew (see P10-06 OQ2), "failed recurring charge" becomes "renewal reminder ignored" and the dunning model shifts. **Coordinate with the P10-06 provider decision.**
5. **Notifications integration:** reuse the existing Notifications module via `Shared.Contracts` for parent dunning alerts — confirm the event contract.
6. **Negative-balance / over-spend race:** if a refund webhook arrives while the child is spending, the atomic transaction + clamp must hold. Flag the concurrency test for api-tester.
