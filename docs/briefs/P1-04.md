# Pipeline Brief — P1-04 (Backend) Link a parent to a child account

## Summary & traceability
- **Task (one line):** Introduce the `ParentStudent` parent↔child linkage in the Identity module, auto-create it on add-child (P1-03), expose a link-an-existing-child endpoint, and add a reusable family-scoped authorization primitive so a parent can read only their own children's data.
- **User story:** `user-stories/Phase-1-Foundation/P1-04-link-parent-to-child.md` (note: actual filename is `…link-parent-to-child.md`, not `…link-parent-child.md` referenced by the dispatch).
- **Task file:** `tasks/Backend/Phase-1-Foundation/P1-04-BE.md` (BE-1..BE-4). FE: `tasks/Frontend/student-app/Phase-1-Foundation/P1-04-FE.md`.
- **FR-IDs:** FR-ID-3 (parents link to one or more student accounts). Enables FR-PA-1/2 (Phase 5 reports) and P5-05 (per-child grade transition). Family scoping supports NFR-4.
- **BRD goal:** G4 (Parent visibility).
- **Phase/sprint/epic:** Phase 1 — Foundation (Week 1–2), Epic *Identity & Onboarding*. SP 3.
- **Wave model:** runs on `feat/P1-04-link-parent-child` off `feat/wave-2`, in parallel with **P1-02** (same Identity module). P1-03 (add-children) and P1-05 (RBAC family-scope) both depend on this story.
- **Override note:** Parent-driven onboarding — parents add children; students do not self-register. Primary linkage path is the add-child step (P1-03), not a student-initiated invite. No teacher role.

## Business context & value
- **Who benefits:** Parents (see/manage each child's progress + weekly reports), and indirectly students (correct data isolation) and the platform (the core access-control primitive for child data).
- **Value:** Establishes the family graph that every parent-facing feature (Phase 5 reports, grade transition, per-child dashboards) reads from, and the authorization boundary that prevents one family from seeing another's child data (IDOR protection on the most sensitive data class — minors).
- **Success measures:** Linkage auto-created on every add-child; a parent can list/access only their linked children; cross-family access is denied (403); link-to-non-existent-child returns a clear error; many-to-many supported (a child may be linked by more than one parent).

## Acceptance criteria (testable)
1. **AC-1 — Auto-link on add-child:** When a parent adds a child during onboarding (P1-03's Add-Child), a `ParentStudent(ParentId, StudentId)` row is created in the same operation. (BE-2, consumed by P1-03-BE-4.)
2. **AC-2 — Link an existing child:** An authenticated parent can link to an additional already-provisioned child via the link endpoint; the response returns the linked child summary.
3. **AC-3 — Family-scoped read:** A parent linked to child X can access child X's data and is denied (403) for any child not linked to them. A student is scoped to self only (handler reused by P1-05-BE-3).
4. **AC-4 — Many-to-many:** A parent may be linked to multiple children; a child may be linked by more than one parent. The composite key `(ParentId, StudentId)` prevents duplicate links.
5. **AC-5 — Non-existent child → clear error:** Linking to a non-existent child returns a clear, non-leaking error (recommend 404/422; see open question Q3). Linking to a user that is not a Student should also be rejected.
6. **AC-6 — Idempotency / no double-link:** Re-linking an already-linked (parent, child) pair does not create a duplicate and does not error opaquely (recommend treat as success/no-op or explicit "already linked").
7. **AC-7 — Guard against arbitrary linking:** A parent cannot link a child that belongs to (was created by) a different family in a way that grants visibility into another family's existing child (see open question Q2 — link-by-email semantics). Only authenticated parents may call the link endpoint.

## Affected modules & data
- **Module:** Identity only. No cross-module references; `Parent` and `Student` are both `User` rows in the `identity` schema, so the linkage is intra-module (no cross-module FK — complies with module-isolation rule).
- **New entities/tables:**
  - `ParentStudent` (new) — table in `identity` schema. Composite PK `(ParentId, StudentId)`, both FK → `AspNetUsers` (`User.Id`, `int`). Optional audit columns (`CreatedAt`, `CreatedBy`) to match the codebase convention. `DeleteBehavior.Restrict` is the DbContext default (see `IdentityModuleDbContext.OnModelCreating`) — confirm desired delete behavior for unlinking.
- **Existing entities touched:**
  - `User` (`…Identity.Domain/Entities/User.cs`) — currently has no parent/child navigation. Optionally add `ICollection<ParentStudent>` navigations (LinksAsParent / LinksAsStudent). Adding navigations is optional; the entity + config can stand alone.
  - `Roles` enum already contains `Parent` and `Student` (`…Domain/Constants/Roles.cs`) — no new role needed.
- **Current state confirmed:** No parent↔child relationship exists today. No `ParentStudent` type, no `FamilyScope*`, no `IAuthorizationHandler`/resource-based authorization anywhere in the backend. Authorization today is role policies (`AdminOnly`) + permission-claim policies (`Catalog.*` only). `Claims.GenerateModules()` returns only `"Catalog"`.

## Handoff → db-migration
- **New entity:** `ParentStudent` in `Learnexia.Modules.Identity.Domain/Entities`.
  - Fields: `int ParentId`, `int StudentId` (composite PK); recommended `DateTime CreatedAt` (default `now()`), `int? CreatedBy`.
  - **EF config:** add `ParentStudentConfig : IEntityTypeConfiguration<ParentStudent>` under `…Infrastructure/Persistence/Configurations`. It is auto-discovered — `OnModelCreating` calls `ApplyConfigurationsFromAssembly`, so **no DbContext edit is required** beyond optionally exposing a `DbSet<ParentStudent>`. Configure composite key `HasKey(x => new { x.ParentId, x.StudentId })`, two FKs to `User` with explicit `WithMany`, and `OnDelete(DeleteBehavior.Restrict)` (the global default; choose `Cascade`/`Restrict` deliberately per Q4).
  - Add a `DbSet<ParentStudent>` to `IdentityModuleDbContext` (this file is shared — see merge-overlap note).
- **Migration:** new EF migration in `…Identity.Infrastructure/Migrations`, target schema `identity`, provider **Npgsql** (`UseNpgsql`). Table name e.g. `ParentStudents`. Include an index on `StudentId` (reverse lookup "who are this child's parents"). Composite PK gives the `(ParentId, StudentId)` uniqueness for AC-4/AC-6.
- **Generate with the Identity design-time factory** (`IdentityModuleDbContextFactory`). Migrations history table is `__EFMigrationsHistory` in the `identity` schema (see Identity DI `AddDbContext`).
- **Constraint:** P1-06 is already complete (Npgsql + per-module schemas + migrations exist) — this is an additive migration on top of `20260520084838_InitialIdentity`.

## Handoff → backend-feature
- **Auto-link service (BE-2):** a small linkage service/method (e.g. `ILinkParentStudentService` or a method on the Identity service manager) that creates a `ParentStudent` row given `(parentId, studentId)`, idempotent (no-op if exists). Invoked by P1-03's `AddChildCommandHandler` (P1-03-BE-4). Keep it callable in the same flow as child creation; note `AddUser`/Identity persists via ASP.NET Identity `CreateAsync` (commits immediately) rather than UnitOfWork — sequence the link write after the child user exists.
- **Link-existing-child command/endpoint (BE-4):**
  - Command: `LinkChildCommand : ICommand<BaseResponse<...>>` + `LinkChildCommandHandler : BaseResponseHandler`. Return `BaseResponse<T>` (success flag spelled `Successed`), controller uses `NewResult(...)`.
  - **Endpoint (assumption):** `POST /api/Users/UserManagement/Link-Child`. **CAUTION:** the existing `UserManagementController` is class-level `[Authorize(Policy = AuthorizationPolicies.AdminOnly)]` — a parent linking their own child is **not** admin. Do **not** place this action under the AdminOnly gate. Recommend a **new parent-facing controller** (e.g. `ParentController` / `FamilyController`, route `api/Users/...`) gated to the `Parent` role, OR an action-level `[Authorize(Roles = Parent)]` override on a dedicated action. Flag to planner/security-auditor (Q5).
  - **Input contract (from FE task):** link-existing identifies the child by **child email** (`LinkChildForm` uses child email). So `LinkChildCommand { string ChildEmail }`, resolve to a Student user, then create the link for the **current parent** (`ICurrentUserService.UserId`). Returns the linked child summary (id, name, grade).
  - **Validation (FluentValidation, runs for `ICommand<>`):** child email present/well-formed; child must exist and hold the `Student` role (else AC-5 error); current user must be a parent; reject self-link / linking a non-student. Decide the 404 vs 422 vs 400 shape (Q3) and avoid leaking whether an email exists in another family (Q2/security).
  - **Current-user source:** `CurrentUserService.UserId` reads the `Id` claim; `Roles` reads `ClaimTypes.Role`. Reuse it; do not trust a `parentId` from the request body.
- **Family-scope authorization (BE-3) — reusable, consumed by P1-05-BE-3:**
  - Greenfield. Recommend ASP.NET Core **resource-based authorization**: a `FamilyScopeRequirement : IAuthorizationRequirement` + `FamilyScopeAuthorizationHandler : AuthorizationHandler<FamilyScopeRequirement, TResource>` where the resource carries a target `studentId`. Handler succeeds when: caller is Admin/SuperAdmin (full), OR caller is the Student themself (`UserId == studentId`), OR caller is a Parent with a `ParentStudent` row for `(UserId, studentId)`.
  - Needs DB access to check linkage → handler lives in **Identity Infrastructure** (can inject `IdentityModuleDbContext` or the linkage service). Register it as `IAuthorizationHandler` in Identity Infrastructure DI, and optionally add a named policy. **This handler registration is the file most likely to collide with P1-02 — see merge note.**
  - Keep the handler API generic enough for P1-05 to call across modules via `IAuthorizationService.AuthorizeAsync(user, resource, requirement)`; the cross-module question (how learning/assessment modules invoke it without referencing Identity) is **Q6** for the planner — likely a `Shared.Contracts` seam (e.g. `IFamilyScopeChecker`).

## Open questions / assumptions / risks
- **Q1 (assumption):** Endpoint path `POST /api/Users/UserManagement/Link-Child` — confirm. Recommend a separate parent-scoped controller instead (see Q5).
- **Q2 (security, important):** Link-by-email semantics. If any parent can link by typing any child's email, that is a privacy/IDOR vector (one parent attaches to another family's child, or enumerates valid child emails). Need the product rule: link only children the parent **created**, or a child-side confirmation/consent step, or admin-mediated linking. **Flag for the user.**
- **Q3:** Error contract for non-existent / non-student child — 404 vs 422 vs 400, and whether to use a generic "not found / cannot link" message to avoid email enumeration.
- **Q4:** Unlink behavior + delete behavior for `ParentStudent` when a parent or child user is deleted (Cascade vs Restrict). Is unlinking in scope for P1-04? (Story does not mention it — assume out of scope, Restrict.)
- **Q5:** The link endpoint must NOT inherit `UserManagementController`'s class-level `AdminOnly` policy. Confirm parent-role gating approach.
- **Q6 (architecture):** How do other modules (P1-05, Phase 5) invoke family-scope without referencing Identity projects? Likely a `Shared.Contracts` interface (`IFamilyScopeChecker`) implemented in Identity Infrastructure. Planner to decide whether to introduce the seam now (in this story) or in P1-05.
- **Q7:** Is the "list my linked children" endpoint owned by P1-04, P1-03, or P1-09? FE-1 needs it; BE task table does not explicitly list it.
- **Q8 (tracked, out of scope):** COPPA-style parental consent for under-13 (BRD §10) — story Notes explicitly defer this. Do not implement here; surface as a separate item.
- **Risk — merge overlap with P1-02 (same Identity module, parallel branch):** Files this story is expected to touch that P1-02 may also touch:
  - `…Identity.Infrastructure/DependencyInjection.cs` — **highest risk.** This story adds `IAuthorizationHandler` (and possibly linkage-service) registration here; P1-02 may touch it for Redis/`IDistributedCache` session wiring (P1-02-BE-2). Coordinate / serialize edits.
  - `…Identity.Infrastructure/Persistence/IdentityModuleDbContext.cs` — this story adds a `DbSet<ParentStudent>`; lower P1-02 risk but watch.
  - `Directory.Packages.props` / `Program.cs` / `Claims.cs` — not expected to be touched by this story (no new package; policy registration stays in Identity DI). If a named policy is added globally, keep it in Identity DI's `AddAuthorization` to avoid Host/Program.cs contention.
  - New files (`ParentStudent.cs`, `ParentStudentConfig.cs`, the migration, `LinkChildCommand(Handler)`, `FamilyScopeRequirement`/`Handler`, controller) are conflict-free.

## Recommended pipeline order (first cut — planner finalizes)
1. **db-migration** — `ParentStudent` entity + EF config + Npgsql migration (BE-1). Foundational; everything else depends on the table.
2. **backend-feature** (after migration) — can run as two parallel-ish sub-batches that both depend only on the entity:
   - Linkage service + auto-link hook (BE-2) and Link-Child command/endpoint + validation (BE-4).

4. **api-tester** — integration tests for the Link-Child endpoint (happy path, non-existent child, non-student target, duplicate/idempotent link, cross-family denial 403, unauthenticated 401, non-parent 403). Pattern: mirror `tests/Learnexia.IntegrationTests/P1_01_RegisterParent_Tests.cs` (WebAppFactory + seed; dual camelCase/PascalCase JSON paths).
5. **reviewer** — gate against the AC list above + CONVENTIONS (BaseResponse/`Successed`, module isolation, ILoggerManager, validation on commands only).
6. **committer** — only after reviewer PASS, on `feat/P1-04-link-parent-child`.
