## Business context & value
- **Who benefits:** the **student** primarily — clear visual distinction between "any unit lesson" and "the boss at the end" (the kid-UI wireframes treat bosses as a separate icon class, a celebration moment, the "you fought through the unit, now prove it" gate). The **frontend** (P2-03-FE) — needs an `isBoss` flag delivered on the same payload it already consumes; without it, FE would have to either invent a heuristic ("last lesson in `SequenceOrder` is the boss") or make a separate query. The **Learning Path Engine** — no change; bosses are styling/semantics, not progression. **Parents** indirectly — Phase-5 dashboards can summarise "Sara has beaten 3/5 bosses in Math G3" once the flag exists.
- **Why now / why this is the closing story of Phase-2 backend:** P2-04 delivered the deterministic engine. P2-05 delivered the lesson runtime (explanation + visual + quick-check). P2-09 delivered the home dashboard. The remaining four-state contract from `FR-LR-2` ("locked, unlocked, completed, **boss**") is the missing piece — without the boss flag the wire contract is 3/4 of the spec. P2-03 ships that fourth piece and closes Phase-2 BE.
- **Why a flag on `Lesson` (not a new entity, not a new enum value):** bosses are **end-of-unit lessons** (`Lesson` row, `SequenceOrder = max(Unit.Lessons.SequenceOrder)`), not a separate kind of artefact. The story's "fourth node state" phrasing is a kid-UI rendering category, not a database state — semantically a boss can be `Locked`, `Available`, or `Completed` orthogonally. A non-nullable `bool IsBoss` column with default `false` is the minimum schema change.
- **Why orthogonal to `NodeState` (not `Boss=3` on the enum):** a boss lesson the student hasn't reached yet is **Locked AND a boss**; one they've finished is **Completed AND a boss**. Folding boss into `NodeState` would force the FE to track "is this state-3 a locked-boss or a completed-boss?" — exactly the modelling failure the orthogonal flag avoids.
- **Why on `Lesson` (not `Skill`):** the story text reads "end-of-unit challenge" (units own lessons, not skills). The kid-UI mockups place the boss icon at the foot of a unit's lesson list, not on a skill node. Skill-level bosses are a P3-08 / P3-10 concept (adaptive challenge generation, spaced repetition for failed bosses) — out of scope here. **See Q1 for the lead's call.**
- **Success measure (testable):** (a) every seeded "last lesson of each unit" row carries `IsBoss = true`; (b) every other lesson row carries `IsBoss = false`; (c) the four read DTOs (`LessonInUnitDto`, `SingleLessonResponse`, `ContinueTargetDto`, and **optionally** `SkillNodeDto.HasBoss`) surface the flag; (d) the migration is reversible; (e) the seeder re-run flips zero rows the second time (idempotent); (f) `LearningPathEngine.ComputeStates(...)` and `NodeState` enum are untouched (the engine doesn't care about boss-ness).

## Open questions for the lead — recommended defaults

> Default recommendation summary: **"approve all defaults"** ships the smallest possible coherent change. **Q1 (boss flag on Lesson vs Skill) is the one genuine semantic fork.** Q3 is a smaller fork (seeder strategy). Everything else is a "ship as drafted unless the lead disagrees."

### Q1 — Boss flag location: `Lesson.IsBoss` or `Skill.IsBoss`? — **the one genuine fork**
**Recommended default:** **`Lesson.IsBoss`** (non-nullable bool, default `false`).
**Why:**
- Story text reads "end-of-unit challenge." Units own lessons, not skills.
- Kid-UI wireframes place the boss icon on the lesson card at the foot of a unit, not on a skill node.
- The same skill is often taught across multiple units / grades; tagging the *skill* as boss would mis-tag every lesson that touches that skill.
- Skill-level bosses are explicitly a Phase-3 concept (P3-08 adaptive challenges + P3-10 spaced repetition for failed bosses).
- The seeder rule "mark the highest-`SequenceOrder` lesson per `Unit`" maps trivially to a `Lesson` column.
**Alternative (rejected):** `Skill.IsBoss` — would require a seeder to pick "one boss skill per Concept" which has no clean natural rule and would mis-tag skills that span units. **Do not recommend.**
**Decision needed:** **lead to confirm Lesson over Skill**, or override.

### Q2 — Schema shape
**Recommended default:** non-nullable `bool IsBoss` column with `defaultValue: false` at the migration layer; `.IsRequired()` at the EF-config layer. Migration name: `AddLessonIsBoss`.
**Why:** matches the `IsLocked` precedent on `Lesson` exactly; clean schema; backfills the 162 existing rows to `false` deterministically, so the seeder's mark pass produces a known 66-row delta on first run.
**Alternative (rejected):** nullable `bool?` — wastes a tri-state where two states (true / false) are enough; introduces a "did the curriculum author skip this row?" ambiguity that adds no value.

### Q3 — Seeder strategy: which lessons get marked as bosses, and how is it kept idempotent?
**Recommended default — "mark the highest-`SequenceOrder` lesson of each Unit as boss":**
1. After `EnsureLessonAsync(...)` has run for every lesson in a unit, add a new `MarkBossLessonsAsync(LearningDbContext, ILoggerManager)` step in `SeedAsync` (called once at the end, after `SeedDemoLessonContentAsync`).
2. The step loads every `Unit` with `.Include(u => u.Lessons)` (AsNoTracking — read first), groups lessons by `UnitId`, picks `lessons.OrderByDescending(l => l.SequenceOrder).First()` per unit, and marks it as boss.
3. **Idempotency:** only updates rows where the current `IsBoss` value differs from the desired value — for the recommended rule the "last per unit" set is deterministic from `SequenceOrder`, so on a second run zero rows change. Implementation: fetch the lessons tracked, set `IsBoss = true` only when currently `false`; commit only when `db.ChangeTracker.HasChanges()`.
4. Log: `"P2-03 seed: marked N lesson(s) as boss; M already marked."`
**Why:** matches the "end-of-unit challenge" semantics literally; deterministic; idempotent without natural-key acrobatics.
**Alternative A (rejected):** Hard-code a list of boss lesson names (similar to `SeedDemoLessonContentAsync`'s explicit array). Brittle — the seeded lesson names already include grade suffixes (`"Place Value: Tens and Hundreds (G1)"`), so the list would be 66 entries long and would need an update every time the curriculum changes.
**Alternative B (rejected):** Mark every "Hard"-difficulty lesson as boss. Doesn't match the unit-end semantics and would over-mark.
**Decision needed:** lead to confirm "highest `SequenceOrder` per Unit" rule, or override.

### Q4 — `NodeState` enum: add `Boss=3`?
**Recommended default:** **NO.** Keep `NodeState` at 3 values (`Locked=0`, `Available=1`, `Completed=2`). Boss is **orthogonal** — surface as a separate `bool IsBoss` field on the lesson-bearing DTOs.
**Why:** a boss lesson the student hasn't reached is **Locked AND a boss**; one they've finished is **Completed AND a boss**. Folding boss into `NodeState` would force the FE to track "is this state-3 a locked-boss or a completed-boss?" — semantically broken.
**Alternative (rejected):** add `Boss=3` and treat it as "Available AND boss" (i.e. the kid-UI's "boss" icon also implies the lesson is unlocked). Conflates two concerns; would force engine changes (the engine derives Locked/Available/Completed; it has no boss data). **Do not recommend.**

## Risks & assumptions
- **Most of the named BE work is already shipped via P2-04.** This is a feature, not a risk — the brief reflects the real scope (BE-3 only). Downstream agents should not waste cycles "re-implementing" BE-1 / BE-2.

- **Migration ordering on existing dev DBs.** Devs with an already-migrated database will pick up `AddLessonIsBoss`; the column defaults to `false`, so all rows are non-boss until the seeder's mark-step runs on next startup. Document this in HANDOFF.md under "load-bearing config" — *"P2-03 dev DBs need a startup after migrating to pick up boss markers."*
- **No design pattern introduced.** Plain entity property + seeder loop + DTO additions. CLAUDE.md rule 8 respected (no Strategy/Factory/Decorator — just data).
- **No cross-module change.** Learning module only. Module isolation rule 1 respected.
- **No new endpoints.** Pure extension of existing read DTOs. No controller changes (controllers don't change shape when their handlers add a field).
- **No new auth / security surface.** `IsBoss` is curriculum-public data, not student-private. No PII concern; no IDOR vector. Security-auditor batch can be skipped — reviewer absorbs the checks.
- **No engine cost change.** `LearningPathEngine` is untouched. Per-request DB work increases by **zero** (the `Lesson.IsBoss` column rides along on the existing `Lesson` queries).
- **`SkillNodeDto.LessonIds` ordering today is `sk.Lessons.Select(l => l.Id)`** — not explicitly ordered. If a future story exposes "first boss in skill" semantics it will need explicit `OrderBy(SequenceOrder)`. Not a P2-03 concern.
