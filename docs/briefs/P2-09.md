## Business context & value
- **Who benefits:** the **student** — opens the app → sees XP, streak, and one obvious "Continue" button → taps it → lands in the next lesson the engine says is unlocked. This is the Phase-2 closing surface that ties together the previously-built skill tree (P2-02), unlock engine (P2-04), and attempt loop (P2-06/P2-07/P2-08). The **parent** (later) and **content/admin** (later) consume the same engine output transitively.
- **Why this matters now:** without this endpoint there's no FE-side "home" — the student would have to navigate to a subject, then to a unit, then to a lesson to start. Phase 2 ships demoable end-to-end with this story. The XP/streak/mission/league widgets exist *as a contract* in this story so the FE doesn't need a breaking response-shape change in Phase 4 — only the backend population changes.
- **Why placeholders, not "Coming soon" hard-codes:** Phase 4 builds against the established contract. If P2-09 returns `xp: 0`, `streak: 0`, `dailyMission: null`, `leaguePreview: null` now, then P4-02 only has to flip `xp` from "always 0" to "read from `XpLedger.SumForStudent`" — no DTO change, no FE refactor, no api-client regen.
- **Success measure:** authenticated student gets `200` with a populated `continue` for any seeded student who has attempts; gets `continue: null` for a brand-new student with zero attempts and no `Available` lessons in any subject; gets `xp: 0`, `streak: 0`, `dailyMission: null`, `leaguePreview: null` consistently in Phase 2; gets `401` when unauthenticated; tapping the returned `continue.lessonId` resolves to an `Available` lesson in the same student's `Subjects/{id}/SkillTree` response (consistency invariant).

## Open questions for the lead — recommended defaults

> Default recommendation: **"approve all defaults"** ships a coherent v1; **Q3** is the one genuine fork.

### Q1 — Endpoint signature
**Recommended default:** `GET /api/Learning/Dashboard`, **no route / query `studentId` param** — the student is read from `_currentUser.UserId` (JWT). IDOR-proof by construction (mirror P2-08's per-student endpoints).
**Why:** the dashboard is *always* "my dashboard"; a parent dashboard is a different surface (Phase 5). No future-proofing the URL for a non-existent role unlocks no value today.

### Q2 — Response shape (the `DashboardDto` contract)
**Recommended default:**

    int Xp,                              // 0 in Phase 2 (TODO P4-02)
    int Streak,                          // 0 in Phase 2 (TODO P4-03)
    DailyMissionDto? DailyMission,       // null in Phase 2 (TODO P4-06)
    LeaguePreviewDto? LeaguePreview,     // null in Phase 2 (TODO P4-07)

**Why:** nullable typed shells let Phase 4 populate without a contract change. `NodeState` reused from the existing enum keeps DTO surface tight. `Xp`/`Streak` are `int` (not nullable) because their Phase-2 zero-state is meaningful, not "unknown."
**Alternative if rejected:** add an aggregated `RecentActivity` record (last attempt summary) — explicitly **descoped** here; can land in a small follow-up once FE asks for it.

### Q3 — How to resolve the student's "current subject" for the Continue target (THE ONE FORK)
**Recommended default — Option A (most-recent-activity, with cross-subject fallback):**
1. Read the student's most recent `Attempt` (any status) ordered by `StartedAt` desc.
2. Resolve its `LessonId → Lesson.Unit.SubjectId`.
3. Run `LearningPathEngine` once for that subject.
4. Pick the lowest-`SequenceOrder` lesson where `NodeState == Available`.
5. **If none found** (the active subject is fully Completed, or the student has zero attempts):
   - Iterate the 4 subjects of the student's grade-1 (default fallback grade — see Q3.bis) by `Subject.Id` order, run the engine for each in turn, take the first Available lesson found.
6. **If still none found**, return `Continue = null`.

**Why:**
- Matches user intent — "where I left off" feels right for an at-home flow.
- Single engine call in the common case (worst case 4 calls on the rare "new student" or "fully-completed" branch).
- Doesn't require a Grade JWT claim (deferred to P6-06).
- Deterministic given inputs — easy to test.

**Alternative B (deterministic grade-Math):** Pick the student's grade-level Math subject. **Rejected** — requires resolving the student's grade which has no JWT claim today; brittle until P6-06.

**Alternative C (all-subjects aggregate):** Iterate all subjects and pick the "best" Continue by some priority (least-recent? closest-to-mastery?). **Rejected for Phase 2** — over-engineered; engine cost grows ×N subjects per request.

**Q3.bis — fallback grade when no attempts exist:** Default **Grade 1** (first row in `Grades` table — easy to demo with the seeded data). If that's wrong, alternative is "iterate every grade, pick the first with an Available lesson" — slightly more expensive but more correct for a Grade-3 student who's never touched the app.

**Decision needed:** lead to confirm Option A + Grade-1 fallback, or pick differently.

### Q4 — `LearningPathEngine` call cost
**Recommended default:** **at most one engine call per request** in the common case. Worst case (new student, no activity): up to 4 engine calls (iterating grade-1 subjects). Each engine call runs 5 AsNoTracking queries. **No caching** in Phase 2.
**Why:** Phase-2 traffic is demo-scale; even the worst case is ~20 simple queries. Caching the engine output per `(studentId, subjectId)` with a short TTL belongs in Phase 6 (P6-06 perf ticket) — flag it but don't build it.
**Alternative if rejected:** pre-aggregate via a new `GetDashboardSnapshot(studentId)` materialized view — premature optimization; reject.

### Q5 — XP / streak source in Phase 2
**Recommended default:** return **`Xp = 0`, `Streak = 0`** with `// TODO P4-02` / `// TODO P4-03` comments in the handler. FE renders zero-state ("0 XP", "0-day streak") — kid-friendly "fresh start."
**Why:** there are no XP / Streak entities, services, or events that write data on `main`. Synthesizing values from `Attempts` (e.g., "completed attempts × 10") is hacky, hides the Phase-4 hole, and breaks once P4-02 lands real ledger data.
**Alternative if rejected:** compute a synthetic XP = `count(Completed attempts) * 50` so demos look non-zero. Explicitly **NOT recommended** — sets a Phase-4 migration trap (the synthetic and real values won't line up).

### Q6 — Daily mission / league placeholders
**Recommended default:** return **`null`** for both `DailyMission` and `LeaguePreview`. FE conditionally renders a "Coming in Phase 4" badge or hides the widgets.
**Why:** nullable typed properties keep the JSON contract clean (`"dailyMission": null` is unambiguous). A "ComingSoon" shell adds a magic string the FE has to branch on — same UX, more coupling.
**Alternative if rejected:** return placeholder shells with `Status: "ComingSoon"`. Adds FE branching with no benefit.

### Q7 — Authorization
**Recommended default:** `[Authorize]` on the `DashboardController.Get` action (no role restriction). Mirrors `StudentsController.GetAttempts`.
**Why:** in Phase 2 the JWT-derived `_currentUser.UserId` IS the student account (parent-driven onboarding produces child accounts in the Student role). A parent dashboard is a distinct Phase-5 surface; a `Roles="Student"` lockdown here would only need to be loosened later. **No** `RoleManager` dependency — the `[Authorize]` (auth required, role-agnostic) is sufficient.
**Alternative if rejected:** `[Authorize(Roles="Student")]` — slightly tighter but explicitly forbids a future parent / admin from calling. Defer that decision.

### Q8 — Empty state
**Recommended default:** if the student has zero `Attempt` rows AND zero subjects with any `Available` lesson, return `200` with `{xp:0, streak:0, dailyMission:null, leaguePreview:null, continue:null}`. **No 404, no 500.**
**Why:** the dashboard is a read-aggregation — emptiness is a valid state ("you're new — pick something"). FE handles `continue == null` by showing a "browse subjects" CTA.

### Q9 — Performance / caching
**Recommended default:** **no caching in Phase 2.** Document the cost (~5–20 DB queries per request) and flag a Phase-6 performance follow-up (Redis cache of engine output per `(studentId, subjectId)`, short TTL, invalidated on `LessonCompletedIntegrationEvent`).
**Why:** demo-scale traffic; premature optimization without a measured baseline.

### Q10 — Controller location & route
**Recommended default:** brand-new `DashboardController` at `Learning.Api/Controllers/DashboardController.cs`. Route `[Route("api/Learning/[controller]")]`. Single action `[HttpGet] [Authorize] async Task<IActionResult> Get()` — parameterless from the caller's POV (handler reads `_currentUser.UserId`). Inherit `AppControllerBase`.
**Why:** mirrors `StudentsController.cs` (P2-08) exactly. Plural controller name (`Dashboards`) is **rejected** — there's only one dashboard per user; singular reads better in the URL (`/Dashboard` not `/Dashboards`). Per CONVENTIONS the controller class name follows the route segment.

### Q11 — Repository extensions
**Recommended default with Q3 = Option A:** add **one** thin helper to `ILearningRepository`:

If null and fallback subjects remain, retry per Q3 step 5.
- **Step 5 — project to `ContinueTargetDto`:** fetch the `Lesson` (with `Unit.Subject` loaded — single `Include` is fine, the engine already pre-fetched lessons but didn't include Unit) and project the IDs + names.
- **Step 6 — assemble `DashboardDto`:** `Xp=0`, `Streak=0`, `DailyMission=null`, `LeaguePreview=null`, `Continue=<resolved or null>`.
- **Step 7 — wrap + return:** `Success(dto)`. On exception: `_logger.LogError(ex, "Error in GetDashboardQuery")` then `ServerError<DashboardDto>()` — **do NOT echo `ex.Message`** to the client (rule from P2-08 security audit).
