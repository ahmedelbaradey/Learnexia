# Pipeline Brief — P9-02: Grant monthly energy per plan (scheduled grant + expiry)

> **Phase 9 credit economy — the supply side.** A Hangfire scheduled job grants each active child their plan's monthly energy allotment into `GrantedBalance`, stamps it with a cycle expiry, and expires any unspent granted credits at rollover (`PurchasedBalance` untouched). **Hard-depends on P9-01** (the `CreditAccount` + `ApplyGrant`/`Expire` primitives + idempotency) and on **P9-05** (the subscription/plan is the source of the allotment) and **P9-11** (the allotment amounts are admin-config). Read `docs/briefs/P9-01.md` and `docs/briefs/P9-11.md` alongside this.

## Summary & traceability

- **Task (1 line):** A **Hangfire recurring job** grants each active child their plan's **monthly energy allotment** (config-driven: Free = 100, Premium = 5000) into `GrantedBalance` on the billing-cycle date, stamps the granted pool with an **expiry = end of the current cycle**, and at cycle rollover writes an **`Expire`** transaction zeroing any unspent `GrantedBalance` while leaving `PurchasedBalance` untouched — **idempotently** (re-running for the same child+cycle never double-grants) and respecting **mid-cycle plan changes (next grant, not current)**.

## Business context & value

- **Who benefits:** the **parent** (their plan automatically funds each child every cycle — no manual top-up, the core value proposition of a subscription) and the **child** (energy is just there; AI help never silently runs dry mid-month for a paying family). The **business** benefits from the perishable-grant model: unused granted energy expires, which caps liability and nudges engagement (use-it-or-lose-it).
- **Granted-expire vs Purchased-persist (the central rule):** granted energy is a **monthly entitlement** that resets — it must expire at cycle rollover or a dormant child would accumulate an unbounded balance and the "monthly plan" stops meaning anything. Purchased energy is **paid-for property** — it never expires (a parent who bought a pack keeps it across cycles). This asymmetry is the heart of P9-02 and must be enforced exactly: grant writes only to Granted; expire zeroes only Granted; Purchased is never touched by this job.
- **Why a scheduled job (Hangfire):** grants are time-driven (cycle date), not request-driven — no user action triggers them. Hangfire already hosts every recurring sweep in the system (`StreakSweepJob`, `LeagueRolloverJob`, `MissionRolloverJob`) with the exact idempotent-re-run + per-row fail-soft pattern this needs. **Reuse that pattern; do not invent a new scheduler.**
- **Success measure (from AC):** (1) each active child gets their plan allotment into Granted on the cycle date; (2) the granted pool carries `GrantExpiresAtUtc = end of cycle`; (3) at rollover unspent Granted → `Expire` row, Purchased untouched; (4) re-running for the same child+cycle is a no-op; (5) a mid-cycle plan change affects the **next** grant, not the current one (proration is OQ-2).

## Current-state findings (reality in code)

1. **Hangfire recurring-job pattern is established and directly reusable** — `Gamification.Infrastructure/Jobs/StreakSweepJob.cs`: `[DisableConcurrentExecution(timeoutInSeconds:…)]`, `IServiceScopeFactory.CreateAsyncScope()` per run (Hangfire worker has no request scope), `ISystemClock` for time, `IOptions<…>` for config, **explicitly documented idempotent re-run** ("running twice — finds 0 rows"), per-row try/catch fail-soft. Jobs are registered Transient in `Add…Infrastructure` and the recurring schedule is wired in `…Module.InitializeAsync`. **Mirror this exactly** — the grant job is a `BillingGrantJob` of the same shape.
2. **Cron-scheduled monthly cadence** is supported (existing jobs use cron like `"5 0 * * *"`, `"15 0 * * 1"`). A monthly grant uses a monthly cron or a daily job that checks each child's cycle date (OQ-3 — fixed monthly cron vs per-child anniversary).
3. **P9-01 supplies the write primitives** — `CreditAccount.ApplyGrant` / `Expire` + the idempotency-key unique constraint. P9-02 **must not** mutate balances directly; it calls those primitives so balance + ledger stay coupled.
4. **No subscription/plan entity exists yet** (P9-05 unbuilt). The allotment source is therefore either a P9-05 `Subscription.PlanTier` lookup (when built) or a loose `PlanTier` + config-default until then (OQ-1).
5. **Timezone:** `StreakSweepJob` uses a configured `TimeZoneId` for "today". A monthly cycle + expiry should likewise be timezone-aware (cycle boundaries at the family's local time, or a single platform timezone — OQ-4). Mind `EnableLegacyTimestampBehavior` carryover when writing `GrantExpiresAtUtc`.

## Acceptance criteria (testable)

1. **AC-1 (scheduled grant per plan):** A Hangfire recurring job grants each **active** child their plan's monthly allotment (Free = 100, Premium = 5000 — **from P9-11 config**, not literals) into `GrantedBalance` via `CreditAccount.ApplyGrant`, writing a `Grant` ledger row.
2. **AC-2 (expiry stamp):** The granted pool is stamped with `GrantExpiresAtUtc = end of the current cycle`. The amount granted equals the configured allotment for the child's current plan tier at grant time.
3. **AC-3 (rollover expiry):** At cycle rollover, any unspent `GrantedBalance` is zeroed via an **`Expire`** transaction; **`PurchasedBalance` is untouched.** Whether expiry is a separate sweep or folded into the next grant is OQ-5.
4. **AC-4 (idempotency):** Re-running the grant for the same **child + cycle** is a no-op — the idempotency key is `child + cycleId` (or `child + cycle-period`), DB-unique (per P9-01 AC-4). No double-grant even on job retry / overlapping run (`[DisableConcurrentExecution]`).
5. **AC-5 (mid-cycle plan change → next grant):** A plan change mid-cycle does **not** re-grant or claw back the current cycle; it affects the **next** grant only. **Proration is explicitly OQ-2** (the story flags it open).
6. **AC-6 (conventions):** Job mirrors the Gamification job shape (DI scope per run, `ISystemClock`, `ILoggerManager`, `[DisableConcurrentExecution]`, fail-soft per child); writes only through P9-01 primitives; no UoW assumptions beyond the per-child atomic grant; lives in `Billing.Infrastructure/Jobs`.

## Handoff → backend-feature

- **`BillingGrantJob.RunAsync(CancellationToken)` (mirror `StreakSweepJob`):**
  - Fresh DI scope; resolve `BillingDbContext` + the grant config + `ISystemClock`.
  - Compute the current cycle id/period and `cycleEndUtc` (timezone-aware — OQ-4).
  - Enumerate **active** children + their current plan tier (via the contract seam / config default — OQ-1). Page for scale (mirror the 500-row batching in `StreakSweepJob`).
  - For each child: build idempotency key `grant:{childId}:{cycleId}` → call `CreditAccount.ApplyGrant(allotment, cycleEndUtc, key)` inside the per-child explicit transaction (P9-01 primitive) → the DB unique constraint makes a re-run a no-op (catch + skip). **Per-child try/catch fail-soft** — one child's failure never aborts the run.
  - Log a summary line (granted count, skipped-already, failed) like the existing jobs.
- **Expiry path (OQ-5 — two designs):**
  - **(A, recommended) Fold into grant:** at the start of each child's new-cycle grant, first `Expire` any remaining Granted from the prior cycle (key `expire:{childId}:{priorCycleId}`), then `ApplyGrant` the new cycle. One job, one pass, naturally idempotent.
  - **(B) Separate expiry sweep:** a distinct `BillingExpiryJob` (or a query for accounts whose `GrantExpiresAtUtc < now`) that writes `Expire` rows. Cleaner separation but two jobs to coordinate. **Recommend (A).**
- **Active-children + plan-tier seam:** declare/consume a `Shared.Contracts` read (e.g. `IBillingSubscriptionContract.GetActiveChildrenWithTierAsync()`), implemented when P9-05 lands; a config/default fallback until then (OQ-1). No cross-module project ref.
- **Conventions:** `ILoggerManager`; `ISystemClock`; `[DisableConcurrentExecution]`; no direct balance mutation (only P9-01 methods); registered Transient + `InitializeAsync` wiring (serialized shared-file edit if it touches Host).

## Handoff → security-auditor (light gate)

- **No double-grant:** confirm the idempotency key `child+cycle` is DB-enforced (P9-01 constraint) and the job catches the duplicate rather than 500-ing — a double-grant is "free money" and a real abuse/error surface.
- **No claw-back of Purchased:** confirm the `Expire` path zeroes only `GrantedBalance` and never reads/writes `PurchasedBalance`. A bug here would destroy paid-for credits — treat as a correctness-critical invariant.
- **Authorization:** the grant job is server-only (Hangfire) — no external trigger. Confirm there is no public endpoint to invoke a grant (an attacker-triggerable grant = free credits). If a manual admin "run grant now" endpoint is wanted, it must be admin-authorized and still idempotent.
- **Active-only:** confirm cancelled/inactive children are not granted (no granting energy to a lapsed plan).

## Handoff → api-tester

Primarily **integration tests on the job** (no public endpoint expected):
- Grant: an active Free child with an empty account → `GrantedBalance = 100`, one `Grant` ledger row, `GrantExpiresAtUtc = cycleEnd`. Premium → 5000.
- Idempotency: run the job twice for the same cycle → balance still 100, exactly one `Grant` row (DB unique constraint holds).
- Expiry: a child with `GrantedBalance = 120` and `PurchasedBalance = 50` at rollover → after the new-cycle run, prior Granted is expired (`Expire` row for 120), Purchased still 50, new Granted = allotment.
- Plan change mid-cycle: change tier mid-cycle → current cycle grant unchanged; next cycle grants the new tier's amount.
- Config-driven: change the allotment in P9-11 config → the next grant uses the new amount (no redeploy).
- Inactive child → no grant.

## Open questions for the lead

- **OQ-1 (plan/allotment source — sequencing):** build P9-02 against a **config-default tier** seam now and swap in the **P9-05** subscription contract when it lands, or block P9-02 until P9-05? **Recommend build-now against config default + a `Shared.Contracts` seam** so the economy isn't gated on the full subscription story.
- **OQ-2 (proration — the story's named open question):** when a parent upgrades/downgrades mid-cycle, is there any proration of the current-cycle grant, or strictly "current cycle unchanged, new tier applies next cycle"? **Recommend strictly next-cycle (no proration)** for MVP — simplest, matches AC-5 — but this is a **product decision** the lead/PO owns. Flag explicitly.
- **OQ-3 (schedule shape):** a single fixed **monthly cron** (everyone grants on the 1st) vs a **per-child billing anniversary** (grant on each child's own cycle date). **Recommend per-child anniversary aligned to the parent's subscription start** (fairer, matches "billing-cycle date" wording) — but that needs the subscription start date from P9-05. A platform-wide monthly cron is the simpler interim. Confirm.
- **OQ-4 (timezone for cycle/expiry):** cycle boundaries + `GrantExpiresAtUtc` computed in a single platform timezone, or the family's local timezone (consistent with P9-04's per-child local-midnight reset)? **Recommend a single platform timezone for the monthly cycle** (billing is coarse-grained) while the **daily** soft-cap reset (P9-04) is per-child local — confirm the split is acceptable.
- **OQ-5 (expiry: folded into grant vs separate sweep):** **Recommend folded** (expire-prior-then-grant in one pass — fewer moving parts, naturally idempotent). Confirm.
- **OQ-6 (grant-run tracker table):** rely solely on the ledger's `child+cycle` idempotency key, or add a dedicated `BillingGrantRun` audit row? **Recommend ledger-only** (no extra table). Confirm — this decides whether db-migration runs.
- **OQ-7 (mid-cycle new child / new subscription):** when a parent adds a child or subscribes mid-cycle, does that child get an immediate first grant (full or prorated) or wait for the next cycle? **Recommend an immediate full first grant on activation** (good onboarding UX) — but it interacts with OQ-2 proration. Product decision — flag.

### Assumptions
- P9-01 is merged and exposes `ApplyGrant(amount, expiresAtUtc, idempotencyKey)` + `Expire(idempotencyKey)` on `CreditAccount`.
- Hangfire connection (`ConnectionStrings:Hangfire`) is configured (existing requirement since P1-07 per HANDOFF.md) — the recurring job registration depends on it.
- "Active child" is derivable (a child whose parent has a current, non-cancelled plan) — from P9-05 or the interim seam.

### Risks (top 3)
- **R1 — double-grant on job retry/overlap** = free credits. **Mitigation:** `child+cycle` DB-unique idempotency (P9-01) + `[DisableConcurrentExecution]`.
- **R2 — expiry destroying Purchased credits** (a pool mix-up) = paid-for property lost, a refund/trust incident. **Mitigation:** `Expire` touches only Granted; explicit api-tester + security-auditor invariant check.
- **R3 — proration ambiguity** stalls the story. **Mitigation:** force OQ-2 to a product decision before backend-feature; default to no-proration if undecided.
