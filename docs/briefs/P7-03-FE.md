# Pipeline Brief — P7-03 (admin-dashboard) Author skills & the skill dependency graph

> **FE-focused brief.** Backend P7-03 is **built + merged** (Learning module: `SkillsController`, `KnowledgeGraphController`). This brief specs the **Next.js `admin-dashboard`** UI (Wave 2 of the admin FE) over those endpoints. ## Summary & traceability
- **Task (one line):** Build the admin-dashboard UI to author skills (CRUD) and edit the per-language skill **prerequisite dependency graph** — add/remove prerequisite edges with cycle + cross-language rejection surfaced to the admin — over the already-merged Learning endpoints.
- **User story:** `user-stories/Phase-7-Admin-Console/P7-03-author-skill-dependency-graph.md` (SP 8).
- **FE task file:** `tasks/Frontend/admin-dashboard/Phase-7-Admin-Console/P7-03-FE.md` (FE-1..FE-5).
- **BE task file (reference, done):** `tasks/Backend/Phase-7-Admin-Console/P7-03-BE.md`.
- **FR-IDs:** SRS §3 (Admin role), FR-ADM-2 (curriculum admin), FR-CI-3 (content ingestion/authoring). **BRD goal:** G3 (curriculum quality / adaptive engine fed by a correct skill graph — "the most important asset in the company"). **Epic:** Admin — Curriculum Management. **Phase 7, Wave 2.**
- **Depends on:** P7-01 (admin Subjects — the subject picker keyed by `(SubjectCode, Language)`); P2-11 (graph storage + acyclic validator + prereq/unlock queries); P1-10 admin shell (`AdminShell`/`useAdminGuard`); P1-05 Admin policy. Wave-1 admin FE foundation (P7-06/07/08, merged) is the pattern source.

## Business context & value
- **Who benefits:** the **admin/curriculum team** (only role with write access; there is no teacher role). Indirectly every **student**, because the adaptive engine's unlock/prerequisite logic and the student SkillTree are driven by this graph.
- **Value:** replaces hand-edited seed data with a safe authoring UI. The two guardrails are the whole point of the story: **(1) no cycles** in the prerequisite graph (a cycle would deadlock the student's unlock path), and **(2) no cross-language edges** (curriculum is bilingual parallel `ar`/`en` trees; an `ar`→`en` prerequisite is meaningless and corrupts both trees).
- **Success measured by:** admin can create/edit skills and add/remove prerequisite edges; cycle and cross-language attempts are rejected with a clear message and **nothing persists / the bad edge does not render**; prerequisites-of / unlocked-by lists are viewable; all of it admin-only.

## Acceptance criteria (testable)
Mirrors the story's ACs, made concrete for the FE:
1. **Skill CRUD** — admin can create and edit a skill carrying `name`, `masteryThreshold` (0–100), `estimatedTimeMinutes`, and `conceptId` (owning concept); it persists and re-appears in the list. Delete removes it from the list.
2. **Per-language graph scope** — the editor works inside **one** subject tree at a time, chosen via a subject picker; each subject row already encodes a single `(SubjectCode, Language)` tree, so the graph it shows is inherently one language. The active subject + language is shown in the header.
3. **Add prerequisite edge** — connecting two nodes in the same tree creates a `KnowledgeEdge` (type `Prerequisite`, optional `strength` default 1.0) and the edge appears.
4. **Cross-language rejection** — the editor only offers same-tree nodes as edge targets; if the backend still rejects an edge as cross-language (`Successed=false`), the UI shows a clear inline message and does **not** render/persist the edge.
5. **Cycle rejection** — an edge that would create a cycle is rejected by the backend (`Successed=false`); the UI shows a clear "would create a cycle" message and does **not** render/persist the edge (revert any optimistic add).
6. **Prerequisites-of / unlocked-by** — for a selected skill/node, "prerequisites of X" and "skills unlocked by X" are listed (reusing the P2-11 read queries).
7. **Remove edge** — removing an edge deletes it and the graph re-renders without it.
8. **Admin-only** — non-admin / signed-out → redirected to `/login` by `useAdminGuard`; all calls go to AdminOnly endpoints (backend returns 403/401 as the real gate).
9. **States** — every data surface has loading / empty / error+retry states (mirror the Wave-1 users page), bilingual EN+AR copy, and RTL + a11y handled (see a11y section).

## Affected modules & data

- **Backend:** **no new entities or endpoints.** All consumed endpoints already exist and are merged. Graph model (existing, read-only for the FE's understanding):
  - `KnowledgeNode` — `Id`, `Name`, `NodeType` (Skill=0 / Concept=1 / Review=2), `SubjectId`, `GradeId`, `Difficulty`, `SkillId?` (a node *may* wrap a Skill), `IsSkillActive` (admin graph only).
  - `KnowledgeEdge` — `Id`, `SourceNodeId`, `TargetNodeId`, `RelationshipType` (Prerequisite=0 / Related=1), `Strength` (decimal 0.0–1.0).
  - **Language is derived, not stored on the node/edge** — it comes from the node's owning Subject `(SubjectCode, Language)`. The graph read is scoped by `subjectId`; one subject = one language tree.

**Load-bearing details the FE MUST get right:**
- **Edges are keyed by `KnowledgeNode` IDs, NOT skill IDs.** `AddKnowledgeEdgeCommand` takes `sourceNodeId`/`targetNodeId`. The graph nodes returned by `GetGraph` carry both `id` (node id) and `skillId?`. The editor must work in **node-id space** for edges, and only display skill metadata. Do not pass skill ids to the edge endpoints.
- **Edge add/remove return a message string, not a Guid/bool.** The FE task file says `<Guid>`/`<bool>` — wrong. They return `BaseResponse<string>`; on success there is **no created-edge object in the response** → the FE must **refetch the graph** (TanStack invalidation) to get the new edge with its server `id` (same "mutations return a message → invalidate" pattern Wave 1 established). No optimistic-keep of a fabricated edge.
- **No `language` query param on the graph read.** Per-language scoping is achieved purely by choosing a subject (each subject IS one `(SubjectCode, Language)`). Ignore the `&language=` in the task file.
- **`successed=false` is thrown by the api-client** (`apiClient.ts` `handleResponse`: throws `ApiEnvelopeError` when `envelope.successed === false`). So cycle / cross-language / duplicate rejections arrive as a **thrown error in the mutation's `onError`**, carrying `err.status` (400) and `err.message` (the localized server message). This is exactly the `SuspendUserDialog.mapSuspendError` pattern — map server message → admin copy.
- **Backend rejection messages** the FE maps (EN source strings; backend also returns AR when `Accept-Language: ar`):
  - Cycle → `"Adding this edge would create a cycle in the prerequisite graph and was rejected."` (`KnowledgeEdgeWouldCreateCycle`)
  - Cross-language → `"Both nodes of an edge must belong to the same language tree. Cross-language edges are not allowed."` (`KnowledgeEdgeCrossLanguageForbidden`)
  - Duplicate → `"An edge with the same source, target, and relationship type already exists."` (`KnowledgeEdgeDuplicate`)
  - Node missing → `"The requested knowledge node was not found."` (`KnowledgeNodeNotFound`)
  - Subject unresolvable → `KnowledgeNodeSubjectNotResolvable`; strength out of range → `KnowledgeEdgeStrengthOutOfRange`.
  - **Acyclic guard runs only for `Prerequisite` edges.** `Related` edges skip the cycle check (but still get cross-language + duplicate checks). This story is about prerequisites, so default the editor's edges to `Prerequisite`.

## RTL (ar + en) + accessibility
- **RTL:** reuse the users-page idioms — `dir="ltr"` wrappers around technical/number strings (ids, thresholds, minutes), logical CSS props (`insetInlineStart`, `marginInlineEnd`), Tamagui tokens. The whole AR string set must be authored even though the runtime toggle is deferred.
- **a11y is the hard part of this story — address it head-on:**
  - **Do not gate editing behind a drag-to-connect canvas.** The accessible, recommended primary editor is the **list/adjacency editor** (native `<button>`/`<select>`/`<ul>` semantics, full keyboard, screen-reader friendly). This is the strongest reason to recommend the list-first approach over a graph-viz library.
  - Edge add/remove and **cycle/cross-language rejection** must be announced via `aria-live="polite"` (or `assertive` for the rejection error) so a non-visual user knows the action failed and nothing changed.
  - Node pickers: labelled `<select>` or a combobox with proper `aria-` roles; exclude invalid targets (self, cross-language — though cross-language can't even appear since one tree is shown) so the user isn't offered impossible edges.
  - If/when a visual graph render is added, it must be **supplementary** (`aria-hidden` decorative, or with an equivalent accessible table/list), never the only way to read or edit the graph.
  - Focus management on dialogs (reuse `AdminConfirmDialog`'s existing focus trap). Visible focus rings via the existing `--lx-focus-ring-admin`.

## Security / audit
- **AdminOnly writes:** every mutating call (skill CRUD, edge add/remove) hits an AdminOnly endpoint — the backend `[Authorize(Policy = AuthorizationPolicies.AdminOnly)]` is the **real** gate; `useAdminGuard` is only a UX boundary (sessionStorage tokens → no server-side middleware enforcement; documented debt). The FE must not assume client-guard == authorization.
- **P7-12 audit (already wired backend-side):** `AddKnowledgeEdgeCommandHandler` raises `AdminActionPerformedDomainEvent` (`KnowledgeEdgeAdded`) post-commit; skill CRUD likewise produces audit rows (HANDOFF "Curriculum admin creates now produce audit rows"). **No FE work needed for audit**, but the FE must not do anything that bypasses these endpoints (e.g. no direct writes, no swallowing of the real admin identity).
- **No PII** flows through this surface (curriculum metadata only) → `security-auditor` is likely **not mandatory** for this story under the CLAUDE.md trigger list (no auth/authz change, no user/child data, no upload, no AI prompt, no secrets, no payments). **Recommend the lead confirm** whether to run it anyway given it is an admin write surface (OQ-5). The reviewer still checks the AdminOnly + guard wiring.
- The **known AddEdge race** (two complementary edges added concurrently could both pass the acyclic check — `AddKnowledgeEdgeCommandHandler` Finding #3) is an accepted backend low-risk for the single-admin phase; **no FE mitigation expected**, but the FE should not encourage rapid concurrent edge submits (disable the add control while a mutation is in flight).
