# Pipeline Brief — P3-09 Track per-skill mastery (Student Modeling Engine)

## Summary & traceability

- **FR-IDs:**

  - **FR-AD-3** (primary) — "Mastery shall be rule-based: ≥80% = mastered, <50% = needs remediation." *(G2)*
  - **FR-AI-6** (constraint) — AI shall **not** decide progression/difficulty — mastery is a deterministic engine, not AI.

## Business context & value
- **Who benefits:** the **student** (their learning path, weak areas, and recommendations reflect what they actually know — not just "did the lesson"); the **parent** (P5-02 weak-area report reads mastery status); **adaptivity/SR engines** (P3-08/P3-10/P3-11 all read mastery as their core signal); **content/admin** (validates the P2-11 graph + question pool are calibrated).
- **Why it matters:** Today P2-04 reads a *transient* per-skill accuracy aggregate (`GetSkillStatsQuery`, recomputed every call). That is enough for binary unlock but provides **no status state machine**, **no `needs_review`/remediation signal**, and **nothing for the parent report or SR scheduler to read**. P3-09 turns the dormant `StudentSkillMastery` entity (SRS §6) into a **live, persisted, queryable** model — it is the keystone the entire adaptivity cluster depends on (P3-08, P3-10, P3-11 all read it). The strongest moat (BE5) per the barrier-to-entry gap analysis.
- **Why deterministic / rule-based (no AI):** FR-AD-3 + FR-AI-6 — engines decide; the same answer history must always produce the same mastery % and status, so it is debuggable, explainable to a parent, and re-computable on demand.
- **Success measure (testable):** for a seeded student answering questions on a seeded skill, `StudentSkillMastery` rows are created/updated after each completed attempt; mastery % matches the deterministic formula; status transitions `not_started → in_progress → mastered`/`needs_review` per the thresholds; a `GET .../mastery` query returns the rows per student and per skill; the same answer history recomputed yields identical values.

## Open questions for the lead — recommended defaults
> "Approve all defaults" ships a coherent v1.

### Q1 — Mastery % formula (THE algorithm decision — flag explicitly)
This is the real modelling choice the cluster brief calls out. Options, simplest first:
- **(A) Cumulative accuracy (recommended).** `MasteryPercentage = round(correctAnswers / totalAnswers * 100)` over **all** of the student's answers for that skill — identical to what `GetSkillStatsQuery` already computes. Deterministic, trivially explainable to a parent ("you got 7/10 right on Fractions"), already proven in P2-04.
- **(B) EWMA (exponentially-weighted recent accuracy).** Weight recent answers higher so improvement/forgetting shows faster. More responsive, still deterministic, but introduces a decay constant `α` (a new tunable the product hasn't specified) and is harder to explain.
- **(C) BKT / IRT (Bayesian Knowledge Tracing / Item Response Theory).** Probabilistic latent-mastery models. **Not recommended for MVP** — needs per-item difficulty calibration data we don't have, is a black box (conflicts with FR-AD-3 "rule-based" + BRD "explainable"), and is a heavyweight algorithm that triggers the **design-patterns/ask-first** gate.
- **Recommendation: (A) cumulative accuracy for v1**, with the formula isolated in a pure `MasteryEngine.ComputeMastery(...)` so (B) EWMA can replace it later without touching the store or callers. **Do NOT silently introduce EWMA/BKT — flag to lead.** The `needs_review` decay-over-time signal (forgetting) is handled by **P3-10's scheduler reading `LastPracticedAt`**, not by the mastery % formula, which keeps P3-09's % purely accuracy-based.
  - **Note on response time / hints:** FR-AD-2 mastery is accuracy-based; AC2 thresholds are accuracy thresholds. **Response time + hint usage belong to the P3-08 *difficulty* engine, not the mastery %.** Keep them out of P3-09's % to avoid conflating "how well you know it" with "how hard the engine should make it." Flag if the lead wants them folded in.

### Q2 — Threshold reconciliation: FR-AD-3 fixed (80/50) vs. per-`Skill.MasteryThreshold` (70..85)
- FR-AD-3 says ≥80% = mastered, <50% = needs remediation. The seed sets **per-skill** `MasteryThreshold` (70/75/80/85) and **P2-04 already honours the per-skill value**.
- **Recommended default:** status uses **per-skill `MasteryThreshold`** for the `mastered` boundary (consistent with P2-04, avoids two conflicting "mastered" definitions in the same module), and a **fixed 50%** floor for `needs_review` (FR-AD-3's remediation bar, no per-skill override exists for it). Document that FR-AD-3's "80%" is the **default** threshold and seeded per-skill values are deliberate subject-tuned overrides (same stance P2-04's brief took). **Status state machine (recommended):**
  - `NotStarted` — `AttemptsCount == 0` (no answers for the skill).
  - `NeedsReview` — answered, `MasteryPercentage < 50`.
  - `InProgress` — `50 ≤ MasteryPercentage < MasteryThreshold`.
  - `Mastered` — `MasteryPercentage ≥ MasteryThreshold`.
- **Alternative if rejected:** hardcode 80/50 globally (ignore per-skill threshold). Not recommended — it would desync from P2-04's unlock gate.

### Q3 — `SkillId` relationship: intra-module FK or loose int?
- **Recommended default:** **real intra-Learning FK** `StudentSkillMastery.SkillId → Skill.Id` (Restrict delete) — both are in `learning`, so this is allowed (module isolation only forbids *cross-module* FKs). Gives referential integrity + cascade behaviour. `StudentId` stays a **loose int** (Identity is a different module). Mirrors how `StudentAnswer.QuestionId` is an intra-module FK while `Attempt.StudentId` is loose.

### Q4 — When mastery is (re)computed (the update trigger)
- **Recommended default:** **synchronously inside `CompleteAttemptCommandHandler`** — on attempt completion, recompute mastery for **each skill touched by that attempt's answers** (the distinct `Question.SkillId` set), upsert the `StudentSkillMastery` rows, bump `AttemptsCount`, set `LastPracticedAt = UtcNow`. One extra aggregation query + upsert per completion; cheap (an attempt has ~5–15 answers spanning 1–few skills). **No event bus needed** for v1.
  - **Atomicity caveat (CLAUDE rule 3 — no UoW):** the attempt completion + mastery upsert is a multi-write. `CompleteAttempt` currently commits the attempt via the service layer. **Recommend wrapping the completion + mastery upsert in an explicit transaction** (the rule's sanctioned escape hatch) so a student never sees a completed attempt with stale mastery. Flag this to the lead as a deliberate transaction.
- **Alternative if rejected (defer):** emit a `LessonCompleted`/`AttemptCompleted` integration event and recompute mastery in a handler (P2-08 notes mention `LessonCompleted` event stubs). Cleaner decoupling, but adds event plumbing; recommend deferring unless gamification (P4-02 XP) already consumes the same event — **check whether an `AttemptCompleted` integration event already exists** (Gamification has jobs that may listen). If it does, piggyback on it.

### Q5 — Does P2-04 keep its transient aggregate or read the persisted model?
- **Recommended default:** **P2-04's `LearningPathEngine` keeps reading the transient `GetSkillMasteryForStudentAsync` aggregate for now** — do NOT rip out a working unlock path in this story. P3-09 **adds** the persisted store and the status state machine that *other* consumers (P3-08/10/11, P5-02) need. A follow-up can migrate P2-04 to read the persisted `MasteryPercentage` for consistency, but that is a refactor with its own test surface — keep it out of P3-09's scope. **Flag the eventual convergence** so the two never silently disagree (both use the same cumulative-accuracy formula from Q1, so they won't).
- **Alternative if rejected:** make the persisted `StudentSkillMastery.MasteryPercentage` the single source P2-04 reads — requires P2-04 regression testing in this story.

### Q6 — Query surface
- **Recommended default:** two read endpoints, mirroring `GetSkillStats` shape (`[Authorize(Roles="Student")]`, IDOR-guarded by JWT):
  - `GET /api/Learning/Mastery` — all mastery rows for the current student (for the home dashboard + adaptivity).
  - `GET /api/Learning/Mastery/Skill/{skillId}` — single skill mastery for the current student.
  - Plus an **internal query method** on the repo/service consumable by P3-08/P3-10/P3-11 **in-process** (same module — direct call, no HTTP). For P5-02 (parent report, likely Parent module) expose either a query the report reads via integration contract or a `Shared.Contracts` seam — **flag the cross-module read for P5-02** (Parent module needs child mastery; that crosses module isolation → integration event / read contract, decide when P5-02 is built).

### Q7 — Engine shape (pattern caution, rule 8)
- **Recommended default:** a **pure static** `MasteryEngine` domain service (mirror `LearningPathEngine`/`SkillGraphValidator`): `MasteryEngine.Compute(int totalAnswers, int correctAnswers, int masteryThreshold) → (int masteryPercentage, MasteryStatus status)`. No DB, no DI, fed pre-fetched aggregates by the write-path handler. Trivially unit-testable + reproducible.
- **Pattern caution:** a pure rule function is **not** a design pattern. If the implementer reaches for a **Strategy** ("pluggable mastery algorithm" interface) or **State** ("mastery status state machine" class hierarchy) to make Q1's formula swappable, they **must stop and ask the lead first** (CLAUDE rule 8). The cluster is exactly where someone reaches for Strategy/State — default is a plain method + an enum.

## Risks & assumptions
1. **Backfill of `AttemptsCount`/existing answers.** New table starts empty; students with prior attempts have no mastery rows until their next completion (or a one-time backfill job). Recommend lazy fill (created on next completion) for MVP; flag if a backfill is wanted.
2. **`MasteryThreshold` units (int 0..100 = percent)** — same contract P2-04 relies on; document it on the engine.
3. **Grade transition preserves mastery** — ensure no query filters mastery by current grade in a way that hides preserved history; the rows are student×skill, grade-agnostic. Confirm with the grade-transition story owner.
4. **Atomicity (Q4)** — completing an attempt and upserting mastery is a multi-write under the no-UoW rule; needs an explicit transaction. Don't let a partial write leave attempt-completed-but-mastery-stale.
5. **Concurrency** — two concurrent completions for the same skill could race the upsert; the unique `(StudentId, SkillId)` index + upsert-by-recompute (idempotent: recompute is a pure function of all answers) makes a lost update self-healing on the next completion. Note for reviewer.
6. **P5-02 cross-module read** — Parent module reading child mastery crosses isolation; resolve when P5-02 is built (integration contract), not here.

### Handoff → api-tester
Story exposes HTTP endpoints → api-tester runs after backend-feature. Against running API + Testcontainers Postgres + seeded graph + Student-role JWT (reuse P2-08 parent→child onboarding harness):
- New student, no answers → `GET /Mastery` empty (or all `NotStarted`); skill query → `NotStarted`.
- Complete an attempt with high accuracy on a skill → mastery row created, `MasteryPercentage` correct, `Status = Mastered` (≥ per-skill threshold).
- Complete with <50% accuracy → `Status = NeedsReview`.
- Mid-range (e.g. 60% with threshold 80) → `InProgress`.
- Reproducibility: same answer history recomputed → identical `MasteryPercentage`/`Status`.
- IDOR: cannot read another student's mastery (JWT-scoped).
- Idempotency: completing the same attempt twice doesn't double-count.
- Unknown skillId → zeroed/`NotStarted`, never 500.
