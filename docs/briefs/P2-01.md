# Pipeline Brief — P2-01 Model the curriculum hierarchy

## Summary & traceability
- **Task (1 line):** Scaffold a new backend `learning` module and model the curriculum as Grade → Subject → Unit → Lesson → Skill (with Concept), with EF configurations and an initial Npgsql migration — the data foundation every other Phase 2 learning feature builds on.
- **User story:** [user-stories/Phase-2-Learning-Core/P2-01-model-curriculum-hierarchy.md](../../user-stories/Phase-2-Learning-Core/P2-01-model-curriculum-hierarchy.md) (SP 5, Technical Enabler).
- **Task file:** [tasks/Backend/Phase-2-Learning-Core/P2-01-BE.md](../../tasks/Backend/Phase-2-Learning-Core/P2-01-BE.md) (BE-1..BE-5). **Backend/infra only — no Frontend.**
- **FR-IDs:** **FR-LR-1** (model curriculum as Grade → Subject → Unit → Lesson → Skill). Sets up FR-LR-2/3/4, FR-AD-2, FR-QZ-* downstream.
- **BRD goals:** **G2** (learning outcomes), **G5** (scalable platform).
- **Phase / Epic:** Phase 2 — Learning Core (Week 3–4) · Epic: Learning Module. Covers B2.1 / D2.2.
- **Authoritative model:** [SRS §6](../../docs/SRS.md) ERD + [architecture.md §16](../../docs/architecture.md) (which marks Catalog as demo scaffolding to be **replaced** by this module).
- **Blocked by:** P1-06 (PostgreSQL/Npgsql) — **already satisfied** (all modules run `UseNpgsql` today).

## Business context & value
- **Who benefits:** indirectly all three roles. Students get a navigable skill tree (FR-LR-2) and lessons (FR-LR-4); the Adaptivity/Student-Modeling engines (FR-AD-2/3) hang per-skill mastery off `Skill`; the Quiz engine (FR-QZ-*) attaches `QuizQuestion` to `Skill`; admins later upload curriculum into this hierarchy (FR-CI-*).
- **Value:** a single consistent curriculum spine so lessons, skill tree, adaptivity, gamification, and AI tutoring all reference the same structure. This is a **technical enabler** — no end-user-facing screen ships in P2-01; success is measured by every later Phase 2 story being able to build against a stable schema.
- **Product decisions in force:** 4 subjects (Math, Science, Arabic, English; **no Social Studies**); grades 1–6; **no teacher role**; grade transition preserves history (relevant to how `Grade` is modeled — see open questions).

## Acceptance criteria (testable)
1. A new `learning` module exists as four projects (`Learnexia.Modules.Learning.{Domain,Application,Infrastructure,Api}`) added to `Learnexia.Modular.sln` and registered in the Host via `AddLearningModule(configuration)`.
2. The module defines five domain entities: **Subject, Unit, Lesson, Concept, Skill** (deriving from `AggregateRoot` — see handoff note), each carrying the SRS §6 fields.
3. Relationships match [SRS §6](../../docs/SRS.md): **Subject 1—* Unit**, **Unit 1—* Lesson**, **Subject 1—* Concept**, **Concept 1—* Skill**, and **Lesson *—o1 Skill** ("Lesson teaches Skill", optional on the Lesson side).
4. Each **Skill** carries `MasteryThreshold` (int %) and `EstimatedTimeMinutes` (int).
5. Each **Lesson** carries `Difficulty`, `SequenceOrder` (int), and `IsLocked` (bool). Each **Unit** carries `SequenceOrder`.
6. An initial Npgsql migration creates all five tables in the **`learning`** schema with correct FKs and indexes (FK columns indexed; sequence/lookup columns indexed where sensible), and applies cleanly on PostgreSQL (`dotnet ef database update`).
7. `dotnet build backend/Learnexia.Modular.sln` succeeds; the module is wired into the cross-module MediatR registration and (per Track B) into `Claims.GenerateModules()`.
8. Module isolation respected — no references to other modules' projects, no cross-module FKs. `CreatedBy/UpdatedBy` stay plain `int`.

> Note: P2-01 ships **schema + module wiring only**. No commands/queries/controllers are required by the story's ACs (the task file lists none). See handoff + open questions on whether to add a minimal read/seed surface.

## Affected modules & data
- **New module:** `learning` (schema `learning`). Entirely new — **nothing exists under `backend/src/Modules/Learning/` today** (confirmed).

- **New entities (all new):** `Subject`, `Unit`, `Lesson`, `Concept`, `Skill`.

### Relationship shape
```
Subject 1 ──< Unit 1 ──< Lesson
Subject 1 ──< Concept 1 ──< Skill
Lesson * ──o1 Skill        (Lesson.SkillId nullable; "Lesson teaches Skill")
```
All FKs are **within** the `learning` schema (intra-module) — allowed. No FK crosses to `identity`/`catalog`.

## Handoff → db-migration
- **New `LearningDbContext`** (`Infrastructure/Persistence/`): `public const string Schema = "learning";`, a `DbSet<>` per entity, `HasDefaultSchema(Schema)`, `ApplyConfigurationsFromAssembly(...)`, and the audit-stamping `SaveChangesAsync(int userId)` override. **Mirror** [CatalogDbContext.cs](../../backend/src/Modules/Catalog/Learnexia.Modules.Catalog.Infrastructure/Persistence/CatalogDbContext.cs) but **drop the pgvector/EmbeddingDemo demo bits** (not needed here). Add a design-time `LearningDbContextFactory` mirroring Catalog's.
- **EF configurations** (`Persistence/Configurations/`): Catalog uses pure conventions, but this story has real relationships — prefer explicit `IEntityTypeConfiguration<T>` for the optional `Lesson → Skill` FK (`OnDelete` behavior must be chosen — Q6), the required FKs, and indexes. Conventions otherwise.
- **Indexes:** FK columns (`Unit.SubjectId`, `Lesson.UnitId`, `Lesson.SkillId`, `Concept.SubjectId`, `Skill.ConceptId`); consider a composite `(SubjectId, SequenceOrder)` on Unit and `(UnitId, SequenceOrder)` on Lesson for ordered reads.
- **Provider:** `UseNpgsql` in both runtime DI and the design-time factory; `MigrationsHistoryTable("__EFMigrationsHistory", LearningDbContext.Schema)`; `MigrationsAssembly` = the Infrastructure assembly. Mirror [Catalog Infrastructure DI](../../backend/src/Modules/Catalog/Learnexia.Modules.Catalog.Infrastructure/DependencyInjection.cs).
- **Migration:** `dotnet ef migrations add InitialLearning --project src/Modules/Learning/...Infrastructure --startup-project src/Host/Learnexia.Host`. No startup auto-migrate is required, but follow the existing pattern: expose a Host-callable `LearningModule.InitializeAsync` that calls `MigrateAsync` (mirror [CatalogModule.cs](../../backend/src/Modules/Catalog/Learnexia.Modules.Catalog.Api/CatalogModule.cs)) and call it in `Program.cs`.
- **Cardinality note:** delete behavior on the **required** FKs (Subject→Unit→Lesson, Concept→Skill) — confirm cascade vs restrict (Q6); these entities are audited/soft-deletable (`IsDeleted`), so hard cascade is likely undesirable.

## Handoff → backend-feature
- **Deferred-commit module (critical).** Per [ADR 0001](../../docs/dev/adr/0001-unit-of-work.md) + [ADR 0002](../../docs/dev/adr/0002-domain-events-and-dispatch.md), `learning` is a **new module** and must use **deferred commit + after-commit domain-event dispatch**, **NOT** Catalog's per-call `SaveChangesAsync`. Concretely:
  - Entities derive from **`AggregateRoot`** (`Shared.Kernel.Entities.AggregateRoot`), not `FullAuditedEntity` directly — so they can raise domain events later (P2-02+ / Phase 4).
  - Add a module-local **`UnitOfWorkBehavior<TRequest,TResponse>`** in `Learning.Infrastructure/Behaviors/` injecting `LearningDbContext`, `ICurrentUserService`, `IDomainEventDispatcher`. **Copy** [Identity's UnitOfWorkBehavior.cs](../../backend/src/Modules/Identity/Learnexia.Modules.Identity.Infrastructure/Behaviors/UnitOfWorkBehavior.cs) verbatim, swapping the DbContext type. Register it `AddTransient(typeof(IPipelineBehavior<,>), typeof(UnitOfWorkBehavior<,>))` in Infrastructure DI **after** `ValidationBehavior` (which is registered in Application DI). Repositories must **not** call `SaveChangesAsync`.
- **Application DI** (`AddLearningApplication`): register validators + AutoMapper + `ValidationBehavior` only. **Do NOT call `AddMediatR` per module** — MediatR is registered once at the Host (see shared-file impact). Mirror [Catalog Application DI](../../backend/src/Modules/Catalog/Learnexia.Modules.Catalog.Application/DependencyInjection.cs).
- **Repository/Service layer:** copy the Catalog Infrastructure shapes (`GenericRepository`, `RepositoryManager`, `BaseService<TEntity>`, `ServiceManager`, `CurrentUserService`) **but** ensure writes are stage-only for the UoW behavior (per ADR 0001's caveat — Catalog's `BaseService.AddAsync` returns success from the immediate save; the new module must not depend on that). Define `ILearningRepositoryManager`/`ILearningServiceManager` + typed `I<Aggregate>Service : IBaseService<TEntity>` in `Application/Abstractions`. Add an `AssemblyReference` in Application (needed for the Host MediatR scan).
- **Commands/queries/DTOs/controllers:** **none are mandated by the story ACs** — P2-01 is schema + wiring. If the lead wants a smoke surface, add a minimal `GET /api/learning/subjects` list query + a seed (see Q7); otherwise leave the Api project with `AppControllerBase` only and no controllers. **Recommend confirming with the lead before adding endpoints** (no `api-tester` run is needed if no HTTP endpoints ship).
- **No-free-text / enums rule:** per the project rule, `Difficulty`/`DifficultyLevel` should be **enums** (stored as int or via `HasConversion`), not free strings, even though SRS types them `string`. Names that are user-facing UI labels are i18n'd at the presentation layer — but **Subject/Unit/Lesson/Skill names are curriculum content authored by admins**, so they remain string columns (not enums). Confirm enum choice in Q3.
- **AuthZ:** add `[Authorize(policy)]` only if/when endpoints are added; policies `Learning.View/List/Create/Edit/Delete` are generated once the module is added to `Claims.GenerateModules()` (shared-file impact below). Not enforced by default.

## Open questions / assumptions / risks
- **Q1 — Grade modeling.** SRS §6 models grade as an **int column on Subject** (and on KnowledgeNode), with **no standalone `Grade` entity**, yet the story title says "Grade → Subject". **Assumption:** follow SRS — `Subject.Grade` is an int (1–6), no `Grade` table. This also matters for the **grade-transition-preserves-history** product decision: a child changing grade re-scopes which Subjects are in view; history attaches to Skill/mastery, which is unaffected. **Confirm** no separate Grade entity is wanted.
- **Q2 — Defaults / value ranges.** `Skill.MasteryThreshold` — default to 80 (FR-AD-3 "≥80% = mastered")? Range-check (0–100)? `Grade` constrained to 1–6? These are validation/seed concerns; no command exists yet to validate against. **Assumption:** model as plain int columns now; enforce ranges when write commands are added (later story).
- **Q3 — Enums vs strings (no-free-text rule).** Recommend `Difficulty`/`DifficultyLevel` become an enum (e.g. `DifficultyLevel { Easy, Medium, Hard }`) per the project's no-free-text/enum rule, stored via `HasConversion<int>` or as a constrained value. **Subject/Unit/Lesson/Skill `Name`** stay string (admin-authored curriculum content). Confirm the enum approach and storage (int vs string column).
- **Q4 — Nullability.** `Subject.Country` and `Concept.Description` — required or nullable? SRS doesn't say. **Assumption:** `Country` nullable (single-country MVP), `Description` nullable. Confirm.
- **Q5 — Catalog retirement.** SRS §7 / architecture §16 say Catalog is demo scaffolding to be **replaced** by `learning`. **Assumption for P2-01:** do **not** delete or modify Catalog in this story (additive only); retirement is a separate, later cleanup. Confirm the lead agrees Catalog stays for now.
- **Q6 — FK delete behavior.** Cascade vs Restrict on Subject→Unit→Lesson and Concept→Skill, given entities are soft-deletable (`IsDeleted`). **Recommendation:** `Restrict`/`NoAction` (avoid hard cascade; rely on soft-delete). The optional `Lesson.SkillId` should be `SetNull`/`Restrict`. Confirm.
- **Q7 — Scope of P2-01: schema-only or include a read/seed surface?** The story ACs and task file mandate **no** commands/queries/controllers. **Recommendation:** keep P2-01 to module scaffold + entities + migration (+ optionally a seed of the 4 subjects). If the lead wants a verifiable HTTP endpoint, add a single `List Subjects` query — but that pulls in `api-tester` and is arguably P2-02 scope. **Decision needed.**
- **Risk — BaseService/UoW coupling.** ADR 0001 explicitly warns the copied Catalog `BaseService.AddAsync` returns success from an immediate save; in a deferred-commit module the `UnitOfWorkBehavior` owns commit/rollback. If `backend-feature` copies `BaseService` unchanged and later adds a write command, success/rollback semantics could be wrong. Flag for the planner to ensure the deferred-commit pattern (Identity's, not Catalog's) is the reference for any write path. (No write path ships in P2-01, so it's a latent risk only.)
- **Risk — shared-file serialization.** Five shared files (sln, Program.cs, MediatRExtensions, Claims, Host csproj) are touched. If any Phase 2 sibling runs in parallel, these must be serialized per [PARALLELISM.md](../../docs/dev/PARALLELISM.md). P2-01 is the foundation, so it should land **before** other Phase 2 stories regardless.

## Recommended pipeline order (first cut — planner finalizes)
1. **db-migration + backend-feature scaffold (mostly sequential, one batch):** because this is a brand-new module, the scaffold (4 projects, DbContext, DI, module wiring, AggregateRoot entities, UoW behavior) and the migration are tightly coupled. Suggested internal order: (a) entities (`AggregateRoot`) → (b) `LearningDbContext` + EF configs + factory → (c) module/DI/Host wiring + Claims + MediatR registration → (d) `InitialLearning` migration + `database update`.
2. **reviewer** gates against the ACs above + CONVENTIONS (module isolation, deferred-commit pattern, schema isolation, `Successed` untouched, no cross-module FK, build green, migration applies).
3. **No `designer`** (backend-only). **No `api-tester`** unless Q7 adds an endpoint. **No `security-auditor`** required (no auth/child-data/upload/AI/secrets surface in P2-01) — revisit if an endpoint is added.
