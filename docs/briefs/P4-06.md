## Business context & value

- **Who benefits:** the **student** directly — missions are the *today's-anchor* reward layer. XP rewards every action, streaks reward consecutive presence, hearts gate punishment, badges reward lifetime milestones. Missions are the **only** layer that says "here's what to do *today* / *this week*, and here's what you get for finishing it." They make the open-ended "do lessons" loop into "do 3 lessons → earn 30 bonus XP." **Secondary — the parent**: missions show up in P5-04 weekly reports as the per-period habit signal. **Tertiary — the system**: missions are the rail P4-09 hangs the daily nudge off (*"You have 1 lesson left to complete your daily mission"*) and the rail P3-10 spaced-repetition uses to surface weak skills as targeted mission objectives (Notes).
- **Why it matters now:** the dashboard has had a `DailyMission: null` placeholder since P2-09 (~3 months of dead UI). P4-08's gamification screens already mockup a Missions screen (`P4-08-gamification-screens-and-motion.md` line 15). P4-09 nudges can't fire the *"daily-mission reminder"* nudge without rows to count. P4-11 weekly challenges layers ON TOP of mission infrastructure. P3-10 spaced repetition wants to "target weak skills into missions." This is the last brick in the Phase-3 reward economy.
- **Success measurement:**
  - Brand-new student loads dashboard → daily missions auto-instantiated (5 rows), all with `Progress = 0, Status = NotStarted`.
  - Student completes 1 lesson → `CompleteLessons` daily mission progress goes 0 → 1, `Status = InProgress`. `Status` flips to `Completed` and reward XP is awarded when `Progress >= Target`.
  - Same `LessonCompletedIntegrationEvent` redelivered → no double-count (one `MissionProgressLog (StudentMissionId, OriginEventId)` row per increment).
  - Next day's first dashboard load → today's missions auto-instantiated (5 new rows); yesterday's *uncompleted* missions flipped to `Expired` by overnight `MissionRolloverJob`.
  - Completed yesterday's missions stay `Completed` forever (mission history is preserved — feeds parent reports + analytics).
  - `IStudentMissionsQuery.GetByStudentIdAsync` returns daily list + weekly summary (or both lists per Q3).
  - `GET /api/Gamification/Missions/Me` returns the full daily + weekly snapshot, JWT-scoped, IDOR-proof.
- **Deterministic principle (BRD §8 / FR-AI-6):** mission predicates are **pure integer counters** over `(event, mission, target)`. No AI, no randomness. The catalog is config-as-code (seeded), tunable per env at deploy time only. Mission instantiation per period is deterministic (same student, same period → same 5 daily + 3 weekly missions from the catalog).

## Acceptance criteria (verbatim from story + testable backend gates)

From `P4-06-missions.md`:

1. **AC1 — Missions have a type (daily/weekly), an objective, a reward (XP), and an expiry.**
   - Backend gate: `MissionDefinition` row exposes `(Code, Title, Description, IconKey, MissionType, TargetType, TargetValue, RewardXp, SortOrder)`. `StudentMission` row carries `(MissionDefinitionId, MissionType, PeriodStartUtc, PeriodEndUtc, Progress, Target, Status, CompletedAtUtc?)`. `PeriodEndUtc` is the expiry. Catalog is seeded by `MissionSeeder` at startup (idempotent upsert by `Code`). Five `TargetType` values used in MVP: `CompleteLessons`, `CorrectAnswers`, `EarnXp`, `MaintainStreak`, and a forward-compat `CompleteUnit` (placeholder — Q2 decision on initial catalog).

2. **AC2 — `StudentMission` tracks status and progress %; progress updates from learning events.**
   - Backend gate: three new `INotificationHandler<>` classes in `Gamification.Application/Features/Missions/EventHandlers/`:
     - `LessonCompletedMissionHandler : INotificationHandler<LessonCompletedIntegrationEvent>` — increments `CompleteLessons` daily/weekly missions.
     - `AnswerSubmittedMissionHandler : INotificationHandler<AnswerSubmittedIntegrationEvent>` — increments `CorrectAnswers` daily/weekly missions when `CorrectAnswerCount > 0`.
     - `StreakAdvancedMissionHandler : INotificationHandler<StreakAdvancedDomainEvent>` — completes `MaintainStreak` daily missions (progress 0 → 1 — `Target = 1`).
   - Each handler loads the student's *active* mission instances for the relevant `TargetType`, calls `MissionProgressUpdater.Apply(instance, originEventId, incrementBy: 1)` per instance, sends one `IncrementMissionProgressCommand` per matched instance. The command runs through `UnitOfWorkBehavior` — atomic write of `MissionProgressLog` (idempotency row) + `StudentMission.Progress`, after-commit dispatch of `MissionCompletedDomainEvent` if `Progress >= Target`.
   - **Note: the story says "progress %" — we store `Progress` (int) + `Target` (int); FE computes the percentage `(Progress * 100) / Target`. This avoids floating-point drift across the boundary and is consistent with how the existing `DailyMissionDto` already shapes `(Target int?, Progress int?)`.**
   - **Idempotency:** `MissionProgressLog (StudentMissionId, OriginEventId)` unique constraint — one row per event-per-mission. A redelivered event is a no-op (handler short-circuits via existence pre-check; DB unique constraint is the backstop).

3. **AC3 — Completing a mission grants its reward and reflects on the dashboard.**
   - Backend gate: when `StudentMission.Progress >= StudentMission.Target` for the first time (`Status` transition `InProgress → Completed`):
     - Set `Status = Completed`, `CompletedAtUtc = event.OccurredOnUtc`.
     - Raise `MissionCompletedDomainEvent(StudentId, MissionCode, MissionType, RewardXp, CompletedAtUtc)` on the `StudentXpProfile` aggregate via `profile.RecordMissionCompleted(...)` (mirrors `profile.RecordBadgeEarned` from P4-05).
     - Add an `XpAward` row with `Reason = XpReason.MissionCompleted`, `OriginEventId = Guid.NewGuid()`, `Amount = mission.RewardXp`. The fresh GUID is always unique on `UX_XpAwards_OriginEventId_Reason`.
     - Recompute level via `LevelCurve.LevelFor(TotalXp)`; if level increases, the existing `StudentLeveledUpDomainEvent` chain fires → triggers P4-05's `StudentLeveledUpBadgeHandler` → may award a LEVEL badge. **Cascade-correct chain semantics, terminates (bounded by catalog size).**
   - Dashboard read (`GetDashboardQueryHandler`) consumes `IStudentMissionsQuery.GetByStudentIdAsync(studentId)` which returns a `StudentMissionsSnapshot { IReadOnlyList<MissionSummary> Daily, IReadOnlyList<MissionSummary> Weekly }`. Sentinel snapshot `([], [])` for brand-new students (mirrors `IStudentHeartsQuery`/`IStudentBadgesQuery` pattern). The handler lazily instantiates the current period's missions if no rows exist for the student in this period (Q4 decision).

4. **AC4 — Expired incomplete missions close out and new ones are issued on schedule.**
   - Backend gate: **two coordinated mechanisms** (hybrid lazy + Hangfire — Q4 decision):
     - **Lazy instantiation on dashboard read** — `StudentMissionsQuery.GetByStudentIdAsync` checks: do you have non-Expired daily missions whose `PeriodEndUtc > now`? If not, instantiate today's 5 from the catalog. Same check for weekly. Atomic per-student; UNIQUE `(StudentXpProfileId, MissionDefinitionId, PeriodStartUtc)` prevents duplicate instantiation under concurrency. **This is the source-of-truth for instantiation** — handles inactive-students cleanly (no DB churn for students who don't open the app).
     - **`MissionRolloverJob` (Hangfire, mirrors `StreakSweepJob`)** — runs `Daily 00:05 UTC` AND a separate `Weekly 00:10 UTC Mondays`. Bulk `ExecuteUpdateAsync` flips `Status = Expired` for any `StudentMission` where `Status IN (NotStarted, InProgress) AND PeriodEndUtc <= now`. Does NOT instantiate (lazy path does that on next dashboard load) — only closes out yesterday's loose ends so they don't pollute the dashboard for active students. Idempotent. **R3 note: bulk update bypasses change tracker — no domain events from this path. Same precedent as `StreakSweepJob` (R3 was accepted there too).**

### I. Hardening (do NOT skip)

- **Per-`(StudentMissionId, OriginEventId)` idempotency** — two layers: `HasMissionProgressLogAsync` pre-check + DB unique constraint. Defense-in-depth.
- **Per-handler isolation** — each notification handler wrapped in try/catch (fail-soft); `IsolatedNotificationPublisher` also isolates at the publisher level.
- **Per-command UoW** — each `mediator.Send` from a notification handler opens its own transaction.
- **Lazy-instantiation race** — `UX_StudentMissions_StudentXpProfileId_MissionDefinitionId_PeriodStartUtc` backstops. `StudentMissionsQuery` catches `DbUpdateException` and re-reads.
- **Row-lock on profile** for the completion path (XP write needs `AcquireProfileLockAsync`, same as P4-05 badge award).
- **No `ex.Message` echoed** — `ServerError<T>()`.
- **JWT-derived StudentId in queries** — `GetMyMissionsQueryHandler` uses `_currentUser.UserId`; **no `studentId` route/query parameter** (IDOR-proof by construction).
- **Trust the event payload's `StudentId`** in notification handlers — not `_currentUser` (which is null in the post-commit dispatch scope). Same invariant as P4-02/03/04/05.
- **Conventions:** module isolation (no cross-module project ref), `ILoggerManager` only, `BaseResponse<T>`, `Successed`, no design pattern (rule 8).

## Open questions / assumptions / risks

### Top open questions (priority order — planner decides any not answered before kick-off)

**Q1: Rollover schedule** — daily UTC midnight (`5 0 * * *`) for daily missions; weekly Monday UTC 00:10 (`10 0 * * 1`) for weekly — both running against `TimeZoneId = UTC` (mirrors P4-03 default). **Recommendation: ship UTC**; per-user TZ is deferred to a future story (no `User.TimeZoneId` field exists; mirrors P4-03 Q2 decision). **Lead confirm.**

**Q2: Initial mission catalog** — see Concrete catalog proposal below. **Recommendation: 5 daily + 3 weekly**. **Lead confirm + adjust XP rewards.**

**Q3: Dashboard surface shape** — three sub-options:
- **(a) Reuse `DailyMission` slot, append `WeeklyMission`** — least churn; FE has lived with `DailyMission?` for months. **Recommended.**
- **(b) Replace both with a `Missions: StudentMissionsSnapshot?` single field.** Cleaner, more breaking.
- **(c) Don't show weekly on dashboard at all** — let it live only on the Missions screen (`/Me` endpoint). Reduces dashboard chrome.

**Q4: Mission instantiation strategy** — **lazy on dashboard read** (recommended) vs eager nightly Hangfire job that creates instances for every student. **Recommended: lazy** — avoids row churn for inactive students; the Hangfire job ONLY closes out expired-but-incomplete rows.

**Q5: `EarnXp` / `CompleteUnit` target types** — **recommend DEFER**. Three target types (`CompleteLessons`, `CorrectAnswers`, `MaintainStreak`) cover ~95% of the catalog the story needs and have clean event mappings. EarnXp has no clean event; CompleteUnit has no integration event yet.

**Q6: Endpoint surface** — `GET /api/Gamification/Missions/Me` mirroring `Badges/Me`. **Recommended.**

**Q7: XP reward shape** — **per-mission scalar value on `MissionDefinition.RewardXp`**. NOT rarity-tiered (missions are recurring, rarity feels wrong). Recommended values in catalog below (range 30..200). **Lead confirm range.**

**Q8: Lazy-instantiation race-condition handling** — race between two concurrent dashboard loads (same student) racing to instantiate today's missions. `UX_StudentMissions_StudentXpProfileId_MissionDefinitionId_PeriodStartUtc` is the backstop. **Recommendation: catch `DbUpdateException` in `StudentMissionsQuery`, re-read once, return.** Adds ~10 LoC; matches the P4-03/04/05 race pattern.

**Q9: Practice Mode interaction.** Hearts=0 + student completes a lesson — should mission counters advance? **Recommend YES.** Lesson completion is real student work; missions shouldn't punish kids in Practice Mode. (Badge engine made the same call.) `MaintainStreak` is by-construction unreachable in PM (streak event never fires). `CompleteLessons` and `CorrectAnswers` WILL advance in PM. **Lead confirm.**

**Q10: `AnswerSubmittedIntegrationEvent.CorrectAnswerCount` semantics.** Verify with Learning module: does each event represent ONE answer (count = 0 or 1) or can it represent a batch? Looking at `SubmitAnswerCommandHandler` patterns from P2 — appears to be one-per-event. **Recommendation: treat as one-per-event; `CorrectAnswerCount > 0 → increment by 1`.** Confirm with Learning module behaviour.

**Q11: Mission state mutation location.** Pure `MissionProgressUpdater` static returning a result vs. encapsulating state mutation on `StudentMission` (`mission.ApplyProgress(...)`). **Recommend: encapsulate on entity** — keeps state invariants with the data; the static service holds the *decision* logic only (or remove the static and put both decision + mutation on the entity). Matches the P4-05 `StudentXpProfile.RecordBadgeEarned` precedent.

**Q12: FE wire-up scope.** Story labels include `frontend`. **Recommend minimal scope:** flip the existing `MissionBanner` to render when `dashboardQuery.data.dailyMission` is non-null (~1h). Full Missions screen is P4-08. **Lead confirm scope.**

**Q13: `StudentMission` audit shape — `CreationAuditedEntity` or `FullAuditedEntity`?** The row is created once and mutated on every progress event. `FullAuditedEntity` would stamp `UpdatedAt`/`UpdatedBy` on each progress write — slightly more truthful. **Recommend `CreationAuditedEntity`** — progress is event-driven; the `MissionProgressLog` ledger IS the audit trail; `UpdatedAt` would just track the most recent event timestamp redundantly. Mirrors `StudentBadge` (one-shot) but the analogue isn't perfect.

### Assumptions

- **`StreakAdvancedDomainEvent`** fires reliably AFTER its originating commit; **`IsolatedNotificationPublisher`** isolates per-handler failures; **`UnitOfWorkBehavior`** dispatches post-commit. All verified in P4-02..P4-05.
- **`AcquireProfileLockAsync`** still works inside the `IncrementMissionProgressCommandHandler` UoW transaction (same as P4-05 used it).
- **`LevelCurve.LevelFor(TotalXp)`** is the single source of truth for level computation — reused for the mission-XP-triggered level recompute.
- **No Redis dependency** — Phase-3 storage stays Postgres-only; P4-10 is the cutover story.
- **The `MissionBanner` FE primitive** (built in P2-09-FE) accepts the field shape that `MissionSummary` projects to. Verify in FE batch.

### Risks (top 3)

- **R1 — Lazy instantiation races.** Two concurrent dashboard loads for the same student race to insert today's 5 rows. **Mitigation:** UNIQUE `(StudentXpProfileId, MissionDefinitionId, PeriodStartUtc)` backstop + `DbUpdateException` catch-and-retry in `StudentMissionsQuery`. **Test:** case 3 (second dashboard load same day) + a dedicated 3-concurrent-load stress test.
- **R2 — Daily missions never instantiate for never-logged-in students.** A student who completes a lesson via embedded learning flow but NEVER opens the dashboard won't have today's missions instantiated → `LessonCompletedMissionHandler` finds zero active missions → mission progress is lost forever. **Mitigation:** the notification handler can ALSO lazy-instantiate before counting (mirror of dashboard logic). Decide: instantiate in event handler too OR accept that dashboard-first is the UX (recommend the latter — students see missions only when they look at the dashboard, and the lesson flow is dashboard-reachable). **Lead decision.**
- **R3 — Rollover job races with active completion.** A student completes their last lesson at 00:04:58 UTC; commit lands at 00:05:01 UTC; sweep job fires at 00:05:00 UTC, expires the in-progress mission. **Mitigation:** 5-minute cron buffer (`5 0 * * *` not `0 0 * * *`) gives transactions time to land. Same precedent as P4-03 `StreakSweepJob`. Acceptable for MVP. Document in `MissionRolloverJob` XML comments.
