## Business context & value

- **Who benefits:** the **student** directly — the flame counter ticks up each day they show up, gives them a number to defend, and triggers a +30 XP bonus that's only available by coming back tomorrow. This is the BRD §3 G3 success metric ("Streak length, daily-mission completion rate"); without streaks, the daily-habit loop is hollow.
- **Why it matters now:** P4-09 (re-engagement notifications) reads streak state to fire "streak-at-risk" nudges; P4-11 (streak freeze) consumes streak state when it auto-protects a streak; P4-05 (badges) includes "N-day streak" rules; the dashboard (P2-09) and FE animations (P4-08) render the flame. P4-03 is the keystone for *every* habit-formation story that follows.
- **Success measurement:** every qualifying `LessonCompletedIntegrationEvent` whose `OccurredOnUtc`'s day-bucket is **strictly after** `LastActivityDateUtc`'s day-bucket writes exactly one streak update; first activity of a brand-new student writes `CurrentStreak = 1`; activity on day-N+1 writes `CurrentStreak = N+1`; activity that skips a day writes `CurrentStreak = 1` and triggers a `StreakBrokenDomainEvent`; the dashboard's `Streak` field reflects the running counter within p95 < 500ms; a duplicate event (same `EventId`) is a no-op (date-based + `OriginEventId`-based defenses); a brand-new student returns `Streak = 0`.
- **Deterministic principle (BRD §8 / FR-AI-6):** the streak rule is **a pure day-difference comparison** — no AI, no randomness, no grace window. The day boundary itself is a config (timezone — Open Question Q2).

## Acceptance criteria (verbatim from story + testable backend gates)

From `P4-03-streaks.md`:

1. **AC1 — Completing qualifying activity on a day increments the streak; the streak state is visible (animated flame).**
   - Backend gate: `LessonCompletedIntegrationEventHandler` now ALSO sends an `AdvanceStreakCommand` (or augments the existing `AwardLessonCompletedXpCommand` — Open Question Q4). The handler advances `CurrentStreak` by exactly 1 when `OccurredOnUtc.Date > LastActivityDateUtc.Date` and the gap is 1 day; "visible" = the new `Streak` value on `GET /api/Learning/Dashboard`. **FE animation is P4-08, not this story** (story labels include `frontend` but the P4-08 dependency note in P4-08-FE owns the flame.svg).

2. **AC2 — Missing the required activity resets the streak per the configured rule.**
   - Backend gate: on the next activity after a gap > 1 day, the handler sets `CurrentStreak = 1` (new activity counts as day-1 of a new streak — NOT 0), keeps the old `LongestStreak` if `CurrentStreak < LongestStreak`, and raises a `StreakBrokenDomainEvent(StudentId, PreviousStreak, BreakAtUtc)` for P4-09 (re-engagement) to consume later. **No grace window** — SRS FR-GM-2 rider closes BRD §10 #4 in favor of streak-freeze (P4-11) only. Lazy-evaluated on next activity.

3. **AC3 — Streak count is stored on the student profile and surfaced on the dashboard.**
   - Backend gate: streak state lives in the Gamification module (NOT Learning, NOT Identity — module isolation). Recommended placement: **extend `StudentXpProfile`** with `CurrentStreak`, `LongestStreak`, `LastActivityDateUtc` columns (Open Question Q1 — three options compared below). Dashboard reads via new `IStudentStreakQuery` in `Shared.Contracts/Gamification/`. The existing `DashboardDto.Streak` (already a non-nullable int) gets a real value; no DTO contract change.

4. **AC4 — A daily background job evaluates streak continuity reliably across time zones.**
   - Backend gate: Hangfire `RecurringJob` (e.g., `streak-daily-sweep`) runs once per day (Open Question Q3 — UTC midnight vs Cairo midnight) and scans `StudentXpProfile` rows where `LastActivityDateUtc.Date < (today - 1 day)` AND `CurrentStreak > 0`. For each match, it **flags the streak as broken** (sets `CurrentStreak = 0`) AND raises `StreakBrokenDomainEvent` so P4-09 can fire "streak-at-risk" → "streak-broken" nudges. **Important design call (Open Question Q5):** the source of truth for the streak counter remains **lazy break detection in the activity handler** — the job is a *defensive observability sweep* for students who go silent (otherwise their streak shows N forever until they return, and re-engagement nudges never fire). Without the job, a student who hasn't opened the app in 10 days still shows `CurrentStreak = N` until they come back. With the job, the dashboard says 0 and the nudge fires.

### A. Domain (`P4-03-BE-1` + `P4-03-BE-2`)

1. **Extend `StudentXpProfile`** with the 3 streak fields and 3 mutation methods:
   - `void AdvanceStreak(DateOnly activityDate)` — sets `CurrentStreak = LastActivityDateUtc is null || CurrentStreak == 0 ? 1 : CurrentStreak + 1`; sets `LastActivityDateUtc = activityDate`; sets `LongestStreak = Math.Max(LongestStreak, CurrentStreak)`; **raises `StreakAdvancedDomainEvent(StudentId, CurrentStreak, LongestStreak, activityDate)`**.
   - `void ResetStreakAndStart(DateOnly activityDate)` — sets `CurrentStreak = 1`, `LastActivityDateUtc = activityDate`, raises `StreakBrokenDomainEvent(StudentId, previousStreak, brokenAtUtc=activityDate)` THEN raises `StreakAdvancedDomainEvent(StudentId, 1, LongestStreak, activityDate)`. (Brick: the broken event captures the just-ended streak, the advanced event captures the new day-1.)
   - `void BreakStreak()` — used by the sweep job; sets `CurrentStreak = 0`, leaves `LastActivityDateUtc` and `LongestStreak` alone, raises `StreakBrokenDomainEvent`.
2. **`StreakAdvancedDomainEvent.cs`** + **`StreakBrokenDomainEvent.cs`** — record types in `Gamification.Domain/Events/`. Implement `IDomainEvent`. No handler this cycle.

### B. Application — command + handler (`P4-03-BE-3`)

1. **`AdvanceStreakCommand : ICommand<BaseResponse<Unit>>`** in `Gamification.Application/Features/Streaks/Commands/AdvanceStreak/`. Fields: `(int StudentId, Guid OriginEventId, DateTime OccurredAtUtc, int? LessonId, int? SkillId)`. Mirror `AwardLessonCompletedXpCommand`.
2. **`AdvanceStreakCommandValidator`** — non-zero `StudentId`, non-empty `OriginEventId` (cheap defense against malformed payloads even though sender is trusted).
3. **`AdvanceStreakCommandHandler`** steps:
   1. **Idempotency pre-check** — `await _repo.HasXpAwardAsync(request.OriginEventId, XpReason.StreakBonus, ct)`. If true, log "P4-03: duplicate StreakBonus event" and `return Success(Unit.Value)`. (Defense-in-depth alongside the date-based check below.)
   2. **Row-lock** — `await _repo.AcquireProfileLockAsync(request.StudentId, ct)`.
   3. **Compute day-bucket** — `var activityDate = StreakDayCalculator.DayOf(request.OccurredAtUtc, _options.TimeZoneId);` where `_options` is the bound `StreakOptions` (`TimeZoneId` defaulting to `"UTC"` — Q2). The calculator returns `DateOnly`. **Pure function — unit-tested in isolation.**
   4. **Load or create profile** — `var profile = await _repo.GetProfileByStudentIdAsync(request.StudentId, ct) ?? StudentXpProfile.CreateFor(request.StudentId);` + `_repo.UpsertXpProfile(profile);` to ensure tracking.
   5. **Branch on `profile.LastActivityDateUtc` vs `activityDate`:**
      - **Equal** (same day, redelivery or second lesson same day): log "P4-03: same-day activity — streak unchanged", **return Success(Unit.Value) WITHOUT awarding StreakBonus XP** (only first lesson of the day fires the bonus — see Q5).
      - **Null OR `activityDate == LastActivityDateUtc + 1 day`** (continue streak — first ever, or next consecutive day): `profile.AdvanceStreak(activityDate)`.
      - **`activityDate > LastActivityDateUtc + 1 day`** (gap > 1 day — broken): `profile.ResetStreakAndStart(activityDate)`.
      - **`activityDate < LastActivityDateUtc`** (out-of-order event, e.g. delayed publish from days ago): log warning "P4-03: out-of-order activity event ignored", **return Success(Unit.Value)** without changing state. Don't award XP either (event is stale).
   6. **Award StreakBonus XP** — `var bonusAmount = GamificationConstants.XpRewards.StreakBonus; var award = XpAward.Create(profile, XpReason.StreakBonus, bonusAmount, request.OriginEventId, request.OccurredAtUtc, request.LessonId, request.SkillId); await _repo.AddXpAwardAsync(award, ct);`
   7. **Recompute level** — `int newLevel = LevelCurve.LevelForXp(profile.TotalXp + bonusAmount); profile.ApplyAward(bonusAmount, newLevel);` (this also raises `StudentLeveledUpDomainEvent` if the +30 crosses a threshold).
   8. **Log** "P4-03: StreakAdvanced (studentId=X, currentStreak=Y, longestStreak=Z) — +30 XP awarded".
   9. **`return Success(Unit.Value)`.** The UoW commits everything atomically — streak update + XpAward + level update + after-commit dispatch of the two domain events.
4. **DbUpdateException catch** — same shape as `AwardLessonCompletedXpCommandHandler:126-133` for the idempotency-race defense.

### G. Hardening (do NOT skip)

- **Per-event idempotency** — defense-in-depth: (a) `HasXpAwardAsync(eventId, StreakBonus)` pre-check, (b) DB unique constraint on `(OriginEventId, StreakBonus)` already exists from P4-02's `UX_XpAwards_OriginEventId_Reason`, (c) date-based check (`LastActivityDateUtc == activityDate` short-circuits). Three layers.
- **Concurrency on a single student** — same `AcquireProfileLockAsync(studentId)` row-lock that P4-02 uses; two concurrent advances for the same student serialize on the profile row.
- **Out-of-order event delivery** — handler explicitly handles `activityDate < LastActivityDateUtc` (logs warning, returns Success without writing). Otherwise a delayed event would clobber a newer streak.
- **Sweep job idempotency** — the job's `BreakStreak()` is a no-op when `CurrentStreak == 0`, so re-running the job same-day is safe.
- **No `ex.Message` echoed** to clients.
- **Conventions:** module isolation, `ILoggerManager` only, `BaseResponse<T>`, `Successed`, no design pattern.

## Open questions / assumptions / risks

> Listed in priority order. Defaults are recommendations the lead can `APPROVE DEFAULTS` to greenlight.

**Top open questions (decision-shaping):**

**Q1 — Storage placement: extend `StudentXpProfile` vs. new entity `StudentStreakProfile`.**
- **Recommend extend `StudentXpProfile`.** Three columns added (`CurrentStreak`, `LongestStreak`, `LastActivityDateUtc`) — no new entity, no new FK, no new index, no duplicated `StudentId` row, single profile row per student matching the established pattern. The Gamification module owns one canonical per-student snapshot, and XP-bonus computation already touches that row anyway (StreakBonus writes a row to `XpAwards` AND updates `StudentXpProfile.TotalXp`).
- **Alternative — new `StudentStreakProfile` entity:** separate-of-concerns purity, but doubles the read path for the dashboard (two queries instead of one), doubles the row-lock requirement (two locks for streak-advance + XP write), and creates a "cousin" entity to `StudentXpProfile` that's always 1:1 anyway. Reject for P4-03.
- **Alternative — `StreakActivity` log table** (one row per activity-day): great for analytics but heavy for the hot path. Defer to P5-03 / analytics module.

**Q2 — Timezone for the day boundary.**
- **Recommend `UTC` as the configured default for P4-03**, with the calculator built TZ-aware so a future story can switch it to per-user when `User.TimeZoneId` is added (the field doesn't exist today — only `PreferredLanguage="ar-EG"` and `CountryCode="+20"` Egypt default).
- **Why UTC despite the Egypt-default audience:** simplicity. Per-user timezone would require (a) a new `User.TimeZoneId` column in Identity, (b) a cross-module read seam to fetch it from Gamification's handler, (c) test seeds for multiple TZs. This is real work the story didn't budget. Cairo (UTC+2 / UTC+3 DST) is 2-3 hours ahead of UTC, so a student studying late at night (00:00–03:00 Cairo) might find their "day" rolled over earlier than expected — annoying but not unfair, since the rule is the same for everyone.
- **Alternative — hard-code `Africa/Cairo`:** cleaner UX for the dominant audience but penalizes Gulf users (UTC+3/+4). Reject as a default but allow via config.
- **Alternative — per-user TZ:** ideal long-term, but introduces 3 new dependencies. Defer.

**Q3 — Sweep-job cadence + cron.**
- **Recommend `00:00 UTC daily`.** Lines up with the Q2 UTC default. Runs once per day, no concurrent-instance protection needed (single Hangfire server in MVP).
- **Alternative — `00:30 UTC` or `01:00 UTC`** to give late-night activity time to settle before the sweep fires. Marginal benefit.
- **Alternative — every 6 hours** as a more aggressive nudge cadence. Over-engineered for MVP.

**Q4 — Single command vs separate command from the notification handler.**
- **Recommend separate `AdvanceStreakCommand`** sent as a second `_mediator.Send` from the existing `LessonCompletedIntegrationEventHandler`. **Why separate:**
  1. Failure isolation — a streak crash doesn't roll back the XP award (each `Send` opens its own UoW transaction).
  2. Single-responsibility — `AwardLessonCompletedXpCommand` already does two things (LessonComplete +50 AND QuizPass +20). Adding a third (streak) bloats the handler.
  3. Future-friendly — if P4-04 (hearts) or P4-05 (badges) also want to react to `LessonCompletedIntegrationEvent`, they each get their own command path. The handler becomes a fan-out router.
- **Alternative — merge into `AwardLessonCompletedXpCommand`:** atomic semantics (one transaction), but couples streak failure to XP failure. Reject.

**Q5 — When does StreakBonus +30 fire?**
- **Recommend: every day the streak ADVANCES** — including day-1 (brand-new streak) AND day-N+1 (continuation). **NOT** on same-day repeat lessons (only the FIRST lesson of the day pays the bonus). **NOT** on streak-reset days (a fresh day-1 after a missed day still pays the bonus — the student showed up). **NOT** on sweep-job break (no XP for breaking; only on activity).
- **Rationale:** the bonus exists to reward the daily return — paying it on every advance day is the cleanest incentive. Paying it on threshold days only (e.g., every 7) over-engineers; FR-GM-1 says "streak bonus +30" without a qualifier.
- **Alternative — threshold days only** (every 7-day milestone): pairs with P4-05 badges; reject as P4-03 scope.

**Q6 — Does `AnswerSubmittedIntegrationEvent` advance the streak?**
- **Recommend NO.** Only `LessonCompletedIntegrationEvent` counts as "qualifying activity." Rationale: (a) story AC1 says "completing qualifying activity" — lesson completion is the natural unit; (b) every lesson generates many `AnswerSubmittedIntegrationEvent`s, so making each one a streak-advance candidate adds noise + race risk; (c) the bonus is tied to "coming back today and finishing a lesson" — finishing matters.
- **Alternative — any correct answer counts:** rewards short visits, but a child who submits one answer and bails is not really building a habit. Reject for MVP; revisit if BRD §3 metrics suggest otherwise.

**Q7 — Time-source seam for testability.**
- **Recommend introducing a tiny `ISystemClock`** (`UtcNow() : DateTime`) interface in `Shared.Kernel/Abstractions/` if it doesn't exist, injected into `StreakDayCalculator.Today(timeZoneId, clock)` and `StreakSweepJob`. Lets api-tests seed "today" deterministically without messing with the OS clock or Testcontainers.
- **Alternative — call `DateTime.UtcNow` directly** (P4-02's pattern): simpler but makes the date-based tests flaky around midnight. The seam is 30 lines of code.

**Q8 — Per-stack task file** for `tasks/Backend/Phase-3-Gamification/P4-03-BE.md`?
- **Recommend planner generates one** for traceability. Same gap P4-01 and P4-02 flagged.

**Q9 — Should we close out the story Notes' "open question"?**
- The story file says *"streak grace-period mechanics are unspecified (BRD §10) — confirm before finalizing reset rule."* SRS FR-GM-2 rider already closed this (no grace window — freeze in P4-11). Recommend the HANDOFF write-back also strikes through the story-file Note with a back-reference to FR-GM-2 + P4-11. This is housekeeping, not a blocker.

- A1: Extend `StudentXpProfile` with 3 streak columns (Q1).
- A2: UTC day-boundary with TZ-aware code path for future (Q2).
- A3: Sweep job at `00:00 UTC daily` (Q3).
- A4: Separate `AdvanceStreakCommand` (Q4).
- A5: StreakBonus +30 on every advance day, including reset day-1 (Q5).
- A6: Only `LessonCompletedIntegrationEvent` advances streak (Q6).
- A7: `ISystemClock` seam introduced (Q7).
- A8: No grace window (SRS FR-GM-2 rider closed BRD §10 #4).
- A9: No FE work this cycle (P4-08 owns the flame animation).
- A10: No new admin endpoint for manual streak grant/reset.
- A11: Per-user timezone deferred (no `User.TimeZoneId` field added).

**Risks:**

- **R1 (HIGH) — Date-vs-DateTime timezone bugs.** Storing `LastActivityDateUtc` as `date` but comparing against an event's `OccurredOnUtc` `DateTime` is exactly where bugs creep in. **Mitigation:** all date conversion goes through `StreakDayCalculator.DayOf(utc, tz)`, unit-tested at the boundaries (00:00, 23:59 in both UTC and target TZ). Don't sprinkle `.Date` calls.
- **R2 (HIGH) — Same-day double-advance.** Two consecutive lessons same day, each with a different `EventId`, would both increment the counter if the date-based check is wrong. **Mitigation:** the `LastActivityDateUtc == activityDate` branch returns `Success` BEFORE any write. **Gate AC1 with test case 3** (same-day repeat).
- **R3 (MED) — Out-of-order event delivery.** A delayed `LessonCompletedIntegrationEvent` arriving days later would either clobber a newer streak or break it. **Mitigation:** the `activityDate < LastActivityDateUtc` branch is a no-op. Test case 7.
- **R4 (MED) — Ghost streak on Learning rollback (R3 from P4-02).** Producer publishes inside Learning UoW. If Learning rolls back AFTER `Publish` succeeded, streak has already advanced for an attempt that never persisted. ADR 0002 §3 accepts this; the `OriginEventId` idempotency prevents *double* advance, but the **single** ghost advance is still there. Document, don't fix.
- **R5 (MED) — Sweep job missing a student.** If the job's worker is down at the scheduled time, broken streaks won't be flagged that day — students will see `CurrentStreak = 5` on the dashboard until they return. **Mitigation:** lazy break detection on next activity catches it (the handler's `gap > 1 day` branch resets). The job is observability/nudge-fuel only; correctness is preserved.
- **R6 (MED) — Sweep job perf at scale.** O(n) over `StudentXpProfile` with `CurrentStreak > 0` rows. At 100k actively-streaking students, fine. At 10M, needs batching + a partial index. **Mitigation:** batch `Take(500)` from the start; document the index opportunity in HANDOFF.
- **R7 (LOW) — Hangfire worker scope vs `_currentUser`.** The sweep job runs without an HTTP request scope; `ICurrentUserService.UserId` will be null. The audit-stamping behavior must handle null gracefully (P4-02 already verified this for `XpAward` writes from the event-handler scope; sweep is similar). Verify.
- **R8 (LOW) — `StreakAdvancedDomainEvent` defined but not consumed.** Same pattern as `StudentLeveledUpDomainEvent` in P4-02 (defined-without-consuming is fine; `IsolatedNotificationPublisher` tolerates no-handler). Confirmed safe.
- **R9 (LOW) — DateOnly + Npgsql.** `DateOnly` → PG `date` mapping works natively in Npgsql 8+. Verify the project's Npgsql version (P4-02 migration uses standard types, no DateOnly yet — this is the first one).
- **R10 (LOW) — Sweep job firing during deploy.** Hangfire's `RecurringJob.AddOrUpdate` is idempotent at startup; redeploys won't double-register. Test by stopping and restarting the host locally.
