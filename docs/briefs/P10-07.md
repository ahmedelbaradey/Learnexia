**Product-decision context:** parent-driven monetization — **purchase is parent-gated; children cannot purchase**. The pack is assigned to one child. Family-scope: a parent may only buy for their own children. No teacher role.

**Upstream dependencies:** **P10-01** (credit account/ledger — `PurchasedBalance` + `CreditTransaction` of type `Purchase`) and **P10-06** (reuses the `IPaymentProvider` checkout + webhook seam) — **both block P10-07**. **P10-11** (pack size/price config — 1000 credits / $5).

---

## Business context & value

- **Who benefits:** the **parent** (a child who ran out of monthly energy can keep using the Helper without upgrading the whole plan) and the **child** (uninterrupted AI help — though the child never sees the purchase; the out-of-energy state routes to "ask a parent" per P10-10).
- **Value:** a flexible, lower-commitment top-up that monetizes heavy users on the Free tier and gives Premium families a way past the monthly cap. **Never-expires** purchased credits is a **lead-confirmed** product promise — these credits persist across cycles (P10-01 keeps `PurchasedBalance` untouched at cycle rollover; P10-02 only expires `GrantedBalance`).
- **Success measured by:** successful purchase → 1000 credits in the chosen child's `PurchasedBalance` + a `Purchase` ledger row with the payment reference; failed payment → **no credits**; children cannot trigger a purchase.

---

## Acceptance criteria (testable)

1. A parent **buys a 1000-credit pack ($5)** via the payment provider (the P10-06 `IPaymentProvider` checkout — hosted/redirect, no card data on our servers) and **assigns it to a specific child**.
2. On a **successful payment**, 1000 credits land in that child's **`PurchasedBalance`** and **never expire** (untouched by the monthly grant/expiry cycle in P10-02).
3. The successful purchase is recorded as a **`Purchase`** `CreditTransaction` (P10-01) carrying the **payment reference** + idempotency key; the credit-add is **idempotent** (a replayed webhook does not double-credit).
4. A **failed payment grants no credits** and is surfaced as an error (handed to P10-09).
5. **Pack size (1000 credits / $5) and price are config-driven** (P10-11) — never hard-coded in the FE or handler.
6. **Children cannot purchase** — the purchase command is parent-gated (family-scope authz); the child app has no purchase surface (P10-10 is read-only).
7. The pack is assigned to a child the **purchasing parent actually owns** (family-scope check); buying for a non-owned child is rejected.

## Affected modules & data

### Module — `Billing` (schema `billing`) — same NEW module (lead sign-off)
- The purchase, payment, and credit-add all live in `Billing` (P10-01 placed the credit account/ledger in `Billing` per the cache-schema decision). The child is a **loose id** — no cross-module FK.
- **Atomicity note:** the credit-add (debit/credit + ledger row) is atomic via an **explicit transaction** (ADR 0001, per P10-01). Because the payment success arrives via the P10-06 **webhook**, the grant-on-success is part of the idempotent webhook handler.

### New / reused entities
- **Reuses** `Payment` (P10-06) with `Kind = Pack` and a `TargetChildId` (loose id) so the webhook handler knows which child to credit. *(Add `TargetChildId` + `Kind` to `Payment` if not already present from P10-06 — coordinate.)*
- **Reuses** `CreditAccount` + `CreditTransaction` (P10-01): on success, append a `Purchase` transaction to the target child's account, increment `PurchasedBalance` by the configured pack size.
- Possibly a thin **`PackPurchase`** projection/record if the planner wants pack purchases queryable separately from subscription payments — *optional; recommend reusing `Payment{Kind=Pack}` + the ledger `Purchase` row rather than a new table.* Confirm.

## Handoff → db-migration

- Likely **no net-new table** — extend `Payment` (P10-06) with `Kind` (`Subscription`/`Pack`) and `TargetChildId` (loose id, nullable; set for packs). Coordinate with the P10-06 migration.
- Ensure the **idempotency** anchor for the credit-add is the provider event / payment ref (so a replayed webhook does not double-credit) — reuse the `WebhookEvent`/idempotency mechanism from P10-06 and the `CreditTransaction.IdempotencyKey` from P10-01.
- Schema `billing`; no card columns; no cross-module FK to the child (loose id).

## Handoff → backend-feature

- **Command:** `StartPackCheckout(parentUserId, childId, packCode?)` — validates the parent owns `childId`, reads pack size/price from P10-11 config, creates `Payment{Kind=Pack, TargetChildId=childId, Status=Initiated}`, returns the P10-06 checkout redirect ref.
- **Webhook continuation:** extend the P10-06 `HandleProviderWebhook` handler — on a `Pack` payment success, **append a `Purchase` `CreditTransaction`** to the target child's `CreditAccount` and increment `PurchasedBalance` (atomic transaction), **idempotently** (dedup on provider event id; the `CreditTransaction.IdempotencyKey` guards double-credit). On failure → `PaymentFailed` (P10-09), no credit.
- **Reuse**, do not duplicate, the P10-06 `IPaymentProvider` seam. No new design pattern (CLAUDE.md rule 8) — same interface, same webhook handler with a `Kind` switch.
- **Authz:** `[Authorize]` + family-scope — only the owning parent; the command rejects non-owned children. **Children's JWTs must be rejected** (parent-only).
- **Crediting across the credit-core boundary:** if the credit account/ledger ends up in a different logical area than the payment handler, credit via `Shared.Contracts` (a `PackPurchased`/`CreditPurchased` integration event the credit-core consumes). Since P10-01 places the ledger in `Billing`, this may be an in-module call — confirm the boundary with the planner.
- Envelope `BaseResponse<T>`/`Successed`; `ILoggerManager`; commands auto-validated.

## Handoff → security-auditor (payment-sensitive)

- Same PCI / webhook-signature / idempotency / secrets concerns as P10-06 (it reuses that seam).
- **Extra focus:** **no double-credit** on webhook replay (the credit-add idempotency is the critical money-correctness invariant here); the **amount = configured pack price** (server-set, not client); **family-scope** — a parent cannot credit a child they don't own; **children cannot purchase** (parent-gated). Critical/High block the gate.

## Handoff → frontend + frontend-e2e-tester

- **No designer stage required** unless the planner wants one — this is a small parent-area flow that mirrors the P10-06 checkout. If a design spec is warranted, it's the **"Buy energy pack" sheet** (choose child + see 1000 credits / $5 + price → checkout).
- **Surface:** parent area — likely on the P5-05 parent dashboard (per-child) or the P2-12 plan/billing tab: a **"Buy energy pack" CTA → choose child → checkout redirect → success/fail return**. **Never on a child route.** P10-10 (child) shows only a read-only "ask a parent" prompt when out of energy.
- **Frontend:** `useStartPackCheckout(childId)`, return handler refreshing the child's energy/balance (truth via webhook → show "pending" until reconciled). Pack size/price from config. EN+AR, RTL.
- **frontend-e2e-tester:** parent web PWA — buy pack for child A (sandbox), success credits child A's purchased balance, failure credits nothing, cannot buy for a non-owned child, no purchase surface on any child route.

## Handoff → api-tester

- Cases: start pack checkout creates `Payment{Kind=Pack, TargetChildId}` + returns redirect; **webhook success** appends a `Purchase` transaction + increments `PurchasedBalance` by 1000 **once**; **duplicate webhook** does not double-credit; **failed payment** credits nothing (hands to P10-09); buying for a non-owned child is rejected; a child JWT is rejected; purchased credits **survive a simulated cycle rollover** (never expire) — coordinate with the P10-02 grant/expiry test; `BaseResponse<T>`/`Successed`.

## Open questions / assumptions / risks

1. **New `Billing` module** sign-off (shared with P10-05/06) — gate.
2. **Reuse `Payment{Kind=Pack}` vs a new `PackPurchase` table?** Recommend reuse + the `Purchase` ledger row. Confirm with planner.
3. **Where the credit-add happens** (in-module to the P10-01 ledger vs via a `Shared.Contracts` event) depends on whether the ledger and payment handler share the module. P10-01 places the ledger in `Billing`, so likely in-module — confirm.
4. **Pack assignment timing:** child is chosen **before** checkout (carried on `Payment.TargetChildId`) so the webhook knows whom to credit — confirm vs assigning after payment.
5. **Multiple packs / quantity:** is it always 1×1000 per checkout, or can a parent buy N packs at once? Assume 1 pack per checkout for v1. Confirm.
6. **Refund/clawback of an unspent pack** is owned by **P10-09** — P10-07 must record enough (payment ref + ledger `Purchase` row) for P10-09 to claw back unspent credits.
