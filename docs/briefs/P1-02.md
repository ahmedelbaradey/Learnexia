# Pipeline Brief — P1-02 (Backend) Stay signed in (token refresh & sign-out)

## Summary & traceability
- **Task (1 line):** Make the existing Identity refresh-token and sign-out endpoints actually work end-to-end — issue a valid new access token from a stored refresh token, revoke the session/refresh token on sign-out (Redis-backed), and return 401 for expired/revoked refresh tokens.
- **User story:** `user-stories/Phase-1-Foundation/P1-02-stay-signed-in.md` (SOURCE OF TRUTH)
- **Task file:** `tasks/Backend/Phase-1-Foundation/P1-02-BE.md` (BE-1, BE-2, BE-3)
- **FR-ID:** FR-ID-4 · **BRD goal:** G1 (engagement/retention — frictionless returning sessions) and trust/security on shared devices.
- **Phase / Epic:** Phase 1 — Foundation (Week 1–2) · Identity & Onboarding · SP 2.
- **Depends on:** P1-01 (register/sign-in — DONE, `Register-Parent`/`Sign-In` exist), P1-06 (Redis `IDistributedCache` — DONE, see Program.cs).
- **Wave:** runs in parallel with **P1-04** on the **shared Identity module** — see merge-overlap note at the end.

## Business context & value
- **Who benefits:** every signed-in user (parent and, later, child profiles operating under a parent). The parent stays logged in across visits without re-entering a password, and can deliberately end a session on a shared/family device.
- **Value:** reduces re-auth friction (retention) while giving a clean security boundary (sign-out really ends the session). This is foundational for all authenticated flows in later phases.
- **Success measure:** a returning client silently refreshes its access token; after sign-out the refresh token can no longer be exchanged and the session is gone from Redis.

## Current-state findings (verified in code — this is NOT just "verify + wire")
The endpoints and plumbing exist, but the refresh/sign-out flow is **functionally incomplete**. Net-new work is required, not only confirmation.

1. **Endpoints exist** — `AuthenticationController` (`backend/.../Identity.Api/Controllers/AuthenticationController.cs`):
   - `[AllowAnonymous] POST /api/Users/Authentication/Refresh-Token` → `RefreshTokenCommand` (AccessToken + RefreshToken).
   - `[Authorize] POST /api/Users/Authentication/Sign-Out` → `SignOutCommand` (empty body; identity from JWT).
   - Both return `BaseResponse<JwtAuthResponse>` / `BaseResponse<string>`.
2. **Sign-in never issues or persists a refresh token.** `AuthenticationIdentityService.GetJwtToken` returns access-token-only (`JwtAuthResponse { AccessToken = ... }`); `SignInCommandHandler` never sets `refreshToken` and never writes the `userrefreshtoken-{userId}` cache entry. `GenerateRefreshToken()` exists but is **never called**. The cache key `userrefreshtoken-{userId}` is **only ever read** (`GetById`), never written anywhere in the codebase.
3. **Refresh does not validate or rotate the token.** `GetRefreshToken(...)` mints a new access token but **echoes back the same refresh token** and **does not re-persist** it. `ValidateDetails(...)` reads `userrefreshtoken-{userId}` but (a) never compares the *supplied* `request.RefreshToken` string against the stored token, and (b) never returns the `"RefreshTokenIsExpired"` case the handler switches on — so an expired refresh token is not detected.
4. **Error mapping returns 500, not 401.** `RefreshTokenCommandHandler` maps `RefreshTokenNotFound` / `RefreshTokenIsExpired` / `TokenIsRunning` to `ServerError<>` (HTTP 500). AC-3 requires **401** for expired/revoked refresh.
5. **Sign-out terminates the wrong key + does not invalidate the access token.**
   - `SessionManagementService.CreateSessionAsync` stores the session under `session:{new GUID}` and returns that GUID as `SessionId`, while the JWT carries *two distinct* claims: `Jti` (used as `JwtTokenId`) and a separate `SessionId` GUID claim. `SignOutCommandHandler.GetCurrentSessionId()` reads the **`Jti`** claim and calls `TerminateSessionAsync(jti)` → looks up `session:{jti}`, which **does not exist** → termination silently fails (`LogWarn`). The session key, the `SessionId` claim, and the lookup key are three different values. **This mismatch must be reconciled.**
   - There is **no session-validation middleware** in the request pipeline (Program.cs has `AuthorizationLoggingMiddleware` only, then `UseAuthentication`/`UseAuthorization`). So even a correctly-terminated session/`UpdateSecurityStampAsync` does **not** invalidate an already-issued access token — the JWT stays valid until natural 30-min expiry. Decide and document the chosen invalidation model (see open questions).
6. **Token policy:** access-token 30 min is correct (`JwtSettings.AccessTokenExpireMinutes = 30`). Refresh expiry config is `RefreshTokenExpireDate = 7` (days) in appsettings, but `JwtSettings` exposes it as `RefreshTokenExpireDate` (int) and **nothing consumes it** when issuing a refresh token (because none is issued). The 7-day refresh window is currently unenforced.
7. **No db-migration needed.** The `UserRefreshToken` entity + `UserRefreshTokenConfig` + `InitialIdentity` migration already exist, but the refresh-token store in use is **Redis (`IDistributedCache`)**, not the EF table. Confirm with the lead whether refresh tokens should live in Redis (current direction, blacklist semantics in the story) or the existing table; either way **no new migration is expected**. (Flag if the decision lands on the EF table — that would add a migration.)

## Acceptance criteria (testable)
- **AC-1 (BE-1):** Given a valid (un-expired) refresh token issued at sign-in, when `POST /Refresh-Token` is called with the expired access token + that refresh token, then it returns 200 `BaseResponse<JwtAuthResponse>` with `Successed=true` and a **new, valid, non-empty** access token whose lifetime is ~30 min.
- **AC-2 (BE-1):** Sign-in (`/Sign-In`) and parent registration issue **and persist** a refresh token, returned on `JwtAuthResponse.refreshToken` (so the client has something to refresh with). *(This is the prerequisite the refresh flow currently lacks.)*
- **AC-3 (BE-2):** Given an authenticated user, when `POST /Sign-Out` is called (Bearer access token), then the user's session/refresh token is invalidated in Redis (cannot be exchanged again) and the response is 200 `Successed=true`. A subsequent `/Refresh-Token` with the same refresh token fails.
- **AC-4 (BE-3):** Given an expired OR revoked (signed-out) refresh token, `/Refresh-Token` fails with **HTTP 401** (not 500), `Successed=false`, prompting re-login.
- **AC-5 (BE-3):** Refresh-token exchange validates that the supplied refresh token **matches the stored one** for that user (no accepting an arbitrary string just because a cache entry exists).
- **AC-6:** Token policy confirmed and enforced: access 30 min, refresh 7 days; refresh token carries/honors its expiry.
- **AC-7 (validation):** Missing `AccessToken` or `RefreshToken` → 422 with `Errors[]` (existing `RefreshTokenValidatior`, confirm it still fires via `ValidationBehavior` for `ICommand<>`).
- **AC-8 (security):** Refresh token is high-entropy and rotated on use (old one no longer valid after a successful refresh) — recommended; confirm scope with lead (see open questions).

## Affected modules & data
- **Module:** Identity only. No cross-module contract changes.
- **Entities:** no new entities. `UserRefreshToken` (EF table, `identity` schema) already exists but is **not** the active store; refresh tokens + sessions live in Redis via `IDistributedCache`. **No new migration expected.**
- **Redis keys in play:** `userrefreshtoken-{userId}` (refresh-token store, currently write-missing), `session:{sessionId}`, `user_sessions:{userId}`, `activity:{sessionId}` (SessionManagementService).

## Handoff → backend-feature
Primary surface = `AuthenticationIdentityService` + the two command handlers + `SignInCommandHandler`. Concretely:
- **Issue + persist refresh token at sign-in/registration (AC-2):** in the sign-in path, generate a refresh token (use the existing `GenerateRefreshToken()` CSPRNG helper), persist it to Redis under `userrefreshtoken-{userId}` with the 7-day expiry, and return it on `JwtAuthResponse.refreshToken`. Apply the same to `RegisterParentCommandHandler` if that path should yield a refresh token (confirm — see open questions).
- **Refresh validation (AC-1, AC-4, AC-5):** in `ValidateDetails`, after loading the stored token, (a) compare the supplied `request.RefreshToken` to the stored value; (b) check stored `ExpiryDate` and return the `"RefreshTokenIsExpired"` sentinel when past; (c) keep the `"TokenIsRunning"` guard (access token not yet expired). Note: `UserRefreshToken` model stored in cache uses `ExpiryDate`; the read in `ValidateDetails` returns `userRefreshtoken.ExpiryDate`.
- **Error → 401 mapping (AC-4):** change `RefreshTokenCommandHandler` so `RefreshTokenNotFound` / `RefreshTokenIsExpired` map to `Unauthorized<JwtAuthResponse>(...)` (HTTP 401), not `ServerError`. (`BaseResponseHandler` provides `Unauthorized<T>()` — confirm name in `Shared.Kernel.Responses`.)
- **Rotation (AC-8):** on successful refresh, write a new refresh token to `userrefreshtoken-{userId}` (replacing the old) and return it; mark/replace so the old token cannot be reused.
- **Sign-out invalidation (AC-3):** reconcile the session-key mismatch — terminate the session under the key that was actually stored at sign-in. Options to confirm with lead: (i) terminate by the `SessionId` claim (the GUID that was the storage key) instead of `Jti`; or (ii) delete the `userrefreshtoken-{userId}` cache entry directly so the refresh token can no longer be exchanged (this is the most direct way to satisfy "refresh token is invalidated"). Removing the refresh-token cache entry is the minimal change that makes AC-3 testable; session termination is complementary.
- **Conventions:** handlers stay `BaseResponseHandler` + `ICommandHandler<>`; return `BaseResponse<T>`; success flag spelled `Successed`; inject `ILoggerManager`; commands auto-validated by `ValidationBehavior`. Mirror Catalog patterns.
- **DTOs/contract for FE (P1-02-FE):** `Refresh-Token` request `{ accessToken, refreshToken }` → `BaseResponse<JwtAuthResponse>` with new `accessToken` (+ rotated `refreshToken`). `Sign-Out` requires Bearer access token, empty body, returns `BaseResponse<string>`.

## Open questions / assumptions / risks
1. **Refresh-token store: Redis vs EF table?** Code direction = Redis (`userrefreshtoken-{userId}`), story says "Redis blacklist". The `UserRefreshToken` EF table + migration exist but are unused for this flow. **Confirm Redis is authoritative** (assumption: yes; if so, no migration). RISK: leaving a dead EF table is confusing — flag for cleanup, do not delete in this story.
2. **Access-token invalidation on sign-out.** There is no per-request session-validation middleware, so a signed-out user's *existing* access token remains valid until 30-min expiry. Is "invalidate the refresh token so it can't be re-exchanged" sufficient for AC-3 (assumption: **yes**, given the 30-min access TTL and the story wording), or must we also add a session/JTI denylist middleware to kill the live access token immediately? The latter is a larger change — recommend deferring unless the lead/security says otherwise.
3. **Refresh-token rotation (AC-8).** Story doesn't explicitly require rotation. Recommend rotating on each refresh (security best practice). Confirm scope.
4. **"Remember me" / persistent session.** The story title says "stay signed in" but there is **no remember-me flag** in `SignInCommand` and no AC for it. Assumption: out of scope (the 7-day refresh window IS the persistence mechanism). Confirm.
5. **Does parent registration issue a refresh token?** `RegisterParentCommandHandler` currently returns a `JwtAuthResponse` (auto-login). If sign-in is changed to issue refresh tokens, decide whether registration should too (assumption: yes, for consistency).
6. **Sign-out session-key bug** (Jti vs SessionId vs storage GUID) is pre-existing and shared with P1-04's session concerns — coordinate so both stories don't fix it divergently.
