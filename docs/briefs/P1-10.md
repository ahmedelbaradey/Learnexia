# Pipeline Brief — P1-10 Sign in to the admin dashboard

> Canonical brief. **Supersedes** the earlier `docs/briefs/P1-10-admin-sign-in.md` (that file was a draft, tracked only in the main repo and not present in this worktree). Treat this file as the source brief for the pipeline; the old slug may be deleted.

## Summary & traceability
- **Task (one line):** Stand up the Next.js `admin-dashboard` app shell, an admin sign-in screen, an authenticated dashboard shell with placeholder nav, admin-only route protection, and sign-out — reusing the existing Identity API + shared FE packages. Auth + shell only, **no admin feature logic**.
- **User story:** `user-stories/Phase-1-Foundation/P1-10-admin-sign-in.md` (SP 3, Epic: Identity & Onboarding).
- **Task files:** `tasks/Frontend/admin-dashboard/Phase-1-Foundation/P1-10-FE.md` (FE-1..FE-5) and `tasks/Backend/Phase-1-Foundation/P1-10-BE.md` (BE-1..BE-4).
- **FR-IDs / SRS:** SRS §3 (Admin role), FR-ID-1 (sign-in), FR-ID-4 (session/refresh), NFR-4 (security).
- **BRD goal:** supports platform operations/content governance (admin can later manage curriculum/content); enables G-level content delivery indirectly. This story itself is enablement (access + shell), not a learner-facing goal.
- **Phase / sprint:** Phase 1 — Foundation (Week 1–2). Wave 4 branch context (`feat/P1-10-admin-signin` off `feat/wave-4`).
- **Product overrides honored:** no public admin self-registration (seed/invite only); no teacher role.

## Business context & value
- **Who benefits:** Admin / SuperAdmin staff (the only roles that should reach the dashboard).
- **Value:** establishes the secure entry point and shell for all future admin features (curriculum upload/structuring, content moderation — Backlog BL-01..BL-05, Phase 2+). Without it, none of those features have a home.
- **Success measured by:** an admin can sign in and land on the shell; a non-admin (parent/student/unauthenticated) is denied; session refresh + sign-out work; the shell renders nav placeholders with zero feature logic.

## Acceptance criteria (testable)
1. Visiting any admin route while unauthenticated redirects to `/login` (no protected content flashes).
2. Signing in with valid **admin/superadmin** credentials issues a JWT, persists it, and lands the user on the dashboard shell.
3. Signing in with valid **non-admin** credentials (parent/student) is denied access to admin routes — redirected to login or shown a 403/"not authorized" state; they never see the shell.
4. The admin app exposes **only a Login page** for entry — there is no admin self-registration UI or route.
5. The authenticated dashboard shell renders authenticated chrome: top bar + side nav with **placeholder** entries for later features (e.g. Curriculum, Content), and a visible signed-in identity. No feature data is fetched/rendered.
6. Sign-out clears tokens and returns the user to `/login`; a subsequent protected-route visit redirects to login.
7. Session refresh works for admins (a 401 triggers the api-client single-flight refresh; on refresh failure the user is signed out).
8. Backend: the AdminOnly policy denies non-admin principals with 403 on any endpoint that carries it (already true; verified, not changed).
9. Build/lint/type-check pass for the new app and it consumes the shared packages via workspace aliases (no duplicated client/auth logic).

## Affected modules & data
- **Frontend (net-new):** `apps/admin-dashboard` — currently a **bare stub** (`package.json` only: `@learnexia/admin-dashboard`, private, no Next app, no `@tamagui/next-plugin` wiring). The entire Next.js 15 App Router shell is built here.
- **Frontend (reused, no change expected):**
  - `packages/api-client` — `useSignIn` (POST `/api/Users/Authentication/Sign-In`, `skipAuth`), `useUserProfile`/`useCurrentUser` (GET `/api/Users/UserManagement/GetUserProfile`), `ApiClient` (envelope unwrap, JWT attach, single-flight 401 refresh, sign-out hook), `ApiClientProvider`.
  - `packages/shared` — `useAuthStore` (Zustand), `TokenStorage` abstraction + `createWebTokenStorage` (sessionStorage default; cookie proxy available), `ROLES` (lowercase string values; admin role token Name is PascalCase `Admin`/`SuperAdmin`), `Role`/`CurrentUser`/`JwtAuthResponse` types.
  - `packages/design-system` (Tamagui config — loaded into Next via `@tamagui/next-plugin`), `packages/ui` (Button/Card; note many `ui` components are RN-only with native peer deps — use web-safe primitives in the admin app).
- **Backend (no data changes; verification + tiny seed only):** Identity module. **No new entities, no migration.**
  - `AuthenticationController`: `Sign-In`, `Refresh-Token` (`[AllowAnonymous]`), `Sign-Out` (`[Authorize]`) — all already exist.
  - `AdminOnly` policy (`AuthorizationPolicies.AdminOnly`) = `RequireRole("Admin","SuperAdmin")` — already registered in Identity Infrastructure DI.
  - `RoleSeeder` seeds `Admin` + `SuperAdmin` (self-heals casing to PascalCase). `UserSeeder.SeedSuperAdminAsync` already seeds a `superadmin` user holding **Admin + SuperAdmin** roles (default password `123Pa$$word!`). Invoked from `Program.cs` via `IdentityModule.SeedAsync`.

## Handoff → db-migration
- **None.** No new entities/fields/relationships. No EF migration in this story. (If the team decides to seed a dedicated standalone `admin` user separate from `superadmin` — see Open Questions — that is a seeder data change, still **not** a schema migration.)

## Handoff → backend-feature (likely MINIMAL / verification-only)
The BE is essentially **pure reuse**. Confirm and, only if a gap is found, close it:
- **BE-1 (seed):** An admin-capable account already exists (`superadmin` holds `Admin`+`SuperAdmin`). Decide whether to also seed a dedicated `admin`-only user for the dashboard demo/QA. If yes: add an idempotent `SeedAdminAsync` in `UserSeeder` (mirror `SeedSuperAdminAsync`, role = `Admin` only), call it from `IdentitySeeder.SeedAsync`. Keep it idempotent (find-by-email guard). **No public registration path.**
- **BE-2 (sign-in):** No change — `POST /api/Users/Authentication/Sign-In` returns `BaseResponse<JwtAuthResponse>` and the JWT carries role claims. Verify the seeded admin can sign in and the token includes `Admin`/`SuperAdmin` role claims.
- **BE-3 (authz):** No change — `AdminOnly` already returns 403 for non-admins. (There are currently no admin-only endpoints in this story; the policy will gate future admin feature endpoints. Optionally add a trivial `[Authorize(AdminOnly)]` ping endpoint if the FE needs a server-side admin check beyond the role-from-profile gate — see Open Questions.)
- **BE-4 (role for gating):** **Important contract detail** — `JwtAuthResponse` does **NOT** contain roles. It returns `accessToken`, `refreshToken`, `userId`, `isFirstLogin`, `sessionTimeout`, `sessionId`. The FE obtains the role list by calling `GET /api/Users/UserManagement/GetUserProfile?userId={userId}` → `UserProfileResponseDto` which includes `Roles: string[]`. Confirm this endpoint returns the admin's roles (it maps via `AuthorizationService.GetUsersRoles`). Role strings are PascalCase (`Admin`, `SuperAdmin`).
- **api-tester:** Only needed **if a BE endpoint is added/changed** (e.g. a new admin-only ping endpoint or a new seed that affects an integration test). If BE is verification-only, no new api-tester run is required beyond confirming existing P1-02/P1-05 tests still pass. Existing coverage: `P1_02_RefreshAndSignOut_Tests.cs`, `P1_05_RBAC_Tests.cs`.

## Handoff → frontend (Next.js 15 — has UI surface → designer required)
**App scaffold (FE-1):**
- Build `apps/admin-dashboard` as Next.js 15 App Router + `@tamagui/next-plugin`, consuming `@learnexia/design-system` config. Add `next.config.*` with the Tamagui plugin, `tamagui.config` re-export, an `app/` tree, root layout, providers (`TamaguiProvider` with the design-system config, `QueryClientProvider`, `ApiClientProvider`, theme/RTL provider).
- Wire the api-client: build the `ApiClient` with `baseUrl` (env), `tokenStorage = createWebTokenStorage()` (sessionStorage; or cookie proxy if cookie-auth is chosen — see Open Questions), and `onSignOut` → `useAuthStore.signOut()`. Call `authStore.setStorage(createWebTokenStorage())` + `hydrate()` at startup.

**Login (FE-2):** `app/login/page.tsx`
- Form (react-hook-form + zod) → `useSignIn({ userName, password })`.
- On success: persist via `authStore.setTokens({ accessToken, refreshToken: refreshToken.tokenString })`, then fetch profile via `useUserProfile(userId)` to read `Roles`, set `authStore.setUser(...)`, and redirect to the dashboard.
- **Gate at login too:** if the signed-in user's roles do not include `Admin`/`SuperAdmin`, do not enter the shell — sign out and show a "not authorized" message (covers AC #3 for a non-admin who has valid creds).
- No registration link/route.

**Dashboard shell (FE-3):** `app/(admin)/layout.tsx` + `AdminShell`
- Authenticated chrome: side nav with placeholder items (Curriculum, Content — non-functional), top bar with signed-in identity + sign-out. No feature data.

**Route guard (FE-4):** `middleware.ts` + `useAdminGuard`
- Unauthenticated or non-admin → redirect to `/login`. Gate on roles from the profile (`Roles` includes `Admin`/`SuperAdmin`). NOTE: with sessionStorage tokens, Next.js `middleware.ts` (server edge) cannot read the token — the guard is effectively **client-side** (a layout/hook check). If true server-side route protection is required, cookie-based auth is needed (Open Question). Designer + frontend should align on whether the guard is client-only for this story.

**Session/sign-out (FE-5):** `useSignOut`
- Call `POST /api/Users/Authentication/Sign-Out` (Authorize) then `authStore.signOut()` (clears storage) and redirect to `/login`. Refresh is automatic via the api-client interceptor.

**API shapes (verified against code):**
- Sign-In: `POST /api/Users/Authentication/Sign-In` body `{ userName, password }` → `BaseResponse<JwtAuthResponse>` (client unwraps to `JwtAuthResponse`: `accessToken`, `refreshToken: { tokenString, expireAt, userName }`, `userId`, `isFirstLogin`, `sessionTimeout`, `sessionId`). **No roles in this payload.**
- Profile/role: `GET /api/Users/UserManagement/GetUserProfile?userId={userId}` → `UserProfileResponseDto` with `Roles: string[]` (PascalCase).
- Refresh: `POST /api/Users/Authentication/Refresh-Token` body `{ accessToken, refreshToken }` (handled inside the client).
- Sign-Out: `POST /api/Users/Authentication/Sign-Out` (Authorize).

**Designer handoff:** UI surface = Login page + authenticated dashboard shell (top bar, side nav with placeholders, signed-in identity, sign-out, "not authorized" state, loading/redirect states). Ground in `design-system/` tokens (dark palette, Poppins/Cairo). This is a data-dense Next.js surface (admin), not the gamified student look — keep it clean/professional. Designer produces `design-system/ui_kits/admin-dashboard/P1-10.md` before the frontend batch.

## Open questions / assumptions / risks
1. **Token storage on web — sessionStorage vs HttpOnly cookie.** Default shared web storage is `sessionStorage`, which means `middleware.ts` cannot enforce auth server-side (guard is client-only). Cookie auth would enable real server-side protection but requires a backend cookie path **not in scope**. **Recommend:** confirm with the lead — for this story, accept a client-side guard with sessionStorage (documented), or escalate cookie-auth as a follow-up. Security-auditor should weigh in.
2. **Dedicated `admin` user vs reuse `superadmin`.** `superadmin` already satisfies AdminOnly. Is a separate `admin`-only seeded account needed for the dashboard (BE-1)? **Assumption:** reuse `superadmin` unless the lead wants a distinct `admin` demo account. Either way, default seed password `123Pa$$word!` must be changeable / not used in production — flag for security-auditor and ops.
3. **Server-side admin check endpoint.** The role gate relies on `GetUserProfile` returning `Roles`. Is a dedicated `/me`-style or admin-ping endpoint wanted, or is profile-based gating sufficient? **Assumption:** profile-based gating is sufficient for this story; no new endpoint.
4. **`packages/ui` web compatibility.** Several `ui` components declare native peer deps (reanimated/skia/moti). The admin app must only import web-safe primitives (Button/Card) or design-system primitives directly to avoid pulling native deps into the Next build. **Risk:** Tamagui + Next plugin setup is the steepest part of the stack (per FRONTEND_ARCHITECTURE §9) — budget time.
5. **Role string casing.** Shared `ROLES` constants are lowercase (`admin`), but the JWT/profile role Names are PascalCase (`Admin`, `SuperAdmin`). FE gate must compare case-insensitively or against the PascalCase values. **Flag for frontend.**
6. **Locale/RTL for admin.** Default app locale is Arabic (RTL). Confirm whether the admin dashboard ships ar/en + RTL in this story or English-only for v1. **Assumption:** wire the providers but admin can default to English; confirm with lead.
