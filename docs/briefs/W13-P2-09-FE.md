## Business context & value
- **Who benefits:** the **student** — opens the app → sees their progress at a glance + one obvious "Continue" → taps it → lands inside the same lesson player W12 shipped. This is the final missing link in the Phase 2 daily-use loop: register/login (P1) → home (P2-09) → subjects/units (P2-02) → skill tree (P2-03) → lesson + quiz + feedback (P2-05/06/07).
- **Why it matters now:** without a home dashboard, a returning child lands on a flat subjects list with no "what should I do next?" cue. Pre-Phase-4 the dashboard's *real* job is the **Continue Card** — XP / Streak / Mission / League are forward-looking stubs ensuring the FE contract doesn't churn when Phase 4 turns them on.
- **Why stubs instead of "Coming soon":** Phase 4 ships into the established contract. If the dashboard renders zero XP and a flame-with-`0`-day-streak today, Phase 4 only changes the numbers — no component swap, no contract regen, no migration trap. Mirrors the BE decision (P2-09 BE: `xp:0, streak:0, dailyMission:null, leaguePreview:null`).
- **Success measure:** an authenticated child sees the dashboard within 1s of nav; the Continue Card resolves to a valid in-progress or next-Available lesson (or hides cleanly when there is none); tapping it lands in the W12 lesson player on the right `lessonId`; the Subjects section underneath still works exactly as it does today; renders cleanly in EN LTR and AR RTL.

## Hooks to add to `@learnexia/api-client`

### `useDashboard()` — new
```ts
// packages/api-client/src/hooks/useDashboard.ts
import { useQuery, type UseQueryResult } from '@tanstack/react-query';
import { useTypedClient } from './apiClientContext';
import { unwrapEnvelope } from '../client/typedClient';
import { queryKeys } from '../query/queryKeys';
import type { UseApiQueryOptions } from './useApiQuery';
import type { DashboardDto } from '../schemas';

/** GET /api/Learning/Dashboard — [Authorize], per-student via JWT (no studentId param).
 *  Phase-2 contract: xp=0, streak=0, dailyMission=null, leaguePreview=null; continue is real. */
export function useDashboard(
  options?: UseApiQueryOptions<DashboardDto>,
): UseQueryResult<DashboardDto, Error> {
  const client = useTypedClient();
  return useQuery<DashboardDto, Error, DashboardDto>({
    ...options,
    queryKey: queryKeys.learning.dashboard(),
    queryFn: () => unwrapEnvelope(client.dashboard()) as Promise<DashboardDto>,
  });
}
```
- Exported from `packages/api-client/src/hooks/index.ts`.
- `DashboardDto` (+ `ContinueTargetDto`, `DailyMissionDto`, `LeaguePreviewDto`) re-exported from `packages/api-client/src/schemas.ts`.
- `queryKeys.learning.dashboard()` already exists — reused.

### No additional hooks for the Continue Card
Best-guess in the W13 prompt was to compose Continue from `useStudentAttempts` — **rejected**: that endpoint is untyped today (same `Promise<void>` issue) AND the BE dashboard endpoint already does the Continue resolution server-side (most-recent-Attempt subject → engine → first Available lesson → cross-subject fallback). FE wins by **reading `dashboardQuery.data.continue` directly** — fewer hooks, fewer races, no client-side Continue heuristic to maintain alongside the server's.

export default function ChildHomeScreen() {
  const meQuery = useMe();

  return (
    <Screen>
      <HeaderBar onSignOut={...} />          {/* preserves W11 sign-out */}
      <DashboardHeader
        childName={childName}
        grade={grade}
        hearts={3}                            // TODO P4-05

        weeklyXpTarget={100}                  // TODO P4-02

      />

        <ContinueCard
          subjectName={continueTarget.subjectName}
          subjectKey={resolveSubjectKey(continueTarget.subjectName) ?? 'math'}
          lessonName={continueTarget.lessonName}
          unitName={continueTarget.unitName ?? undefined}
          skillName={continueTarget.skillName ?? undefined}

## Open questions + best-guess answers (planner adopts unless lead overrides)

### Q1 — Single dashboard endpoint or compose from multiple hooks?
**Best-guess answer:** **Single endpoint** (`useDashboard`). The BE already does the Continue resolution server-side and returns all 5 widget fields in one envelope. Composing client-side would (a) require fixing the untyped `attempts(studentId)` client (out of scope here), (b) duplicate the Continue heuristic, (c) introduce a multi-query race for nothing. Original W13-prompt's "compose from `useSubjectsForGrade` + `useStudentAttempts`" suggestion is rejected on those grounds — keep `useSubjectsForGrade` for the Subjects section only.

### Q2 — Where does the greeting source come from?
**Best-guess answer:** `useMe().data.fullName.split(/\s+/)[0]` (first token of full name) + `useMe().data.grade` for the optional grade caption. Mirrors W11. Fallback to empty string if missing (no awkward "Hi, !").

### Q3 — How to pick "last attempt" for the Continue Card?
**Best-guess answer:** **No FE work — the BE already picks it** (most-recent-Attempt subject → engine → first Available lesson; cross-subject fallback Math/Science/Arabic/English; Grade-1 Math for net-new students). FE reads `dashboardQuery.data.continue` directly. If `null` → hide the card. The W13-prompt's suggestion to "filter `useStudentAttempts` for `status:'InProgress'`, sort by `startedAt` desc, take first" is rejected — duplicates BE logic + needs the untyped attempts endpoint fixed first.

### Q4 — Subjects list section header copy?
**Best-guess answer:** `child.home.subjectsHeading` → EN `"Your subjects"` / AR `"موادك"`. (W13-prompt's suggestion adopted verbatim.)

### Q5 — Should we render a "Nothing in progress yet — pick a subject" placeholder when `continue === null`?
**Best-guess answer:** **No — hide the Continue Card cleanly.** Reasoning: in Phase 2 `continue` is almost always non-null because the BE falls back to Grade-1 Math for net-new students. `null` only happens when there's literally no Available lesson anywhere (degenerate seed). The Subjects section below already gives the user a CTA. **Lead can override** if user-research-style empty states are preferred.

### Q6 — Are we shipping the `MissionBanner` primitive even though it's never rendered in W13?
**Best-guess answer:** **Yes** — designer captures the AR "مهمة اليوم" tile spec while in the file, primitive is small, P4-06 picks it up unchanged. Alternative is to defer to P4-06; recommend ship. **Lead's call** — both are reasonable; defaulting to ship.

### Q7 — Should the Continue Card show a progress percent / progress bar?
**Best-guess answer:** **No in W13.** `ContinueTargetDto` doesn't expose progress (BE only returns the next-Available lesson + identity). Phase 3 adaptive (`P3-08`) introduces per-attempt progress aggregation. Primitive accepts an optional `progressPercent` prop wired up later.

### Q8 — Hearts widget — render zero or hard-code 3?
**Best-guess answer:** **Hard-code 3** (matches W12 lesson intro precedent). Rendering `0` would imply game-over and is hostile UX while Hearts isn't a real concept yet. TODO P4-05.

### Q9 — Should the Continue Card carry the Boss flag visually?
**Best-guess answer:** **Yes** — BE returns `isBoss` on `ContinueTargetDto` (P2-03 boss patch). Render with the `Badge variant="boss"` (already in `@learnexia/ui` from W11). Kid-friendly + factually accurate.

### Q10 — Locale / RTL parity with the AR screenshots?
**Best-guess answer:** Designer's spec must reconcile the EN + 2 AR captures explicitly (the AR captures show forward-looking Phase-4 chrome that's NOT shipping). Frontend then implements against the designer's reconciled spec, not the screenshots directly. RTL pattern: logical props (`rowDir` flip), `writingDirection={direction}`, no `marginLeft`/`marginRight`.

### Q11 — Worktree / branch name?
**Best-guess answer:** `feat/W13-P2-09-FE-home-dashboard` (per HANDOFF wave-naming convention). Off `main` (W12 will merge first; if not, off `feat/W12-...`).
