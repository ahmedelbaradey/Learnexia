## Business context & value
- **Who benefits:** the **student** directly — every answer gets a confirming/corrective beat without a reload, which is the Phase-2 engagement contract. The **gamification engine** (Phase 4) and **analytics engine** (Phase 5) start receiving the event signal they were designed to consume. The **adaptivity engine** (Phase 3) starts seeing answer-level signal too.
- **Why it matters now:** P2-08 shipped the persistence + state machine but left the public response unrefined (no per-type correctness) and the event un-published. **Until P2-07 lands, P4-02..P4-07 + P5-03 + P3-08/P3-09 cannot meaningfully subscribe** — they would build against an event that's never raised. This story is small in code but high in unblock value.
- **Success measure:** (a) every successful `SubmitAnswer` for an answer whose question has a non-null `SkillId` emits exactly one `AnswerSubmittedIntegrationEvent` after persistence; (b) every successful `CompleteAttempt` emits exactly one `LessonCompletedIntegrationEvent`; (c) the `SubmitAnswerResponse` carries authoritative per-type correctness; (d) no event leaks on failure paths (cross-lesson / duplicate / non-InProgress / non-owner / 5xx); (e) tests prove handler isolation (one failing downstream subscriber does not fail the API response). Validated by `api-tester` + targeted unit tests.

## Acceptance criteria (verbatim from story + testable)
1. **Correct → positive confirmation, recorded as correct.** Server: `SubmitAnswer` returns `{ isCorrect: true, correctAnswer: null, hintAvailable: <see Q3> }` and the persisted `StudentAnswer.IsCorrect = true`. (P2-08 baseline satisfies — P2-07 inherits, but per-type comparator must not regress.)
2. **Wrong → correct/wrong screen with hint affordance.** Server: `{ isCorrect: false, correctAnswer: "<value>", hintAvailable: <see Q3> }` and persisted `StudentAnswer.IsCorrect = false`. Heart loss is **Phase 4** (downstream subscriber consumes the event — out of scope here).
3. **Same-screen feedback (no reload).** Server responsibility: synchronous response on the same `POST` (already true in P2-08). No new contract.
4. **Result of each answer persisted for later analytics.** P2-08 satisfies persistence; P2-07 extends by **publishing** `AnswerSubmittedIntegrationEvent` (per task BE-3) so downstream analytics can consume in real time. AND `LessonCompletedIntegrationEvent` on attempt completion (the parallel TODO left by P2-08).

### A. Per-type correctness comparator (BE-1, ties to Q1)
Add a static helper `AnswerComparator.AreEqual(QuestionType, string studentPayload, string correctAnswer)` in `…/Application/Features/Attempts/Services/`. Plain `switch` on `QuestionType` — **no Strategy/Factory pattern** (CLAUDE.md rule 8; mirror `QuizQuestionTypeValidation.cs` shape). Per-type rules (recommended; confirm via Q1):
- **MCQ:** trim both, `OrdinalIgnoreCase` equality on the stored option-string value (current baseline — keep).
- **TrueFalse:** parse both as `bool` (case-insensitive `"true"`/`"false"`) and compare; reject malformed payload by returning `false` (the validator already accepts only non-empty string answer payloads).
- **FillInBlank:** trim + `OrdinalIgnoreCase`; **do NOT** implement multi-acceptable-answer semantics this cycle (`CorrectAnswer` is a single string per current schema — Q1).
- **Matching:** parse both as JSON `[{"left":"...","right":"..."}]` (or whatever shape the FE will send — confirm in Q1.b); order-independent pair-set equality (e.g. canonicalize both lists by sorted `left` and compare). **If FE contract not yet defined, defer Matching to fall through to current OrdinalIgnoreCase string compare with a `// TODO P2-07-matching-shape-tbd` comment.**

Replace lines 95–98 of `SubmitAnswerCommandHandler` with the call. Unit-test the comparator directly (one test per type, happy + wrong + malformed-payload).

### B. Publish `AnswerSubmittedIntegrationEvent` (BE-3, ties to Q5, Q6, Q8, Q9)
Insert publication **after** `await _repository.Learning.AddAsync(studentAnswer, cancellationToken)` and **before** `var response = new SubmitAnswerResponse {...}` (replacing the TODO at line 106).

**Recommended pattern (defaults — confirm via Q5):** raise the event AS a domain event on the `Attempt` aggregate so the `UnitOfWorkBehavior` dispatches it strictly after `CommitAsync`. Two sub-options:
- **Option A (recommended):** create a thin `Learning.Domain.Events.AnswerSubmittedDomainEvent` that wraps the integration event shape; have `Attempt.RaiseAnswerSubmitted(...)` produce it; have an internal `INotificationHandler<AnswerSubmittedDomainEvent>` in `Learning.Application` that converts → `IPublisher.Publish(new AnswerSubmittedIntegrationEvent(...))`. This keeps the integration event publish strictly **after commit** (no "ghost event on rollback" risk per Q9).
- **Option B (matches existing Identity pattern):** inject `MediatR.IPublisher` directly into `SubmitAnswerCommandHandler` and `await _publisher.Publish(new AnswerSubmittedIntegrationEvent(...), ct)` inside a try/catch. Fires BEFORE commit (inside UoW's `next()`); rollback risk is non-zero but matches what RegisterParent/AddUser/GoogleSignIn already do today. **Smaller diff, less new surface.**

**`SkillId` nullability** (Q6 — must resolve before BE writes): the event record requires `int SkillId`, but `QuizQuestion.SkillId` is `int?`. **Recommended default: skip publication when `SkillId is null`, log an info line `"Skipping AnswerSubmittedIntegrationEvent — question {QuestionId} has no SkillId"`, and add `// TODO P3-09: track no-skill answers separately`.** Do NOT publish `SkillId = 0` (silent corruption of any downstream "skill mastery" aggregate).

**Idempotency / failure-path guard (Q8):** publication MUST happen only on the success path. With Option A this is automatic (the UoW dispatches only after commit). With Option B the publish call sits after the `AddAsync` and before `return Success(...)` — outside the catch — and the early `return Unauthorized/NotFound/BusinessValidation` paths (duplicate question, cross-lesson, not-InProgress, not-owner) all return before reaching it. Add an explicit unit/integration test asserting "duplicate `(AttemptId, QuestionId)` rejection emits no event."

### C. Publish `LessonCompletedIntegrationEvent` (Q7)
Same pattern choice as B, applied to `CompleteAttemptCommandHandler.cs` line 111 (after `await _repository.Learning.UpdateAsync(attempt)`). Build the event from the recomputed aggregates:
- `EventId = Guid.NewGuid()`, `OccurredOnUtc = DateTime.UtcNow`
- `StudentId = attempt.StudentId`, `LessonId = attempt.LessonId`
- `SkillId` — **same nullability problem** as Q6, but at the *lesson* level: `Lesson.SkillId` may also be nullable (verify). Apply the same "skip publication when null" recommendation, log + TODO.
- `AccuracyPercentage = (int)Math.Round(attempt.AccuracyPercentage)` (event field is `int`; aggregate is `double`)
- `CorrectAnswerCount = answers.Count(a => a.IsCorrect)`

Idempotent re-call of `CompleteAttempt` on an already-`Completed` attempt currently short-circuits (lines 77–92) and returns the snapshot **without** re-publishing — keep that behavior. Document it.
