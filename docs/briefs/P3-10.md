# Pipeline Brief — P3-10 Schedule spaced-repetition practice

## Summary & traceability
- **Task (one line):** Build a deterministic, idempotent **spaced-repetition scheduler** that selects skills due for review from the P3-09 mastery model (status + time since last practice), surfaces weak/forgotten skills for reinforcement (e.g. daily missions / practice), runs as a Hangfire background job, and lengthens the review interval for a reviewed skill that improves.
- **User story (source of truth):** `user-stories/Phase-4-AI-Tutor/P3-10-spaced-repetition.md`
- **Task file:** none yet (Phase-4 task breakdown pending — HANDOFF). **`planner` decomposes BE tasks from this brief.** Flag to lead.
- **FR-IDs:**
  - **FR-AD-4** (primary) — "The system shall schedule spaced-repetition reinforcement on weak/forgotten skills." *(G2, G3)*
  - **FR-AD-2/3** (consumed) — mastery status drives "weak/forgotten."
  - **FR-AI-6** (constraint) — scheduling is rule-based, not AI.
- **BRD goal / epic:** **G2** Learning outcomes + **G3** Daily habit. Epic: **Adaptivity & Student Modeling**. Barrier-to-entry **BE4** (Daily Habit) + **BE5** (Adaptive). Covers **B4.3**.
- **Phase / sprint:** Phase 4 — AI Tutor (Week 6–7). **SP 3** — "scheduler over mastery data + a background job; moderate logic."
- **Product-decision context:** 4 subjects, no Social Studies, no teacher role. **Grade transition preserves history** — a forgotten skill from a prior grade stays reviewable (mastery rows persist); the scheduler reads mastery, which is grade-agnostic.

## Business context & value
- **Who benefits:** the **student** (retains what they learned instead of forgetting — the story's core promise); the **habit loop** (review surfaces become daily-mission fodder → "come back tomorrow," BE4's top metric); the **parent** (durable mastery shows up in weekly reports).
- **Why it matters:** Mastery (P3-09) captures *current* accuracy but not *forgetting over time*. Spaced repetition closes that gap deterministically — a skill mastered weeks ago and not practiced becomes "due for review." It is the engine that makes the platform a "habit-forming educational system" rather than a one-pass course. The infra exists: **Hangfire + PostgreSQL is wired (P1-07)** with recurring jobs already in Gamification (`StreakSweepJob`, etc.) — P3-10 adds a Learning-side recurring job in the same pattern.
- **Why rule-based:** FR-AI-6 — intervals/eligibility are a deterministic schedule (a spaced-repetition curve), not an AI decision.
- **Success measure (testable):** the scheduler marks skills with status `needs_review`/weak (and/or mastered-but-stale) as due; due skills are queryable and feed missions/practice; the job is idempotent (re-running produces the same state, no duplicates); a skill that's reviewed and improves gets a longer next-review interval.

## Acceptance criteria (testable)
1. **AC1 — Due selection.** The scheduler selects skills due for review based on **mastery status and time since last practice**. *(verbatim — reads P3-09 `Status` + `LastPracticedAt`.)*
2. **AC2 — Surfaced for reinforcement.** Skills marked `needs_review`/weak are surfaced for reinforcement (e.g. in daily missions or practice). *(verbatim — a queryable "due review" list, consumed by P4-06 missions / a practice surface.)*
3. **AC3 — Background + idempotent.** Scheduling runs as a background job (Hangfire/Quartz) and is **idempotent**. *(verbatim — reuse the P1-07 Hangfire host + Gamification job pattern.)*
4. **AC4 — Expanding interval.** A reviewed skill that improves is rescheduled with a **longer interval**. *(verbatim — the spaced-repetition curve; see Q2.)*

## Affected modules & data
**Module:** **Learning only** (schema `learning`). Reads P3-09 mastery (Learning); the Hangfire job lives in `Learning.Infrastructure/Jobs` mirroring Gamification's jobs. **No new module.**

For v1, P3-10 can satisfy AC2 by exposing the due-list query + an own "practice" surface; the missions wiring is a flagged follow-up. Don't build cross-module FKs.

Unique index `(StudentId, SkillId)`. Audited.

## Open questions for the lead — recommended defaults
> "Approve all defaults" ships a coherent v1.

### Q1 — Store: new `ReviewSchedule` table, or columns on `StudentSkillMastery`?
- **Recommended default: extend `StudentSkillMastery` with `ReviewIntervalDays int` + `NextReviewDueAt datetime?`** (and reuse `LastPracticedAt` + `RepetitionNumber` if needed). Keeps schedule co-located with mastery (one row per student-skill), avoids a join, simplest to query "what's due." **Coordinate this migration with P3-09** (same table) — ideally P3-09 ships these columns nullable up front so P3-10 only adds logic, or P3-10 adds them in its own migration after P3-09.
- **Alternative:** a dedicated `ReviewSchedule` table — cleaner separation if review state grows (multiple review queues, per-subject schedules). Pick if the lead expects richer SR features (SM-2 ease factors, lapses). For MVP the columns-on-mastery shape is lighter.

### Q2 — The spaced-repetition curve (THE algorithm — flag explicitly)
- **Recommended default: a simple fixed expanding ladder.** Intervals like `1d → 3d → 7d → 14d → 30d` (a `RepetitionNumber`-indexed array in config). On a **successful** review (mastery still ≥ threshold), advance to the next, longer interval (AC4); on a **failed/weak** review (dropped to `needs_review`), reset to the shortest interval. Deterministic, explainable, idempotent, tunable via config.
- **Alternative (richer): SM-2 (Anki-style)** with an `EaseFactor` adjusted by review quality. More adaptive but adds a per-skill float and a more complex rule; **flag — do NOT silently introduce SM-2.** Recommend the fixed ladder for MVP; SM-2 is a deliberate upgrade the lead should approve.
- **Do NOT** use an AI/ML forgetting model (FR-AI-6). Flag any such temptation.
- **"Due" rule (AC1):** a skill is due iff `Status ∈ {NeedsReview}` **OR** (`Status == Mastered` AND `now ≥ NextReviewDueAt`). i.e. weak skills surface immediately; mastered skills surface when their interval elapses (forgetting check). Confirm the "mastered-but-stale" half — it's what makes SR more than "just review weak skills" (it catches forgetting). Recommend including it.

### Q3 — Job cadence + idempotency (AC3)
- **Recommended default: a daily recurring Hangfire job** (`SpacedRepetitionSweepJob`, mirror `StreakSweepJob`) that recomputes `NextReviewDueAt`/due-flags from mastery + the curve. **Idempotency:** the job is a pure recompute — running it twice yields the same `NextReviewDueAt` (it's a deterministic function of `LastReviewedAt` + `RepetitionNumber` + curve), so no duplicate work, no drift. Use a fixed `RecurringJob` id (Hangfire dedupes by id). No mutable accumulation.
- **Alternative:** event-driven recompute on attempt completion (no daily job) — but FR-AD-4/AC3 explicitly want a background job; keep the job. The job + on-completion update can coexist (completion updates the schedule for that skill; the daily job catches forgetting across all skills).

### Q4 — Interval progression trigger (AC4): on review completion, by the job, or both?
- **Recommended default: on review completion** — when a student completes a practice/quiz attempt on a due skill, P3-09's mastery update fires; P3-10 hooks the same completion to advance/reset the interval (success → longer, failure → reset) and set the new `NextReviewDueAt`. The **daily job** only flips the due-flag when `NextReviewDueAt` passes; it doesn't change intervals. Clean separation: completion changes the curve position, the job surfaces what's due.

### Q5 — What "review" practice the student actually does (AC2 surfacing)
- **Recommended default:** P3-10 produces a **queryable "due reviews" list** (`GET /api/Learning/Reviews/Due`, Student JWT, IDOR-guarded) — skill ids + names due for review. How they're practiced (a review quiz, a mission) reuses the **existing quiz path** (`StartAttempt` on a lesson teaching that skill) — no new practice mechanic needed for v1. Missions consumption (P4-06) is the flagged cross-module follow-up (see Affected modules).

### Q6 — Engine shape (pattern caution, rule 8)
- **Recommended default:** pure static `SpacedRepetitionEngine` (mirror `LearningPathEngine`): `ComputeNextReview(int repetitionNumber, DateTime lastReviewedAt, bool improved, SpacedRepetitionOptions options) → (int nextInterval, int nextRepetitionNumber, DateTime nextDueAt)` and `IsDue(MasteryStatus status, DateTime? nextReviewDueAt, DateTime now) → bool`. Curve in `SpacedRepetitionOptions` (config). The Hangfire job is a thin orchestrator calling the engine. No DB/DI in the engine.
- **Pattern caution:** SR scheduling invites **Strategy** ("pluggable interval algorithm" for fixed-ladder vs SM-2). **Do NOT introduce it without asking the lead** (rule 8). Default = plain functions + config options; SM-2-vs-ladder is a config/branch decision, not a pattern.

## Risks & assumptions
1. **Depends on P3-09 mastery** (status + `LastPracticedAt`) — merge order: P3-09 → **P3-10**. Independent of P3-08/P3-11 (parallel-able once P3-09 lands).
2. **Clock determinism** — `IsDue` uses `now`; the job's "idempotent" claim means *given the same now* it produces the same state. The job naturally runs at different times; idempotency means no duplicate side-effects per run, not time-invariance. Document precisely.
3. **`DateTime.Kind`/UTC quirk** (HANDOFF P2-08 note: `Attempt` rows had a `Kind=Local` issue) — SR does time arithmetic on `LastReviewedAt`/`NextReviewDueAt`; **store and compare in UTC consistently** or the curve drifts. Call this out for the implementer.
4. **Cross-module missions surfacing (AC2)** — don't build a Gamification FK; expose a read seam, defer P4-06 wiring.
5. **Migration coordination with P3-09** (Q1 columns-on-mastery) — serialize the shared-table edit; ideally P3-09 reserves the columns.
6. **Hangfire in test/CI** — Gamification jobs already run under Hangfire; reuse that test setup. The job is gated on a Default connection string (Program.cs) — Testing env behaviour mirrors existing jobs.

### Handoff → api-tester
Story exposes an HTTP endpoint **and** a background job → api-tester runs after backend-feature. Against running API + Testcontainers Postgres + Hangfire + Student JWT (reuse Gamification job test setup + P2-08 harness):
- Skill with `needs_review` status → appears in `GET /Reviews/Due`.
- Mastered skill with `NextReviewDueAt` in the past → appears as due (forgetting check); future due date → not yet due.
- Run the sweep job twice → identical due state, no duplicates (AC3 idempotency).
- Complete a successful review on a due skill → `NextReviewDueAt` pushes to a **longer** interval (AC4); `RepetitionNumber` increments.
- Complete a failed review (mastery drops) → interval **resets** to shortest.
- IDOR: another student's due list not addressable.
- New student (no mastery) → empty due list, no error.
