## Business context & value

- **Who benefits:** the **student** directly (the nudge is the only signal that reaches the device when the app is closed — every other Phase-3 system is only visible WHEN the student is already in the app), the **parent** (controls the prefs, sees the audit, decides on quiet hours), and the **product** (closes the loop measured by BRD §3 G3 KPI "daily retention / D7 return"). **No analytics → no proof of impact → no story** — that's why the analytics emit is in scope.
- **Why it matters now:** Phase-3 has built XP, streaks, hearts, badges, missions, leagues — six engagement engines that **only fire while the app is open**. The barrier-to-entry analysis (docs/briefs/barrier-to-entry-gap-analysis.md, referenced as BE4 / gap 3a-5) names *"make the child come back tomorrow"* as **the single most important metric** and this is the only story addressing it. Without P4-09, every nudge-able event (`HeartsDepletedDomainEvent` says "your hearts refill at 18:00" — but the student has to OPEN the app to see that) is half-built. P4-09 makes the previous 6 stories pay off outside the session.
- **Success measurement:**
  - A student who completes 0 lessons on a streak-active day and has `StreakAtRisk` enabled receives **at most one** push by 18:00 UTC (cron-driven) with the message *"Your X-day streak ends in 6 hours — earn 30 XP by completing one lesson"*.
  - A student who completes their daily mission triggers a `MissionCompletedIntegrationEvent` → Notifications writes an inbox row AND fires a push *"You finished today's mission! +30 XP"* (if `Achievement` push enabled).
  - A student who hasn't opened the app for 3 days gets one `LapseWinBack` push *"We miss you — your hearts are full and 3 missions await"*.
  - A push that violates quiet hours (22:00–08:00 by default — Q6) is **never sent** and **never queued for catch-up** — it is dropped silently with a log line + analytics-event-not-eligible.
  - Hitting the daily cap (3 by default — Q5) blocks any further push that day across all categories.
  - A duplicate domain event (same `EventId`) does NOT produce a duplicate nudge (Redis dedupe per-`(childId, category, day)`).
  - The parent can disable all categories or set quiet hours from `PUT /api/Notifications/Preferences/Children/{childId}/Reengagement`; the child JWT cannot.
- **Deterministic principle (BRD §8 / FR-AI-6):** eligibility is `prefs.EnabledFor(category) AND now ∉ quietHours AND !redis.exists(child:category:day) AND sentsToday < dailyCap`. The COPY is a string template lookup, not AI. The TRIGGER is a deterministic event + cron. No AI, no randomness.

## Acceptance criteria (verbatim from story + testable backend gates)

From `P4-09-reengagement-notifications.md`:

1. **AC1 — A re-engagement engine evaluates each active child daily and fires at most one nudge per category per day: streak-at-risk (streak active but no qualifying activity yet today), daily-mission reminder, lapse win-back (no session for N days).**
   - Backend gate:
     - 3 nudge categories live as enum values: `StreakAtRisk` (already exists), `DailyMissionReminder` (new), `LapseWinBack` (new).
     - **Streak-at-risk** is **cron-driven**: `StreakAtRiskJob` runs daily at 18:00 UTC (Q6), scans `StudentXpProfile WHERE CurrentStreak > 0 AND LastActivityDateUtc < today_utc`, publishes `StreakAtRiskIntegrationEvent(StudentId, CurrentStreak, OccurredAtUtc)` per match.
     - **Daily-mission reminder** is also **cron-driven**: same `StreakAtRiskJob` extended (or sibling) scans `StudentMission WHERE Status IN (NotStarted, InProgress) AND MissionType = Daily AND PeriodEndUtc > now AND PeriodEndUtc < now + 6h`, publishes `DailyMissionReminderIntegrationEvent(StudentId, OccurredAtUtc)` per match (one per student, even if 5 missions outstanding — see Q5).
     - **Lapse win-back** is `LapseWinBackJob` daily at 12:00 UTC, scans `StudentXpProfile WHERE LastActivityDateUtc <= today_utc - LapseDays` (default `LapseDays = 3` — Q8), publishes `LapseWinBackIntegrationEvent(StudentId, DaysIdle, OccurredAtUtc)`.
     - **At most one per category per day** enforced by `IDistributedCache.SetStringAsync(key=$"nudge:{childId}:{category}:{utcDay}", value="1", ttl=36h, options=WhenNotExists)`. If the SET-IF-NOT-EXISTS returns false, the handler short-circuits.
     - **Dedupe key uses event-day, not wall-clock day** — so a delayed redelivery of yesterday's event doesn't override today's nudge.

2. **AC2 — Triggers are driven by the `P4-01` domain events / streak + mission state — no polling of raw tables in the hot path.**
   - Backend gate:
     - **Event-triggered nudges** (Achievement category): `BadgeEarnedDomainEvent`, `MissionCompletedDomainEvent`, `HeartsRefilledDomainEvent` re-published as `Shared.Contracts/Gamification/*IntegrationEvent`s via in-module re-publishers. Notifications subscribes and fires nudges.
     - **State-triggered nudges** (StreakAtRisk, DailyMissionReminder, LapseWinBack): driven by the two Hangfire jobs running on `StudentXpProfile` + `StudentMission` queries — these queries ARE polls, but the story's *"no polling in the hot path"* rule applies to the **user-request hot path**, not the background sweep. The Hangfire jobs are the exception (same as `StreakSweepJob`, `MissionRolloverJob`, `LeagueRolloverJob`). Document.
     - **`StreakSweepJob` refactor:** today it bulks `ExecuteUpdateAsync(CurrentStreak = 0)` without raising `StreakBrokenDomainEvent` (the in-source comment marks this as the P4-09 trigger). **P4-09 replaces the bulk path with a page-loop** (Take(500), foreach, call `profile.BreakStreak()` which raises the domain event, save) so `StreakBrokenIntegrationEvent` actually gets re-published. Same pattern for `MissionRolloverJob` (Q12 — defer or include).
     - **Hearts refill** is currently lazy on read (P4-04). When the read query computes a positive delta and crosses the 0 → 1 boundary, it raises `HeartsRefilledDomainEvent`. P4-09's re-publisher fires the integration event from there.
     - **`HeartsDepletedDomainEvent`** is already raised inside `LoseHeartCommandHandler` when hearts reach 0. P4-09 re-publishes.
     - **Achievement** category: `BadgeEarnedDomainEvent` + `MissionCompletedDomainEvent` (the user already-in-app sees the badge popup; the nudge is for the parent's bell icon + an optional push if they leave the app between popup and read).

3. **AC3 — Parent controls per child: enable/disable each category, set quiet hours, and a hard daily cap. Defaults are conservative (opt-in friendly) and COPPA-appropriate; the child cannot change them.**
   - Backend gate:
     - **New entity `ChildReengagementPreference`** in Notifications, keyed on `(ParentId, ChildId, Category)`. Fields: `ParentId int`, `ChildId int`, `Category NotificationCategory`, `PushEnabled bool`, `InAppEnabled bool` (default true — see Q3), `QuietHoursStartLocal TimeOnly?`, `QuietHoursEndLocal TimeOnly?`, `DailyCap int` (default 3 — Q5). Audit fields (CreatedAtUtc, CreatedBy=ParentId, UpdatedAtUtc).
     - **Defaults synthesised on first read** (mirrors `GetMyNotificationPreferencesQueryHandler` pattern). **Conservative defaults: ALL categories `PushEnabled = false`, `InAppEnabled = true`, `DailyCap = 3`, `QuietHours = 22:00–08:00 Africa/Cairo`** (Q6). Parent must opt-in to push.
     - **Write endpoint:** `PUT /api/Notifications/Preferences/Children/{childId}/Reengagement` — **parent-only** (`[Authorize(Roles = "Parent")]`); the handler verifies `_parentChildQuery.IsParentOfChildAsync(parentId, childId)`; rejects with 403 + generic message if no link (anti-IDOR — security-auditor will check this).
     - **Read endpoint:** `GET /api/Notifications/Preferences/Children/{childId}/Reengagement` — same parent-only guard. Returns the 3 category rows (defaults + persisted overlay).
     - **Child JWT cannot read or write** the prefs (verified by absence of any `[Authorize(Roles="Student")]` route on the prefs endpoints). The child *can* read their own inbox via `/Inbox/Me`.

4. **AC4 — Delivery is channel-abstracted (push / web push / in-app inbox) so the same engine serves native + PWA; channel availability degrades gracefully.**
   - Backend gate:
     - **`INudgeDispatcher`** seam in `Notifications.Application/Abstractions/`: `Task<NudgeDispatchResult> DispatchAsync(NudgeMessage message, IReadOnlyList<NudgeChannel> channels, CT)` where `NudgeChannel = { Push, WebPush, InAppInbox }`.
     - **Default impl** `NudgeDispatcher` in `Notifications.Infrastructure`: composes `IInAppInboxWriter` (always writes the row — that's the durable receipt) + an `IPushSender` (Expo recommended — Q1) + optional `IWebPushSender` (deferred — Q1). **Graceful degradation:** push attempt failures (no device token registered, expired token, provider 5xx) are logged + analytics-emit-failure, but the inbox row STILL writes — so the next time the child opens the app, the bell badge updates.
     - **No Strategy/Factory pattern** (rule 8) — single dispatcher; channels are loop-iterated; provider selection is composition-root config (`Notifications:Push:Provider = "Expo" | "None"`).
     - **Web Push deferred** (Q1.bis) — Phase-3 students are primarily on the Expo native build per HANDOFF; web-push is a P4-08 / P5 concern.

5. **AC5 — Notification copy is Arabic-first, child-safe, encouraging (never shaming a missed streak), and localizable.**
   - Backend gate:
     - **`ReengagementCopyTemplates`** static class in `Notifications.Domain/Templates/`. Maps `(Category, Locale)` → `(TitleKey, BodyTemplate)`. Locales: `ar-EG` (default), `en-US` (fallback). The templates use named placeholders `{streakLength}`, `{daysIdle}`, `{badgeName}`, `{missionTitle}`, `{heartsRefillAt}`.
     - **NEVER use "you broke your streak" or any failure framing** — child-safety review will block this at security-auditor. Sample copy (placeholder — Q10 to finalize):

       var publisher = scope.ServiceProvider.GetRequiredService<IPublisher>();

### C. Gamification — `StreakSweepJob` refactor (`P4-09-BE-3b` — Q12)

Replace the bulk update with a page-loop OR add a synthetic event emit after the bulk update. **Recommend the latter for minimal risk:**

```csharp
public async Task RunAsync(CancellationToken ct)
{
    var today = StreakDayCalculator.Today(_options.Value.TimeZoneId, _clock);
    var threshold = today.AddDays(-1);

    await using var scope = _scopeFactory.CreateAsyncScope();
    var db = scope.ServiceProvider.GetRequiredService<GamificationDbContext>();
    var publisher = scope.ServiceProvider.GetRequiredService<IPublisher>();

    // CAPTURE affected rows FIRST (lightweight projection) so we can emit events after the bulk update.
    var brokenIds = await db.StudentXpProfiles
        .Where(p => p.CurrentStreak > 0
                 && (p.LastActivityDateUtc == null || p.LastActivityDateUtc < threshold))
        .Select(p => new { p.StudentId, p.CurrentStreak })
        .ToListAsync(ct);

    var rowsAffected = await db.StudentXpProfiles
        .Where(p => p.CurrentStreak > 0
                 && (p.LastActivityDateUtc == null || p.LastActivityDateUtc < threshold))
        .ExecuteUpdateAsync(s => s.SetProperty(p => p.CurrentStreak, 0), ct);

    // Synthetic integration-event emit so Notifications gets the nudge signal.
    foreach (var row in brokenIds)
        await publisher.Publish(new StreakBrokenIntegrationEvent(
            row.StudentId, row.CurrentStreak, threshold, _clock.UtcNow), ct);

    _logger.LogInfo($"P4-03/P4-09: streak-sweep — rowsReset={rowsAffected}, eventsPublished={brokenIds.Count}.");
}
```

This preserves the existing bulk-update perf and only adds the per-row event publish. The TOCTOU window (rows captured but not yet zeroed get zeroed by the `ExecuteUpdateAsync`; a new student that earns activity in between is fine — they're not in the captured set). Risk: an event might be published for a profile that another concurrent write updated to a new streak — bounded, low-likelihood, acceptable for MVP.

```csharp
public sealed class StreakBrokenIntegrationEventHandler
    : INotificationHandler<StreakBrokenIntegrationEvent>
{
    public async Task Handle(StreakBrokenIntegrationEvent ev, CancellationToken ct)
    {
        var parentLink = await _parentResolver.FindParentForChildAsync(ev.StudentId, ct);
        if (parentLink is null) return;  // child has no parent? shouldn't happen post-onboarding — log + skip

        var prefs = await _prefs.GetOrDefaultAsync(parentLink.ParentId, ev.StudentId, NotificationCategory.StreakAtRisk, ct);
        var eval = ReengagementEvaluator.Evaluate(prefs, _clock.UtcNow, await _sentTodayCount(...), prefs.TimeZoneId);
        if (!eval.Eligible) { _logger.LogInfo($"P4-09: streak-broken not eligible — reason={eval.Reason}"); return; }

        var dedupeKey = $"nudge:{ev.StudentId}:{NotificationCategory.StreakAtRisk}:{_clock.UtcNow.Date:yyyyMMdd}";
        var fresh = await _cache.SetIfNotExistsAsync(dedupeKey, "1", ttl: TimeSpan.FromHours(36), ct);
        if (!fresh) return;

        var locale = await _userLocale.GetAsync(ev.StudentId, ct) ?? "ar-EG";
        var (title, body) = ReengagementCopyTemplates.Render(NotificationCategory.StreakAtRisk, locale,
            new { streakLength = ev.PreviousStreak });
        await _dispatcher.DispatchAsync(
            new NudgeMessage(ev.StudentId, NotificationCategory.StreakAtRisk, title, body, dataJson: ...),
            channels: prefs.ResolveChannels(),
            ct);

        _logger.LogInfo($"analytics.reengagement.sent category=StreakAtRisk childId={ev.StudentId}");
    }
}
```

A new **`IParentForChildResolver`** seam wrapping `IParentChildQuery` (reverse lookup: child → parent) is needed — single new method `Task<ParentLink?> FindParentForChildAsync(int childId, CT)`. Add to `IParentChildQuery` (Q4 — extend that seam, not a new one).

### I. Notifications — `ReengagementEvaluator` (`P4-09-BE-2`)

```csharp
public static class ReengagementEvaluator
{
    public static EvalResult Evaluate(ChildReengagementPreference prefs, DateTime nowUtc, int sentsToday, string tzId)
    {
        if (!prefs.PushEnabled && !prefs.InAppEnabled) return new(false, NotEligibleReason.DisabledByParent);
        if (sentsToday >= prefs.DailyCap) return new(false, NotEligibleReason.DailyCapReached);
        if (IsInQuietHours(prefs.QuietHoursStartLocal, prefs.QuietHoursEndLocal, nowUtc, tzId))
            return new(false, NotEligibleReason.QuietHours);
        return new(true, NotEligibleReason.None);
    }
}
```

Pure. Unit-tested at boundaries (just-before-quiet-start, just-after-quiet-end, cap-at-N, cap-at-N+1, cross-midnight quiet window).

### J. Hardening (do NOT skip)

- **Idempotency 1:** Redis SETNX dedupe per (`childId`, `category`, `utcDay`). 36h TTL covers DST edge cases and clock skew. Fallback: when Redis is down, skip dedupe + LOG WARN — better to send 2 than block all (Q15).
- **Idempotency 2:** Integration event re-delivery (same `EventId`) is intercepted by dedupe — even though the analytics emit will say "fresh=false", no actual push goes out.
- **Cross-module trust:** every event handler trusts the payload's `StudentId`, NEVER reads from `ICurrentUserService` (events run in the publisher's scope).
- **Parent-only writes — verify on every request**, not via JWT role alone. JWT role says "Parent" but the **child ID** in the route must be one of THEIR linked children via `IsParentOfChildAsync`.
- **Anti-enumeration:** when `IsParentOfChildAsync` returns false, return 403 with a single generic message — NEVER 404 (don't disclose whether a child exists).
- **PII discipline:** no email, name, or copy body in logs. Only IDs + categories + eligibility outcomes.
- **No `ex.Message` echo** from any new path.
- **Conventions:** module isolation, `ILoggerManager` only, `BaseResponse<T>`, `Successed`, no design pattern (rule 8).

## Handoff → security-auditor

**Mandatory run — child-data + COPPA implications + first push-notification integration + parent-only authorization. Findings ≥ High block the gate.**

Required checks:

- **C1 — Parent-only verify on every write.** Confirm `_parentChildQuery.IsParentOfChildAsync(callerId, childId)` runs on EVERY prefs read/write, before any state. Test that JWT role=Parent without a link to `childId` → 403.
- **C2 — Anti-enumeration on prefs endpoint.** Same generic 403 for "child doesn't exist" vs "you're not their parent". No status code differentiation.
- **C3 — Child JWT cannot write prefs.** Role-based AND link-based.
- **C4 — Inbox IDOR.** All inbox/mark-read endpoints are JWT-scoped; the `id` route param is verified to belong to `_currentUser.UserId` before any read/write.
- **C5 — Device-token endpoint IDOR.** Self-scoped; token registered against caller's `UserId` only.
- **C6 — Push provider secrets.** Expo access token (if needed) lives in env vars (`Notifications__Push__Expo__AccessToken`), never logged, never echoed.
- **C7 — PII in push payload.** Notification copy MUST NOT include the child's full name, email, or other PII. Only first name (or no name) + game-state numbers (streak length, days idle).
- **C8 — PII in logs.** Audit log lines for absence of email/name/copy body.
- **C9 — Child-safety copy review.** Read every template in `ReengagementCopyTemplates` for shaming language ("you broke your streak", "you're falling behind", "your child hasn't been active"). All copy must be encouraging-only. The Arabic copy specifically — find an Arabic-speaking reviewer if needed.
- **C10 — Quiet hours enforced server-side.** Cannot be bypassed by FE.
- **C11 — Daily cap enforced server-side.** Cannot be bypassed.
- **C12 — Replay attacks via fake integration events.** Confirm Notifications only consumes events from `Shared.Contracts` types — no public endpoint accepts raw event payloads. (Already enforced — MediatR registration is internal.)
- **C13 — Push provider denial of service.** Expo allows ~600 pushes/sec free. We're far under at MVP scale. No DoS risk.
- **C14 — Dedupe Redis SETNX race.** Two concurrent identical events could theoretically both pass dedupe if Redis is partitioned. SETNX with TTL is atomic enough for MVP. Document.
- **C15 — Token leakage.** A device token in a log line is medium-severity — review log calls. Tokens are like passwords for push.
- **C16 — COPPA: minimal data retention.** Inbox rows aging out — recommend a Hangfire sweep job that deletes inbox rows older than 90 days (Q13 — defer to follow-up).

## Open questions / assumptions / risks

> Listed in priority order. Defaults are recommendations the lead can `APPROVE DEFAULTS` to greenlight.

**Top open questions (decision-shaping):**

**Q1 — Push provider: Expo Push vs FCM-direct vs OneSignal vs none-this-cycle.**
- **Recommend: Expo Push** — the FE is Expo per HANDOFF (P2-09 / P4-07 FE batches all mention Expo native + PWA). The Expo Push API is FREE, supports unlimited devices, abstracts FCM (Android) + APNS (iOS) + web push, and the integration is a single HTTPS POST. Zero infrastructure setup; one `EXPO_ACCESS_TOKEN` env var.
- **Alternative — FCM direct:** more control, more work (separate Android cert + iOS APNS cert + service-account JSON). Reject for MVP.
- **Alternative — OneSignal:** commercial, freemium; nice analytics dashboard. Reject — adds a vendor dependency we don't need yet.
- **Alternative — Defer push entirely, ship in-app-inbox only:** halves the surface; story still ships nudges (the inbox bell). Reject — story explicitly requires push as the primary channel (the in-app inbox is the degradation target).
- **Q1.bis — Web Push:** **Defer.** Phase-3 students are mobile-first; web-push (VAPID + browser registration) is its own pipeline. Add when PWA polish lands in P5.

**Q2 — `NotificationCategory` enum expansion: 2 new values, or split Achievement further?**
- **Recommend: add exactly 2 — `DailyMissionReminder = 4`, `LapseWinBack = 5`.** Keep `StreakAtRisk = 1` (existing) and `Achievement = 3` (existing) covering all five "good news" events (badge, mission, level-up, hearts-refilled, streak-advanced not used). Five enum values is the new total.
- **Alternative — split Achievement into `BadgeEarned`, `MissionCompleted`, `HeartsRefilled`:** finer-grained parent control, more rows in the prefs table per child. Reject for MVP — parent prefs UI gets noisy.
- **Alternative — re-use `StreakAtRisk` for ALL 3 habit nudges:** loses the per-category parent toggle on lapse vs daily-mission. Reject.

**Q3 — Default for `InAppEnabled` (vs `PushEnabled` = false default).**
- **Recommend: `InAppEnabled = true` default for all categories, `PushEnabled = false` default for all categories.** Conservative defaults that still let the inbox bell update — parents opt-in to push only.
- **Alternative — both default off:** safest possible but kills the bell update on the child's home screen. Reject; the inbox is in-product UX, not a notification.

**Q4 — Prefs entity shape: extend `NotificationPreference` OR new `ChildReengagementPreference`.**
- **Recommend NEW `ChildReengagementPreference`** — keyed on `(ParentId, ChildId, Category)` plus the quiet-hours + daily-cap fields. The existing `NotificationPreference (UserId, Category)` is for SELF-prefs (a parent's own weekly-report opt-in); the new entity is for parent-controls-child prefs. **Different access patterns, different actors, different writes — different table.**
- **Alternative — extend `NotificationPreference` with `OnBehalfOfChildId int?`:** doubles the table semantically and complicates the existing P2-12 queries. Reject.

**Q5 — Daily cap default + cap scope.**
- **Recommend: `DailyCap = 3` default, applies to PUSH channel only**, NOT to inbox writes. The inbox is the durable receipt — it should always populate; only the push (which interrupts the user) is capped.
- **Alternative — cap applies to inbox too:** harms the "you missed something" UX when the child opens the app. Reject.
- **Alternative — `DailyCap = 1`:** too restrictive. Reject.
- **Q5.b — Sub-question: does each category have its own cap, or is the cap global across all categories?** **Recommend global cap** (3 pushes total per day across all categories) — easier to reason about, prevents prefs misconfig from spamming.

**Q6 — Quiet hours: global default vs per-user timezone.**
- **Recommend: per-child quiet hours stored as `(StartLocal TimeOnly, EndLocal TimeOnly, TimeZoneId string)`**, default `(22:00, 08:00, "Africa/Cairo")`. Per-child because the parent might have multiple children with different schedules.
- **Why "Africa/Cairo" default**: the primary audience is Arabic-speaking school students; per HANDOFF `PreferredLanguage = "ar-EG"`. No per-user TZ field exists on `User` — but we don't need one because the prefs row itself carries the TZ. Parent can change it.
- **Q6.b — Catch-up queue: hold push during quiet hours and send next morning?** **Recommend NO — drop entirely.** A stale "your streak is at risk!" sent at 08:00 when the at-risk window expired at midnight is annoying. Inbox row still writes (no expiry concept for inbox).

**Q7 — Cross-module integration-event publish: in-Gamification republisher (recommended) vs Notifications subscribes to Gamification's domain events directly.**
- **Recommend: in-Gamification republisher** — each in-module domain event has a sibling `INotificationHandler<TDomainEvent>` in Gamification that calls `_publisher.Publish(new TIntegrationEvent(...))`. The integration event then fans out to Notifications via the host's unified MediatR registration. **Why:** preserves module isolation (Notifications never refs Gamification.Domain.Events). The pattern matches how Learning publishes `LessonCompletedIntegrationEvent` from inside its own Application layer.
- **Alternative — Notifications subscribes directly to Gamification's domain events:** would require Notifications to ref Gamification.Domain (rule 1 violation) OR move all domain events into Shared.Contracts (rule 1 violation in the other direction — domain events are NOT public contracts). Reject.

**Q8 — `LapseWinBackJob` semantics: one-shot vs daily-while-idle.**
- **Recommend: one-shot on the exact day a student crosses `LapseDays = 3` (today - 3 days)**. Otherwise the same kid gets the same nudge every day until they return (anti-pattern).
- **Implementation:** scan `LastActivityDateUtc > today - 4 AND LastActivityDateUtc <= today - 3` — narrow window catches the transition day only.
- **Alternative — escalating cadence** (3 days, 7 days, 14 days) with different copy: better UX, more state. Defer to a follow-up; story names a single category "lapse win-back" with no tiering.

**Q9 — Analytics emit: structured log marker vs P5-03 sink.**
- **Recommend: ship `ILoggerManager.LogInfo("analytics.reengagement.sent ...")` structured marker now.** When P5-03 lands, swap for a real Mediator publish. The marker is searchable in CloudWatch / Loki / etc. — measurable enough for MVP.

**Q10 — Final copy templates (Arabic + English) — who writes them?**

**Q11 — Notification audit log: separate `NotificationLog` table (per SRS §6) vs columns on `Notification`.**

- **Q11.b — Backfill `Category` for existing welcome rows:** map to `NotificationCategory.WeeklyReport = 0` as the sentinel-no-opinion value (or add an explicit `System` value to the enum — recommend the latter; cleanest).

**Q12 — `StreakSweepJob` refactor scope.**

**Risks:**

- **R1 (HIGH) — Push provider integration first time, no fallback.** Expo Push API outages would silently drop nudges. **Mitigation:** inbox row is the durable receipt; on next app open the bell updates. Add a retry queue in a follow-up.
- **R2 (HIGH) — COPPA + child-safety copy.** Any shaming language or PII leak in push payload is a regulatory issue. **Mitigation:** security-auditor reviews all copy; analyzer-level checklist of "what NOT to say"; native-Arabic reviewer for `ar-EG` strings.
- **R3 (HIGH) — `StreakSweepJob` regression.** The refactor changes a P4-03-validated bulk-update job. **Mitigation:** keep the bulk update; ADD the per-row event emit afterward (section C). Existing P4-03 tests still pass.
- **R4 (MED) — Redis dedupe SETNX race.** Two concurrent events for the same `(child, category, day)` could both pass. **Mitigation:** SETNX with TTL is atomic enough; impact is "one extra push" not "incorrect data". Accept.
- **R5 (MED) — Parent-link cache staleness.** If a parent unlinks a child, the cross-module `IParentChildQuery` should reflect immediately. **Mitigation:** no caching in the new method; one DB read per event handler — cheap at MVP scale.
- **R6 (MED) — Cron drift across DST.** Quiet hours stored as local time; jobs run UTC. **Mitigation:** conversion in `ReengagementEvaluator` via `TimeZoneInfo.ConvertTimeFromUtc`; unit-tested across DST boundaries.
- **R7 (MED) — Event ghost after Learning rollback.** Same R4 from P4-03 — Gamification could publish a re-engagement event for a state change that gets rolled back upstream. **Mitigation:** ADR 0002 §3 accepts ghosts; nudges might over-fire, never under-fire. Document.
- **R8 (LOW) — Two-stage event dispatch latency.** Domain event → in-module republisher → integration event → Notifications consumer. Each hop is one MediatR `Publish`. Total: ~5ms. Acceptable.
- **R9 (LOW) — Cron job thundering herd.** At 18:00 UTC, a 100k-student `StreakAtRiskJob` would publish 100k events. Each event spawns a `_publisher.Publish`. **Mitigation:** batch the publishes via `Parallel.ForEachAsync` with a parallelism cap; at MVP scale this is 100s of students.
- **R10 (LOW) — `UserDeviceToken` token leakage.** Push tokens can be used by attackers to spam a device. **Mitigation:** server-only access; never echoed to clients; revoke on logout.
- **R11 (LOW) — `IPublisher` from background job missing scope.** Hangfire workers create a fresh DI scope; verify `IPublisher` resolves there. Same precedent as `LeagueRolloverJob` raising events — already verified.
