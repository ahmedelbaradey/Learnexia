# Pipeline Brief — P2-02 Browse subjects and lessons

## Summary & traceability
- **Task (1 line):** Add student-facing query endpoints to browse the 4 MVP subjects, their units→lessons (in sequence order), and a subject's skill-tree payload — all filtered to the student's grade, with empty-state-friendly results.
- **User story (source of truth):** `user-stories/Phase-2-Learning-Core/P2-02-browse-subjects-and-lessons.md` (SP 3).
- **Task file:** `tasks/Backend/Phase-2-Learning-Core/P2-02-BE.md` (BE-1..BE-4).
- **FR-IDs:** FR-LR-1, FR-LR-2.
- **BRD goal:** G1 (engaging, personalized learning experience) — subject/lesson discovery is the entry point to the learning loop.
- **Epic / phase:** Learning Module · Phase 2 — Learning Core (Week 3–4).
- **Product override applied:** 4 subjects (Math, Science, Arabic, English) — **no Social Studies** (overrides BRD §4). Seed already enforces this.
- **This is a backend-only brief.** FE consumer is P2-02-FE (separate story); P2-03 (skill-tree UI) and P2-04 (learning-path engine) are downstream and inform the SkillTree contract.

## Business context & value
- **Who benefits:** the **student** (signed-in child account) browsing what to learn; indirectly the parent (children engage with grade-appropriate content).
- **Value:** subject selection is the front door to the learning loop. A student opens Subject Selection, sees the 4 MVP subjects for their grade, picks one, sees its units/lessons in order, and (P2-03) navigates the skill tree.
- **Grade-filtered browsing:** a student must only see content scoped to their grade (`Subject.GradeId` → `Grade.Number` 1–6). Cross-grade content must not leak.
- **Empty-state handling:** if a subject has no lessons for the grade (or no subjects exist yet), the API must return a clean empty result (200 + empty collection), NOT a 404 or error — the FE renders an "appropriate empty state".
- **Success measured by:** student can reach a lesson list for any of the 4 subjects in their grade; no cross-grade leakage; empty states render gracefully.

## Acceptance criteria (testable)
1. `GET /api/Learning/Subjects?grade=N` returns exactly the subjects scoped to grade N — for the seeded data, the 4 MVP subjects (Math, Science, Arabic, English) and nothing from other grades.
2. `GET /api/Learning/Subjects/{id}/Lessons` returns the subject's **units, each with its lessons, both ordered by `SequenceOrder` ascending** (units by `Unit.SequenceOrder`, lessons by `Lesson.SequenceOrder`).
3. All three endpoints filter by grade (directly via the route subject's grade, or via the `grade` parameter / resolved student grade) — no content from another grade appears.
4. A subject that has no lessons for the grade returns **200 with an empty (or empty-units) collection** — not an error. A non-existent subject id returns **404**.
5. `GET /api/Learning/Subjects/{id}/SkillTree` returns a skill-tree payload: the subject's concepts → skills as **nodes**, plus the data the FE needs to lay them out. Each node carries a **state field** (see Open Questions — for now a default/static state, since per-student progress is not built yet).
6. All responses use the `BaseResponse<T>` envelope (`Successed` flag) — consistent with the rest of the module.
7. (If enforced) endpoints require an authenticated Student; grade is resolved per the decision in Open Questions.

## Affected modules & data
- **Module:** Learning only (`backend/src/Modules/Learning/...`). Schema `learning`.
- **Entities — all EXISTING (P2-01 + P2-10 already laid the schema; no migration expected):**
  - `Grade` { Id, Number (1–6), DisplayName, Subjects[] } — Grade is a **separate entity**, not an int column (lead decision Q1).
  - `Subject` { Id, Name, Country?, **GradeId** (FK→Grade), Units[], Concepts[] }.
  - `Unit` { Id, Name, **SequenceOrder**, SubjectId, Lessons[] }.
  - `Lesson` { Id, Name, Difficulty, **SequenceOrder**, IsLocked, UnitId, **SkillId? (nullable)** }.
  - `Concept` { Id, Name, Description?, DifficultyLevel, SubjectId, Skills[] }.
  - `Skill` { Id, Name, MasteryThreshold, EstimatedTimeMinutes, ConceptId, Lessons[] } — **no prerequisite/dependency edge field yet** (that arrives in P2-11).
- **Relationships:** Grade 1—* Subject; Subject 1—* Unit; Subject 1—* Concept; Unit 1—* Lesson; Concept 1—* Skill; Lesson *—o1 Skill (nullable).
- **No new entities, no new columns** are needed for the read-only browse story. **No per-student progress / node-state tables exist** — those are P2-03/P2-04 scope.

## Handoff → db-migration
- **Expected: NO migration.** The full curriculum schema (Grade/Subject/Unit/Lesson/Concept/Skill) already exists from P2-01 and is seeded by P2-10. These are read-only queries over existing tables.
- If the planner/implementer discovers a genuinely missing index (e.g. on `Subject.GradeId`, `Unit.SubjectId`, `Lesson.UnitId`, `Concept.SubjectId`, `Skill.ConceptId`) needed for query performance, that is the only candidate migration — flag it; do not add speculative schema.
- **Do not** add a Skill prerequisite/dependency column here — that is P2-11's scope and renaming/altering the curriculum schema would collide with it.

## Handoff → backend-feature
**Mirror the existing Learning query shape** (`ListSubjectsQueryHandler` / `ListLessonsQueryHandler`): `IQuery<BaseResponse<T>>` record + `IQueryHandler` deriving `BaseResponseHandler`, inject `ILearningServiceManager` + `IMapper` + `ILoggerManager`, project with AutoMapper `ProjectTo`, `try/catch → ServerError`, return `Success(...)` / `EmptyCollection(...)` / `NotFound(...)`. Queries are **not** auto-validated (`ValidationBehavior` is `ICommand<>`-only) — guard inputs in-handler. Reference: Catalog module + `StartAttemptCommandHandler` for the student/JWT pattern.

These are **NEW student-oriented read queries** — the existing `ListSubjectsQuery`/`ListLessonsQuery` are admin-style **paginated, flat** lists keyed by optional `GradeId`/`UnitId`. They do NOT return the nested units→lessons hierarchy, do NOT sort by sequence, and do NOT resolve the student's grade. See Gap Analysis. Add new features; do not overload the admin queries.

### BE-1 — `GetSubjectsQuery(Handler)` → `GET /api/Learning/Subjects?grade=`
- Input: `grade` (int — the grade **number** 1–6; see Open Question Q2 on whether it is a query param or resolved from the student).
- Logic: resolve the `Grade` entity by `Number == grade`, then return subjects where `Subject.GradeId == grade.Id`. (Note: the seeder ties `Subject.GradeId` to `Grade.Id`, while the URL/JWT carries the grade **number** — map number→GradeId, do not assume they're equal.)
- Output: list of subject DTOs (Id, Name; optionally a unit/lesson count for the selection card). Empty list → `EmptyCollection` (200), never 404.
- **Decide pagination:** there are only 4 subjects per grade — a flat (non-paginated) `BaseResponse<List<...>>` is cleaner for the FE than the admin `PaginatedResult<>`. Confirm with planner; default to a simple list for the student endpoint.

### BE-2 — `GetSubjectLessonsQuery(Handler)` → `GET /api/Learning/Subjects/{id}/Lessons`
- Input: `subjectId` from the route.
- Logic: load the subject (404 if missing). Return its Units **ordered by `SequenceOrder`**, each with its Lessons **ordered by `SequenceOrder`**. Include per-lesson: Id, Name, Difficulty, SequenceOrder, IsLocked, SkillId.
- Empty: subject exists but no units/lessons → 200 with empty units array.
- Grade scoping: the subject is already grade-scoped via its `GradeId`, so loading by id is sufficient; optionally assert the subject's grade matches the student's grade if grade is enforced (Open Q2).
- Suggested shape: `SubjectLessonsResponse { SubjectId, SubjectName, Units: [{ UnitId, Name, SequenceOrder, Lessons: [{ LessonId, Name, Difficulty, SequenceOrder, IsLocked, SkillId }] }] }`.

### BE-3 — `GetSkillTreeQuery(Handler)` → `GET /api/Learning/Subjects/{id}/SkillTree`
- Input: `subjectId` from the route.
- Logic: load the subject (404 if missing). Build the tree from the subject's **Concepts → Skills**. Each Skill becomes a **node**; the FE groups by concept and lays out the tree.
- **Node shape:** `{ SkillId, Name, ConceptId, ConceptName, MasteryThreshold, EstimatedTimeMinutes, State, LessonIds? }`. Surface `Lesson.SkillId` links so a node can open its lesson(s).
- **`State` field — IMPORTANT (see Open Q1):** per-student progress and skill prerequisites do **not** exist yet (P2-04 path engine + P2-11 dependency graph + any progress tables are downstream). For P2-02, the recommended approach is to **include the `State` field in the contract but return a static default** — e.g. derive a coarse state from `Lesson.IsLocked` (locked vs unlocked) or return all nodes `Unlocked`/`Available`. Model `State` as an enum with the 4 P2-03 states (`Locked`, `Unlocked`, `Completed`, `Boss`) so the contract is stable for P2-03/P2-04 to fill in real logic later, but **do not invent a progress computation here** — that is out of scope and would duplicate P2-04.
- **Dependencies/edges:** there is no Skill→prerequisite edge in the schema yet (P2-11). Return a **flat node list (grouped by concept)** for now; the dependency graph / edges arrive with P2-11. The FE skill-tree (P2-03) can render a concept-grouped layout from this.

### Controllers
- Add the 3 routes. The task file lists `GET /api/Learning/Subjects?grade=`, `GET /api/Learning/Subjects/{id}/Lessons`, `GET /api/Learning/Subjects/{id}/SkillTree`. The existing `SubjectsController` already owns `api/learning/[controller]` — add `GET /{id}/Lessons` and `GET /{id}/SkillTree` there, and either a new `GET ?grade=` action or fold into the existing list (prefer a distinct student action to avoid clashing with the admin `List` route).
- **Auth:** decide deliberately (rule 6) — student endpoints likely `[Authorize(Roles="Student")]` (mirror `StartAttempt`). Confirm in Open Q2 whether parents/admins may also browse.

## Handoff → api-tester
After backend-feature, validate the running API (integration tests against real PostgreSQL, seeded):
- `GET /api/Learning/Subjects?grade=1` → 200, returns the 4 MVP subjects for grade 1, none from other grades.
- `GET /api/Learning/Subjects/{mathId}/Lessons` → 200, units in `SequenceOrder`, lessons in `SequenceOrder` within each unit (Math = 5 units × 3 lessons per the seeder).
- `GET /api/Learning/Subjects/{id}/SkillTree` → 200, nodes present (Math grade = 15 skills across 5 concepts), each node carries a `State`.

- (If auth enforced) unauthenticated → 401; wrong role → 403; no answer/grade leakage across grades.

## Handoff → frontend (P2-02-FE — separate story, for reference)

- The SkillTree node `State` is the seam P2-03 builds its 4-state rendering on — FE should treat it as authoritative but expect the BE value to be a placeholder until P2-04 lands real progress.
- Regenerate `@learnexia/api-client` after the endpoints merge (needs the .NET 9 runtime side-by-side — see HANDOFF.md).

## Open questions / assumptions / risks
- **Q1 (BE-3 SkillTree state — needs a decision):** Per-student progress, skill prerequisites (P2-11), and the learning-path engine (P2-04) are NOT built. P2-03's 4 states (locked/unlocked/completed/boss) depend on them. **Recommendation:** ship the `State` enum in the contract now but return a static/default state (e.g. derived from `Lesson.IsLocked`, or all `Unlocked`), and a flat concept-grouped node list (no real prerequisite edges). Confirm the lead accepts a placeholder state so P2-02 isn't blocked on P2-04/P2-11. **This is the main thing for the lead to confirm before planning.**
- **Q2 (grade source — needs a decision):** The task file shows `?grade=` as a query param, but a signed-in student's grade is authoritative server-side. Options: (a) trust the `grade` query param (simplest, but lets a student query any grade); (b) resolve the student's grade from identity and ignore/validate the param. **Risk:** the student's grade lives in the **Identity** module (`User.Grade`), and there is **no current seam** exposing "current student → grade" — `ICurrentUserService` has no grade claim, `IUserLookup` returns only Id/UserName/Email (no Grade), and `IChildAccountService.GetChildrenAsync` is parent-scoped. So option (b) requires **either** a new grade claim in the student JWT **or** a new `Shared.Contracts` seam (e.g. extend `IUserLookup`/`UserSummary` or add `IStudentGradeLookup`) — a real cross-module change. **Recommendation for MVP/this story:** accept `?grade=` as a query param (option a) to keep P2-02 self-contained, and log a follow-up to enforce server-side grade. Confirm with the lead.
- **Q3 (pagination):** Admin list queries return `PaginatedResult<>`. For 4 subjects / a single subject's lessons, a flat `BaseResponse<List<...>>` is friendlier. Assumption: student endpoints return flat lists, not paginated. Confirm with planner.
- **Q4 (Grade.Number vs GradeId):** the URL/JWT carries the grade **number** (1–6) but `Subject.GradeId` references `Grade.Id` (a surrogate key). The handler must map number→GradeId, not assume equality. Flagged so the implementer doesn't filter `Subject.GradeId == gradeNumber` directly.
- **Assumption:** P2-01 (curriculum schema) and P2-10 (seed) are merged/available in the target DB before this runs (the story lists both as blockers; HANDOFF shows P2-10 committed, pending Wave-6 PR). If the target DB is not seeded, the empty-state path is exercised but the "4 subjects" AC can't be demoed.
- **Risk (low):** module isolation — do NOT add a cross-module FK to Identity for grade; any grade lookup must go through a `Shared.Contracts` seam or a JWT claim (rule 1).

## Recommended pipeline order (first cut — planner finalizes)
1. **db-migration:** expected **NO-OP** (no schema change). Skip unless a missing index is confirmed.
2. **backend-feature:** implement BE-1, BE-2, BE-3 (+ BE-4 grade filtering is folded into all three) — they share entities but are independent queries, so a single backend-feature batch can build all three. No designer stage (backend-only).
3. **api-tester:** integration tests for the 3 endpoints (after backend-feature) — these are HTTP endpoints, so api-tester is required.
4. **reviewer:** gate against the ACs above + CONVENTIONS.
5. **committer:** on `feat/P2-02-browse-subjects-and-lessons`, PR to main.
- **security-auditor:** the endpoints read curriculum data scoped to a child's grade — if grade enforcement (Q2 option b) and Student-role auth are added, run security-auditor (child-data + authz). If it ships as a public-ish `?grade=` read with no PII, it is low-sensitivity — planner to decide based on the Q2 outcome.
- **Blocker before planning:** resolve **Q1** and **Q2** with the lead/user — both shape the BE-3 contract and the auth/grade surface.
