## Business context & value

- **Who benefits:** the **operator/admin** (tune price, grants, caps, and per-action costs to keep the economy margin-positive as AI prices and usage shift — without a deploy), indirectly the **business** (the economy is a live dial, not a code constant — critical when AI model pricing changes, `ai-cost-routing.md` "verify pricing before launch"). No direct student/parent benefit — it's an internal control plane.
- **Why config, not constants:** P9-02/03/04 currently reference literal amounts (300/3000, 1/3/5/5, 20/150). Hardcoding them means every economy tweak is a deploy. P9-11 promotes these to a **versioned, audited config store** so a pricing change is an admin action, takes effect on the next cycle/request, and is fully traceable (who changed what, when, old→new) — the same audit discipline the P7 admin console already applies to its config.
- **Effective-from-next, never retroactive (hard AC):** a cost change must **not** re-charge a past action. A child who spent 1 energy on a hint yesterday is never retro-billed because the hint cost changed to 2 today. This is both a fairness invariant and a ledger-integrity invariant (the ledger records the cost *at the time of the action*; config changes only affect future reads). P9-03 already records the actual charged amount in the `Spend` ledger row — config changes never rewrite history.
- **Validation guards a sensitive dial:** a fat-fingered negative cost, a zero pack size, or a grant smaller than the daily cap (which would make the daily cap meaningless or unreachable) are blocked. The economy is load-bearing for revenue — bad config has real money/UX impact.
- **Success measure (from AC):** admin can edit all listed values; changes are versioned + audited (who/when/old→new) and effective next-cycle/next-request, never retroactive; validation rejects nonsensical values; admin-only behind the P7 console.

## Current-state findings (reality in code)

1. **The P7 admin console + audit pattern exists** (per MEMORY.md: "P7-01..08 + P7-12 + P7-13 BACKEND BUILT — curriculum + user/account + audit/Moderation + gamification overrides"). P9-11 is **the same shape as the P7-13 gamification-overrides config** (admin edits config values, versioned + audited). **Mirror P7's config-CRUD + audit pattern** rather than inventing one. The `Moderation.AuditLog` entity already records who/when/what for admin actions — reuse it (OQ-2 — reuse `Moderation.AuditLog` vs a billing-local audit/version table).
2. **No billing config store exists** — P9-02/03/04 will reference literals until P9-11 provides the store. P9-11 introduces a `BillingConfig` (or `BillingConfigVersion`) entity in the `billing` schema (or wherever the ledger lands per P9-01 OQ-2).
3. **Versioning is a real requirement, not just audit** — the AC says *"versioned + audited"* and *"effective from the next cycle"*. A pure mutable-config-row + an audit log satisfies "audited" but the "versioned + effective-from-next" wording suggests **effective-dated versions** (a new version row with an `EffectiveFromUtc`, the current value resolved as "latest version effective ≤ now"). **Recommend effective-dated version rows** (OQ-3) — this also cleanly delivers "never retroactive" (a past action read the version effective at its time; new versions don't touch it).
4. **Consumers read config, don't write it** — P9-02/03/04 need a **read seam** (`IBillingConfigReader.GetMonthlyGrant(tier)`, `GetActionCost(actionKind)`, `GetDailyCap(tier)`, `GetPackSizePrice()`). They consume it in-process (same `Billing` module) or via `Shared.Contracts` if any consumer is in another module (P9-03's spend wiring is in the `Ai` module → it reads cost via the same `Shared.Contracts` seam P9-01 exposes, or P9-03 passes the cost in). Confirm the read seam placement (OQ-4).
5. **Admin authorization** — the P7 console enforces admin-only access; P9-11 endpoints go behind the same admin policy. No teacher role (SRS §3).

## Acceptance criteria (testable)

1. **AC-1 (editable config set):** Admin can edit: plan price (199 EGP), monthly grant (Free 300 / Premium 3000), daily soft cap (20 / 150), pack size + price (500), and per-action costs (hint 1, explain-mistake 3, deep-explanation 5, practice-generation 5). All persisted in a `BillingConfig` store.
2. **AC-2 (versioned + audited):** Every change creates a new **version** (old→new captured) and an **audit record** (who/when). The change history is queryable (who changed what, when).
3. **AC-3 (effective next, never retroactive):** A change takes effect from the **next cycle** (grant amounts → P9-02's next grant) / **next request** (action costs → P9-03's next spend); it **never re-charges a past action** (the `Spend` ledger row's recorded cost is immutable). Tested: change a cost, verify a prior `Spend` row is unchanged and the next spend uses the new cost.
4. **AC-4 (validation):** Rejects nonsensical values — negative costs/grants/prices, zero pack size, **grant < daily cap** (the daily cap must be ≤ the monthly grant or it's meaningless), and any other cross-field sanity rule (OQ-5). Validation runs via `ValidationBehavior` on the `ICommand<>` (commands are auto-validated; rule 4).
5. **AC-5 (admin-only, behind P7):** All endpoints require the admin policy (the P7 console's auth); no teacher role; not reachable by parent/student.
6. **AC-6 (conventions):** `BaseResponse<T>` / `Successed`; `ILoggerManager`; `ValidationBehavior` for the config-edit commands; audit via the P7/`Moderation.AuditLog` pattern; lives in `Billing`.

## Affected modules & data

- **NEW entity `BillingConfig` / `BillingConfigVersion`** (`billing` schema, or per P9-01 OQ-2). Two shapes (OQ-3):
  - **(A, recommended) Effective-dated versions:** a `BillingConfigVersion` row per change — `Id`, `EffectiveFromUtc`, the config payload (either columns or a jsonb blob of the full config set), `CreatedBy`, `CreatedAtUtc`, `Note`. "Current config" = the latest version with `EffectiveFromUtc <= now`. Cleanly delivers versioning + effective-from-next + never-retroactive.
  - **(B) Mutable config + audit log:** a single mutable `BillingConfig` row updated in place, with each change written to `Moderation.AuditLog` (old→new). Simpler, but "versioned" + "effective-from-next-cycle" is weaker (no effective-dating).
  - **Recommend (A).** Confirm.
- **Config payload fields:** `PlanPrice` (per tier — or a single Premium price), `MonthlyGrant` (per tier: Free 300 / Premium 3000), `DailyCap` (per tier: 20 / 150), `PackSize` + `PackPrice` (500), per-action costs (`Hint`, `ExplainMistake`, `DeepExplanation`, `PracticeGeneration`). Whether per-tier values are separate columns or a normalized `(tier, key) → value` table is OQ-6 (recommend a typed config object / jsonb for simplicity at 3 SP).
- **AUDIT:** reuse `Moderation.AuditLog` (who/when/old→new) via the existing P7 pattern (OQ-2) — **recommend reuse** rather than a billing-local audit table.
- **READ seam (`IBillingConfigReader`):** consumed by P9-02/03/04. In-process within `Billing`; exposed via `Shared.Contracts/Billing` if a cross-module consumer (P9-03 in the `Ai` module) reads cost directly (OQ-4).
- **Existing entities:** none modified (beyond reusing `Moderation.AuditLog`). The P7 admin console gains a billing-config screen (frontend).

## Handoff → backend-feature

- **`UpdateBillingConfigCommand` (admin):** `ICommand<>` (auto-validated) carrying the new config values; creates a **new `BillingConfigVersion`** (shape A) with `EffectiveFromUtc` (now or a scheduled future cycle date — OQ-7) and writes the audit record (old→new) via the P7/`Moderation.AuditLog` pattern. `[Authorize(adminPolicy)]`.
- **`GetBillingConfigQuery` (admin read):** the current effective config + the version history (who/when/old→new) for the admin screen.
- **`IBillingConfigReader` (consumer seam):** `GetMonthlyGrant(tier)`, `GetActionCost(actionKind)`, `GetDailyCap(tier)`, `GetPackSizePrice()`, resolving the **latest version effective ≤ now** — consumed by P9-02 (grant), P9-03 (cost), P9-04 (cap). **This is the read contract P9-02/03/04 build against** (with config defaults until P9-11 lands). Cache the current version in-memory with invalidation on update (optional — OQ-8).
- **Validation (`FluentValidation`, runs via `ValidationBehavior`):** non-negative price/grant/cap/cost; pack size > 0; **daily cap ≤ monthly grant** per tier (AC-4); per-action cost ≥ 0; any other cross-field rule (OQ-5). Reject with a clear message (no raw exception).
- **Never-retroactive (AC-3):** new versions are effective-dated; the `Spend` ledger (P9-03) records the cost at action time and is immutable — config changes never rewrite past rows. Confirm P9-03 records the actual charged amount (it does, per P9-01/P9-03 design).
- **Conventions:** `BaseResponse<T>` / `Successed`; `ILoggerManager`; `ValidationBehavior` on the command; admin policy; audit via the P7 pattern.

## Handoff → security-auditor (admin-authz gate)

- **Admin-only (CRITICAL):** confirm every config-edit endpoint is behind the admin policy — a parent/student/unauthenticated caller must not edit the economy. The economy is revenue-load-bearing; an authz hole here is high-severity.
- **Audit completeness:** confirm every change writes who/when/old→new (non-repudiation for an economy change).
- **Validation can't be bypassed:** the cross-field rules (grant ≥ daily cap, non-negative, pack > 0) must run server-side via `ValidationBehavior`, not only in the admin UI.
- **No retroactive re-charge:** confirm a config change cannot trigger a re-charge or rewrite of past `Spend` rows (AC-3) — verify the ledger is untouched by config updates.
- **No secrets in config:** plan/pack *prices* are config, but payment-gateway keys/secrets are NOT (those belong to the payment story P9-06 + secret store) — confirm no payment secrets leak into `BillingConfig`.

## Handoff → api-tester

- Admin updates a per-action cost → a new version is created, audit recorded (who/when/old→new), the next spend (P9-03) uses the new cost, **a prior `Spend` row is unchanged** (never-retroactive).
- Admin updates the monthly grant → P9-02's next grant uses the new amount; the current cycle's already-granted balance is unchanged.
- Validation: negative cost / zero pack size / grant < daily cap → rejected with a clear message, no version created.
- Authz: a non-admin (parent/student) call → 403/unauthorized, no change.
- History read returns the version trail.
- Defaults: the seeded initial version returns the story defaults (199/300/3000/20/150/500/1,3,5,5).

### Risks (top 3)
- **R1 — retroactive re-charge bug** (a config change rewriting past `Spend` rows) = fairness/ledger-integrity violation. **Mitigation:** effective-dated versions + immutable ledger; explicit api-tester never-retroactive case.
- **R2 — authz hole** on the config endpoints = anyone tuning the economy. **Mitigation:** admin policy on every endpoint; security-auditor authz gate.
- **R3 — bad config slipping through** (grant < daily cap, negative cost) = broken economy / UX. **Mitigation:** server-side `ValidationBehavior` cross-field rules; api-tester rejection cases.
