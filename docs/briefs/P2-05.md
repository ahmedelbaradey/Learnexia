## Business context & value
- **Who benefits:** the **student** primarily — this is the page where actual learning happens. The **frontend** team — P2-05-FE renders the lesson screen (tutor bubble, visual area, hearts/streak, embedded quick-check) and needs one assembly endpoint to drive it without orchestrating 3 calls. The **parent** indirectly — every completed lesson contributes to the dashboard signal (Phase 5). The **Learning Path Engine** (P2-04) — its `Completed` derivation finally gets real production signal.
- **Why it matters now:** P2-01..P2-04 + P2-06..P2-08 + P2-10..P2-11 all shipped; **P2-05 is the missing first-class user surface** that ties the Phase-2 backend together. Without it, the FE has to compose the page from 3 separate calls (`GET lesson` → `POST Quizzes/{lessonId}/Attempt` → `POST …/Answers` → `POST …/Complete`) and the lesson has no explanation/visual content to render. With it, the lesson is one GET + the existing 3-call quiz flow (or one wrapper call, per Q3 below).
- **Success measure:** (a) `GET /api/Learning/Lessons/{id}` returns a populated `{ name, difficulty, sequenceOrder, skillId, explanation, visual, quickCheck }` for at least one seeded demo lesson; (b) `quickCheck` carries no `CorrectAnswer`; (c) the existing quiz-attempt flow continues to record per-lesson `Attempt.Status==Completed` rows which the engine reads; (d) reproducible (no clock-dependent fields in the response); (e) `LessonCompletedIntegrationEvent` continues to fire as it does today (no regression).

## Open questions for the lead — recommended defaults
Listed in order of "must-resolve before backend-feature starts." Two genuine forks (**Q1** and **Q3**) — the rest have safe defaults the lead can approve in one line.

### Q1 — Schema for `Explanation` + `Visual` content (genuine fork)
The current `Lesson` row has no place for either. Three options:
- **(A) [RECOMMENDED]** **Add two nullable columns to `Lesson`:** `Explanation : text?` + `Visual : text?`. **Cheapest**; matches AC4's "seeded/static content"; one migration; one update to `LessonsProfile` + `LessonDto`; the column shape is neutral when P3-04 swaps in the AI source. **Trade-off:** if P3-04 needs versioned/templated explanations or multiple visuals per lesson, a future migration will lift these into a child table.
- **(B)** **New `LessonContent` table** with `LessonId` FK (one-to-one) + `Explanation` + `Visual` + future fields (`Audio`, `Version`, `Locale`). Future-proof for multi-version / multi-locale content + AI-generated variants alongside hand-authored seed; **more complex**; requires migration + new entity + repository surface. Probably overkill for Phase 2; the right shape if P3-04 explicitly needs versioned content (it doesn't, per the SRS today).
- **(C)** Store both inside a single JSON `Content` column on `Lesson` (mirrors `QuizQuestion.Content`-style jsonb). Flexible; lets the FE evolve the shape without further migrations. **Trade-off:** harder to query/index; the schema documentation moves into the DTO + a comment.

**Recommend (A)** — two nullable columns. Defer (B) until a P3-04 / content-authoring story needs versioning.

### Q2 — Quick-check selection rule
"Embedded quick-check question" — is it a single `QuizQuestion` flagged as the quick-check, or "the lesson's first question"? Today `QuizQuestion` has **no order column and no quick-check flag**. Options:
- **(A) [RECOMMENDED]** **Return the lesson's first `QuizQuestion` by `Id ASC`** (insertion order). Simplest; no schema change; matches the seeder pattern (one quick-check per lesson). **Trade-off:** when P3-05 starts generating multiple questions per lesson, "first by `Id`" is fragile — but by then we'll have a sequencing column anyway.
- **(B)** Add `IsQuickCheck: bool` (or `Order: int`) to `QuizQuestion`. Another migration; over-engineered when the seeder only authors one question per lesson.
- **(C)** Use `Difficulty = DifficultyLevel.Easy` as the implicit "quick-check" filter. Couples two unrelated concepts.

**Recommend (A)** — first-by-Id. The `StartAttempt` flow already takes all questions of the lesson; the lesson-open endpoint just takes the first one for preview.

### Q3 — `CompleteLessonCommand` vs reuse of `CompleteAttemptCommand` (genuine fork, CRITICAL)
P2-08 already shipped the full record-attempt loop:
- `POST /api/Learning/Quizzes/{lessonId}/Attempt` — start attempt (P2-06)
- `POST /api/Learning/Quizzes/{attemptId}/Answers` — submit answer (P2-08)
- `POST /api/Learning/Quizzes/{attemptId}/Complete` — finalize attempt + publish `LessonCompletedIntegrationEvent` (P2-07/P2-08)

P2-05 BE-3 says "record lesson attempt + mark lesson progress on quick-check completion." For a lesson whose quick-check is a single `QuizQuestion`, this is **exactly what the existing flow does** when the student starts an attempt, submits the one answer, and completes the attempt. `LearningPathEngine` already reads `Attempt.Status==Completed` as "lesson completed."

Options:
- **(A) [RECOMMENDED]** **Reuse the existing flow; ship NO new command/endpoint.** P2-05 BE-3 becomes: (1) confirm the flow works end-to-end for a seeded quick-check lesson; (2) document the FE contract — for the lesson-open page, the FE calls `GET Lessons/{id}` to render, then calls `POST Quizzes/{lessonId}/Attempt` → `POST …/Answers` → `POST …/Complete` to record completion. No new code, just an api-tester end-to-end test + a HANDOFF note.
- **(B)** **Add `CompleteLessonCommand` as a thin convenience wrapper** at `POST /api/Learning/Lessons/{lessonId}/Complete`. Body carries the quick-check answer payload; the handler internally orchestrates StartAttempt (or resume) → SubmitAnswer → CompleteAttempt and returns an `AttemptSummaryDto` + the quick-check feedback (`IsCorrect`, `CorrectAnswer`). Reduces FE round-trips from 3 to 1 and gives the FE a single failure surface. **Trade-off:** duplicates 3 handler call sites' invariants in a wrapper; if the inner commands evolve (validations, events), the wrapper must keep up. Also crosses the line on CLAUDE.md rule 8 (the "wrapper" itself is fine as it's not a design pattern, but it's a new abstraction).
- **(C)** **Add a separate `LessonProgress` entity** with `(StudentId, LessonId, CompletedAt)`. **Reject** — P2-04 already derives progress from `Attempt.Status==Completed`; adding a parallel signal creates a sync bug surface.

**Recommend (A)** — no new endpoint. The 3-call flow is already authenticated, event-publishing, idempotent, and consumed by P2-04. If the lead prefers (B), the planner adds a 4th batch and bumps SP. **Lead must pick before backend-feature starts.**

### Q5 — Authorization on `GET /api/Learning/Lessons/{id}`
Today the endpoint is **anonymous**. Options:
- **(A) [RECOMMENDED]** `[Authorize]` (any authenticated user — Student, Parent, future Admin). Matches the P2-04 tightening of `Subjects/{id}/Lessons` and `…/SkillTree`. Parents can preview their child's lesson; admins (later) can preview content.

### Q6 — Lock state on lesson open
If a student opens a `Locked` lesson (per `LearningPathEngine`), should the endpoint return 200 or 403?

**Recommend (200)**. The lock concept is enforced at **`StartAttempt`** (Q6.b — see "Risks" — actually that's not enforced either today, see Risk R3 below). Treating lesson-open as a read-only preview lets parents/admins inspect locked content and lets the FE render-and-warn using the `Subjects/{id}/Lessons.State` field from P2-04. **Do not enforce lock at lesson-open in this story.**

### Q7 — Does `GET Lessons/{id}` auto-create an Attempt?
**Recommend NO**. Keep lesson-open (read-only) separate from start-attempt (state-mutating). The FE calls lesson-open to render the page, then start-attempt when the student presses "Start." Auto-creating an attempt on render would conflate intent and break the P2-06 "resume in-progress" semantics.
