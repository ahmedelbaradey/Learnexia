- **Who benefits:** Parents (set up the family, provision children, manage access) and children (a one-tap login in their own language). Admin is out of scope (P1-10, separate app).
- **Value:** This is the front door of the product — the first screens any real user touches. Until P1-09 ships, the merged backend Identity APIs and the foundation packages have **no running app** exercising them. Success = a parent can register, add one or more children with grade/language/country, and a child can log in and land on a (placeholder) home in their chosen language with correct RTL.
- **Success measures:** parent register→onboarding→add-child happy path completes end to end; child login routes to a localized home; all screens render correctly in ar (RTL) and en at web 390/768/1024 and on native; session survives reload and silently refreshes; sign-out ends the session.

## Acceptance criteria (testable)
Shell & session:
- [ ] `apps/student-app` boots as an Expo app (web + native) with Metro/Babel/Tamagui compiler configured and Expo Router file-based routing.
- [ ] At boot, `authStore.hydrate()` runs against the platform token storage; the root layout routes signed-in users to their home/onboarding and guests to `(auth)`.
- [ ] Token storage is wired: `createNativeTokenStorage(SecureStore)` on native, the web strategy on web (both already in `@learnexia/shared`).
- [ ] A silent-refresh failure (expired/revoked refresh token) routes the user to login with a gentle message; sign-out clears tokens and calls `Sign-Out`.

Parent register & login:
- [ ] Parent register form (email, password, confirm) validates client-side (zod, password policy mirroring backend) and posts to `Register-Parent`; on success persists JWT via `authStore.setTokens` and routes into onboarding.
- [ ] Duplicate-email and weak-password backend errors (in `BaseResponse.errors` / 422) are surfaced as inline, localized messages; no client crash.
- [ ] There is **no** student self-registration route — only parent Register and the shared Login.
- [ ] Login posts to `Sign-In`; invalid-credentials error is shown clearly.

Onboarding & add-child:
- [ ] An authenticated parent can add a child with: full name, parent-assigned login email, password, grade (1–6 selector), language (ar/en), country — posting one `Add-Child` call per child.
- [ ] The parent can add multiple children (list editor: add/edit/remove) before finishing; each child is a separate `Add-Child` call.
- [ ] Invalid grade (outside 1–6), duplicate email, and weak password are surfaced per child with specific messages; no account created on failure.
- [ ] No child-facing onboarding/self-onboard route exists.

Linkage & child login:
- [ ] "My Children" lists the parent's linked children from `My-Children`; a child switcher writes `childContextStore.activeChildId`.
- [ ] A parent can link an additional existing child via `Link-Child` (child email); a non-existent child shows a clear error.
- [ ] A child signs in via the Login screen with the parent-assigned email and lands on a (placeholder) home in the child's chosen language with correct RTL for Arabic.

RTL/i18n:
- [ ] All auth/onboarding screens render correctly in Arabic (RTL) and English using `@learnexia/design-system` tokens + `@learnexia/ui`; verified at web 390/768/1024 and on native.
- [ ] New screen copy is added to the i18n `auth`/onboarding namespaces (ar + en) — current resources are seed-only.

## Handoff → backend-feature
Likely **no new .NET features required** for the core flow — the endpoints exist. But there is a real contract gap to resolve before the frontend guard can be built:

**Verified existing endpoints (from this worktree's controllers — NOT from the stale generated types):**
- `POST /api/Users/Authentication/Register-Parent` — body `{ Email, Password, FullName? }` → `BaseResponse<JwtAuthResponse>`. (`...\AuthenticationController.cs:20`)
- `POST /api/Users/Authentication/Sign-In` — body `{ userName, password }` → `BaseResponse<JwtAuthResponse>`.
- `POST /api/Users/Authentication/Refresh-Token` — body `{ accessToken, refreshToken }` (already wired in `apiClient.ts`).
- `POST /api/Users/Authentication/Sign-Out` — requires the access token.
- `POST /api/Users/Parent/Add-Child` — `[Authorize(Roles="Parent,Admin,SuperAdmin")]`; body `{ FullName, Email, Password, Grade(1–6), Language("ar"|"en"), Country }` → `BaseResponse<AddedChildResponse{ Id, FullName, Email, Grade?, Language, Country }>`. Single child per call; parent resolved from JWT. (`...\ParentController.cs:26`)
- `POST /api/Users/Parent/Link-Child` → `BaseResponse<LinkedChildResponse{ Id, FullName, Email }>`.
- `GET /api/Users/Parent/My-Children` → `BaseResponse<IEnumerable<LinkedChildResponse>>`.

**GAP — flag to the lead (blocks P1-09-FE-4 "route by Me"):**
- The story/task assumes a `Me` endpoint returning **role + onboarding-complete + language** to drive the post-login redirect. **It does not exist.** `JwtAuthResponse` carries only `accessToken/refreshToken/userId/isFirstLogin/sessionTimeout/sessionId` — **no roles, no onboarding flag**. The legacy `GET /api/Users/UserManagement/GetUserProfile` takes a `userId` query and returns admin/template fields (IBAN, passport, CV, `registrationIsCompleted`, `roles`) — it is the source-template's admin profile, not a clean parent/child "Me".
- **Decision needed (recommend backend-feature adds a small `Me` endpoint):** the cleanest fix is `GET /api/Users/Authentication/Me` (or `/api/Users/Me`) returning `{ userId, roles[], preferredLanguage, onboardingComplete }` resolved from the JWT. Alternatives the lead may prefer: (a) decode roles from the JWT claims client-side (roles are in the token) and infer onboarding-complete from `My-Children` being non-empty for parents / from `isFirstLogin` for children; (b) extend `JwtAuthResponse` to include roles + onboarding flag. **Flag this; do not guess.** Until resolved, the frontend can ship using JWT-claim decoding for role and `My-Children`/`isFirstLogin` heuristics for onboarding state — call this out as a temporary approach.

**Also note (stale artifact, not a backend code bug):** `packages\api-client\src\generated\api-types.ts` pre-dates the P1-01/03/04 merges — it lacks `Register-Parent`, `Parent/Add-Child`, `Parent/Link-Child`, `Parent/My-Children`. Regenerating it (`pnpm gen:api` against the running backend Swagger) is a prerequisite for typed hooks. The frontend agent should regenerate it (or hand-add the DTO aliases) as part of the api-client extension — flag if Swagger isn't reachable.

If the lead approves the `Me` endpoint, run **backend-feature → api-tester → security-auditor (auth/child-data) → reviewer** for that small slice before/parallel to the FE shell.

## Open questions / assumptions / risks
1. **`Me` endpoint (BLOCKER for routing).** No endpoint returns role + onboarding-complete + language. Recommend a small backend `Me`; otherwise approve the temporary JWT-claim-decode + `My-Children`/`isFirstLogin` heuristic. **Lead must decide before the routing guard is built.**
2. **Onboarding-complete signal.** Even with `My-Children`, "has children" ≠ "onboarding complete" (a parent could register and quit). Is there a persisted onboarding-complete flag, or do we treat "≥1 child" as complete? Confirm with the lead.
3. **Add-Child is single-child per call** (confirmed in controller) — the FE loops for siblings and must handle partial failure (child 2 of 3 fails): which children were created? Assume per-child optimistic add with per-row error; confirm desired UX.
4. **Child language → locale on login.** `My-Children`/`LinkedChildResponse` does NOT include grade/language (module-isolation note in `LinkedChildResponse.cs`). On child login, how does the app learn the child's chosen language to set locale? `JwtAuthResponse` has no language field either. Likely needs the `Me` endpoint to return `preferredLanguage`. **Tie to Q1.**
5. **Stale generated types / Swagger reachability.** `generated/api-types.ts` must be regenerated against the running backend. Assumption: backend runs locally and Swagger is reachable for `pnpm gen:api`. Flag if not.
6. **`ui` form primitives.** No TextField/Select exported. Assumption: add reusable form primitives to `packages/ui` (shared edit). Confirm vs. app-local.
7. **Web token storage security.** `shared/storage/web.ts` strategy — confirm it meets the security bar (httpOnly cookie vs. web storage). The security-auditor should review since this is child + auth data.
8. **COPPA/parental consent** (BRD §10, noted in P1-03/P1-04 stories) — tracked separately; not in P1-09 scope. Assumption: no consent gate this story.
9. **Splash/onboarding visual source** = kids-UI wireframes, reframed parent/child, no teacher role — designer to reconcile stale wireframe actors.
