## Summary & traceability
- **Task (1 line):** Add a scheduled, de-identified calibration loop in the Learning module that computes per-question empirical difficulty, raises **human-promotable** difficulty-recalibration proposals when empirical diverges from the authored band, **auto-flags** poor AI-generated questions out of auto-serve, and exposes an AdminOnly review/promote/reject API — never silently overwriting authored content.
- **User story:** P5-07 (Phase 5 — Parent + Analytics, Week 8). Epic: Analytics & Insights. SP 5.
- **FR-ID:** FR-PA-4 (data feedback / calibration — SRS §4.7).
- **BRD goal / strategy:** Barrier-to-entry **BE7 "data network effect"** — turn collected-but-dormant signals into a compounding moat. Closes gap **3a-7**.
- **Depends on (all built):** P2-08 (answer signals), P3-06 (`GeneratedBy` provenance), P5-03 (analytics), P7-04/P7-05 (`IsActive`/`LifecycleState`). Synergizes with P3-13 (richer signals).
- **Approved safety model (LOCKED):** PROPOSE-ONLY + human promotion. Authored content never auto-overwritten; AI questions auto-flagged (excluded from auto-serve), not auto-served.
- **Approved scope (LOCKED):** FOCUSED SLICE = BE-1 + BE-2 + BE-3 + BE-5 + BE-6 + BE-7. **BE-4 DEFERRED.**

## Business context & value
- **Who benefits:** the platform / every future student (the network effect), the content/admin team (data-driven quality control), and indirectly each student (better-calibrated difficulty + fewer broken AI questions in the adaptive path P3-08/P3-11).
- **Value:** today raw signals are captured (`StudentAnswer.IsCorrect/TimeSpentSeconds/HintUsed`) and AI provenance is tagged (`GeneratedBy`), but nothing consumes the aggregate to improve the system. This story makes the data compound: each cohort's outcomes recalibrate difficulty and weed out bad AI questions for the next cohort — the "hard for a newcomer to replicate" moat.
- **Success measure:** proposals are generated for questions whose empirical difficulty diverges from authored; admins can promote/reject; bad AI questions stop being served; **zero per-child identifiers** persisted or logged in the calibration pipeline.

## Acceptance criteria (testable, this slice)
1. A Hangfire recurring job (mirrors `Rec-Recompute`) runs on a schedule, sweeps `QuizQuestion`s that have answer data, and **upserts** one `QuestionDifficultyStats` row per question with: p-value (% correct), avg time-to-answer, hint-usage rate, `SampleSize`, `ComputedAtUtc`. Idempotent (re-running overwrites the same row) and fail-soft per question.
2. The aggregation query **groups by `QuestionId` and outputs counts/aggregates only** — no `childId`/`StudentId` selected, persisted, or logged. (Verified feasible: see Handoff → db-migration.)
3. When empirical difficulty band diverges from authored `Difficulty` beyond `DivergenceThreshold` **AND** `SampleSize >= MinSamples`, a `QuestionRecalibrationProposal` (`Pending`) is written carrying authored band, proposed band, evidence (p-value, sample size), and a reason. The authored `QuizQuestion.Difficulty` is **never mutated** by the job.
4. Re-running the job **updates the open `Pending` proposal** for a question (or no-ops if unchanged) — it does not create duplicate open proposals.
5. For `GeneratedBy != Curated` (i.e. AI) questions with extreme p-value (past `AiFlagLowPValue`/`AiFlagHighPValue`) and `SampleSize >= MinSamples`, the question is flagged (`QualityState = FlaggedForReview`) with a stored reason, and **excluded from the auto-serve candidate pool** (`StartAttemptService.GetPublishedActiveQuestionsAsync`). In-flight attempts that already served the question still score normally.
6. AdminOnly API (`[Authorize(AdminOnly)]`): list open proposals (paged), list flagged questions (paged), **Promote** (apply proposed band / confirm-or-clear flag, audited via `AdminActionPerformedDomainEvent`), **Reject** (close proposal / unflag, audited). All responses use `BaseResponse<T>`/`Successed`/`NewResult`; all user-facing messages localized EN + AR.
7. Promote/Reject are reversible and explainable: the proposal retains its evidence + final state; an admin action audit event is raised; no destructive deletion of the original authored band history.

## Handoff → backend-feature (BE-1, BE-2, BE-3, BE-5)

### Pattern to mirror (verified)
- **Job:** `Infrastructure/Jobs/RecommendationRecomputeJob.cs` — `sealed class`, injects `IServiceScopeFactory` + `ILoggerManager`, `[DisableConcurrentExecution(300)]`, `Execute(CancellationToken)`, creates its own `CreateAsyncScope()`, resolves service + `LearningDbContext`, fail-soft per item, commits with `SaveChangesAsync(userId: 0)` (system actor) **outside** the UoW pipeline (ADR-0001 — background jobs own their commit). - **Engine/Service split:** pure rule logic (empirical p-value → band; divergence test; AI-flag bounds) as a **pure static** engine in `Application/Services` (mirror `RecommendationEngine` — no I/O, deterministic, no design pattern — rule #8). The I/O orchestrator (`CalibrationService` in `Infrastructure/Service`, Option C — EF only here, behind an `ICalibrationService` interface in `Application`) pre-fetches aggregates, calls the engine, upserts rows.
- **Options binding:** `CalibrationOptions` in **Domain/Services** (mirror `RecommendationOptions`/`AdaptivityOptions` — `const string SectionName`, defaults on properties), bound in `DependencyInjection.cs` via `services.Configure<CalibrationOptions>(configuration.GetSection(CalibrationOptions.SectionName))`. Add the section to `appsettings.json`.

### BE-1 — aggregation
- Aggregation query (in `CalibrationService`, Infrastructure): group `StudentAnswers` by `QuestionId`, project counts only:
  - `SampleSize = COUNT(*)`, `PValue = AVG(CASE WHEN IsCorrect THEN 1 ELSE 0 END)`, `AvgTimeSpentSeconds = AVG(TimeSpentSeconds)`, `HintUsageRate = AVG(CASE WHEN HintUsed THEN 1 ELSE 0 END)`.
  - **Do NOT select `StudentId`/`AttemptId.StudentId`** anywhere in the projection (AC5). Use `AsNoTracking`.
- Upsert one `QuestionDifficultyStats` per question (mirror `UpsertStudentRecommendationAsync`: lookup-by-key → Add or mutate-in-place). Idempotent.
- Add repository methods to `ILearningRepository`/`LearningRepository` for the group-by read + upsert (mirror existing recommendation repo methods).

### BE-2 — recalibration proposals (engine + job step)
- Empirical-difficulty → band mapping (**pure engine**, config-driven thresholds):
  - p-value HIGH (many correct) ⇒ question is easy; p-value LOW ⇒ hard. Map p-value to `DifficultyLevel` via two cut points, e.g. `EasyMaxPValueLowerBound` / `HardMaxPValueUpperBound`:
    - `PValue >= EasyThreshold` (e.g. 0.85) → empirical = Easy
    - `PValue <= HardThreshold` (e.g. 0.45) → empirical = Hard
    - else → Medium
  - **Divergence test:** empirical band != authored `Difficulty` (treat as ordinal distance; `DivergenceThreshold` can be "any band difference" v1, or a magnitude if a 5-band scale is later introduced). Require `SampleSize >= MinSamples`.
- On divergence + enough samples: upsert the open `Pending` proposal for that question (update if exists, else insert) carrying authored snapshot, proposed band, evidence, reason. **Never** mutate `QuizQuestion.Difficulty`.

### BE-3 — AI-question flagging (engine + job step + serve-path exclusion)
- Engine rule: `GeneratedBy != Curated` (AI) AND `SampleSize >= MinSamples` AND (`PValue >= AiFlagHighPValue` OR `PValue <= AiFlagLowPValue`) ⇒ set `QualityState = FlaggedForReview` + store reason. (Optionally also factor "frequent reports" — **no report signal exists today**, see OQ-7; v1 uses p-value extremes only.)
- **Serve-path exclusion (single point, verified):** `Infrastructure/Service/StartAttemptService.GetPublishedActiveQuestionsAsync` (lines 57-63) is the ONLY auto-serve candidate-pool query. Add `&& q.QualityState == QuestionQualityState.Approved` (alongside the existing `IsActive && LifecycleState == Published`). The two `AttemptWriteService.QuizQuestions` reads are scoring/mastery-time (post-serve) and `GetQuestionForAnswerAsync` scores an already-served question — **do not** filter those, so in-flight attempts still score correctly.
- The job mutates `QuizQuestion.QualityState` directly (a controlled system-side flag, not authored content) — this is allowed and reversible via BE-5. It does NOT touch `Difficulty`, `QuestionText`, `Options`, or `CorrectAnswer`.

### BE-5 — AdminOnly review/promote/reject API
- Mirror `QuestionsController` (`[Route("api/Learning/[controller]")]`, `: AppControllerBase`, `[Authorize(Policy = AuthorizationPolicies.AdminOnly)]` per action, `NewResult(await Mediator.Send(...))`, `[ProducesResponseType(typeof(BaseResponse<...>), 200)]`). Suggested `CalibrationController` (route `api/Learning/Calibration`).
- Endpoints:
  - `GET /Proposals?status=Pending&page=&pageSize=` → paged list of `QuestionRecalibrationProposal` DTOs (include evidence + authored/proposed bands).
  - `GET /Flagged?page=&pageSize=` → paged list of flagged `QuizQuestion`s (id, lesson, generatedBy, p-value, reason).
  - `POST /Proposals/{id}/Promote` → apply `ProposedDifficulty` to the `QuizQuestion` (the ONE place authored band is changed — by a human), set proposal `Promoted`, raise `AdminActionPerformedDomainEvent`.
  - `POST /Proposals/{id}/Reject` → set proposal `Rejected`, audit event, no band change.
  - `POST /Flagged/{questionId}/Confirm` (keep flagged / take further action) and `POST /Flagged/{questionId}/Clear` (set `QualityState = Approved`, re-enable serving), both audited.
- Handlers: `BaseResponseHandler` + `ICommandHandler`/`IQueryHandler`, `IStringLocalizer<SharedResources>` with NEW `SharedResourcesKey.*` constants (add EN + AR strings to `SharedResources.en-US.resx` + `SharedResources.ar-EG.resx` + the key constant). Commands run inside `UnitOfWorkBehavior` (ICommand) → atomic + post-commit audit dispatch. Queries are NOT auto-validated — validate inputs in-handler.
- **Audit:** reuse `AdminActionPerformedDomainEvent` (`Shared.Contracts.Admin.AdminActions`) on the tracked aggregate (`QuestionRecalibrationProposal`/`QuizQuestion`) exactly like `SetQuestionActiveCommandHandler` does — gives AC4 auditability + reversibility for free. May need new `AdminActions` constants (e.g. `DifficultyProposalPromoted`, `QuestionUnflagged`).

## Handoff → api-tester (after backend-feature)
Integration scenarios (running API):
1. **Aggregation correctness:** seed answers for a question (mix of correct/incorrect, varied times, some hints) → trigger the job (or its service) → `QuestionDifficultyStats` row has correct p-value/avg-time/hint-rate/SampleSize. Re-run → row updated, not duplicated (idempotent).
2. **No-PII guarantee:** inspect the `QuestionDifficultyStats` + `QuestionRecalibrationProposal` tables and job logs after a run → **no `StudentId`/childId** column or value anywhere. (Pairs with security-auditor.)
3. **Proposal raised on divergence:** authored=Easy but empirical p-value low (hard) with `SampleSize >= MinSamples` → exactly one `Pending` proposal with correct authored/proposed/evidence; authored `Difficulty` unchanged. Below `MinSamples` → no proposal.
4. **Proposal idempotency:** re-run job → open proposal updated, no second `Pending` row.
5. **AI flagging + serve exclusion:** AI question with extreme p-value + enough samples → `QualityState=FlaggedForReview`; then `StartAttempt` for its lesson → flagged question NOT in the served set. Curated question with same signals → NOT flagged.
6. **In-flight scoring unaffected:** a question served before being flagged still scores via SubmitAnswer.
7. **AdminOnly auth:** all BE-5 endpoints → 401/403 without an admin token (and as a student token); 200 with admin.
8. **Promote applies band (human-only):** `POST Promote` → `QuizQuestion.Difficulty` becomes `ProposedDifficulty`, proposal `Promoted`, audit event recorded. **Reject:** proposal `Rejected`, band unchanged.
9. **Unflag re-serves:** `Clear` a flagged question → it reappears in the served pool.
10. **Pagination + localization:** list endpoints page correctly; messages return AR under `Accept-Language: ar`.

Verify job log statements contain only question-level counts (mirror the recommendation job's log shape, which logs counts not student data).

5. **Audit completeness:** promote/reject/flag-clear raise `AdminActionPerformedDomainEvent` (who/what/when) for traceability.

## Open questions / assumptions / risks
- **OQ-1 (aggregation scope):** Aggregate over ALL `StudentAnswer` rows for a question, or only answers from **completed** attempts (`Attempt.Status == Completed`)? Completed-only is cleaner signal (abandoned attempts skew p-value/time) but requires joining `Attempt`. **Assumption (v1):** include all answers; revisit if noise. Lead to confirm.
- **OQ-2 (FK vs loose int):** Should `QuestionDifficultyStats.QuestionId` / `QuestionRecalibrationProposal.QuestionId` be a real intra-module FK to `QuizQuestion` (like `StudentAnswer.QuestionId`, Restrict) or a plain indexed int? FK gives integrity but means a soft-deleted/hard-deleted question interaction to consider. **Recommendation:** real intra-module FK with `Restrict` (consistent with `StudentAnswer`), since both stay inside the Learning schema. Lead to confirm.
- **OQ-3 (one-open-proposal enforcement):** Enforce "at most one `Pending` proposal per question" via a **partial unique index** (`WHERE Status=1`) at the DB level, or only in job logic? DB-level is safer against races but Postgres-specific syntax in the migration. **Recommendation:** partial unique index. Confirm acceptable.
- **OQ-4 (flag shape):** `QualityState` enum (`Approved`/`FlaggedForReview`) + separate `FlagReason string?`, vs a single `bool FlaggedForReview`? Brief assumes the enum+reason shape for explainability (AC4). Lead/designer to confirm naming.
- **OQ-5 (p-value units & band cut points):** Express p-value as 0.0–1.0 or 0–100? And what are the **default** Easy/Hard cut points and `DivergenceThreshold`, `MinSamples`, `AiFlagLowPValue`/`AiFlagHighPValue`? These are product tunables. **Proposed v1 defaults:** p-value 0.0–1.0; `MinSamples=30`; Easy if p>=0.85, Hard if p<=0.45 (Medium between); AI flag if p>=0.95 or p<=0.20; divergence = any band mismatch. **These are guesses — lead/product should sign off** (they drive how aggressive calibration is).
- **OQ-6 (reason localization):** `Reason` stored as machine text — store a **stable reason code** + render localized strings in BE-5 DTOs (preferred), or store English now and defer localization? Note: prior P5 stories deferred "localize persisted recommendation strings." **Recommendation:** store a reason code, localize at read. Confirm.
- **OQ-7 (reports signal absent):** The story mentions "frequent reports" as an AI-flag input, but **no question-report mechanism exists in the codebase today** (verified — no report entity/signal). v1 uses p-value extremes only. Flag whether a report signal is in scope elsewhere or a future enhancement.
- **OQ-8 (cron schedule):** What cadence — daily (after `Rec-Recompute` at 00:05), weekly, or less frequent? Calibration over slow-changing aggregates likely doesn't need daily. **Assumption:** daily off-peak (config-driven cron). Confirm.
- **Risk — small samples:** early-cohort questions will have tiny `SampleSize`; `MinSamples` gating is the guard. Set conservatively to avoid noisy proposals/flags.
- **Note vs task file:** the task file's BE-1 line hedges that hint-usage "comes in via `HintUsedIntegrationEventHandler`." **Verified:** hint usage is persisted directly on `StudentAnswer.HintUsed` (the handler writes that column) and is fully queryable per question via `IX_StudentAnswers_QuestionId` — **no event replay needed** for aggregation. This simplifies BE-1.
