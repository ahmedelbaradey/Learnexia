# Pipeline Brief — P7-13 Gamification admin overrides (BACKEND ONLY)

## Summary & traceability
- **Task (1-line):** add an `AdminOnly`, audited **write surface** on top of the shipped Phase-4 Gamification engine so an admin can override league tiers, CRUD the badge & mission catalogs, write/transition timed events, and grant streak-freezes — each with a required **reason** and a post-commit `AdminActionPerformedEvent` audit record.
- **User story:** [user-stories/Phase-7-Admin-Console/P7-13-gamification-admin-overrides.md](../../user-stories/Phase-7-Admin-Console/P7-13-gamification-admin-overrides.md) (SP 8, Epic "Admin — Gamification Management").
- **BE task file:** [tasks/Backend/Phase-7-Admin-Console/P7-13-BE.md](../../tasks/Backend/Phase-7-Admin-Console/P7-13-BE.md) (BE-1..BE-9).
- **FR-IDs:** story cites **FR-ADM-8**, but FR-ADM-8 (SRS §4.9 line 124) is the *content-moderation queue* (story P7-09) — **this is a mis-trace** (see Open Question Q0). The actual functional anchor for admin gamification writes is **FR-ADM-1/2/12** (admin manages platform config; admin-only + audited) and the **FR-GM-*** engine requirements being overridden (FR-GM-1 XP/levels, FR-GM-2 streaks + freeze, FR-GM-4 badges, FR-GM-6 leagues/tiers, timed events). Needs a lead tie-break before the planner locks traceability.
- **BRD goal:** **G5** (operability / admin tooling) primary; **G4** (retention via correct gamification state) secondary.
- **Phase / epic:** Phase 7 — Admin Console; post-MVP write surface over the merged Phase-4 engine.

> **Critical scope correction vs the task file.** The BE task file's "Contract for Frontend" and AC list describe FOUR override areas + streak-freeze: (1) **league tier override**, (2) **badge catalog CRUD**, (3) **mission catalog CRUD**, (4) **timed-event write/transition**, (5) **streak-freeze grant**. It does **NOT** include set/adjust **XP**, **level**, **hearts**, or direct **badge grant/revoke to a student**. The dispatch prompt asks about XP-set/level-recompute/hearts/badge-grant-revoke semantics — **those quantities are out of scope for P7-13 as written**. If the lead wants them, that is a scope expansion (Q1). The brief below is written to the story's actual ACs; the XP/level/hearts/badge-grant questions are surfaced as Open Questions rather than specced in.

## Business context & value
- **Who benefits:** the **admin/ops** persona (the only privileged role — no teacher role). Downstream value to **students/parents** is indirect: corrected league standings, fixed catalog metadata, promo timed events, and support-case streak-freeze grants without hand-editing seed data or the DB.
- **Value:** the entire Phase-4 engine shipped **read-only** for admins (only `GET api/admin/timed-events` exists; everything else is student-self or job-driven). P7-13 is the operational lever to correct mistakes, run promotions, and resolve support tickets safely and auditably.
- **Success measure:** every override persists, is reflected in the live engine (standings/catalog/missions/freeze balance), and produces exactly one immutable audit row (actor + timestamp + target + old→new + reason) with no child PII; non-admins get 403.

## Acceptance criteria (testable)
1. **League tier override** — `POST` overriding a child's tier in the active league window persists the new tier, is applied to live standings, requires `reason` + `confirm`, rejects unknown tier and no-op, and is audited.
2. **Badge catalog CRUD** — create/edit/**deactivate** a `BadgeDefinition` (code, name, description, icon, criteria fields, **active state**) persists and is reflected in the catalog students earn against; **deactivation does NOT retroactively strip already-earned `StudentBadge` rows**.
3. **Mission catalog CRUD** — create/edit/**deactivate** a `MissionDefinition` (code, copy, cadence daily/weekly/weekly-challenge, target, reward, **active state**) persists and is reflected in missions generated for students.
4. **Timed-event writes** — create/update + **activate/expire** transitions on `TimedEvent` (window start/end, multiplier, scope) persist and drive the engine; complements existing read-only `GET api/admin/timed-events`; invalid windows / illegal transitions → `Successed=false`.
5. **Streak-freeze grant** — granting a child N freezes increases `FreezeBalance` (bounded by `MaxFreezes`), is reflected in the engine, requires `reason` + `confirm`, and is audited.
6. **Audit on every write** — actor, timestamp, target, old→new, and reason recorded; before/after snapshots PII-safe (ids + values only).
7. **AdminOnly** — all new endpoints `[Authorize(Policy = AuthorizationPolicies.AdminOnly)]`; non-admin → 403.
8. **Seed-vs-admin precedence** — `BadgeSeeder`/`MissionSeeder` must **seed-if-absent** and never clobber admin-modified rows on the next boot.

## Affected modules & data (new vs existing)
**Module:** `Gamification` only (mirror its existing command/query/controller shapes; `Successed`, `NewResult(...)`, `ILoggerManager`, `BaseResponseHandler`). **Do not scaffold a new module.** Cross-module child targeting flows via `Shared.Contracts` only (no cross-module FK).

### Existing entities & how they're mutated today (code-grounded)
- **`StudentXpProfile`** (`Domain/Entities/StudentXpProfile.cs`) — `TotalXp`, `CurrentLevel`, `CurrentStreak`/`LongestStreak`/`LastActivityDateUtc`, `FreezeBalance` (private set; `const MaxFreezes = 2`), `Hearts`, `CurrentTier` (`LeagueTier`, private set). Mutated only through aggregate methods: `ApplyAward` (the single XP chokepoint → raises `XpAwardedDomainEvent` + conditional `StudentLeveledUpDomainEvent`), `AdvanceStreak/ResetStreakAndStart/BreakStreak`, `GrantFreeze(occurredAtUtc)` (+1, no-op at cap, raises `StreakFreezeGrantedDomainEvent`) / `ConsumeFreeze`, `LoseHeart/RegainHeartFromPractice`, `UpdateTier(LeagueTier)` (**no event raised today**).
- **`League`** (`CreationAuditedEntity`, append-only, no admin edits planned) + **`LeagueMembership`** (`WeeklyXp` internal set, `FinalRank/TierAfter/Status` stamped by `LeagueRolloverJob` via `FinalizePromotion`). The student's *current* tier lives on `StudentXpProfile.CurrentTier`; the *weekly cohort placement* lives on `LeagueMembership`. **An override must clarify which it writes** (Q-tier).
- **`BadgeDefinition`** (`FullAuditedEntity`) — `Code` (immutable per its own docstring), `Name`, `Description`, `IconKey`, `Rarity`, `SortOrder`, `TriggerType`, `Threshold`, `RewardXp`. **NO `IsActive` field today.** Only mutator is `UpdateMetadata(...)` (no Name/Description/Code change). `StudentBadge` (append-only ledger, RESTRICT delete FK to `BadgeDefinition`).
- **`MissionDefinition`** (`FullAuditedEntity`) — `Code`, `IconKey`, `TitleKey`, `Cadence` (`MissionType`), `TargetType`, `Target`, `RewardXp`, `SortOrder`. **NO `IsActive` field today.** Only mutator is `UpdateMetadata(...)`. Note: cadence is **Daily/Weekly** (`MissionType`); the story/task ask for **daily/weekly/weekly-challenge** — "weekly-challenge" has no enum value today (Q-mission).
- **`TimedEvent`** (`FullAuditedEntity`) — `Code`, `NameEn/Ar`, `DescriptionEn/Ar`, `StartUtc`, `EndUtc`, `Multiplier` [1.00..5.00], `Scope` (`TimedEventScope`), `IsActive`. Factory validates window+multiplier; `Activate()`/`Deactivate()` exist (today called only by `TimedEventSweepJob`). **No update mutator** for window/multiplier/copy exists yet → needs adding.

### New entities/fields likely required
- **`BadgeDefinition.IsActive`** (bool, default true) + migration. AC2 ("deactivate") cannot be satisfied without it. Add an `Activate/Deactivate` (or `SetActive`) mutator + allow `UpdateMetadata` to also touch Name/Description (currently immutable).
- **`MissionDefinition.IsActive`** (bool, default true) + migration. Same reasoning for AC3.
- **`TimedEvent` update mutator** (no new column; new method to edit window/multiplier/copy/scope with the factory's invariants re-applied).
- Optionally a **seed-source/ownership flag** on `BadgeDefinition`/`MissionDefinition` (e.g. `IsAdminEdited`/`Source`) to implement seed-if-absent precedence (BE-7, Q-seed) — only if the chosen precedence rule needs it.

**Migration needed? — YES (small).** Contrary to the prompt's "likely none", at minimum `IsActive` columns on `BadgeDefinition` and `MissionDefinition` are new columns (with the engine's earn/generation queries needing to filter on them). League tier, streak-freeze, timed-event-window writes are all over **existing** columns and need no migration. The db-migration agent should add: `IsActive` (Badge + Mission), the optional seed-ownership flag, and update both EF configs + the model snapshot.

## Handoff → db-migration
- **Add** `BadgeDefinition.IsActive` (bool, NOT NULL, default `true`) — backfill existing rows to `true`. Update `BadgeDefinitionConfig` + snapshot.
- **Add** `MissionDefinition.IsActive` (bool, NOT NULL, default `true`) — backfill `true`. Update `MissionDefinitionConfig` + snapshot.
- **(Conditional, pending Q-seed)** add a seed-ownership flag (`IsAdminEdited bool default false` or `Source` enum) to both catalog tables if the precedence rule is "flag-based".
- **(Conditional, pending Q-mission)** if "weekly-challenge" is a real third cadence, extend `MissionType` (enum stored as int) — additive value, no destructive change.
- **No new columns** for league-tier override, streak-freeze grant, or timed-event writes — all target existing columns.
- Mirror the existing Gamification migration style (`20260531075845_AddBadgeDefinitionAndStudentBadge` etc.); schema-per-module (`gamification`), `UseNpgsql`.

## Handoff → backend-feature
**Controller:** new `AdminGamificationController` in `Gamification.Api/Controllers`, routed `api/Admin/Gamification/*`, **every action** `[Authorize(Policy = AuthorizationPolicies.AdminOnly)]`. Mirror `GamificationController` + Learning's admin controllers. Resolve `AdminUserId` from the JWT via the module `ICurrentUserService` (`_currentUser.UserId.GetValueOrDefault()`) — never from a request body.

**Commands (all `ICommand<BaseResponse<T>>` so `ValidationBehavior` + `UnitOfWorkBehavior` run; FluentValidation validator each):**
1. `OverrideLeagueTierCommand(int ChildId, LeagueTier Tier, string Reason, bool Confirm)` → `BaseResponse<bool>`. Handler loads the child's `StudentXpProfile` (tracked), calls `UpdateTier(tier)`, and (per Q-tier) also restamps the active `LeagueMembership`/standings; rejects unknown tier + no-op (`Tier == CurrentTier`). Endpoint: `POST .../children/{childId}/league-tier`.
2. **Badge catalog**: `CreateBadgeDefinitionCommand`, `UpdateBadgeDefinitionCommand`, `SetBadgeDefinitionActiveCommand` (deactivate) + `GetBadgeDefinitionsQuery` (admin list — includes inactive). Requires the new `IsActive` field + an entity mutator that allows editing Name/Description/criteria (today `UpdateMetadata` excludes them). Endpoints `GET/POST/PUT/DELETE .../Badges[/{id}]` (DELETE = deactivate, not hard delete — AC2 preserves earned badges).
3. **Mission catalog**: `CreateMissionDefinitionCommand`, `UpdateMissionDefinitionCommand`, `SetMissionDefinitionActiveCommand` + `GetMissionDefinitionsQuery`. Validator enforces cadence/target/reward shape. Endpoints `GET/POST/PUT/DELETE .../Missions[/{id}]`.
4. **Timed events**: `CreateTimedEventCommand`, `UpdateTimedEventCommand`, `ActivateTimedEventCommand`, `ExpireTimedEventCommand` + reuse/extend the existing list query. Validator rejects `StartUtc >= EndUtc`, multiplier ∉ [1.00..5.00], and illegal state transitions (e.g. expire an already-expired event). Endpoints `GET/POST/PUT .../TimedEvents[/{id}]` + `.../{id}/activate` + `.../{id}/expire`.
5. `GrantStreakFreezeCommand(int ChildId, int Count, string Reason, bool Confirm)` → `BaseResponse<bool>`. **Implementation note:** the existing `GrantFreeze(occurredAtUtc)` only adds **+1** and no-ops at `MaxFreezes`. Granting N either loops `GrantFreeze` N times (silently capped) or needs a new bounded `GrantFreeze(int count, ...)` overload — backend-feature should add the overload (clamp to `MaxFreezes`, raise the event once). Endpoint: `POST .../children/{childId}/streak-freeze`.

**DTOs:** `BadgeDefinitionDto`, `MissionDefinitionDto`, `TimedEventDto` (mirror existing read DTOs). Request bodies as in the FE contract: `{ tier, reason, confirm }`, `{ count, reason, confirm }`, plus catalog/timed-event create/update payloads.

**Validation rules (FluentValidation, `ICommand<>` only):** `Reason` `NotEmpty` (and a max length) on the two child-affecting overrides; `Confirm == true`; tier ∈ enum; `Count` `GreaterThan(0)` and `LessThanOrEqualTo(MaxFreezes)`; catalog codes non-empty/length-bounded; timed-event window + multiplier bounds.

**Consistency / derived state:** league-tier override touches `CurrentTier` (and standings per Q-tier) — **no XP/level recompute** because tier is not XP-derived in P4-07 (tier is job-stamped, `CurrentTier` is an independent field). Catalog edits change future earn/generation only — **do not** touch existing `StudentBadge`/`StudentMission` rows. Streak-freeze grant only moves `FreezeBalance`. **None of the in-scope overrides mutate `TotalXp`**, so the `ApplyAward`/`LevelCurve` recompute path is NOT invoked by P7-13 as scoped (this is why the XP-set/level-recompute questions in the prompt are out of scope — see Q1/Q3).

**Transactions:** deferred commit + `UnitOfWorkBehavior` (ADR 0001); Gamification already runs this behavior and dispatches domain events strictly post-commit (verified in `Infrastructure/Behaviors/UnitOfWorkBehavior.cs`).

## Handoff → audit / post-commit publish (the relay decision)
**Recommendation: mirror the Learning domain-event relay verbatim** — it is the established, code-proven post-commit path, and Gamification's `UnitOfWorkBehavior` is a verbatim copy of Learning's (it already collects `AggregateRoot` domain events and dispatches them only after `CommitAsync`).

Concretely:
1. Add a `Gamification.Domain/Events/AdminActionPerformedDomainEvent` record (copy of `Learning.Domain.Events.AdminActionPerformedDomainEvent` — same payload: `AdminUserId, Action, TargetEntityType, TargetEntityId, Details`, `IDomainEvent`).
2. Each admin write handler calls `aggregate.RaiseDomainEvent(new AdminActionPerformedDomainEvent(...))` on the mutated `AggregateRoot` before returning (exactly as `SetSubjectActiveCommandHandler` does).
3. Add a `Gamification.Application/Features/Admin/Relay/AdminActionPerformedDomainEventRelayHandler` (copy of Learning's) that re-publishes `Shared.Contracts.Admin.AdminActionPerformedEvent` post-commit, **fail-soft** (catch+log; never fail the committed mutation).
4. The new `Moderation` module's `AuditLogEventHandler` (already built P7-12) consumes the integration event and writes the immutable audit row — **no change needed there**.
- **Caveat for non-aggregate targets:** `BadgeDefinition`, `MissionDefinition`, `TimedEvent`, and `League`/`LeagueMembership` are **not** `AggregateRoot` (they derive from `FullAuditedEntity`/`CreationAuditedEntity`, which do not raise domain events). Catalog/timed-event handlers therefore have **no aggregate to hang the domain event on**. Options: (a) raise the `AdminActionPerformedDomainEvent` on a convenient tracked `AggregateRoot` (none exists for catalog edits), or (b) for those handlers, publish the integration event **directly** but only after explicitly opening a transaction-aware post-commit hook — messier. **Recommended:** promote the relay to not require an aggregate by either (i) making `BadgeDefinition`/`MissionDefinition`/`TimedEvent` carry a lightweight domain-event capability, or (ii) keep a tiny "admin-action" aggregate seam. This is a real design choice (Q5) — flag to the lead; do not invent a pattern unilaterally (CLAUDE.md rule 8). For the two **child-affecting** overrides (league tier, streak-freeze) the target **is** `StudentXpProfile` (an `AggregateRoot`), so the relay works cleanly there with no new abstraction.
- **PII-safe `Details`:** ids + values only (e.g. `"Tier: Bronze→Silver"`, `"FreezeBalance: 0→2; count=2"`, `"IsActive=false"`). Never child name/email. New `AdminActions.*` string constants per action (e.g. `Gamification.LeagueTierOverridden`, `Badge.Created/Updated/Deactivated`, `Mission.*`, `TimedEvent.*`, `Gamification.StreakFreezeGranted`) added to `Shared.Contracts/Admin/AdminActions.cs`.

## Open questions / assumptions / risks
- **Q0 — FR mis-trace.** Story cites **FR-ADM-8**, which is the moderation queue (P7-09). Confirm the correct FR anchor (recommend FR-ADM-1/2/12 + the FR-GM-* being overridden) so the planner locks traceability.
- **Q1 — Override scope (prompt's XP/level/hearts/badge-grant questions).** The story's ACs cover **only** league tier, badge/mission catalog CRUD, timed-event writes, and streak-freeze. They do **NOT** include set/adjust student **XP**, **level**, **hearts**, or **grant/revoke a badge to a specific student**. Is the prompt's broader list (XP set/adjust, level, hearts, badge grant/revoke) **in scope** (scope expansion + extra migrations/commands) or **out** (build only the four areas + freeze as written)? Recommend: build to the story; treat XP/hearts/badge-grant as a follow-up unless the lead expands scope.
- **Q2 — Set-absolute vs adjust-by-delta.** League tier = set-absolute (an enum value). Streak-freeze = the contract says `count` (adjust-by-delta, i.e. grant N), capped at `MaxFreezes=2`. Confirm freeze is grant-only (cannot remove/zero) and capped. If XP/hearts come into scope (Q1), their set-vs-delta semantics need an explicit decision.
- **Q3 — XP→level/tier recompute.** Moot under the story's scope (no override touches `TotalXp`). If XP override is added (Q1), it MUST reuse `LevelCurve.LevelForXp` and go through `ApplyAward`/a new bounded chokepoint to keep `CurrentLevel` consistent — and decide whether it can *decrease* XP (the engine currently treats `TotalXp` as monotonic; `ApplyAward` only adds).
- **Q4 — Badge grant/revoke + XP clawback.** Not in the story's scope. If added: revoking a `StudentBadge` (which is an append-only ledger with RESTRICT-delete FK) would need a new revoke path, and clawing back its `RewardXp` would violate the monotonic-XP invariant. Recommend NOT clawing back XP even if grant/revoke is added; confirm with lead.
- **Q5 — Post-commit publish mechanism for non-aggregate targets.** Recommended path is the Learning relay (works for `StudentXpProfile`). But `BadgeDefinition`/`MissionDefinition`/`TimedEvent` are not `AggregateRoot`s — choose how their admin actions reach the relay (give them domain-event capability, an admin-action seam, or direct fail-soft publish). This is a design-pattern decision → ask the lead before implementing (rule 8).
- **Q-seed — Seed-vs-admin precedence (BE-7).** **Current `BadgeSeeder` actively drift-corrects (overwrites) catalog metadata on every boot** (`UpdateMetadata` when fields differ). This directly clobbers admin edits and must change to **seed-if-absent only** (insert when missing, never update existing). Decide the rule: pure seed-if-absent (simplest, recommended) vs a `Source`/`IsAdminEdited` flag that lets seed update only un-edited rows. Per rule 8, settle before implementing.
- **Q-tier — What "league tier override" writes.** `StudentXpProfile.CurrentTier` (the persistent tier used for next placement) vs the **active-week `LeagueMembership`** standings (which is a cohort row keyed by tier+period). AC says "applied to live standings" — implies the active membership/cohort must move too, which is more invasive (re-place into a same-week cohort of the new tier). Clarify exact semantics and whether mid-week re-placement is required or just the next-week tier.
- **Q-mission — "weekly-challenge" cadence.** `MissionType` enum is **Daily/Weekly** only today; story/task reference daily/**weekly**/weekly-challenge. Confirm whether "weekly-challenge" is a new enum value (additive migration) or just a label.
- **Q-badge-fields — editable fields.** `BadgeDefinition.Code/Name/Description` are documented immutable; AC2 lets admin edit name/description. Confirm those become editable (the mutator must be widened) and that `Code` stays immutable.
- **Risk — guardrails / abuse (BE-9).** Bounds: freeze `Count ∈ [1..MaxFreezes]`; reason required + length-bounded on child-affecting writes; `Confirm` required; no hard-delete of catalog rows that have earned ledger rows (RESTRICT FK already enforces this for `StudentBadge`); timed-event window + multiplier clamped at the validator AND factory. Whether an admin may **zero-out / harm** a student is largely avoided by scope (no XP/hearts override), but a malicious tier demotion or freeze spam is possible — `security-auditor` REQUIRED.

   - 2c. Badge catalog CRUD + seeder seed-if-absent fix.
   - 2d. Mission catalog CRUD + seeder seed-if-absent fix.
   - 2e. Timed-event create/update/activate/expire.
   - (2c–2e depend on the Q5 non-aggregate relay decision.)
