## Summary & traceability
- **Task (one line):** Build the universal Tamagui design-system (tokens/themes/fonts/RTL) and the core + gamification component library in `packages/design-system` and `packages/ui`, so every Learnexia screen is consistent, kid-accessible, and works in Arabic (RTL) and English on both Expo (web + native) and Next.js.
- **User story (source of truth):** `E:\Wrokspace\Learnexia.worktrees\P1-08\user-stories\Phase-1-Foundation\P1-08-design-system-and-components.md`

- **Requirements:** NFR-5 (Localization: Arabic-first + English, RTL, Cairo/Tajawal/Poppins), NFR-6 (Kid accessibility: large touch targets, one primary action/screen, minimal text, high contrast, visual feedback), NFR-7 (Usability: instant feedback, gamified reinforcement). Story covers feature notes F1.1–F1.3.
- **BRD goal:** Supports G1 (engaging, gamified learning) and G3 (accessible, Arabic-first UX) — the visual/interaction foundation all student-facing features depend on. (Confirm exact G-IDs against `docs/BRD.md` if the planner needs precise mapping; the story does not name a G-ID.)

## Business context & value
- **Who benefits:** Students (kid-friendly, motivating, instant-feedback UI), parents (consistent, legible Arabic-first screens), and the solo dev/AI team (one component set reused across Expo student-app and future Next.js admin/marketing — DRY, faster delivery).
- **Value:** This is pure enabling infrastructure. No user-visible feature ships from P1-08 alone, but it is the prerequisite that lets every subsequent screen be built quickly, consistently, and accessibly. Success = downstream stories compose screens from `@learnexia/ui` + `@learnexia/design-system` without redefining tokens, fonts, RTL handling, or accessibility rules.
- **How success is measured:** components render identically on Expo native, RN-Web, and Next; Arabic flips to RTL with Cairo/Tajawal and English uses Poppins; tokens are the single source of color/spacing/radius/typography; the kid-accessibility baseline (touch target sizes, contrast, visual feedback) is enforced by the components themselves.

## Acceptance criteria (testable)
From the story, made concrete against the kit + task breakdown:
1. **Tokens defined and consumed.** `packages/design-system` exports a `createTamagui()` config encoding the tokens from `design-system/colors_and_type.css`: colors (primary `#4F46E5`, success `#22C55E`, reward/accent `#F59E0B`, danger `#EF4444`, badge purple `#A855F7`; bg `#0F172A`, card `#1E293B`, soft card `#334155`, light `#F8FAFC`; text `#F8FAFC/#CBD5E1/#94A3B8`; gamification accents xp/streak/heart/gold/gem), spacing scale (4,8,12,16,20,24,32,40,48,64), radii (sm 8 / button 16 / card 20 / modal 24 / pill 9999), shadows (soft, float, popup, glow variants), and gradients (xp, reward, level-up). Every `packages/ui` component reads these tokens — no hard-coded hex/px in components.
2. **Core + gamification components exist and are documented.** `packages/ui` exports and documents: `Button` (Primary / Secondary / Success / Danger / Disabled + Default/Hover/Active/Disabled/Loading states), `Card`, `XPBar`, `Hearts`, `StreakFlame`, `Badge` (Bronze/Silver/Gold/Legendary, earned/locked), `AITutorBubble` (AI / student / hint types), `RewardPopup` (XP / badge / level-up). A component catalog demonstrates each (FE-7).
3. **Locale → RTL + fonts.** Switching locale to Arabic flips layout to RTL (logical props / direction) and uses Cairo/Tajawal; English uses Poppins. Wiring goes through the existing `packages/shared` helper (`isRtlLocale`, `directionForLocale`, `applyWebDirection`, `applyNativeRtl`) — P1-08 does NOT duplicate RTL logic; it consumes it and provides the Tamagui-side font/theme switching.
4. **Kid-accessibility baseline.** Components meet: large touch targets (min ~44–48px / explicit hitSlop where needed), one-primary-action affordance, high-contrast color states, and visual feedback on interaction (press scale ~0.95, color/elevation state changes). Documented as a baseline so screens inherit it.
5. **Dual-runtime render.** Each component renders without crashing on (a) Expo native, (b) RN-Web, and (c) Next via `@tamagui/next-plugin`. Verified via a component catalog and at least a smoke render check on each runtime (see open questions on how far this is achievable given app shells are still stubs).

## Open questions / assumptions / risks
1. **FE-7 dual-runtime verification vs. stub apps (HIGH — for planner).** `apps/student-app` (Expo) and `apps/admin-dashboard` (Next) are bare stubs with no Metro/`@tamagui/next-plugin` setup. Verifying "renders on both runtimes" needs a host. **Question for lead:** Is P1-08 expected to also stand up a minimal Expo + Next harness (or a Storybook/Tamagui playground) to host the catalog, or is FE-7 limited to a single available runtime now with the rest deferred to the app-shell story? Recommend planner scopes a minimal catalog host and flags any app-shell wiring as out-of-scope/blocking.
2. **Cairo font on native (MEDIUM).** `colors_and_type.css` loads Cairo from Google Fonts via `@import`; Poppins + Tajawal ship as local `.ttf`. Expo native cannot use a CSS `@import` URL. **Assumption to confirm:** either (a) add Cairo `.ttf` files to `design-system/fonts/` (preferred for native parity), or (b) use Tajawal as the sole/primary Arabic face on native and treat Cairo as web-display only. Flag to lead/designer.
3. **Tamagui compiler setup cost (MEDIUM, known risk).** FRONTEND_ARCHITECTURE §9 explicitly calls Tamagui compiler setup the steepest part of the stack and says to budget for it. Without an app build pipeline, the optimizing compiler may not be exercised in P1-08; components must at least work in the non-optimized runtime path.
4. **Reanimated/Moti/Skia versions vs Expo SDK 53 / RN 0.76 New Arch (MEDIUM).** These native-animation deps must be version-aligned with the target Expo SDK; since no Expo app is wired yet, pin to SDK-53-compatible versions and document. Risk of churn when the app shell lands.
5. **Component scope boundary (LOW).** The kit and FRONTEND_ARCHITECTURE list `SkillNode`, `LessonCard`, `QuizCard`, `MissionCard` in `packages/ui`, but the P1-08 task file scopes only the 8 components in AC #2. **Assumption:** those are deferred to their feature stories; P1-08 builds only Button, Card, XPBar, Hearts, StreakFlame, Badge, AITutorBubble, RewardPopup. Confirm with lead.
6. **Theme default (LOW).** Architecture says default is the dark game-world palette; the kit ships a `--lx-bg-light` surface for parent/print. Assume dark default + a light theme provided but not default. Designer to confirm which surfaces use light.
7. **No BRD G-ID named in story (LOW).** Story lists NFR-5/6/7 but no explicit BRD goal. Mapped to G1/G3 by inference; planner can refine against `docs/BRD.md` if precise traceability is required.
