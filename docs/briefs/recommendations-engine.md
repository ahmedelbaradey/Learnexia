## Summary & traceability
- **One-line task:** compute a daily, deterministic, per-child set of "Areas to focus on" + recommended next actions in the **Learning** module (free, explainable), and let **Lexi** (the Ai module) optionally narrate that persisted content kid-style on demand (energy-costed, reusing the existing safety + cache + debit path).
- **Locked design source:** lead decision 2026-06-16 ("ONE TAKE ONLY" — deterministic core + on-demand voice), reconfirmed 2026-06-16 authoritative. Deferral condition ("after the Option-C sweep") is now **satisfied** — Learning Option-C refactor merged 2026-06-16 (HANDOFF.md §"Option C refactor — Learning module DONE").
- **Maps to existing stories:** **P5-02** (detect & rank weak areas, FR-PA-2) is the foundation input — DONE. **P3-08** (adaptivity, FR-AD-1) and **P3-13** (adaptive student profile, FR-AD-5) are the enrichment inputs — both DONE. **P5-08** (parent-scoped read API) is the surfacing host — DONE. The recommendation engine is a **new story** (no existing story covers the persisted daily recommendation set or the Lexi narration intent); proposed IDs below.
- **BRD goal:** **G3** (personalised adaptive learning / "areas to focus") + **G5** (parent visibility/engagement). The Lexi voice also serves the barrier-to-entry "rich adaptive profile → personal guidance" moat.
- **Epic / phase:** Parent & Analytics (P5) for the deterministic engine + parent surfacing; AI Tutor (P3/Ai module) for the Lexi narration intent. Post-MVP wave.

## Business context & value
- **Who benefits:** the **parent** (sees concrete, prioritised "what to do next" per child on the dashboard — closes the faked `RecommendationsCard`/`FocusAreasCard` stubs) and the **student** (gets a friendly, on-demand kid-voice explanation of what to work on). Admin is unaffected.
- **Value:** turns the already-computed weak-areas + adaptivity + behavioral profile into actionable guidance — the "personal tutor that knows me" promise — without burning AI cost on the core (deterministic = free, cacheable, explainable, reproducible). The optional Lexi voice is the delight layer and a deliberate energy sink consistent with the locked Phase-10 economy.
- **Success measure:** parent dashboard shows real recommendations (not stubs); recommendations change as mastery improves (resolved areas drop off, mirroring P5-02 AC4); Lexi narration reuses the cache so repeat asks are cheap; no increase in non-deterministic AI spend on the core path.

## Verified facts against current code (state these as facts)
1. **P5-02 weak areas — DONE.** `WeakAreaDetectorService` (Learning.Infrastructure) implements `IWeakAreaDetectorService.DetectAsync(studentId, maxResults, ct)` and the cross-module seam `Shared.Contracts/Learning/IStudentAllSubjectsWeakAreasQuery.GetWeakAreasAsync(...)`. Output record: `WeakAreaEntry(SkillId, SkillName, SubjectCode:int, MasteryPercent, Severity, SuggestedNextAction)`; `WeakAreaSeverity { Low=1, Medium=2, High=3 }`. Severity rule: High <30%, Medium 30–<50%, Low ≥50% but recent attempt accuracy <60%. `SuggestedNextAction` is an enum-backed key (`ReviewConcept` / `PracticeSkill`), not free text. Already bridged into Ai via `AiWeakAreasQueryBridge : IStudentWeakAreasQuery` (subject-scoped filter over the all-subjects detector). **This is the foundation input.**
2. **P3-08 AdaptivityEngine — DONE, exposed as an in-module seam.** `Learning.Application/Services/IAdaptivityService.GetTargetDifficulty(studentId, skillId?, ct) → AdaptivityDecision(DifficultyLevel, IsDefault, Score)`, implemented by `AdaptivityService` (deterministic, reads the 4 FR-AD-1 signals + persisted mastery, never throws, returns Medium/IsDefault on cold-start/error). **No `Shared.Contracts` seam** — it is consumed in-module today (e.g. P3-11 quiz selection, `GetAdaptivityDecisionQueryHandler` + `AdaptivityController`). Per-skill, not per-student — the recommendation engine calls it per weak-area skill.
3. **P3-13 adaptive student profile — DONE + persisted + nightly job exists.** Entity `StudentLearningProfile` (one row/student; `QuestionTypeAffinity`, `RecurringErrorClusters`, `AttentionSpanMinutes`, `FatigueSignal`, `PreferredExplanationStyle`, `DataPointCount`, `LastRecomputedAt`). In-module seam `Learning.Application/Services/IStudentProfileService.GetProfile(studentId, ct) → DerivedProfile` (cold-start safe: `DataPointCount==0` ⇒ neutral defaults). **The nightly job to mirror is `StudentProfileRecomputeJob`** (`Learning.Infrastructure/Jobs`), registered in `LearningModule.InitializeAsync` via `recurringJobs.AddOrUpdate<StudentProfileRecomputeJob>("SP-Recompute", job => job.Execute(...), Cron.Daily(), TimeZone=Utc)`. It sweeps stale rows (`GetStaleProfilesAsync(cutoff)`), commits per-student (`SaveChangesAsync(userId:0)` — background jobs own their own commit, ADR-0001), `[DisableConcurrentExecution]`, grade-agnostic. **This is the exact template for the daily recommendation job.** Note P3-13's profile is **not** exposed via `Shared.Contracts` yet (its own doc flags that as deferred to P3-03) — so the recommendation engine reading it stays **in-module** (Learning computes), which is exactly the locked ownership split.
4. **Energy spend mechanism — verified.** The 4 Ai handlers (`ExplainConceptCommandHandler`, `GetHintCommandHandler`, `SimilarExampleCommandHandler`, `SimplifyExplanationCommandHandler`) follow: rate-limit (`IAiTutorRateLimiter`) → `IChildAccessStateQuery.GetAccessDecisionAsync` (P10-18/15 pause/seat gate) → `ICreditSpendService.GetBalanceAsync` pre-auth (fail-soft) → cache lookup → safety → debit on delivery via `ICreditSpendService.TryDebitAsync(childId, cost, reasonCode, idempotencyKey, ct)`. **Cost is server-resolved, client-blind:** `CreditCostResolver.ResolveCost(HelperIntent)` reads `IGlobalSettingsProvider` keys with locked defaults — `ai_cost.hint`=1, `ai_cost.explain_mistake`=2 (WhyWrong), `ai_cost.deep_explanation`=3 (Explain+Simplify), `ai_cost.practice_generation`=5 (SimilarExample). Keys are defined in `Billing.Domain/Constants/GlobalSettingKeys.cs` + its `ManagedKeys` allowlist; the same strings are inlined in `CreditCostResolver` (no Billing project ref — rule #1). `ICreditSpendService` lives in `Shared.Contracts/Billing`, implemented by Billing's `CreditSpendService`. **A new Lexi intent needs: a new `ai_cost.recommendation` key (added to `GlobalSettingKeys` + `ManagedKeys` + the seeder + `CreditCostResolver`), a new `CreditReasonCode` (e.g. `AiRecommendation`), and it calls the same `ICreditSpendService.TryDebitAsync` seam.**
5. **Ai intent anatomy (Explain reference) — the moving parts a new intent reuses:** a Command + Validator + Handler (`Features/<Intent>/Commands/...`), a Controller (`Ai.Api/Controllers/<Intent>Controller.cs`), the `HelperIntent` enum value (`Shared.Contracts/Ai/HelperIntent.cs` — currently `Explain=1, Hint=2, WhyWrong=3, SimilarExample=4`, a **closed exhaustive set** wired into `TemplateSelector`; adding a member forces the exhaustive switch to be updated — by design), `ISafetyLayer.GenerateSafeAsync` (NEVER `IAiGateway` directly — arch-test enforced), `IPromptBuilder.Build(PromptContext)` + a subject template, `IAiResponseCache` (cache-first; write approved on safety pass, `AiCacheKeyBuilder`), `CreditCostResolver` + `ICreditSpendService` pre-auth/debit, the access gate (`IChildAccessStateQuery`), `IAiTutorRateLimiter`, localization (`IStringLocalizer<SharedResources>` + `SharedResourcesKey`), and integration events (`HelpRequested`/`HelpDelivered`/`HelpDeclined`). Response is **SSE-streamed** for Explain/Hint (buffer→safety→emit) and there is a synchronous result shape too. **The Lexi narration intent must reuse all of these.**
6. **Surfacing — `ParentAnalyticsController` (`api/Parent/*`, `[Authorize(Roles="Parent,Admin,SuperAdmin")]`) is built** with E1 Progress (has `weakestSkill`), E4 SubjectMastery, **E5 WeakAreas** (`GET Children/{id}/WeakAreas` → `WeakAreasResponseDto{ Areas: WeakAreaItemDto[] }`, mirrors the FE `FocusAreaStub`). Every per-child route runs `IParentChildQuery.IsParentOfChildAsync` (IDOR guard) before fan-out, handlers are EF-free (Option C) with per-seam try/catch. **FE already has stub components** `apps/student-app/app/(parent)/_components/RecommendationsCard.tsx` (the "Recommendations from Lexi" panel — icon + title + body + ghost CTA per row, currently 3 i18n-keyed stub rows) and `FocusAreasCard.tsx`, plus the design mock `design-system/preview/web-recommendations.html`. **FE is the other lead's** — this brief authors nothing FE; it only records the contract the FE will consume.

## Acceptance criteria (testable — deterministic engine)
- A per-child recommendation set is computed **deterministically** (rule-based, no LLM call) from: P5-02 weak areas + P3-08 target difficulty per weak-area skill + P3-13 derived profile + the child's grade. Same inputs ⇒ same output (reproducible, mirrors P3-08/P3-13 determinism).
- The set is **persisted once per day per child** by a scheduled job (mirroring `StudentProfileRecomputeJob` / `Cron.Daily()`), keyed by `(StudentId, RecommendationDate)`; the dashboard reads the persisted row and does **NOT** recompute on load.
- Each recommendation item carries (proposed — see OQ-1): a stable skill/subject reference, a human-readable title key + body key (localisation keys, not free text), a severity/priority, a recommended **action type** (practice / review / keep-streak / celebrate), and the **target difficulty** for the suggested practice.
- "At his level" stays **un-conflated:** grade (Identity/JWT) drives Lexi language/tone + curriculum scope; per-skill mastery% (Learning) drives which areas + practice difficulty (AdaptivityEngine); gamification level drives **motivational framing only** (never which area).
- Resolved/improved areas drop off automatically (a skill no longer weak per P5-02 is no longer recommended) — consistent with P5-02 AC4.
- Cold-start: a brand-new child with no data returns a safe, non-empty default set (e.g. "start your first lesson") or an explicit empty-with-friendly-state — never an error (mirror P5-02 empty-list-is-not-an-error + P3-13 cold-start).
- A new `Shared.Contracts/Learning/IStudentRecommendationsQuery` seam returns the persisted `RecommendationItem[]` for a student; Learning implements it, Parent (dashboard) and Ai (Lexi grounding) consume it. Never null, never throws (sentinel pattern, like `IStudentAllSubjectsWeakAreasQuery`).
- All derived data is per-child and **never leaks another child's data**; the seam takes a loose `int studentId` (no cross-module FK). Behavioral profile of a minor ⇒ `security-auditor` gate.

## Acceptance criteria (testable — Lexi narration layer)
- A **new Ai intent** ("Lexi recommendation narration") narrates the **persisted** recommendation content kid-style, **on demand** (parent taps "Ask Lexi" / child opens guidance) — it is NOT auto-run and NOT part of the daily job.
- It is **grounded only on** the persisted `RecommendationItem[]` (via `IStudentRecommendationsQuery`) + grade/age/language (tone) — it does **not** invent new recommendations; the deterministic set is the source of truth.
- It reuses the full intent path: rate-limit → access gate (`IChildAccessStateQuery`) → energy pre-auth → cache-first → `ISafetyLayer` (never `IAiGateway`) → debit-on-delivery → events. Charge-on-delivery, cache-hit charged the same, no charge on refuse/safety-block/error (locked economy).
- It has its **own energy cost key** (`ai_cost.recommendation`, default TBD — see OQ-2) + its own `CreditReasonCode` + its own `HelperIntent` member; cost is server-resolved and client-blind.
- Localised ar/en; child-safe tone; PII-minimised prompt (grade/age proxies only, never the child's name/email in the prompt body — mirror `PromptContext` rule).

## Open questions / assumptions / risks (for the lead → user)
- **OQ-1 (`RecommendationItem` shape + count):** exact fields + how many items per child per day (FE stub shows 3). Propose: `{ SkillId, SubjectCode, TitleKey, BodyKey, CtaKey, Severity, ActionType (enum: Practice/Review/KeepStreak/Celebrate), TargetDifficulty }`, cap 3–5, ordered by severity. **Decision needed:** field list, cap, ordering, and whether copy is i18n keys (recommended, consistent with P5-02) or templated strings.
- **OQ-2 (Lexi energy cost):** the new `ai_cost.recommendation` default vs the locked ladder (Hint=1, WhyWrong=2, Explain=3, Practice=5). It is a multi-item summarisation/narration (richer than a hint, similar effort to Explain). **Recommend 3** (deep-explanation tier) — confirm with the lead/economy owner.
- **OQ-3 (narration trigger UX/contract + response mode):** SSE-streamed (like Explain/Hint) or synchronous (like a one-shot summary)? One narration per day cached, or per-tap? Where exactly triggered (parent "Ask Lexi" on the card vs a child-app surface)? Affects the controller + FE contract.
- **OQ-4 (surfacing — new endpoint vs fold-in):** new `GET api/Parent/Children/{id}/Recommendations` (recommended — clean separation from E5 weak areas, matches the FE's separate `RecommendationsCard`) **or** extend E5. Also: is there a **child-app** read surface for recommendations, or parent-only for v1?
- **OQ-5 (cache TTL / invalidation for the narration):** the deterministic content changes daily; the Lexi narration cache key must include the recommendation date (or a content hash) so a new day's recommendations produce a fresh narration rather than serving yesterday's. Confirm the cache key dimensions + TTL (note the existing `AiResponseCache` auto-approval-confidence gate at `ai.cache.autoApprovalConfidence` and that cache serving is currently dormant per OQ-7 in the operationalize-phase4 work — confirm narration caching is active or accept live-each-time for v1).
- **OQ-6 (daily-job timing + scope):** cron time for `Rec-Recompute` and that it runs **after** `SP-Recompute` (recommendations read the profile). Which children does it sweep — all active children, or only those active in the last N days (cost/scale)? Mirror P3-13's stale-sweep or sweep-all?
- **OQ-7 (v1 split — deterministic-only first, or both together):** ship the deterministic engine + parent surfacing first (lights up the real `FocusAreasCard`/`RecommendationsCard` data immediately, free) and the Lexi narration as a **fast-follow** (it depends on the persisted content + a new intent + economy key + security audit)? **Recommend split: deterministic engine = v1, Lexi narration = v1.1.** Confirm.
- **OQ-8 (new Ai intent approval — rule #8):** adding `HelperIntent.Recommendation` is a 5th intent in a deliberately-closed set and a new design surface — **lead must explicitly approve** the new intent before the Ai work is built (this brief flags it, does not assume it).
- **Risk — determinism vs the energy model:** the core MUST stay rule-based (a live LLM core would burn energy + be non-deterministic) — keep the LLM strictly in the on-demand narration. Already locked; call out in review.
- **Risk — child privacy:** both the persisted behavioral-derived recommendations and the Lexi prompt touch a minor's profile → `security-auditor` gate mandatory (data minimisation, purpose limitation, no PII in prompt, IDOR on the parent endpoint).
- **Assumption:** all three inputs (P5-02/P3-08/P3-13) are present in every environment the job runs in (verified in code + integration suites P3_08/P3_13). If a future env lacks P3-13 data, the engine degrades to weak-areas + grade (cold-start path) — no hard dependency failure.
