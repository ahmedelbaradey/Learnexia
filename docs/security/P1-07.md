### Positive controls verified
- Health probes mapped **before** auth, rate limiting, and the auth-logging middleware (`Program.cs:148-164`) — probes never 401/429 and never trigger the error-handler that could leak detail.
- `/health` + `/health/live` explicitly **excluded from the IP rate limiter** via `EndpointWhitelist = ["get:/health", "get:/health/live"]` (`ServiceExtensions.cs:35`).
- Redis health check is **degraded-tolerant** (`failureStatus: Degraded`) and only registered when a connection string exists — no readiness flap when Redis is absent.
- Dockerfile is multi-stage (`sdk:10.0` build → `aspnet:10.0` runtime); no secrets baked via `ARG`/`ENV`; no credentials in image layers.
- CI `docker build` validates the Dockerfile without pushing; deploy push isolated to the separate `deploy-staging.yml`.
- No `.env` or `.pfx` files committed in this change (git status verified).

## Verdict: PASS-with-notes

No Critical or High findings. The three security-sensitive surfaces the brief called out are correctly handled:
- Hangfire dashboard: gated to Development only + local-requests-only default filter — not anonymously reachable in staging/prod.
- `/health`: default writer leaks no connection strings, versions, hostnames, or stack details.
- Secrets: no hardcoded credentials introduced; new staging artifacts are fully secret-referenced.

All remaining findings are Low/Medium hardening items (most pre-existing from P1-06) — none block the reviewer gate.

## Notes / accepted risks
- Findings #9–#13 are **pre-existing** dev defaults (JWT `CHANGE_ME`, compose `postgres/admin`/`minioadmin`, cert password `123456`, CORS fallback, `RequireHttpsMetadata=false`) — flagged for a future staging/prod-hardening story; out of scope to fix in P1-07 per the brief. The staging override + `staging-decision.md` already document the rotation path.
- Findings #5–#8 are **new** (this story's Dockerfile/workflows) but Low severity — recommended for follow-up, not blocking.
