### Positive controls verified (defensive checklist)

- **Parent identity from JWT only.** `LinkChildCommand` has **no** `ParentId`; the acting parent is read from `ICurrentUserService.UserId`, which resolves the `Id` claim from `HttpContext.User` (`CurrentUserService.cs:19-26`). No handler/service reads a parent id from the request body. (IDOR / mass-assignment closed.)
- **Fail-closed on missing identity.** Both the command handler and the list query return `Unauthorized` when `UserId is null` (`LinkChildCommandHandler.cs:42-43`, `ListMyChildrenQueryHandler.cs:40-41`).
- **`FamilyScopeAuthorizationHandler` is default-deny.** `context.Succeed` is called only on a verified condition (Admin/SuperAdmin role, self `callerId == studentId`, or an awaited `ParentStudents.AnyAsync` link match). The DB check is fully awaited before `Succeed`; no `Fail()`/early-succeed; unparsable/absent `Id` claim returns without succeeding. No exception path leads to success.
- **Enumeration / existence disclosure.** Non-existent email, non-Student target, self-link, and another-family's-child all collapse to a single `BadRequest(CannotLinkChild)` with identical shape and message. The validator is intentionally shape-only (presence + email format) and performs **no** existence lookup, avoiding a 422-vs-200 oracle.
- **Controller gating.** `ParentController` is `[Authorize(Roles = "Parent,Admin,SuperAdmin")]`, does **not** inherit `UserManagementController`, and `AppControllerBase` carries no `[AllowAnonymous]` and no relaxing attribute. Unauthenticated → 401; authenticated non-matching role → 403.
- **Family-scoped reads.** `GET My-Children` keys strictly on `CurrentUserService.UserId`; `GetLinkedStudentsAsync` filters `Where(ps => ps.ParentId == parentId)`. No route/body parameter can widen scope. Cross-family isolation holds.
- **Idempotency without leak.** Re-link of an already-linked pair returns success no-op (`IsLinkedAsync` pre-check); composite PK `(ParentId, StudentId)` backstops uniqueness.
- **No sensitive-data exposure in errors.** `ServerError<T>` is called with a localized constant (`SystemErrorSavingData` / `SystemErrorRetrievingData`), never `ex.Message`. The exception is logged server-side via `ILoggerManager`; no stack trace or internal detail reaches the client.
- **Logging hygiene.** Security-relevant rejects/links are logged via `ILoggerManager` using the child **id** and parent **id** only — no child email, no token, no PII in log lines.
- **Injection.** All data access is EF Core LINQ (`AnyAsync`, `Where`, `Select`) — parameterized. No `FromSqlRaw`/`ExecuteSqlRaw`/interpolated SQL in P1-04 code. `System.Linq.Dynamic.Core` appears only as a transitive dependency and is not used in this feature. Migration contains no raw `Sql()`.
- **JWT secret.** `GuardJwtSecret` fails startup in Production/Staging if the secret is empty or the committed `CHANGE_ME…` default; default tolerated only in Development/Testing. No hardcoded secret introduced by P1-04.
- **Module isolation.** `ParentStudent` is intra-Identity (both FKs → `AspNetUsers`); `CreatedBy` is a plain `int?` with no cross-module FK; `LinkedChildResponse` deliberately omits grade (Curriculum concept).
- **Dependency scan.** `dotnet list backend/Learnexia.Modular.sln package --vulnerable` → no vulnerable packages in any project.

## Verdict: PASS

No Critical or High findings. The feature correctly enforces the family-scope access-control boundary for minors' data: parent identity is server-resolved, the authorization handler is fail-closed, error responses are non-enumerable, and the controller is properly role-gated.
