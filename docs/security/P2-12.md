## Findings

| # | Severity | Issue | Location (file:line) | Remediation |
|---|---|---|---|---|
| 1 | **High** | **ChangePassword leaks raw Identity error descriptions to client.** On a failed `ChangePasswordAsync`, the handler interpolates the raw `result.Errors.Select(e => e.Description)` collection directly into the `BadRequest` response message. ASP.NET Identity error descriptions can include internal detail such as "Incorrect password", "Password is too short", "PasswordRequiresNonAlphanumeric", etc. On a children's platform these strings may disclose server-side password-complexity configuration. More critically, they allow Oracle-style probing: the distinguishable "Incorrect password" vs "PasswordRequiresDigit" message reveals whether the current password was correct. | `ChangePasswordCommandHandler.cs:62-63` | Replace the interpolated error string with a fixed localized message. Log the `errors` string server-side (already done for other Identity calls in the codebase). Pattern: `return BadRequest<string>(_localizer[SharedResourcesKey.PasswordIncorrectOrInvalid]);` — never expose `errors` in the response body. |
| 2 | **High** | **ChangePasswordValidator has zero active validation rules.** `ApplyValidationRules()` is called in the constructor but the method body is empty. `NewPasswordDifferentFromCurrent()` is defined but never wired into a `RuleFor`. This means the `ChangePasswordCommand` passes `ValidationBehavior` with no shape checks: `NewPassword` and `ConfirmPassword` can be empty strings, and `NewPassword == CurrentPassword` is not rejected before the Identity layer sees it. A client can submit an empty `NewPassword`, Identity will reject it, and the raw error description (Finding #1) is returned. | `ChangePasswordValidator.cs:22-24` | Wire the missing rules in `ApplyValidationRules()`: `RuleFor(x => x.NewPassword).NotEmpty().Matches(PasswordPolicyPattern)`, `RuleFor(x => x.ConfirmPassword).NotEmpty().Equal(x => x.NewPassword)`, and wire `NewPasswordDifferentFromCurrent` as `MustAsync`. This keeps current-password verification in the Identity layer but prevents trivially invalid inputs from reaching it. |
| 3 | **Medium** | **TOCTOU race on Unlink last-parent guard.** The `UnlinkChildCommandHandler` executes `IsLinkedAsync` (check 1) → `CountParentsForStudentAsync` (check 2) → `UnlinkAsync` (delete) as three separate database reads/writes within a `READ COMMITTED` transaction (PostgreSQL default, opened by `UnitOfWorkBehavior`). Two concurrent unlink requests from two different parents of the same child can both observe `parentCount = 2` at check 2, both pass the guard, and both proceed to delete, leaving the child with zero parents — exactly the invariant the guard is meant to protect. | `UnlinkChildCommandHandler.cs:44-59`, `LinkParentStudentService.cs:69-91`, `UnitOfWorkBehavior.cs:40` | Wrap the count-check-then-delete in a `REPEATABLE READ` (or `SERIALIZABLE`) transaction so the second concurrent reader re-reads the actual committed count. Alternatively, add a serializable advisory lock or a database-level check constraint (e.g. a trigger/procedure). The simplest fix is to replace the begin-transaction isolation level in `UnitOfWorkBehavior` with `REPEATABLE READ`, or more targeted: open an explicit `REPEATABLE READ` transaction inside `UnlinkChildCommandHandler` for just this sequence, bypassing the generic behavior for this command. |
| 4 | **Medium** | **`RequireHttpsMetadata = false` is not guarded to Development only.** The JWT bearer configuration sets `RequireHttpsMetadata = false` unconditionally. In Production/Staging this means the bearer token is accepted over plain HTTP, allowing token interception via a network MitM (the TLS layer is the last defence for bearer tokens). HSTS (`app.UseHsts()`) is present in Program.cs and mitigates this partially, but a misconfigured reverse proxy or a direct-to-pod connection bypasses HSTS. | `Identity.Infrastructure/DependencyInjection.cs:160` | Add environment guard: `x.RequireHttpsMetadata = !environment.IsEnvironment("Development");`. Pattern identical to the existing `GuardJwtSecret` environment detection already in the same file. |
| 5 | **Medium** | **`ChangePasswordCommand` exposes a client-settable `UserId` field that is silently ignored.** The command record has `public int UserId { get; set; }` (not `[JsonIgnore]`). The handler correctly ignores it and always reads from JWT, and the comment documents this. However, model-binding will populate the field from the request body, making it appear to API consumers as an accepted parameter. This is a mass-assignment surface: if any future handler, middleware, or audit log mistakenly reads `command.UserId`, it could use an attacker-supplied value instead of the JWT value. The field is also unnecessary. | `ChangePasswordCommand.cs:8` | Remove the `UserId` property from `ChangePasswordCommand` entirely. The handler already uses `ICurrentUserService.UserId` exclusively. Removing the property eliminates the latent mass-assignment surface without any behavioral change. |
| 6 | **Medium** | **Rate limiting absent on new authenticated sensitive endpoints.** `POST /api/Users/Account/ChangePassword` is a password-change endpoint. While it requires a valid JWT (so brute-force without credentials is harder), the global 200 req/min ceiling is the only protection. An attacker with a stolen refresh token can attempt many password-guess calls within the global limit. There are no per-endpoint rate-limit rules for the three new Identity endpoints or the Unlink-Child endpoint. | `ServiceExtensions.cs:28-53` | Add per-endpoint rules for `post:/api/users/account/changepassword` (e.g. 5 req/15min per IP), mirroring the pattern used for sign-in and forgot-password. Consider similar limits on `POST /api/Parent/Unlink-Child`. |
| 7 | **Low** | **`ChildProfile` in the `IChildAccountService` seam includes the child's email address.** `GetChildrenAsync` returns `ChildProfile` records that include `Email`. The `ListMyChildrenQueryHandler` maps these to `LinkedChildResponse` which also includes `Email`. This means a parent's `GET /api/Parent/My-Children` response exposes each child's email address. For children on a COPPA-context platform this may be more PII exposure than the UI requires (the display might only need FullName + Grade). | `IChildAccountService.cs:71-76`, `ListMyChildrenQueryHandler.cs:51-57` | Review whether the frontend UI needs the child's email in the list response. If it is needed only for the edit screen, consider returning it only from `Update-Child` / a dedicated `Get-Child` endpoint rather than the bulk list. This minimizes PII surface on a children's platform. This is an accepted-risk candidate if the UX requires it. |
| 8 | **Low** | **`ILoggerManager` double-registration risk in Parent module.** `AddParentInfrastructure` registers `ILoggerManager` as `AddSingleton`. Identity Infrastructure also calls `AddLoggerServices` which registers `AddSingleton<ILoggerManager>` and then separately `AddScoped<ILoggerManager>` in `AddIdentityInfrastructure`. Multiple competing singleton/scoped registrations of the same interface across modules may result in a captive dependency when a scoped service resolves the singleton logger from Identity's registration. Not a security issue in itself but could produce inconsistent logging if the wrong implementation is resolved. | `Parent.Infrastructure/DependencyInjection.cs:24`, `Identity.Infrastructure/DependencyInjection.cs:53,107` | Follow the CLAUDE.md convention: "Don't add a second logger registration." Remove the `AddSingleton<ILoggerManager>` from `AddParentInfrastructure`; rely on Identity's global registration (which already runs first). |
| 9 | **Low** | **`appsettings.json` committed with the default JWT secret and MinIO default credentials.** The `CHANGE_ME_super_secret_key_at_least_32_chars_long_0123456789` JWT secret and MinIO `minioadmin`/`minioadmin` are in the committed config. The existing `GuardJwtSecret` guard correctly blocks the app in Production/Staging, but the MinIO credentials have no equivalent guard. For a children's data platform these should be env-variable-only in production. | `appsettings.json:9,52-53` | Pre-existing finding (noted in prior audit P1-02). Not introduced by P2-12 — carry forward. Add a startup guard for `MinIOConfiguration:SecretKey` matching the JWT guard pattern. |
| 10 | **Info** | **`DateTime.Now` (Kind=Local) used in `LinkParentStudentService` alongside `DateTime.UtcNow` in entity initializer.** Mixed clock kinds in the same table. Not a security finding but `AppContext.SetSwitch("Npgsql.EnableLegacyTimestampBehavior", true)` was added to mask this. | `LinkParentStudentService.cs:46`, `ParentDbContext.cs:45` | Pre-existing codebase pattern. Low priority; migrate to `DateTime.UtcNow` consistently in a future cleanup. |
| 11 | **Info** | **`SessionId` claim key alignment confirmed.** `ChangePasswordCommandHandler` uses `GetClaimValue("SessionId")` to identify the current session before terminating others. This is correct. ## Verdict: FAIL

**2 blocking findings** (Critical/High threshold):

- **Finding #1 (High):** `ChangePasswordCommandHandler` leaks raw Identity error descriptions (which distinguish "wrong current password" from "invalid new password") to the client response — violates sensitive-data-exposure and timing-oracle principles on a children's platform.
- **Finding #2 (High):** `ChangePasswordValidator` has no active validation rules — empty `ApplyValidationRules()` body means `NewPassword` and `ConfirmPassword` have no shape guards before reaching the Identity layer, which exacerbates Finding #1.

---

## Notes / Accepted Risks

- **Finding #3 (TOCTOU):** Rated Medium rather than High because the real-world probability of two concurrent parents both unlinking the same child at the exact same millisecond is very low, and the guard errs on the side of safety (both unlinks completing without the orphan scenario requires the race to hit a narrow window). The plan already flagged this as open. Recommend wrapping in `REPEATABLE READ` before the story is closed.
- **Finding #4 (RequireHttpsMetadata):** Mitigated in production by HSTS and reverse proxy; still worth a dev-only guard per defence-in-depth.
- **Finding #9 (appsettings secrets):** Pre-existing, not introduced by this story. MinIO guard is a follow-up.
- **Finding #5 (UserId mass-assignment):** Correctly mitigated in the handler; the latent risk is future regression. Removal is the cleanest fix.
- **Finding #7 (child email in list):** Accepted risk if the UI requires it; flagged for product review on a COPPA-adjacent platform.

---

## Top must-fix items before reviewer gate

1. **(#1 — High — BLOCKS)** Remove Identity error descriptions from `ChangePasswordCommandHandler:63` response; log server-side only.
2. **(#2 — High — BLOCKS)** Wire validation rules into `ChangePasswordValidator.ApplyValidationRules()` — at minimum `NewPassword.NotEmpty().Matches(policy)`, `ConfirmPassword.Equal(NewPassword)`.
3. **(#3 — Medium)** Wrap `IsLinkedAsync → CountParentsForStudentAsync → UnlinkAsync` in a `REPEATABLE READ` transaction.
4. **(#4 — Medium)** Guard `RequireHttpsMetadata = false` to Development environment only.
5. **(#5 — Medium)** Remove `UserId` property from `ChangePasswordCommand`.
