## Findings

## Per-focus-area assessment (from brief/plan handoff)

1. **Access control / privilege escalation — PASS.** `RegisterParentCommand` (`RegisterParentCommand.cs`) exposes only `Email`, `Password`, `FullName?` — **no `Roles`/`Role` field**, so a smuggled JSON role field is simply ignored by model binding. The handler hard-codes `AddToRoleAsync(user, Roles.Parent.ToString())` (`RegisterParentCommandHandler.cs:72`). No client-controlled role; no mass-assignment to a `User` entity (the handler constructs `User` field-by-field and never sets `IsActive`, `CreatedBy`, audit, or role fields from the command). **No privilege escalation path.**
2. **No anonymous child/Student creation — PASS.** This is the only anonymous account-creation endpoint; it can only ever produce a Parent. No `Register-Student` or role-parameterized anonymous route exists. Children remain parent-provisioned (P1-03). AC-2 satisfied.
3. **Credential handling — PASS.** Password is hashed by ASP.NET Identity `CreateAsync(user, password)` (`RegisterParentCommandHandler.cs:64`); never stored plaintext. The command/response (`JwtAuthResponse`) contains **no password field**. No log statement includes the password — logs reference only `user.Id` (`:101`, `:118`, `:122`). AC-5 satisfied.
4. **Validation / password policy alignment — PASS.** Validator regex `^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)(?=.*[^a-zA-Z\d]).{6,}$` (`RegisterParentCommandValidator.cs:13-14`) matches the configured Identity policy exactly (`DependencyInjection.cs:80-85`: digit, lower, upper, non-alnum, min length 6). Identity `CreateAsync` is a defense-in-depth backstop. No weaker bypass path through the handler. Email validated via `EmailAddress()` + async uniqueness.
5. **Injection — PASS.** No raw SQL / `FromSqlRaw` / dynamic LINQ. Uniqueness check uses parameterized `UserManager.FindByEmailAsync`. `JwtSecurityTokenHandler.ReadJwtToken` is wrapped in try/catch and only reads the just-minted local token. No unsanitized file paths.
6. **Data exposure — see Findings 2, 4, 5.** Duplicate-email message reveals account existence (Low); `ServerError(ex.Message)` can leak internals (Medium); JWT carries PII claims (Info).
7. **Transport / CORS / headers — PASS for this story.** CORS uses an explicit origin allow-list from `AllowedOrigins` (not wildcard) alongside `AllowCredentials()` (`ServiceExtensions.cs:14-21`) — acceptable. `UseHsts()` is on (`Program.cs:99`). Note (not P1-01-specific): JWT bearer sets `RequireHttpsMetadata = false` (`DependencyInjection.cs:114`) — must be dev-only; ensure it's `true` in prod. Flag for the platform, not blocking this story.
8. **Dependencies — PASS.** `dotnet list backend/Learnexia.Modular.sln package --vulnerable` reported **no vulnerable packages** across all 20 projects.
9. **Logging / audit — PASS.** Uses `ILoggerManager` (per conventions). Logs user id and event publication only; no secrets/tokens/passwords/PII (beyond user id) logged.

## Verdict: **FAIL — 1 blocking finding**

Finding **#1 (High — default `CHANGE_ME` JWT secret)** blocks the reviewer gate. While the weak secret pre-exists the story, P1-01 ships a new anonymous, token-issuing endpoint that depends on this signing key, putting it squarely in scope. With a publicly-known signing key, an attacker can forge admin/parent tokens — directly defeating the access-control guarantees this very feature relies on.

The feature **logic itself is sound** — role is server-assigned, no escalation path, password hashed and never leaked, validator aligned with the Identity policy, no injection, no vulnerable dependencies. Findings #2–#5 are non-blocking (Medium/Low/Info) and should be tracked.

## Must-fix (top items)
1. **(Blocking, #1)** Source `JwtSettings:Secret` from env/secret store; reject the `CHANGE_ME…` default at startup. File to lead/backend-feature (config, not feature code).
2. **(#2)** Replace `ServerError<JwtAuthResponse>(ex.Message)` with a generic localized message; log details only.
3. **(#3, follow-up)** Add a tighter per-endpoint rate limit on `/api/Users/Authentication/*` and a story for CAPTCHA + email confirmation.

## Notes / accepted risks
- Findings #2 and #4 mirror existing behavior in `SignInCommandHandler`; fixing consistently across the auth handlers is preferable.
- Finding #5 (PII in JWT) and `RequireHttpsMetadata=false` are platform-wide, not introduced by P1-01 — noted for awareness, not blocking this story.
- Role casing was standardized to PascalCase in `RoleSeeder` (existence-checked, idempotent) and the handler assigns `Roles.Parent.ToString()` consistently — no broken role assignment / silent authz failure observed.
