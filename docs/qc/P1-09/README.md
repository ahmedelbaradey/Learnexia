**Verdict on the BE surface:** P1-09 adds **exactly one new endpoint — `GET /api/Users/Me`**

Everything else P1-09 "depends on" (`Register-Parent`, `Sign-In`, `Add-Child`, `Link-Child`,
`My-Children`, `Sign-Out`) is owned and tested by **P1-01 / P1-02 / P1-03 / P1-04** and is **not
re-tested here** — those are cross-referenced, not duplicated. The only P1-09-specific behavior
beyond `Me`'s own contract is **BE-2: the child-login → `Me` chain that yields the child's locale +
grade + learningLanguage** so the app can render the child's home in the right language/RTL.

**Important — existing coverage already in the repo.** An integration-test file already exists:
`backend/tests/Learnexia.IntegrationTests/P1_09_Me_Tests.cs` (~23 facts). This catalog is written to
(a) **trace the existing facts** to the story criteria so we know what is already green, and
(b) specify the **additional cases** that file does **not** yet cover (the child-login locale chain,
`preferredLanguage` correctness, post-sign-out behavior of `Me`, refreshed-token acceptance, and the
profile-field null/echo semantics). `api-tester` should treat the existing file as the baseline and
**extend** it — not rewrite it.

**Scope note on the live `Me` contract vs. the brief.** The real `MeResponse`
(`…/Features/Authentications/Queries/GetMe/MeResponse.cs`) has grown well past the brief's 6-field
sketch. It now returns: `id, roles[], fullName, preferredLanguage, learningLanguage, isFirstLogin,
hasChildren, phone, country, avatarUrl, grade`. The extra fields (`learningLanguage` P8-01;
`phone/country/avatarUrl` P1-12; `grade` P2-02) were added by **later stories**, which own their
deep validation. This run covers the **P1-09 contract** (role / language / onboarding / child-home
context) and asserts the later fields only at the **envelope-presence / null-semantics** level so
the P1-09 routing-and-locale contract is fully traced; it does not re-own P8-01/P1-12/P2-02 logic.

## 3. Risk notes (where cases are weighted)

1. **`Me` is the routing oracle for the whole app** — if `roles`, `isFirstLogin`, or `preferredLanguage`
   are wrong, every authenticated user lands on the wrong screen or wrong locale. This is the single
   highest-value BE surface in the story, so the P0 weight sits on role correctness (BE-TC-05/06/07),
   onboarding flag (BE-TC-09/10), and the child-locale chain (BE-TC-11/12).
2. **Self-scoping / no-IDOR is a child-data risk.** `Me` is `[Authorize]`-only (not role-gated) so
   children call it too. The handler resolves the user from the JWT (`ICurrentUserService.UserId`) with
   no id parameter. BE-TC-03/04/15 lock in that there is no way to read another user's profile and no
   sensitive field leaks — this overlaps with the `security-auditor` scope (Gate 0A) and is intentional
   defense-in-depth.
3. **Child-login locale chain (BE-2) is the only P1-09-distinct behavior beyond `Me`'s own contract.**
   The child has no separate login endpoint; the app learns the child's language from `Me` after
   `Sign-In`. `LinkedChildResponse` deliberately omits language (module isolation), so `Me` is the
   *only* source of the child's `preferredLanguage` + `learningLanguage` + `grade`. If any of these is
   wrong/null for a child, the home renders in the wrong language / wrong RTL. BE-TC-11..14 carry this.
4. **Stale-contract drift.** The live `MeResponse` is richer than the brief and the existing test file
   (which predates P8-01/P1-12/P2-02). New cases must assert against the **live** shape, and the field-set
   case (BE-TC-16) is intentionally tolerant of additive fields so it does not break when later stories
   add more.
5. **Token lifecycle around `Me`.** A refreshed token must still authorize `Me` (BE-TC-17); the
   behavior of `Me` after `Sign-Out` (does the session-revocation middleware reject the old access token,
   or does it remain valid until JWT expiry?) is a *behavior-to-confirm*, not an assumed pass — flagged
   as an open question and carried as BE-TC-17's second leg.

## 4. Open questions / assumptions (lead to resolve before implementation)

1. **Does this story have a distinct BE surface? — YES, exactly one: `GET /api/Users/Me`.** BE-2 is not
   a new endpoint; it is the child-login→`Me` locale chain over the existing `Sign-In`. Everything else
   is owned by P1-01/02/03/04. Confirm the lead is content scoping this run to `Me` + the child-locale
   chain and **cross-referencing** (not duplicating) the P1-01/02/03/04 cases. *(Assumption taken: yes.)*

2. **`Me` after `Sign-Out` — what is the expected status?** `Sign-Out` revokes the session, but the
   access token is a JWT with its own expiry. Does the session-validation middleware reject the
   now-revoked token on the next `Me` call (→ 401), or does the old access token keep working until it
   expires? BE-TC-17 is written to **assert the documented behavior** — the lead/`api-tester` must
   confirm which is intended so the case asserts the right status rather than guessing. *(Until
   confirmed, BE-TC-17 leg 2 is marked "confirm-expected".)*

3. **`preferredLanguage` source for a parent.** For a parent who registered without choosing a UI
   language, what is `preferredLanguage` expected to be — `"ar"` (Arabic-default product), `null`, or
   the DB default? BE-TC-08 asserts "a non-null, valid locale string ∈ {ar, en} OR null-with-documented-
   fallback"; the lead should confirm the exact expected value so the assertion can be tightened. The
   child path (BE-TC-11) is firmer because the parent sets the child's language at Add-Child.

4. **Existing-file ownership.** `P1_09_Me_Tests.cs` already exists with ~23 facts. Assumption: `api-tester`
   **extends** this file with the 7 net-new cases (and keeps the existing facts as the baseline) rather
   than creating a parallel file. Confirm no objection to editing the existing test file.

5. **"Onboarding-complete" semantics.** `isFirstLogin = !RegistrationIsCompleted`. The story treats
   "has children" and "onboarding complete" as related but distinct (brief open-Q2). BE-TC-09/10 assert
   `isFirstLogin` strictly from `RegistrationIsCompleted`; whether the FE additionally uses `hasChildren`
   to decide routing is an FE concern, not asserted here. No BE change needed — just noting the boundary.
