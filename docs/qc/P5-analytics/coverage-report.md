### Why only P5-01 / P5-02 / P5-04 get new cases
The other P5 backend stories already ship with substantial, AC-mapped test suites (enumerated in §3). P5-01, P5-02, and P5-04 each have strong **unit** coverage but a real **integration gap**: the generation path (job/service → persisted row + event + localize-at-read), detection accuracy over **Postgres + real DI seams**, and the **delivery acceptance criteria** (linked-parent targeting, suppression, fail-soft) triggered from the real producer rather than a hand-published event. The new cases are integration-level and deliberately complement — not duplicate — the existing unit tests.

## 4. Coverage verdict

**Every Phase-5 backend acceptance criterion is covered** by either an existing test, a new case in this run, or is explicitly out of backend scope (FE / DEVOPS), with two flags:

- **No hard GAP** remains for any backend AC.
- **Soft flags (not gaps):**
  - P5-03 AC4 (no latency degradation) is a **DEVOPS/perf** assurance (P6-01 harness), not a functional QC case — correctly out of scope here.
  - P5-08 AC3 AR-localization is asserted structurally (envelope) but the existing P5-08 file does not exercise `Accept-Language: ar` per request; P5-01 GEN-INT-06 adds an explicit EN/AR localize-at-read assertion for the weekly report and will validate whether the integration harness supports per-request culture (see blocker note). If it does not, AR localization remains best-asserted at handler-unit level.
  - P5-04 AC3 recipient semantics need a lead decision (see §5) — DEL-INT-03 asserts cross-family isolation regardless of the outcome.

## 5. Open questions / assumptions (lead decisions before implementation)

1. **P5-04 recap recipient.** The `WeeklyRecapReadyIntegrationEventHandler` resolves the parent via `FindParentForChildAsync` but the persisted re-engagement row is queried by `childId` in P9-06. Is the recap a **child-keyed** re-engagement row read through linkage, or must the literal recipient be the **parent**? AC3 ("only linked parents notified") reads as the latter. The api-tester will record the as-built recipient; the lead decides if it is the intended contract or a defect.
2. **Integration harness per-request culture.** P5-01 GEN-INT-06 (and any AR delivery assertion) depends on the harness supporting `Accept-Language`/culture per request. If unsupported, mark those cases BLOCKED-harness-locale and rely on handler-unit localization coverage.
3. **Direct Hangfire job invocation.** GEN-INT-07/08 assume `WeeklyReportJob.RunAsync()` can be resolved and invoked in-process (it is a thin DI-scoped sweep). Confirm; otherwise assert the service per-child and treat the prior-week-window math as covered by the job's own logic.
4. **Multi-subject activity seeding.** The cleanest way to make the cross-module seams return non-zero data for a report week (seed via source-module seams vs. direct DbContext) — assumed direct DbContext seeding within a DI scope is acceptable for integration tests, consistent with P9-06/P5-08 patterns.

## 6. Risk notes (where cases were weighted)

- **Highest risk — P5-04 delivery targeting (P0, DEL-INT-03):** child-data delivery crossing family boundaries would be a privacy defect; the recipient-semantics ambiguity makes this the riskiest area, hence the cross-family isolation case is load-bearing and P0.
- **High risk — Npgsql vs InMemory divergence (P5-02 WA-INT-01/02):** the detector's recent-accuracy lookup uses group-by + `OrderByDescending(...).FirstOrDefault()` and a 3-hop navigation join; InMemory may translate these differently than Postgres, so a small targeted integration set guards the real provider.
- **Medium risk — localize-at-read (P5-01 GEN-INT-02/06):** recommendations are persisted as stable codes and rendered at read; a regression to persisting prose (or a missing resource key) is silent at the DB level and only visible end-to-end.
- **Medium risk — zero-activity suppression (P5-01 GEN-INT-03, P5-04 DEL-INT-04):** the row-written-but-event-suppressed split is subtle (never-shaming FR-GM-8) and easy to break when refactoring the producer; covered at both producer-unit and end-to-end levels.
- **Lower risk — idempotency / distinct enumeration (GEN-INT-05/08):** backed by a DB unique constraint and `.Distinct()`; covered at P1/P2 as regression guards.
