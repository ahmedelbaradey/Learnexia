# Design Spec — P8-01-FE Add-Child Learning-Language Field

> Surface: `apps/student-app/app/(onboarding)/_components/AddChildForm.tsx` (the one-child detail
> form inside the Add-Child onboarding screen). Parent-facing. Arabic-first (default `ar`, RTL),
> dark theme default.
> Extends P1-03 add-child. **This is an additive field spec, not a redesign** — every existing
> field keeps its current shape, tokens, and order.
>
> No capture/preview-card exists for this onboarding form (it is an app screen, not a web
> dashboard surface — the screen→capture index covers parent-dashboard + marketing + mobile-HUD
> screens, not the onboarding add-child form). The fidelity target here is therefore the
> **already-built form components** (`TextField`, `Select`/`LanguageSelect`, `GradePicker`,
> `Button`) and the **`--lx-*` / Tamagui tokens** they already consume — cited inline below.
> Any pixel value is transcribed from the live component source, not eyeballed.

## 1. The core decision — three concepts, two of them "language"

The form currently has ONE language field (`language` = the child's account/UI language,
`PreferredLanguage`). P8-01 adds a SECOND: `learningLanguage` (medium of instruction for Math &
Science). On one short form, two fields both labelled "language" is a real confusion trap for an
Arabic-speaking parent. The spec resolves this with **grouping + relabelling + ordering + helper
text + a default-to-match affordance**, all built from existing component shapes.

### Decision summary (answers to the brief's open questions)

| Question | Decision | Rationale |
|---|---|---|
| Is the learning-language field required? | **Required, with NO pre-selected value** (placeholder shown, empty until the parent picks). | Medium of instruction selects which curriculum trees the child ever sees and (per architecture §5) is expensive to change later (fresh-start, progress reset). A silent default could be submitted blindly and mis-set the child for the whole year. Force a deliberate choice. The other fields (name/email/password/country) are also empty-by-default, so this is consistent. |
| Relabel the UI-language field here? | **YES.** Rename it on this form from "Preferred language" to **"App language"** (EN) / **"لغة التطبيق"** (AR). Keep the learning-language field as the prominent, fully-described one. | Two fields both reading "language" are indistinguishable. Renaming the UI field to "App language" + describing it as "buttons, menus, and messages" makes the contrast self-evident: one is *what the child studies in*, the other is *what the app's chrome reads in*. |
| De-emphasise the UI-language field? | **Lightly.** Order **learning language FIRST (prominent, with helper)**, app language **SECOND (with a short helper that references the learning field)**. Do not hide or collapse it — it stays a full `LanguageSelect`, just second and described as the app-chrome language. | The medium of instruction is the load-bearing choice; the UI language is secondary and auto-fills (next row). Ordering encodes priority without removing functionality. |
| Default-to-match surfaced how? | **Auto-fill on selection.** When the parent picks a learning language, the App-language field's value is set to match **only if the parent has not already touched App language**. A short helper under App language explains it. Editable at all times. | Meets the architecture §7 "default the UI `PreferredLanguage` to match the chosen `LearningLanguage`, but keep them editable independently" rule without trapping the parent. The "only if untouched" guard prevents stomping an explicit parent choice. |

## 2. Layout & field order (final)

The form is a single `Stack gap="$4"` column inside the existing `$cardSoft` / `borderRadius="$card"`
form card (unchanged). New/changed rows in **bold**. Order top→bottom:

```
Child's full name        (unchanged — TextField)
Login email              (unchanged — TextField, forceLtr value)
Password                 (unchanged — TextField, secure)
Grade                    (unchanged — GradePicker)
┌─ Language group ─────────────────────────────────────────────┐   ← NEW visual grouping
│  GROUP EYEBROW: "Languages" / "اللغات"                        │   (see §4 for the group header)
│                                                               │
│  **Learning language**  (NEW — LanguageSelect, REQUIRED)      │   ← prominent, first
│    helper: "The language your child will study Math &         │
│             Science in."                                      │
│                                                               │
│  **App language**       (RELABELLED — the existing `language` │   ← second, de-emphasised
│                          field; LanguageSelect)               │
│    helper: "The language for buttons, menus, and messages.    │
│             We've matched it to the learning language — you   │
│             can change it."                                   │
└───────────────────────────────────────────────────────────────┘
Country                  (unchanged — TextField)

[ Add Child to List ]    (unchanged — Button variant="secondary" size="full")
```

Rationale for the group: a thin labelled container visually fences the two language fields together
so the parent reads them as a *related pair* ("here is where I set the two languages"), which is
exactly the disambiguation the brief asks for — they are compared side-by-side rather than scattered.

### Responsive (390 / 768 / 1024)

The add-child screen is a single-column scroll (`ScrollView` → `Stack paddingHorizontal="$6"`).
The form column is full-width within the card at every breakpoint. **No multi-column** — keep the
two language fields **stacked vertically** (not side-by-side) at all widths, so the helper text under
each stays attached and the "learning first / app second" priority is preserved by vertical order.

- **390 (mobile, primary target):** full-bleed column, fields 100% width, 48px triggers.
- **768 / 1024 (web/tablet):** the existing add-child screen does not widen the form card beyond its
  column; keep the form's intrinsic max width as-is (inherits the existing screen layout — no change
  requested). Fields remain stacked.

One primary action on the screen remains the bottom **"Add … Children and Continue"** button; the
form's own **"Add Child to List"** is `variant="secondary"` (unchanged) so there is still a single
visual primary.

## 3. Component composition (mirror existing shapes — no new components)

### 3.1 Learning-language field — `LanguageSelect` (existing)

Identical component and props to the current `language` field, only new label/placeholder/helper +
its own `Controller name="learningLanguage"`. From `packages/ui/.../Select/index.tsx`:

- Stacked label: `Text` color `$fg3`, `fontSize 12`, `fontWeight 600`, `fontFamily $heading`,
  `textTransform uppercase`, `letterSpacing 0.6`, aligned per `direction`.
- Trigger (`XStack`): `height 48`, `paddingHorizontal 14`, `borderRadius 14` (the `inputRadius`
  local constant — matches TextField), `borderWidth 1`, `backgroundColor $card`.
  Border color logic (already in component): `$danger` on error → `$borderFocus` open →
  `$borderStrong` selected → `$border` resting.
- Open panel: `$card`, `borderRadius $sm` (8), `borderColor $borderStrong`, shadow
  `#000 / 0.3 / radius 16 / offset y 8`. Options `minHeight 52`, selected row tint `$primarySoft`
  with `$primaryLight` label + ✓.
- Value text: `fontSize 15`, `fontFamily $body`; placeholder uses `$fg3`, selected uses `$fg1`.
- Options come from `useLanguageOptions()` (existing) — same `onboarding.language.{ar,en}` labels
  (`عربي / Arabic`, `الإنجليزية / English`). **Reuse the same option set** — the brief open
  question #6 is answered: no separate learning-language option list; both fields offer ar/en from
  `LOCALES`.

**Required, no default:** `value` starts `null` → placeholder renders. zod blocks submit (see §6).

### 3.2 App-language field — the EXISTING `language` `LanguageSelect`, relabelled

Same component instance/position-in-DOM as today, only:
- label key → `onboarding.addChild.labelAppLanguage` ("App language" / "لغة التطبيق").
- placeholder key → unchanged concept; reuse `onboarding.addChild.languagePlaceholder`.
- gains a helper line (see §3.3).
- gains the auto-fill behaviour (§5).

`language` keeps its current default `'ar'` in `EMPTY` — but because it auto-fills from the learning
language on selection, the visible value tracks the learning choice.

### 3.3 Helper text — rendered as a sibling `Text`, NOT a new component prop

Neither `Select` nor `TextField` has a `helperText` prop today, and the brief forbids inventing
patterns. **Do not add a prop.** Instead render the helper as a sibling `Text` immediately under
each field's `Controller`, styled to match the components' own secondary text:

- `Text` color `$fg3`, `fontSize 12`, `fontFamily $body`, `lineHeight` generous (≥ 1.4 → ~17px),
  `marginTop 2`, `textAlign` per direction, `writingDirection={direction}`.
- This mirrors the existing error `Text` style in `Select`/`TextField` (same `$fg3`-family muted
  small body text), so it reads as part of the field, not a new widget.

> Helper text is decorative/explanatory, not the error. It is always visible (not only on error).
> When the field is in error, the red error `Text` from the component renders **in addition** below
> the helper (error = `$danger`, helper = `$fg3`), so the two never collide in color.

### 3.4 Group container & eyebrow — built from a plain `Stack` + `Text` (no new component)

- Outer group: `Stack gap="$3"`, `padding="$3"`, `borderRadius="$sm"` (8), `borderWidth 1`,
  `borderColor "$borderSubtle"` (the 0.06 hairline already used for dividers), `backgroundColor`
  transparent (do **not** darken — brand law #1; the card already steps to `$cardSoft`, a nested
  darker fill would violate "cards step lighter"). The hairline border alone fences the group.
- Group eyebrow `Text`: color `$fg3`, `fontSize 12`, `fontWeight 600`, `fontFamily $heading`,
  `textTransform uppercase`, `letterSpacing 0.6` — identical to the list-section label already used
  on the add-child screen (`onboarding.addChild.listLabel`). Copy: "Languages" / "اللغات".

> This grouping is plain layout primitives (`Stack` + `Text`) with existing tokens — it is **not** a
> new design-system component or a new pattern; it is the same fencing technique the form already
> uses for the children list section. If the lead considers even a token-only labelled group a "new
> pattern", see Open Questions Q1 for the fallback (drop the border, keep eyebrow + helper).

Arabic conventions (Tajawal body, sentence case, no gratuitous exclamation — this is instructional,

## 5. Default-to-match behaviour (P8-01-FE-3)

On selecting a **learning language**, default the App-language (`language`) field to the same value,
**without trapping** the parent:

- Track whether the parent has manually edited App language (e.g. a `appLanguageTouched` flag set in
  the App-language field's `onChange`).
- In the learning-language field's `onChange`: set `learningLanguage`, and **if
  `appLanguageTouched === false`**, also `setValue('language', chosenLearningLanguage)`.
- Once the parent edits App language directly, `appLanguageTouched = true`, and subsequent
  learning-language changes **no longer** overwrite it.
- Both fields remain independently editable at all times; neither is disabled or locked.
- The `appLanguageHelper` copy surfaces this in words ("We've matched it … you can change it"), so
  the auto-fill is never surprising.

This is form logic (react-hook-form `setValue` + a local touched flag) — no component change.

No motion required on auto-fill beyond the field simply showing the new selected value (the existing
selected-state styling: border `$borderStrong`, value text `$fg1`). Do **not** animate/flash it —
it's a quiet convenience, not a reward moment.

## 6. States

| State | Behaviour / tokens |
|---|---|
| **Empty / initial** | Learning language: `value=null` → placeholder `Choose learning language` in `$fg3`, resting border `$border`. App language: shows default `ar` selected (or whatever auto-fill last set). Helpers visible in `$fg3`. |
| **Selected** | Trigger border `$borderStrong`, value text `$fg1`. Selected option row in the panel tinted `$primarySoft` + `$primaryLight` label + ✓ (existing). |
| **Open** | Border `$borderFocus` (#4F46E5) + the component's existing focus shadow `rgba(99,102,241,0.25)` radius 4. |
| **Required error** (submit with learning language empty) | Component renders its error slot: border `$danger`, error `Text` in `$danger`, fontSize 12, announced `accessibilityLiveRegion="polite"`. Copy: `errors.learningLanguageRequired`. The `$fg3` helper stays visible above it. |
| **App-language untouched** | Auto-fills to learning language on each learning-language change. |
| **App-language touched** | Locks out auto-fill; retains the parent's explicit value. |
| **Disabled** (not used on this form, but inherited) | `opacity 0.5`, `pointerEvents none` (Select default). |
| **Loading / submit** | The field itself has no loading state; submit is gated at the screen level. While the screen's bottom submit runs, `Button loading` spins (existing). The per-form "Add Child to List" press triggers zod validation on submit (`mode: 'onSubmit'`) — error appears inline if learning language is empty. |

### zod (P8-01-FE-1, informs the error state)
Add to `addChildSchema`: `learningLanguage: z.enum(LOCALES, { errorMap: () => ({ message: 'onboarding.addChild.errors.learningLanguageRequired' }) })`. Because there is no default in `EMPTY`,
leaving it produces the required error. Add `learningLanguage` to the `EMPTY` constant as
`undefined`/omitted so the field starts unselected (the schema makes it required so submit is
blocked). Keep `language` as-is (`'ar'` default, auto-filled).

## 7. RTL / i18n

The form already passes `direction` to every field; the new field uses the same `direction` prop —
no special handling beyond reusing it. Specifics:

- **Both selects** flip via the component's existing `flexDirection: row-reverse` and
  `textAlign: right` when `direction === 'rtl'`. Pass the same `direction={direction}` from
  `useLocale()`.
- **Helper `Text`** and **group eyebrow `Text`**: set `writingDirection={direction}` and
  `textAlign={isRtl ? 'right' : 'left'}` (mirror the components' own label alignment).
- **Group container**: use logical props only (`padding`, `gap`, `borderRadius`) — no left/right
  hardcoding, so it mirrors automatically.
- **Option labels** are bilingual strings; do not mirror the glyphs — they render as-is.
- Default product locale is **ar** → the parent sees Arabic labels, RTL layout, learning-language
  field on top by reading order (first in the RTL column = top, unaffected by horizontal mirroring
  since fields are stacked vertically).
- No inline numerals in this field set, so the Eastern-Arabic-numeral rule does not apply here.
  (Email value stays LTR via the existing `forceLtr` on the email field — unchanged.)

## 8. Accessibility / kid-platform (parent-facing)

- **Labels:** each select's visible stacked label feeds `accessibilityLabel` (component default).
  For the learning-language field, pass an explicit `accessibilityLabel` that includes the purpose,
  e.g. `t('onboarding.addChild.labelLearningLanguage')` (already descriptive: "Learning language").
- **Required indication:** rely on the inline required-error announcement (live region) — the form
  uses `mode: 'onSubmit'`, so the error is the required signal. **Recommend** additionally appending
  a required marker to the label for sighted parents — see Open Questions Q2 (the existing required
  fields like name/email do not show an asterisk today, so adding one only here would be
  inconsistent; flagging rather than unilaterally adding).
- **Helper text as accessible description:** the helper `Text` should be associated as the field's
  description where the platform allows (web: `aria-describedby`; RN: it reads in order after the
  label). At minimum it is a visible, screen-reader-reachable sibling. Do not hide it from a11y.
- **Tap targets:** triggers are 48px tall (`TRIGGER_HEIGHT.md`) → meets the ≥48px target. Option
  rows are `minHeight 52`. No change needed.
- **Color contrast:** helper `$fg3` (#94A3B8) on `$cardSoft` (#334155) and on `$card` (#1E293B)
  passes for 12px secondary text in dark theme (existing usage pattern). Error `$danger` is the
  distinct error channel.
- **Focus:** keyboard nav lands on each trigger (`accessibilityRole="combobox"`); the open state
  uses the indigo focus shadow. Honor the global focus-ring expectation on web.

## 9. Motion

None new. The select open/close uses the component's existing instant toggle. The auto-fill is a
silent value set (no flash, no confetti — not a reward moment, per brand law #3/#12). The only motion
on the form remains the existing button press feedback (`scale 0.95` handled by `Button`).

## 11. New components needed

**None.** Everything is composed from existing components (`LanguageSelect`, `Stack`, `Text`,
`Button`) and existing tokens. No new design-system component, no new variant.

component — but because the form has not used a fenced field-group before, it is flagged in Open
Questions Q1 for the lead's explicit OK (CLAUDE.md rule #8: ask before introducing a pattern).

## Open questions for the lead

1. **Labelled field-group (Q1).** I specify a thin hairline-bordered `Stack` fencing the two language
   fields, with an "اللغات / Languages" eyebrow. It's built from existing primitives + tokens
   (`$borderSubtle`, `$sm`, the existing eyebrow style), but the form has not grouped fields before.
   **OK to add this token-only group, or prefer the lighter fallback** (no border/container — just
   the two fields adjacent, each with its helper, and a plain eyebrow `Text` above the pair)? Either
   satisfies the disambiguation AC; the bordered group is clearer, the fallback is zero-new-structure.

2. **Required asterisk (Q2).** Existing required fields (name/email/password/country) show **no**
   visual required marker today — they rely on submit-time errors. Should the learning-language field
   (the only one whose mis-set is costly) get an explicit required marker (e.g. a `*` in `$danger`
   appended to the label, or "(required)" text), accepting it's inconsistent with the other fields —
   or stay consistent and rely on the inline error like the rest? I lean **consistent (no asterisk)**
   to avoid a one-off, but flagging because this field's stakes are higher.

3. **AR wording (Q3).** Confirm "لغة الدراسة" (learning language) vs "لغة التطبيق" (app language) as
   the disambiguating pair, and the helper copy in §4. An alternative for learning language is
   "لغة التدريس" (language of *instruction*) — I chose "الدراسة" (study) as more parent-natural.

4. **Child-card meta (Q4).** The draft `ChildCard` meta currently reads `Grade · {UI language}`.
   Should it now show the **learning** language instead of (or in addition to) the UI language, since
   learning language is the more meaningful per-child attribute? Out of strict scope (FE-2…FE-5 don't
   require it) — flagging as a small polish decision.

5. **Capture coverage (Q5).** There is no screenshot/preview-card for the onboarding add-child form
   in `design-system/`. This spec is grounded in the live components instead. If a canonical capture
   is desired for this onboarding surface, that's a separate design-system task — flagging the gap,
   not blocking implementation.

Design spec ready for frontend.
