# Design Spec — P1-12-FE Web Account Features

> Surface: parent-facing web (Expo web PWA, `apps/student-app`). Default locale **ar (RTL)**, default theme **dark**.
> Scope = the six P1-11-deferred account affordances that the merged P1-12 backend now lights up. These have **no prior pixel capture** (only the Login link, `web/02-login.png`, the Settings profile area in `web/07-settings.png`, and `web/04-my-children.png` ground them). Everything below reuses existing primitives + tokens and mirrors existing auth/settings shapes. **No new design pattern is introduced** (the one borderline case — a confirm dialog for avatar remove — is flagged in Open Questions; the recommended path avoids it).
> This is a **design delta** spec, not a from-scratch redesign. Each surface points at the existing component to extend and the exact states/tokens/copy to add.

Tokens referenced are the Tamagui `$…` mirrors of `design-system/colors_and_type.css` (`packages/design-system/src/tokens/*`). Brand law (dark canvas, radii buckets, soft shadows, glow only on reward/CTA, focus ring) applies throughout. Copy lives in `packages/shared/src/i18n/resources.ts` under `en` + `ar`; every new string below names its i18n key.

Shared conventions reused on every surface (already established in the codebase, do not reinvent):
- **RTL:** `direction`/`isRtl` from `useLocale()`; row containers use `flexDirection={isRtl ? 'row-reverse' : 'row'}`; text uses `writingDirection={direction}` + `textAlign` end/start. Latin technical fields (email, phone, token) use `forceLtr` on `TextField`.
- **Errors:** `ServerErrorBanner` (`apps/student-app/src/components/ServerErrorBanner.tsx`) + `useServerError()` mapping (`byStatus` / `hints`).
- **Success:** the established `$successSoft` panel + `$success` text with `accessibilityLiveRegion="polite"` (see `SettingsWeb` ProfilePanel).
- **Targets:** all interactive rows ≥ 48px (Checkbox already enforces `minHeight={48}`; Buttons `size="md"` ≈ 52px).
- **Motion:** Button press `scale 0.95`; no extra motion unless noted.

## Surface 1 — Avatar upload / remove (Settings ▸ Profile)

**File to extend:** `apps/student-app/app/(parent)/_components/SettingsWeb.tsx` → `ProfilePanel`, the avatar row at lines ~327–360 (the two `disabled` stub buttons).
**Primitives:** `Avatar` (`packages/ui` — already takes `uri`), `Button` (`primary` for upload, `danger` for remove), `ServerErrorBanner`. Web file pick = programmatic `<input type="file" accept="image/png,image/jpeg,image/webp">` behind a `Platform.OS === 'web'` guard (native deferred per plan B-3).
**Hooks:** `useUploadAvatar` (POST), `useRemoveAvatar` (DELETE) — both invalidate `queryKeys.account.profile()` + `queryKeys.auth.me()` so the `Avatar` re-renders from the new `avatarUrl`.

### Layout (390 / 768 / 1024)
The avatar row stays a single horizontal cluster (`flexDirection={rowDir}`, `alignItems="center"`, `gap={18}`): the `Avatar size="xl"` (72px) followed by a vertical stack of the two action buttons + helper/error text.
- **390 (phone):** Avatar above, actions wrap below it (the row already `flexWrap`s; let the button group drop under the avatar). Buttons full-bleed within their column.
- **768 / 1024:** Avatar left (right in RTL), actions to its inline-end. Helper + error text sit directly **below the avatar row**, start-aligned (the inline anchor the brief asks for), not in the form's bottom banner.

### Composition
```
[ Avatar(xl) ]   [ Button primary "Upload photo" ]  [ Button danger "Remove" ]
                 helper: "PNG or JPG, up to 5 MB"      ← $fg3, 12px, below the button group
                 (inline error / success / pending text replaces helper)
```
- Upload button keeps `variant="primary" size="sm"`. **Remove** changes from `variant="ghost"` to **`variant="danger"` size="sm"** (destructive intent → `$danger` fill per brand law + brief). Only show Remove when `profile.avatarUrl` is set; hide it when the avatar is already initials-only.
- Add a 12px helper line under the buttons (new): file-type/size guidance.

### States
| State | Visual | Tokens / behavior |
|---|---|---|
| **idle (has photo)** | image avatar + Upload + Remove enabled | `Avatar uri=profile.avatarUrl`; helper text `$fg3 12px` |
| **idle (no photo)** | initials avatar + Upload only (Remove hidden) | initials fallback already in `Avatar` |
| **picking** | OS file dialog open (web `<input>`) | no UI change; buttons stay enabled until a file is chosen |
| **validating (client)** | instant | reject if `!type.startsWith('image/')` or `size > 5MB` → inline error, no network call |
| **uploading / pending** | spinner overlay on the avatar + both buttons disabled | `Button loading` on Upload; overlay = absolute `$overlay`-tinted layer over the avatar with a small spinner; `aria-busy`; helper text → `parent.settings.profile.avatar.uploading` |
| **success** | new image shows (cache invalidation refetch) + transient confirmation | reuse `$successSoft` panel briefly OR inline `$success` text `parent.settings.profile.avatar.uploadSuccess`; live region polite |
| **upload error** | inline error below avatar row | `$danger` text `parent.settings.profile.avatar.uploadError` (server) or `…tooLarge` / `…wrongType` (client); `accessibilityLiveRegion="assertive"` |
| **remove → success** | avatar falls back to initials; Remove hidden | `parent.settings.profile.avatar.removeSuccess` |
| **remove error** | inline error | `parent.settings.profile.avatar.removeError` |

**Remove confirm:** recommended **no modal** — `danger` color + the destructive label are sufficient and avoid a new pattern; removal is reversible (re-upload). (Flagged in Open Questions Q1 if the lead wants an explicit confirm.)

**Hook:** `useForgotPassword` (anonymous). **Wire from Login:** replace `LoginForm.handleForgotPassword` no-op with `router.push('/(auth)/forgot-password')`.

### Layout (390 / 768 / 1024)
Identical to Login: split panel ≥768 (brand left in LTR / right in RTL via existing scaffold flip), single column ≤768 with logo mark on top. Form max-width 500 (scaffold default).

### Composition
```

[ TextField email — forceLtr ]
[ ServerErrorBanner ]
[ Button primary size=full "Send reset link →" ]
[ link → "Back to Sign in" → router.replace('/(auth)/login') ]
```
On **success** the whole form body is replaced by a confirmation panel (see states). The "Back to Sign in" link persists in both views.

### States
| State | Visual | Behavior |
|---|---|---|
| **idle** | email field + submit | zod: required + email format |
| **invalid email** | inline field error | `auth.forgotPassword.errors.invalidEmail` |

## Surface 6 — Edit child on web (`MyChildrenWeb` + edit sheet)

**Files:** `apps/student-app/app/(parent)/_components/MyChildrenWeb.tsx` (add the Edit entry point), `ChildDashboardCard.tsx` (add optional `onEdit`), and an edit sheet.
**Hook:** `useUpdateChild` (`{ childId, fullName, grade, language, country }`).

### ⚠️ Key design decision — DO NOT reuse `AddChildForm` verbatim for the backend-wired edit
`updateChild` accepts only **`fullName / grade / language / country`**. But `AddChildForm` (which `EditChildSheet` renders) also requires **`email`, `password`, and `learningLanguage`** (`addChildSchema`, `packages/shared/src/schemas/index.ts` lines 95–117). Reusing it as-is for the real edit would:
1. force the parent to re-enter a **password** that is never sent (confusing + a security smell), and
2. collect `email`/`learningLanguage` that `updateChild` ignores.

**Recommended composition (mirror the sheet shell, use an edit-only field set):**
- Keep `EditChildSheet`'s shell (RN `Modal` bottom sheet, drag handle, header with title + close, `$overlay` scrim, `$card`, `borderTopStartRadius/EndRadius="$modal"`) — this is the existing pattern, reused.
- Inside, render an **edit-only field set** = the four editable fields only: `fullName` (`TextField`), `grade` (`GradePicker`), `language` (`LanguageSelect`), `country` (`Select` of `COUNTRIES`, matching the Settings profile country select — not the free-text `TextField` the onboarding form uses). Email is shown **read-only/display** (identifies the child) if available, never editable here. No password field.
- This is a **field-set variation of the existing form**, not a new pattern. The onboarding `add-child` flow keeps using full `AddChildForm` unchanged. (Flagged Q2 — confirm building a slim `EditChildFields` vs. forcing `AddChildForm`.)

> If the lead insists on literally reusing `AddChildForm`: it must hide password + email + learningLanguage when in edit mode, which is a larger change to that shared form. The slim edit field set is cleaner and lower-risk.

### Edit entry point on the card (delta to `ChildDashboardCard`)
Add an optional `onEdit?: () => void` prop. When provided, render an **Edit affordance** in the card header — a small icon button (pencil / Lucide `pencil`, 2px line, `$fg3`) at the card's inline-end of the header row (opposite the avatar), 44×44 target, `hoverStyle` brighten, `pressStyle scale 0.95`. Place it so it does not collide with the active/inactive status. In RTL it sits at the visual left of the header (row reverses). `accessibilityLabel = "Edit {childName}"`.
`MyChildrenWeb` holds `editingChild` state seeded from the child (`id, fullName, grade, language, country`) and passes it to the sheet; close handler clears it.

| **closed** | card with Edit icon | — |

| **saving / loading** | submit button `loading`, fields disabled | `useUpdateChild.isPending` |
