# Design Spec — P7-09 Content Moderation Queue (Admin Console Frontend)

**Surface:** `apps/admin-dashboard` (Next.js 15, desktop-first, dark theme)
**Token authority:** `design-system/colors_and_type.css` + `packages/design-system/src/tokens/`
**Shell authority:** Established admin shell from P1-10 / P7-admin-users-wave.md — all layout, nav, topbar, and skeleton rules carry forward unchanged.
**Locale:** English-first at runtime, RTL-ready (all copy has AR slot; `dir="rtl"` toggles layout).
**Theme:** Dark by default (`--lx-bg` = `#0F172A`).
**Backend contract:** `api/Admin/Moderation` (PR #180, merged). All endpoints `[Authorize(Policy = AuthorizationPolicies.AdminOnly)]`.

> Note on captures: No screenshot captures exist for this admin surface. All specifications are derived from the P1-10 / P7 admin shell tokens, the existing admin component source (`StatusBadge`, `AdminConfirmDialog`, `ReasonField`, `SuspendUserDialog`, `AdminErrorBanner`, `AdminSideNav`, `users/page.tsx`, `users/[id]/page.tsx`), the contract DTOs, and the `--lx-*` token set. This is not a gap — the admin surface is built entirely from design-system tokens, not from a separate visual-capture set.

---

## Admin surface principles (carry-forward — unchanged)

1. No gamification chrome — no XP bars, confetti, streak flames, mascots, or reward gradients.
2. Gradients forbidden on all admin elements (XP/Reward/Level-Up are student-app only).
3. Motion minimal: hover transitions 120ms `--lx-ease-out`; dialog entrances 200ms fade+translate; skeleton shimmer. No spring overshoot.
4. One primary action per screen. All destructive/state-changing actions require explicit confirmation dialogs.
5. Typography: Poppins (EN) / Cairo (AR headings) / Tajawal (AR body). Max heading H2 24px on admin.
6. Density: cards use `--lx-space-4` (16px) padding where tight. Tables are compact.

---

## Enum wire values (resolved from merged backend code)

Both `ModerationStatus` and `ModerationSource` are persisted as strings. Send and expect **string names** on the wire:

| Enum | Values (string name) |
|---|---|
| `ModerationStatus` | `"Pending"` / `"Approved"` / `"Rejected"` / `"Flagged"` |
| `ModerationSource` | `"AiOutput"` / `"CurriculumUpload"` |

Send `Status="Pending"` in query params, `decision="Approved"` in POST body. If the running API binds by int (OQ-3 — needs a quick verify), fallback order is Pending=0, Approved=1, Rejected=2, Flagged=3. **The api-tester must confirm enum wire form against the live API before frontend batch 2b ships.**

## PART A: Shared Primitives (new, additive only — no structural changes to existing components)

### A.1 — `ModerationStatusBadge` (extend `StatusBadge`, additive)

**Approach:** add a `variant="moderation"` to the existing `StatusBadge` component (additive — same pattern as existing `variant="status"` and `variant="role"`). No new component file required.

**Anatomy:** identical to the existing pill shape — inline-flex, height 22px, borderRadius `--lx-radius-pill` (9999px), paddingHorizontal 10px, gap 5px. A 6px dot + uppercase label text 12px weight 600.

**Colour mapping:**

| ModerationStatus | Label EN | Label AR (i18n key) | Dot color | Background | Text color |
|---|---|---|---|---|---|
| `Pending` | Pending | قيد المراجعة (`mod.status.pending`) | `#F59E0B` (`--lx-accent`) | `rgba(245,158,11,0.15)` | `#F59E0B` |
| `Approved` | Approved | موافق عليه (`mod.status.approved`) | `#22C55E` (`--lx-secondary`) | `rgba(34,197,94,0.15)` | `#22C55E` |
| `Rejected` | Rejected | مرفوض (`mod.status.rejected`) | `#EF4444` (`--lx-danger`) | `rgba(239,68,68,0.12)` | `#EF4444` |
| `Flagged` | Flagged | مُعلَّق (`mod.status.flagged`) | `#A855F7` (`--lx-purple`) | `rgba(168,85,247,0.15)` | `#A855F7` |

**Rationale for colour choice:** Pending=amber (awaiting action), Approved=green (positive outcome), Rejected=red (negative outcome), Flagged=purple (escalated / scrutiny — distinct from the red of Rejected so the two terminal states are not confused).

**A11y invariant (carried forward from existing `StatusBadge`):** colour is never the only signal. The dot provides shape, the text label provides semantic meaning. Screen readers read the label; do not add aria-label redundantly.

**RTL:** text direction follows `dir` attribute of parent. In AR locale use Tajawal 12px weight 600.

**Props addition to `StatusBadge`:**

```
interface StatusBadgeModerationProps {
  variant: 'moderation';
  value: ModerationStatus;  // string: 'Pending' | 'Approved' | 'Rejected' | 'Flagged'
  strings: AdminStrings;
}
```

**Fallback:** unknown status string → render a neutral `$fg3` / `rgba(255,255,255,0.08)` pill with the raw value text (never crash).

### A.4 — `SafetyVerdictView` (new inline component or section in `moderation/[id]/page.tsx`)

**Purpose:** parses the `safetyVerdict` JSON string from the DTO and renders its contents as human-readable chips/list. Never renders raw flagged content.

**Parse strategy:** wrap in try/catch. On parse failure render a fallback. Check for missing keys defensively; treat `undefined` arrays as empty.

**Parsed `SafetyVerdict` shape:**

```typescript
interface SafetyVerdict {
  failedChecks?: string[];     // e.g. ["ToxicityCheck", "HarmfulContentCheck"]
  reasonCodes?: string[];      // e.g. ["TOXIC_LANGUAGE", "UNSAFE_TOPIC"]
  actionTaken?: string;        // "Blocked" | "Regenerated" | "FallbackReturned"
  modelId?: string;            // opaque model identifier string
}
```

**Layout:**


## PART I: RTL / a11y Specification

### RTL layout rules (carry-forward from admin spec + SKILL.md)

1. `dir="rtl"` on `<html>` or the root admin layout for AR locale.
2. All padding, margin, text-align, border use logical properties: `paddingInline`, `marginInlineStart`, `textAlign: start` (not `left`/`right`).
3. Chevron direction in pagination flips: LTR = `chevron-left` for Prev / `chevron-right` for Next; RTL = opposite.
4. Dialog action row in RTL: Cancel on right (inline-start in LTR flips to inline-end in RTL), Confirm on left. Use `flex-direction: row-reverse` under `dir="rtl"` or logical flex — same as existing `AdminConfirmDialog.tsx` `lx-dialog-actions` class.
5. ContentReference, sourceEventId, modelId, studentId, dates, timestamps, item ID: always `dir="ltr"` — these are technical strings that are not Arabic text.
6. Grade numerals in Arabic reading text: Eastern-Arabic numerals (١٢٣…) — e.g. "الصف ٣". Exception: XP counters, IDs, timestamps stay Latin.
7. Subject/Grade cell in AR: "رياضيات · ٣" (Eastern-Arabic grade, Arabic subject name, middle-dot separator is direction-neutral).
8. The `SafetyVerdictView` chip labels (check names, reason codes) are programmatic English strings from the safety pipeline — render as-is, `dir="ltr"` for each chip in RTL context.

### Accessibility specification

**Queue list page:**
- `<table>` with `<caption class="sr-only">` (mod.tableCaption), `<th scope="col">` on all header cells, `<td>` with `verticalAlign: middle`.
- Each row: `tabIndex={0}`, `role="button"`, `aria-label="{contentReference} — {strings.modViewDetail}"`. `onKeyDown` handles Enter and Space to navigate.
- `aria-live="polite" aria-atomic="false"` wrapper around results area — announces state changes.
- Filter inputs: visually-hidden `<label>` elements associated via `htmlFor`/`id`. All native `<select>` and `<input>` elements are inherently accessible.
- Loading skeleton: `role="status"` `aria-label={strings.modListLoadingLabel}` on the container.
- Error state: `AdminErrorBanner` already has `role="alert"` — fires immediately.

**Detail page:**
- Back link: `<Link>` element, focus style from `--lx-focus-ring`.
- All section headings use semantic hierarchy (h2 for page heading, h3 for section headings via micro-label pattern — in admin the sections use `<p>` or `<span>` styled as micro-labels, not semantic `<hN>` — match existing pattern from users detail page).
- ReviewActionsPanel buttons: `aria-label` includes context, e.g. `aria-label="Approve item: {contentReference}"` / `aria-label="Reject item: {contentReference}"` / `aria-label="Flag item: {contentReference}"`.
- Terminal notice: `role="status"` (not `role="alert"`) — informational, not urgent.
- Success banner after review: `AdminErrorBanner variant="success"` already has `role="alert"`.

**ReviewItemDialog:**
- Inherits `AdminConfirmDialog` a11y: `role="dialog"`, `aria-modal="true"`, `aria-labelledby={titleId}`, ESC cancels, focus trap, trigger-restore on close.
- `ReasonField` aria: `aria-required={required}`, `aria-invalid` when over limit or error, `aria-describedby` linking counter + error.
- Confirm button: `aria-disabled` (not HTML `disabled`) when gated — remains focusable, screen reader reads label + state.

**Touch targets:** all interactive elements (buttons, row clicks, filter controls) >= 44px height. This is the admin surface (desktop-first) but the minimum is preserved.

## Design Gaps and Open Questions

**OQ-3 (MUST RESOLVE before batch 2b): Enum wire form.** The spec recommends sending string names (`Status="Pending"`, `decision="Rejected"`). The api-tester must verify this against the live API at port 3001 before the frontend sends real requests. If the API binds by int (Pending=0, Approved=1, Rejected=2, Flagged=3), the hooks must be updated before ship. This is the single highest-risk contract gap.

**OQ-4 (known, no action): Subject/grade sparsity.** `subjectCode` and `grade` are nullable on AI-sourced items in v1. The filter controls are shown regardless (they serve the future CurriculumUpload producer). The "—" fallback in the subject/grade cell handles null gracefully.

**OQ-5 (resolved by this spec): Post-review feedback.** Uses `AdminErrorBanner variant="success"` on the detail page (auto-dismiss 5s), matching the existing lifecycle-action feedback pattern. No global toast system introduced.

**OQ-6 (resolved): CurriculumUpload empty state.** Neutral "no items" copy — not an error, not "coming soon". The spec's empty-state flavours cover this.

**Design gap — `ReasonField` near-limit threshold.** The existing constant `NEAR_LIMIT_THRESHOLD = 450` (90% of 500) will not automatically scale when `maxLength={2000}`. The fix (compute as `Math.floor(maxLength * 0.9)` inside `ReasonField`) is marked as a required change above. This is an additive internal change, not a prop API change.

**Design gap — Student ID cross-link.** The detail page shows `studentId` as a plain number. A link to `/users/{studentId}` would be useful but is not specified for v1 (the brief does not mention it and it is a cross-surface affordance). Flag for a follow-up story if the lead wants it.

**Design gap — Nav ordering.** The spec proposes: Dashboard → Users → Moderation → Curriculum → Content. The current `AdminSideNav.tsx` has: Users → Curriculum → Content. The insertion point for Moderation is between Users and Curriculum. Confirm with the lead if ordering differs.

**Design gap — `ReasonField` placeholder prop.** `ReasonField.tsx` already accepts `placeholder?: string`. Pass a placeholder in the review dialogs: Reject → EN: "Describe why this item is being rejected…" / AR: "اذكر سبب رفض هذا العنصر…"; Approve/Flag → optional placeholder or omit.
