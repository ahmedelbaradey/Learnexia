## Admin Surface Design Principles (inherited from Wave 1 — unchanged)

1. No gamification chrome — no XP bars, confetti, reward gradients, streak flames, mascot owl.
2. Dark canvas by default (`#0F172A`). Cards step lighter (`#1E293B` → `#334155`). Never darken on interaction.
3. Motion is minimal: hover transitions `120ms --lx-ease-out`, dialog entrances `200ms --lx-ease-out` fade + translateY(8px→0), skeleton shimmer. No spring overshoot.
4. One primary action per screen. Destructive and high-impact actions require explicit confirm dialogs.
5. Typography: Poppins (EN). Cairo (AR display/headings). Tajawal (AR body). Max heading H2 24px on this surface.
6. Density: `--lx-space-4` (16px) card padding allowed where tight. Tables are compact.
7. Semantic `<table>` for all tabular data — no CSS-grid substitutes.
8. Focus ring on all interactive elements: `--lx-focus-ring` = `0 0 0 2px #4F46E5, 0 0 0 6px rgba(99,102,241,0.45)`.

## LOAD-BEARING — `CorrectAnswer` / `Options` jsonb Round-Trip Contract

This section is the most critical part of the spec. Implement exactly as described. A deviation silently breaks student grading.

### Non-Matching (MCQ / TrueFalse / FillInBlank)

**On READ (GET — populating the editor):** `AdminQuestionDto.correctAnswer` arrives as the **raw scalar string**. The backend has already decoded it from jsonb (`QuizProfile.DecodeJsonScalar`). The FE receives `"Paris"`, `"true"`, or `"photosynthesis"` — never `"\"Paris\""`. Bind this value directly into the form. **Do NOT `JSON.parse`.**

**On WRITE (POST/PUT):** send `correctAnswer` as the **same raw scalar string** the editor holds. Do NOT `JSON.stringify`. The backend wraps it on write (`JsonSerializer.Serialize → stores "\"Paris\""`) and strips the wrapper on read. The round-trip is symmetric for the FE.

### Matching

**On READ:** `AdminQuestionDto.options` arrives as a raw JSON object string (passthrough — no decode); parse it yourself:
```
JSON.parse(options) → { left: Array<{id,text}>, right: Array<{id,text}> }
```
`AdminQuestionDto.correctAnswer` is also a raw JSON object string; parse it:
```
JSON.parse(correctAnswer) → { pairs: Array<{leftId, rightId}> }
```
Parsing MUST be wrapped in try/catch. On parse failure → render an error banner inside the editor: EN "Failed to load question data — invalid format." / AR "فشل تحميل بيانات السؤال — تنسيق غير صالح."

**On WRITE:** serialize the FE form model back:
```typescript
// options wire value:
JSON.stringify({
  left:  matchLeft,   // Array<{id: "l1", text: "…"}> — FE-generated stable ids
  right: matchRight,  // Array<{id: "r1", text: "…"}> — store right in non-aligned order
})

// correctAnswer wire value:
JSON.stringify({
  pairs: matchPairs,  // Array<{leftId: "l1", rightId: "r1"}> — one entry per left item
})
```
The backend stores these as-is (no extra wrap). The FE is the authoritative serializer for Matching.

### Options for Non-Matching Types

| Type | `options` wire value |
|---|---|
| MCQ | `JSON.stringify(optionStrings)` — e.g. `'["Paris","London","Cairo"]'` (≥2 strings). FE serializes on write; FE calls `JSON.parse` on read to restore `optionStrings[]`. |
| TrueFalse | `JSON.stringify(["True","False"])` — fixed. Send this on every write. On read, parse is unnecessary (value is fixed); the editor ignores it. |
| FillInBlank | `JSON.stringify([])` — empty array. Send on every write; ignore on read. |

### Summary table

| Type | options on write | correctAnswer on write | options on read | correctAnswer on read |
|---|---|---|---|---|
| MCQ | `JSON.stringify(string[])` | raw option text (e.g. `"Paris"`) | `JSON.parse(string)` → `string[]` | raw string → bind to radio |
| TrueFalse | `JSON.stringify(["True","False"])` | `"true"` or `"false"` | ignore | raw string → bind to toggle |
| FillInBlank | `JSON.stringify([])` | answer text | ignore | raw string → bind to input |
| Matching | `JSON.stringify({left,right})` | `JSON.stringify({pairs})` | `JSON.parse` → `{left,right}` | `JSON.parse` → `{pairs}` |

## Route Shape

**Decision D-OQ-P04-route (from plan):** nested context-carrying route under the P7-02 lesson. Because P7-02 provides the lesson list and lesson detail at `curriculum/subjects/[id]/units/[id]/lessons`, the question manager sits at:

```
app/(admin)/curriculum/subjects/[subjectId]/units/[unitId]/lessons/[lessonId]/questions/page.tsx
```

The full URL carries `subjectId`, `unitId`, and `lessonId` as path params. This keeps context unambiguous and mirrors the P7-01 subject→unit nested route. The lesson name and subject/language identity are shown as a read-only breadcrumb banner at the top of the page (not a picker — the user arrives here from the P7-02 lesson list).

**Interim fallback (if P7-02 lesson list is not yet available):** the route may be reached via `curriculum/questions/[lessonId]/page.tsx` with `lessonId` as the only path param. The banner then shows a loading state while fetching lesson metadata. The designer specifies the full nested route as the target; the interim is an implementation fallback only.

The question editor (create/edit) opens as a **modal dialog overlay** on top of the list page — not a separate route — matching the `SubjectForm`/`UnitForm` pattern.


## S8 — RTL / Arabic Content Rules for This Surface

The admin chrome is English-only at runtime (`ADMIN_LOCALE='en'`, `dir="ltr"`). However, **question content is authored by admins and may be Arabic**. These two concerns are kept separate:

1. **Admin chrome (all labels, buttons, table headers):** `dir="ltr"` from the `<html>` element. AR strings authored statically in `lib/strings.ts`; not runtime-reachable today. Do NOT flip the admin chrome's layout.

2. **Question content (questionText, option texts, Matching item texts):** These inputs use `dir="auto"`. The browser detects the base direction from the first strong character (if the admin types Arabic first, the input renders RTL; if they type Latin first, it renders LTR). This correctly handles bilingual content with zero config.

3. **CorrectAnswer in the table (question text preview):** the table cell uses `dir="auto"` on the question text cell. Truncation with `text-overflow: ellipsis` works correctly with `dir="auto"` in modern browsers.

4. **`dir="ltr"` exceptions (always Latin):** lessonId, sequenceOrder number, char counters, `"L1"`/`"R1"` stable ID labels in Matching, version numbers, timestamps, `options` JSON in the preview.

5. **Eastern-Arabic numerals in future AR runtime:** result count in the page header should use Eastern-Arabic numerals (٣ سؤال) when rendered for the AR locale. Since the runtime is currently EN-only, implement as a utility function that returns Latin numerals now and Eastern-Arabic when the locale flag is AR. Do not hardcode numerals.

6. **Progress bars / sequence order numbers:** always Latin numerals, `dir="ltr"`.

## S10 — Accessibility Checklist

- All interactive elements have `--lx-focus-ring` on `:focus-visible`.
- Table has semantic `<table>`, `<thead>`, `<tbody>`, `<th scope="col">`, `<th scope="row">` (for order cell), `<td>`.
- Table `<caption class="sr-only">` on the questions table.
- `aria-live="polite"` on the results area `<div>` wrapping the table (announces load completion, count changes).
- `aria-live="polite"` on the reorder announcement `<span class="sr-only">`.
- Dialog: `role="dialog"`, `aria-modal="true"`, `aria-labelledby={titleId}`. Focus trap inside. ESC closes.
- MCQ radio inputs: associated `<label htmlFor>` for each radio. Group wrapped in `<fieldset>` + `<legend>` EN "Options" / AR "الخيارات".
- TrueFalse: the two pill buttons are visually styled `<label>` elements wrapping hidden native `<input type="radio">`. Both inside `<fieldset>` + `<legend>` EN "Correct Answer" / AR "الإجابة الصحيحة".
- Matching: outer `<fieldset>` + `<legend>` "Matching configuration" / "إعداد المطابقة"; inner `<fieldset>` + `<legend>` "Correct pairings" / "التطابقات الصحيحة". Each pair `<select>` has `aria-label` naming the left item it pairs.
- `data-testid` on every interactive element, list row, and editor field (admin E2E harness relies on these).
- Touch targets: all interactive elements ≥ 32px height (admin is desktop-first; Wave 1 baseline is 32px minimum for icon buttons, 36–44px for labeled buttons).
- Char counters use `aria-live="polite"` on the counter span, or alternatively `aria-describedby` linking the input to the counter span, so screen readers report the count on blur.
- Validation errors: `role="alert"` on each error message so they are announced immediately on appearance.
- Non-interactive row cells with truncated content should use `title={fullText}` attribute for mouse-hover tooltip access (keyboard / SR users are not affected since they navigate to the action buttons which name the question).
- The `AdminErrorBanner` (existing component) already implements `role="alert"` for the error variant and `role="status"` for the success variant.

## Design Gaps / Open Questions

**Gap 1 — `lifecycleState` not in `AdminQuestionDto`**
The brief (§"Affected modules & data") states that `QuestionsController` does NOT return `lifecycleState` in `AdminQuestionDto` — lifecycle is managed by a separate `ContentLifecycleController`. The `CurriculumLifecycleControl` in the question editor (§S3.7) requires `lifecycleState` to know which buttons to render. The `LifecycleBadge` in the table lifecycle slot (§S5) also requires it.

Resolution options (designer does not choose — flag for the lead):
- (A) Extend `AdminQuestionDto` to include `lifecycleState` (BE follow-up, separate lead approval).
- (B) Fetch `lifecycleState` per-question via `GET /api/learning/ContentLifecycle/VersionHistory?entityType=4&entityId={id}` (the last entry gives current state) — but this is O(N) for the list.
- (C) Ship P7-04 without the lifecycle control in the editor and leave the lifecycle slot empty. P7-05 follows up to wire it once the DTO is extended.

**Recommendation:** option (C) for now — ship the reserved slot and the empty `<td>`. The lifecycle control in the editor is conditional on `lifecycleState != null`. Flag this gap with a `TODO: P7-04 lifecycle — waiting for lifecycleState in AdminQuestionDto` comment at the slot render site.

**Gap 2 — Type selector locked on edit**
The spec locks the question type selector in edit mode to avoid CorrectAnswer shape mismatch. This means there is no UI path to change a question's type. The admin must delete + recreate. This is intentional UX but should be documented in the admin help copy. The "type cannot be changed" notice (§F1) covers this.

**Gap 3 — Matching BE validator gap (from brief Open Q3)**
`QuizQuestionTypeValidation.ValidateMatching` only checks equal-length `left`/`right` arrays — it does not validate `{id,text}` shapes or the `CorrectAnswer` `{pairs}` structure. The FE is the authoritative validator and must emit the correct CO-BE-1 shape. Downstream: the `qc-test-designer` must include "Matching grades correctly end-to-end" as a must-prove test case. The designer flags this but does not build a BE fix.

**Gap 4 — `SkillId` on questions (from brief Open Q7)**
`AddQuestionPayload.skillId` is optional. The spec sends `null` for all admin-authored questions (no skill picker). If the lead wants admins to attach a skill, a `SkillPicker` component and a `useSkillList` hook would be needed — that depends on P7-03 (skills list) existing first. This is out of scope for P7-04 and must be flagged as a separate follow-up story.

**Gap 5 — No admin lesson list/picker (from brief Open Q2)**
The route uses `lessonId` from the path. The admin must navigate here from the P7-02 lesson list. If P7-02 is not built yet (2b-B not landed), the questions route is unreachable via normal navigation. The interim path is: navigate directly to `/curriculum/subjects/{subjectId}/units/{unitId}/lessons/{lessonId}/questions` with known IDs (e.g., from seed data). The breadcrumb will load lesson metadata from a `useAdminLesson(lessonId)` call in the page.

**Gap 6 — Runtime RTL for admin chrome**
The admin runtime locale is a build-time constant `ADMIN_LOCALE='en'`. All AR strings are authored statically (§S7) and verified by a static "ar strings present" check. Runtime RTL verification is blocked pending a runtime locale toggle story. The E2E tests run English-runtime only; document RTL cases as blocked, not failed.

**Gap 7 — Audit trail gaps for Add and Reorder**
Per the brief, `AddQuestionCommandHandler` and `ReorderQuestionsCommandHandler` raise `AdminActionPerformedDomainEvent` with `TargetEntityId: 0` (id not flushed pre-event / batch operation). The audit log rows for these won't carry the question id. This is a known BE limitation; no FE action needed. Document in HANDOFF.
