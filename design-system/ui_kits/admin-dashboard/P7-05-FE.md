## Admin Surface Design Principles (inherited, not modified)

These carry forward unchanged from `P7-admin-users-wave.md` §"Admin surface design principles":

1. No gamification chrome (no XP bars, confetti, mascots, reward gradients).
2. Gradient fills forbidden. No XP/Reward/Level-Up gradients on any element.
3. Motion is minimal: hover 120ms, dialog entrance 200ms fade+translate, skeleton shimmer. No spring overshoot.
4. One primary action per screen. All destructive/high-impact actions require explicit confirm dialogs.
5. Typography: Poppins (EN). Cairo (AR display). Tajawal (AR body). No `--lx-size-display` (48px).
6. Card density: `$4` (16px) padding allowed when space is tight.

## Component 1 — `LifecycleBadge`

**File:** `apps/admin-dashboard/components/LifecycleBadge.tsx`
**Story task:** P7-05-FE-1
**Depends on:** `LIFECYCLE_STATE` const (added to `@learnexia/shared/constants` by 2a-C batch); `AdminStrings.clLifecycle*` keys.

### Purpose and reuse

This badge appears on every curriculum entity row and detail surface across P7-01 (subjects, units), P7-02 (lessons), and P7-04 (questions). It is the primary visual signal for the `LifecycleState` axis (Draft=1 / Published=2 / Archived=3), entirely separate from the `IsActive` boolean axis owned by P7-01..04. These two axes must never be conflated or combined into a single badge.

### Visual design — mirror `StatusBadge`, distinct palette

The `LifecycleBadge` uses the exact same atom structure as `StatusBadge`: pill shape, inline dot + uppercase label. The dot provides a non-color signal (shape + position) so color is never the only indicator (a11y).

```
[LifecycleBadge — tag="span", display inline-flex, flexDirection row,
                  alignItems center, gap 5,
                  height 22, paddingHorizontal 10,
                  borderRadius 9999 ($pill = --lx-radius-pill)]

  [Dot — aria-hidden, width 6, height 6,
          borderRadius 9999, backgroundColor (state-color), flexShrink 0]

  [Label — fontFamily $body (Poppins / Tajawal AR), fontSize 12,
            fontWeight 600, letterSpacing 0.04em (--lx-tracking-wide),
            textTransform uppercase, color (state-color)]
```

### State palette

| LifecycleState (int) | Const key | Label EN | Label AR (i18n key) | Dot color | Background | Text color |
|---|---|---|---|---|---|---|
| 1 — Draft | `LIFECYCLE_STATE.Draft` | Draft | مسودة (`clLifecycleDraft`) | `#94A3B8` (`--lx-fg3`) | `rgba(148,163,184,0.12)` | `#94A3B8` |
| 2 — Published | `LIFECYCLE_STATE.Published` | Published | منشور (`clLifecyclePublished`) | `#22C55E` (`--lx-secondary`) | `rgba(34,197,94,0.15)` | `#22C55E` |
| 3 — Archived | `LIFECYCLE_STATE.Archived` | Archived | مؤرشَف (`clLifecycleArchived`) | `#F59E0B` (`--lx-accent`) | `rgba(245,158,11,0.12)` | `#F59E0B` |

**Rationale for palette choices:**
- Draft = neutral grey (`--lx-fg3`): content not yet ready, deliberately low-prominence.
- Published = green (`--lx-secondary`): live to students, success signal, mirrors `Active` in `StatusBadge`.
- Archived = amber (`--lx-accent`): not deleted but no longer live; amber (caution) rather than red (danger) because archiving is reversible.

These three states are visually distinct from the `StatusBadge` status palette (Active green / Suspended amber / Deleted red) while using the same token set. When both badges appear on the same row (entity IsActive toggle + LifecycleBadge), their semantic distinction is clear via label text, not just color.

### Props

```typescript
interface LifecycleBadgeProps {
  /** LifecycleState int from the API (1/2/3). Use LIFECYCLE_STATE.* — never raw ints. */
  state: LifecycleStateValue;
  /** Pass the AdminStrings instance for the active locale. */
  strings: AdminStrings;
}
```

### States

- **Default:** as above.
- **In a table row (hover):** badge does not change; row hover handles the row. Do not add hover styles to the badge itself.
- **Unknown/out-of-range value:** render a neutral grey pill with label "—" (defensive fallback; should never occur if the backend enum is correct).

### RTL

- Text direction follows parent `dir` attribute. In AR, label uses Tajawal 12px weight 600.
- Dot is logical-start (inline-start of the label). No mirroring needed.

### Integration contract for P7-01..04

When P7-01..04 entity rows are built, they reserve a `LifecycleBadge` slot as follows:

```
[Entity row]
  [Name / title]
  [IsActive toggle — P7-01..04 responsibility]
  [LifecycleBadge slot — receives lifecycleState from the entity DTO]
  [Actions menu]
```

The `LifecycleBadge` slot must receive `lifecycleState` as a prop from the parent row. P7-01..04 entity DTOs are expected to include the `lifecycleState` field (from the `Learning` module entity). If the entity read endpoints do not return `lifecycleState`, flag as a design gap and fall back to fetching it via `GET /VersionHistory` (last entry state) — but that is an O(N) problem; flag, do not silently build.

## Component 2 — `CurriculumLifecycleControl`

**File:** `apps/admin-dashboard/components/CurriculumLifecycleControl.tsx`
**Story tasks:** P7-05-FE-2, P7-05-FE-5 (re-scoped)
**Depends on:** all four confirm dialogs below, `useTransitionLifecycle` hook, `LifecycleBadge`.

### Purpose

This is the single shared control that P7-01..04 detail surfaces compose. Given an entity's `{entityType, entityId, currentState, language}`, it renders the legal set of action buttons for the current lifecycle state and opens the appropriate confirm dialog on press. It is never a dropdown — it is a small group of buttons (2 max at any state), matching the `LifecycleActionsMenu` shape from Wave 1.

The re-scoped FE-5 ("live vs pending draft toggle") is implemented here: the control renders the entity's current `LifecycleBadge` + the state-conditional action buttons, and below them a "View preview" link (→ `/curriculum/preview/[type]/[id]`). There is no dual live/draft toggle because the backend has no pending-draft-of-a-published-entity model.

### Props

```typescript
interface CurriculumLifecycleControlProps {
  entityType: VersionedEntityTypeValue;   // VERSIONED_ENTITY_TYPE.Subject/Unit/Lesson/QuizQuestion
  entityId: number;
  currentState: LifecycleStateValue;      // LIFECYCLE_STATE.Draft/Published/Archived
  language: ContentLanguageValue;         // CONTENT_LANGUAGE.Ar/En — for the preview link label
  strings: AdminStrings;
  /** Called after any successful transition so the parent can refresh its own data. */
  onSuccess?: () => void;
}
```

### Legal transition table — drives which buttons render

| currentState | Button rendered | targetState sent | Dialog |
|---|---|---|---|
| Draft (1) | Publish | Published (2) | `PublishCurriculumDialog` |
| Draft (1) | (no Archive — must publish first) | — | — |
| Published (2) | Unpublish | Draft (1) | `UnpublishCurriculumDialog` |
| Published (2) | Archive | Archived (3) | `ArchiveCurriculumDialog` |
| Archived (3) | Restore | Draft (1) | `RestoreCurriculumDialog` |
| Archived (3) | (no direct Publish — must restore first) | — | — |

Draft state: one button (Publish). Published state: two buttons (Unpublish + Archive). Archived state: one button (Restore). Max two buttons visible at any time.

**Loading state (pending mutation):** all buttons replace label with a 16px spinner (same `SpinnerIcon` from `SuspendUserDialog`) and become non-interactive (`pointer-events: none`, `opacity: 0.6`). Do not hide the buttons — keep the layout stable.

**Success handling:** on mutation success, the control receives new `currentState` via the parent's refetch (invalidation-only, no optimistic update per wave decision D8). The `onSuccess` callback fires so the parent can refetch its entity. The action button set re-renders for the new state automatically.

### Error handling

A 400 from the API (illegal transition — should not happen if the UI is correct, but defensive):
- Show `AdminErrorBanner variant="error"` below the actions row.
- Keep the dialog open (if the error fires inside a dialog, keep dialog open + show error inside it).
- 404: show `AdminErrorBanner` "Content not found" and hide the action buttons.

### RTL

- Action row uses `flexWrap: wrap`. No explicit `flex-direction: row-reverse` — the row reads inline-start first, which is right in RTL. The "View Preview" link uses `marginInlineStart: auto` to push it to the inline-end edge in both directions.

### A11y

- Each button has an `aria-label` that names the specific entity (e.g. "Publish Math — Grade 3").
- The state row uses a visually-hidden `<span>` if needed: "Current lifecycle state: Published".
- After a dialog opens, focus trap is handled by `AdminConfirmDialog`. After dialog closes on success, focus returns to the button that opened it (the trigger element, via `AdminConfirmDialog`'s existing `triggerRef` pattern).
- `aria-live="polite"` region wraps the state row so screen readers announce state changes after mutation.

## RTL / i18n Spec

**Runtime:** English only (`ADMIN_LOCALE='en'`). Arabic strings are authored and statically verified.

**Preview direction exception:** `CurriculumPreview`'s snapshot card uses `dir` driven by `PreviewDto.language` (Ar=0 → `dir="rtl"`, En=1 → `dir="ltr"`), independent of the admin locale. This is a per-card direction, not a page-level direction. Field labels inside the snapshot card must switch language accordingly.

**Technical strings that always stay Latin + `dir="ltr"`:**
- Version numbers: "v{N}"
- Published IDs: "{N}"
- Dates (EN-runtime): formatted via `Intl.DateTimeFormat`
- Sequence order numbers: "{N}"
- Brand name "Learnexia"
- Emails (not present in lifecycle surfaces)
- XP/point counters (not on admin surface)

**RTL layout rules (for when AR runtime is enabled):**
- Dialog action row: `flex-direction: row-reverse` under `dir="rtl"` (Cancel on left → right, Confirm on right → left per reading order). Already handled by `.lx-dialog-actions` in globals.css per Wave 1.
- ReasonField: label + counter row uses `justifyContent: space-between` — no change needed under RTL.

- Coverage table: columns remain in LTR order (AR-column first in the table is a design choice matching natural bilingual reading; the first data column is still the Subject, not flipped).
- Progress bars (not present in lifecycle surfaces — no flip needed).
- `borderInlineStart` / `borderInlineEnd` logical properties used throughout to auto-flip side borders.

## Accessibility Spec

Beyond individual component notes above:

- **Dialog focus trap:** reused from `AdminConfirmDialog` (already implemented). All four new dialog variants extend the existing `DialogVariant` union — no changes to the focus-trap logic.
- **State announcements:** `aria-live="polite"` on the state row in `CurriculumLifecycleControl` ensures screen readers announce lifecycle state changes after mutation.
- **Color independence:** `LifecycleBadge` has a dot (shape) + uppercase text (content) + color — three independent signals. Badges are never distinguished by color alone.
- **Disabled buttons:** `aria-disabled="true"` (not the `disabled` attribute) on the RollbackVersionDialog confirm button so it remains focusable and screen readers can announce the required reason. Visual `opacity: 0.4`.
- **Version history rollback buttons:** each "Roll back" button has an `aria-label` containing the version number so all three buttons in the list are distinguishable by screen readers.
- **Coverage warning chips:** `aria-label` on the chip element spells out the full gap (not just "one-sided").
- **Preview draft banner:** `role="alert"` (immediately announced, not polite).
- **Table captions:** SR-only `<caption>` on both the version history list (if rendered as table) and the coverage grid.
- **Touch targets:** all interactive elements ≥ 32px height (rollback button) to ≥ 44px height (confirm buttons, grade selector). This is a desktop-first admin surface; 32px minimum is acceptable for secondary actions in dense lists.

## Design Gaps and Open Questions

**DG-1 (AdminSideNav icons):** The existing nav uses emoji placeholders (`📚`, `📄`, `👤`). Lucide icons are the spec'd substitution (2px stroke, 18px). The promoted "Curriculum" nav item should use Lucide `book-open` (18px, `$fg3` inactive / `$primary` active), matching the intent of Wave 1's note "Design Gap 1 — no admin icon set". Flag as cosmetic gap; the frontend can use the emoji placeholder as Wave 1 did and upgrade in a follow-up.

**DG-2 (entity DTO — `lifecycleState` field availability):** The `CurriculumLifecycleControl` and `LifecycleBadge` require `lifecycleState` from the entity DTO (Subject, Unit, Lesson, QuizQuestion). Confirm that the P7-01..04 entity read endpoints (`GET /api/learning/Subjects/{id}`, etc.) return a `lifecycleState` field. If they do not, the lifecycle badge on entity rows is not renderable without an extra call per row. This is a **potential design gap that blocks P7-01..04 integration** — the brief only documents the `ContentLifecycleController` endpoints, not the shape of the entity read endpoints. Flag for the reviewer and the lead.

**DG-3 (PublishedByUserId name resolution — OQ3):** Version history shows `publishedByUserId` as a raw int with a "Published by ID {N}" label. The brief confirms this as the default (OQ3 default). A tooltip on the ID text ("Admin user ID") is the v1 treatment. Name resolution (via `GET /api/Admin/Users/{id}`) is deferred unless the lead approves; it would require a per-version lookup which could be expensive in a long history list.

**DG-4 (Rollback reason not persisted — OQ2):** The `RollbackVersionDialog` requires a reason via `ReasonField` as a FE-only UX guardrail. The reason is not sent to the backend (the `POST /Rollback` body has no reason field) and is not persisted server-side. The dialog body includes a notice explicitly stating this. If product later requires audit persistence, a backend follow-up (add `Reason` to `RollbackToVersionCommand`) is needed — do not build it under this story.

**DG-5 (QuizQuestion Options shape in preview):** The `CurriculumPreview` renders `Options` (raw JSON string) from `QuizQuestion` snapshot. The exact per-type shape is not fully documented in the brief. The spec says "best-effort": parse the JSON and render as a list/map. If the parse fails, show the raw string in a monospace block. A type-specific renderer (MCQ list / Matching pairs) requires the `QUESTION_TYPE` const from P7-04's 2b batch; if it is not available when 2a-D lands, render the raw parsed JSON as a pretty-printed object (using `JSON.stringify(parsed, null, 2)` in a `<pre>` block, `fontFamily $mono`, `fontSize 13`). Flag this as a follow-up when P7-04 ships its const.

**DG-6 (Visual URL safety in Lesson preview):** The Lesson snapshot `Visual` field is rendered as an image if it looks like an image URL. The frontend must validate the URL: only render `<img>` for URLs starting with `https://` and ending in `.jpg/.jpeg/.png/.webp/.gif/.svg`. Block `javascript:` and `data:` schemes. This is a security-sensitive rendering decision — flag for the security-auditor gate.

**OQ-1 (Re-scoped FE-5 confirmed):** The "live vs pending-draft toggle" is re-scoped to: `LifecycleBadge` showing current `lifecycleState` + "View Preview" link + `VersionHistory` panel for the last published version. No dual live/draft toggle is designed because the backend has no such model. This is the confirmed default (D5 from the plan).

**OQ-4 (Standalone host confirmed):** The `/curriculum` landing page (PublicationCoverage) serves as the standalone host. The `CurriculumLifecycleControl` and `VersionHistory` are composable components embedded into the landing as a demo panel (wrapping a hardcoded demo entityType/entityId controlled by a small entity-picker form). This makes them E2E-testable before P7-01..04 wire them into real entity detail pages.
