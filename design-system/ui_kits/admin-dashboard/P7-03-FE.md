> **A11y is the defining challenge of this story.** The prerequisite dependency graph MUST be edited via an accessible list/adjacency editor — NOT a drag canvas. > **Node-id vs skill-id.** All edge endpoints consume `KnowledgeNode` IDs (`sourceNodeId`, `targetNodeId`). The graph read returns `{ id (nodeId), skillId? }`. The editor must work in node-id space and resolve skill metadata for display only.

## Admin Surface Design Principles (inherited from Wave 1 — unchanged)

1. No gamification chrome — no XP bars, confetti, reward gradients, streak flames, mascot owl.
2. Dark canvas by default (`#0F172A`). Cards step lighter (`#1E293B` → `#334155`). Never darken on interaction.
3. Motion is minimal: hover transitions `120ms --lx-ease-out`, dialog entrances `200ms --lx-ease-out` fade + `translateY(8px→0)`, skeleton shimmer. No spring overshoot. No glow, no spring, no confetti.
4. One primary action per screen. Destructive and high-impact actions require explicit confirm dialogs.
5. Typography: Poppins (EN). Cairo (AR display/headings). Tajawal (AR body). Max heading H2 24px.
6. Density: `--lx-space-4` (16px) card padding where tight. Tables compact.
7. Semantic `<table>` for all tabular data — no CSS-grid substitutes.
8. Focus ring on all interactive elements: `--lx-focus-ring` = `0 0 0 2px #4F46E5, 0 0 0 6px rgba(99,102,241,0.45)`.

## FE-Local DTO Types (hand-written, next to skill/graph hooks)

```typescript
// packages/api-client/src/hooks/skill.types.ts

import type { NodeTypeValue, RelationshipTypeValue } from '@learnexia/shared/constants';

/** Wire shape from GET /api/learning/Skills/List (PaginatedResult<SingleSkillResponse>). */
export interface SingleSkillResponse {
  id: number;
  name: string;
  masteryThreshold: number;       // int 0–100
  estimatedTimeMinutes: number;   // int ≥ 0
  conceptId: number;              // owning concept node id
  isActive?: boolean;             // see OQ-Lifecycle below
}

/** POST body: AddSkillCommand */
export interface AddSkillDto {
  name: string;
  masteryThreshold: number;   // 0–100
  estimatedTimeMinutes: number;
  conceptId: number;          // must be > 0
}

/** PUT body: EditSkillCommand */
export interface EditSkillDto {
  id: number;
  name: string;
  masteryThreshold: number;
  estimatedTimeMinutes: number;
  conceptId: number;
}

/** Node in the full graph (from SkillGraphDto). */
export interface KnowledgeNodeDto {
  id: number;             // KnowledgeNode.Id — use for edge endpoints
  name: string;
  nodeType: NodeTypeValue;          // 0 Skill | 1 Concept | 2 Review
  subjectId: number;
  gradeId: number;
  difficulty: number;
  skillId?: number | null;          // if nodeType===Skill; null otherwise
  isSkillActive?: boolean | null;   // admin-only graph exposes this; may be null for non-skill nodes
}

/** Edge in the full graph. */
export interface KnowledgeEdgeDto {
  id: number;
  sourceNodeId: number;
  targetNodeId: number;
  relationshipType: RelationshipTypeValue;  // 0 Prerequisite | 1 Related
  strength: number;                          // decimal 0.0–1.0
}

/** Full graph DTO from GET /api/Learning/KnowledgeGraph/Graph?subjectId=. */
export interface SkillGraphDto {
  subjectId: number;
  nodes: KnowledgeNodeDto[];
  edges: KnowledgeEdgeDto[];
}

/** Item from GET /api/Learning/KnowledgeGraph/Prerequisites/{nodeId}
    and GET /api/Learning/KnowledgeGraph/UnlockedBy/{nodeId} */
export interface StudentKnowledgeNodeDto {
  id: number;       // nodeId
  name: string;
  nodeType: NodeTypeValue;
  skillId?: number | null;
}

/** POST body: AddKnowledgeEdgeCommand */
export interface AddKnowledgeEdgeDto {
  sourceNodeId: number;
  targetNodeId: number;
  relationshipType: RelationshipTypeValue;  // always RELATIONSHIP_TYPE.Prerequisite (0) in v1
  strength?: number;                         // always 1.0 in v1 (default, per OQ-6)
}

/** Concept picker item from GET /api/learning/Concepts/List */
export interface ConceptListItemDto {
  id: number;
  name: string;
  subjectId?: number | null;
}
```

## S4 — Graph Editor (`SkillGraph` component)

### 4.1 Overview and philosophy

The graph editor is the core of P7-03. It is an **accessible list/adjacency editor**, NOT a canvas. There is no visual graph render in this story. Visual graph rendering is explicitly deferred as a future enhancement (per the brief, plan D1 decision, and CLAUDE.md rule 8).

**Why list/adjacency:** (a) fully keyboard-operable with native HTML semantics; (b) no new npm dependency; (c) no RTL-flip liability on a canvas; (d) `aria-live` announcements work naturally on list mutations.

The future visual graph (if and when approved) would be a **read-only supplementary render** alongside the list editor, `aria-hidden="true"` on the canvas, never the sole editing path.

function mapEdgeError(err: unknown, strings: AdminStrings): string {
  if (isApiError(err)) {
    if (err.status === 400) {
      const msg = err.message;
      // Match backend EN strings (brief §Exact endpoints; backend may return AR if Accept-Language: ar)
      if (msg.includes('cycle') || msg.includes('KnowledgeEdgeWouldCreateCycle'))
        return strings.skillGraphErrCycle;
      if (msg.includes('cross-language') || msg.includes('KnowledgeEdgeCrossLanguageForbidden'))
        return strings.skillGraphErrCrossLanguage;
      if (msg.includes('already exists') || msg.includes('KnowledgeEdgeDuplicate'))
        return strings.skillGraphErrDuplicate;
      if (msg.includes('node was not found') || msg.includes('KnowledgeNodeNotFound'))
        return strings.skillGraphErrNodeNotFound;
      if (msg.includes('KnowledgeNodeSubjectNotResolvable'))
        return strings.skillGraphErrSubjectUnresolvable;
      if (msg.includes('strength') || msg.includes('KnowledgeEdgeStrengthOutOfRange'))
        return strings.skillGraphErrStrengthOutOfRange;
      // Generic 400
      return err.message || strings.skillGraphErrGeneric;
    }
    if (err.status === 404) return strings.skillGraphErrNodeNotFound;
  }
  return strings.skillGraphErrNetwork;
}

## S7 — Accessibility Spec (the make-or-break section)

Accessibility is the primary design constraint for this surface. Every interactive element must be fully operable without a mouse.

### 7.1 `aria-live` for graph mutations

A single visually-hidden `<span aria-live="polite" className="sr-only">` is placed outside the graph card (so DOM insertions/removals inside the card don't interrupt it). It is updated after every successful edge mutation:

```html
<!-- Outside the graph card, permanent in the DOM -->
<span
  id="graph-announcement"
  aria-live="polite"
  aria-atomic="true"
  className="sr-only"
>
  {/* Updated on each edge add/remove success:
      EN: "{name} added as a prerequisite."
      EN: "{name} removed from prerequisites."
      AR: "تمت إضافة {name} متطلبًا سابقًا."
      AR: "تمت إزالة {name} من المتطلبات السابقة."
  */}
</span>
```

The **inline error region** (§4.6) uses `aria-live="assertive" aria-atomic="true"` for rejection announcements (cycle, cross-language, duplicate). Assertive because the admin must immediately know the action failed — the graph is unchanged, not eventually consistent.

### 7.2 Node listbox keyboard navigation

The node list (§4.7) uses the `listbox` / `option` pattern:
- Container: `role="listbox"`, `aria-label`, `aria-multiselectable="false"`, `tabIndex={0}`
- Items: `role="option"`, `aria-selected={isSelected}`, `tabIndex` managed by roving tabindex
- Keyboard: `ArrowUp` / `ArrowDown` cycle through options; `Enter` or `Space` selects; `Home` / `End` jump to first/last
- When a node is selected, announce: SR reads `aria-selected="true"` on the newly selected option
- When no node is selected: `aria-label` on the container reminds: "Use arrow keys to select a node"

### 7.3 Prerequisite picker keyboard

The `<select>` element (§4.11.1) is a native HTML select — fully keyboard-operable by default. Tab order:

1. Subject picker (`skill-subject-picker`)
2. Concept filter
3. Search input
4. Skills table rows (roving tabindex)
5. Node listbox (`graph-node-listbox`)
6. Selected node deselect button (when node is selected)
7. Prerequisite picker (`prerequisite-picker`)
8. Add button (`add-prerequisite-btn`)
9. Each Remove button per prerequisite (`remove-prerequisite-{edgeId}`)

### 7.4 Combobox enhancement (future — do not build now)

The native `<select>` covers the a11y requirement for v1. A combobox (`role="combobox"` with `role="listbox"` popup and text search) can replace it in a follow-up if the node list grows large. Document this as a planned enhancement, not a day-one requirement. Flag in §Design Gaps.

### 7.5 Focus management on mutations

- **After successful Add:** focus returns to the picker element (ready to add another prerequisite without re-navigating)
- **After successful Remove:** focus moves to the first remaining prerequisite remove button, or to the picker if the list is now empty
- **On error:** `role="alert"` on the error region auto-announces; the admin's current focus position does not change (they can re-try without re-navigating)
- **On dialog open (SkillForm, SkillDeleteDialog):** focus moves to the first interactive element in the dialog; on close, focus returns to the trigger

### 7.6 Screen-reader accessible edge list

The prerequisites `<ul>/<li>` pattern (§4.9) gives screen readers:
- "Prerequisites, list, N items" (on focus entering the list)
- Per item: "{prerequisite name} — [node type], Remove as prerequisite button"
- On removal: `aria-live="polite"` announces "{name} removed from prerequisites"

The Unlocks section is identical structure but with no remove buttons.

### 7.7 Visible focus rings

ALL interactive elements: `outline: none; box-shadow: var(--lx-focus-ring)` on `:focus-visible`.
`var(--lx-focus-ring)` = `0 0 0 2px #4F46E5, 0 0 0 6px rgba(99,102,241,0.45)`.
No element may have `outline: none` without a visible alternative.

### 7.8 Color — not the only signal

- Node type (Skill/Concept/Review): pip color + text weight difference + explicit label in picker options
- Selected node: indigo background + `aria-selected="true"` (not color alone)
- Edge rejection: `role="alert"` text + icon + color (triple signal)
- Inactive skill: opacity + icon + `ActiveBadge` text

### 7.9 Disable during mutation

While `isEdgeMutating === true`:
- Picker `<select>`: `disabled` attribute + `aria-disabled="true"`
- Add button: `disabled` + `aria-busy="true"` + spinner
- All Remove buttons in the list: `disabled` (prevent concurrent removes)

This satisfies the brief's note about the concurrent-edge race condition — the UI does not encourage rapid concurrent submits.

## S8 — RTL / Arabic Spec

### 8.1 Layout direction

The admin surface ships English-runtime only (`ADMIN_LOCALE = 'en'`). The AR strings are authored statically and verified in a static strings-presence check (not runtime RTL rendering). The RTL layout spec below defines what a future AR runtime would render.

The full page uses `dir="ltr"` (English). Technical strings in the AR locale that must remain LTR:
- Mastery threshold percentages: `{N}%` — always `dir="ltr"` inner `<span>`
- Estimated time in minutes: `{N} min` / `{N} دق` — N always Latin, `dir="ltr"`
- Node IDs (internal, not shown to user)
- Edge strength value (not shown in v1)
- The brand name "Learnexia", email addresses, URLs (not on this surface)

Eastern-Arabic numerals (٠١٢٣٤٥٦٧٨٩) are used in AR strings for:
- Inline reading text: threshold hint "٠–١٠٠", time hint "٠ أو أكثر"
- Error messages: "بين ٠ و١٠٠"

### 8.2 Directional arrow in edge descriptions

In EN: prerequisites flow `A → B` (A enables B). The arrow `→` points "next".
In AR RTL: the semantic is identical but the visual arrow flips: `B ← A`. The glyph to use:
- EN: `→` (U+2192) or Lucide `arrow-right` in the context chip
- AR: `←` (U+2190) or Lucide `arrow-left`

In the prerequisites section heading, the icon `arrow-right-to-line` (Lucide) means "arrow arriving at this node from the left" (EN). In AR RTL this icon should be `arrow-left-to-line` (mirrored). Use CSS `transform: scaleX(-1)` on directional arrow icons when `dir="rtl"`, OR use `dir`-aware icon selection in the component.

The Unlocks section: `arrow-right-from-line` (EN), `arrow-left-from-line` (AR/RTL). Same mirroring rule.

Do NOT mirror avatar gradients, logo marks, or non-directional icons.

### 8.3 The skills table in AR

In AR RTL:
- `textAlign: start` resolves to right — correct for the current locale
- `borderInlineStart` (selected row indicator) resolves to the right border — correct
- `paddingInlineStart` on input icons resolves to right side — icon appears at right edge of input
- Lucide `chevron-right` in the node list items becomes `chevron-left` in RTL (direction-aware swap, same as P7-01/P7-02 breadcrumb pattern)

### 8.4 AR copy discipline

- Button labels: Title Case in EN ("New Skill", "Save Changes"); full word form in AR ("مهارة جديدة", "حفظ التغييرات")
- Body/hint text: sentence case in both locales
- Exclamation marks: not used on this admin surface (no reward moments)
- Graph error messages: clear, direct, no apologies — "This would create a cycle… Choose a different node."

### 10.3 Invalidation strategy

No optimistic updates (plan D8 decision). On every mutation: wait for the mutation to resolve, then invalidate the affected keys. TanStack Query refetches automatically.

The mutation flow for Add Edge:
1. POST succeeds → `queryClient.invalidateQueries({ queryKey: adminCurriculum.graph(subjectId) })`
2. Graph refetches → `SkillGraphDto` now contains the new edge with its server-assigned `id`
3. The prerequisites list re-derives from the new edge list
4. `aria-live` announcement fires

The mutation flow for Remove Edge:
1. DELETE succeeds → same invalidation
2. Graph refetches → edge is gone
3. Prerequisites list re-renders without it

## Design Gaps / Open Questions

### Gap 1 — OQ-3: Concept picker scoping (BLOCKING for SkillForm)
`GET /api/learning/Concepts/List` (`ListConceptsQuery`) may not support a `subjectId` filter. If unfiltered, the picker shows concepts from all subjects, making it hard for the admin to pick the right concept for a skill in the currently selected subject tree. The frontend should consume the list and **filter client-side by `concept.subjectId === currentSubjectId`** if that field is present on `ConceptListItemDto`. If `ConceptListItemDto.subjectId` is not present on the wire, the picker shows all concepts with no scoping — the admin must pick correctly without UI guidance. **Flag to the lead:** confirm whether `ListConceptsQuery` returns a `subjectId` field on each concept, or whether a `subjectId` filter param exists. If neither, add a note in the picker: EN "Select a concept from this subject's tree" / AR "اختر مفهومًا من شجرة هذه المادة."

### Gap 2 — OQ-Lifecycle: Do skills have `IsActive`?
The brief lists `(Optional) activate/deactivate` at `PUT /api/learning/Skills/{id}/Active` and the DTO includes `isActive?: boolean`. The `VERSIONED_ENTITY_TYPE` const does NOT include a Skill entry. The spec conditionally renders `ActiveBadge` only when `isActive` is present. The **frontend agent must verify** whether `SingleSkillResponse` carries `isActive` on the wire — if yes, add the Active column to the skills table and the Is-Active toggle to `SkillForm` (mirror the SubjectForm F6 toggle exactly). If absent, omit both. Do not add one speculatively. This is flagged as a design gap, not a silent choice.

### Gap 3 — OQ-6: Related edges and Strength UI (DEFERRED by plan decision)
The spec hard-codes `relationshipType = RELATIONSHIP_TYPE.Prerequisite` (0) and `strength = 1.0` in all edge mutations. The plan decision D-OQ6 is to defer Related edges and Strength authoring. If the lead opens this in a future story, the picker and add-edge form would need a `<select>` for relationship type (Prerequisite / Related) and a numeric input for strength (0.0–1.0). The acyclic guard only applies to Prerequisite edges. This spec does not design for Related edges or Strength UI.

### Gap 4 — OQ-5: Security auditor run (lead decision)
The plan defaults to SKIP for P7-03 (curriculum metadata only, no PII, auto P7-12 audit). Confirm with the lead. The reviewer still checks AdminOnly + guard wiring as a baseline.

### Gap 5 — Visual graph render (future, NOT this story)
The current spec defines the list/adjacency editor only. A visual graph render (e.g. SVG DAG layout, read-only) is explicitly deferred. When it ships, it MUST be `aria-hidden="true"` on the canvas element (decorative supplement) or paired with an equivalent accessible table/list. It MUST NOT become the only editing path. The implementation must get explicit lead sign-off on the library + the dependency (CLAUDE.md rule 8).

### Gap 6 — Combobox upgrade for node picker
The native `<select>` is the v1 implementation for the prerequisite picker. If the graph has many nodes (>20–30), a searchable combobox would improve usability. This is a future enhancement — design the combobox when the node count warrants it, using `role="combobox"` + `role="listbox"` + `aria-autocomplete="list"` + `aria-owns`. The current `<select>` is fully a11y-compliant for v1.

### Gap 7 — Lucide icon availability
Lucide `brain-circuit` may not be in the version currently installed. Use `layers` (available, used in P7-01/P7-02) as the fallback for the Skill form's create-mode icon. The frontend agent should check the installed Lucide version and pick the closest available icon. `git-fork` for the no-subject-selected state may similarly need a fallback (`share-2` or `network`).

### Gap 8 — useNodePrerequisites vs. client-side derivation
The spec recommends deriving prerequisites from `graph.edges` (client-side, no extra network call). The `useNodePrerequisites(nodeId)` endpoint is available if richer node metadata is needed. For v1, use client-side derivation. The frontend agent may use the endpoint if the `SkillGraphDto.edges` do not carry enough metadata (e.g. node names are not on `KnowledgeEdgeDto`). In that case, resolve node names by looking up `graph.nodes` by id — the full node list is already in memory.
