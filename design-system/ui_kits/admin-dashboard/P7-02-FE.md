## Admin Surface Design Principles (inherited from Wave 1 — unchanged)

1. No gamification chrome — no XP bars, confetti, reward gradients, streak flames, mascot owl.
2. Dark canvas by default (`#0F172A`). Cards step lighter (`#1E293B` → `#334155`). Never darken on interaction.
3. Motion is minimal: hover transitions `120ms --lx-ease-out`, dialog entrances `200ms --lx-ease-out` fade + `translateY(8px→0)`, skeleton shimmer. No spring overshoot.
4. One primary action per screen. Destructive and high-impact actions require explicit confirm dialogs.
5. Typography: Poppins (EN). Cairo (AR display/headings). Tajawal (AR body). Max heading H2 24px on this surface.
6. Density: `--lx-space-4` (16px) card padding where tight. Tables are compact.
7. Semantic `<table>` for all tabular data — no CSS-grid substitutes.
8. Focus ring on all interactive elements: `--lx-focus-ring` = `0 0 0 2px #4F46E5, 0 0 0 6px rgba(99,102,241,0.45)`.

## S1 — Route shape (settled here per plan D-route-P02)

The route follows the P7-01 nested convention:

```
/curriculum/subjects/[id]/units/[unitId]/lessons/page.tsx
  ← "Lessons under unit" list page (FE-1)

/curriculum/subjects/[id]/units/[unitId]/lessons/[lessonId]/page.tsx
  ← "Lesson detail + content editor" page (FE-2/FE-5/FE-6 + lifecycle)
```

The `[id]` is the `subjectId`; `[unitId]` is the unit's id. Both come from the P7-01 tree navigation (the unit row in the subject-detail page links here). The subject's `language` (ContentLanguage int) is carried down as a route search param `?lang=0|1` OR via the URL context — see §S2 breadcrumb. The FE resolves `InheritedLanguageBadge` from this value (never a new endpoint — brief Q1 decision: FE-side resolution).

`export const dynamic = 'force-dynamic'` on both pages.

## S9 — `BlockPreview` (FE-5)

**File:** `apps/admin-dashboard/components/BlockPreview.tsx`

This is the **primary XSS risk surface**. Every Markdown-to-HTML render in this component MUST go through a sanitization step.

### 9.1 Purpose

Renders an inline read-only preview of a block's content as the admin would roughly expect students to see it (direction, font, media). It is not a student-experience simulation — it is an author preview. Labeled "Preview" only if needed (no explicit label is fine in the card context).

### 9.2 Security requirement (MANDATORY — blocks security gate)

**Text and Callout blocks contain author-supplied Markdown stored verbatim.**

The preview MUST use a **sanitized Markdown-to-HTML pipeline**:

1. Parse Markdown → HTML using a Markdown library (e.g. `marked`, `micromark`, `markdown-it`). Flag as a lead decision (CLAUDE.md rule 8) if a new npm dep is needed — see §Design Gaps gap 2. The default approach is: **use a sanitized subset renderer that produces only safe HTML tags**, not full HTML passthrough.
2. Sanitize the resulting HTML before injection. Recommended approach: use `DOMPurify` (already required; this is also a new npm dep if not present — flag as gap 2). Configure to:
   - Allow: `p, br, strong, em, ul, ol, li, h1, h2, h3, h4, blockquote, code, pre, hr`
   - Disallow: ALL event handlers (`on*`), `<script>`, `<style>`, `<iframe>`, `<object>`, `<embed>`
   - URL allowlist (for any `href` / `src` in Markdown): only `https://` scheme; strip `javascript:`, `data:`, `vbscript:`
3. Inject via `dangerouslySetInnerHTML={{ __html: sanitizedHtml }}` ONLY on the specifically-contained preview div. NEVER use `dangerouslySetInnerHTML` elsewhere on this page.

The security-auditor must verify:
- No raw Markdown/HTML injected without sanitization
- `javascript:` and `data:` URLs are stripped from any attribute
- Event handlers (`onclick`, `onerror`, etc.) are stripped
- Image/video `src` goes through the URL-scheme guard

```
function isSecureImageUrl(url: string): boolean {
  try {
    const u = new URL(url);
    if (u.protocol !== 'https:') return false;
    const host = u.hostname;
    if (/^(localhost|127\.|10\.|172\.(1[6-9]|2\d|3[01])\.|192\.168\.|0\.0\.0\.0)/.test(host)) return false;
    const ext = u.pathname.split('.').pop()?.toLowerCase();
    const ALLOWED = ['jpg', 'jpeg', 'png', 'webp', 'gif', 'svg', 'avif'];
    return !!ext && ALLOWED.includes(ext);
  } catch { return false; }
}
```

## S12 — Accessibility, RTL, Focus

### Focus flow in the content editor

1. "Add Block" button → BlockTypePickerSheet (first option focused).
2. Pick type → BlockForm (first field focused, same entrance as LessonForm).
3. BlockForm Save → focus returns to the "Add Block" button.
4. Block card edit button → BlockForm (edit mode).
5. Block card delete button → DeleteBlockDialog (first focusable in dialog).
6. Dialog Cancel / confirm → focus returns to the block card delete button (same `triggerRef` pattern as `AdminConfirmDialog.tsx`).
7. Move-up / move-down → `aria-live="polite"` announces position change; focus stays on the pressed button.

### RTL (`dir="rtl"`)

- Block card reorder buttons: inline-start buttons still read "move up / move down" correctly — the concept of up/down order is vertical, not horizontal, so no mirroring.
- BlockTypeBadge: icon is inline-start, text is inline-end (logical; flips correctly under RTL).
- BlockTypePickerSheet: insetInlineEnd: 0 (correct in both LTR and RTL).
- BlockPreview container: `dir` follows inherited language, not admin locale. A lesson with AR content renders AR-direction preview even in the EN admin session.
- Form inputs with `dir="auto"`: Arabic text right-aligns naturally without locale change.
- URL inputs: `dir="ltr"` always (technical strings).
- Breadcrumb: chevron icons flip (chevron-left in RTL); use logical flex direction.

### Screen reader semantics

- `<table>` with `<caption>` for lessons list. `<thead>`, `<th scope="col">` for all columns.
- `<ol>` for the ordered block list with `aria-label`.
- `role="status"` on loading states; `role="alert"` on error banners and inline form errors.
- `aria-live="polite"` on results area and block list; `aria-busy="true"` on loading states.
- All icon-only buttons have `aria-label`. No icon-only affordance without a label.
- Block card uses `<li>` semantics within `<ol>`.
- BlockTypePickerSheet: `role="menu"` on container, `role="menuitem"` on each option.
- Reorder `aria-live` announcement on every move-up/down.

### Keyboard flow (block editor)

- Tab order: "New Lesson" → "Add Block" → [block cards in order, each: move-up / move-down / edit / delete].
- Within a block card: move-up → move-down → edit → delete (all reachable without mouse).
- Enter/Space activates all buttons per HTML default.
- ESC closes any open BlockForm or picker.
- No drag-only operation (all reorder via keyboard buttons — plan D2).

### Touch targets

All interactive elements: minimum 40px height, 40px width (icon buttons: 28px for block-card inline buttons — acceptable for desktop-first admin; 32px for row actions — desktop-only surface, no mobile breakpoint required per Wave 1 patterns).

## Design Gaps

**Gap 1 — No unit-detail route (`[unitId]` page).**
P7-01 has no dedicated `/curriculum/subjects/[id]/units/[unitId]` route (units are edited inline on the subject-detail page). The breadcrumb segment for the unit is therefore plain text (non-linked) in v1. When P7-01 ships a unit-detail route, upgrade the breadcrumb segment to a link without touching P7-02 components.

**Gap 2 — Markdown sanitization library.**
`BlockPreview` requires:
1. A Markdown parser (e.g. `marked`, `markdown-it`, `micromark`)
2. A sanitizer (e.g. `DOMPurify`)

Both are likely new npm dependencies (`DOMPurify` may not be in `package.json` yet — verify before 2b-C). **CLAUDE.md rule 8 applies: flag to lead; do not add deps without explicit approval.** Recommended approach: `marked` (no new dep if already present) + `DOMPurify` (new dep — flag). Alternative: `sanitize-html` (single package, new dep — flag). The lead must approve the package choice before 2b-C is dispatched. If no dep is approved, the fallback is a whitelist-only tag-stripping approach using `DOMParser` on the client (more limited but zero-dep). The spec requires sanitization — the implementation approach is the lead decision.

**Gap 3 — Block `IsActive` toggle endpoint absent.**
Per brief Q4 and plan D-OQ-block-active: no `PUT /ContentBlocks/{id}/Active` endpoint exists. `AdminContentBlockDto.isActive` is displayed as read-only in this spec (§8.3 block card inactive notice). If the backend adds this endpoint in a future story, the block card can add a toggle without structural changes (add a `useSetBlockActive` hook + swap the notice for a toggle).

**Gap 4 — Inherited language not in Lesson/ContentBlock DTOs.**
`AdminLessonDetailDto` / `SingleLessonResponse` do not carry a `language` or `subjectCode` field (brief Q1). Language is resolved FE-side from the route param (the subject's language carried via `?lang=0|1` query param from the P7-01 tree navigation). If the lead prefers the backend to include `language` on `AdminLessonDetailDto`, flag as a BE additive change — a small `int` field that `GetAdminLessonQueryHandler` can resolve from `Unit.Subject.Language`. This spec designs for the FE-side resolution; the backend path is a no-UI-change upgrade.

**Gap 5 — Video embed security.**
In-preview video embed (`<iframe>` or `<video>`) is intentionally excluded to avoid unguarded embeds. A future enhancement could add a safe iframe embed (e.g. YouTube with explicit domain allow-list) — but requires security review. Flag to lead when video embed UX is prioritized.

**Gap 6 — `CurriculumPreview` for lessons with blocks.**
P7-05's `CurriculumPreview` (`app/(admin)/curriculum/preview/[type]/[id]/page.tsx`) currently renders lesson snapshot fields from the `ContentLifecycle/Preview` endpoint. That endpoint returns a serialized snapshot that may or may not include the `contentBlocks` array. The P7-05 spec's Lesson snapshot table (P7-05-FE.md §Component 5 — Lesson snapshot) does not list blocks. If the snapshot includes blocks and the preview is expected to render them, extend the P7-05 `CurriculumPreview` to use `BlockPreview` for those block entries. Flag to P7-05 implementer.

## Open Design Questions

**OQ-1 (Markdown library — lead decision required).**
Which Markdown parser + sanitizer to use in `BlockPreview`? Options:
- `marked` + `DOMPurify` (most common, ~20KB gzipped combined, both well-maintained)
- `markdown-it` + `DOMPurify` (more extensible, heavier)
- `sanitize-html` alone (includes markdown-like stripping but is not a proper MD parser — NOT recommended for proper Markdown rendering)
- Zero-dep: custom tag-whitelist stripper using `DOMParser` (safe but renders raw text only — no styled headers/lists/code blocks — poor author UX)
Flag to lead before 2b-C is dispatched.

**OQ-2 (Sequence order on create).**
Brief Q5: `AddLessonCommand` accepts `sequenceOrder`. This spec sends `existingLessons.length + 1` (append semantics). Confirm: is appending acceptable, or should the admin choose a position on create? This spec hides the sequence order field per plan D-OQ-block-active and brief Q5 assumptions — confirm with lead before 2b-B.

**OQ-3 (BlockPreview in packages/ui for reuse).**
Brief suggests `BlockPreview` (FE-5) may live in `packages/ui` for later student-app reuse. The student app currently uses flat `Lesson.Explanation` / `Lesson.Visual` — the block renderer is not yet needed there. Decision: build `BlockPreview` in `apps/admin-dashboard/components/` for now; move to `packages/ui` in a follow-up when the student app migrates to content blocks. Flag to lead if immediate placement in `packages/ui` is preferred.

**OQ-4 (Media upload vs URL-only).**
Brief Q6: v1 is URL-only per plan D7 (no upload endpoint on `ContentBlocksController`). This spec designs URL-only. Confirm with lead if in-dashboard file upload is expected for v1. If yes, a separate FE + BE follow-up is required (an upload endpoint on `ContentBlocksController`).
