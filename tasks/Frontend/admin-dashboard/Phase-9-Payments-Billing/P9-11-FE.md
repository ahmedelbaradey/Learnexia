## Acceptance-criteria coverage

- Admin can edit all named config values and save a new version → **FE-2** (+ P9-11-BE-3)
- Change history visible (who/when/old→new) → **FE-3** (+ P9-11-BE-5)
- Validation rejects nonsensical values (inline + server error surfacing) → **FE-4**
- Admin-only (non-admin redirect) → **FE-1** via `useAdminGuard`
- RTL/EN → **FE-5**

## Contract from Backend (P9-11-BE)

- `GET /api/Admin/Billing/Config` → `BaseResponse<BillingConfigDto>` with `CurrentValues` + `VersionHistory: BillingConfigVersionHistoryDto[]`.
- `POST /api/Admin/Billing/Config` `{ planPrice, freeMonthlyGrant, premiumMonthlyGrant, freeDailyCap, premiumDailyCap, packSize, packPrice, hintCost, explainMistakeCost, deepExplanationCost, practiceGenerationCost, note? }` → `BaseResponse<bool>`. Validation failure → `Successed=false` + message (422 or 200 with false — mirror existing pattern).
- Both endpoints admin-gated; 403 for non-admin.

## Notes

- Mirror P7-13 (`GamificationAdminOverrides`) for the form/table/dialog layout; do not invent new abstractions (CLAUDE.md design-patterns-ask-first rule 8).
- The confirm dialog before save is important: billing config changes have economy-wide impact. Mirror P7-07 or P7-08 destructive-action confirm patterns.
- The history table should show field-level old→new diff if the backend returns it (or show the full config snapshot per version if a diff is not returned). Confirm the API shape with the BE implementer.
- All mutations go through `@learnexia/api-client` (NSwag) + TanStack Query; invalidate `billing-config` query key on save.
- AdminOnly via `useAdminGuard` + middleware (same as every other admin screen).
