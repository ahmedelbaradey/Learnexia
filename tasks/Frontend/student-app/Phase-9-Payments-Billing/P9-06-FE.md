## Acceptance-criteria coverage

- Successful return → plan shows Active (or Pending until webhook) → **FE-4**
- Declined return → plan unchanged + clear error → **FE-4**
- Cancel → access to cycle end → **FE-2** + **FE-3** (cancel confirmation)
- EN+AR RTL → **FE-3** + **FE-5**
- Cross-account isolation → backend (api-tester); FE-6 asserts parent-only route

## Contract from Backend (P9-06-BE)

- `POST /api/Billing/Subscription/Checkout` → `{ successed: true, data: { checkoutRedirectUrl: "https://..." } }`
- `POST /api/Billing/Subscription/Cancel` → `{ successed: true }`
- Webhook drives actual plan-status truth — FE polls `GET /api/Billing/Subscription/Current` on return

## Notes

- **No card form** in our app at any point — the payment UI is entirely on the provider's hosted page.
- **Never render the checkout flow on a child route** — parent-only layout.
- The "Proceed to payment" action opens the provider URL. Confirm with lead whether `Linking.openURL` (browser-based) or an in-app WebView is preferred. If WebView, confirm the provider allows iframe embedding (many providers block it for security).
- Provider price (199 EGP) comes from the API (`usePlanComparison`), never hard-coded in the FE.
- The `useCancelSubscription` hook may be shared with P9-05-FE — do not duplicate.
