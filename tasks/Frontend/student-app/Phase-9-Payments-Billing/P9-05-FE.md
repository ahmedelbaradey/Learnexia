## Acceptance-criteria coverage

- View current plan + status → **FE-2** + **FE-4** (`useCurrentPlan` + `PlanStatusCard`)
- Compare Free vs Premium (config-driven, not hard-coded) → **FE-2** + **FE-4** (`usePlanComparison` + `PlanComparisonTable`)
- Upgrade → `PendingPayment` (not Active until P9-06 payment) → **FE-3** + **FE-4**
- Downgrade at next cycle → **FE-3** + **FE-4** (confirmation + "effective at cycle end")
- Family-scoped (owning parent only) → **FE-6** (E2E cross-account test)
- EN+AR RTL → **FE-4** + **FE-5**

## Contract from Backend (P9-05-BE)

- `GET /api/Billing/Subscription/Current` → `{ successed: true, data: { planCode, status, cycleEnd, pendingPlanCode } }`
- `GET /api/Billing/Plans/Comparison` → `{ successed: true, data: { free: { monthlyGrant, dailyCap }, premium: { monthlyGrant, dailyCap, priceEgp } } }`
- `POST /api/Billing/Subscription/Upgrade` → `{ successed: true, data: { checkoutRedirectUrl } }` (feeds P9-06 FE)
- `POST /api/Billing/Subscription/Downgrade` / `Cancel` → `{ successed: true }`

## Notes

- The **"Plan & billing" tab** was built as a read-only stub in P2-12 (P2-12d). FE-4 extends that tab's content — do not replace the tab shell, only fill in the real components.
- Upgrade CTA result (`checkoutRedirectUrl`) hands off to the P9-06 FE checkout flow.
- **Never show any plan/payment/billing surface on a child route** — gate at router level (parent-only layout).
- Benefit numbers (300 vs 3000 grants, 20 vs 150 daily caps) come from the API response (`usePlanComparison`), never hard-coded in the FE. Changing them in P9-11 config must flow through automatically.
