## Acceptance-criteria coverage

- Chronological list with date/amount/status/child for packs → **FE-3** (`BillingHistoryList`)
- Downloadable receipt with legally required fields → **FE-4** (receipt download/print)
- Refunds as linked negative entries → **FE-3** (refund rows)
- Owning-parent-only access → **FE-6** (E2E cross-account test) + BE-enforced
- EN+AR, empty state → **FE-3** + **FE-5**

## Contract from Backend (P9-08-BE)

- `GET /api/Billing/History?page=1` → `{ successed: true, data: { items: [{ date, kind, amount, currency, status, targetChildId?, providerRef, linkedRefundId? }], total, page } }`
- `GET /api/Billing/History/Receipt/{paymentId}` → `{ successed: true, data: { sellerName, sellerTaxId, amount, netAmount, vatAmount, grossAmount, date, reference, currency } }` (v1: printable HTML variant TBD)

## Notes

- **Child name mapping is FE-side:** the BE returns `targetChildId`; the FE maps it to the child's display name from the parent's already-loaded children list. No extra BE API call needed.
- Receipt rendering approach (WebView vs external tab for printable HTML) must be confirmed with the lead before FE-4.
- History fully depends on **P9-09** for refund entries to appear in the list — coordinate E2E test timing (FE-6 may need P9-09 to be deployed to show refund rows).
- **Never render billing history on a child route.**
