## Acceptance-criteria coverage

- Parent buys 500-credit pack, assigns to specific child → **FE-2** (child selector + checkout)
- Successful payment: credits visible for that child → **FE-3** (success return + energy refresh)
- Failed payment: no credits + error → **FE-3**
- Pack size/price config-driven → **FE-1** + **FE-2** (from API response)
- Children cannot purchase — no purchase surface on child routes → **FE-6** (E2E assert)
- Pack assigned to parent-owned child only → **FE-2** (child selector from parent's children)
- EN+AR RTL → **FE-2** + **FE-5**

## Contract from Backend (P9-07-BE)

- `POST /api/Billing/Packs/Checkout` body: `{ childId: int }` → `{ successed: true, data: { checkoutRedirectUrl: "..." } }`
- Pack size (500) and price served via the plan comparison/config endpoint (confirm with BE)

## Notes

- **No separate designer stage** — this is a small parent-area flow mirroring P9-06 checkout. If the lead wants a dedicated design spec, that is a planner call; currently treated as a light extension.
- The "Add energy" CTA placement (P5-05 per-child card vs P2-12 billing tab) is a UX/lead decision (FE-4) — confirm before building.
- `useStartPackCheckout` must reject child JWTs at the API level (BE-enforced) — the FE enforces by never rendering on child routes and only allowing parent JWTs to call the hook.
- Coordinate with P9-10-FE-2 (`useEnergyBalance`) so the energy meter refreshes after a successful pack purchase.
