## Acceptance-criteria coverage

- Parent sees per-child remaining (movable) split → **FE-2** (allocation overview)
- Move unspent allowance A→B (zero-sum) → **FE-3** (move control) + **FE-4** (refresh)
- Only remaining is movable; amount capped at source remaining; already-spent not movable → **FE-3** (cap + disable) + **FE-2** (spent shown as non-movable)
- Family-only — both pickers only ever list the parent's own children → **FE-3** (pickers fed by `useFamilyAllocation`) + **FE-7** (assert)
- Parent-gated, never on a child route → **FE-3** + **FE-5** (parent routes only) + **FE-7** (assert absence)
- EN+AR RTL → **FE-2/FE-3** + **FE-6**

## Contract from Backend (P10-16-BE)

- `GET /api/Billing/FamilyEnergy/Allocation` → `{ successed: true, data: { children: [ { childId, childName, allocated, spent, remaining } ] } }`
- `POST /api/Billing/FamilyEnergy/Transfer` body `{ fromChildId, toChildId, amount }` → `{ successed: true, data: { from: { childId, remaining }, to: { childId, remaining } } }`; on rejection `successed=false` with a localized message (exceeds remaining / not your child / same child / no active seat).
- Backend enforces same-family ownership, the remaining cap, and idempotency; the FE only ever offers the parent's own children and caps the amount client-side as a UX guard (the API is the source of truth).

## Notes

- **No bucket conversion** — this UI moves **allocated (subscription/entitlement)** allowance only. It must **not** present or touch the shared **purchased** family reserve, and must not imply spent energy can be reclaimed (only `remaining` is movable). Buying purchased packs is **P10-07**; refunds of purchased energy are **P10-09** — keep those flows separate in the UI.
- **Parent-only** — never render the allocation editor on a child route; the hooks must only be callable with a parent JWT (BE-enforced; FE enforces by route gating).
- Coordinate refresh with **P10-10** (`useEnergyBalance`) so a child's visible energy meter updates after a redistribution.
- **Ask before any new design pattern** (CLAUDE.md rule 8) — reuse existing parent-card / sheet / form primitives (P5-05, P10-07) rather than inventing new abstractions.
- This is a parent-account surface only — never shown in the student-facing learning UI.
