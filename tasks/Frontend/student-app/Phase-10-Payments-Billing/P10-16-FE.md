> Phase 10 · SP: 5 · FR-PAY-7 · Est. hours · App: **apps/student-app** (Expo universal, parent area)
> **Parent-only surface — never on a child route.** Family-energy-model wave. Mid-cycle energy mechanism (2026-06-17 final model).
>
> **MID-CYCLE CONTEXT:** A child added or reactivated mid-cycle receives NO automatic subscription energy grant (P10-14/P10-15 final model). P10-16 is the ONLY way the parent can give that child subscription energy during the current cycle. The UI must explicitly surface this: children with `isMidCycleNoGrant = true` from the API (zero allocation, active seat) must appear in the allocation list with a distinct "no grant this cycle — activated mid-cycle" state and a CTA to give them energy. This is a first-class use case, not an edge case.

## Contract from Backend (P10-16-BE)

- `GET /api/Billing/FamilyEnergy/Allocation` → `{ successed: true, data: { children: [ { childId, childName, allocated, spent, remaining, isMidCycleNoGrant: boolean } ] } }` — includes ALL active-seat children; mid-cycle children have `remaining = 0, isMidCycleNoGrant = true`.
- `POST /api/Billing/FamilyEnergy/Transfer` body `{ fromChildId, toChildId, amount }` → `{ successed: true, data: { from: { childId, remaining }, to: { childId, remaining } } }`; on rejection `successed=false` with a localized message (exceeds remaining / not your child / same child / no active seat). Note: a `toChildId` with `remaining = 0` (mid-cycle child) is a VALID request — the API accepts it and creates the allocation row; the FE must not block this.
- Backend enforces same-family ownership, the remaining cap, active-seat check, and idempotency; the FE only ever offers the parent's own children and caps the amount client-side as a UX guard (the API is the source of truth).

## Notes

- **MID-CYCLE ENERGY MECHANISM (FINAL MODEL 2026-06-17):** P10-16 is the ONLY way a mid-cycle-activated child can receive subscription energy. The UI must make this discoverable: when a parent adds/reactivates a child mid-cycle (P10-14/P10-15), the allocation overview in P10-16 should surface immediately (or via a deep-link from the seat activation confirmation) so the parent can give the child energy without hunting for the feature.
- **No bucket conversion** — this UI moves **allocated (subscription/entitlement)** allowance only. It must **not** present or touch the shared **purchased** family reserve, and must not imply spent energy can be reclaimed (only `remaining` is movable). Buying purchased packs is **P10-07**; refunds of purchased energy are **P10-09** — keep those flows separate in the UI.
- **Zero-allocation destination is valid** — do NOT filter mid-cycle children out of the destination picker or show them as disabled/unavailable. They are the primary case for this feature in the mid-cycle scenario.
- **Parent-only** — never render the allocation editor on a child route; the hooks must only be callable with a parent JWT (BE-enforced; FE enforces by route gating).
- Coordinate refresh with **P10-10** (`useEnergyBalance`) so a child's visible energy meter updates after a redistribution.
- **Ask before any new design pattern** (CLAUDE.md rule 8) — reuse existing parent-card / sheet / form primitives (P5-05, P10-07) rather than inventing new abstractions.
- This is a parent-account surface only — never shown in the student-facing learning UI.
