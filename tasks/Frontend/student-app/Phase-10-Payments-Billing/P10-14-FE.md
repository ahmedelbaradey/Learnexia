## Acceptance-criteria coverage

- View seats (total/occupied/free) + which children are active → **FE-3** (`SeatStatusCard` + `ChildSeatList`)
- Buy N extra seats (monthly, config price, web checkout) → **FE-4** (`useStartSeatCheckout` + checkout)
- Seat purchase success raises free seats; declined adds nothing → **FE-4** (return handler) + **FE-8** (E2E)
- Cancel extra seat → grace-period copy, no energy refund, no child deleted → **FE-5**
- Add-child with no free seat → clean rejection, no child created, buy-seat CTA → **FE-6** + **FE-8**
- Locked/NoSeat children remain visible (progress preserved) → **FE-3**
- Parent-gated, never on a child route → **FE-3** + **FE-8** (E2E assert absence)
- EN+AR RTL → **FE-3** + **FE-7**

## Contract from Backend (P10-14-BE)

- `GET /api/Billing/Seats/Status` → `{ successed: true, data: { totalSeats, occupiedSeats, freeSeats, children: [{ childId, name, seatStatus: "Active" | "NoSeat" | "Locked" }] } }`
- `POST /api/Billing/Seats/Checkout` body `{ seatQuantity: int }` → `{ successed: true, data: { checkoutRedirectUrl } }` (extra-seat **monthly price resolved server-side**; FE shows price from status/config response, never hard-coded)
- `POST /api/Billing/Seats/Cancel` body `{ seatQuantity: int }` → `{ successed: true }` (starts grace period server-side)
- `POST /api/Parent/Add-Child` (existing) → on no free seat returns the localized **no-free-seat** rejection (FE-6 handles it); no child is created

## Notes

- **Light design stage** — extends the P10-05 / P2-12d "Plan & billing" surface with a Seats section; not a standalone screen unless the lead prefers a dedicated `(parent)/settings/seats.tsx`. If a richer spec is wanted, that is a planner/designer call.
- **Never show seats / buy / cancel on a child route** — gate at router level (parent-only layout); E2E asserts absence.
- **Seats ≠ energy in the UI:** buying/canceling a seat changes the seat count, **not** the energy meter. Energy (buckets, allowances, transfers) is **P10-13/15** — do not conflate the copy. "Energy arrives next cycle" messaging only.
- **Config-driven:** seat counts (included/extra/max) and the extra-seat price come from the API/config response — changing them in P10-12 must flow through automatically; never hard-code in the FE.
- **Locked/NoSeat children are never hidden or deleted** — the per-child list keeps them visible with a Locked/NoSeat badge (locked model: children keep progress/XP/history/achievements).
- **Ask before any new design pattern** (CLAUDE.md rule 8) — mirror existing parent-billing component/hook shapes (P10-05/P10-07), do not invent provider/compound-component abstractions.
- Coordinate the add-child error wiring with the **Parent** add-child screen owner (P1-04) and the seat-checkout pattern with **P10-06/P10-07** FE.
