> **Design stage required (extends the P10-05 "Plan & billing" surface + the parent child list).** Parent-only surface — never on a child route.

> **Status: 🔲 Not started**

> **FINAL MODEL (lead-approved 2026-06-17) — key UI implications:**
> - **Voluntary removal → scheduled-removal notice (NOT a grace banner).** Affected child keeps full access until the next renewal date. Copy must say "Your child keeps full access until [renewal date]."
> - **Payment-failure → payment-failure banner** (NOT a generic "grace" banner). Shows failed-charge info, next retry date, grace end, and CTA to update payment method.
> - **Reactivation → prorated-charge preview.** Copy must say reactivation is immediate AND that energy for the remainder of the cycle must be allocated from the family wallet (P10-16) — subscription does NOT auto-grant energy mid-cycle.
> - **No forfeit / no allowance-strip copy** anywhere. Locked child keeps all energy already allocated; copy must not imply any energy is taken back.

## Contract from Backend (P10-15-BE)

- `GET /api/Billing/Seats/Status` → `{ successed, data: { paidActiveSeats, paymentFailureGrace: { isActive, endsAt } | null, children: [ { childId, name, seatState: "Active" | "NoSeatLocked", removalScheduledAt: string | null } ] } }`
- `POST /api/Billing/Seats/ChooseActive` body `{ childIds: number[] }` → `{ successed }`; rejects when `childIds.length > paidActiveSeats` (envelope error message).
- `POST /api/Billing/Seats/Reactivate` body `{ childId }` → `{ successed, data: { redirectUrl: string } }`; fails when payment cannot be initiated (no free seat available without prorated payment).
- **Note:** A `POST /api/Billing/Seats/CancelRemoval` endpoint (cancel a voluntary-removal scheduling) may be needed for FE-5; flag to BE if not already in P10-15-BE scope.

## Notes

- **Parent-app surface only** — never render any seat/grace/locked UI on a child route; gate at the parent-only layout.
- **Two distinct banners, not one.** Payment-failure (`paymentFailureGrace.isActive`) and scheduled voluntary removal (`removalScheduledAt`) are different events with different UI components and different copy. Do not merge them into a single "grace banner."
- **Locked ≠ deleted ≠ data loss ≠ energy loss.** Copy must make clear the child keeps progress/XP/history/achievements AND that energy already allocated for the current cycle is unaffected. Only future AI help is paused. Avoid alarming wording.
- **Reactivation copy must include the energy-from-wallet note.** The platform does not auto-grant subscription energy mid-cycle. The prorated-charge preview (FE-6) must explain that the parent needs to allocate from the family wallet (P10-16) for the child to have energy to spend after reactivation.
- Seat counts, grace dates, renewal dates, and prorated amounts come from the API (`useSeatStatus`, reactivation response) — **never hard-coded** in FE.
- Extends the **P10-05** Plan & billing surface and the existing parent child list; reuse existing card/badge/modal primitives. **Ask before any new design pattern** (CLAUDE.md rule 8).
- Hands off cleanly to sibling **P10-13/P10-14** seat/allocation UI (don't duplicate the allocation/redistribution controls — those are P10-14's surface) and **P10-16** (wallet-allocation UI — the parent uses P10-16 to give energy to a reactivated child).
