## Scope note (for the frontend lead)
This describes screens/flows only — **no app code is written here**. Parent-facing surface: per purchased pack, show the **refundable purchased balance**, and let the parent **request a refund of unused purchased energy**. Subscription/entitlement energy is **never** refundable and must never appear as refundable in the UI. The resulting refund shows as a linked negative entry in billing history. Children never see refunds.

- Per purchased pack: refundable purchased balance shown → **FE-3** (`RefundablePackBadge`)
- Parent can request a refund of unused purchased energy → **FE-4** (`RequestRefundSheet`) + **FE-2** (mutation hook)
- Subscription/entitlement energy never shown as refundable → **FE-3** (hidden for bucket-A rows) + **FE-4** ("not refundable" note) + **FE-6** (assert no CTA on renewal rows)
- Refund appears as a linked negative entry in billing history → **FE-6** (cross-checks P10-08/P10-15)
- Zero-refundable (fully-consumed pack) handled, no CTA → **FE-3** + **FE-6**
- No child surface; owning-parent only → **FE-6** (assert absence on child routes + cross-account denied)
- EN+AR, RTL → **FE-3..FE-5**
- Heavy verification (reconciliation math, idempotency, no-negative-balance, webhook security) → **api-tester** + **security-auditor** (backend)

## Contract from Backend (P10-17-BE)

- `GET /api/Billing/Refunds/Quote/{purchasePaymentId}` → `{ successed: true, data: { purchasedTotal, consumedPurchased, refundable, currency } }`
- `POST /api/Billing/Refunds/Request` body `{ purchasePaymentId, reason }` → `{ successed: true, data: { refundRequestId, refundable, status } }` (status reflects "initiated"; final settlement is webhook-driven)
- The refund, once settled, surfaces in `GET /api/Billing/History` as a linked negative entry (P10-08 / P10-15 contract).

## Notes

- **Settlement is asynchronous (webhook-driven):** the request only *initiates* the provider refund (P10-17-BE-3); the balance/ledger change lands on the `refund.succeeded` webhook (P10-17-BE-4). The UI must show a **pending** state, not an instant balance change.
- **Bucket distinction is load-bearing in the UI:** only **purchased** (bucket B) rows can show a refund CTA; **subscription/monthly** (bucket A) energy is never refundable — never render a refund affordance for it. This is a money-correctness rule, not cosmetic.
- The refundable balance reuses the billing-history surface (P10-08 / P10-15) — extend the existing pack row rather than building a new screen where possible.
- **Never render any refund affordance on a child route.** The only child-visible effect is a smaller family energy reserve, surfaced naturally by the energy meter (P10-10).
- **Ask before any new design pattern** (CLAUDE.md rule 8) — mirror existing billing component/hook shapes (P10-08-FE).
