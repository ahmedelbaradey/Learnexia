# P6-07 (frontend) — Handle server-side token revocation (401 → re-auth)

> Story: [../../../user-stories/Phase-6-Stabilization/P6-07-access-token-revocation.md](../../../user-stories/Phase-6-Stabilization/P6-07-access-token-revocation.md)
> Phase 6 — Stabilization · Module: **student app (Expo) + admin (Next.js later)** · thin client-side follow-on to the backend G2 work.
> **Backend-owned story; this FE slice is small.** Once the backend revokes access tokens server-side (`OnTokenValidated`), a token that used to "work until expiry" can now start returning **401 mid-session** (after sign-out elsewhere, password change on another device, or admin suspend). The client must handle that gracefully instead of showing broken/blank screens.

## Required behavior (lead spec, 2026-06-21)
When the backend returns **`401` (session expired/revoked)** mid-session, the client MUST:
1. **NOT loop** (no infinite refresh→401→refresh cycle).
2. **clear auth state**
3. **clear cache** (query cache / persisted state)
4. **navigate to login**
5. **show the message:** `"تم انتهاء الجلسة، سجل الدخول مرة أخرى"` (ar) / "Your session ended — please sign in again" (en)

> A normal access-token *expiry* should still try the refresh-token flow **once** first; only when refresh ALSO fails (the session was revoked, so the refresh token is gone too) do steps 2–5 run. The backend returns a plain `401` for both cases (no reason leaked, by design), so "refresh once, then on a second 401 hard-sign-out" is the discriminator.
