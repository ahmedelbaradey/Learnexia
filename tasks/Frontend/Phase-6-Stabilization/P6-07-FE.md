# P6-07 (frontend) — Handle server-side token revocation (401 → re-auth)

> Story: [../../../user-stories/Phase-6-Stabilization/P6-07-access-token-revocation.md](../../../user-stories/Phase-6-Stabilization/P6-07-access-token-revocation.md)
> Phase 6 — Stabilization · Module: **student app (Expo) + admin (Next.js later)** · thin client-side follow-on to the backend G2 work.
> **Backend-owned story; this FE slice is small.** Once the backend revokes access tokens server-side (`OnTokenValidated`), a token that used to "work until expiry" can now start returning **401 mid-session** (after sign-out elsewhere, password change on another device, or admin suspend). The client must handle that gracefully instead of showing broken/blank screens.

## Tasks
| ID | Task | Artifact | Deps | Est (h) |
|---|---|---|---|---|
| P6-07-FE-1 | **Global 401 interceptor.** In the shared API client, on a `401` from an authenticated request: attempt the existing refresh-token flow **once**; if refresh also fails (refresh token was revoked too), clear local auth state and route to sign-in with a localized "your session ended — please sign in again" toast (ar/en). | shared `api-client` interceptor + auth store | P6-07-BE-2 | 4 |
| P6-07-FE-2 | **Don't loop / don't thrash.** Ensure a revoked token can't cause an infinite refresh→401 loop (single retry, then hard sign-out). Verify the "sign out other devices" and "change password" screens reflect that other sessions are now actually gone. | api-client retry guard + sessions screen | FE-1 | 2 |
| P6-07-FE-3 | **frontend-e2e-tester:** sign in on two browsers; sign out / change password on one; confirm the other gets a clean redirect-to-login (not a broken screen) on its next action; RTL (ar) + en. | frontend-e2e-tester | FE-1, FE-2 | — |

## Notes
- Purely client-side resilience — no new endpoints. Mirrors existing auth-store + api-client shapes; **ask before introducing any new pattern** (per project rule #8).
- Depends on the backend (`P6-07-BE-2`) being live in the target environment.
