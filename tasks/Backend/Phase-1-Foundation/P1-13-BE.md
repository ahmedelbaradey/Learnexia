## Acceptance-criteria coverage
- Account lockout engaged after N failures, resets on success → **BE-1** (Gap #1)
- Sign-in no longer leaks internals; no email-enumeration oracle → **BE-2** (Gap #2)
- Admin provisioned from config (no committed credential), idempotent → **BE-3** (Gap #5)
- Anonymous register protected by a bot challenge in addition to IP rate-limit → **BE-4** (Gap #3)
- *Email delivery (Gap #4) + registration-message send (Gap #6) → **P1-13a** (built first).*

## Contract to Frontend (P1-11-FE / admin app)
- Sign-in error responses become **uniform** (`BaseResponse`, `Successed=false`, single "invalid credentials" message) — FE must not branch on user-not-found vs wrong-password. Locked-account returns its own localized message + (optionally) a retry-after hint.
- Register may require a CAPTCHA token field when the bot-challenge is enabled (config-gated); FE sends it only when the server advertises the requirement. All `BaseResponse<T>`, camelCase, `Successed`, `NewResult(...)`.

## Notes
- **Identity-module-scoped** → parallel-safe; cross-module only via `Shared.Contracts` integration events, no cross-module FK. No Unit of Work — `GenericRepository` commits per call; open an explicit transaction only for atomic multi-write.
- **Security-sensitive** (auth path, secrets) → security-auditor blocks Critical/High before the reviewer gate.
- **Ask before adding any design pattern** — e.g. the bot-challenge verifier abstraction in BE-4. Name it and wait for approval.
- **Sequencing:** BE-1/BE-2/BE-3 are quick, no new abstractions; BE-4 (CAPTCHA) may defer to a P6 hardening pass per the gap-analysis recommendation. Email work is in **P1-13a** and built first.
