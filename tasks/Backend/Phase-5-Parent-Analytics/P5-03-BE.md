# P5-03 (backend) — Analytics event-capture backbone

> Story: [../../../user-stories/Phase-5-Parent-Analytics/P5-03-analytics-event-capture.md](../../../user-stories/Phase-5-Parent-Analytics/P5-03-analytics-event-capture.md)
> Phase 5 · **NEW `Analytics` module** (lead-approved 2026-06-19) · schema `analytics` · cross-module via `Shared.Contracts` integration events only (no FK, no project refs)

## Lead decisions (binding — 2026-06-19)
- **New `Analytics` module** (4-project scaffold mirroring the `Moderation` module), schema `analytics`. Owns the activity-event sink + the platform read seams that P7-10 consumes. (`ask-before-new-modules` gate cleared.)
- **Inactivity-window session model:** sessions are **derived at read-time** from the `ActivityEvent` stream — a session is a run of one student's events with gaps `< SessionGapMinutes` (default **30**). NO explicit sign-out, NO persisted Session table in v1. **Retention = distinct active UTC days** per student.
- **Fail-soft capture (NFR-1):** ingestion runs in idempotent `INotificationHandler<T>` consumers of `Shared.Contracts` integration events; a sink failure MUST NOT affect the producing path. Append-only writes per ADR-0001 (direct `SaveChangesAsync`, no UoW). No measurable hot-path latency on producers.

## Design rules (binding)
- **Module isolation (rule #1):** Analytics references NO other module's projects. It consumes only `Shared.Contracts` integration events and exposes only `Shared.Contracts` read seams. `StudentId` is a plain `int` (no cross-module FK).
- **PII-light:** `ActivityEvent` stores ids, an event-type, a subject-code facet, a UTC timestamp, and an optional duration — **never** names/emails/prompt/response/answer text.
- `BaseResponse<T>` / `Successed`, `NewResult(...)`, `ILoggerManager`, localized messages (EN+AR), **Option C** (EF only in Infrastructure; Application handlers EF-free behind service/seam interfaces), MediatR CQRS (queries skip `ValidationBehavior` → validate ranges in-handler).
- **Shared-file serialization (PARALLELISM.md):** the module scaffold touches `Learnexia.Modular.sln`, Host `Program.cs`, cross-module MediatR registration, and `Directory.Packages.props` — serialize these edits; do not run in parallel with another story touching them.

## Acceptance-criteria coverage (story P5-03)
- Captures DAU/WAU, session duration, mission completion, quiz accuracy, retention, subject engagement → BE-1 (event shape incl. subject facet + duration), BE-3 (consumers for mission/attempt/sign-in), BE-4 (DAU/duration/retention derivation).
- Recorded reliably via event handlers (P4-01) → BE-2/BE-3 (consume the existing backbone; idempotent + fail-soft).
- Queryable for KPI dashboards (P6-05 / P7-10) → BE-5 (seams) + BE-6 (P7-10 wired).
- No measurable latency degradation (NFR-1) → fail-soft async consumers, append-only, no producer-path writes.

## Notes
- **Mandatory security-auditor** (student activity data, child-privacy) before the reviewer gate.
- Sessions/retention are **read-time derived** in v1 (no Session table) — if event volume makes read-time derivation slow later, materialize daily session/active-day rollups (documented follow-up).
- Cohort-based retention curves (D1/D7/D30) are the **foundation** here (active-days + returning-user); full cohort curves can layer on the same `ActivityEvent` table later.
- Pairs with **P7-11b** (streaming AI-usage capture) in the same wave but is independent of it.
