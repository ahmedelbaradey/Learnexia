## Contract for Frontend (P7-07-FE)
- `POST /api/Admin/Users/{id}/suspend` `{ reason }` → `BaseResponse<AdminUserProfileDto>`.
- `POST /api/Admin/Users/{id}/reactivate` `{ reason? }` → `BaseResponse<AdminUserProfileDto>`.
- `DELETE /api/Admin/Users/{id}` `{ reason, confirm, cascadeChildren? }` → `BaseResponse<bool>`.
- All gated by the admin policy; commands are validated (ValidationBehavior on `ICommand<>`); `Successed` flag per envelope.

## Notes
- **Suspend ≠ lockout:** admin suspension (`AccountStatus.Suspended`) is a deliberate governance state — keep it **separate** from the P1-13 failed-login `LockoutEnd` mechanism (different field, different lifecycle, different unlock path). Suspend must actively **revoke active sessions** (bump the JWT validity/security stamp so issued tokens stop validating), not merely block the next sign-in.
- **Account-lifecycle fan-out (Phase 3 + Parent):** `AccountSuspended/Reactivated/Deleted` are consumed by **Learning, Gamification, and Parent** modules — Gamification (Phase 3, merged) must freeze/clean league/streak/XP state, Parent must update family/linkage views. Wire all three handlers, each reacting in its own schema via the contract (no cross-module FK/write).
- Reuses the **Identity** module — Identity already has `UserManagementController` gated AdminOnly; this story extends it (NOT greenfield). Mirror the **Identity / Learning** module shape (not Catalog — Catalog was removed 2026-06-03, PR #84).
- Cross-module cleanup is via `Shared.Contracts` integration events only — never direct FK/writes. Delete touches multiple Identity rows (parent + children) → wrap in an **explicit transaction** (no Unit of Work). Child data is sensitive: reason + confirm + audit are mandatory.
- **Policy:** `AuthorizationPolicies.AdminOnly` for now; promoting to granular `{Module}.{Action}` policies (via `Claims.GenerateModules()`) is a follow-up if the lead wants finer-grained authz.
