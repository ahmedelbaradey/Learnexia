# P7-13 (Backend) — Gamification admin overrides

> Story: [../../../user-stories/Phase-7-Admin-Console/P7-13-gamification-admin-overrides.md](../../../user-stories/Phase-7-Admin-Console/P7-13-gamification-admin-overrides.md)
> Phase 7 — Admin Console · Epic: Admin — Gamification Management · SP: 8 · SRS §3, FR-ADM-8 · Est. unit: hours
> Stack: .NET 10 `Gamification` module, CQRS/MediatR, FluentValidation, Npgsql.

> **Reality check (write surface over a shipped engine, not greenfield):** Phase 3 gamification is **merged** — `League` + tiers (`LeagueTier`), `BadgeDefinition`/`MissionDefinition` catalogs (each seeded by an **idempotent** `BadgeSeeder`/`MissionSeeder`), streak-freeze, and `TimedEvent` all exist. Those endpoints shipped **read-only**; only `GET api/admin/timed-events` exists on the timed-event side. This story adds the **AdminOnly write surface** (the four override areas + streak-freeze grant) on top of the existing entities — **NOT greenfield**. All endpoints are `[Authorize(Policy = AuthorizationPolicies.AdminOnly)]`; multi-writes use deferred commit + `UnitOfWorkBehavior` (ADR 0001).

## Acceptance-criteria coverage
- Override a child's league tier (reason + confirm), applied to live standings, audited → **BE-2, BE-8**
- Badge catalog create/edit/deactivate; deactivation does not strip earned badges → **BE-3**
- Mission catalog create/edit/deactivate, reflected in generated missions → **BE-4**
- Timed-event create/update/activate/expire driving the engine (was read-only) → **BE-5**
- Grant streak-freeze to a child (reason + confirm), reflected in engine, audited → **BE-6, BE-8**
- Every override/edit/grant records actor/timestamp/target/old→new/reason + audited; PII-safe → **BE-8**
- Seeders don't clobber admin edits (seed-if-absent precedence) → **BE-7**
- All endpoints AdminOnly; non-admin → 403 → **BE-1** (+ **BE-9** audit)

## Contract for Frontend (P7-13-FE)
- `POST /api/Admin/Gamification/children/{childId}/league-tier` `{ tier, reason, confirm }` → `BaseResponse<bool>`.
- `GET/POST/PUT/DELETE /api/Admin/Gamification/Badges[/{id}]` → `BaseResponse<List<BadgeDto>>` / `<Guid>` / `<bool>`.
- `GET/POST/PUT/DELETE /api/Admin/Gamification/Missions[/{id}]` → `BaseResponse<List<MissionDto>>` / `<Guid>` / `<bool>`.
- `GET/POST/PUT /api/Admin/Gamification/TimedEvents[/{id}]` + `.../{id}/activate` + `.../{id}/expire` → `BaseResponse<...>`.
- `POST /api/Admin/Gamification/children/{childId}/streak-freeze` `{ count, reason, confirm }` → `BaseResponse<bool>`.
- All admin-gated; invalid input / illegal state-transition → `Successed=false` + message; success flag spelled `Successed`.

## Notes
- Lives in the **`Gamification`** module (the shipped Phase 3 engine) — mirror its existing command/query/controller shapes; `Successed`, `NewResult(...)`, `ILoggerManager`. Do **not** scaffold a new module.
- **Seed vs admin precedence (design consideration — ask first):** `BadgeSeeder`/`MissionSeeder` are idempotent startup seeders. Admin catalog edits must survive a reboot — the seeders must seed-if-absent and never overwrite admin-modified rows. Settle the precedence rule before implementing; per CLAUDE.md rule 8, **ask the lead before introducing any new pattern** to reconcile seed vs admin authorship.
- **Privileged/destructive surface → security-sensitive (BE-9):** child-affecting overrides (league tier, streak-freeze grant) and platform-config writes (catalogs, timed events) require confirm + reason where they touch a child; `security-auditor` audits before the reviewer gate (Critical/High block).
- **Auditing:** every action publishes `AdminActionPerformedEvent` (the `Shared.Contracts` seam defined in P7-12-BE-3) and lands in the P7-12 audit log under new `ActionType`s; before/after snapshots are PII-safe (ids + changed fields only).
- **Module isolation:** no cross-module FK; targeting a child (league tier / streak-freeze) and all cross-module effects flow via `Shared.Contracts` integration seams only.
- **Transactions:** catalog edits and multi-step state transitions use the deferred commit + `UnitOfWorkBehavior` per ADR 0001; no explicit Unit of Work type.
- **Policy:** `AuthorizationPolicies.AdminOnly` for now; promoting to granular `{Module}.{Action}` policies (via `Claims.GenerateModules()`) is a follow-up if the lead wants finer-grained authz.
