# P10-15 (Backend) — Seat enforcement, grace period & NoSeat/Locked child lifecycle

> Story: [../../../user-stories/Phase-10-Payments-Billing/P10-15-seat-enforcement-grace-period-noseat-locked-lifecycle.md](../../../user-stories/Phase-10-Payments-Billing/P10-15-seat-enforcement-grace-period-noseat-locked-lifecycle.md)
> Phase 10 — Payment, Billing & Credits · Epic: Payment, Billing & Credits · SP: 8 · FR-PAY-11 · Est. unit: hours
> **Security-sensitive (money-derived entitlement + child data) — mandatory `security-auditor` gate.** Builds on P10-13 (wallet + per-child allocation rows + reservation seam), P10-14 (seats + extra-seat checkout), P10-05 (downgrade), P10-09 (dunning), P10-01 (ledger). **Canonical mapping: 13 wallet · 14 seats · 15 lifecycle (this story) · 16 redistribution · 17 refunds.**
> **Option C service-only (CONVENTIONS §7): the `Billing.Application` layer is EF-free and depends on SERVICE INTERFACES only** — no DbContext, no repository, no EF in handlers. Module isolation: child is a loose `int` id; cross-module only via `Shared.Contracts` (no FK).

> **Status: 🟡 Scope-confirmed (lead 2026-06-17), build starting** — folds in P10-14 security finding #3 (BE-10 reservation idempotency) + the dedicated `SeatLedgerEntry` seat-audit ledger (BE-11; energy stays `CreditTransaction`). Tie-break + grace-re-trigger OQs resolved (below).

> **FINAL MODEL (lead-approved 2026-06-17) — key invariants for this task file:**
> - **Voluntary removal = effective at cycle end.** Seat stays Active until next renewal; child keeps current allocation; NO mid-cycle energy forfeit; NO refund. At renewal: seat removed, grant recalculates, over-seat children → NoSeat/Locked.
> - **7-day grace = payment-failure retry window ONLY.** Downgrade and seat-cancel do NOT start a grace window; they schedule removal at cycle-end.
> - **Reactivation = prorated money (via P10-14 checkout seam) + immediate activation; ZERO energy minted mid-cycle.** Energy for the reactivated child comes from the parent allocating from the family wallet (P10-16).
> - **No mid-cycle forfeit job.** Do not implement any job or service that strips unspent entitlement mid-cycle. Enforcement removes the allocation row for newly-locked children (no future entitlement) but never reclaims already-ledgered energy.

## Acceptance-criteria coverage

- Voluntary removal scheduled at cycle-end (seat stays Active; child keeps allocation; no forfeit; no refund) → **BE-3** (`ScheduleRemovalAtCycleEndAsync`) + **BE-4** (enforcement at renewal boundary)
- Payment-failure grace window (7 days, config-driven, idempotent, payment-failure only) → **BE-2** (`ISeatGraceService`)
- During grace/cycle-remainder seats stay Active (children keep allocation + can spend) → **BE-2** / **BE-3** + **BE-5** (lock state only flips on enforcement)
- Enforcement on renewal/grace expiry: compute over-limit, honor parent choice or default, lock over-limit children, remove allocation row, no energy forfeit, never delete, ledger every move → **BE-4**
- NoSeat/Locked child has no allowance + cannot spend AI (graceful localized decline) → **BE-1** (state) + **BE-5** (spend gate)
- Locked child keeps progress/XP/history/achievements (no Identity/Learning touch) → **BE-4** (hard invariant — Billing-only writes)
- Mid-cycle reactivation: prorated money, immediate activation, zero energy minted → **BE-6** (`ReactivateChildSeatCommand`) + **BE-7** (webhook activation)
- Already-spent energy never reclaimed; no mid-cycle forfeit; purchased untouched → **BE-4** (no forfeit in enforcement)
- Parent chooses which children keep seats, validated ≤ paid active seats, family-scoped, ledgered → **BE-6** + **BE-9**
- Seat-state checkable cross-module without FK → **BE-8** (`Shared.Contracts` seam)
- EN+AR localized declines / messages → **BE-5** + **BE-6** (SharedResourcesKey, no literals)
- Reservation idempotent + concurrency-safe (no two children share one seat row); enforcement reconciles drift → **BE-10** (folds P10-14 finding #3)
- Every seat event (purchase / cancel-scheduled / removed / locked / reactivated / choice) written to the dedicated append-only `SeatLedgerEntry` audit ledger; energy ledger (`CreditTransaction`) untouched → **BE-11**

## Notes

- **OQ-1 (RESOLVED 2026-06-17):** The 7-day grace window applies **only** to payment-failure (P10-09 dunning). Voluntary removal and downgrade are NOT grace events — they schedule removal at cycle-end (`SeatReservation.RemovalScheduledAt`). The single payment-failure clock = `Subscription.SeatGraceEndsAt = trigger_time + seats.grace_days`. Seed `seats.grace_days = 7` + add to `ManagedKeys`.
- **OQ-2 (default selection tie-break) — RESOLVED (lead 2026-06-17): keep the EARLIEST-RESERVED seats** (deterministic, by `SeatReservation.ReservedAt`). Parent can always re-choose afterward (BE-6).
- **OQ-3 (grace re-trigger semantics) — RESOLVED (lead 2026-06-17): NO stacking** — a second payment-failure webhook during an open grace window does not shorten, extend, or stack the deadline (idempotent single window).
- **NO MID-CYCLE FORFEIT — HARD PRODUCT DECISION (2026-06-17).** The earlier OQ-H design (forfeit unspent entitlement of locked child back to family wallet) is **fully removed**. Enforcement removes the allocation row (no future grants) but never strips already-ledgered credit. Do not implement any forfeit job, forfeit service, or forfeit ledger entry for voluntary removal.
- **Reactivation = prorated money + zero energy.** `ReactivateChildSeatCommand` (BE-6) initiates a prorated checkout via P10-14's `IPaymentProvider`/extra-seat seam. The webhook (BE-7) restores seat state and re-joins the allocation row. The parent then uses P10-16 wallet allocation to give the reactivated child energy for the remainder of the cycle. This story owns the seat restoration; P10-16 owns the energy flow.
- **HARD INVARIANT (security-auditor must verify):** enforcement and locking are **Billing-only** writes — they MUST NOT delete a child or cascade into Identity / Learning / Gamification records. Child progress/XP/history/achievements are owned by other modules and stay intact.
- **Module isolation:** child id is a loose `int`; seat-state checks for the AI/Parent modules go through the `Shared.Contracts` seam (BE-8), never a direct Billing reference or FK.
- **Option C (CONVENTIONS §7):** all handlers (BE-6) inject **service interfaces** declared in `Billing.Application/Abstractions`; grace/enforcement/spend-gate logic lives in `Billing.Infrastructure/Services`; **no EF/DbContext/repository in Application**.
- **No UoW (ADR 0001):** enforcement (lock + allocation-row removal + ledger) and choose-active (state flips + allocation + ledger) each run in a single **explicit transaction**; idempotency keys guard re-runs. Concurrency: enforcement vs a concurrent parent choose-active must not double-lock — guard with the per-family+cycle idempotency key.
- **`ValidationBehavior` runs for `ICommand<>` only** — `ChooseActiveChildren` + `ReactivateChildSeat` get FluentValidation validators; the status query does not.
- **No free-text string literals** — every parent/child-facing message is a `SharedResourcesKey` (EN+AR resx); states are enums.
- Builds on **P10-13** (wallet + per-child allocation rows + reservation seam), **P10-14** (seat model + reservation seam + checkout seam for reactivation), **P10-05** (downgrade — calls `ScheduleRemovalAtCycleEndAsync`), **P10-09** (dunning/payment-failure — calls `StartPaymentFailureGraceAsync`), **P10-01** (immutable ledger). Keep seat-state contracts consistent with sibling **P10-16** (redistribution — energy allocation for reactivated children) / **P10-17** (refunds — purchased-energy only, not affected by enforcement).
- **Serialize shared-file edits** (`Program.cs` DI for the Hangfire job, `Shared.Contracts` additions) with concurrent P10-13/P10-14 work per PARALLELISM.md.
