## Architecture guardrails (read before coding)
- **Module isolation:** all work lives in the **Billing** module (`FamilyEnergyAccount`, buckets, ledger, packs, payments, refunds are Billing-owned per the locked model). No cross-module FK. Any cross-module need goes through `Shared.Contracts` only. Identity owns child profiles — do **not** reach into it.
- **Option C — service-only (CONVENTIONS §7):** the Application layer is **EF-free and depends on service interfaces ONLY**. Handlers inject **service interfaces** from `Billing.Application/Abstractions` — never a `DbContext`, `DbSet`, `IQueryable`, repository, or `Microsoft.EntityFrameworkCore`. Chain is **Handler → Service → Repository → EF**. Reconciliation logic + explicit transactions live in the **service impl in Infrastructure**.
- **No UoW (ADR 0001):** refund reconciliation (read ledger → compute refundable → append `Refund` row → decrement shared purchased balance) is a multi-write atomic operation → wrap in an **explicit transaction inside the service**, never in a handler.
- **No free-text string literals** — refund reasons / statuses / error keys are **enums or localized keys**, not hardcoded strings.
- **Refines, does not duplicate, P10-09:** extend the existing `RefundService` and the `refund.succeeded` webhook branch rather than adding a parallel refund path.

## Acceptance-criteria coverage

- Refundable = purchased − consumed-purchased, reconciled from the immutable ledger (10000 − 3000 → 7000) → **BE-1** (contract) + **BE-2** (impl + math)
- Subscription/entitlement (bucket A) energy is **never** refundable → **BE-2** (bucket-B-only reconciliation excludes subscription/allocation rows)
- Already-consumed purchased energy can never be refunded; refundable clamped ≥ 0, never exceeds remaining purchased → **BE-2** (clamp) + **BE-4** (re-clamp at settlement, no negative balance)
- Successful refund = idempotent `Refund` ledger row linked to original `Purchase`, decrements shared family purchased balance → **BE-4**
- Reconciled against the immutable ledger as source of truth (not a mutable cached balance) → **BE-2** + **BE-4** (re-reconcile at settlement)
- Settled only via verified provider webhook (`refund.succeeded`); in-app request only initiates → **BE-3** (initiate-only) + **BE-4** (webhook-driven balance change)
- Parent-gated, owning-parent only; children can't request → **BE-3** + **BE-5** (parent-JWT-only `[Authorize]` + family-scope authz)
- Refundable balance + refund request exposed to parent UI → **BE-5** (`GET /Refunds/Quote`, `POST /Refunds/Request`)
- EN+AR error/reason keys → localized keys / `RefundReason` enum (no free text) → **BE-3** validator

## Notes

- **LEAD GATE (OQ-1):** confirm the refundable unit is **energy reconciled to currency at the original purchase price** (refund the monetary value proportional to unused purchased energy), and that partial refunds (unused remainder only) are the v1 behaviour — not all-or-nothing. Block BE-1/BE-2 on this.
- **OQ-2 (refund trigger):** in-app parent request (BE-3/BE-5) vs provider-dashboard-only. The locked model says parents request refunds → BE-3/BE-5 are in scope; confirm whether an admin-side refund action is also required (would reuse P10-09-BE-5).
- **OQ-3 (RESOLVED via P10-13):** purchased spend is identified by ledger rows that drew from the **shared family purchased row** (bucket B fallback), per the locked spend order (child allocation first → shared purchased fallback). The P10-13 ledger (`P10-13-BE-3`) tags each `Spend` row with `SourceBucket`, and the **P10-13-BE-12 pack-credit re-home** writes bucket-B `Purchase` rows against the shared reserve — so reconciliation is unambiguous. No further P10-13 flag needed.
- **OQ-4 (multi-pack accounting):** if a family bought several packs, confirm whether refund is per-`Purchase`-payment (FIFO consumption attribution) or against the aggregate shared purchased balance. Recommend: refund per original `Purchase` payment, refundable = that payment's purchased amount minus its attributable consumed share, capped at the current shared purchased balance. Confirm with lead before BE-2.
- **Supersedes P10-09 clawback semantics:** P10-09 clawed back unused credits from a single per-child `PurchasedBalance`; here the purchased balance is a **shared family reserve** and reconciliation is ledger-driven. Refine the existing branch — do not add a parallel one.
- No UoW (ADR 0001) — reconciliation + ledger append + balance decrement run in an **explicit transaction inside the service** (Infrastructure), never a handler. Negative-balance race is the primary correctness risk.
- `ValidationBehavior` runs for `ICommand<>` only — `RequestPurchasedEnergyRefundCommand` gets a FluentValidation validator; the quote query does not.
- Blocked by **P10-13** (two-bucket family ledger + shared purchased row + the **P10-13-BE-12 pack-credit re-home** that lands purchased packs as the shared family reserve + bucket-B `Purchase` ledger rows) and **P10-09** (refund/webhook seam being refined — the `WebhookEventService.HandleRefundSucceededAsync` Pack branch). **Canonical mapping: 13 wallet · 14 seats · 15 lifecycle · 16 redistribution · 17 refunds (this story).**
