## Acceptance-criteria coverage

- Plan defines INCLUDED seats (config) + max-seats ceiling; subscription tracks extra seats → **BE-1** (`IncludedSeats`/`PurchasedExtraSeats`) + **BE-3** (max-seats from config)
- Active seat count = `IncludedSeats + PurchasedExtraSeats` while billing-active (incl. grace) → drives P10-13 → **BE-3** (`GetActiveSeatCountAsync`)
- Parent views seat status (total/occupied/free + which children active) → **BE-9** (`GetSeatStatusQuery`)
- Only paid active seats generate entitlement energy; a child profile mints none → **BE-3** (count) consumed by P10-13 (no energy minted here)
- Buy N extra seats, monthly add-on, config price, web checkout only; **mid-cycle charge = `SeatPrice × remaining-cycle-ratio` (prorated money, computed server-side)** → **BE-6** (`StartSeatCheckoutCommand`, server-side price + proration)
- Seat purchase confirmed only via verified, idempotent provider webhook; ledgered; **child activated immediately on success**; failure adds nothing → **BE-7**
- Mid-cycle seat add **NEVER mints subscription energy**; no duplicate-grant guard; newly-seated child's mid-cycle energy comes from P10-16 allocation only; at renewal the seat counts normally in `ActiveSeats × PlanEnergyPerSeat` → **BE-7**
- Cancel extra seat → effective at **cycle end** (NOT instant, NOT grace-triggered); seat stays Active; child keeps remaining allowance; no energy reclaim/forfeit; no prorated refund; over-seat children move to NoSeat/Locked at renewal (P10-15) → **BE-8**
- Add-child reserves a seat FIRST via the Shared.Contracts seam; child activated immediately on seat reserved; no free seat → clean reject, no child created; compensation on failure; idempotent → **BE-4** (seam) + **BE-5** (handler wiring)
- Cross-module via Shared.Contracts only, loose int ids, no FK → **BE-4** (seam shape) + **BE-5** (Parent uses seam only)
- Seat reactivation mid-cycle: same rule as add — prorate MONEY, no energy mint, immediate activation → **BE-6** + **BE-7**
- 7-day grace = payment-failure retry window at renewal boundary only; voluntary cancels do NOT trigger grace → **BE-8** (no grace marker on cancel) + **BE-3** (active-count includes grace-window seats)

- **OQ-2 (free-plan seats):** recommend free/included-only plans still expose their included seats but **cannot** buy extra seats (gate in BE-6 against plan tier). Confirm with lead + P10-05.
- **OQ-3 (seam shape — coordinate with P10-13):** the `ISubscriptionSeatContract` reserve/release/check methods and `GetActiveSeatCountAsync` must align with how P10-13's grant job reads the active-seat count. Lock the seam with P10-13 before BE-4.
- **OQ-4 (`Payment.Kind=Seat`):** recommend reusing `Payment{Kind=Seat}` + an immutable seat-purchase ledger row — no new `SeatPurchase` table. Extend `PaymentKind` if `Seat` is absent (coordinate the migration with P10-06/07). The `Payment` entity must carry the **prorated amount** (not the full monthly price) for mid-cycle adds. Confirm.
- **OQ-5 (cycle-end cancel marker — lead-approved 2026-06-17):** BE-8 records a `CancelledAt`/`EffectiveAt=NextRenewalDate` marker. This is NOT a grace marker — it is a scheduled-removal marker. The P10-15 grace path is triggered only by payment failure at the renewal boundary, not by voluntary seat cancels. Coordinate the marker shape with P10-15.
- **Mid-cycle ADD/REACTIVATE = MONEY prorates, ENERGY does NOT mint (final, lead-approved 2026-06-17).** BE-6 computes and charges `SeatPrice × remaining-cycle-ratio` server-side. BE-7 activates the seat immediately on webhook success and appends the ledger row. BE-7 must NOT mint, grant, or deposit any subscription energy — no energy path at all. No duplicate-grant guard. The child's mid-cycle energy comes from the parent via P10-16.
- **Mid-cycle CANCEL = effective at CYCLE END, NOT instant, NOT grace-triggered (final, lead-approved 2026-06-17).** BE-8 marks the seat for end-of-cycle removal. It does NOT start a P10-15 grace window, does NOT reduce the active-seat count immediately, does NOT reclaim/forfeit any energy. The child retains the remaining energy allowance for the current period. Enforcement at renewal is P10-15.
- **7-day grace = payment-failure retry window at renewal boundary only.** Reconcile all "grace" wording here and in P10-15 to this definition. Grace does NOT strip mid-cycle energy.
- **No duplicate-grant guard.** Remove any earlier "duplicate grant guard" language from BE-7 or elsewhere — because no grant is issued at seat-add time, double-granting is impossible.
- **Module isolation (rule 1):** Parent must reference **only** `Shared.Contracts/Billing.ISubscriptionSeatContract` — never any `Billing.*` project. Seam interface in `Shared.Contracts`, impl in `Billing.Infrastructure` (mirrors `IBillingSubscriptionContract`/`ICreditSpendService`). No cross-module FK — `ChildId`/`parentUserId` are loose ints.
- **No UoW (ADR 0001):** seat reservation (free-seat check + reservation insert), the webhook seat increment (subscription update + ledger append + payment flip + activation), and the add-child reserve→create→activate flow are each atomic via **explicit transactions in the service**, never in a handler.
- **Localization (CONVENTIONS §10):** the no-free-seat rejection and all seat messages use `SharedResourcesKey.*` (AR+EN) — **no free-text string literals**; statuses are enums.
- **Security-sensitive:** money path (provider-verified webhook only; server-side price + proration; idempotent) **and** child-data path (seat reservation gates child creation). `security-auditor` gate before the review gate; never log card data / PII / secrets (`ILoggerManager` only).
- **`ValidationBehavior` runs for commands only** — `StartSeatCheckoutCommand` / `CancelExtraSeatCommand` get FluentValidation validators; the seat-status query is validated inside the handler.
- Blocked by **P10-05** (Plan/Subscription) and **P10-06** (payment seam + webhook + `WebhookEvent`). Builds on **P10-01** (ledger) and the **P10-07** webhook pattern. Reads **P10-12** config. Feeds **P10-13** (active-seat count). Requires **P10-16** for mid-cycle energy to newly-seated children. The **CreditAccount→FamilyEnergyAccount** ownership migration is **P10-13**, not here.
