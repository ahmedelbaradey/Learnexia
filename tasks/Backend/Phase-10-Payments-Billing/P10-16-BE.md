# P10-16 (Backend) — Family energy redistribution & mid-cycle energy mechanism

> Story: [../../../user-stories/Phase-10-Payments-Billing/P10-16-family-energy-redistribution.md](../../../user-stories/Phase-10-Payments-Billing/P10-16-family-energy-redistribution.md)
> Phase 10 — Payment, Billing & Credits · Epic: Payment, Billing & Credits · SP: 5 · FR-PAY-7 · Est. unit: hours
> **Security-sensitive — money + child data — `security-auditor` gate.** Family-energy-model wave (locked 2026-06-16; mid-cycle model finalized 2026-06-17).
> **Persistence = Option C service-only** (CONVENTIONS §7): Application EF-free; handler → service → repository → EF. No `DbSet`/`IQueryable`/`DbContext`/EF/repo in `Billing.Application`.
>
> **MID-CYCLE MECHANISM (2026-06-17):** Adding/reactivating a seat mid-cycle mints NO subscription energy (P10-14/P10-15 final model). A mid-cycle-activated child starts the cycle with zero allocation. P10-16 is the ONLY source of subscription energy for that child during the current cycle. The `TransferAllocationAsync` service method must therefore handle a destination child with zero allocation (no existing `ChildEnergyAllocation` row for the current cycle): it must INSERT a new row for the destination child rather than require one to pre-exist. This is a hard requirement, not an edge case.

## Notes

- **MID-CYCLE MECHANISM (FINAL MODEL 2026-06-17):** P10-16 is the ONLY source of subscription energy for a mid-cycle-added/reactivated child. The service MUST create the `ChildEnergyAllocation` row for the destination child if none exists for the current cycle. This is a mandatory behavior — do not gate it behind a flag or special path. The `isMidCycleNoGrant` flag on the DTO tells the FE to show explanatory copy; it does not change the transfer flow itself.
- **Two valid use cases, one command:** (a) parent rebalances between children who both have existing non-zero allocations; (b) parent gives energy to a just-activated mid-cycle child who has zero (or no) allocation. Both go through `TransferAllocationCommand` → `FamilyAllocationService.TransferAllocationAsync`. Do not special-case them.
- **Module ownership (HARD):** Billing owns `FamilyEnergyAccount`, allocation rows and the ledger; **Identity owns child profiles**. Children are referenced by **loose int id** — **no cross-module FK**. The same-family guard validates ownership via the Billing-owned `FamilyEnergyAccount → SeatReservation/allocation rows`, **not** by reaching into Identity. Active-seat validation also goes through the Billing-owned seat model (P10-14 `SeatReservation`), not Identity.
- **No bucket conversion, ever** — this command must not read or write the shared **purchased** reserve. Reviewer + security-auditor: confirm the spend-order rows (own allocation first → shared purchased fallback) are untouched.
- **Already-spent is immutable** — the cap is the live **remaining** allowance, not the original allocation. There is no code path that re-credits spent energy. The ledger never records reclaimed-spend.
- **Destination zero-allocation is valid, not an error.** A destination child with no current-cycle `ChildEnergyAllocation` row (mid-cycle add) must be served by INSERTing a new row — not by returning a "no allocation" error. The only rejection for the destination is "not an active-seat child."
- **Idempotency** — `TransferAllocationAsync` dedups on `IdempotencyKey` so a retried POST does not double-move. Pair this with the `CorrelationId` so the two ledger sides of one logical transfer are auditable as a unit. Idempotency also covers the row-creation case: a retried request on a destination that now has a row (from the first attempt) must not INSERT again.
- **Atomicity** — paired debit + credit + two ledger rows (+ potential destination row INSERT) commit together or not at all. No UoW; the **service** owns the explicit transaction at the Infrastructure boundary (CONVENTIONS §7 / ADR 0001) — never a handler.
- **Option C (CONVENTIONS §7):** `Billing.Application` stays EF-free; the handler injects `IFamilyAllocationService` only — no `DbContext`, no `DbSet`/`IQueryable`, no repository in the handler, EF exceptions translated inside Infrastructure.
- **Security-sensitive:** money movement + child data → `security-auditor` audits before the gate; the cross-family boundary, owning-parent authz, idempotency, and the "cannot move spent / cannot exceed remaining" guards are the critical checks. Critical/High findings block.
- **`ValidationBehavior` runs for commands only** — `TransferAllocationCommand` gets a validator (shape rules); the query is validated inside its handler.
- **Blocked by P10-13** (FamilyEnergyAccount + dual-bucket + ledger + **per-child allocation rows** + `CreditAccount→FamilyEnergyAccount` migration). Also aligns with P10-14 (seat model; active-seat check) and P10-15 (NoSeat/Locked definition; no forfeit mid-cycle). Coordinate migration ordering with the rest of the family-energy wave to avoid `billing` schema conflicts (serialize per PARALLELISM.md). **Canonical mapping: 13 wallet (+allocation) · 14 seats · 15 lifecycle · 16 redistribution/mid-cycle-mechanism (this story) · 17 refunds.**
