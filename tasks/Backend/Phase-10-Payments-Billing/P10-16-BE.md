## Acceptance-criteria coverage

- Move unspent allocated allowance between own children (zero-sum) → **BE-3** (`TransferAllocationAsync` decrement/increment) + **BE-5**
- Only UNSPENT allocated movable; already-spent never reclaimable; cap at source `Remaining` → **BE-3** (cap rule `amount > source.Remaining` reject) + **BE-2** (`Remaining = allocated − spent`)
- Family-only (same `FamilyEnergyAccount`); cross-family rejected (anti-abuse) → **BE-3** (same-family guard)
- Touches allocated bucket (A) only — never purchased (B), never converts buckets → **BE-3**
- Every movement in the immutable per-child ledger; paired entries with shared `CorrelationId` + idempotency → **BE-1** (ledger fields) + **BE-3** (paired append-only write)
- Atomic (both sides or none) → **BE-3** (single explicit transaction)
- Parent views per-child remaining (movable) split → **BE-4** (`GetFamilyAllocationQuery`)
- Parent-gated, owning-parent only, children can never transfer → **BE-6** (parent-JWT `[Authorize]` + family-scope) + **BE-5** (`parentUserId` from JWT)
- EN + AR messages → **BE-7**
- Parent-facing allocation editor → frontend (P10-16-FE)

## Notes

- **Module ownership (HARD):** Billing owns `FamilyEnergyAccount`, allocation rows and the ledger; **Identity owns child profiles**. Children are referenced by **loose int id** — **no cross-module FK**. The same-family guard validates ownership via the Billing-owned `FamilyEnergyAccount → allocation rows`, **not** by reaching into Identity. If parent→child ownership ever needs the Identity side, go through a `Shared.Contracts` seam (`IUserLookup`/family contract) — never a project reference.
- **No bucket conversion, ever** — this command must not read or write the shared **purchased** reserve. Reviewer + security-auditor: confirm the spend-order rows (own allocation first → shared purchased fallback) are untouched.
- **Already-spent is immutable** — the cap is the live **remaining** allowance, not the original allocation. There is no code path that re-credits spent energy. The ledger never records reclaimed-spend.
- **Idempotency** — `TransferAllocationAsync` dedups on `IdempotencyKey` so a retried POST does not double-move. Pair this with the `CorrelationId` so the two ledger sides of one logical transfer are auditable as a unit.
- **Atomicity** — paired debit + credit + two ledger rows commit together or not at all. No UoW; the **service** owns the explicit transaction at the Infrastructure boundary (CONVENTIONS §7 / ADR 0001) — never a handler.
- **Option C (CONVENTIONS §7):** `Billing.Application` stays EF-free; the handler injects `IFamilyAllocationService` only — no `DbContext`, no `DbSet`/`IQueryable`, no repository in the handler, EF exceptions translated inside Infrastructure.
- **Security-sensitive:** money movement + child data → `security-auditor` audits before the gate; the cross-family boundary, owning-parent authz, idempotency, and the "cannot move spent / cannot exceed remaining" guards are the critical checks. Critical/High findings block.
- **`ValidationBehavior` runs for commands only** — `TransferAllocationCommand` gets a validator (shape rules); the query is validated inside its handler.
- **Blocked by P10-13** (FamilyEnergyAccount + dual-bucket + ledger + **per-child allocation rows** + `CreditAccount→FamilyEnergyAccount` migration). Coordinate migration ordering with the rest of the family-energy wave to avoid `billing` schema conflicts (serialize per PARALLELISM.md). **Canonical mapping: 13 wallet (+allocation) · 14 seats · 15 lifecycle · 16 redistribution (this story) · 17 refunds.**
