## Acceptance-criteria coverage

- Per-child-per-day counter tracks energy used; cap from P9-11 config (Free 20 / Premium 150) → **BE-4**
- Soft semantics: cap reached → warning state + allows continuation (hard-stop OFF default); `HardStopEnabled` config → **BE-4, BE-5**
- Low-energy warning fires at threshold → `LowEnergy` flag in `EnergyStatusQuery` → **BE-4**
- Daily counter resets at child's local midnight (timezone-aware lazy reset); monthly pool untouched → **BE-2, BE-3**
- `BaseResponse<T>`/`Successed`; `ILoggerManager`; `ISystemClock` + timezone; reads P9-01 pool (no parallel balance); config from P9-11 → **BE-4, BE-5**

## Notes

- **Coordination with P9-01:** the `DailyUsed`/`DailyUsedDateLocal` columns live on `CreditAccount` (P9-01's entity). If both stories are dispatched in the same wave, fold BE-1 into P9-01's `InitialBilling` migration. Otherwise run as a separate additive migration.
- **Coordination with P9-03:** `IncrementDailyUsage` (BE-5) is called inside the same explicit transaction as the `TryDebitAsync` in P9-03-BE-3 — the increment and the ledger debit are atomic together (column approach per OQ-3).
- **No new pool:** `DailyUsed` is an informational counter, not a second balance. The monthly `GrantedBalance + PurchasedBalance` (P9-01) remains the authoritative ceiling.
- **P9-10 consumes `EnergyStatusQuery`** (BE-4) to render the energy meter + warning copy. P9-04 returns typed state; P9-10 owns the AR+EN copy — do not mix localized strings into BE-4's output.
- `WarningState.None` is the default; the child app only shows warnings when state is `DailyCapReached` or `LowEnergy`.
