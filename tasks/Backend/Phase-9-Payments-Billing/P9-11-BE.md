## Acceptance-criteria coverage

- Admin can edit all named config values; persisted in `BillingConfigVersion` → **BE-1, BE-3**
- Every change creates a new version + audit record (who/when/old→new) → **BE-3**
- Change takes effect next cycle/request; never retroactively re-charges past `Spend` rows (ledger is immutable) → **BE-2** (latest-effective-≤-now resolution) + effective-dated architecture (BE-1)
- Validation rejects negative costs, zero pack size, grant < daily cap → **BE-4**
- All endpoints admin-only (`[Authorize(adminPolicy)]`; 403 for non-admin) → **BE-3, BE-5, BE-6**
- `BaseResponse<T>`/`Successed`; `ILoggerManager`; `ValidationBehavior`; audit via P7 pattern → **BE-3, BE-6**
- `IBillingConfigReader` seam for P9-02/03/04 to consume config → **BE-2**

## Notes

- **Never-retroactive invariant (AC-3):** `BillingConfigVersion` rows are append-only (effective-dated); the current config is always the latest version with `EffectiveFromUtc <= now`. A new version replaces nothing — it just takes precedence for future reads. Past `Spend` ledger rows record the cost at action time and are immutable (P9-01 no-mutation rule). Config updates never touch the ledger.
- **Cross-module audit:** the `Moderation.AuditLog` write from P9-11 must go through a `Shared.Contracts/Moderation/IAuditLogWriter` seam — `Billing` must not reference the `Moderation` module's projects (rule 1).
- **P9-02/03/04 sequencing:** those stories build against the `IBillingConfigReader` seam with config defaults. When P9-11 is merged, the `BillingConfigReader` impl reads from the versioned store — no changes to P9-02/03/04 needed.
- **No payment secrets in config:** plan/pack *prices* are billing config, but payment-gateway API keys/secrets (P9-06) are **not** stored in `BillingConfigVersion` — they go in the secret store. Security-auditor will check.
