## Acceptance-criteria coverage

- Per-action cost read from **`IGlobalSettingsProvider`** (hint 1 / explain-mistake 3 / deep-explanation 5 / practice-generation 5), server-side — no `IBillingConfigReader` → **BE-1**
- Charge fires only after response produced and safety filter passes → **BE-3**
- Cache-hit charged same as live delivery (debit step is downstream of cache/LLM fork) → **BE-3** (no special-casing cache)
- No charge on refuse / error / insufficient → **BE-4** (teardown guard) + **BE-5** (explicit tests) + **BE-3** (debit is last step)
- Insufficient → graceful decline + cached canned response, never hard block → **BE-2**
- Atomic debit + delivery (no charge without delivery, debit-as-final-delivery-step) → **BE-3**
- MVP `IAiUsageBudget` daily-count gate removed → **BE-4**

## Notes

- **HARD BLOCKER: P3-01 + P3-04/05/06 must be merged before BE-2/BE-3/BE-4 can be dispatched.** P9-03 cannot be implemented until the AI Helper exists. Build P9-01, P9-04, and P9-11 in the interim.
- **Module isolation:** the `Ai` module consumes `ICreditSpendService` from `Shared.Contracts/Billing/` and `IGlobalSettingsProvider` from `Shared.Contracts/Platform/` only — **no reference to `Learnexia.Modules.Billing.*` projects** from any `Ai.*` project. Violation is a CONVENTIONS breach (rule 1). `IBillingConfigReader` is NOT used (superseded by `IGlobalSettingsProvider`).
- **Child id security:** the `childId` passed to `TryDebitAsync` must come from the authenticated session (JWT claim), never from a client-supplied request body or query param. Security-auditor will check this.
- **Idempotency key:** use the AI request/action id (a per-request GUID generated server-side); store it in the request context so the retry of the same HTTP call reuses the same key. Do not generate a new key on each retry.
- **No new migration:** P9-03 writes through P9-01's `CreditTransaction` (type `Spend`). Zero new tables.
