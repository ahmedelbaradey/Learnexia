## Acceptance-criteria coverage

- `GlobalSetting` store (key, value, type, `UpdatedBy`, `UpdatedAt`) holds all 17 managed keys; bootstrap defaults seeded → **BE-1, BE-2**
- Consumers read values **only through `IGlobalSettingsProvider`** typed getters → **BE-3** (interface shape) + consumer task-file updates
- Values cached in `IDistributedCache` (Redis) and invalidated on change — no stale read after admin update → **BE-4** (warm-up + invalidation in BE-5)
- Every change audited (who/when/old→new) via `IAuditLogWriter` → **BE-5**
- Managed keys cover credit economy + AI action costs + cache/review thresholds → **BE-1, BE-2**
- Changes take effect at next read (post-invalidation); never retroactive → **BE-5** (no ledger writes)
- Admin-only write surface → **BE-5, BE-8** (`[Authorize(AdminPolicy)]`)
- Key allowlist prevents arbitrary key injection → **BE-6** (validator)
- Bootstrap default used when key absent from DB → **BE-3, BE-4**
- Code/appsettings safe defaults for bootstrap (before DB row exists) → **BE-3** (`BootstrapDefaultGlobalSettingsProvider`)

- **Cross-key validation in BE-6:** the `credits.free_daily_cap ≤ credits.free_monthly` cross-key check requires loading the *other* key's current value from the DB (not from the command payload, since only one key is updated at a time). Read the current value of the related key inside the validator using a direct DB query (not through the cache, to avoid a stale read during a batch update).
- **No new Hangfire jobs:** P9-12 is not time-driven; it is request-driven (admin writes) and startup-driven (cache warm-up via `IHostedService`).
